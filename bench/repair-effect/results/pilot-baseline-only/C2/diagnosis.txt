── 서버 수정 방향 (claude / claude-sonnet-5) ──

⚠ 이 명세는 승인 지문이 일치하지만 실제 서버 실행 기록이 없습니다.
  --baseline-only 나 --no-dry-run 으로 저장하면 케이스가 한 번도 실행되지 않은 채 승인됩니다.
  입력값이 생성 시점의 자리값일 수 있어, 아래 제안은 명세 쪽 원인도 함께 받았습니다.

test-error-handling-success  (test_error_handling)
  원인 후보  명세는 정상 응답(isError:false)을 기대하지만, test_error_handling 도구는 진단 메모에 '이 도구는 테스트를 위해 의도적으로 오류를 반환한다'고 명시되어 있다. 즉 오류 응답이 도구의 정상 동작이며, 케이스의 기대값이 실제 도구 목적과 반대로 설정됐을 가능성이 크다.
  확인할 곳  케이스 test-error-handling-success 의 expected 필드 (test_error_handling 도구의 description 및 동작과 대조)
  근거       diagnostics[0]: expected=false, actual=true, notes=['This tool intentionally returns an error for testing']
  분류       명세 쪽 원인으로 봄

test-reconnection-success  (test_reconnection)
  원인 후보  test_reconnection 도구 설명에 '서버가 호출 도중 스트림을 끊고 클라이언트 재연결 후 결과를 전송한다(SEP-1699)'고 되어 있어, 재연결 왕복에 시간이 걸리는 것이 의도된 동작일 수 있다. 명세의 케이스 제한시간 10000ms가 이 재연결 시나리오를 감안하지 않고 자리값으로 설정됐을 가능성이 있다.
  확인할 곳  케이스 test-reconnection-success 의 timeout 설정값
  근거       tool description: 'Server will close the stream mid-call and send the result after client reconnects'; CASE_TIMEOUT at 10000ms; approvedAs 표시 없음(승인 시점 미실행)
  분류       명세 쪽 원인으로 봄

test-reconnection-success  (test_reconnection)
  원인 후보  반대로 서버가 재연결 이후 실제로 결과를 재전송하지 않는(SEP-1699 재연결 로직 미구현/버그) 서버 결함일 가능성도 배제할 수 없다. OPERATION_RESULT_UNAVAILABLE은 결과 자체가 끝내 도달하지 않았음을 시사한다.
  확인할 곳  test_reconnection 도구의 재연결 후 결과 재전송 로직
  근거       diagnostics: CASE_TIMEOUT + OPERATION_RESULT_UNAVAILABLE (assertion을 검사할 MCP 작업 결과 자체가 없음)
