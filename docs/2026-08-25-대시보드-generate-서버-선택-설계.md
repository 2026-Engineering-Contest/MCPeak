# 대시보드 Generate 서버 선택과 단계 재배치 설계 (2026-08-25)

상위 문서: `docs/2026-08-19-대시보드-설계.md`(아키텍처), `docs/2026-08-19-대시보드-UI-설계.md`
(이하 "UI 설계"), `docs/2026-08-25-대시보드-홈-실행-폼-설계.md`(이하 "홈 설계"). 이 문서는
UI 설계 §5-3 Generate 마법사의 단계 표를 대체한다. 홈 설계 §3 비범위 첫 항목("Generate
마법사 1단계에 서버 후보 목록을 붙이는 일")이 이 문서의 범위다. 다른 화면은 건드리지 않는다.

구현 계획은 별도 문서(`docs/plans/2026-08-25-대시보드-generate-서버-선택-구현계획.md`)로 만든다.
이 문서는 무엇을 만들지와 그 계약만 확정한다.

## 1. 배경

Generate 마법사 1단계는 실행 방법 세그먼트와 스크립트 경로 입력뿐이다. 홈은 이미
`GET /api/servers` 로 프로젝트의 `.mcp.json`·`package.json` 에서 서버 후보를 읽어 라디오
카드로 보여주는데(홈 설계 §5-2), Generate 는 같은 프로젝트에서 같은 서버를 대상으로 하면서
경로를 손으로 붙여넣게 한다. UI 설계 §1-2 "명령어를 몰라도 쓸 수 있어야 한다"를 Generate 가
가장 못 지키고 있다.

두 번째 문제는 속성 배치다. `--reset-cmd` 는 시험 실행(`--no-dry-run` 아님)에 종속인데
시험 실행 토글은 3단계, 초기화 명령은 4단계에 있다. 그래서 `GenerateWizard.patch()` 에
"시험 실행을 끄면 초기화 명령을 비운다"는 땜질이 들어갔다(PR #199). 종속 관계가 한 화면에
있으면 토글 옆에서 비활성 사유가 보이고 땜질이 필요 없다.

세 번째는 `mcpeak generate` 가 `--url`·`--header-env`(원격 HTTP 대상)를 받는데(#137)
마법사에 그 갈래가 없다는 점이다. 홈은 §5-4 로 노출했다. 같은 사람이 홈에서 HTTP 서버를
테스트하고 Generate 에서는 못 고르면 그 차이를 기능으로 읽는다.

## 2. 목표

1. 1단계에서 **서버를 고르기만** 하면 되게 한다. 홈과 같은 후보 목록(`ServerPicker`)이
   맨 위에 오고, 직접 입력은 마지막 갈래로 남는다.
2. 후보를 고르면 2단계의 저장 위치·스위트 ID·이름이 자동으로 차서 "다음, 다음, 다음, 생성
   시작"으로 끝난다. 사용자가 고친 값은 덮어쓰지 않는다.
3. 단계를 "무엇에 관한 속성인가"로 다시 묶는다: 서버 접속 / 산출물 / 케이스를 누가 만드나 /
   만든 케이스를 어떻게 검증하나.
4. `--url`·`--header-env` 를 1단계 접속 방식으로 노출하고, 대시보드 generate 배선에
   `connectHttp`·`readEnv` 를 넣는다.
5. **stdio 갈래의 argv 는 한 토큰도 바뀌지 않는다.** 지금 마법사로 만들던 명령은 재배치 뒤에도
   같은 순서로 나간다(`build-argv.test.ts` 의 기존 단언 전량 유지).

## 3. 비범위

- 마법사를 한 화면 폼으로 바꾸는 일. 4단계 구조와 스텝 인디케이터는 유지한다.
- 후보 갈래에서 서버 인자를 편집하는 일. 후보는 `package.json`·`.mcp.json` 의 선언이고,
  인자를 고치면 더 이상 그 선언이 아니다. 인자 편집은 직접 입력 갈래에서만 한다(§8).
- "지난 생성" 갈래. 홈의 `last-run` 은 스위트 경로별 저장인데 Generate 는 스위트가 아직
  없다. 최근 명령(`recentCommands`)의 datalist 로 충분하다.
- `.mcp.json` 항목의 `env`. 홈 설계 §3 과 같은 이유로 무시하고 후보 행에 적는다.
- 서버 후보 API·스캔 규칙 변경. `GET /api/servers` 는 그대로 쓴다(ADR-0079).
- `runner`·`cli`·`generate` 패키지 수정. 이 문서는 `packages/dashboard` 안에서 끝난다.

| 단계 재배치 | 3단계 "생성 방식" = mode/provider/model. 4단계 "검증과 확인" = dryRun/repair/resetCmd + 선택 요약 + CLI 명령 전문 |

## 5. 화면 사양

가운데 카드 800px, 상단 스텝 인디케이터, 하단 이전/다음은 UI 설계 §5-3 그대로다. 단계
이름은 `["테스트할 서버", "만들어질 스위트", "생성 방식", "검증과 확인"]` 이다.

### 5-1. 1단계 테스트할 서버

위에서 아래로 세 블록이다.

**접속** 세그먼트: `stdio (아래 서버 명령)` / `HTTP URL`. 기본 stdio. `TransportFields` 가
그린다. HTTP 를 고르면 그 아래로 URL 입력과 헤더 환경변수 칩(`<헤더이름>=<환경변수이름>`,
`추가` 버튼, Enter 로도 추가)이 펼쳐진다. 문구는 홈 §5-4 와 같다.

**서버** 목록: `ServerPicker`. 항목 순서는 스캔 후보(`GET /api/servers` 순서) 다음 `직접
입력`. 후보 카드의 이름·부제·출처 배지·`env` 안내는 홈 §5-2 와 같다. 후보가 0개면 홈과 같은
안내 상자(탐색 루트 포함)와 함께 직접 입력이 펼쳐진 채 시작한다. HTTP 를 골랐으면 목록이
비활성이고 힌트 `원격 서버에 붙습니다. 위 서버 명령은 쓰이지 않습니다.` 가 붙는다.

**직접 입력**: `choice.kind === "manual"` 일 때만 그 아래로 현재 `StepServer`(실행 방법
세그먼트, 서버 스크립트 + 최근 사용값, 서버 인자 칩, 실행될 명령 확인줄)가 펼쳐진다.
`idPrefix` 는 `generate`(현재 DOM id 유지). HTTP 면 비활성.

마운트 시 초기 선택: 후보가 있으면 첫 후보, 없으면 `manual`. `GET /api/servers` 실패는 빈
목록과 같게 다룬다(홈과 같은 정책).

다음 버튼 활성 조건: stdio 면 유효 명령이 비어 있지 않을 것(후보 갈래는 항상 참, 직접 입력은
`target` 비어 있지 않을 것). HTTP 면 URL 이 공백 아닌 문자열일 것. 비활성 사유 문구:
`서버를 고르거나 실행 명령을 입력하세요.` / `URL 을 입력하세요.`.

### 5-2. 2단계 만들어질 스위트

컨트롤은 지금과 같다(스위트 ID, 스위트 이름, 저장 위치, 덮어쓰기). 바뀌는 것은 기본값이다.

- 1단계에서 넘어올 때 저장 위치를 §6-3 규칙으로 제안한다. 제안값이 없으면(HTTP, 또는 직접
  입력에서 경로를 못 뽑음) 비워 둔다.
- 저장 위치가 바뀔 때마다 스위트 ID·이름을 `deriveSuiteName` 과 같은 규칙으로 다시 뽑는다.
  단, 그 필드가 "이전 제안값과 같거나 비어 있을 때"만이다. 사용자가 한 번이라도 다른 값을
  적었으면 그대로 둔다(§6-4).
- 저장 위치 힌트: `서버 스크립트 옆에 제안한 값입니다. 바꿔도 됩니다(.json 파일).`. 제안값이
  없을 때는 `원격 서버는 기준 경로가 없어 직접 적습니다(.json 파일).`.
- 스위트 ID·이름 힌트(제안값일 때만): `저장 위치의 파일명에서 뽑았습니다.`.

### 5-3. 3단계 생성 방식

`StepMode` 에서 시험 실행·자동 교정 토글을 뺀 것이다. 남는 것은 "AI가 테스트 케이스 작성"
/ "기본 골격만" 라디오 카드, AI 도구(claude/codex), 모델(선택). 문구·CLI 대응은 현재와 같다.

### 5-4. 4단계 검증과 확인

위에서 아래로:

1. 토글 `저장 전에 시험 실행으로 검증`(기본 켬), 토글 `실패한 입력값 자동 교정`(기본 켬).
   둘을 동시에 끌 수 없으므로 나중에 끄려는 쪽이 비활성이고 사유가 힌트로 붙는다(현재
   `StepMode` 의 로직 그대로 이동).
2. 입력 `시험 실행 전 초기화 명령 (선택)`. 시험 실행이 꺼져 있으면 비활성이고 힌트
   `시험 실행이 꺼져 있어 초기화 명령을 쓸 수 없습니다.`. 시험 실행을 끄는 순간 값을 비운다
   (현재 `patch()` 규칙 유지. 한 화면에 있어도 값이 남으면 `buildGenerateArgv` 가 throw 해
   시작 버튼이 막힌다).
3. 선택 요약 `dl`. 행은 `실행 명령`(HTTP 면 `원격 <url>` 과 헤더 개수), `스위트`, `저장 위치`,
   `생성 방식`, `시험 실행`, `자동 교정`, `초기화 명령`.
4. 실행될 CLI 명령 전문(`formatCliCommand`). `buildGenerateArgv` 가 throw 하면 그 문장을 대신
   보여주고 시작 버튼을 비활성한다.

## 6. 계약

### 6-1. Generate 상태 모델

```ts
type ServerChoice =
  | { readonly kind: "candidate"; readonly id: string }
  | { readonly kind: "manual" };
// `last-run` 은 홈 전용이다. ServerPicker 의 ServerChoice 타입은 그대로 두고 Generate 는
// 그 부분집합만 만든다. `lastRun: null` 을 넘기면 카드가 그려지지 않는다.

interface WizardState {
  readonly choice: ServerChoice;
  /** 후보 갈래의 유효 명령. manual 이면 쓰이지 않는다. */
  readonly candidateCommand: string;
  readonly candidateArgs: readonly string[];
  /** 직접 입력 갈래. */
  readonly method: CommandMethod;
  readonly target: string;
  readonly args: readonly string[];
  readonly transport: "stdio" | "http";
  readonly url: string;
  readonly headerEnvs: readonly string[];
  readonly suiteId: string;
  readonly suiteName: string;
  readonly outPath: string;
  /** §6-4. 제안값 추적. 사용자가 고친 필드는 다시 제안하지 않는다. */
  readonly suggested: { readonly outPath: string; readonly suiteId: string; readonly suiteName: string };
  readonly force: boolean;
  readonly mode: "ai" | "baseline";
  readonly provider: "claude" | "codex";
  readonly model: string;
  readonly dryRun: boolean;
  readonly repair: boolean;
  readonly resetCmd: string;
}
```

유효 명령·인자는 갈래별로 구한다(홈 §6-6 과 같은 규칙). `candidate` 는
`candidateCommand`·`candidateArgs`, `manual` 은 `splitCommand(method, target)` 의 `command` 와
`[...leadingArgs, ...args]`. 이 값이 `GenerateForm.command`·`args` 가 된다.

`ServerPicker` 는 라디오 `name` 을 `home-run-server` 로 고정하고 있다. 홈과 Generate 는 같은
문서에 동시에 그려지지 않지만 테스트에서 겹칠 수 있으므로 선택 prop `radioName?: string`
(기본값 `home-run-server`)을 더한다. 홈 쪽 호출은 바꾸지 않는다.

### 6-2. `buildGenerateArgv` 확장

`GenerateForm` 에 세 필드를 더한다.

```ts
export interface GenerateForm {
  readonly transport: "stdio" | "http";
  /** transport 가 http 일 때만 쓴다. */
  readonly url: string;
  /** `<헤더이름>=<환경변수이름>`. transport 가 http 일 때만 쓴다. */
  readonly headerEnvs: readonly string[];
  readonly command: string;
  readonly args: readonly string[];
  // 이하 기존 필드 그대로
}
```

거절 규칙(기존 규칙 뒤에 추가, 메시지는 `buildTestArgv` 와 같은 문장):

```ts
const http = form.transport === "http";
if (!http && form.command === "") throw new Error("서버를 고르거나 실행 명령을 입력하세요.");
if (http) {
  if (form.url.trim() === "") throw new Error("URL 을 입력하세요.");
  for (const entry of form.headerEnvs) {
    if (!isHeaderEnv(entry)) {
      throw new Error(`헤더 환경변수는 <헤더이름>=<환경변수이름> 형식이어야 합니다: '${entry}'`);
    }
  }
}
```

`isHeaderEnv` 는 `build-test-argv.ts` 의 것과 같은 판정(`=` 가 첫 글자가 아니고 우변이 비어
있지 않음)이며 한 곳에 두고 두 파일이 import 한다. 기존 필수 검사에서 `command` 를 뺀다
(위 규칙이 대신한다). `suiteId`·`suiteName`·`outPath` 필수 검사는 그대로다.

argv 순서. **stdio 는 지금과 동일**하다.

```ts
const argv: string[] = [];
if (http) {
  argv.push("--url", form.url.trim());
  for (const entry of form.headerEnvs) argv.push("--header-env", entry);
  // args 는 싣지 않는다. HTTP 로 바꿔도 직접 입력 값을 지우지 않으므로 여기서 걸러야
  // CLI 의 "`--arg` 는 `--url` 과 함께 쓸 수 없습니다" 에 닿지 않는다.
} else {
  argv.push("--command", form.command);
  for (const arg of form.args) argv.push("--arg", arg);
}
argv.push("--suite-id", form.suiteId);
argv.push("--name", form.suiteName);
argv.push("--out", form.outPath);
// 이하 --force, --baseline-only, --provider/--model, --no-dry-run, --no-repair, --reset-cmd 순서 그대로
```

### 6-3. 저장 위치 제안 규칙 `suggestOutPathFor`

```ts
/** 실행 파일 뒤의 첫 인자가 스크립트 파일이면 그 옆에 `.suite.json` 을 제안한다. */
const SCRIPT_EXT = /\.(?:[cm]?js|ts|py)$/i;

export function suggestOutPathFor(input: {
  readonly transport: "stdio" | "http";
  readonly args: readonly string[];
  /** 후보를 읽은 파일의 루트 상대경로(`ServerCandidate.path`). manual 이면 null. */
  readonly sourcePath: string | null;
  readonly candidateName: string | null;
}): string {
  if (input.transport === "http") return "";
  const script = input.args.find((arg) => SCRIPT_EXT.test(arg));
  if (script !== undefined) return script.replace(/\.[^./\\]+$/, "") + ".suite.json";
  if (input.sourcePath !== null && input.candidateName !== null) {
    const dir = input.sourcePath.includes("/") ? input.sourcePath.slice(0, input.sourcePath.lastIndexOf("/")) : "";
    return (dir === "" ? "" : `${dir}/`) + `${input.candidateName}.suite.json`;
  }
  return "";
}
```

근거. `package-bin` 후보의 `args[0]` 은 bin 스크립트의 루트 상대경로라 첫 규칙에 걸린다.
`.mcp.json` 의 `npx -y @scope/server` 같은 항목은 스크립트가 없어 두 번째 규칙으로 `.mcp.json`
이 있는 디렉터리에 `<이름>.suite.json` 을 둔다. 직접 입력은 `target` 이 `args` 선두로 오므로
현재 `suggestOutPath(target)` 과 같은 결과다(`custom` 은 `leadingArgs` 가 없어 빈 문자열,
지금도 제안하지 않는다).

### 6-4. 스위트 ID·이름 제안 규칙

CLI 의 `deriveSuiteName`(`packages/cli/src/generate-command.ts:364`)과 같은 규칙을 프론트에
둔다. `cli` 의 함수는 export 되지 않았고 web 은 `src` 를 import 하지 않으므로 복제하되, 주석에
원본 위치를 적고 테스트가 같은 입력·출력 표를 단언한다.

```ts
/** `--out` 파일명에서 `.suite.json` / `.json` 을 대소문자 무관하게 벗긴 것. 빈 문자열이면 제안 없음. */
export function deriveSuiteName(outPath: string): string {
  const base = outPath.split(/[/\\]/).pop() ?? "";
  const strip = (v: string, suffix: string) => (v.toLowerCase().endsWith(suffix) ? v.slice(0, -suffix.length) : v);
  return strip(strip(base, ".json"), ".suite");
}
```

제안 적용 규칙(`patch` 안에서 한 번에 처리):

```ts
// outPath 가 바뀌면 파생값을 다시 제안한다. 단, 필드가 이전 제안값과 같거나 비어 있을 때만.
const derived = deriveSuiteName(next.outPath);
const keepOrSuggest = (current: string, previousSuggestion: string) =>
  current === "" || current === previousSuggestion ? derived : current;
next = {
  ...next,
  suiteId: keepOrSuggest(next.suiteId, previous.suggested.suiteId),
  suiteName: keepOrSuggest(next.suiteName, previous.suggested.suiteName),
  suggested: { ...next.suggested, suiteId: derived, suiteName: derived },
};
```

저장 위치 제안도 같은 모양이다: 1단계에서 서버 선택·접속 방식이 바뀔 때 `outPath` 가 비어
있거나 `suggested.outPath` 와 같으면 `suggestOutPathFor` 결과로 바꾸고 `suggested.outPath`
를 갱신한다. 사용자가 고친 값은 서버를 바꿔도 유지된다.

## 8. 임의 판단 기록

- **후보 갈래의 인자는 편집 불가.** 홈 설계 §5-3 은 후보 인자를 칩으로 편집하게 했지만
  Generate 는 다르게 간다. 홈은 "이 서버를 어떻게든 띄워 테스트"가 목적이라 인자 조정이
  잦고, Generate 는 "이 선언에서 명세를 뽑는다"가 목적이라 선언과 다른 인자로 뽑은 명세는
  나중에 홈에서 같은 후보로 돌릴 때 어긋난다. 편집이 필요하면 직접 입력이 있다.
- **`--suite-id`·`--name` 을 argv 에서 생략하지 않는다.** CLI 가 `--out` 에서 뽑아 주므로
  생략해도 되지만, 그러면 4단계 요약과 CLI 명령 전문에 실제 값이 안 보인다. 프론트가 같은
  규칙으로 미리 뽑아 보여주고 명시적으로 보낸다. 규칙이 두 벌이 되는 비용은 §6-4 의 표
  테스트로 막는다.
- **`suggested` 추적으로 "사용자가 고쳤는가"를 판정한다.** 대안은 "한 번이라도 입력 이벤트가
  있었으면 고침"인데, 제안값을 지웠다가 다시 비워 둔 경우 영영 제안이 안 온다. 값 비교가 더
  단순하고 되돌릴 수 있다.
- **`TransportFields` 를 뽑는다.** 복제하면 홈과 Generate 의 문구·검증이 갈라진다. 같은
  패키지 안이라 뽑는 비용이 작다.
- **시험 실행을 끌 때 초기화 명령을 비우는 규칙은 유지한다.** 같은 화면에 왔어도 값이 남아
  있으면 시작 버튼이 막힌 채 이유를 찾아야 한다. 비우는 편이 복구 경로가 짧다.
- **UI 설계 §5-3 표의 4단계 "녹화와 확인"(카세트·재녹화)은 ADR-0059 로 이미 사라진
  항목이다.** 이 문서의 표가 그 표를 대체한다.
