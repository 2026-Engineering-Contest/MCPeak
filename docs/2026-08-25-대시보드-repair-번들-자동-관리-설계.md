# 대시보드 repair 번들 자동 관리 설계 (2026-08-25)

상위 문서: `docs/2026-08-25-대시보드-홈-실행-폼-설계.md`(이하 "홈 설계"),
`docs/2026-08-19-대시보드-UI-설계.md`. 결정 기록: ADR-0080. 이 문서는 홈 설계 §5-5 의
`Repair 번들` 칸과 §3 비범위 세 번째 항목("`RunSummary` 에 argv 를 남기지 않는다")을
덮어쓴다. 그 밖은 건드리지 않는다.

## 1. 배경

repair 를 쓰려면 사용자가 지금 이 순서를 밟아야 한다.

1. 실패를 보기 **전에** 홈 옵션에서 `Repair 번들` 경로를 적어 둔다.
2. 그 경로의 디렉터리를 손으로 만든다(CLI 가 `mkdir -p` 를 안 한다).
3. 실행이 실패하면 실행 뷰의 `repair 시작` 을 누르고 **같은 경로를 다시 친다.**

1 이 가장 큰 벽이다. 번들 옵션은 실패를 본 뒤에야 필요해지는데, 그때는 이미 번들 없이
돌았다. 대시보드는 run 의 argv 를 안 남기므로(`RunSummary` 는 `runId`·`flow`·`status`·
`exitCode` 뿐) 실행 뷰가 "이 run 에는 번들이 없다" 를 말하지 못하고, 실패한 run 마다
`repair 시작` 을 내민다.

근본 원인은 번들 경로를 사용자에게 묻는 것이다. JUnit 리포트는 CI 가 읽으니 경로가
사용자 몫이 맞다. 번들은 **대시보드 자신이** repair 에 넘기려고 만드는 내부 입력이다.
자기가 읽을 파일의 위치를 사용자에게 묻고 있었다.

## 2. 목표

1. 홈에서 시작한 test 실행이 실패하면 **번들이 이미 있다.** 사용자는 아무 옵션도 켜지
   않는다.
2. 실행 뷰의 `repair 시작` 폼에 번들 경로가 **채워져 있다.** 사용자는 provider·model 만
   고른다.
3. 번들이 있을 수 없는 run(번들 옵션 없이 시작된 run) 에서는 `repair 시작` 대신 **이유를
   말한다.**
4. `.mcpeak/` 산출물이 사용자 저장소에 커밋되지 않는다.

## 3. 비범위

- CLI 가 `--repair-bundle` 의 부모 디렉터리를 `mkdir -p` 하는 일. `packages/cli` 는 다른
  오너다. 대시보드가 자기 관리 경로만 직접 만든다. CLI 쪽은 제안으로 남긴다.
- 번들 파일이 **실제로 있는지** 서버가 확인하는 일. 실행 뷰는 argv 만 보고 "번들을 요청한
  run 인가" 를 판정한다. 실패했는데 파일이 없는 경우(연결 실패로 케이스가 하나도 안 돈
  경우 등)는 repair CLI 가 "번들을 읽을 수 없다" 로 말한다. 그 문장은 이미 제품 수준이다.
- 번들 없이 실패한 run 에서 "번들 켜서 다시 실행" 버튼. 이 설계로 홈 실행에는 항상 번들이
  있으므로 그 갈래는 외부 클라이언트가 POST 한 run 에서만 생긴다. 후속으로 둔다.
- 번들 보관 이력. 같은 스위트의 다음 실행이 덮어쓴다. repair 는 마지막 실패를 고치는
  것이라 그것으로 충분하다.
- Generate 마법사·RepairReview 화면.

## 4. 결정 요약

- **번들은 항상 켠다.** 홈의 test 실행 argv 에 `--repair-bundle <관리 경로>` 가 항상 붙는다.
  홈 설계 목표 4("기본값 폼의 argv 는 지금과 같다") 를 의도적으로 깬다. 조용한 변경이
  아니다. 미리보기에 항상 보인다(ADR-0080).
- **관리 경로는 프론트가 정한다.** 서버는 argv 를 손대지 않는다(`wiring.ts` 의 "가공 없이
  `runCli` 에 넘긴다" 유지). `buildTestArgv` 도 그대로다. `Home.tsx` 가 폼 값을 넣을 뿐이다.
- **관리 경로는 스위트 경로에서 결정론적으로 만든다.** `runId` 는 POST 응답에서야 오므로
  프론트가 미리 못 안다. 같은 스위트면 같은 파일이다.
- **`Repair 번들` 칸은 남긴다.** 비우면 관리 경로, 적으면 그 경로. CI 용으로 직접 지정할
  사람을 위해서다. 직접 적은 경로의 디렉터리는 사용자 몫이다(CLI 와 같은 의미).
- **서버가 `.mcpeak/repair/` 를 만든다.** test 실행을 시작할 때마다 `mkdir -p`. 함께
  `.mcpeak/.gitignore` 에 `*` 를 써서 어느 저장소에서든 커밋되지 않게 한다. 루트
  `.gitignore` 는 건드리지 않는다.
- **`RunSummary` 에 argv 를 남긴다.** 실행 뷰가 그 run 의 `--repair-bundle` 값을 읽어 repair
  폼을 채운다. 홈 설계 §3 의 비범위를 뒤집는 것이다. 메모리 안에서만 살고 재시작하면
  사라지는 것은 같다.

## 5. 화면 사양

### 5-1. 홈 옵션 패널의 `Repair 번들` 칸

- 라벨 `Repair 번들` 그대로. placeholder 는 그 스위트의 관리 경로 전문
  (예: `.mcpeak/repair/generated__weather.baseline.repair-bundle.json`).
- 설명 문장을 바꾼다. 기존 `실패를 Repair 화면에서 고칠 수 있게 묶어 둡니다.` 를
  `비우면 대시보드가 관리하는 경로에 만듭니다. 직접 적으면 그 경로에 만들고 디렉터리는
  있어야 합니다.` 로.
- 머리줄 요약의 `N개 바꿈` 은 그대로. 관리 경로는 폼 값이 `""` 이므로 "바꾼 것" 으로
  세지 않는다. 직접 적으면 1로 센다.

### 5-2. 실행될 명령 미리보기

`--repair-bundle .mcpeak/repair/...` 가 항상 보인다. 감추지 않는다. 사용자가 "왜 이게
붙지" 하고 옵션 패널을 열면 5-1 의 설명이 답한다.

### 5-3. 실행 뷰의 `repair 시작`

- run 의 argv 에 `--repair-bundle <p>` 가 있으면: 폼의 `repair 번들 경로` 칸이 `p` 로
  채워진 채 열린다. 칸은 편집 가능하게 둔다(직접 다른 번들을 가리킬 수 있다). 안내 문장은
  `이 실행이 만든 번들입니다. 다른 번들을 쓰려면 경로를 바꾸세요.`.
- argv 에 없으면: `repair 시작` 버튼을 그리지 않고 그 자리에 한 줄을 적는다.
  `이 실행은 repair 번들 없이 시작됐습니다. 홈에서 다시 실행하면 번들이 만들어집니다.`
- argv 를 아직 못 받았으면(스트림 오류 등): 버튼도 안내도 없다. 모르는 것은 모른다고
  둔다(#295 와 같은 원칙).

### 5-4. 통과한 run

CLI 가 `repair 번들: 실패한 케이스가 없어 파일을 만들지 않았습니다.` 를 stdout 에
찍는다. 대시보드 실행마다 이 줄이 하나 늘어난다. 그대로 둔다. 그 줄은 "왜 파일이
없는지" 를 말하는 CLI 의 실패 메시지이고, 대시보드가 그것을 지우면 CLI 로 같은 명령을 친
사람과 화면이 달라진다.

## 6. 계약

### 6-1. 관리 경로 (`web/src/repair-bundle-path.ts`, 신규)

```ts
/** 대시보드가 번들을 두는 디렉터리. 루트 기준 상대경로. 서버의 REPAIR_BUNDLE_DIR 와 같다. */
export const REPAIR_BUNDLE_DIR = ".mcpeak/repair";

/**
 * 스위트 경로 → 관리 번들 경로. 같은 스위트면 같은 값이다(결정론).
 * `/` 를 `__` 로 바꾸고 끝의 `.json` 을 떼어 `.repair-bundle.json` 을 붙인다.
 *   "generated/weather.baseline.json" → ".mcpeak/repair/generated__weather.baseline.repair-bundle.json"
 *   "suite.json"                       → ".mcpeak/repair/suite.repair-bundle.json"
 *   "a/b.suite"                        → ".mcpeak/repair/a__b.suite.repair-bundle.json"
 */
export function managedRepairBundlePath(suitePath: string): string;

/** 사용자가 적었으면(trim 후 비어 있지 않으면) 그것, 아니면 관리 경로. */
export function effectiveRepairBundlePath(suitePath: string, userPath: string): string;
```

`Home.tsx` 의 `argvResult` 는 `options` 를 그대로 넘기지 않고
`{ ...options, repairBundlePath: effectiveRepairBundlePath(suitePath, options.repairBundlePath) }`
를 넘긴다. `saveLastRun` 에는 원래 `options`(사용자 값) 를 저장한다. 관리 경로를 저장하면
다음에 "직접 적은 값" 으로 읽혀 `1개 바꿈` 이 된다.

### 6-2. `RunSummary` 확장 (`src/api-types.ts`)

```ts
export interface RunSummary {
  readonly runId: string;
  readonly flow: StartRunRequest["flow"];
  readonly status: RunStatus;
  readonly exitCode: number | null;
  /** 시작 요청의 argv 그대로. 실행 뷰가 --repair-bundle 값을 여기서 읽는다. */
  readonly argv: readonly string[];
}
```

`RunRegistry.start(flow, argv, execute)` 로 시그니처를 늘린다. `RunRecord` 가 argv 를
보관하고 `summary` 에 싣는다. `GET /api/runs` 와 `GET /api/runs/:id` 가 자연히 포함한다.

실행 뷰가 argv 에서 번들 경로를 읽는 규칙(`web/src/repair-bundle-path.ts`):

```ts
/**
 * argv 의 `--repair-bundle <p>` 또는 `--repair-bundle=<p>` 에서 p. 없으면 null.
 * 둘 다 있으면 CLI 가 거절했을 것이므로 첫 것만 본다.
 */
export function repairBundlePathOf(argv: readonly string[]): string | null;
```

### 6-3. 서버의 디렉터리 준비 (`src/server/files.ts`)

```ts
/** 프론트의 REPAIR_BUNDLE_DIR 와 같은 값. 두 곳에 있는 이유는 web 이 src 를 import 하지 않기 때문이다. */
export const REPAIR_BUNDLE_DIR = ".mcpeak/repair";

/**
 * `<root>/.mcpeak/repair/` 를 만들고 `<root>/.mcpeak/.gitignore` 가 없으면 `*\n` 을 쓴다.
 * 멱등이다. 실패는 던진다(호출부가 실행을 시작하지 않고 500 으로 옮긴다).
 */
export async function ensureRepairBundleDir(root: string): Promise<void>;
```

`routes.ts` 의 `handleStartRun` 은 `flow === "test"` 일 때 `registry.start` 앞에서 이것을
부른다. 다른 flow 는 부르지 않는다. 실패하면 `500 { error: ".mcpeak/repair 디렉터리를
만들지 못했습니다: <원인>" }` 이고 run 은 만들지 않는다.

`.mcpeak/.gitignore` 의 내용은 `*\n` 한 줄이다. 자기 자신도 무시되므로 어느 저장소든
`.mcpeak/` 아래가 추적되지 않는다. 이미 파일이 있으면 내용을 보지 않고 둔다(사용자가
고쳤을 수 있다).

### 6-4. 관리 경로의 문자 규칙

스위트 경로는 서버가 준 루트 기준 상대경로라 `..` 이 없고 `/` 구분이다. `/` → `__` 치환만
한다. 그 밖의 문자(공백, 한글, `.`)는 파일명에 그대로 둔다. 다른 스위트가 같은 관리 경로를
갖는 경우는 `__` 를 이름에 쓴 스위트뿐이며(`a/b.json` 과 `a__b.json`), 감수한다. 그 둘이
한 프로젝트에 같이 있을 가능성보다 경로를 해싱해 읽을 수 없게 만드는 비용이 크다.

## 8. 사용자에게 보이는 변화 요약

| 전 | 후 |
|---|---|
| 실패 전에 `Repair 번들` 경로를 적어야 번들이 생긴다 | 홈 실행은 항상 번들을 만든다 |
| `.mcpeak/` 을 손으로 만든다 | 서버가 만들고 `.gitignore` 도 쓴다 |
| `repair 시작` 폼에 경로를 다시 친다 | 채워져 있다 |
| 번들 없는 run 에도 `repair 시작` 이 뜬다 | 이유를 적은 한 줄로 바뀐다 |
| 미리보기가 `... --arg server.mjs` 로 끝난다 | `... --repair-bundle .mcpeak/repair/...` 가 붙는다 |
| 통과한 run 의 출력 끝 | `repair 번들: 실패한 케이스가 없어 파일을 만들지 않았습니다.` 한 줄 추가 |
