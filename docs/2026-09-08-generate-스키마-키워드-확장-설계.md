# generate 스키마 키워드 확장 설계 (2026-09-08)

- 이슈: #389 `[feat] 실제 MCP 스키마의 additionalProperties·참조·조합·pattern을 단계적으로 지원한다`
  https://github.com/2026-Engineering-Contest/MCPeak/issues/389
- 라벨: `pkg:generate` · `type:feat`
- 검토 기준 커밋: `d22aa91` (이슈가 가리키는 `c0a1934` 이후 `packages/generate` 변경 없음)
- 대상 패키지: `generate` 만. `runner`·`mock`·`cli` 는 읽기 전용이며 §7 에 경계를 적는다.
- 선행 ADR: ADR-0004(생성 범위) · ADR-0015(runner 의 해석 포기 규칙) · ADR-0036(툴 단위 부분 생성)
- 선행 설계: `docs/superpowers/specs/2026-08-17-schema-constraint-support-design.md`(이하 "제약 설계").
  그 문서 §2 가 `pattern`·`anyOf`·`$ref` 를 명시적으로 비범위로 남겼고, 이 문서가 그 자리를 채운다.
- 통합 이슈: 없음. #407(zod 예제 서버 E2E)·#387(상한 위반)·#404(README) 는 별건이며 §3 에 경계를 적는다.

## 1. 배경

### 1.1 지금 코드가 하는 일

`packages/generate/src/schema.ts:40` 의 `SUPPORTED_SCHEMA_KEYS` 에 없는 키가 하나라도 있으면
`validateSchema`(`schema.ts:177`)가 `UNSUPPORTED_SCHEMA` 를 던진다. `baseline.ts:111` 은 그 코드만
툴 단위로 격리해 `skippedTools` 에 싣고(ADR-0036), 전 툴이 건너뛰어지면 `baseline.ts:119` 에서
첫 원인을 들어 전체를 중단한다. 그래서 이슈의 재현 예처럼 툴 하나짜리 서버는
`additionalProperties: false` 한 줄로 생성이 0 이 된다.

값 합성은 `synthesize.ts:205` 의 `synthesizeValue` 가 한다. `const → default → examples[0] →
enum[0] → 타입별 규칙` 순이고, 마지막에 `valueMatchesSchema`(`synthesize.ts:161`)로 자기 제약을
다시 검사한다. 이 검사기는 `type`·`const`·`enum`·범위·`required`·`properties`·`items` 만 안다.

값 출처는 `provenance.ts:71` 의 `tallyField` 가 센다. 검증을 거치지 않은 `inputSchema` 도 받으므로
던지지 않고 끝나야 한다(`seen` 순환 방어).

위반 케이스(`violation-cases.ts:166`)는 `runner` 의 `deriveContractAxes` 가 준 축만 쓴다. 축은
`runner` 의 `analyzeInputSchema`(`packages/runner/src/input-schema.ts:92`)가 만든다.

### 1.2 실제 SDK 가 내는 스키마 (2026-09-08 실측)

저장소에 설치된 `@modelcontextprotocol/sdk@1.30.0` + `zod@4.4.3` 으로 `McpServer.registerTool`
을 거쳐 `tools/list` 를 받았다. 변환기는 SDK 안의 `zod-to-json-schema` 이고 출력은 **draft-07**
이다. Python 쪽은 로컬 pydantic v2 의 `model_json_schema()` 로 같은 형태를 뽑았다(MCP Python SDK
는 이 결과를 그대로 `inputSchema` 로 쓴다).

| 선언 | zod 4 + SDK 1.30.0 | pydantic v2 |
|---|---|---|
| `z.string().regex(/^[a-z-]+$/)` / `Field(pattern=…)` | `{ type: "string", pattern: "^[a-z-]+$" }` | 같음 |
| `z.string().uuid()` | `{ type: "string", format: "uuid", pattern: "^([0-9a-fA-F]{8}-…\|0000…\|ffff…)$" }` | 해당 없음 |
| `z.string().datetime()` | `format: "date-time"` 에 60자 넘는 `pattern` 동반 | 해당 없음 |
| `z.string().email()` | `format: "email"` 에 **전방탐색 `(?!\.)`** 이 든 `pattern` 동반 | 해당 없음 |
| `z.string().nullable()` / `Optional[str]` | `{ anyOf: [{ type: "string" }, { type: "null" }] }` | 같음. 기본값 있으면 `default: null` 동반 |
| `z.enum([...]).nullable()` | `{ anyOf: [{ type: "string", enum: [...] }, { type: "null" }] }` | |
| `z.union([z.string(), z.number()])` | `{ anyOf: [{ type: "string" }, { type: "number" }] }` | |
| `z.discriminatedUnion(...)` | `{ oneOf: [{ type: "object", … }, …] }` | |
| 중첩 모델 / 재귀 | `{ $ref: "#/definitions/__schema0" }` + 루트 `definitions` | `{ $ref: "#/$defs/Inner" }` + 루트 `$defs` |
| `.strict()` / `extra="forbid"` | 루트 또는 중첩 객체에 `additionalProperties: false` | 루트에 `additionalProperties: false` |
| `z.record(...)` | `{ type: "object", propertyNames: {...}, additionalProperties: { type: "number" } }` | |
| `z.tuple([...])` | `{ type: "array", items: [ {...}, {...} ] }` | |
| 모든 필드 | `$schema: "http://json-schema.org/draft-07/schema#"` 루트 1회 | 필드마다 `title` |

이슈 본문의 관찰과 다른 점 둘. (1) zod 는 `$defs` 가 아니라 draft-07 의 `definitions` 를 쓴다.
`$defs` 만 지원하면 zod 재귀 스키마는 그대로 막힌다. (2) `oneOf` 가 이슈에 없지만
`discriminatedUnion` 이 내므로 함께 다룬다. `propertyNames`·튜플 `items` 는 §3 비범위다.

`docs/adoption.md` §1.4.3 의 2026-08-17 실측도 같은 방향이다. `mcp-server-git` 이 루트 `anyOf`
(`[{ required: ["a"] }, { required: ["b", "c"] }]` 꼴)로 3툴을 잃었다. 이 꼴은 갈래에 `type`
이 없고 바깥 스키마와 **합쳐야** 뜻이 된다. §5.5 의 병합 규칙이 이것 때문에 필요하다.

### 1.3 이슈와 코드가 다른 곳

- 이슈는 "`$defs/$ref`" 라 썼으나 zod 는 `definitions` 다. 둘 다 받는다(§5.3).
- 이슈 대안 절의 "키워드를 무시하면 입력 계약을 바꾼다" 는 코드 관점에서도 맞다. `runner` 가
  `additionalProperties === false` 를 `rejectsUndeclared` 로 읽고 있어(`input-schema.ts:137`)
  무시하면 두 패키지의 해석이 갈린다. 이 문서는 어느 키워드도 무시하지 않는다.

## 2. 목표와 완료 조건

**목표.** `generate` 가 `additionalProperties`·`pattern`·로컬 `$ref`·`anyOf`/`oneOf` 를 읽고,
그 뜻을 지키는 입력값을 결정론적으로 합성한다. 못 읽는 갈래·구문은 그 갈래·그 툴만 건너뛰고
원인 경로를 남긴다. 기존 지원 툴의 출력 바이트와 지문은 바뀌지 않는다.

완료 조건. 각 항목이 구현 계획의 정확히 한 태스크 또는 통합 게이트에 대응한다.

1. 이슈 재현 예(`{ type: "object", properties: { x: { type: "string" } }, required: ["x"],
   additionalProperties: false }`)로 `createBaselineSuite` 가 성공하고 정상 케이스 입력이
   `{ x: "example" }` 이다.
2. `{ type: "string", pattern: "^[a-z-]+$" }` 의 합성값이 `"a"` 이고, `{ type: "string",
   minLength: 3, pattern: "^[a-z]+$" }` 의 합성값이 `"aaa"` 이다.
3. zod 의 `uuid`·`date-time`·`email` 출력(§1.2 의 `format` + `pattern` 동반)에서 합성값이 각각
   `FORMAT_VALUES` 의 값 그대로이고, 그 값이 동반 `pattern` 을 통과한다.
4. `{ anyOf: [{ type: "string" }, { type: "null" }] }` 의 합성값이 `"example"` 이고,
   `{ type: "object", properties: { a, b, c }, anyOf: [{ required: ["a"] }, { required: ["b", "c"] }] }`
   의 합성값이 `{ a: … }` 뿐이다.
5. §1.2 의 zod 재귀 스키마(`$ref: "#/definitions/__schema0"`, `kids` 선택)와 pydantic 스키마
   (`$ref: "#/$defs/Inner"`)에서 툴이 건너뛰어지지 않고 정상 케이스가 만들어진다. 같은 재귀가
   **필수** 경로에 있으면 `UNSUPPORTED_SCHEMA` 로 그 툴만 건너뛰고 경로와 참조 문자열이
   메시지에 있다.
6. `pattern` 에 전방탐색이 있고 알려진 `format` 도 후보값도 없으면 그 툴만 건너뛰며, 메시지에
   경로와 지원하지 않는 구문의 위치가 있다.
7. `pattern` 이 정규식으로 컴파일되지 않으면 `INVALID_SCHEMA_CONSTRAINT` 로 전체가 멈춘다.
8. 위 확장 뒤에도 `packages/generate/tests` 의 기존 케이스 중 "여전히 미지원 키워드" 자리를
   `pattern` 에서 `not` 으로 바꾼 것 말고는 수정 없이 통과한다. 새 키워드가 없는 툴의
   `baselineFingerprint` 는 확장 전과 같다.
9. `packages/generate/tests/fixtures/sdk-schemas/` 에 §1.2 실측 출력이 고정 파일로 있고, 그
   파일로 `createBaselineSuite` 를 돌려 `skippedTools` 가 비어 있음을 단언하는 테스트가 있다.
10. `pnpm build --force` · `pnpm test` · `pnpm typecheck --force`(`Cached: 0 cached`) ·
    `pnpm lint` 통과. `examples/` 대상 기존 E2E 통과.

## 3. 비범위

- `allOf` · `not` · `if`/`then`/`else` · `patternProperties` · `propertyNames` · `dependentRequired` ·
  `unevaluatedProperties` · `$dynamicRef`. 실측에 없거나(`allOf`) 우리 합성값에 영향이 없어도
  `runner` 가 차단하는 키워드다. `propertyNames`·`additionalProperties`(스키마 형태) 조합인
  `z.record` 는 다음 단계 후보로 §10 에 적는다.
- 배열 형태의 `type`(`["string", "null"]`). zod 4·pydantic 모두 `anyOf` 로 내므로 실측에 없다.
- 튜플 형태의 `items`(배열). `z.tuple` 이 내지만 실측 표본에서 한 번이고 별도 합성 규칙이 필요하다.
- 원격·상대 `$ref`(`http://…`, `other.json#/…`). 네트워크나 파일을 읽지 않는다.
- `additionalProperties: false` 위반(선언 밖 필드) 거절을 검증하는 **새 위반 축**. 축은 `runner`
  의 `ContractAxisKind` 라 다른 패키지 작업이다. 후속 이슈로 남긴다(§10).
- `runner`·`mock` 이 `anyOf`·`$ref` 필드를 해석하게 만드는 일. ADR-0015 의 결정이며 이 문서는
  그 결과(그 필드의 위반 축 없음)를 받아들인다(§7).
- `examples/zod-notes-server` 와 실서버 E2E. #407 이다. 이 문서는 고정 파일 회귀만 둔다.
- `BASELINE_POLICY_VERSION` 인상. 기존 지원 툴의 바이트가 안 바뀌므로 올리지 않는다. 올리면
  영향 없는 사용자까지 재승인한다. #387 이 자기 변경으로 올린다.
- generate README 의 지원 범위 전면 개정(#404). 이 문서는 틀린 한 문단만 고친다.

## 4. 결정 요약

| 항목 | 결정 | 기각한 대안 |
|---|---|---|
| 키워드 추가 | `SUPPORTED_SCHEMA_KEYS` 뒤에 `additionalProperties`, `pattern`, `$ref`, `$defs`, `definitions`, `anyOf`, `oneOf` 순으로 덧붙인다. 삽입 순서가 hint 문장이 된다 | 앞에 끼우기. `"description, title, $schema"` 단언이 깨진다 |
| `additionalProperties` | boolean 또는 스키마 객체를 받는다. 합성값은 선언된 `required` 만 넣으므로 어느 값이든 결과가 같다. 후보값(`const`·`default`·`examples`) 은 `false` 일 때 선언 밖 키가 있으면 후보 불만족으로 거절한다 | 무시. `runner` 와 해석이 갈린다(§1.3) |
| `pattern` | ECMA-262 부분집합을 파싱해 **최소 문자열**을 만든다. 알려진 `format` 값이 있으면 그것을 먼저 쓰고 `pattern` 으로 검증만 한다. 부분집합 밖 구문은 그 툴만 건너뛴다 | 후보값 있을 때만 허용. 이슈의 재현 예(`z.string().regex`)가 그대로 막힌다 |
| `$ref` | `#` 로 시작하는 JSON Pointer 만. 대상은 루트 스키마에서 찾는다. 형제 키워드는 대상과 병합한다(§5.5) | 형제 무시(draft-07 규칙). pydantic 이 `$ref` 옆에 `default` 를 붙이는데 그것을 버리면 후보 우선순위가 깨진다 |
| `anyOf` / `oneOf` | 선언 순서대로 갈래를 바깥 스키마와 병합해 첫 번째로 합성에 성공하는 갈래를 쓴다. `oneOf` 는 그 값이 정확히 한 갈래만 만족하는지 추가 검증한다 | null 갈래 회피 같은 선호 규칙. 근거 없는 매직 규칙이고 zod·pydantic 은 어차피 non-null 을 앞에 둔다 |
| 미지원 갈래 | 갈래 하나가 `UNSUPPORTED_SCHEMA` 면 다음 갈래로 간다. 전부 실패하면 첫 갈래의 원인으로 툴을 건너뛴다. `INVALID_SCHEMA_CONSTRAINT` 는 갈래에서도 즉시 전체 중단 | 갈래 하나라도 못 읽으면 툴 거절. `anyOf` 의 뜻(어느 하나) 에 어긋난다 |
| 순환 | 검증은 활성 경로에 있는 참조 대상을 다시 만나면 **조용히 멈춘다**(이미 위에서 검증 중). 합성은 필수 경로에서 다시 만나면 `UNSUPPORTED_SCHEMA` | 깊이 상한 숫자. 근거 없는 매직넘버이고 유한 스키마는 순환 탐지만으로 종료된다 |
| 값 출처 | `pattern` 이 있는 문자열은 `declared`. 조합은 합성이 고른 갈래의 출처를 물려받는다 | 새 출처 값 추가. `ValueProvenance` 는 `cli` 가 소비하는 공개 타입이라 이 PR 범위 밖 |
| 부분 생성 | 그대로 ADR-0036. 새 오류는 전부 `UNSUPPORTED_SCHEMA`(툴 단위) 또는 `INVALID_SCHEMA_CONSTRAINT`(전체 중단) 둘 중 하나로만 낸다 | 새 오류 코드. `cli` 가 코드로 분기하므로 늘리면 다른 패키지 작업이 된다 |

## 5. 키워드별 규칙

### 5.1 `additionalProperties`

- 값이 boolean 이거나 일반 객체면 받는다. 그 밖(문자열·null·배열)은 `UNSUPPORTED_SCHEMA`
  `${path}.additionalProperties`.
- 스키마 객체 형태의 값은 **검증하지 않는다.** 우리는 선언 밖 프로퍼티를 만들지 않으므로 그
  안의 키워드가 무엇이든 합성값이 달라지지 않는다. `description` 을 검증만 하고 쓰지 않는 것과
  같은 범주다.
- `valueMatchesSchema` 는 `additionalProperties === false` 인 객체 스키마에서 값의 키가
  `properties` 밖이면 불일치다. 후보값 검사에만 영향을 준다.
- `provenance` 는 영향 없음.

### 5.2 `pattern`

`assertConstraints`(`constraints.ts:60`)가 값을 검사한다. 문자열이 아니거나 정규식으로
컴파일되지 않으면 `INVALID_SCHEMA_CONSTRAINT` 다(제약 설계 §3.1 과 같은 계열: 선언이 깨졌다).
컴파일은 `new RegExp(pattern, "u")` 를 먼저 시도하고 `SyntaxError` 면 플래그 없이 다시
시도한다. 둘 다 실패해야 거절이다. 검증용 `RegExp` 는 같은 순서로 만든다.

문자열 합성 순서(`synthesizeValue` 의 `string` 분기). 앞 단계가 값을 내면 뒤로 가지 않는다.

1. `const` → `default` → `examples[0]` → `enum[0]` (종전과 같음). 그 값이 `pattern` 을 통과하지
   못하면 종전대로 "후보가 제약을 만족하지 않습니다" `UNSUPPORTED_SCHEMA`.
2. 표에 있는 `format` 이 있으면 그 값. **`pattern` 이 함께 있으면 그 값이 `pattern` 을
   통과할 때만** 쓴다. 통과하지 못하면 3 으로 간다. zod 의 `uuid`·`date-time`·`email` 은
   여기서 끝난다(§1.2 의 세 `pattern` 을 `FORMAT_VALUES` 의 값이 통과하는 것을 테스트로 고정).
3. `pattern` 이 있으면 §5.2.1 의 부분집합 생성기로 최소 문자열을 만든다. 그 뒤 `minLength`
   부족분은 §5.2.2 로 채운다.
4. `pattern` 이 없으면 종전 `boundedString`.

마지막 `valueMatchesSchema` 는 `pattern` 을 `RegExp#test` 로 다시 검사한다. 생성기가 만든
값이 여기서 떨어지면 그것은 생성기 결함이므로 `UNSUPPORTED_SCHEMA` 로 툴을 건너뛰되 메시지에
"생성기가 만든 값이 pattern 을 통과하지 못했습니다" 와 값을 싣는다. 조용히 다른 값을 쓰지 않는다.

#### 5.2.1 정규식 부분집합과 선택 규칙

`packages/generate/src/pattern.ts` 에 둔다. 파서는 아래 표만 안다. 표 밖 구문은 위치(오프셋)와
구문 이름을 든 `UNSUPPORTED_SCHEMA` 다. 선택은 전부 "첫 번째" 또는 "최소" 라 결정론적이다.

| 구문 | 만드는 것 |
|---|---|
| 리터럴 문자 | 그 문자 |
| `\d` `\D` `\w` `\W` `\s` `\S` | `0` `a` `a` `-` ` `(공백) `a` |
| `\n` `\r` `\t` `\f` `\v` `\0` | 해당 제어 문자 |
| `\xHH` `\uHHHH` `\u{H…}` | 그 코드 포인트 |
| 그 밖의 `\X`(예: `\.` `\-` `\/`) | 문자 `X` 그대로 |
| `.` | `a` |
| `[…]` | 적힌 순서로 첫 원소. 범위 `a-z` 는 시작 문자. 클래스 안의 `\d` 류는 위 표의 값 |
| `[^…]` | `a`…`z`, `A`…`Z`, `0`…`9`, `-`, `_`, 공백 순으로 집합에 없는 첫 문자. 없으면 미지원 |
| `(…)` `(?:…)` `(?<name>…)` | 안쪽을 그대로 |
| `a\|b` | 첫 갈래 |
| `*` `+` `?` `{n}` `{n,}` `{n,m}` 와 lazy 접미 `?` | 최소 횟수(`0` `1` `0` `n` `n` `n`) 만큼 반복 |
| `^` `$` `\b` `\B` | 빈 문자열 |
| `(?=…)` `(?!…)` `(?<=…)` `(?<!…)` | **미지원** |
| `\1` `\k<name>` | **미지원** |
| `\p{…}` `\P{…}` `\cX` | **미지원** |

빈 `pattern`(`""`)은 빈 문자열을 만든다. `^$` 도 같다.

#### 5.2.2 길이 제약과의 결합

최소 문자열이 `minLength` 보다 짧으면 **왼쪽부터 첫 번째로 만나는, 상한에 여유가 있는
수량자**의 반복 횟수를 늘려 부족분을 채운다. 그 수량자의 여유(`{n,m}` 이면 `m - n`, 상한 없으면
무한)를 다 써도 모자라면 다음 수량자로 넘어간다. 반복 단위가 여러 글자면 그만큼씩 는다.
채운 뒤 길이가 `maxLength` 를 넘거나, 모든 수량자를 써도 모자라면 `UNSUPPORTED_SCHEMA` 로 그
툴을 건너뛰고 메시지에 만든 값·길이·두 제약을 싣는다.

예. `^[a-z]+$` 와 `minLength: 3` → `+` 를 3회로 늘려 `"aaa"`. `^a-\d{2}$` 와 `minLength: 6`
→ 여유 있는 수량자가 없어 건너뜀.

### 5.3 `$ref` · `$defs` · `definitions`

- `$defs`·`definitions` 는 어느 깊이에서든 키로만 허용한다. 안의 스키마는 **참조될 때만**
  검증한다. 참조되지 않는 정의에 미지원 키워드가 있어도 합성값과 무관하다.
- `$ref` 값은 문자열이고 `#` 로 시작해야 한다. 그 밖은 `UNSUPPORTED_SCHEMA`(§6 문안 4).
- 포인터 해석: `#` 뒤를 `/` 로 나누고 각 조각에 `decodeURIComponent` → `~1`→`/` → `~0`→`~`
  순으로 되돌린다. 루트 스키마(툴의 `inputSchema`)에서 조각을 따라 내려간다. 배열이면 정수
  인덱스, 객체면 키다. 못 찾거나 결과가 일반 객체가 아니면 `UNSUPPORTED_SCHEMA`(문안 5).
  `#` 단독은 루트 자신이다.
- **루트를 따로 받아야 한다.** `validateSchema`·`synthesizeValue`·`valueMatchesSchema`·
  `tallyField` 에 `root` 인자를 더하고 기본값을 자기 자신으로 둔다. `render.ts` 는 지금도
  `tool.inputSchema` 를 넘기므로 호출부 변경이 없다. `violation-cases.ts` 의 `arrayOfLength`
  (`violation-cases.ts:93`)는 `items` 스키마만 넘기고 있어 `$ref` 가 든 원소를 만들 수 없다.
  `tool.inputSchema` 를 루트로 넘기도록 고친다.
- 형제 키워드(`$ref` 옆의 `default`·`title` 등)는 대상과 §5.5 로 병합한 뒤 그 결과를 검증·합성한다.
- 순환. 활성 집합에는 `$ref` 를 **해석한 대상 객체**를 넣는다(병합 결과는 매번 새 객체라
  동일성으로 잡을 수 없다).
  - 검증: 대상이 이미 활성이면 더 내려가지 않고 돌아온다. 그 대상은 스택 위에서 검증 중이다.
    선택 필드에 든 재귀(zod `kids`)가 여기 해당하며 툴은 살아남는다.
  - 합성: 대상이 이미 활성이면 `UNSUPPORTED_SCHEMA`(문안 6). 합성은 필수 경로만 따라가므로
    여기 도달한 순환은 유한한 값이 없는 순환이다.
  - 그 밖의 깊이·개수 상한은 두지 않는다. 스키마는 유한하고 활성 집합이 재방문을 막으므로
    종료가 보장된다. `anyOf` 갈래 시도가 중첩되면 시도 횟수가 갈래 수의 곱으로 늘 수 있으나
    실측 스키마에서 중첩 조합은 2단을 넘지 않았다. 문제가 되면 그때 상한을 근거와 함께 넣는다.

### 5.4 `anyOf` · `oneOf`

- 값은 비어 있지 않은 배열이고 원소는 전부 일반 객체여야 한다. 아니면 `UNSUPPORTED_SCHEMA`
  (`${path}.anyOf` 또는 `${path}.anyOf[i]`).
- 갈래 `i` 의 **유효 스키마** = 바깥 스키마에서 그 조합 키를 뺀 것과 갈래를 §5.5 로 병합한 것.
- 검증: 유효 스키마마다 `validateSchema` 를 돌린다. `UNSUPPORTED_SCHEMA` 는 갈래 단위로
  삼키고 다음 갈래로 간다. 하나라도 통과하면 통과다. 전부 실패하면 첫 갈래의 오류를 그대로
  던진다(경로가 `…anyOf[0]…` 로 남는다). `INVALID_SCHEMA_CONSTRAINT` 는 삼키지 않는다.
- 합성: 선언 순서대로 유효 스키마에 `synthesizeValue` 를 시도해 첫 성공값을 쓴다. 실패 조건은
  검증과 같다. `oneOf` 는 성공값이 **정확히 한 갈래의 유효 스키마만** 만족하는지
  `valueMatchesSchema` 로 세고, 아니면 다음 갈래로 간다. 어느 갈래도 안 되면 문안 8.
- `valueMatchesSchema`(후보값 검사): `anyOf` 는 어느 유효 스키마든 만족하면 참, `oneOf` 는
  정확히 하나면 참.
- 한 스키마에 여러 조합 키가 있으면 `$ref` → `anyOf` → `oneOf` 순으로 하나씩 푼다. 푼 결과에
  남은 조합 키는 재귀가 처리한다. 갈래 안의 조합 키도 같다.

### 5.5 병합 규칙 (공유 계약, 전량)

`packages/generate/src/composition.ts` 에 둔다. 두 스키마 `outer`(조합 키를 뺀 바깥)와
`inner`(갈래 또는 `$ref` 대상)를 AND 로 합친다. 한쪽에만 있는 키는 그대로 가져온다. 양쪽에
있으면 아래 표다. 표에 없는 키가 양쪽에 있고 JSON 값이 같으면 하나를 두고, 다르면 충돌이다.
충돌은 `UNSUPPORTED_SCHEMA` 이며 경로는 `${path}.anyOf[i].${key}` 또는 `${path}.$ref.${key}` 다.

| 키 | 양쪽에 있을 때 |
|---|---|
| `required` | 합집합. `outer` 순서 뒤에 `inner` 의 새 이름. 중복 제거 |
| `properties` | 이름 단위 합집합. **같은 이름이 양쪽에 있으면** 값이 JSON 으로 같을 때만 허용, 다르면 충돌 |
| `minimum` `exclusiveMinimum` `minItems` `minLength` | 큰 값 |
| `maximum` `exclusiveMaximum` `maxItems` `maxLength` | 작은 값 |
| `enum` | JSON 동등 기준 교집합, `outer` 순서. 비면 충돌 |
| `type` `const` `format` `pattern` `items` `additionalProperties` | 같으면 하나, 다르면 충돌 |
| `default` `examples` | 같으면 하나, 다르면 **`inner` 를 버리고 `outer`** (pydantic 이 `$ref` 옆에 붙인 `default` 는 `outer` 다) |
| `title` `description` `$schema` | `outer` |
| `$defs` `definitions` | `outer`(참조는 항상 루트에서 푼다) |
| `$ref` `anyOf` `oneOf` | `inner` 의 것을 남긴다(다음 재귀가 푼다). `outer` 의 것은 이미 풀린 키라 여기 오지 않는다 |

```ts
// packages/generate/src/composition.ts
/** 조합 키 하나를 푼 바깥 스키마와 갈래(또는 $ref 대상)를 AND 로 합친다. 충돌이면 UNSUPPORTED_SCHEMA. */
export function mergeSchemas(outer: JsonSchema, inner: JsonSchema, path: string): JsonSchema;

/** `#` 로 시작하는 JSON Pointer 를 루트에서 푼다. 실패는 전부 UNSUPPORTED_SCHEMA. */
export function resolveLocalRef(ref: unknown, root: JsonSchema, path: string): JsonSchema;

/**
 * 스키마가 조합 키를 갖는지. `$ref` → `anyOf` → `oneOf` 순으로 첫 것을 돌려준다.
 * 없으면 null. 세 호출자(validate · synthesize · provenance)가 같은 순서를 쓰게 하는 장치다.
 */
export function compositionKey(schema: JsonSchema): "$ref" | "anyOf" | "oneOf" | null;

/**
 * 조합 키 하나를 푼 유효 스키마 목록. `$ref` 면 1개, `anyOf`/`oneOf` 면 갈래 수만큼.
 * 병합 충돌은 그 갈래의 오류로 던지지 않고 목록에서 뺀다. 전부 빠지면 첫 충돌 오류를 던진다.
 */
export function expandComposition(
  schema: JsonSchema,
  root: JsonSchema,
  path: string,
): readonly { readonly schema: JsonSchema; readonly path: string; readonly target: object | null }[];
```

`target` 은 `$ref` 일 때 해석한 대상 객체이고 활성 집합 키로 쓴다. 갈래는 `null` 이다.

### 5.6 값 출처

- `pattern` 이 있는 `string` 은 `declared` 다. 범위 제약과 같은 근거(선언된 규칙을 따른 값)다.
  정규식이 만든 `"a"` 가 도메인 값으로 약할 수 있다는 점은 §10 에 남긴다.
- `$ref` 는 병합한 유효 스키마의 출처를 그대로 센다. 해석 실패는 `placeholder` 1.
- `anyOf`/`oneOf` 는 **합성이 고른 갈래**의 출처를 센다. 고르는 방법은 `synthesizeValue` 를
  갈래마다 시도하는 §5.4 와 같은 코드다(`provenance.ts` 가 `synthesize.ts` 를 import 한다.
  역방향 import 가 없으므로 순환이 아니다). 전 갈래 실패는 `placeholder` 1.
- `tallyField` 는 여전히 던지지 않는다. 위 시도에서 나온 `GenerateTestsError` 는 전부 삼킨다.

둘 중 하나다. 이 표가 사양이고, 구현이 문안을 다듬어도 **경로·값·해결 수단 세 가지는 빠지지
않는다.**

`"description, title, $schema"` 부분 문자열은 그대로 남는다(기존 단언).


| `runner` | `analyzeInputSchema` 는 필드에 `anyOf`·`$ref` 가 있으면 그 필드를, 루트에 있으면 툴 전체를 해석 포기한다(ADR-0015). `pattern`·`$defs`·`definitions`·`additionalProperties` 는 차단 목록에 없다 | 필드 `anyOf`: `REQUIRED_OMITTED` 축은 남고 `TYPE`·`ENUM`·`RANGE` 축은 없다. 루트 `anyOf`: 커버리지 `analyzable: false, unanalyzableReason: "anyOf"` 로 정상 케이스만 실린다. **이 문서는 이것을 바꾸지 않는다.** 정상 케이스가 0 이던 툴이 1 이 되는 것이 이번 목표다 |
| `mock` | `UNREADABLE_KEYWORDS` 에 `anyOf`·`$ref` 가 있어 그런 툴의 인자 검사를 건너뛴다 | 영향 없음. 목은 이 명세를 받아 실행할 뿐이다 |
| `cli` | `skippedTools` 의 `message`·`path` 를 그대로 찍는다(`generate-command.ts:1985`). `UNSUPPORTED_SCHEMA` 코드 문자열로만 분기한다 | 새 코드를 만들지 않으므로 변경 없음. 문안이 바뀌어도 `cli` 테스트는 자기 가짜 오류를 쓴다 |

`ContractAxisKind` 에 `UNDECLARED_FIELD` 축을 더해 `additionalProperties: false` 거절을
검증하는 일은 `runner` 변경이라 후속 이슈다(§10).

## 10. 미결과 후속

- **`pattern` 값의 도메인 약함.** `^[a-z]+$` 에서 `"a"` 는 규칙은 지키지만 실제 조회에는
  실패할 수 있다. 출처를 `declared` 로 두면 AI 사전보완이 이 필드를 덮어쓰지 못한다. 새 출처
  값(`patternDerived`)은 `cli` 가 소비하는 공개 타입 변경이라 이 PR 밖이다. dry run 실패
  분류에서 사후수리가 이어받는 현재 경로로 충분한지 실측 뒤 정한다.
- **`z.record`(`propertyNames` + 스키마형 `additionalProperties`).** 둘 다 우리 합성값에 영향이
  없어 허용해도 안전하다. 실측 표본에서 빈도를 본 뒤 다음 단계 이슈로 올린다.
- **`UNDECLARED_FIELD` 위반 축.** `runner` 의 `rejectsUndeclared` 는 이미 읽고 있다. 축과
  위반 케이스(선언 밖 키 하나 추가)를 넣으면 `additionalProperties: false` 서버의 거절 검증이
  생긴다. `runner` 오너 작업으로 이슈를 연다.
- **조합 시도 횟수 상한.** §5.3 의 이유로 두지 않았다. 중첩 조합이 3단 이상인 실제 스키마가
  나오면 그때 근거와 함께 넣는다.
- **`oneOf` 의 판정 기준.** 정확히 한 갈래 만족을 `valueMatchesSchema` 로 세는데, 이 검사기는
  우리가 아는 키워드만 본다. 갈래를 구분하는 키워드가 우리 밖(`patternProperties` 등)이면
  둘 다 만족으로 세어 다음 갈래로 넘어간다. 보수적인 쪽이라 오탐은 없고 건너뜀만 는다.
