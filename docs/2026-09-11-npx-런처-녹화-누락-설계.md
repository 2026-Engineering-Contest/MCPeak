# npx 로 띄운 서버의 녹화 0건을 없앤다 (2026-09-11)

관측: `docs/2026-09-11-공개서버-직접조작-데모-실측-문제.md` §2.
참조: ADR-0052(Coordinator 가 Engine 과 Session Store 를 소유한다),
ADR-0057(External 어댑터는 global fetch 까지만 가로챈다),
ADR-0062(되돌아온 URL 지문), ADR-0068(범위 밖 호출 관측), ADR-0094(녹화 완료 판정).

기준 커밋 `13c9ae9`.

## 1. 배경

### 1.1 지금 코드가 하는 일

Coordinator 는 자식에게 두 가지를 준다(`coordinator.ts:656`). 하나는 설정 환경변수 여섯 개이고,
다른 하나는 `NODE_OPTIONS` 에 얹은 `--import=<bootstrap.mjs>` 다.

```ts
const childEnvironment = Object.freeze({
  [ENV_MODE]: options.mode,
  [ENV_URL]: url,
  [ENV_TOKEN]: token,
  [ENV_ADAPTERS]: "node.fetch.v1",
  [ENV_SCHEMA]: String(PROTOCOL_SCHEMA_VERSION),
  [ENV_TIMEOUT]: String(timeout),
  ...(observer === undefined ? {} : { [ENV_OBSERVER_PATH]: observer.path }),
  NODE_OPTIONS: childNodeOptions(options.existingNodeOptions),
});
```

`bootstrap.mjs` 는 모듈이 로드되는 즉시 그 환경변수를 읽고 **지운다**(`bootstrap.mjs:23`).

```js
const values = Object.fromEntries(
  Object.entries(ENV_KEYS).map(([name, key]) => [name, process.env[key]]),
);
const observerPath = process.env[ENV_OBSERVER_PATH];
for (const key of Object.values(ENV_KEYS)) delete process.env[key];
// 손자 프로세스에 새지 않게 같이 지운다. 남으면 서버가 띄운 자식이 같은 파일에 덮어쓴다.
delete process.env[ENV_OBSERVER_PATH];
```

지우는 이유는 주석에 적혀 있다. 세션 하나에 기록하는 프로세스를 하나로 고정하려는 것이다.
그 보증이 결정론성의 뿌리다. 재생은 `(protocol, matchKey, occurrence)` 로 찾는데
(`engine.ts:121`), 두 프로세스가 같은 세션에 섞여 쓰면 `occurrence` 번호가 실행마다 달라진다.

### 1.2 실측과 재현

같은 서버를 두 형태로 띄웠다. 실측 문서 §2 의 표다.

| 실행 형태 | 녹화 |
|---|---|
| `node examples/live-weather-server/server.mjs` | 5건 |
| `node shim.mjs examples/live-weather-server/server.mjs` (npx 와 같은 구조) | 0건 |

2026-09-11 에 기준 커밋에서 최소 재현으로 다시 확인했다. 중간에 Node 프로세스 하나를 끼우고
손자가 무엇을 보는지만 찍었다.

```
--- 직접 실행 ---
TARGET sees MCPEAK_EXTERNAL_MODE = "record"
TARGET sees NODE_OPTIONS = undefined
--- shim(=npx 구조) 경유 ---
TARGET sees MCPEAK_EXTERNAL_MODE = undefined
TARGET sees NODE_OPTIONS = "--import=file:///.../packages/record/src/external/child/bootstrap.mjs"
```

### 1.3 진짜 문제는 닿지 못하는 것이 아니라 임자를 잘못 정하는 것이다

위 출력의 둘째 줄이 이 설계의 출발점이다. **`NODE_OPTIONS` 는 손자까지 살아서 간다.** 진짜
서버도 `bootstrap.mjs` 를 로드한다. 다만 설정 값이 중간에서 사라진 뒤라 `configured` 가
`false` 이고(`bootstrap.mjs:27`), 아무것도 설치하지 않고 조용히 지나간다.

그러므로 고칠 것은 "설정을 손자에게 어떻게 전달하는가" 가 아니다. 전달은 이미 되고 있다.
고칠 것은 **"체인에 있는 여러 Node 프로세스 중 누가 이 세션의 임자인가" 를 정하는 방법**이다.
지금 규칙은 "가장 먼저 뜬 Node 프로세스" 이고, `npx` 를 쓰면 그것이 서버가 아니라 런처다.

런처는 자기 몫의 일을 하고 진짜 서버를 자식으로 띄운다. 그래서 임자 자격을 프로세스가 뜨는
순서로 정하는 한 이 결함은 남는다.

### 1.4 그래서 화면이 틀린 원인을 말한다

녹화가 0건이면 CLI 가 이렇게 적는다(`test-command.ts:1992`).

```
알림: 이 실행에서 외부 호출이 하나도 녹화되지 않았습니다.
→ 서버가 외부 API를 호출했다면 지원 범위를 벗어났는지 확인하세요.
→ MCPeak은 서버가 `globalThis.fetch`로 부른 것만 잡습니다.
```

범위 안에 있는 서버인데 범위를 의심하라고 한다. 공개 서버의 표준 실행법이 전부
`npx -y <패키지>` 이고 대시보드 서버 등록 화면에도 `npx 패키지`가 일급 선택지로 있으므로,
사용자가 문서대로 등록하면 이 화면을 본다.

## 2. 목표와 완료 조건

**목표.** 중간에 Node 런처가 끼어도 진짜 서버의 외부 호출이 녹화된다. 그러면서 세션 하나에
기록하는 프로세스는 여전히 하나다.

| # | 완료 조건 | 판정 방법 |
|---|---|---|
| 1 | `node shim.mjs <서버>` 로 띄운 서버의 외부 호출이 녹화된다 | 신규 E2E. 직접 실행과 shim 경유의 `interactionCount` 가 같다 |
| 2 | 한 세션에 기록하는 프로세스는 하나다 | 신규 유닛. 두 번째 프로세스의 `/begin` 이 `WRITER_CONFLICT` 로 거절된다 |
| 3 | 기록자가 아닌 프로세스의 녹화 실패가 숫자로 남는다 | 요약의 `otherProcessCalls` 가 거절 건수와 같다 |
| 4 | 재생에서 기록자가 아닌 프로세스는 실제 네트워크로 나가지 않는다 | 신규 E2E. origin 서버의 호출 수가 0이다 |
| 5 | 0건 알림이 기록자 경합을 원인으로 지목할 수 있다 | CLI 유닛. `otherProcessCalls > 0` 갈래의 문장이 다르다 |
| 6 | 기존 녹화·재생 동작이 그대로다 | `pnpm test` 전량, `dist-external-e2e.mjs` |
| 7 | 빌드·테스트·타입체크·린트 | 통합 게이트 |

## 3. 비범위

- **`npx` 를 우리가 미리 실제 실행 파일로 해석하는 것.** §4.5 에서 기각한다.
- **범위 밖 호출 관측(`outOfScope`)의 런처 환경 정확도.** 관측 사이드카는 재생에서만 돌고
  이번 결함은 녹화가 막히는 것이라 원인 갈래가 다르다. §8.2 에 남은 갈래로 적고 후속 이슈로
  올린다. 이번 변경은 그 동작을 **그대로 둔다.**
- **대시보드 `npx 패키지` 선택지에 고지 붙이기.** 실측 문서가 차선책으로 적은 것인데, 근본을
  고치면 그 고지가 오히려 틀린 말이 된다. §4.4 에 적는다.
- **세션 저장 형식과 `matchKey` 규칙.** 한 글자도 바꾸지 않는다.
- 실측 문서의 §1 · §3 부터 §11 까지. 각각 별건이다.

## 4. 결정

### 4.1 결정 1: 설정 소비를 모듈 로드 시점에서 첫 가로챈 호출 시점으로 옮긴다

`bootstrap.mjs` 는 환경변수를 읽되 지우지 않는다. 지우는 일은 어댑터가 **실제로 가로챈 첫
`globalThis.fetch` 호출** 안에서 한다.

그러면 이렇게 된다.

| 프로세스 | 설정을 보는가 | 어댑터 | 소비 시점 |
|---|---|---|---|
| `npx` | 본다 | 설치된다 | 가로챈 호출이 없어 **소비하지 않는다** |
| 진짜 서버 (npx 의 자식) | **본다** | 설치된다 | 첫 호출에서 소비한다 |
| 서버가 첫 호출 뒤에 띄운 자식 | 못 본다 | 설치되지 않는다 | 해당 없음 |

런처는 `globalThis.fetch` 를 쓰지 않으므로 설정을 삼키지 않는다. npm 의 레지스트리 클라이언트는
`node:http` 계열이고 어댑터는 ADR-0057 대로 `globalThis.fetch` 까지만 본다. 이 전제는 §8.1 의
위험으로 적고 통합 게이트에서 실제 `npx` 로 확인한다.

남는 틈은 **서버가 자기 첫 호출보다 먼저 띄운 자식**이다. 그 자식은 설정을 물려받는다. 결정 2가
그 틈을 막는다.

### 4.2 결정 2: Coordinator 가 단일 기록자를 확정한다

각 자식 프로세스는 자기 식별자를 하나 만들어 모든 Coordinator 요청에 헤더로 싣는다.
Coordinator 는 **처음 도착한 식별자를 그 세션의 기록자로 고정**하고, 다른 식별자의 요청은
`WRITER_CONFLICT` 로 거절하며 그 수를 센다.

지금은 "프로세스가 하나뿐이니 안전하다" 였고, 바뀐 뒤에는 "여럿일 수 있지만 하나만 통과한다"
가 된다. 결정론성 보증의 세기는 같고, 보증하는 자리가 자식의 환경변수에서 부모의 상태로
옮겨간다. 부모에 두는 편이 낫다. 자식이 강제 종료되거나 환경을 만져도 보증이 깨지지 않는다.

거절당한 쪽의 처리는 모드마다 다르다.

| 모드 | 거절당한 프로세스가 하는 일 | 이유 |
|---|---|---|
| record | 원래 `fetch` 로 그대로 내보낸다. 녹화하지 않는다 | 지금도 그 호출은 녹화되지 않았다. 달라지는 것은 부모가 그 사실을 셀 수 있다는 것뿐이다. 던지면 진단 때문에 멀쩡한 서버를 죽인다 |
| replay | 던진다. 네트워크로 내보내지 않는다 | 재생의 계약은 "실제 네트워크는 호출하지 않았습니다" 다. 지금은 이 호출이 조용히 실제 네트워크로 나간다. 막는 쪽이 옳다 |

**식별자는 세션에 저장되지 않는다.** 와이어에만 산다. 저장되면 실행마다 다른 값이 녹화본에
들어가 재생 바이트가 달라진다.

### 4.3 결정 3: 기록하지 못한 호출 수를 요약에 싣는다

`RecordSessionSummary` 와 `ReplaySessionSummary` 에 `otherProcessCalls?: number` 를 더한다.
Coordinator 가 `finish()` 에서 얹는다.

`outOfScope` 와 의미가 다르다. `outOfScope` 의 `undefined` 는 "못 셌음" 이다. 자식이 보고
훅을 못 뛰면 알 길이 없기 때문이다. `otherProcessCalls` 는 **부모가 자기 거절을 직접 센 값**
이라 못 셀 일이 없다. 그래서 필드가 없으면 0이다. 선택 필드로 두는 것은 Store 가 이 값을
모르기 때문이고, 그 갈래는 `bodyUrls` 와 같다.

### 4.4 결정 4: 0건 알림에 기록자 경합 갈래를 더한다. npx 고지는 넣지 않는다

실측 문서의 차선책은 0건 메시지와 대시보드 `npx 패키지` 선택지에 "npx 를 거치면 잡히지
않습니다" 를 적는 것이었다. **근본을 고치면 그 문장이 틀린 말이 된다.** npx 를 거쳐도 잡히기
때문이다. 그래서 넣지 않고, 대시보드는 이번 변경에서 건드리지 않는다.

대신 고친 뒤에 실제로 남는 원인을 적는다. 기록자 경합이다.

`externalSessionNotice` 의 record 갈래를 둘로 나눈다(`test-command.ts:1989`).

**`interactionCount === 0` 이고 `otherProcessCalls > 0` 일 때 (신규)**

```
알림: 이 실행에서 외부 호출이 하나도 녹화되지 않았습니다.
→ 다른 프로세스가 먼저 이 세션의 기록을 시작해, 이 실행의 호출 N건을 녹화하지 않았습니다.
→ 서버가 외부 API를 자식 프로세스에서 부르면 먼저 시작한 쪽만 녹화됩니다.
```

`N` 은 `otherProcessCalls` 다. 숫자를 적는 이유는 사용자가 "조금 샜다" 와 "전부 샜다" 를
구분해야 하기 때문이다.

**`interactionCount === 0` 이고 `otherProcessCalls` 가 0이거나 없을 때 (기존 유지)**

```
알림: 이 실행에서 외부 호출이 하나도 녹화되지 않았습니다.
→ 서버가 외부 API를 호출했다면 지원 범위를 벗어났는지 확인하세요.
→ MCPeak은 서버가 `globalThis.fetch`로 부른 것만 잡습니다.
```

한 글자도 바꾸지 않는다. 이 갈래는 여전히 사실이다.

**`interactionCount > 0` 이고 `otherProcessCalls > 0` 일 때 (신규)**

```
알림: 이 실행의 외부 호출 N건이 다른 프로세스에서 나와 녹화되지 않았습니다.
→ 녹화본은 이 서버가 한 일의 일부만 담고 있습니다. 재생은 나머지를 막지 못합니다.
```

이 갈래가 없으면 부분 녹화가 초록으로 보인다. 기존 경고 갈래가 전부 `interactionCount > 0`
에서 아무 말도 하지 않기 때문이다. ADR-0068 이 `outOfScope` 를 만든 것과 같은 이유다.

### 4.5 버린 선택지

**(A) 런처 허용 목록.** `bootstrap.mjs` 가 `process.argv[1]` 을 보고 `npx-cli.js` ·
`npm-cli.js` · `pnpm.cjs` · `yarn.js` 면 설치도 소비도 건너뛴다. 가장 작다. 기각 이유는 목록
밖 런처에서 같은 결함이 그대로 재현되고, 그때 화면이 또 틀린 원인을 말한다는 것이다. 우리가
npm 내부 파일명에 의존하게 되는 것도 문제다. 결정 1은 목록을 쓰지 않고 같은 것을 얻는다.

**(B) `npx <패키지>` 를 우리가 실제 실행 파일 경로로 해석해 spawn 한다.** `record` 를 안
건드린다는 장점이 있다. 기각 이유는 `npx -y` 의 설치 기능, 버전 해석, 캐시 경로를 우리가 다시
구현해야 한다는 것이다. 그러고도 `pnpm dlx` · `uvx` 는 또 깨진다. 생태계 동작을 흉내 내는 코드는
우리가 유지할 수 없다.

**(C) 삭제만 없앤다.** 결정 1에서 결정 2를 뺀 것이다. 기각 이유는 단일 기록자 보증이 사라지는
것이다. 서버가 첫 호출 전에 띄운 자식이 같은 세션에 섞여 쓰면 `occurrence` 번호가 실행마다
달라진다. 결정론성이 이 저장소의 핵심 가치라 우연에 맡길 수 없다.

**(D) 문구만 고친다.** 실측 문서의 차선책이다. 오진은 막지만 녹화는 여전히 0건이고, 공개 서버
데모의 녹화·재생 장면 자체가 성립하지 않는다.

## 5. 계약 (전량)

### 5.1 기록자 식별자를 나르는 자리

`.ts` 와 `.mjs` 양쪽에서 써야 한다. `coordinator.ts` 가 읽고
`child/coordinator-client.mjs` 가 쓴다. `errors.mjs` 가 적어 둔 규칙대로 `.mjs` 정본에 두고
`.d.mts` 로 타입을 붙인다.

**신규 `packages/record/src/shared/writer.mjs`**

```js
/**
 * 기록자 식별자를 나르는 헤더.
 *
 * body 가 아니라 헤더인 이유는 `/begin` · `/complete` · `/lookup` 세 payload 의 형식을 건드리지
 * 않기 위해서다. 그 셋은 ADR-0052 의 마스킹 재검사를 지나는데, 거기에 실행마다 달라지는 값을
 * 넣으면 검사 대상과 저장 대상이 뒤섞인다. 식별자는 저장되지 않는 값이라 payload 밖에 둔다.
 */
export const WRITER_HEADER = "x-mcpeak-external-writer";
```

**신규 `packages/record/src/shared/writer.d.mts`**

```ts
export declare const WRITER_HEADER: "x-mcpeak-external-writer";
```

### 5.4 `child/fetch-adapter.mjs`

소비 시점과 거절 처리 두 곳이다. `installFetchAdapter` 본문을 아래로 바꾼다. `wire` 와 지문
계산은 손대지 않는다.

```js
export function installFetchAdapter(options) {
  if (globalThis[INSTALLATION] === true) return;
  const originalFetch = globalThis.fetch;
  if (typeof originalFetch !== "function") throw new Error("global fetch is unavailable");
  const client = createCoordinatorClient(options);

  /**
   * 설정 소비는 정확히 한 번이고, 첫 호출의 **동기 구간**에서 일어난다. `await` 뒤로 미루면
   * 그 사이에 서버가 띄운 자식이 설정을 물려받아 같은 세션에 끼어든다.
   */
  let consumed = false;
  const consumeOnce = () => {
    if (consumed) return;
    consumed = true;
    options.onFirstCall();
  };

  globalThis.fetch = async (input, init) => {
    const request = new Request(input, init);
    consumeOnce();
    const normalized = await normalizeHttpRequest(request);
    if (options.mode === "replay") {
      // 기록자가 아니면 여기서 `WRITER_CONFLICT` 로 던진다. **원래 fetch 로 넘기지 않는다** —
      // 재생의 계약은 실제 네트워크를 부르지 않는 것이고, 그 계약은 프로세스마다 달라지지
      // 않는다(설계 §4.2).
      const hit = await client.lookup(normalized);
      return restoreHttpOutcome(hit.outcome);
    }

    const requestPathname = new URL(request.url).pathname;
    const findings = bodyUrlFingerprints(
      normalized.display.body.kind === "json" ? normalized.display.body.value : null,
      requestPathname,
    );

    let reservation;
    try {
      reservation = await client.begin(normalized);
    } catch (error) {
      // **기록자 경합만 삼킨다.** 다른 오류는 그대로 올린다 — Coordinator 가 죽었거나
      // payload 가 상한을 넘은 것은 사용자가 알아야 하는 실패다.
      //
      // 이 호출은 녹화되지 않는다. 지금도 녹화되지 않았다(설정이 이 프로세스까지 오지 않았다).
      // 달라지는 것은 부모가 거절을 세어 화면에 적을 수 있다는 것뿐이다. 던져서 서버를 죽이는
      // 것은 진단을 위해 멀쩡한 실행을 깨는 것이라 하지 않는다.
      if (error?.code !== "WRITER_CONFLICT") throw error;
      return originalFetch.call(globalThis, request);
    }

    let response;
    try {
      response = await originalFetch.call(globalThis, request);
    } catch (error) {
      await client.complete(reservation.interactionId, encodeHttpThrow(error), wire(findings));
      throw error;
    }
    const outcome = await encodeHttpResponse(response.clone());
    await client.complete(
      reservation.interactionId,
      outcome,
      wire(findings, bodyUrlFingerprints(outcome.body, requestPathname)),
    );
    return response;
  };
  Object.defineProperty(globalThis, INSTALLATION, { value: true });
}
```

`consumeOnce()` 의 자리가 판단이다. `new Request(input, init)` 바로 뒤이며 첫 `await` 앞이다.
`new Request` 가 던지면(잘못된 URL 등) 소비하지 않는다. 그 호출은 어댑터를 지나지 않은 것이라
임자 자격의 근거가 되지 않는다.

| origin 서버가 받은 요청 수 | `2` |

같은 키로 녹화됐는지는 모른다. 재생이 그 키로 찾으므로 거기까지 봐야 판정이 끝난다.

`MCPEAK_EXTERNAL_MODE` 를 stderr 에 찍게 한다. 그 값이 `"record"` 이고, 그럼에도 케이스 1이
통과하는 것을 함께 본다. 런처가 설정을 보고도 삼키지 않는다는 것이 결정 1의 내용이다.

### 7.3 첫 호출 뒤에 태어난 자식은 빈손이다 (신규 E2E)

같은 파일. 픽스처 서버에 툴 하나를 더한다.

**`fetch-mcp-server.mjs` 에 더할 것.** `tools/list` 에 `spawn_and_dump` 를 더하고,
`tools/call` 에서 그 이름이 오면 `child_process.spawnSync(process.execPath, ["-p",
"JSON.stringify({mode: process.env.MCPEAK_EXTERNAL_MODE ?? null})"])` 의 stdout 을 그대로
돌려준다.

| 순서 | 단언 |
|---|---|
| `spawn_and_dump` 를 먼저 부른다 | 자식이 본 `mode` 가 `"record"` 다. 아직 소비 전이다 |
| `fetch_weather` 를 부른다 | `interactionCount === 1` |
| `spawn_and_dump` 를 다시 부른다 | 자식이 본 `mode` 가 `null` 이다. 소비됐다 |

이 셋이 §4.1 표의 세 줄을 그대로 판정한다.

## 8. 위험

### 8.1 `npx` 가 `globalThis.fetch` 를 쓰면 런처가 임자가 된다

결정 1은 "런처는 `globalThis.fetch` 를 쓰지 않는다" 에 기댄다. npm 의 레지스트리 클라이언트는
`make-fetch-happen` 계열이고 그 아래가 `node:http` 라 어댑터에 안 걸린다. 하지만 이것은 npm
내부 구현이고 우리가 고정할 수 없다.

**걸리면 어떻게 되나.** 런처가 레지스트리를 부르며 임자가 되고, 서버의 호출은 전부
`WRITER_CONFLICT` 로 거절된다. 결과는 오늘과 같은 녹화 0건인데, **다른 점은 화면이 이유를
안다는 것이다.** §4.4 의 첫 갈래가 `otherProcessCalls` 를 숫자로 적는다. 침묵이 진단으로
바뀌는 것이 이 설계가 최악의 경우에도 남기는 것이다.

**확인 방법.** 통합 게이트에서 실제 `npx -y @modelcontextprotocol/server-memory` 를 녹화로
한 번 돌려 `otherProcessCalls` 가 0인지 본다. 캐시가 있는 상태와 없는 상태
(`npm cache clean --force` 뒤) 두 번 돌린다. 레지스트리 호출은 캐시가 없을 때만 나가므로,
캐시가 찬 상태만 보면 이 위험을 놓친다.

### 8.2 범위 밖 호출 관측은 런처 환경에서 여전히 부정확하다

`ENV_OBSERVER_PATH` 는 지금처럼 로드 시점에 지운다(§5.2). 그래서 런처를 거치면 관측
사이드카가 런처 프로세스에 설치되고, 서버의 `node:http` 호출은 세어지지 않는 반면 런처 자신의
호출은 세어진다.

**이번 변경이 이것을 나쁘게 만들지는 않는다.** 오늘과 같다. 다만 오늘은 어댑터도 함께 죽어서
재생 자체가 성립하지 않았고, 고친 뒤에는 재생이 되면서 `outOfScope` 숫자만 틀린 상태가 된다.
숫자가 틀린 채로 초록이 나오는 것이 더 위험하므로 후속 이슈로 올린다. 제안하는 방향은 관측
보고를 프로세스마다 다른 파일로 나누고 Coordinator 가 합치는 것이다. 이번 설계에 넣지 않는
이유는 원인 갈래가 다르고(재생 전용), 넣으면 이 변경이 두 배가 되기 때문이다.

### 8.3 worker_threads

`--import` 는 worker thread 에도 적용되고 worker 는 자기 `globalThis` 를 가진다. 그래서 worker
안의 어댑터는 별도로 설치되고 별도 식별자를 만든다. 메인 스레드가 먼저 호출하면 worker 가
거절당한다. 오늘은 worker 가 아예 어댑터 없이 실제 네트워크로 나갔으므로 나빠지지 않고,
`otherProcessCalls` 로 보이게 된다. 테스트 대상으로 넣지는 않는다. MCP stdio 서버에서 흔한
모양이 아니다.

### 8.4 소비 시점을 놓치는 경로

어댑터를 지나지 않는 첫 호출은 소비를 일으키지 않는다. `new Request()` 가 던지는 경우가 그렇다.
그 프로세스는 다음 정상 호출에서 소비한다. 소비가 늦어지는 동안 태어난 자식이 설정을
물려받지만 결정 2가 막는다. 이 갈래에 테스트를 두지 않는 이유는 결정 2가 이미 그것을 덮고
있고, 덮지 못하는 경우가 없기 때문이다.
