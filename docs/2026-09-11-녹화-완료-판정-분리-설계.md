# 녹화 완료 판정을 테스트 판정에서 떼어낸다 (2026-09-11)

- 출처: `docs/2026-09-11-공개서버-직접조작-데모-실측-문제.md` §1 (블로커, 이슈 미등록)
- 우선순위: 실측 문서의 우선순위 표 2위. 1위(§2 `npx` 녹화 0건)와 파일이 겹치지 않아 독립이다.
- 기준 커밋: `8093660`
- 대상 패키지: `cli`(본체) · `dashboard`(문구) · `docs/adr`. `record` 는 읽기 전용이다.
- 선행 ADR: ADR-0052(Coordinator 수명주기) · ADR-0057(어댑터 범위) · ADR-0066(무엇을 했는가) ·
  ADR-0085(세션이 자기 출처를 담는다)
- 신설 ADR: ADR-0094

## 1. 배경

### 1.1 지금 코드가 하는 일

`packages/cli/src/test-command.ts:2082` 한 줄이 세션의 종료 상태를 테스트 판정에 묶어 둔다.

```ts
const summary = await wiring.finish(exitCode === 0 ? "completed" : "failed");
```

`exitCode` 는 `runCliCore` 가 돌려준 값이다. 케이스가 하나라도 실패하면 1이 되고, 그 실행의
세션은 `failed` 로 닫힌다.

재생은 그 상태를 정면으로 본다. `packages/record/src/external/engine.ts:107` 이
`source.status !== "completed"` 면 `REPLAY_SOURCE_INVALID` 를 던지고,
`packages/record/src/external/session-store-sqlite.ts:412` 의 `lookup` 이 같은 검사를 한 번 더
한다. CLI 는 그 코드를 `EXTERNAL_SESSION_FAILED` 로 옮겨 아래 문장을 낸다
(`test-command.ts:1763`).

```
오류 [EXTERNAL_SESSION_FAILED]: 녹화가 완료되지 않은 세션입니다: …
해결: 녹화 실행이 실패했을 수 있습니다. `--record-session` 으로 다시 녹화하세요.
```

대시보드도 같은 상태를 읽어 `녹화 실패` 로 칠하고 같은 뜻의 사유를 말한다
(`packages/dashboard/web/src/screens/ReplayView.tsx:39`, `:77`).

### 1.2 그래서 생기는 닫힌 고리

실측 문서 §1 이 기록한 것이 이것이다. 호출 3건을 DB 에 온전히 담고도 세션은 `failed` 이고,
화면은 "다시 녹화하세요" 라고 말한다. 다시 녹화해도 같은 케이스가 또 실패하므로 결과가 같다.

승인 게이트에서 `[s] 서버 결함` 으로 분류한 케이스는 **의도적으로 계속 실패하는 회귀 테스트**다.
그런 케이스를 가진 명세는 영원히 종료 코드 1이고, 따라서 그 서버의 녹화본은 영원히 만들 수 없다.

여기에 `SESSION_ALREADY_EXISTS`(`test-command.ts:1780`)가 겹친다. 같은 경로로 다시 녹화하려면
파일을 먼저 지워야 하므로, 사용자는 "버려진 녹화본을 지우고 또 버려질 녹화를 뜨는" 동작을
반복하게 된다.

### 1.3 상태가 실제로 뜻하는 것

`status` 세 값이 지금 뜻하는 바를 코드에서 확인했다.

| 값 | 세션 저장소가 붙이는 조건 |
|---|---|
| `running` | `begin` 이 열렸고 아직 `finish` 가 불리지 않았다 |
| `completed` | `finish("completed")` 이 불렸고 미완료 interaction 이 없다 |
| `failed` | `finish("failed")` 이 불렸거나, 미완료 interaction 이 남은 채 완료를 시도했거나, 마스킹 불변식 위반으로 Coordinator 가 즉시 닫았다 |

재생이 이 값을 보는 이유는 **반쪽짜리 녹화를 정상 원본으로 읽지 않기 위해서**다. 그 목적에
필요한 사실은 "어댑터와 Coordinator 가 끝까지 정상 동작했는가" 하나뿐이다. 테스트가 통과했는지는
녹화본의 완전성과 아무 관계가 없다. 녹화본이 담는 것은 서버가 외부에 무엇을 묻고 무엇을
받았는가이고, 그 값은 케이스가 실패해도 똑같이 참이다.

## 2. 목표와 완료 조건

**목표.** 녹화 세션의 종료 상태를 테스트 판정에서 떼어내고, 그 결과 달라지는 화면 문장을
사실에 맞춘다.

**완료 조건** (전부 검증 가능한 문장이다)

1. 실패 케이스가 있는 스위트를 `--record-session` 으로 녹화하면, 종료 코드가 0이 아니더라도
   세션 `status` 가 `completed` 이고 잡은 호출이 그대로 남는다.
2. 그 세션 파일을 `--session` 으로 재생하면 `REPLAY_SOURCE_INVALID` 가 나지 않고, origin 호출
   카운터가 움직이지 않는다. 재생 실행의 종료 코드는 여전히 0이 아니다(케이스가 실패하는 것은
   같다). 판정이 실패하는 것과 재생이 성립하는 것은 다른 축이다.
3. `runCliCore` 가 예외로 빠져나간 실행의 세션은 여전히 `failed` 다.
4. 미완료 interaction 이 남은 실행은 `INCOMPLETE_SESSION` 진단을 사람이 읽을 수 있는 형태로
   받고, 세션은 `failed` 로 남는다.
5. `externalSessionOutcome` 의 record 실패 갈래가 테스트 판정을 원인으로 지목하지 않는다.
6. `REPLAY_SOURCE_INVALID` 안내문과 대시보드 `녹화 실패` 사유가 실제 원인 둘(끊긴 녹화,
   끝내지 못한 호출)만 말한다.
7. `pnpm build --force` · `pnpm test` · `pnpm typecheck --force` · `pnpm lint` 가 전부 통과한다.

## 3. 비범위

- **세션에 테스트 판정을 함께 저장하는 것.** "이 녹화는 실패한 실행에서 떴다" 를 화면에
  보여주려면 `sessions` 테이블에 열을 더하고 스키마 버전을 올려야 한다. 이 결함을 푸는 데
  필요하지 않고, 스키마 버전을 올리면 기존 세션 파일이 전부 거절된다. 별건으로 남긴다.
- **`SESSION_ALREADY_EXISTS` 의 재녹화 흐름.** §1.2 에서 함께 아프지만 원인이 다르다.
- **실측 문서의 §2 · §3 · §4 · §5 · §6 · §7 · §8 · §9 · §11.** 각각 별도 설계 대상이다.
- **`record` 패키지의 상태 계약 변경.** 저장소가 지키는 불변식("완료된 세션에 미완료
  interaction 이 없다")은 그대로 둔다. 이 설계는 그 불변식을 **더 자주 만족시키는** 쪽이다.

## 4. 결정

### 4.1 종료 상태 규칙 (새 계약)

record 세션의 종료 상태는 **어댑터와 Coordinator 가 끝까지 정상 동작했는가**로만 정한다.
`runCli` 은 정상 반환 경로에서 언제나 `finish("completed")` 을 부른다.

| 실행이 끝난 방식 | `finish` 인자 | 최종 `status` | 사용자가 보는 것 |
|---|---|---|---|
| `runCliCore` 가 0을 반환 | `"completed"` | `completed` | `외부 호출 N건을 녹화했습니다` |
| `runCliCore` 가 0이 아닌 값을 반환 (케이스 실패, 명세 오류, 서버 기동 실패) | `"completed"` | `completed` | `외부 호출 N건을 녹화했습니다` + 기존 실패 리포트 |
| `runCliCore` 가 예외로 빠져나감 | `"failed"` | `failed` | 던진 예외가 그대로 올라간다(기존과 같다) |
| 미완료 interaction 이 남음 | `"completed"` | `failed` (저장소가 뒤집는다) | `INCOMPLETE_SESSION` 진단 + 종료 코드 1 |
| 마스킹 불변식 위반 (ADR-0052) | `"completed"` | `failed` (Coordinator 가 이미 닫았다) | `녹화가 완료되지 않았습니다` 갈래 |

네 번째 줄이 이 변경의 유일한 동작 변화다. 지금은 `exitCode !== 0` 이면 `finish("failed")` 이
불려 미완료 검사 자체를 건너뛰므로, 비-JSON 응답이나 1 MiB 초과 본문 때문에 끊긴 호출이
**조용히 묻힌다.** 앞으로는 그 실행에서 `INCOMPLETE_SESSION` 진단이 나온다. 그 진단은
`store-messages.ts:37` 이 이미 갖고 있고, 끊긴 호출의 메서드와 URL 을 최대 3건까지 보여준다.
진단이 늘어나는 것이지 실패가 늘어나는 것이 아니다. 그 실행은 원래도 종료 코드 1이었다.

### 4.2 종료 코드 규칙

`finish` 가 성공하면 `exitCode` 를 그대로 돌려준다(기존과 같다). `finish` 가 던지면 기존처럼
`externalCloseFailure` 를 찍고 1을 돌려준다. `exitCode` 가 0이었는데 녹화가 깨진 경우 1로
바뀌는 것이 맞다. 사용자는 재생 원본을 얻지 못했고, 그 사실이 종료 코드에 남아야 한다.

### 4.3 `status !== "completed"` 갈래를 남겨 두는 이유

`externalSessionOutcome` 의 record 실패 갈래는 지워지지 않는다. 4.1 표의 다섯째 줄이 그 갈래로
들어온다. 마스킹 불변식 위반은 Coordinator 가 `engine.finish("failed")` 로 세션을 먼저 닫고
(`coordinator.ts:614`), 이후 `finish("completed")` 은 `current !== "running"` 가드에 걸려
저장된 상태를 그대로 돌려준다(`session-store-sqlite.ts:425`). 그래서 요약의 `status` 가
`failed` 인 채 정상 반환된다. 갈래를 지우면 그 실행이 "녹화했습니다" 라고 거짓말한다.

바꾸는 것은 **그 갈래의 문장**이다. 지금 문장은 원인을 테스트 실패로 지목하는데, 새 규칙에서
그것은 원인이 아니다.

## 5. 문안 (전량)

이 프로젝트에서 실패 메시지는 곧 제품이다. 아래 표가 정본이고, 구현은 이 문자열을 그대로 쓴다.

### 5.1 `externalSessionOutcome` record + `status !== "completed"`

`packages/cli/src/test-command.ts:1899`

기존:

```
→ 이 실행이 실패해 녹화를 완료하지 않았습니다: {path}
  외부 호출 {N}건을 잡았지만 재생 원본으로 쓸 수 없습니다.
→ 실패 원인을 고친 뒤 다시 녹화하세요.
```

새로:

```
→ 녹화가 완료되지 않은 채 닫혔습니다: {path}
  외부 호출 {N}건을 잡았지만 재생 원본으로 쓸 수 없습니다.
→ 테스트 판정과는 무관합니다. 녹화 자체가 도중에 중단됐습니다.
→ 위에 나온 원인을 고친 뒤 다시 녹화하세요.
```

셋째 줄이 새로 들어간다. 이 갈래에 닿는 사용자는 바로 앞에서 마스킹 불변식 위반 진단을 이미
받았고, 그럼에도 "실행이 실패해서" 라고 읽으면 엉뚱한 곳을 고친다.

### 5.2 `externalOpenFailure` 의 `REPLAY_SOURCE_INVALID`

`packages/cli/src/test-command.ts:1763`

기존 `hint`: `녹화 실행이 실패했을 수 있습니다. \`--record-session\` 으로 다시 녹화하세요.`

새 `hint`:

```
녹화가 도중에 끊겼거나, 지원하지 않는 응답(비-JSON·redirect)을 만나 호출을 끝내지 못한 세션입니다. `--record-session` 으로 다시 녹화하세요.
```

`message` 는 `녹화가 완료되지 않은 세션입니다: {path}` 그대로 둔다. 그 문장은 지금도 참이다.

### 5.3 `externalCloseFailure` 의 `INCOMPLETE_SESSION`

`packages/cli/src/test-command.ts:1809`

기존은 코드와 무관하게 `message` 가 `External 세션을 닫지 못했습니다.` 하나였다. 갈래를 나눈다.

| `code` | `message` | `hint` |
|---|---|---|
| `INCOMPLETE_SESSION` | `녹화를 완료하지 못했습니다. 끝나지 않은 외부 호출이 남았습니다.` | record 원문 그대로(이스케이프하지 않는다) |
| 그 밖 | `External 세션을 닫지 못했습니다.` | `escapeTerminalText(detail)` |

`INCOMPLETE_SESSION` 원문을 이스케이프하지 않는 기존 규칙은 유지한다. 그 원문은 여러 줄짜리
구조를 가졌고 `display` 는 ADR-0053 이 마스킹을 보장한다.

4.1 표의 네 번째 줄이 이 문장에 닿는 유일한 경로이므로, 여기서 "테스트가 실패해서" 로 읽힐
여지를 남기지 않는 것이 중요하다.

### 5.4 대시보드 `ReplayView`

`packages/dashboard/web/src/screens/ReplayView.tsx:77` 의 `STATUS_REASON`

| `status` | 기존 | 새로 |
|---|---|---|
| `running` | `녹화가 끝나지 않은 세션입니다. 다시 녹화하세요.` | 그대로 |
| `failed` | `녹화 실행이 실패한 세션입니다. 다시 녹화하세요.` | `녹화가 도중에 끊겼거나 지원하지 않는 응답 때문에 완료되지 않은 세션입니다. 다시 녹화하세요.` |

`STATUS_LABEL` 의 `failed: "녹화 실패"` 는 그대로 둔다. 라벨은 상태의 이름이고, 새 규칙에서도
그 세션은 실패한 녹화가 맞다. 바뀐 것은 원인이지 이름이 아니다.

화면과 터미널이 같은 뜻이어야 한다는 `ReplayView.tsx:72` 주석의 계약은 5.2 의 새 `hint` 와
맞물린다. 둘을 함께 고친다.

## 7. 테스트 사양

### 7.1 `runCli` 이 무엇으로 닫는가 (신규 유닛)

`packages/cli/tests/external-session-finish.test.ts`

`../src/external-wiring.js` 를 `vi.mock` 으로 갈아 `finish` 에 들어온 인자를 잡는다. 실제
Coordinator 도 SQLite 도 뜨지 않으므로 빠르고 결정론적이다. `runCliCore` 는 없는 스위트 파일을
받아 0이 아닌 값으로 끝난다.

```ts
const finished: string[] = [];
vi.mock("../src/external-wiring.js", async (importOriginal) => ({
  ...(await importOriginal<typeof import("../src/external-wiring.js")>()),
  startExternalWiring: async () => ({
    env: {},
    finish: async (status: string) => {
      finished.push(status);
      return { mode: "record", sessionId: "default", status: "completed",
               interactionCount: 0, consumedCount: 0, unusedCount: 0 };
    },
  }),
}));
```

케이스와 단언은 다음 셋이다.

| 케이스 이름 | 단언 |
|---|---|
| `실패한 실행도 녹화는 완료로 닫는다` | `exitCode !== 0` 이고 `finished` 가 `["completed"]` |
| `성공한 실행도 완료로 닫는다` | `finished` 가 `["completed"]` |
| `예외로 끝난 실행은 실패로 닫는다` | `runCliCore` 가 던지도록 만든 뒤 `finished` 가 `["failed"]` 이고 예외가 그대로 올라온다 |

셋째 케이스의 예외 주입은 `dependencies` 의 `writeStdout` 이 던지게 만드는 것으로 한다.
`runCli` 의 `catch` 는 `runCliCore` 가 던진 모든 것을 잡으므로 원인이 무엇이든 경로는 같다.

### 7.2 실패한 실행의 녹화본이 재생된다 (신규 E2E)

`packages/cli/tests/external-session-e2e.test.ts` 에 `describe` 하나를 더한다. 실측 문서 §1 이
기록한 순환을 그대로 재현하는 자리이므로, 이 테스트가 이 작업의 본체다.

새 픽스처 `packages/cli/tests/fixtures/external-fetch-failing.suite.json` 은 기존
`external-fetch.suite.json` 과 같은 툴·같은 입력을 쓰되 단언만 뒤집는다. 외부 호출은 정상으로
나가고 판정만 실패한다.

```json
{
  "schemaVersion": 1,
  "id": "external-fetch-failing",
  "name": "외부 호출은 나가지만 단언이 실패하는 스위트",
  "defaultTimeoutMs": 10000,
  "cases": [
    {
      "id": "seoul-weather-fails",
      "name": "서울 날씨를 가져오지만 오류를 기대해 실패한다",
      "operation": {
        "type": "callTool",
        "tool": "fetch_weather",
        "input": { "city": "seoul" }
      },
      "assertions": [{ "type": "isError", "expected": true }]
    }
  ]
}
```

단언 전량:

```ts
it("케이스가 실패한 실행의 녹화본도 재생 원본으로 쓸 수 있다", async () => {
  const origin = await startOrigin();
  const sessionPath = await newSessionPath();

  const recorded = await captureStderr(() =>
    runWith(server, failingSuite, ["--record-session", sessionPath], origin.url("/weather")),
  );

  // 판정은 실패한다. 그것이 이 시나리오의 전제다.
  expect(recorded.exitCode).not.toBe(0);
  expect(origin.calls()).toBe(1);
  // 실측 문서 §1 이 기록한 문장이 더는 나오지 않는다.
  expect(recorded.stderr).not.toContain("녹화를 완료하지");
  expect(recorded.stderr).not.toContain("재생 원본으로 쓸 수 없습니다");
  // 무엇을 했는지는 그대로 말한다(ADR-0066).
  expect(recorded.stderr).toContain("외부 호출 1건을 녹화했습니다");

  const replayed = await captureStderr(() =>
    runWith(server, failingSuite, ["--session", sessionPath], origin.url("/weather")),
  );

  // 판정은 여전히 실패한다. 재생이 성립하는 것과는 다른 축이다.
  expect(replayed.exitCode).not.toBe(0);
  // 이것이 이 수정의 핵심 증거다. 재생됐다면 origin 카운터가 움직이지 않는다.
  expect(origin.calls()).toBe(1);
  expect(replayed.stderr).not.toContain("녹화가 완료되지 않은 세션입니다");
  expect(replayed.stderr).toContain("녹화된 외부 호출 1건을 재생했습니다");
}, 60_000);
```

`runWith` 와 `captureStderr` 는 그 파일에 이미 있다. `failingSuite` 상수만 파일 머리의 상수
묶음에 더한다.

### 7.3 문안 단언 (기존 유닛 갱신)

`packages/cli/tests/external-session.test.ts:668` 의 `describe("실패한 실행의 결과 문장
(ADR-0066)")` 은 이름과 문장이 함께 바뀐다. 새 이름은 `describe("완료되지 않은 녹화의 결과 문장
(ADR-0094)")` 이다.

| 케이스 이름 | 단언 |
|---|---|
| `완료되지 않은 녹화는 완료했다고 말하지 않는다` | `toContain("녹화가 완료되지 않은 채 닫혔습니다")`, `toContain("재생 원본으로 쓸 수 없습니다")`, `not.toContain("3건을 녹화했습니다")` |
| `테스트 판정을 원인으로 지목하지 않는다` | `toContain("테스트 판정과는 무관합니다")`, `not.toContain("이 실행이 실패해")` |
| `잡은 개수는 그대로 말한다` | `toContain("3건을 잡았지만")` (기존 유지) |
| `실패한 재생은 여전히 재생이라고 말한다` | `toContain("3건을 재생했습니다")` (기존 유지) |
| `완료되지 않아도 경고와의 배타성은 유지된다` | 기존 유지 |

`externalOpenFailure` 와 `externalCloseFailure` 단언은 같은 파일 안의 해당 `describe` 에 더한다.

| 대상 | 단언 |
|---|---|
| `externalOpenFailure("replay", path, { code: "REPLAY_SOURCE_INVALID" })` | `hint` 가 `toContain("비-JSON")` 과 `toContain("다시 녹화하세요")`, `not.toContain("녹화 실행이 실패했을 수 있습니다")` |
| `externalCloseFailure({ code: "INCOMPLETE_SESSION", message: "원문\n둘째 줄" })` | `message` 가 `"녹화를 완료하지 못했습니다. 끝나지 않은 외부 호출이 남았습니다."`, `hint` 가 `"원문\n둘째 줄"` 그대로(개행이 살아 있다) |
| `externalCloseFailure(new Error("그 밖"))` | `message` 가 `"External 세션을 닫지 못했습니다."` |

## 8. 위험

| 위험 | 판단 |
|---|---|
| 미완료 interaction 진단이 실패한 실행에 새로 붙어 출력이 늘어난다 | 의도다. 지금은 그 사실이 묻힌다. 진단이 붙는 실행은 원래도 종료 코드 1이었다 |
| 반쪽짜리 녹화가 `completed` 로 닫힐 수 있다 | 없다. 저장소의 미완료 검사가 그 경우를 `failed` 로 뒤집는다. 이 변경은 그 검사를 **더 자주** 돌린다 |
| 실패한 실행의 녹화본이 쌓여 사용자가 잘못된 원본으로 재생한다 | 녹화본의 내용은 판정과 무관하게 참이다. 어느 실행에서 떴는지는 §3 의 별건이다 |
| 기존 세션 파일 호환 | 스키마를 건드리지 않는다. 이미 `failed` 로 닫힌 옛 파일은 그대로 거절되고, 그 문장이 5.2 로 바뀐다 |
