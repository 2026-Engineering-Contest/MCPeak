# generate 화면은 제안 값과 실패 근거를 감추지 않는다

2026-09-13. `live-weather-server` 데모를 대시보드에서 손으로 밟다가 나온 다섯 가지를 한 번에
닫는다. 전부 같은 계열이다. **화면이 숫자나 문장은 찍는데, 그 숫자가 어디서 나왔고 무엇이
실패했는지는 화면 어디에도 없다.** 이 프로젝트에서 실패 메시지는 곧 제품이므로 그것이 결함이다.

- 관련 ADR: [ADR-0098](./adr/0098-generate-승인-화면은-실패한-케이스만-AI-에-보낸다.md)
  (직전 회차. `보류` 줄과 `--diagnose-rejections` 를 만들었다)
- 실측 기록: [공개 서버 직접 조작 데모 실측 문제](./2026-09-11-공개서버-직접조작-데모-실측-문제.md) §4
- 교정 화면 원본 설계:
  [dry-run input repair design](./superpowers/specs/2026-08-15-dry-run-input-repair-design.md) §8.6

## 1. 문제

### 1.1 `보류 N` 이 무엇을 보류했는지 말하지 않는다

ADR-0098 이 만든 줄이다.

```
AI 사전보완: 툴 10개 중 3개에 값 제안을 받았습니다.
  채택 1 (실제 서버에서 baseline 값이 실패하고 제안 값이 통과)
  미채택 1 (baseline 값이 이미 통과)
  보류 1 (baseline 값도 제안 값도 실패. 분류 화면에서 정합니다)
```

보류는 "AI 제안 값도 실제 서버에서 실패했다" 는 뜻이다. 그런데 **AI 가 무슨 값을 냈는지,
서버가 뭐라고 답했는지가 화면 어디에도 없다.** 2026-09-13 실측에서 `evaluate_expression` 이
보류 1로 나왔는데, 같은 실행의 뒤 단계(입력값 교정)에서는 같은 AI 가 `2 + 2` 를 제안해
통과했다. 두 단계의 결과가 왜 다른지 사용자가 알 데가 없다.

`applyPreFill` 은 제안 값(`aiInputs`)과 AI 회차의 실행 결과(`aiRun`)를 둘 다 손에 쥐고 있는데
개수만 세어 버리고 값을 버린다.

### 1.2 `targetIds` 에서 빠진 제안이 어느 줄에도 안 세어진다

실측 문서 §4 의 관측 "둘" 이다. context7 에서 제안 2건을 받았는데 요약이 `채택 0 · 미채택 0`
이었다. `applyPreFill` 은 제안이 붙은 케이스가 `callTool` 이 아니거나 입력이 객체가 아니거나
명세에 아예 없으면 `targetIds` 에 넣지 않는다. 그 제안은 `cases` 배열에 안 들어가므로
`adopted` 에도 `notAdopted` 에도 안 세어진다. 화면에서 그냥 사라진다.

### 1.3 교정 화면 머리말이 실패 사유를 지어낸다

`packages/cli/src/input-repair.ts` 의 `FAILURE_LINE` 은 고정 문장이다.

```ts
const FAILURE_LINE = `${BODY}isError  정상 응답을 기대했지만 오류 응답을 받았습니다.`;
```

주석은 "대상 판별이 `isError` 단언 실패만 통과시키므로 이것 말고 나올 수 없다" 고 적는다.
**그 전제가 틀렸다.** 2026-09-13 실측에서 `convert_units` 가 교정 대상에 올랐는데, 실제 실패는
호출 자체가 던진 것이었다.

```
✗ convert-units-success  convert_units가 오류 없이 응답한다
    툴 'convert_units' 호출 중 오류가 발생했습니다.
    → 원인: MCP error -32602: Structured content does not match the tool's output schema: data must have required property 'converted'
    해결: 요청한 tool과 서버 기능 및 진단을 확인하세요.
    isError                         (건너뜀) MCP 작업 결과가 없어 assertion을 검사할 수 없습니다.
    해결: 먼저 MCP 작업 실패 원인을 해결하세요.
    structuredContentMatchesSchema  (건너뜀) MCP 작업 결과가 없어 assertion을 검사할 수 없습니다.
    해결: 먼저 MCP 작업 실패 원인을 해결하세요.
```

`repair-target.ts` 의 `failedByIsError` 는 본문 줄이 `isError` 로 시작하기만 하면 실패로 읽는다.
위 블록의 `isError` 줄은 **건너뛴 단언**이다. 주석의 "통과한 단언은 애초에 그려지지 않으므로
존재 자체가 실패의 근거다" 는 `skipped` 단언을 빠뜨렸다. `reporter.ts:334` 가 `skipped` 에
`(건너뜀) ` 접두사를 붙여 그린다.

결과가 둘이다.

- 화면이 실패 사유를 `isError  정상 응답을 기대했지만 오류 응답을 받았습니다.` 라고 말한다.
  같은 실행의 실패 목록은 `MCP error -32602` 라고 말한다. 두 화면이 서로를 반박한다.
- 어떤 입력값을 넣어도 통과할 수 없는 케이스에 대해 사용자에게 값을 세 번 묻는다. 결함은
  서버의 `outputSchema` 불일치이고 입력값과 무관하다.

### 1.4 필드 질문이 맥락을 다 뺀다

AI 제안이 있을 때의 질문은 이 한 줄이다.

```
      value: [1]
```

툴 이름이 없다. 현재 값이 없다. 선언 타입이 없다. 대괄호가 기본값이라는 설명이 없다. 제안이
없을 때의 형식(`city (string, 현재 "example"): `)은 이 넷 중 셋을 갖고 있다. 같은 화면에서
같은 성격의 질문이 두 형식으로 갈린다.

거기에 더해 대시보드에서는 **답한 값이 로그에 남지 않는다.** `value` → `from` → `to` 세 질문을
차례로 받는 동안 터미널 출력은 `124줄` 그대로였다. `to` 를 물을 때 앞의 둘을 뭐라고 답했는지
화면에 없다. 터미널에서는 readline 이 사용자의 입력을 그대로 되비추지만, 대시보드의
`WebReviewIO` 는 질문을 별도 패널로 보내고 답은 아무 데도 찍지 않는다.

### 1.5 대시보드에 `--diagnose-rejections` 가 없다

ADR-0098 이 만든 플래그인데 CLI 에만 있다. 대시보드 generate 폼에서는 켤 수 없다. 대시보드는
argv 를 브라우저에서 조립해 그대로 넘기므로(`packages/dashboard/web/src/generate/build-argv.ts`)
서버 쪽에는 고칠 것이 없다.

## 2. 비범위

- **서버 코드 수정.** `live-weather-server` 의 결함 A·B·C 는 데모용으로 일부러 심은 것이다.
  그대로 둔다.
- **`--determinism` 에서 SDK 가 던지는 케이스의 단언 상태가 1회차 `skipped`, 2회차 `passed` 로
  흔들리는 문제.** runner 소유 영역이고 이 설계와 원인이 다르다. 별도 이슈로 넘긴다.
- **`repair` 명령(사후수리)**. 이 설계는 `generate` 안의 입력값 교정만 다룬다.
- **교정 회차 수·캐시·되돌리기 규칙.** 원본 설계 §4 를 그대로 둔다.

## 3. 결정

### 3.1 보류 케이스는 제안 값과 서버 응답을 한 줄씩 보인다

`ApplyPreFillResult.cases` 의 각 항목에 **보류일 때만** 두 가지를 싣는다.

- `proposedFields`: 그 케이스에 얹은 제안 값. `{ field, value }` 배열. 요청 순서.
- `serverMessage`: AI 회차 실행에서 서버가 낸 위반 줄. 여러 줄이면 개행으로 잇는다.
  없으면 빈 문자열.

요약 화면이 보류 줄 아래에 케이스마다 두 줄을 더 찍는다(§4.1).

**왜 보류만인가.** 채택된 케이스의 제안 값은 명세에 실려 저장되므로 사용자가 파일에서 본다.
미채택은 baseline 이 이미 통과했으므로 제안 값을 몰라도 손해가 없다. 보류만 "무슨 일이
일어났는지 화면에도 파일에도 없는" 상태다.

### 3.2 `targetIds` 에서 빠진 제안은 사유와 함께 센다

`ApplyPreFillResult` 에 `excluded: readonly PreFillExclusion[]` 을 더한다.

```ts
/** 제안을 받았지만 어느 갈래에도 못 들어간 케이스. 사유를 반드시 함께 싣는다. */
export interface PreFillExclusion {
  readonly caseId: string;
  readonly field: string;
  /** 화면에 그대로 찍는 사유. 아래 세 문장만 쓴다. */
  readonly reason: "명세에 없는 케이스" | "callTool 이 아닌 케이스" | "입력이 객체가 아닌 케이스";
}
```

제안 하나(케이스 하나의 필드 하나)마다 한 항목이다. 개수만 세지 않는 것은 `버림` 줄과 같은
규칙이다(이슈 #120). 조기 반환 경로(`byCase.size === 0`, `targetIds.size === 0`)에서도 채운다.

### 3.3 호출이 던진 케이스는 교정 대상이 아니다

판정을 렌더된 텍스트가 아니라 **구조화된 결과**로 한다. `DryRunCaseOutcome` 에 두 필드를 더한다.

```ts
/**
 * 호출 자체가 끝나지 못했는가. `operation.status !== "completed"` 다.
 * 참이면 단언은 전부 `skipped` 이고, 입력값을 고쳐도 결과가 안 바뀐다.
 */
readonly operationFailed: boolean;
/**
 * 실패 사유 첫 줄. 호출이 던졌으면 작업 진단 문장, 아니면 실패한 단언의 줄이다.
 * 통과했거나 진단이 없으면 빈 문자열이다. 교정 화면 머리말이 이것을 그대로 쓴다.
 */
readonly failureLine: string;
```

`selectRepairTargets` 는 `operationFailed` 인 케이스를 대상에서 뺀다. 대신 그것들을 따로 돌려주기
위해 반환 타입을 바꾼다.

```ts
export interface RepairSelection {
  /** 입력값을 고쳐 볼 수 있는 케이스. 기존 `selectRepairTargets` 의 반환값과 같은 배열이다. */
  readonly targets: readonly RepairTarget[];
  /** 호출이 던져 교정할 수 없는 실패. 화면이 사유와 함께 한 번 고지한다. */
  readonly thrown: readonly ThrownCase[];
}

export interface ThrownCase {
  readonly caseId: string;
  readonly caseName: string;
  /** 작업 진단의 첫 줄. `DryRunCaseOutcome.failureLine` 을 그대로 옮긴다. */
  readonly failureLine: string;
  /** 서버가 준 원인 줄. `→ ` 를 벗긴 본문이다. 없으면 빈 문자열이다. */
  readonly serverMessage: string;
}
```

`thrown` 의 판별은 `targets` 와 같은 앞단 조건을 공유한다. 즉 `callTool` 이고, 입력이 비어 있지
않고, `origin` 이 `user` 가 아니고, 위반 케이스(`isError expected true`)가 아닌 실패 중에서
`operationFailed` 인 것이다. 이 조건을 안 맞추면 교정과 무관한 케이스까지 고지에 섞인다.

**왜 대상에서 빼는가.** 입력값을 어떻게 바꿔도 서버의 `outputSchema` 불일치는 안 고쳐진다.
사용자에게 세 번 묻고 세 번 실패시키는 것은 시간을 뺏는 것이고, 더 나쁘게는 "입력값이 거절된
것으로 보입니다" 라고 틀린 원인을 가르친다. 이 케이스들은 분류 화면과 사후수리(`repair` 명령)가
받을 몫이고, 그 경로는 이미 있다.

### 3.4 교정 머리말은 실제 진단을 찍는다

`RepairTarget` 에 `failureLine: string` 을 더하고, `input-repair.ts` 의 상수 `FAILURE_LINE` 을
지운다. 머리말에 서버가 준 위반 줄(`serverMessage`)도 함께 찍는다. 그것이 사용자가 값을 정할
근거인데 지금은 화면에 없다.

번호는 `[1]` 이 아니라 `[1/4]` 로 전체 수를 붙인다. 사용자가 몇 번을 더 답해야 하는지 알 수
있어야 한다.

### 3.5 필드 질문은 한 형식으로 합친다

제안 유무로 갈리던 두 형식을 하나로 합친다. 괄호 안에 **필드 진행도, 선언 타입, 현재 값,
엔터의 뜻** 넷을 순서대로 넣고, 필드 이름 앞에 툴 이름을 붙인다.

```
      convert_units.value (필드 1/3, number, 현재 0, 엔터 = 제안 값 1): 
      convert_units.value (필드 1/3, number, 현재 0, 엔터 = 현재 값 유지): 
```

선언 타입을 못 읽은 필드는 그 자리만 뺀다. 없는 타입을 지어내지 않는 기존 규칙 그대로다.

이것은 원본 설계 §8.6 · §8.6.1 의 문안을 **바꾸는** 결정이다. 그 문서에 정정 주석을 남긴다.

### 3.6 대시보드는 답을 로그에 되비춘다

`WebReviewIO.answer()` 가 답을 받는 순간 `stdout` 이벤트로 질문과 답을 한 줄 찍는다. 터미널의
readline 이 하는 일을 웹에서 대신하는 것이다.

```ts
// 질문 종류별 표시값
input   → 답 문자열. 빈 문자열이면 `(엔터)`
confirm → "y" 면 `예`, 아니면 `아니오`
choose  → 고른 문자열
뒤로    → `(뒤로)`
```

출력은 `${message}${표시값}\n` 이다. 질문 문자열이 이미 `: ` 로 끝나므로 그대로 이어 붙인다.

**CLI 쪽은 건드리지 않는다.** `nodeReviewIO` 경로에서는 readline 이 이미 되비추므로 여기서 또
찍으면 같은 답이 두 줄 난다. 이 결함은 웹 구현에만 있다.

### 3.7 대시보드 generate 폼에 토글을 더한다

`GenerateForm` 에 `diagnoseRejections: boolean` 을 더하고 4단계(StepConfirm)에 `Toggle` 을 둔다.
CLI 가 `--diagnose-rejections` 와 `--no-dry-run` 을 함께 쓰면 사용 오류를 내므로
(`generate-command.ts:528`), `buildGenerateArgv` 의 검증 블록에도 같은 규칙을 넣는다. 검증이
없으면 대시보드가 CLI 가 거부할 argv 를 만들어 보내고, 사용자는 실행이 시작된 뒤에야 오류를
본다.

## 4. 화면 (전량)

문안을 바꾸지 마라.

### 4.1 사전보완 요약

```
AI 사전보완: 툴 10개 중 3개에 값 제안을 받았습니다.
  채택 1 (실제 서버에서 baseline 값이 실패하고 제안 값이 통과)
  미채택 1 (baseline 값이 이미 통과)
  보류 1 (baseline 값도 제안 값도 실패. 분류 화면에서 정합니다)
    evaluate-expression-success  expression: "2"
      → 식을 해석할 수 없습니다: '2' (숫자 · + - * / · 괄호 외의 문자가 있습니다)
  제외 1 (callTool 이 아닌 케이스: ctx7-list.query)
  버림 1 (표 밖 format: search-a.cursor)
```

규칙.

- `보류` 줄은 기존 그대로다. 그 아래에 보류 케이스마다 블록을 하나 찍는다.
- 블록 첫 줄은 `{4칸}{caseId}{공백 2}{제안 목록}`. 제안 목록은 `field: JSON값` 을 `, ` 로 잇는다.
- 블록 둘째 줄부터는 `{6칸}→ {서버 위반 줄}`. 위반 줄이 여럿이면 줄마다 찍는다.
- 서버 위반 줄이 하나도 없으면 AI 회차 실패 블록의 첫 본문 줄을 대신 쓴다. 그것도 없으면
  `→ ` 줄을 아예 안 찍는다. 관측하지 못한 것을 관측했다고 적지 않는다.
- `제외` 줄은 제안 하나마다 한 줄이다. 형식은 `{2칸}제외 1 ({사유}: {caseId}.{field})`.
  `버림` 줄과 같은 규칙이다.
- `제외` 가 0건이면 그 줄을 안 찍는다.
- 대상도 버림도 제외도 전부 0이면 요약 전체가 빈 문자열이다.

### 4.2 교정 대상이 아닌 실패 고지

교정 단계 맨 앞, 대상 목록보다 먼저 한 번 찍는다. `thrown` 이 0건이면 안 찍는다.

```
  교정 대상이 아닌 실패 1건 (호출 자체가 실패했습니다. 입력값 문제가 아닙니다)
    convert_units가 오류 없이 응답한다
      → 원인: MCP error -32602: Structured content does not match the tool's output schema: data must have required property 'converted'

```

- 머리줄은 `{2칸}교정 대상이 아닌 실패 {n}건 (호출 자체가 실패했습니다. 입력값 문제가 아닙니다)`.
- 케이스마다 `{4칸}{caseName}` 한 줄, 이어서 `{6칸}→ {serverMessage 각 줄}`.
- `serverMessage` 가 비었으면 `{6칸}{failureLine}` 한 줄을 대신 쓴다.
- 블록 끝에 빈 줄 하나.

### 4.3 입력값 교정 (AI 제안이 있을 때)

원본 설계 §8.6 을 대체한다.

```
  [1/4] evaluate_expression가 오류 없이 응답한다
      isError  정상 응답을 기대했지만 오류 응답을 받았습니다.
      → 식을 해석할 수 없습니다: 'example' (숫자 · + - * / · 괄호 외의 문자가 있습니다)
      → 숫자, + - * /, 괄호만 쓸 수 있습니다. 예: (2 + 3) * 4 / 5

      입력값이 거절된 것으로 보입니다. claude(sonnet) 가 서버 응답을 보고 제안한 값입니다.
      evaluate_expression.expression (필드 1/1, string, 현재 "example", 엔터 = 제안 값 "2 + 2"): 
```

- 머리줄 번호는 `[{index}/{total}]`. `total` 은 `targets.length` 다.
- 둘째 줄은 `{6칸}{target.failureLine}`. 고정 문장이 아니다.
- 셋째 줄부터는 `{6칸}→ {serverMessage 각 줄}`. `serverMessage` 가 비었으면 안 찍는다.
- 그다음 빈 줄, 출처 문장, 필드 질문 순서다. 출처 문장 세 갈래는 기존 그대로다.

### 4.4 입력값 교정 (근거가 없을 때)

원본 설계 §8.6.1 을 대체한다.

```
  [2/4] get_weather가 오류 없이 응답한다
      isError  정상 응답을 기대했지만 오류 응답을 받았습니다.

      입력값이 거절된 것으로 보입니다. 서버 응답에 쓸 만한 값이 없어 직접 받습니다.
      get_weather.city (필드 1/1, string, 현재 "example", 엔터 = 현재 값 유지): 
```

### 4.5 필드 질문 형식 (전량)

```
{6칸}{tool}.{field} (필드 {i}/{n}{, 타입}{, 현재 {JSON}}, 엔터 = {제안 값 {JSON} | 현재 값 유지}): 
```

- `{i}` 는 이번 회차에 **실제로 묻는** 필드 중 몇 번째인가다. 캐시로 건너뛴 필드는 세지 않는다.
- `{n}` 은 이번 회차에 묻는 필드 수다.
- 타입은 `inputSchema` 가 선언한 것만 쓴다. 못 읽으면 `, 타입` 자리를 통째로 뺀다.
- 현재 값은 `JSON.stringify` 다. `undefined` 면 `, 현재 …` 자리를 뺀다.
- 제안 값이 있으면 `엔터 = 제안 값 {JSON}`, 없으면 `엔터 = 현재 값 유지`.
- 줄 끝에 공백 하나. 기존과 같다.

2회차(제안이 실패해 사람에게 다시 묻는 회차)는 제안이 없는 형식을 쓴다. 이때 `현재` 는 1회차에
쓴 값이다. 기존 동작 그대로다.

### 4.6 대시보드 답 되비추기

터미널 출력 구역에 찍힌다.

```
      evaluate_expression.expression (필드 1/1, string, 현재 "example", 엔터 = 제안 값 "2 + 2"): 2 + 2
이 요청을 전송할까요? 예
```

### 4.7 대시보드 토글

4단계(StepConfirm), `실패한 입력값 자동 교정` 토글 바로 아래.

```
[ ] 거절 근거 진단 보기 (--diagnose-rejections)
    통과한 거절 케이스의 목록과 AI 진단을 함께 봅니다. 시험 실행이 필요합니다.
```

시험 실행이 꺼져 있으면(`dryRun === false`) 토글을 끄고 비활성화한다. 안내는 이렇게 적는다.

```
    시험 실행이 꺼져 있어 거절 근거 진단을 쓸 수 없습니다.
```

## 5. 데이터 흐름

```
runSuite
  └ RunnerReport.cases[].operation.status  ← 호출이 끝났는가 (구조화)
  └ RunnerReport.cases[].assertions[].status ← 단언 판정 (구조화)
        ↓ dry-run.ts
DryRunCaseOutcome { status, detail, operationFailed, failureLine, ... }
        ↓ repair-target.ts
RepairSelection { targets: RepairTarget[{ failureLine, serverMessage }], thrown: ThrownCase[] }
        ↓ generate-command.ts
   §4.2 고지 → input-repair.ts §4.3·§4.4·§4.5

preFill.accepted
        ↓ pre-fill-wiring.ts (aiInputs, aiRun 을 이미 쥐고 있다)
ApplyPreFillResult { cases[{ proposedFields, serverMessage }], excluded, ... }
        ↓ generate-command.ts renderPreFillSummary
   §4.1
```

`failureLine` 과 `serverMessage` 를 **`renderReport` 가 만든 문장에서 옮겨 적는다.** 새 문장을
만들지 않는다. 같은 실패를 `test` 에서 볼 때와 `generate` 에서 볼 때 낱말이 갈리면 사용자가 두
번 배운다. 이것은 `dry-run.ts` 의 기존 규칙과 같다.

다만 **판정은 구조화된 필드로 한다.** `operationFailed` 를 `(건너뜀) ` 문자열로 판별하지 않는다.
렌더 문자열로 판정하는 코드가 이번 결함(§1.3)의 직접 원인이다.

## 6. 완료 조건

1. 보류 케이스가 있는 실행에서 요약에 제안 값과 서버 위반 줄이 §4.1 형식으로 찍힌다.
2. `callTool` 이 아닌 케이스에 제안이 붙으면 `제외` 줄이 사유·caseId·field 와 함께 찍힌다.
3. `live-weather-server` 로 generate 를 돌리면 `convert_units` 가 교정 대상에 안 오르고
   §4.2 고지에 나온다. 사용자에게 `value`·`from`·`to` 를 묻지 않는다.
4. 교정 머리말이 `[1/4]` 형식이고, 둘째 줄이 그 케이스의 실제 진단이다.
5. 필드 질문이 §4.5 한 형식이다. 제안 유무로 형식이 갈리지 않는다.
6. 대시보드에서 답한 값이 터미널 출력에 남는다.
7. 대시보드 4단계에 `--diagnose-rejections` 토글이 있고, 시험 실행이 꺼지면 비활성화된다.
8. 프로젝트 루트에서 `pnpm test`, `pnpm typecheck --force`, `pnpm lint` 가 녹색이다.

## 7. 검토한 대안

**`(건너뜀) ` 문자열로 판별한다.** 한 줄이면 끝난다. 버렸다. 렌더 문안이 바뀌면 조용히 깨지고,
깨진 것을 알아채는 곳이 없다. 이번 결함이 정확히 그 방식의 결과다. 구조화된 필드가 이미
`RunnerReport` 에 있는데 텍스트를 다시 파싱할 이유가 없다.

**보류 케이스를 교정 단계로 바로 넘긴다.** 보류가 생긴 이유를 화면에 적는 대신 다음 단계가
알아서 처리하게 두는 안이다. 버렸다. 두 단계는 다른 값을 제안할 수 있고(실측이 그랬다),
사용자는 여전히 왜 달랐는지 모른다. 그리고 보류는 `--no-repair` 경로에도 생긴다.

**`selectRepairTargets` 의 반환 타입을 그대로 두고 `thrown` 을 별도 함수로 뺀다.** 호출 측이
두 함수를 부르면서 같은 앞단 조건을 두 번 쓰게 된다. 조건이 갈리면 어느 케이스가 양쪽에 다
들어가거나 어디에도 안 들어간다. 한 번 순회해 두 배열로 가르는 쪽이 그 어긋남을 구조적으로
막는다.

**필드 질문에서 툴 이름을 뺀다.** 머리줄에 케이스 이름이 이미 있으니 중복이라는 주장이다.
버렸다. 케이스 이름은 `evaluate_expression가 오류 없이 응답한다` 처럼 사람 문장이라 툴 이름을
기계적으로 못 뽑는다. 그리고 값 재사용 고지(§8.6.3)는 이미 `get_weather.city` 형식을 쓰므로
같은 화면 안에서 표기가 통일된다.

**대시보드 답 되비추기를 CLI 쪽 `input-repair.ts` 에 넣는다.** 모든 구현에 한 번에 적용된다.
버렸다. `nodeReviewIO` 경로에서 readline 이 이미 되비추므로 답이 두 줄 난다. 결함은 웹 구현
하나에만 있고 고칠 자리도 거기다.
