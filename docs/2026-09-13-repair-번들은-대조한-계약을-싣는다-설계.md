# repair 번들은 대조한 계약을 싣는다

2026-09-13. 이슈 [#393](https://github.com/2026-Engineering-Contest/MCPeak/issues/393) 을 닫는다.

`repair` 는 서버를 띄우지 않고 번들 파일 하나만 읽어 진단한다. 그런데 **번들에 "무엇과
대조해서 틀렸다고 판정했는지" 가 없다.** 도구 선언도, 단언도, 어느 서버의 어느 버전인지도
없다. 진단 요청의 `tools` 는 항상 `[]` 다.

- 검토 기준 커밋: `c0a1934fd2c1147556080d7f78f8b9e4b0a3f717`
- 번들 형식 원본 설계: `REPAIR_BUNDLE_VERSION = 2` (`packages/cli/src/repair-bundle.ts`)

## 1. 문제

### 1.1 `tools` 가 항상 비어 있다

`packages/cli/src/repair-command.ts:176` 이다.

```ts
// 번들에는 도구 선언이 없다. `repair` 는 서버를 띄우지 않으므로 목록을 만들 자리가 없다.
tools: [],
```

주석이 사실을 정확히 말한다. **그런데 그것이 문제다.** `buildDiagnosisRequest` 는
`tools: readonly McpToolContext[]` 를 받아 `TOOL_CONTRACT_PATHS` 로 마스킹까지 해서 실어
보내게 돼 있다. 받을 준비가 다 돼 있는데 주는 쪽이 비어 있다.

AI 는 `{ "city": "example" }` 이 실패했다는 것만 보고, `city` 가 무슨 타입이어야 하는지
enum 이 있는지 모른 채 원인을 짚어야 한다. 서버 소스에 접근하지 않는 진단에서 이것은
근거가 아니라 추측이다.

### 1.2 어떤 단언이 깨졌는지가 진단에만 있다

`RepairBundleFailure` 는 `diagnostics` 를 싣는다. 그것은 **깨진 단언의 메시지**다. 그
케이스가 원래 무엇을 기대했는지, 즉 `assertions` 전량은 없다.

`isError: false` 하나만 있던 케이스와 `structuredContentMatchesSchema` 까지 있던 케이스가
번들에서 구분되지 않는다. 진단이 "출력 스키마를 확인하라" 고 해야 할 자리에서 그 단언이
있었는지도 모른다.

### 1.3 무엇을 실행했는지가 없다

번들에 `spec.suiteId` · `suiteName` · `fingerprint` 는 있는데 **대상 서버가 없다.** 같은
명세를 다른 명령·다른 환경에서 돌린 두 실행의 번들이 구분되지 않는다. 사용자가 번들 세 개를
쌓아 두면 어느 것이 어느 서버 것인지 파일명 말고는 알 방법이 없다.

### 1.4 공용 stderr 꼬리를 케이스마다 반복해 읽는다

`bundle.process.stderr` 는 **프로세스 전체의 꼬리**다. 케이스 하나의 것이 아니다. 그런데
진단 요청에는 그것이 통째로 한 번 실려 가고, AI 는 12개 실패 각각의 원인으로 그 꼬리를 읽는다.
실제로는 마지막 케이스 실행 중에 난 것일 수 있다.

이것은 **없는 근거를 만들어 내는 쪽**이라 §1.1~§1.3 보다 나쁘다. 근거가 없는 것보다 틀린
근거가 비싸다.

## 2. 결정

번들 형식을 **버전 3** 으로 올리고 네 가지를 더한다. 그리고 `repair-command.ts` 가 그것을
`buildDiagnosisRequest` 로 넘긴다.

| 더하는 것 | 닫는 문제 |
|---|---|
| `tools` — 실패한 케이스가 부른 도구의 선언 | §1.1 |
| `failures[].assertions` — 그 케이스의 단언 전량 | §1.2 |
| `target` — 대상 식별과 버전 | §1.3 |
| `process.scope` — stderr 가 무엇의 것인지 | §1.4 |

**버전을 올린다.** 선택 필드로 얹지 않는다. `REPAIR_BUNDLE_VERSION = 2` 를 넣을 때 적은
이유가 그대로 유효하다. 선택 필드로 두면 낡은 번들이 근거 절반만 실은 채 조용히 통과하고,
사용자는 진단이 왜 약한지 모른다.

### 2.1 `tools`: 실패한 케이스가 부른 것만

전체 도구 목록을 싣지 않는다. **번들 안의 `failures[].tool` 에 등장하는 이름만** 싣는다.

- 도구가 40개인 서버에서 실패가 2건이면 나머지 38개는 진단에 쓸모가 없고 크기만 먹는다
- `maxCases` 로 실패를 잘랐으면 잘린 뒤 남은 것 기준이다. 안 보낼 케이스의 도구 선언을
  보내면 AI 가 없는 케이스를 추측하기 시작한다

```ts
export interface RepairBundleTool {
  readonly name: string;
  readonly inputSchema: JsonObject;
  /** 선언이 없으면 키를 만들지 않는다. 빈 객체를 넣으면 "빈 스키마" 로 읽힌다. */
  readonly outputSchema?: JsonObject;
  readonly description?: string;
}
```

`description` 을 넣는 이유: 도구가 무엇을 하기로 한 것인지가 원인 판정에 직접 쓰인다.
`convert_units` 가 "단위를 변환한다" 인지 "단위를 검증만 한다" 인지에 따라 같은 응답의
해석이 갈린다.

마스킹은 `generate` 의 `TOOL_CONTRACT_PATHS` 가 이미 한다. 번들을 만들 때 따로 하지 않는다.
**규칙이 두 벌이 되면 화면에 가려진 값이 파일에는 남는다.**

### 2.2 `assertions`: 케이스가 기대한 것 전량

```ts
export interface RepairBundleAssertion {
  readonly type: string;
  /**
   * `runner` 의 `AssertionResult.status` 를 그대로 옮긴다. 넷이다(2026-09-13 확인).
   * `skipped` 는 앞 단계가 결과를 못 내 검사 자체를 못 한 것이고, `notRun` 은 실행에
   * 도달하지 못한 것이다. 둘을 뭉치면 "왜 판정이 없는가" 가 사라진다.
   *
   * 진단은 "무엇이 깨졌나" 만큼 "무엇이 안 깨졌나" 도 쓴다.
   */
  readonly status: "passed" | "failed" | "skipped" | "notRun";
}
```

**값을 손으로 옮겨 적지 마라.** `packages/runner/src/assertions.ts` 의 `AssertionResult` 가
정의이고, 거기가 늘면 여기도 늘어야 한다. 구현할 때 그 파일을 열어 현재 값을 확인한다.

단언의 **값**(기대 스키마 전문 등)은 싣지 않는다. `diagnostics` 의 `expected` · `actual` 이
깨진 것에 대해서는 이미 값을 싣고 있고, 안 깨진 단언의 값까지 실으면 번들이 커지는 만큼
진단이 좋아지지 않는다. 타입과 상태만으로 "출력 스키마 단언이 있었고 통과했다" 가 전달된다.

### 2.3 `target`: transport 만 싣는다

2026-09-13 실측으로 **범위가 줄었다.** 처음에는 실행 명령·URL·서버 이름·버전을 싣기로 했다.
넷 다 못 싣는다. 사유가 각각 다르고 둘 다 확인한 사실이다.

```ts
export interface RepairBundleTarget {
  /** "stdio" 또는 "http". 실행 방식이 다르면 같은 증상도 원인이 다르다. */
  readonly transport: string;
}
```

**왜 실행 명령·URL 을 안 싣는가.** ADR-0097 이 argv 마스킹 규칙(R1~R4)을 정하고
`redactOriginArgs` 로 구현해 뒀다. 그런데 그 함수는 `packages/record/src/external/origin-redaction.ts`
에 있고 **`@mcpeak/record` 의 공개 진입점으로 나오지 않는다.** 확인했다.

| 길 | 판단 |
|---|---|
| `record` 가 그 함수를 공개 API 로 내보내게 한다 | 다른 오너(`@ddxng5`)의 패키지 공개 표면을 넓히는 일이다. 진단 번들의 편의 항목 하나 때문에 할 일이 아니다 |
| `cli` 에 같은 규칙을 다시 쓴다 | **ADR-0097 의 규칙이 두 벌이 된다.** 한쪽만 고쳐지면 녹화본에는 가려진 값이 번들에는 남는다. 정확히 그 ADR 이 막으려던 사고다 |
| 마스킹 없이 싣는다 | 번들은 사용자가 AI 에게 보내는 파일이다. ADR-0097 이 무효가 된다 |
| **안 싣는다** | **채택** |

**왜 서버 이름·버전을 안 싣는가.** 핸드셰이크 결과가 `McpClient` 에 노출돼 있지 않다.
확인했다. 넣으려면 그 인터페이스를 바꿔야 하는데 프로젝트 지침이 변경을 금지한다
(5명의 병렬 작업 기준점이다).

**`transport` 하나는 그래도 값이 있다.** stdio 에서 난 `-32602` 와 http 에서 난 같은 오류는
원인 후보가 다르다. 그리고 이 값에는 비밀값이 들어올 자리가 없다.

이슈 #393 이 요구한 "실행 대상/버전" 은 **이번에 절반만 닫힌다.** §7 에 비범위로 적고 사유를
남긴다. 못 하는 것을 한 척하지 않는다.

### 2.4 `process.scope`: stderr 를 케이스의 원인으로 단정하지 않는다

`ProcessDiagnosticsInput` 은 그대로 두고, 번들이 실을 때 범위를 붙인다.

```ts
readonly process?: ProcessDiagnosticsInput & {
  /**
   * 이 stderr 가 무엇의 것인지. 지금은 항상 "suite" 다. 프로세스 전체의 꼬리이지
   * 특정 케이스의 것이 아니다.
   *
   * 값을 하나뿐인 유니온으로 두는 이유: 나중에 케이스별 수집이 생기면 "case" 가 늘고,
   * 그때 낡은 번들은 버전으로 걸린다. 지금 이 키가 없으면 AI 는 범위를 모른 채 읽는다.
   */
  readonly scope: "suite";
};
```

그리고 **프롬프트가 그 뜻을 말한다.** 값만 넣고 뜻을 안 적으면 §1.4 가 그대로 남는다.
`packages/generate/src/diagnosis-prompt.ts` 에 규칙 한 문단을 더한다.

```
stderr 읽는 법:
stderr 는 서버 프로세스 전체에서 모은 꼬리다. 특정 케이스가 낸 것이 아니다.
어느 케이스의 원인이라고 단정하지 않는다. 케이스와 stderr 를 잇는 근거가 따로 없으면
그 연결을 원인 후보로 내지 않는다.
```

`CASE_HISTORY_RULE` 과 같은 자리에 같은 방식으로 붙인다. 그 상수가 만들어진 이유(#385)와
같은 계열이다. 요청에 값은 실려 있는데 뜻이 프롬프트 어디에도 없어 AI 가 잘못 읽는 것이다.

## 3. 크기

번들이 커진다. 상한을 둔다.

| 항목 | 상한 | 넘으면 |
|---|---|---|
| 도구 하나의 `inputSchema` + `outputSchema` 직렬화 | 8 KiB | 그 도구를 `{ name, description, schemasOmitted: true }` 로 줄인다 |
| `tools` 전체 | 실패한 케이스의 도구만이라 자연히 묶인다 | 별도 상한 없음 |

`8 KiB` 의 근거: 관측된 실제 MCP 도구 스키마는 대부분 1 KiB 아래이고, 8 KiB 를 넘는 것은
`$defs` 가 수십 개 달린 생성 스키마다. 그런 스키마는 통째로 실어도 AI 가 원인을 좁히는 데
쓰지 못하고 요청 예산만 먹는다. `MAX_REQUEST_BYTES` 검사에 걸려 요청 전체가 거절되는 것보다
그 도구만 줄이는 편이 낫다.

**줄였다는 사실을 `schemasOmitted: true` 로 남긴다.** 조용히 빼면 AI 는 그 도구에 스키마가
없다고 읽는다. 없는 것과 안 보낸 것은 다르다.

기존 `truncated` 필드와 같은 자리에 `truncated.toolSchemas` 로 개수를 센다.

## 4. 호환

`REPAIR_BUNDLE_VERSION` 을 `3` 으로 올린다. `readRepairBundle` 은 `2` 를 거절하고 기존
`versionMismatch` 문장이 그대로 뜬다. 그 문장은 이미 "최신 `mcpeak test --repair-bundle` 로
다시 만드세요" 라고 말한다. 고칠 것이 없다.

`failureShapeValid` · `specShapeValid` 의 기준은 **읽는 값**이다. 그 원칙을 유지한다.

| 새 필드 | 필수인가 |
|---|---|
| `failures[].assertions` | 필수. 배열이어야 하고 각 항목의 `type` 이 문자열, `status` 가 세 값 중 하나 |
| `tools` | 필수. 배열이어야 한다. 빈 배열은 허용한다(`listTools` 실패만 있는 번들) |
| `target` | 필수. `transport` 와 `label` 이 문자열 |
| `process.scope` | `process` 가 있을 때만 필수 |

## 5. 사용자 제공 소스 맥락은 이번 범위가 아니다

이슈가 "사용자 제공 소스 맥락은 명시적인 파일 범위와 전송 미리보기로 다룬다" 고 적었다.
**이번에 하지 않는다.**

- 파일을 읽어 보내는 기능은 확인 화면·범위 지정·마스킹·크기 상한을 새로 다 만들어야 한다.
  이 설계가 닫는 네 항목과 크기가 비슷한 별도 작업이다
- 위 네 항목은 우리가 이미 손에 쥔 값을 안 싣고 있는 것이다. 새 입력 통로가 필요 없다
- 소스를 보내는 기능은 "보낼 파일을 사용자가 실제로 확인했는가" 가 핵심이고, 그것을 대충
  하면 비밀값이 나간다. 급하게 얹을 것이 아니다

이슈에 후속으로 남긴다.

## 6. 완료 조건

1. `weather` 서버로 만든 번들의 `tools` 에 실패한 케이스가 부른 도구의 `inputSchema` 가
   들어 있다.
2. 그 번들로 `repair --dry-run` 을 돌리면 진단 요청의 `tools` 가 **비어 있지 않다.**
3. 실패하지 않은 도구의 선언은 `tools` 에 없다.
4. 케이스마다 `assertions` 가 전량 있고, 통과한 단언도 `status: "passed"` 로 들어 있다.
5. `target` 에 `transport` 만 있다. 실행 명령·URL·서버 이름·버전이 번들 어디에도 없다.
   비밀값이 든 명령으로 만든 번들의 직렬화 결과에 그 원문이 없다.
6. `process` 가 있으면 `scope: "suite"` 가 있고, 프롬프트에 stderr 읽는 법 문단이 있다.
7. 8 KiB 를 넘는 스키마를 가진 도구는 `schemasOmitted: true` 로 줄고 `truncated.toolSchemas`
   가 그 개수를 센다.
8. 버전 2 번들을 주면 `versionMismatch` 로 거절하고 기존 문장이 뜬다.
9. 같은 실행에서 두 번 만든 번들이 바이트 단위로 같다.

## 7. 비범위

- 사용자 제공 소스 파일 전송. §5 에 사유를 적었다.
- 케이스별 stderr 수집. `core` 가 프로세스 전체로만 모으고 있고, 케이스 경계로 자르는 것은
  `core` 의 작업이다. 이번에는 **범위를 사실대로 표시하는 것**까지다.
- 단언의 기대값 전문. §2.2 에 사유를 적었다.
- **실행 대상 식별(명령·URL)과 서버 이름·버전.** §2.3 에 사유를 적었다. 전자는 ADR-0097 의
  마스킹 규칙이 `record` 내부 전용이라 규칙을 두 벌 만들지 않고는 못 싣고, 후자는 핸드셰이크
  결과가 `McpClient` 에 없는데 그 인터페이스가 변경 금지다. 둘 다 그 제약이 풀리면 할 수 있다.
  `record` 가 `redactOriginArgs` 를 공개 API 로 내보내면 전자는 바로 붙는다.
