# 범위 위반은 상한과 하한을 따로 검증한다

2026-09-13. 이슈 [#387](https://github.com/2026-Engineering-Contest/MCPeak/issues/387) 을 닫는다.

하한과 상한이 함께 선언된 필드에서 **우리 생성기는 하한 위반만 만들고, 커버리지는 그것을
범위 전체를 덮은 것으로 표시한다.** 상한 검사를 통째로 빼먹은 서버가 생성 스위트 12건을 전부
통과한다. 테스트 도구가 결함을 못 잡는데 화면은 초록이므로, 이 프로젝트에서 가장 나쁜 종류의
결함이다.

- 관련 ADR: [ADR-0100](./adr/0100-범위-밖-호출-관측은-기록자의-것만-센다.md) (직전 회차)
- 재현 기준 커밋: `c0a1934fd2c1147556080d7f78f8b9e4b0a3f717`

## 1. 문제

### 1.1 위반 값이 하한 쪽에서만 나온다

`packages/generate/src/violation-cases.ts` 의 `rangeViolationValue` 는 하한을 먼저 보고,
만들 수 있으면 **거기서 끝낸다.**

```ts
if (range.minimum !== null) return range.minimum - 1;
...
if (range.maximum !== null) return range.maximum + 1;   // 하한이 있으면 여기 못 온다
```

`n: { type: "integer", minimum: 1, maximum: 10 }` 이면 위반 값은 `0` 하나다. `11` 은 만들어지지
않는다. 상한 검사를 뺀 변이 서버(`n >= 1` 만 검사)는 생성된 12건을 전부 통과한다. 실행으로
재현했다.

### 1.2 축이 필드당 하나라 커버리지가 거짓말을 한다

`packages/runner/src/contract-axes.ts` 의 축 정체성은 `(kind, field)` 다.

```ts
for (const [name, field] of analysis.schema.fields)
  if (field.enumValues === null && rangeYieldsViolation(field.range))
    axes.push(axis("RANGE_VIOLATION", name, null, null, field.range));
```

`minimum` 과 `maximum` 이 둘 다 있어도 축은 `RANGE_VIOLATION n` 하나다. 하한 위반 케이스
하나가 이 축을 덮으면 커버리지는 `1/1` 로 **범위 전체가 검증됐다고 보고한다.** 분모가 실제
검증 대상보다 작다.

생성기만 고치면 생성 스위트에서는 두 케이스가 늘 함께 나오므로 겉으로는 문제가 안 보인다.
그러나 손으로 쓴 명세와 AI 작성 경로(`authoring-session.ts`)에서는 한쪽만 있는 스위트가
그대로 `1/1` 로 찍힌다. **분모를 안 고치면 거짓 초록이 남는다.**

### 1.3 상한 경계값을 아무도 호출하지 않는다

`synthesize.ts` 는 하한이 있으면 하한을 정상값으로 쓴다(`minimum: 1` → `1`). 상한이 함께
있어도 `10` 은 어떤 케이스에서도 호출되지 않는다. `n <= 9` 로 잘못 구현한 서버(off-by-one)를
못 잡는다. 경계는 결함이 가장 많이 사는 자리인데 한쪽 경계만 밟고 있다.

## 2. 결정

세 가지를 함께 고친다. 하나만 하면 나머지 둘이 거짓 신호로 남는다.

1. **`runner` 의 `RANGE_VIOLATION` 축을 상·하한으로 쪼갠다.** 축 정체성을
   `(kind, field, bound)` 로 넓힌다.
2. **`generate` 가 하한 미만과 상한 초과 위반 케이스를 각각 만든다.**
3. **`generate` 가 상한 경계 정상 케이스를 추가한다.** 하한 경계는 정상 케이스가 이미 밟고
   있으므로 상한 쪽만 채우면 네 지점이 모두 채워진다.

`cli` 커버리지 화면은 두 축을 구분해 찍는다. 같은 문장이 두 줄 나오면 사용자가 무엇이
미검증인지 읽을 수 없다.

### 2.1 왜 `ContractAxisKind` 를 늘리지 않는가

`RANGE_VIOLATION_LOWER` / `RANGE_VIOLATION_UPPER` 로 종류를 늘리는 대안이 있었다. 버린다.

`cli` 의 `AXIS_LABEL` 은 `Record<ContractAxisKind, string>` 이고, 그 주석은 축이 늘면 여기서
컴파일이 깨지도록 일부러 그렇게 만들었다고 적는다. 종류를 늘리면 그 의도가 발동해 `cli` 가
같은 PR 에서 깨진다. 그리고 종류를 늘리면 "범위 위반" 이라는 한 개념이 두 이름으로 갈라져
`AXIS_LABEL` 에 사실상 같은 문장이 두 번 들어간다.

`bound` 를 필드로 더하면 종류는 그대로고, 축 정체성만 넓어진다. 화면은 기존 문장 뒤에
`(하한)` · `(상한)` 을 붙이면 된다.

## 3. 공유 계약 변경

### 3.1 `packages/runner/src/contract-range.ts`

```ts
/** 범위의 어느 쪽 경계인가. RANGE_VIOLATION 축을 상·하한으로 가른다. */
export type ContractRangeBound = "lower" | "upper";

/**
 * 값이 어느 쪽 경계를 벗어났는지. 벗어나지 않았으면 빈 배열이다.
 *
 * 배열로 내는 이유: `minimum: 10` · `maximum: 1` 처럼 만족 불가능한 선언에서는 한 값이 양쪽을
 * 동시에 어긴다. runner 는 해석기이지 검증기가 아니므로(§3.1) 그런 선언을 거절하지 않는다.
 * 하나만 고르면 어느 쪽을 버릴지에 판단이 들어가고, 그 판단은 여기 있을 자리가 아니다.
 *
 * 순서는 항상 lower 먼저다. 결정론성 때문이다.
 */
export function violatedBounds(
  range: ContractRange,
  value: JsonValue,
): readonly ContractRangeBound[];
```

판정 규칙은 기존 `violatesRange` 와 **정확히 같고**, 어느 조건에서 참이 됐는지만 나눈다.

| 값의 형태 | lower 위반 조건 | upper 위반 조건 |
|---|---|---|
| 유한한 number | `value < minimum` 또는 `value <= exclusiveMinimum` | `value > maximum` 또는 `value >= exclusiveMaximum` |
| string | `코드포인트길이 < minLength` | `코드포인트길이 > maxLength` |
| array | `value.length < minItems` | `value.length > maxItems` |
| 그 밖 | 없음 | 없음 |

`violatesRange` 는 `violatedBounds(range, value).length > 0` 으로 남긴다. 지우지 않는다.
`input-contract.ts` 가 쓰고 있고, 그쪽은 어느 쪽 경계인지 알 필요가 없다.

### 3.2 `packages/runner/src/contract-axes.ts`

`ContractAxis` 에 필드 하나를 더한다. **기존 필드는 건드리지 않는다.**

```ts
export interface ContractAxis {
  readonly kind: ContractAxisKind;
  readonly tool: string;
  readonly field: string | null;
  readonly declaredType: ContractDeclaredType | null;
  readonly declaredEnum: readonly JsonValue[] | null;
  readonly declaredRange: ContractRange | null;
  /**
   * 범위의 어느 쪽 경계를 보는 축인지. RANGE_VIOLATION 에서만 값이 있고 그 밖에는 null 이다.
   * 축 정체성은 이제 (kind, field, bound) 다. 이것을 키에서 빼면 한쪽 경계만 검사한 스위트가
   * 범위 전체를 덮은 것으로 세어진다(이슈 #387).
   */
  readonly bound: ContractRangeBound | null;
}
```

`deriveContractAxes` 의 RANGE 블록:

```ts
for (const [name, field] of analysis.schema.fields) {
  if (field.enumValues !== null || field.range === null) continue;
  // 순서는 lower 다음 upper 로 고정한다. 필드 순서는 analyzeInputSchema 가 이미 코드 단위로
  // 정렬해 두었으므로 여기서 다시 정렬하지 않는다.
  if (hasUsableLowerBound(field.range))
    axes.push(axis("RANGE_VIOLATION", name, null, null, field.range, "lower"));
  if (hasUpperBound(field.range))
    axes.push(axis("RANGE_VIOLATION", name, null, null, field.range, "upper"));
}
```

`rangeYieldsViolation` 은 `hasUsableLowerBound || hasUpperBound` 이므로, 이 형태는 기존에 축을
만들던 범위에서만 축을 만든다. 새로 생기는 것은 **양쪽이 다 있을 때 축이 하나 더 나오는 것**
뿐이다.

`violatedAxes` 의 RANGE 블록은 `violatesRange` 대신 `violatedBounds` 를 써서 위반한 쪽의 축만
낸다.

```ts
else if (
  rangeYieldsViolation(field.range) &&
  !nullSatisfiesField(field, input[name] as JsonValue)
)
  for (const bound of violatedBounds(field.range, input[name] as JsonValue))
    rangeAxes.push(contractAxis(tool, "RANGE_VIOLATION", name, null, null, field.range, bound));
```

`contractAxis` 와 지역 `axis` 헬퍼는 `bound` 를 마지막 선택 인자(`= null`)로 받는다. 그래야
RANGE 아닌 호출부를 한 줄도 안 고친다.

### 3.3 `packages/generate/src/coverage.ts`

축 키에 `bound` 를 넣는다. **세 곳을 같은 식으로 고쳐야 한다.** 하나라도 빠지면 `coveredBy`
조회가 어긋나 전부 미검증으로 찍힌다.

```ts
const axisKey = (axis: { kind: ContractAxisKind; field: string | null; bound: ContractRangeBound | null }): string =>
  `${axis.kind} ${axis.field ?? ""} ${axis.bound ?? ""}`;
```

`AxisCoverage` 에도 `bound` 를 싣는다. 화면이 두 축을 구분하려면 이 값이 필요하다.

```ts
export interface AxisCoverage {
  readonly kind: ContractAxisKind;
  readonly field: string | null;
  /** RANGE_VIOLATION 에서만 값이 있다. 화면이 (하한)·(상한) 을 붙이는 근거다. */
  readonly bound: ContractRangeBound | null;
  readonly caseId: string | null;
}
```

## 4. 생성 케이스

### 4.1 위반 값

`rangeViolationValue` 를 방향별 두 함수로 가른다. 만들 수 없으면 `undefined` 이고, 그러면
그 방향의 케이스를 만들지 않는다.

**`lowerViolationValue(range, fieldSchema, path, root)`**

우선순위대로 첫 번째로 맞는 것을 쓴다.

| 조건 | 값 |
|---|---|
| `fieldSchema.type === "integer"` 이고 `integerLowerBound(minimum, exclusiveMinimum) !== null` | 그 값 `- 1` |
| `minimum !== null` | `minimum - 1` |
| `exclusiveMinimum !== null` | `exclusiveMinimum` |
| `minItems !== null && minItems >= 1` | 원소 `minItems - 1` 개의 배열 |
| `minLength !== null && minLength >= 1` | 길이 `minLength - 1` 의 문자열 |
| 그 밖 | `undefined` |

**`upperViolationValue(range, fieldSchema, path, root)`**

| 조건 | 값 |
|---|---|
| `fieldSchema.type === "integer"` 이고 `integerUpperBound(maximum, exclusiveMaximum) !== null` | 그 값 `+ 1` |
| `maximum !== null` | `maximum + 1` |
| `exclusiveMaximum !== null` | `exclusiveMaximum` |
| `maxItems !== null` | 원소 `maxItems + 1` 개의 배열 |
| `maxLength !== null` | 길이 `maxLength + 1` 의 문자열 |
| 그 밖 | `undefined` |

integer 를 먼저 보는 이유는 기존 주석에 있는 것과 같다. `minimum: 1.2` 에 `-1` 을 하면 `0.2`
가 나와 자기 type 을 어기고, 그러면 그 케이스가 `TYPE_VIOLATION` 축을 덮어 범위 축이 영원히
미검증으로 남는다. 상한 쪽도 대칭으로 같은 위험이 있다(`maximum: 1.8` 에 `+1` 은 `2.8`).

**기존 동작이 바뀌는 지점이 하나 있다.** 지금은 integer 이면서 하한이 없고 상한만 있을 때
`integerUpperBound + 1` 을 하한 함수 안에서 처리했다. 이제 그 경로는 `upperViolationValue`
가 맡는다. 값은 같고 케이스 id 와 이름만 `upper` 쪽으로 간다.

### 4.2 케이스 id 와 이름

축 순서(lower → upper)대로 만든다.

| 방향 | id | name |
|---|---|---|
| lower | `${baseName}-range-lower-${fieldSlug(field)}` | `${tool.name}가 '${field}' 하한 미만 값을 거절한다` |
| upper | `${baseName}-range-upper-${fieldSlug(field)}` | `${tool.name}가 '${field}' 상한 초과 값을 거절한다` |

id 접두사가 `range` 에서 `range-lower` / `range-upper` 로 바뀐다. 기존 생성 스위트의 id 가
바뀌므로 changeset 은 minor 다.

`uniqueId` 의 중복 회피 규칙(`-2`, `-3` 접미사)은 그대로 쓴다. 접두사만 방향별로 다르다.

### 4.3 상한 경계 정상 케이스

`hasUpperBound(range)` 이고 **정상 입력의 그 필드 값이 상한 경계값과 다를 때만** 만든다.
하한만 있거나 상한만 있으면 정상 케이스가 이미 그 경계를 밟고 있으므로 중복이다
(`synthesize.ts` 는 하한이 있으면 하한을, 하한이 없고 상한만 있으면 상한을 쓴다).

경계값은 `upperViolationValue` 의 표에서 한 칸 안쪽이다.

| 조건 | 값 |
|---|---|
| `fieldSchema.type === "integer"` 이고 `integerUpperBound(maximum, exclusiveMaximum) !== null` | 그 값 |
| `maximum !== null` | `maximum` |
| `exclusiveMaximum !== null` | 만들지 않는다 |
| `maxItems !== null` | 원소 `maxItems` 개의 배열 |
| `maxLength !== null` | 길이 `maxLength` 의 문자열 |
| 그 밖 | 만들지 않는다 |

`exclusiveMaximum` 을 number 에서 만들지 않는 이유: 실수에서 "경계 바로 안쪽" 이 정의되지
않는다. `exclusiveMaximum: 10` 의 정상 최댓값은 `10` 도 `9` 도 아니다. 지어낸 값으로 정상
케이스를 만들면 서버가 거절해도 그것이 서버 결함인지 우리가 만든 값이 나쁜 건지 구분할 수
없다. integer 는 `integerUpperBound` 가 답을 주므로 만든다.

- id: `${baseName}-bound-upper-${fieldSlug(field)}`
- name: `${tool.name}가 '${field}' 상한 경계값에 정상 응답한다`
- assertions: `[{ type: "isError", expected: false }]` 에 출력 계약이 지원되면
  `structuredContentMatchesSchema` 를 잇는다. 정상 케이스와 같은 단언이어야 같은 강도로
  검증된다.

이 케이스는 어떤 축도 새로 만들지 않는다. `matchCoveredAxes` 가 `HAPPY_PATH` 로 판정하는데
그 축은 정상 케이스가 이미 덮고 있고, `coverage.ts` 는 첫 케이스만 남기므로 분자도 안 늘어난다.
커버리지 숫자는 그대로고 실제 검증만 늘어난다.

### 4.4 출력 계약을 붙이려면 호출 지점이 바뀐다

`buildViolationCases` 는 이름 그대로 위반만 만든다. 상한 경계 케이스는 정상 케이스라
거기 넣지 않는다. `render.ts` 의 `buildSuite` 가 출력 계약을 손에 쥐고 있으므로 새 함수를
따로 내보내고 거기서 부른다.

```ts
export function buildUpperBoundaryCases(options: {
  readonly tool: ToolDef;
  readonly happyInput: JsonObject;
  readonly baseName: string;
  /** 출력 계약이 지원되면 그 스키마. 아니면 null. 정상 케이스와 같은 단언을 붙인다. */
  readonly responseSchema: ResponseSchema | null;
}): readonly GeneratedCase[];
```

`buildSuite` 의 `cases` 배열 순서는 `정상 → 상한 경계 정상 → 위반` 이다. 정상 계열을 붙여
두어야 실패 목록을 위에서부터 읽을 때 "정상이 되는 입력" 이 한 덩어리로 보인다.

## 5. 화면

`packages/cli/src/generate-command.ts` 의 `axisLabel` 이 `bound` 를 받는다. `AXIS_LABEL` 은
그대로다.

```
선언된 범위 밖 값 거절 (n, 하한)
선언된 범위 밖 값 거절 (n, 상한)
```

`bound` 가 null 이면 기존 문장 그대로다. 괄호 안은 `field` 와 `bound` 를 쉼표로 잇고, 둘 중
하나만 있으면 있는 것만 넣는다.

## 6. 완료 조건

전부 실행으로 판정한다.

1. `n: { type: "integer", minimum: 1, maximum: 10 }` 에서 생성 케이스에 `n: 0` 과 `n: 11` 이
   둘 다 있고, 정상 케이스로 `n: 1` 과 `n: 10` 이 둘 다 있다.
2. 상한 검사만 뺀 목 서버(`n >= 1` 만 검사)가 생성 스위트에서 **실패한다.**
3. 하한 검사만 뺀 목 서버(`n <= 10` 만 검사)가 생성 스위트에서 **실패한다.**
4. 두 경계를 모두 검사하는 정상 목 서버는 전부 통과한다.
5. 커버리지 분모가 그 필드에서 2 다. 하한 위반 케이스만 든 손수 작성 스위트의 커버리지는
   `1/2` 이고 상한 축의 `caseId` 가 null 이다.
6. 같은 입력으로 두 번 생성한 결과가 바이트 단위로 같다.

## 7. 비범위

- 중첩 객체·배열 원소 안의 범위 제약(이슈 #388 이 맡는다). 이번에는 최상위 필드만이다.
- enum 이 함께 선언된 필드. 기존 판단대로 `ENUM_VIOLATION` 축이 대신한다.
- `multipleOf`, `uniqueItems` 등 표에 없는 제약.
- `exclusiveMaximum` 의 실수 경계 정상값. §4.3 에 사유를 적었다.
