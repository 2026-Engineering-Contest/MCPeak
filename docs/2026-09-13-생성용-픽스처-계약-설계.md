# 생성용 픽스처 계약

2026-09-13. 이슈 [#390](https://github.com/2026-Engineering-Contest/MCPeak/issues/390) 을 닫는다.

스키마가 `string` 이라는 사실만으로 **존재하는 파일 경로, 유효한 도시 이름, 실재하는 DB
레코드 ID** 를 알 수 없다. 우리는 `"example"` 을 넣고, 서버는 그것을 거절한다. 그리고
화면은 그것을 서버 결함처럼 보여준다.

- 검토 기준 커밋: `c0a1934fd2c1147556080d7f78f8b9e4b0a3f717`
- 실측 기록: [adoption.md](./adoption.md) §경로 교정
- 값 출처 표기의 직전 회차: 이슈 #286 (`proposedBy`)

## 1. 문제

### 1.1 `"example"` 은 어떤 자원도 가리키지 않는다

`server-filesystem` 실측에서 **실패 8건이 전부 도메인 값 문제**였다. `synthesizeValue` 가
만든 `"example"` 이 경로 자리에 들어가 `ENOENT` 가 났다. 서버는 정상이었다.

우리 자체 날씨 서버에서도 baseline `city: "example"` 이 실패했다. 서버는 도시 목록을 갖고
있고 `"example"` 은 거기 없다. **정확히 옳게 동작한 것이다.**

### 1.2 값 문제와 서버 결함이 화면에서 같아 보인다

두 실패가 화면에서 구분되지 않는다.

| 실제 원인 | 사용자가 해야 할 일 |
|---|---|
| 서버가 유효한 입력을 거절한다 | 서버 코드를 고친다 |
| 우리가 지어낸 값이 유효하지 않다 | **테스트 데이터를 준비한다** |

지금은 둘 다 `✗ 오류 없이 응답한다 — 실패` 로 나온다. 사용자는 서버 코드를 열어 한참
들여다본 뒤에야 값 문제였다는 것을 안다.

### 1.2.1 `format` 은 형식을 보장하지 존재를 보장하지 않는다

**2026-09-13 실측.** 이슈 #401 구현 중 도그푸딩 E2E 가 잡았다. 이 이슈의 가장 좁고 가장
날카로운 사례다.

`examples/zod-notes-server` 의 선언이다.

```js
parentId: z.string().uuid().optional().describe("상위 노트 id"),
```

우리는 `FORMAT_VALUES` 의 `00000000-0000-4000-8000-000000000000` 을 넣는다. **스키마상 완전히
유효하다.** 그런데 서버는 `server.mjs:100` 에서 한 가지를 더 본다.

```js
if (input.parentId !== undefined && !Object.hasOwn(NOTES, input.parentId)) return fail(...);
```

그 노트는 없다. **정상 서버가 우리 정상 케이스를 옳게 거절한다.**

`FORMAT_VALUES` 주석은 "실존 자원을 가리키지 않는다" 를 이미 적어 두었지만, 그것을 **dry run
부작용이 없다는 근거**로만 썼다. 같은 사실이 **정상 케이스를 만들 수 없다는 근거**이기도
한데 그쪽은 어디에도 적혀 있지 않았다.

깨지는 조건은 셋이 겹칠 때다.

| 조건 | 예 |
|---|---|
| `format` 이 표에 있다 | `uuid` · `uri` · `hostname` · `email` · `ipv4` · `ipv6` |
| 후보 키워드(`const`·`default`·`examples`·`enum`)가 없다 | 서버가 실제 값을 안 적었다 |
| 서버가 그 값의 **존재**를 확인한다 | 조회·전송 대상을 받는 툴 |

**위반 케이스는 멀쩡하다.** 거절을 기대하는 케이스는 값이 실재하지 않아도 무방하다. 이
문제는 정상 케이스에만 있다.

#401 은 선택 필드의 '있음' 케이스를 **만들지 않는 것**으로 막았다. 정직하지만 반쪽이다.
그 필드의 정상 분기가 영구히 skip 으로 남는다. **탈출구가 서버 선언의 후보 키워드뿐이고,
서버가 `default`·`examples` 를 안 적으면 길이 없다.** 픽스처 계약이 메워야 할 구멍이
정확히 거기다.

**필수 필드는 아직 안 막혀 있다.** `render.ts` 의 기준 정상 입력은 종전대로 표 값을 쓴다.
필수 필드에 존재 확인이 걸린 서버는 `-success` 케이스가 같은 이유로 깨진다. zod 예제가
안 걸린 것은 `get_note.id` 에 `.examples` 가 있어서이고 **운이다.** 거기는 skip 으로 넘길
수 없다 — 정상 케이스가 없으면 그 툴의 검증이 통째로 사라진다. §2.4 의 해석 순서에서
`userFixture` 가 1순위인 이유가 이것이다.

**이 사실을 유닛테스트가 못 잡는다.** 전부 인메모리라 "서버가 값의 존재를 확인한다" 를
흉내 낼 대상이 없다. 도그푸딩 E2E 만 볼 수 있었다.

### 1.3 고친 값이 한 번 쓰이고 사라진다

`packages/cli/src/input-repair.ts` 의 캐시다.

```ts
/**
 * 사람이 확인했고 재실행까지 통과한 값. `(tool, 필드명)` 하나당 하나다.
 * 이 호출이 끝나면 사라진다(§4.6).
 */
const cache = new Map<string, JsonValue>();
```

주석이 사실을 말한다. 사용자가 대화형으로 12개 필드를 고쳐 통과시켜도, 다음에 `generate` 를
다시 돌리면 **처음부터 다시 묻는다.** AI 제안과 사람 교정은 있는데 그것을 **다시 쓸 자리가
없다.**

### 1.4 값끼리 간섭하는데 그것을 적을 데가 없다

실측에 이렇게 적혀 있다.

> `write_file` 이 만든 파일과 `create_directory` 가 만들 디렉터리에 같은 경로를 주면
> `EEXIST` 가 난다.

부작용이 있는 도구를 한 스위트에서 돌리면 값끼리 부딪힌다. 사용자가 도구마다 다른 경로를
줘야 하는데, 그 의도를 적어 둘 파일이 없다.

## 2. 결정

**픽스처 파일 하나를 계약으로 만든다.** 사용자가 도구·필드별로 값을 선언하고, 그 값이 어디서
왔는지를 생성기가 끝까지 들고 다닌다.

### 2.1 값의 출처를 타입으로 만든다

이것이 이 설계의 뼈대다. 나머지는 전부 여기서 나온다.

```ts
export type ValueProvenance =
  /** 사용자가 픽스처 파일에 적었다. 실재하는 자원을 가리킨다고 사용자가 보증한 값. */
  | "userFixture"
  /** 서버 선언의 const · default · examples · enum 에서 왔다. 서버가 준 값이다. */
  | "schemaDeclared"
  /** 우리가 type·format·pattern 만 보고 지어냈다. 어떤 자원도 가리키지 않는다. */
  | "schemaHint"
  /** AI 가 제안했고 사람이 확인했다. */
  | "aiProposed"
  /** 사람이 교정 화면에서 직접 입력했다. */
  | "humanRepaired";
```

`schemaHint` 가 핵심이다. **그 값은 우리가 지어낸 것이고 실재를 보증하지 않는다.** 이 사실
하나만 알면 §1.2 가 닫힌다.

### 2.2 실패 진단이 출처를 읽는다

케이스가 실패했을 때, 그 케이스 입력에 `schemaHint` 출처의 값이 있으면 화면이 그것을 말한다.

```
✗ get_weather-success  get_weather가 오류 없이 응답한다
    isError  정상 응답을 기대했지만 오류 응답을 받았습니다.
    → 서버 응답: Unknown city: example
    ℹ 이 케이스의 'city' 값 "example" 은 스키마의 type 만 보고 만든 자리값입니다.
      실재하는 자원을 가리키지 않으므로 서버 결함이 아닐 수 있습니다.
      해결: mcpeak.fixtures.json 에 get_weather.city 값을 지정하세요.
```

**필드 이름으로 추측하지 않는다.** `city` · `path` · `id` 같은 이름 표를 만들고 싶어지지만
버린다. 이름이 `q` 나 `target` 인 자원 식별자를 놓치고, 이름이 `name` 인 순수 문자열에
잘못 붙는다. 판정 근거는 **그 값을 우리가 지어냈는가** 하나다. 그것은 추측이 아니라 사실이다.

### 2.3 픽스처 파일 형식

`mcpeak.fixtures.json`. `--fixtures <path>` 로 바꿀 수 있다.

```json
{
  "schemaVersion": 1,
  "tools": {
    "read_file": {
      "path": "./fs-sandbox/a.txt"
    },
    "create_directory": {
      "path": "./fs-sandbox/new-dir"
    },
    "get_weather": {
      "city": "Seoul"
    }
  },
  "notes": {
    "read_file.path": "setup.sh 가 만든다. write_file 과 경로가 겹치면 EEXIST 가 난다."
  }
}
```

| 키 | 뜻 |
|---|---|
| `tools.<도구>.<필드>` | 그 도구의 그 최상위 필드에 쓸 값. JSON 값 전부 허용 |
| `notes.<도구>.<필드>` | 사람이 읽을 메모. 값에 영향을 주지 않는다 |

`notes` 가 §1.4 를 받는 자리다. "왜 이 값인가" 와 "무엇과 겹치면 안 되는가" 를 적는다.
화면에는 그 필드가 실패했을 때만 찍는다.

**전역 기본값(필드 이름만으로 매칭)은 만들지 않는다.** `path` 하나로 모든 도구를 덮으면
§1.4 의 간섭이 곧바로 난다. 도구마다 따로 적게 하는 것이 귀찮지만 옳다.

### 2.4 해석 순서

한 필드의 값을 정할 때 위에서부터 첫 번째로 맞는 것을 쓴다.

| 순서 | 출처 | 근거 |
|---|---|---|
| 1 | `userFixture` | 사용자가 명시했다. 무엇보다 우선한다 |
| 2 | `schemaDeclared` | 서버가 `const`·`default`·`examples`·`enum` 으로 줬다 |
| 3 | `schemaHint` | 우리가 지어낸다. 기존 `synthesizeValue` 그대로 |

1번이 2번보다 앞인 이유: `default` 가 자리값인 서버가 많다. 사용자가 실재 값을 줬는데
서버의 `default` 가 이기면 픽스처 파일이 무의미해진다.

**픽스처 값이 스키마를 어기면 거절한다.** `UNSUPPORTED_SCHEMA` 가 아니라 새 코드
`INVALID_FIXTURE_VALUE` 다. 사용자가 고칠 곳이 스키마가 아니라 픽스처 파일이다.

```
오류 [INVALID_FIXTURE_VALUE]: 픽스처 값이 도구 선언을 만족하지 않습니다:
  get_weather.city
  값: 42
  선언: { "type": "string" }
해결: mcpeak.fixtures.json 의 해당 값을 선언에 맞게 고치세요.
```

### 2.5 교정한 값을 픽스처로 되돌린다

§1.3 을 닫는다. 교정이 끝나면 그 값을 픽스처 파일에 쓸지 묻는다.

```
교정한 값 3건을 mcpeak.fixtures.json 에 저장할까요?
  read_file.path      "./fs-sandbox/a.txt"       (사람이 입력)
  get_weather.city    "Seoul"                    (AI 제안, 사람이 확인)
  create_dir.path     "./fs-sandbox/new-dir"     (사람이 입력)
```

거절하면 안 쓴다. 파일을 말없이 고치지 않는다.

`--yes` 로 돌면 **쓰지 않는다.** 파일을 만드는 것은 사용자 작업 공간을 바꾸는 일이고,
`--yes` 는 "질문에 전부 예" 이지 "내 파일을 고쳐도 좋다" 가 아니다. 비대화형에서는 안내만
찍는다.

## 3. 비밀값은 받지 않는다

이슈가 "외부 비밀값을 저장 명세에 넣지 않는다" 고 적었다. **가리는 것이 아니라 받지 않는
것으로 푼다.**

`$env` 같은 참조 문법을 만들지 않는다. 만들면 두 가지 중 하나를 해야 한다.

| 선택 | 문제 |
|---|---|
| 생성 시점에 풀어 명세에 넣는다 | **비밀값이 디스크에 그대로 쓰인다.** 그 명세는 커밋된다 |
| 참조를 명세에 남기고 실행 시점에 푼다 | `runner` 가 참조를 알아야 한다. 명세 형식과 실행기가 동시에 바뀐다 |

전자는 하면 안 되고 후자는 이번 범위를 넘는다. 그래서 **픽스처 파일은 리터럴 값만 받는다.**

문서와 도움말에 이렇게 적는다.

> 픽스처 파일에 토큰·비밀번호·API 키를 적지 마세요. 이 파일의 값은 생성된 명세에 그대로
> 들어갑니다. 인증이 필요한 서버는 서버 기동 환경변수로 자격을 넘기고, 픽스처에는 그 자격으로
> 접근 가능한 **자원 식별자**만 적으세요.

`.gitignore` 에 넣으라고 권하지 않는다. 픽스처 파일은 **팀이 공유해야 재현된다.** 공유할 수
없는 것을 거기 넣지 말라는 것이 규칙이다.

## 4. 환경별 값과 테스트 의미를 나눈다

`./fs-sandbox/a.txt` 는 환경에 따라 다르고, "존재하는 읽기 가능한 파일" 은 어디서나 같다.

**이번에는 나누지 않는다.** 픽스처 파일은 환경별 값만 담는다.

이유: 의미를 분리하려면 "존재하는 파일" 같은 의미 이름 표를 우리가 정의해야 하고, 그 표는
곧 §2.2 에서 버린 필드 이름 추측과 같은 문제를 갖는다. 어떤 의미가 있는지 우리가 미리 알 수
없다. 사용자가 `notes` 에 문장으로 적는 것이 지금 할 수 있는 정직한 최선이다.

`schemaVersion: 1` 을 두는 이유가 이것이다. 나중에 의미 계층이 필요해지면 버전을 올린다.

## 5. 완료 조건

1. `mcpeak.fixtures.json` 에 `get_weather.city: "Seoul"` 을 적으면 생성된 정상 케이스의
   입력이 `{ "city": "Seoul" }` 이다.
2. 픽스처가 없으면 기존대로 `"example"` 이 들어가고 출처가 `schemaHint` 다.
3. 서버의 `default` 가 있어도 픽스처 값이 이긴다.
4. `schemaHint` 값이 든 케이스가 실패하면 §2.2 의 안내 세 줄이 찍힌다.
5. `userFixture` 값이 든 케이스가 실패하면 그 안내가 **안 찍힌다.** 사용자가 실재를
   보증한 값으로 서버 쪽을 먼저 봐야 한다.
5-1. `parentId: { type: "string", format: "uuid" }` 인 **선택** 필드에 픽스처로 실재하는 id 를
   주면 #401 이 만들지 않던 `-branch-with-parentid` 케이스가 생긴다. §1.2.1 이 남긴 구멍이
   메워지는 자리다.
5-2. 같은 선언이 **필수** 필드일 때 픽스처 값이 기준 정상 입력에 들어간다. 픽스처가 없으면
   종전대로 format 표 값이 들어가고 출처가 `schemaHint` 가 아니라 `schemaDeclared` 다.
   **`format` 에서 온 값의 출처를 무엇으로 셀지 T1 이 정하고 보고한다.** 형식은 서버가
   선언했지만 값은 우리가 표에서 골랐다. 둘 중 어느 쪽으로도 읽을 수 있다.
6. 픽스처 값이 스키마를 어기면 `INVALID_FIXTURE_VALUE` 로 거절하고 도구·필드·값·선언을
   찍는다.
7. 그 필드에 `notes` 가 있으면 실패 안내에 함께 찍힌다.
8. 교정 후 저장 질문에 예로 답하면 픽스처 파일이 생기고, 다시 `generate` 를 돌리면 그
   필드를 묻지 않는다.
9. 거절하거나 `--yes` 면 파일이 생기지 않는다.
10. 파일 형식이 깨졌으면 어느 줄이 문제인지 찍는다. 조용히 무시하지 않는다.
11. 같은 픽스처로 두 번 생성한 결과가 바이트 단위로 같다.

## 6. 비범위
