`docs/2026-10-03-mcp-보안-테스트-도구-시장조사.md` 다. 검사 목록의 보강(전 필드 검사, 실행 명령·공급망·독성
흐름·응답 검사, MCPTox 측정)은 `docs/2026-10-03-audit-검사-목록-보강-검토.md` 가 정하고, 단계 1 구현
계획은 그 문서의 §6 배치를 따른다. 이 문서는 **단계와 순서, 단계별 완료 조건,
단계 사이의 의존**만 고정한다. 각 단계의 구현 계획(태스크·Files·실행 프롬프트)은 단계 착수 시

## 0. 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 새 패키지 이름 | `@mcpeak/audit`, 경로 `packages/audit` | 보안 검사 로직의 집. `core` 에만 의존한다 |
| 오너 | 전원(5명). CODEOWNERS 에 `/packages/audit/` 를 공동 경로로 추가 | 사용자 결정 |
| 격리 수단 | Docker. `docker` CLI 를 자식 프로세스로 호출하고 SDK 의존성은 추가하지 않는다 | 격리 효과가 가장 확실하다(시장조사 §2 toolhive·mcp-harness). npm 의존 금지 규칙 준수 |
| Docker 없을 때 | 정적·프로토콜·드리프트·비밀 카나리 검사는 그대로 돌고, 행위 관측만 "관측 안 함" 으로 **명시 출력** | mcp-harness 의 local 모드 교훈. 격리 없는 결과를 격리된 것처럼 보이면 안 된다 |
| 판정 방식 | 정규식·유니코드 표·해시 비교만. LLM 판정과 외부 API 전송은 쓰지 않는다 | 결정론 원칙. 같은 서버에 두 번 돌리면 바이트 단위로 같은 출력 |
| 의존 방향 | `dashboard` → `cli` → `audit` → `core` | ADR-0091. optimize 와 같은 자리 |
| 대시보드 메뉴 | `Analyze` 하나에 **보안** 탭과 **토큰** 탭. 서버 접속은 한 번 | 입력이 같다(tools/list). 결과 모양도 "도구별 발견 목록" 으로 같다 |

ADR 초안 대상은 셋이다. (a) audit 패키지를 두는 결정과 Docker 격리 채택, (b) 외부 전송·LLM 판정
금지, (c) 사전 체험 프록시가 tools/call 을 어디까지 통과시키는가(§2 참조). 단계 1·2 착수 시 각각 쓴다.

## 1. 순서와 제안 대비 바뀐 점

사용자 제안은 **사전 체험 → 보안 검사 → 토큰 대시보드** 였다. 로드맵은 다음으로 조정한다.

```
단계 1  audit 패키지 핵심 검사 + mcpeak audit CLI      (Docker 불필요)
단계 2  Docker 격리 실행과 행위 관측 = 사전 보안 체험     (Docker 필요)
단계 3  대시보드 Analyze: 토큰 탭 → 보안 탭
```

바뀐 이유는 둘이다.

- **사전 체험은 검사 로직 없이는 빈 화면이다.** 격리 안에서 서버를 띄워 써 보는 것 자체는 사용자에게
  아무 판정을 주지 않는다. "이 서버가 설명에 숨은 지시를 담았다", "가짜 토큰이 응답에 나왔다" 를
  말하려면 규칙과 오라클이 먼저 있어야 한다. 그래서 검사 로직(단계 1)이 체험(단계 2)보다 앞이다.
  단계 1 만으로도 CLI 에서 사전 점검이 된다. 단계 2 는 거기에 격리와 행위 관측을 더한다.
- **토큰 탭이 보안 탭보다 싸다.** optimize 엔진과 CLI `--json` 이 이미 있어 대시보드는 라우트와 화면만
  더한다. 이것으로 Analyze 메뉴의 틀(접속 폼, 결과 목록 프리미티브, 탭)을 먼저 세우고, 보안 탭은 그
  틀에 끼운다. 보안 탭을 먼저 하면 틀 설계와 검사 결과 설계를 동시에 해야 한다.

단계 3 안의 탭 순서는 바꿔도 비용 차이가 작다. 단계 1·2 의 순서는 의존 관계라 바꿀 수 없다.

## 2. 단계별 범위와 완료 조건

### 단계 1. `@mcpeak/audit` 핵심 검사와 `mcpeak audit`

**범위**

- 패키지 골격: `packages/audit`, `core` 만 의존, tsdown 빌드, 루트 `turbo.json`·CODEOWNERS 갱신
  (공유 계약이라 선행 태스크로 분리).
- 검사 가족 네 개. 각 규칙은 id·심각도·메시지·고치는 법을 갖는다.
  - `description`: 주입 문형(ignore previous instructions, do not tell the user 류), 숨은 부차 행위
    문형(also collects, for caching purposes send 류), 도구 섀도잉(다른 도구·서버 이름을 거론하며
    행동을 바꾸라는 문형), 민감 경로 언급(`~/.ssh`, `.env`, `mcp.json`). 제로폭·양방향 제어·혼동
    공백 유니코드.
  - `schema`: 비밀 요구 필드명(`password`, `api_key`, `token` 류), 유출 통로 의심 필드명(`note`,
    `sidenote`, `feedback` 류, 설명이 "항상 포함" 을 요구할 때만), `readOnlyHint=true` 인데 설명이
    파괴적 동사를 쓰는 주석 불일치, `destructiveHint` 누락.
  - `protocol`: HTTP 대상이 `http://` 이면 평문 전송, 헤더 없이 접속이 성립하면 무인증 수락.
    stdio 대상은 해당 없음으로 출력.
  - `surface`: 도구 표면(이름·설명·inputSchema·annotations)을 정규화해 SHA-256 해시. 기준 파일이
    있으면 비교해 추가·삭제·변경을 심각도와 함께 출력(러그풀 탐지). 없으면 기준 파일을 쓴다.
- **비밀 카나리(Docker 불필요)**: 서버를 띄울 때 env 를 비우고, 사용자가 `--env` 로 준 이름에는
  값을 랜덤 토큰으로 바꿔 넣는다. tools/list 와 모든 검사 호출의 응답에 토큰이 나오면 유출 판정.
  `core` 가 spawn 을 소유하므로 추가 메커니즘 없이 된다.
- CLI `mcpeak audit <대상>`: 대상 옵션은 `optimize` 와 같은 `parseTestCommand` 를 쓴다. 사람용
  리포트와 `--json`. 종료 코드는 발견 심각도 최대값으로.
- 규칙 오탐 기준: `examples/` 의 모든 예제 서버에서 발견 0. 이것을 E2E 로 CI 에 넣는다.

**완료 조건**

- `examples/` 예제 서버 전부에서 `mcpeak audit` 발견 0, 그리고 `fixtures/` 에 추가한 악성 도구 정의
  픽스처(각 규칙당 최소 하나)에서 해당 규칙이 정확히 하나씩 발견.
- 같은 대상에 두 번 실행한 `--json` 출력이 바이트 단위로 같다.
- 실패 메시지가 무엇이 어디서 발견됐고 어떻게 고치는지를 담는다. 예:
  ```
  → 도구 'read_file' 설명에 숨은 지시가 있습니다: "do not tell the user" (설명 2번째 문장)
  → 이 서버를 신뢰하지 않는다면 등록하지 마세요. 서버 작성자라면 설명에서 모델 지시를 빼세요.
  ```

**모델 배분**: 규칙 문안과 실패 메시지, 해시 정규화 범위는 상위 모델. 패키지 골격·CLI 배선·리포트
렌더는 표준 모델.

### 단계 2. Docker 격리 실행과 행위 관측 = 사전 보안 체험

**범위**

- `mcpeak audit --sandbox` (또는 별도 `mcpeak try`, 구현 계획에서 확정). Docker 가 있으면 다음으로
  서버를 띄운다: `--network none`, 읽기 전용 루트, `--cap-drop ALL`, 비루트, 작업 디렉터리는 임시
  마운트. 서버 명령은 컨테이너 안에서 실행되고 stdio 는 `docker run -i` 로 호스트의 `core` 트랜스포트에
  이어진다.
- 오라클 셋. mcp-harness 설계를 따르되 코드는 가져오지 않는다(라이선스 없음).
  - 파일 카나리: 허용 디렉터리 밖에 랜덤 토큰 파일. 응답에 토큰이 나오면 파일 유출.
  - 아웃바운드 시도: `strace -f -e trace=connect` 또는 동등한 수단으로 `connect()` 기록. network none
    이라 실제로는 나가지 않지만 **시도 자체**를 증거로 남긴다.
  - 자식 프로세스: `execve()` 기록.
- 검사용 호출: 각 도구에 대해 스키마에서 만든 정상값 호출 한 번, 경로 순회·SSRF 형 페이로드 호출.
  페이로드는 고정 목록(결정론). `generate` 의 값 생성기를 재사용할 수 있으면 하되, 의존 방향상
  `audit` 가 `generate` 를 의존하지는 않는다(둘 다 `core` 위의 형제). 필요한 생성기는 `core` 로
  내리는 제안을 별도로 한다.
- Docker 가 없거나 데몬이 죽어 있으면: 단계 1 검사는 그대로 수행하고, 리포트 머리에
  "행위 관측 안 함: Docker 를 찾을 수 없습니다(설치: ...)" 를 명시한다. 조용히 통과시키지 않는다.
- 사용자 환경 불변 보장: 호스트 파일 시스템 마운트 없음(서버 코드는 이미지 안에서 설치하거나
  읽기 전용 마운트), 사용자 클라이언트 설정 파일을 읽거나 쓰지 않음, 호스트 env 미전달.

**완료 조건**

- `examples/` 에 의도적으로 취약한 예제 서버 하나를 추가(경로 순회 1개, 외부 접속 시도 1개, 자식
  프로세스 1개 도구). 이 서버에서 세 오라클이 각각 정확히 한 번 발견, 다른 예제 서버에서는 발견 0.
  이것은 Docker 를 쓰므로 **직렬 전용 E2E 웨이브**로 분리하고 CI 에서는 Docker 가 있는 러너에서만 돈다.
- 호스트에서 `docker ps` 로 컨테이너 잔존 0, 임시 디렉터리 잔존 0 (`core` 의 종료 정책과 같은 수준).
- Docker 없는 머신에서 실행하면 단계 1 결과 + 명시 경고가 나오고 종료 코드는 단계 1 결과를 따른다.

**모델 배분**: 컨테이너 격리 옵션과 오라클 판정 경계, "관측 안 함" 문안은 상위 모델. 나머지 표준.

### 단계 3. 대시보드 `Analyze`

**범위**

- 3a 토큰 탭: `POST /api/analyze/tokens` 가 대상 서버에 접속해 `optimize` 를 돌리고 `OptimizeOverlay`
  를 돌려준다. 화면은 원본·압축 크기, 변환별 기여, 도구별 감소 목록. 오버레이 저장 버튼은 CLI
  `--out` 과 같은 파일 계약.
- 3b 보안 탭: `POST /api/analyze/security` 가 `mcpeak audit --json` 과 같은 결과를 돌려준다. 화면은
  심각도별 발견 목록, 도구별 묶음, 드리프트 기준 파일 상태, 샌드박스 실행 여부와 Docker 미검출 경고.
  샌드박스 실행은 오래 걸리므로 기존 run-registry·SSE 로 진행을 흘린다.
- 두 탭은 같은 접속 폼을 쓴다. 대시보드는 `cli` 를 통해서만 `optimize`·`audit` 에 닿는다
  (의존 방향).

**완료 조건**

- `examples/` 서버를 대상으로 토큰 탭 숫자가 CLI `mcpeak optimize` 리포트와 같다.
- 보안 탭 발견 목록이 CLI `mcpeak audit --json` 과 같다(순서 포함).
- Docker 없는 환경에서 보안 탭이 "행위 관측 안 함" 을 화면에 보인다.

## 3. 의존 그래프와 터미널 분할

```
단계 1 ─┬─ 1-0 공유 계약(패키지 골격, turbo, CODEOWNERS, fixtures 악성 정의)   [직렬, 먼저]
        ├─ 1-A description·schema 규칙          ┐
        ├─ 1-B protocol·surface(해시·드리프트)   ├ 병렬 3터미널 (Files 겹침 없음)
        └─ 1-C CLI audit 배선·리포트·비밀 카나리  ┘
        └─ 1-E examples E2E (직렬 전용 웨이브)
단계 2 ─┬─ 2-0 취약 예제 서버 추가(examples, 공동 경로)
        ├─ 2-A Docker 실행기(격리 옵션, 수명주기, 정리)
        ├─ 2-B 오라클 셋 + 고정 페이로드
        └─ 2-E Docker E2E (직렬 전용)
단계 3 ─┬─ 3a 토큰 탭 (라우트 + 화면)
        └─ 3b 보안 탭 (3a 의 틀 위에)
```

단계 2 는 단계 1 의 CLI 와 리포트 계약에 의존한다. 단계 3a 는 어느 단계와도 겹치지 않아 **단계 1 과
병렬로 시작할 수 있다.** 단계 3b 는 단계 1 완료 뒤, 샌드박스 표시는 단계 2 완료 뒤에 켠다.

## 4. 비범위

- 서버 소스 코드 정적 분석(mcp-watch, Cisco behavioral 류). 바이너리 배포 서버에 무력하고 범위가 크다.
- LLM 기반 판정과 오탐 필터. 결정론과 외부 전송 금지에 어긋난다.
- 클라이언트 설정 파일(Claude Desktop, Cursor 등) 자동 탐지. 사전 점검은 "등록 전" 이 전제라
  설정 파일을 읽지 않는다.
- 사용되지 않는 도구 탐지 같은 사용 빈도 기반 토큰 분석(ADR-0102 가 범위 밖으로 둔 것과 같음).
- Docker 외 런타임(Podman 등). Docker CLI 호환이면 동작하되 검증 대상은 아니다.

## 5. 다음 행동

1. 이 로드맵을 팀이 확인한다. 특히 §1 의 순서 조정과 §0 의 Docker 선택 의존 결정.
2. 확인되면 단계 1 구현 계획 `docs/plans/2026-10-0X-audit-핵심-검사-구현계획.md` 를 쓴다. 공유 계약
   (`audit` 의 발견 타입, 리포트 JSON 스키마, 규칙 id 체계)은 그 계획의 선행 태스크다.
3. ADR (a)·(b) 초안을 단계 1 계획과 함께 낸다.
