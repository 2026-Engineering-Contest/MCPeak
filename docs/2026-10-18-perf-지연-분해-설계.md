## 1. 목표, 비범위, 완료 조건

### 1.1 목표

개발자가 자기 MCP 서버에 `mcpeak perf` 를 돌리면 **도구 호출 하나의 응답 시간이 외부 API 대기와 서버 안
시간으로 나뉘어 보이고, 서버 코드를 고치면 줄어들 자리가 문장으로 보인다.**

1. `mcpeak perf <suite.json> -- <서버 명령>` 이 명세의 `callTool` 케이스를 반복 호출해 케이스별로 응답 시간
   p50·p95, 외부 대기 p50, 서버 안 시간 p50, 호출당 외부 요청 수를 표로 낸다. 콜드 스타트(기동+핸드셰이크,
   첫 `tools/list`)를 따로 낸다.
2. 외부 대기의 종료 시각은 **응답 본문 끝**이다. 헤더 수신 시점이 아니다. 조사 §4 에서 "무거운 서버 처리"
   진단 3건이 전부 이 오차였다.
3. 진단 규칙 두 개를 낸다. **순차 독립 요청**(`perf/sequential-independent`)과 **반복 요청**
   (`perf/repeated-request`). 각 진단은 무엇이 어디서 몇 번 관측됐고 어떻게 고치는지를 담는다.
4. `--baseline` 으로 이전 측정과 비교해 **서버 안 시간과 외부 요청 수의 회귀**를 종료 코드 2 로 알린다.
   외부 대기 자체는 네트워크 변동(조사 §5-5: 같은 서버 p50 659 대 p95 6,519)이라 게이트에 넣지 않는다.
5. 실패 경로를 측정에서 분리한다. 던진 호출, 타임아웃, `isError: true`, 빈 응답은 지연 통계에 들어가지 않고
   따로 센다.
6. 결정론: 같은 추적과 같은 측정값을 넣으면 리포트가 바이트 단위로 같다. 리포트에 시각·임시 디렉터리 경로·
   pid 를 넣지 않는다. 지연 수치 자체는 측정값이라 실행마다 다르다. 결정론 계약은 **집계·판정·문장**에 건다.
7. 비밀을 싣지 않는다. 리포트와 기준 파일의 URL 은 쿼리 값을 지운 모양(§5.5)만 싣고, 요청·응답 헤더와 본문은
   어디에도 싣지 않는다. 서버 오류 문장도 같은 규칙을 거친다(§5.4).

### 1.2 비범위

- **녹화 지연 재생.** 전후 비교에서 외부 변동을 없애려면 녹화한 외부 호출 소요 시간을 재생해야 한다(조사 §5-5,
  §6 2단계). record 세션 포맷을 바꾸는 일이라 ADR 과 `record` 오너의 결정이 필요하다. §13 Q2 에 자리만 둔다.
- **원격(Streamable HTTP) 대상.** 관측 코드는 우리가 띄운 서버 프로세스에만 실을 수 있다. `--url` 은
  거절한다(§8.5 문장).
- **Node 가 아닌 서버의 분해.** Python 등은 프리로드가 실리지 않는다. 콜드 스타트와 응답 시간만 내고 분해는
  "관측 안 함" 으로 표기한다(조사 §5-7).
- **본문이 안 보이는 경로의 의존 판정.** `node:http`·http2·undici 직접 요청은 시간은 보이지만 본문이 안 보여
  "판정 불가" 로 센다(조사 §3.3).
- **대시보드 연결.** 축 계약은 analyze 설계 §5 가 갖고 있고, 이 패키지의 결과를 카드로 옮기는 일은 그쪽
  구현 계획이 한다.
- **처리량·동시성 한계 측정.** 부하를 거는 도구가 아니다. 한 번에 하나씩 부른다.
- **진단 규칙의 자동 수정.** `repair` 와 묶지 않는다.
- **팀 `CLAUDE.md` 의 의존 방향 줄과 scope 목록 갱신.** 공동 문서라 사람이 정한다(§13 Q5).

### 1.3 완료 조건

모두 명령으로 확인할 수 있어야 한다. 픽스처와 서버는 §10 에 있다.

- `packages/perf/tests/fixtures/golden/` 의 추적 파일과 측정값을 `analyze()` 와 `renderReport()` 에 넣은 결과가
  같은 디렉터리의 기대 텍스트·JSON 과 바이트 단위로 같다. 같은 입력 두 번이 같은 바이트다.
- `packages/perf/tests/fixtures/serial-server.mjs` 를 대상으로 한 E2E 에서 §10.3 표의 "기대" 열이 전부 성립한다.
  요약하면 `serial` 에 `perf/sequential-independent` 가 나고, `parallel`·`dependent` 에는 나지 않으며,
  `repeat` 에 `perf/repeated-request`(호출 안 중복)가, `prefetch` 두 케이스에 `perf/repeated-request`(케이스 간
  반복)가 나고, `retry` 에는 나지 않으며, `local` 은 외부 요청 0 이다.
- 같은 E2E 에서 `serial` 의 외부 대기 p50 이 두 지연의 합(서버 상수 `DELAY_MS × 2`) 이상이고 `parallel` 의
  외부 대기 p50 이 그 합 미만이다.
- 서버 명령을 `-- env -u NODE_OPTIONS -u MCPEAK_PERF_TRACE_DIR node <serial-server.mjs>` 로 주어 프리로드를 끊으면
  종료 코드 0, `settings.observation` 이 `"none"`, 케이스별 응답 시간만 있고 분해 필드가 없으며 표에서 분해 열이
  빠진다.
- 기준선: `--baseline <tmp> --update-baseline` 으로 쓴 뒤 같은 명령을 `--baseline <tmp>` 로 다시 돌리면 종료
  코드 0 이다. 기준 파일의 `serial` 케이스 `requestsP50` 을 `0` 으로 고친 뒤 돌리면 종료 코드 2 와 요청 수 회귀
  한 줄이 난다. 서버 안 시간 회귀는 유닛(§10.1 `baseline.test.ts`)이 판정한다. 루프백 픽스처의 서버 안 시간은
  임계 바닥 20ms 보다 작아 E2E 로는 회귀를 만들 수 없기 때문이다.
- `mcpeak perf x.json --url http://127.0.0.1:1/mcp` 와 `mcpeak perf --url http://127.0.0.1:1/mcp x.json` 이 둘 다
  종료 코드 1 과 §8.5 의 문장으로 끝난다(§3.1 의 선행 검사).
- 프리로드를 실은 실행과 안 실은 실행의 `tools/call` 결과 `content` 가 같다. 대상은 `serial-server.mjs` 의 모든
  도구와 `examples/weather-server`(외부 호출 없는 고정 표 서버라 두 실행의 응답이 같아야 한다)의 측정 대상
  케이스(§3.1 의 선택 규칙)다.
- 도그푸딩: `mcpeak perf examples/weather-server/server.suite.json -- node examples/weather-server/server.mjs` 가
  종료 코드 0, `observation` `"preload"`, 모든 케이스의 `requests.p50` 0 이다.
- `pnpm build --force` 뒤 `pnpm typecheck --force`(`Cached: 0 cached`), `pnpm lint`, `pnpm test` 가 녹색이고,
  `dependency-boundary` 테스트가 `perf → core` 만 허용한다.

## 2. 측정 모델

### 2.1 시간의 정의

호출 하나에 대해 네 값을 잰다. 전부 밀리초, 소수점 포함으로 재고 리포트 표에는 반올림 정수로 낸다.

| 이름 | 정의 | 재는 곳 |
|---|---|---|
| 응답 시간 `total` | `client.callTool` 을 부른 시각부터 결과를 받은 시각까지 | 부모(CLI) |
| 외부 대기 `external` | 호출에 배정된(§5.1) HTTP 요청들의 [시작, 본문 끝] 구간 **합집합** 길이 | 자식 프리로드가 시각을 기록, 부모가 계산 |
| 서버 안 시간 `inside` | `max(0, total − external)` | 계산 |
| 콜드 스타트 | `connectMs`: spawn 직전부터 `initialize` 핸드셰이크 완료까지. `listToolsMs`: 첫 `tools/list` | 부모 |

`inside` 를 "서버 처리" 라고 부르지 않는다. 처리뿐 아니라 레이트리미터·타이머 대기, 채널 밖 DNS 조회와 첫
연결의 TLS, stdio 전송이 들어 있다(조사 §4 의 npm-helper 237ms 가 레이트리미터 대기였다). 리포트 각주가 이것을
말한다.

두 프로세스의 시계는 둘 다 `performance.timeOrigin + performance.now()` 다. 조사에서 프로세스 간 정렬 오차가
1ms 미만이었고, 배정 창의 여유(§5.1)를 2ms 로 둔 근거다.

### 2.2 관측 범위

| 경로 | 시작 시각 | 끝 시각 | 응답 본문 | 의존 판정에서 |
|---|---|---|---|---|
| `globalThis.fetch` | 래퍼 진입 | 복제본을 끝까지 읽은 시각 | 보임(상한까지) | 앞 요청·뒤 요청 모두 가능 |
| `node:http`·`node:https` (axios, node-fetch 등) | `http.client.request.start` | 응답 스트림 `end`, 없으면 `close`, 오류면 `http.client.request.error` | 안 보임 | 앞 요청 자리면 `unknown` |
| HTTP/2 (`node:http2`, got-scraping 등) | `http2.client.stream.created` | `http2.client.stream.close` | 안 보임 | 앞 요청 자리면 `unknown` |
| undici 직접 사용 | `undici:request:create` | `undici:request:trailers`, 오류면 `undici:request:error` | 안 보임 | 앞 요청 자리면 `unknown` |
| Node 자식 프로세스 | `NODE_OPTIONS` 상속으로 같은 프리로드가 실림 | 위와 같음 | 위와 같음 | 위와 같음 |

`fetch` 는 내부적으로 undici 를 써서 같은 요청이 undici 채널에도 찍힌다. 리다이렉트는 홉마다 찍힌다. 이 중복은
§5.2 가 `AsyncLocalStorage` 귀속으로 지운다. undici 채널을 아예 안 보는 길도 있었지만, 그러면 undici 를 직접
쓰는 서버의 외부 대기가 통째로 `inside` 로 들어가 조사 §4 의 오진이 재현된다.

채널 확인 상태: Node 24.14 에서 `http.client.request.start`, `http.client.response.finish`,
`http.client.request.error`, `undici:request:create`, `undici:request:trailers` 의 발행과, fetch 래퍼 안의
`AsyncLocalStorage` 값이 `undici:request:create` 구독자에서 읽히는 것을 검토 단계에서 확인했다. http2 채널과
Node 22.18 의 위 채널들은 확인하지 않았다. 없는 채널을 구독하면 아무것도 받지 않을 뿐 실패하지 않으므로 구독은
무조건 한다. Node 22 에서의 동작은 CI 의 e2e 잡(Node 22)이 §10.3 E2E 로 확인한다. http2 는 E2E 가 덮지 않으며
리포트 각주가 아니라 이 문서의 알려진 한계로 둔다.

## 3. 사용자 흐름

### 3.1 명령

```
mcpeak perf <suite.json> (-- <executable> [args...] | --command <executable> [--arg <value> ...] [--env <NAME> ...])
            [--repeat <n>] [--interval-ms <ms>] [--tool <name> ...]
            [--baseline <path> [--update-baseline]] [--threshold-pct <n>] [--threshold-ms <n>] [--json]
```

대상 옵션의 해석과 거절 문장은 `optimize` 처럼 `parseTestCommand` 를 쓴다. 다만 `optimize` 와 달리 `--url` 과
`--header-env` 는 다른 어떤 검사보다 먼저 거절한다. `parsePerfCommand` 는 첫 `--` 앞의 토큰 전체에서
`--url`·`--header-env`(`=` 형식 포함)를 찾고, 있으면 위치 인자 검사 전에 §8.5 의 문장으로 끝낸다. 그래서 명세
경로 자리에 `--url` 이 와도 같은 문장이 나온다. `--` 뒤는 서버 명령이라 훑지 않는다. 첫 위치 인자는 `test` 와
같은 명세 파일이다. 명세를 쓰는 이유는 **사람이 승인한 실제 입력**으로 불러야 실제 경로의 지연이 나오기
때문이다. `audit` 의 자리값 인자는 검증 실패나 빈 결과 경로를 밟기 쉽다.

측정 대상 케이스는 명세의 `callTool` 케이스 중 **`{ type: "isError", expected: true }` 단언이 없는 것**이다.
거절을 기대하는 케이스는 거절 경로의 시간이라 뺀다. `--tool` 을 주면 그 도구의 케이스만 남긴다. 남는 케이스가
없으면 종료 코드 1 과 §8.5 의 문장이다. `listTools` 케이스는 쓰지 않는다.

옵션 기본값과 뜻은 §8.4.

### 3.2 실행 순서

1. 명세를 읽고 검증한다. 읽기·JSON·검증 실패 문장은 `test` 와 같다(§8.5).
2. 추적 디렉터리를 `makeTempDir` 로 만들고, 자식 환경 변수를 `childEnvironment` 로 만든다(§4.1).
   `existingNodeOptions` 는 `readEnv("NODE_OPTIONS")` 로 읽는다. CLI 는 `process.env` 를 직접 읽지 않는다(ADR-0013).
3. `now()` 를 찍고 `openConnection(target, deps, { env })` 로 붙는다. 붙은 시각까지가 `connectMs`. 이어서
   `listTools` 를 한 번 부르고 그 시간을 `listToolsMs` 로 둔다.
4. `measure()` 가 케이스를 명세 순서대로, 케이스마다 `repeat` 회 **연속으로** 부른다(A×5, B×5, …). 호출 사이에
   `intervalMs` 만큼 쉰다. 라운드 로빈이 아닌 이유는 케이스 간 반복 요청(§6.2 (b))을 같은 조건에서 관측하기
   위해서다. 순서가 결과에 미치는 영향은 리포트의 설정 줄이 알린다.
5. 호출의 타임아웃은 케이스 `timeoutMs`, 없으면 명세 `defaultTimeoutMs`, 없으면 10,000ms 다(`runner` 실행기와
   같은 값). `measure` 가 `callTool` 과 `sleep(timeoutMs, signal)` 을 경쟁시키고, 승자가 정해지면 `signal` 을
   abort 해 타이머를 해제한다(남은 타이머가 CLI 종료를 늦추지 않게). 타임아웃이 나면 그 반복은 `threw`·
   `timedOut: true` 이고 **측정을 끝낸다. 남은 호출은 케이스와 무관하게 전부 부르지 않고 `skipped` 로 센다.**
   서버가 아직 그 호출을 처리하는 중이라 그 뒤의 어떤 호출 창에도 그 작업의 외부 요청이 섞여 요청 수 게이트가
   그 실행에서만 흔들리기 때문이다. 서버 상태를 모르는 채 계속 재는 것보다 멈추고 알리는 쪽이 결정론적이다.
   리포트는 `aborted` 를 채우고 표 뒤에 중단 문장을 낸다(§8.3).
6. 연결을 닫는다. 닫힌 뒤 `readTrace` 로 추적 디렉터리의 파일을 전부 읽는다(프로세스마다 파일 하나).
7. `analyze()` 로 리포트를 만들고, `--baseline` 이 있으면 `compareBaseline` 또는 `toBaseline` 을 한다.
8. 사람용 리포트 또는 `--json` 을 stdout 에 쓴다. 진행 문장은 stderr. 추적 디렉터리는 3단계 이후 어느 경로로
   끝나든 `finally` 에서 지운다. 남으면 요청 헤더·본문이 임시 디렉터리에 남는다.

## 4. 관측: 자식 프리로드

### 4.1 주입

`record` 의 External Bootstrap 과 같은 방식(`NODE_OPTIONS=--import=<파일 URL>`)이다. 다만 **같은 파일을 쓰지
않는다.** record 의 어댑터는 녹화·재생이 목적이라 요청을 Coordinator 로 보내고 재생 때 네트워크를 막는다. perf 는
관측만 하고 아무것도 바꾸지 않아야 한다. 두 목적을 한 파일에 두면 한쪽의 결함이 다른 쪽에 번지고, 소유자도
다르다(record 는 ② 파트).

```ts
// packages/perf/src/child-env.ts
export const PERF_TRACE_DIR_ENV = "MCPEAK_PERF_TRACE_DIR";

/**
 * 자식에게 넘길 환경 변수 두 개. `openConnection` 의 `env` 로 그대로 간다.
 * NODE_OPTIONS 는 existingNodeOptions 뒤에 공백 하나와 `--import=<preload URL>` 을 덧붙인다. 없으면 import 하나.
 * preload URL 은 `new URL("./child/preload.mjs", import.meta.url).href` 라 dist 레이아웃이 그 상대 경로를 지켜야 한다.
 */
export function childEnvironment(options: {
  readonly traceDir: string;
  readonly existingNodeOptions?: string | undefined;
}): Readonly<Record<string, string>>;
```

`--env` 가 `NODE_OPTIONS` 와 `MCPEAK_` 접두 이름을 이미 거절하므로(ADR-0097) 사용자가 이 두 값을 덮을 길은
없다. perf 는 `--session`·`--record-session` 을 받지 않는다(§8.4). 같은 자식에 두 프리로드를 싣는 조합은
1단계에서 다루지 않는다.

프리로드는 `MCPEAK_PERF_TRACE_DIR` 이 없으면 아무것도 하지 않는다. 변수를 **지우지 않는다.** `npx` 같은 중간
런처가 지우면 진짜 서버가 빈손으로 뜬다(record 가 ADR-0095 에서 밟은 것). 그래서 런처의 요청도 기록되지만,
그 요청은 호출 구간 밖(연결 전)이라 §5.1 의 배정이 거른다.

### 4.2 기록 파일

프로세스마다 `${traceDir}/${pid}.jsonl` 하나. 한 파일을 여럿이 쓰면 줄이 섞일 수 있어 나눈다(record 의 관측
디렉터리와 같은 이유, ADR-0100). 쓰기는 `appendFileSync` 다. 비동기로 쓰면 프로세스가 끝날 때 버퍼가 사라진다.

요청 하나는 **두 줄**이다. 시작할 때 `start` 줄, 끝날 때 `end` 줄을 쓰고 둘은 `(pid, seq)` 로 짝을 이룬다. `seq` 는
프로세스 안에서 1부터 오르는 정수다. 끝 줄을 쓰지 못한 요청(본문을 소비하지 않은 keep-alive 요청, 호출 도중 끝난
프로세스)도 시작 줄은 남아 §5.1 의 "끝 없음" 경로로 하한이 표시된다. 한 줄만 쓰면 그런 요청이 추적에서 통째로
사라져 외부 대기가 하한 표시 없이 과소평가된다.

로드 직후 `hello` 한 줄을 쓴다. 이 줄의 존재가 "관측이 실렸다" 의 판정 근거다(§4.4).

### 4.3 경로별 규칙

공통: 요청 헤더는 이름을 소문자로 바꾼 뒤 `authorization`, `proxy-authorization`, `cookie`, 그리고 `x-` 로
시작하는 것만 담는다. 의존 판정(§6.1)이 쓰는 것이 이 헤더들뿐이다. 요청 본문은 문자열로 볼 수 있을 때만
`requestBody` 로 담고, 메서드가 `GET`·`HEAD` 가 아닌데 본문을 못 보면 `requestBodyUnknown: true` 를 적는다.

**`globalThis.fetch`**

1. `new Request(input, init)` 로 메서드·URL·요청 헤더를 읽고, 원래 fetch 에는 그 `Request` 를 넘긴다(record
   어댑터와 같은 방식). 본문은 `init.body` 가 문자열이면 상한(§4.5)까지 담는다. 그 밖의 본문은 담지 않는다.
2. `seq` 를 받고 `start` 줄을 쓴 뒤, 원래 fetch 를 `als.run(seq, () => originalFetch(request))` 로 부른다. `als` 는
   프리로드의 `AsyncLocalStorage` 다(§5.2).
3. `tHeaders` 는 `await` 가 돌아온 직후. 응답을 `clone()` 하고, 복제본의 `body.getReader()` 로 청크를 끝까지
   읽는 작업을 **기다리지 않고** 건다. 원본은 즉시 돌려준다. 청크는 바이트를 세며 상한까지만 보관하고 나머지는
   버린다(큰 다운로드가 통째로 메모리에 오르지 않게). 읽기가 끝난 시각이 `tEnd`, `bodyEnd: true` 이고 그때
   `end` 줄을 쓴다. 보관한 바이트는 UTF-8 로 디코드해 `responseBody` 로, 넘쳤으면 `responseBodyTruncated: true`.
   서버가 원본 본문을 안 읽어도 복제본 읽기가 네트워크를 끝까지 당기므로 `tEnd` 는 본문 끝이다. `res.body` 가
   `null` 인 응답(204, `HEAD`, `redirect: "manual"` 의 3xx)은 읽을 것이 없으므로 `tEnd = tHeaders`, `bodyEnd: true`,
   `responseBody: ""` 로 바로 `end` 줄을 쓴다.
4. `res.status`, `res.headers.get("location")` 을 `responseHeaders.location` 으로, 리다이렉트됐으면 `res.url` 을
   `finalUrl` 로 싣는다.
5. 원래 fetch 가 던지면 던진 시각을 `tEnd`, `bodyEnd: false`, `error` 를 담은 `end` 줄을 쓰고 그대로 다시 던진다.
   복제본 읽기가 던져도 같다.

**`node:http` / `node:https`** (`diagnostics_channel`)

1. `http.client.request.start`: `request` 를 키로 `seq` 를 정하고 `start` 줄(메서드,
   `${protocol}//${host}${path}`, `request.getHeaders()` 에서 고른 헤더, `requestBodyUnknown`)을 쓴다.
2. `http.client.response.finish`: `tHeaders`, `status`, `responseHeaders.location` 을 기억하고
   **`response.once("end")` 와 `response.once("close")` 만 건다.** `data` 리스너를 달거나 `resume()`·
   `setEncoding()` 을 부르지 않는다. 그렇게 하면 스트림이 flowing 으로 바뀌어 서버가 나중에 다는 리스너가
   앞부분을 놓친다. 관측이 서버 동작을 바꾸면 측정이 아니다. 이 채널은 서버의 `response` 핸들러보다 먼저
   발행되므로 리스너를 먼저 달아도 서버가 놓치는 이벤트는 없다(검토 단계에서 Node 24 로 확인).
3. 먼저 온 쪽으로 `end` 줄을 한 번만 쓴다. `end` 면 `bodyEnd: true`, `close` 만 오면(서버가 본문을 안 읽고
   버림) `bodyEnd: false`. 둘 다 안 오면 끝 줄이 없다.
4. `http.client.request.error`: 그 시각을 `tEnd`, `bodyEnd: false`, `error` 로 `end` 줄을 쓴다.

**HTTP/2**

`http2.client.stream.created` 의 `headers[":method"]`, `":scheme"`, `":authority"`, `":path"` 로 메서드와 URL 을
만들고 `start` 줄. `http2.client.stream.close` 가 `tEnd`, `bodyEnd: true` 의 `end` 줄. 헤더·본문은 담지 않고
메서드가 `GET`·`HEAD` 가 아니면 `requestBodyUnknown: true`.

**undici**

`undici:request:create` 에서 `request.method`, `request.origin + request.path` 로 `start` 줄을 쓰고, 그때
`als.getStore()` 가 있으면 그 값을 `parentFetch` 로 담는다. `undici:request:trailers` 가 `tEnd`, `bodyEnd: true`.
`undici:request:error` 는 그 시각을 `tEnd`, `bodyEnd: false`, `error`. 헤더·본문은 담지 않고 메서드가 `GET`·
`HEAD` 가 아니면 `requestBodyUnknown: true`.

**하지 않는 것.** `child_process` 채널은 보지 않는다(상속으로 충분). `process.cpuUsage` 는 재지 않는다
(조사 §4: GC 보조 스레드가 합산되고 네트워크 구간과 겹쳐 지연과 더해지지 않는다). stdin·stdout 을 가로채지
않는다(경계는 부모가 잰다).

### 4.4 관측 유무 판정

추적에 `hello` 줄이 하나라도 있으면 `observation: "preload"`, 하나도 없으면 `"none"`. `"none"` 이면 분해·진단을
하지 않고 응답 시간과 콜드 스타트만 낸다(§8.3). Node 런처 뒤에 Node 가 아닌 서버가 있는 경우는 `hello` 가 있지만
요청이 없어 모든 케이스가 "외부 요청 0" 으로 보인다. 구분할 방법이 없어 각주가 범위를 말하는 것으로 둔다.

## 5. 분해와 집계

### 5.1 추적 병합과 호출 배정

먼저 `start`·`end` 줄을 `(pid, seq)` 로 합쳐 관측 요청 목록을 만든다(`ObservedRequest`, §8.1). 짝 없는 `end`
줄은 버린다.

호출 `c` 의 구간은 `[c.t0, c.t1]`. 요청 `e` 는 두 단계로 배정한다. **먼저 `c.t0 ≤ e.t0 ≤ c.t1` 인 호출(엄밀
구간)을 찾고, 있으면 그중 측정 순서(케이스 순서, 반복 순서)가 가장 앞선 호출에 배정한다.** 측정은 직렬이라 그런
호출은 보통 하나다. 없을 때만 `e.t0 ≥ c.t0 − 2 && e.t0 ≤ c.t1 + 2` 를 만족하는 호출(여유 창)을 후보로 보고,
후보 중 측정 순서가 가장 앞선 호출 하나에 배정한다. 여유 2ms 는 프로세스 간 시계 정렬 오차(§2.1)를 덮는다.

엄밀 구간을 먼저 보는 이유는 연속 호출이다. `--interval-ms 0` 에서는 다음 호출이 앞 호출 끝의 0.1ms 안에
시작하고, 서버가 호출을 받자마자 낸 첫 요청은 앞 호출의 `t1 + 2` 안에도 든다. 여유 창만 보고 앞선 호출을 고르면
그 요청이 앞 호출의 `afterResponse` 로 밀려 외부 대기가 0 이 된다(T6a 의 serial-server E2E 에서 실측, 계획 E20).
어느 단계든 한 요청은 한 호출에만 센다. 두 호출에 세면 요청 수가 실행마다 갈리고 §7.2 의 요청 수 게이트가
흔들린다. 후보가 없는 요청(연결 전 런처 요청, 호출 사이 배경 요청)은 버린다.

배정된 요청 중 `e.t0 > c.t1` 인 것은 `afterResponse` 로 세고 외부 대기에는 넣지 않는다.

요청의 끝 `end(e)` 는 `e.tEnd`, 없으면 `e.tHeaders`, 둘 다 없으면 `c.t1`. `tEnd` 가 없는 요청이 하나라도 있으면
그 호출의 `externalLowerBound: true` 이고 표의 외부 대기 값 앞에 `≥` 를 붙인다.

같은 pid 인지 보지 않는다. Node 자식 프로세스의 요청도 그 호출이 만든 외부 대기다(조사의 npm search 사례).

### 5.2 중복 제거

`parentFetch` 가 있는 undici 요청은 지운다. 그 요청은 fetch 래퍼가 `als.run` 안에서 부른 원래 fetch 가 만든
것이고(리다이렉트 홉 포함), 시간은 fetch 요청이 이미 덮는다. undici 를 직접 쓴 요청은 저장소가 비어 있어 남는다.
시간 창이나 URL 로 짝을 맞추지 않는 이유는 둘 다 오차가 있고(리다이렉트 홉은 URL 이 다르다, 조사 §5-6), 그
오차가 요청 수 게이트를 흔들기 때문이다.

### 5.3 합집합과 백분위

- `external(c)` = 배정된 요청 중 `e.t0 ≤ c.t1` 인 것들의 `[e.t0, min(end(e), c.t1)]` 합집합 길이.
- `inside(c)` = `max(0, total(c) − external(c))`.
- `requests(c)` = 중복 제거 뒤 배정된 요청 수(`afterResponse` 포함). `maxConcurrency(c)` = 어느 시점에 동시에
  열린 요청 수의 최대.
- 케이스 통계는 **`ok` 반복만** 쓴다. 백분위는 nearest-rank: 오름차순 정렬 `s` 에서 `s[ceil(p × n) − 1]`. n=5 의
  p95 는 최대값이다. 그래서 표에 `n` 을 함께 낸다. `min`·`max` 도 JSON 에 싣는다. 이 문서의 다른 "중앙값" 도
  전부 이 p50 이다.

### 5.4 실패 분리

반복 하나의 결과(`CallOutcome`)는 여섯 가지 중 하나다.

| `outcome` | 조건 | 통계 |
|---|---|---|
| `ok` | 결과를 받았고 `isError` 가 참이 아니며 `empty` 가 아니다 | 포함 |
| `isError` | `isError: true` | 제외, 횟수 표기 |
| `empty` | `content` 가 배열이 아니거나 빈 배열이거나 모든 항목이 `type: "text"` 이고 `text` 가 공백뿐이며, 동시에 `raw` 가 객체이고 `raw.structuredContent` 가 `undefined` 다 | 제외, 횟수 표기 |
| `threw` | `callTool` 이 거부됐거나 타임아웃이 났다 | 제외, 첫 오류 문장 |
| `skipped` | 앞선 호출이 타임아웃이라 측정을 끝내 부르지 않았다(§3.2 5항) | 제외, 횟수 표기 |
| `missingTool` | `tools/list` 에 도구가 없어 부르지 않았다 | 제외, 횟수 표기 |

`empty` 를 따로 두는 이유는 조사 §4 의 youtube-transcript 다. 200 에 0바이트 본문이라 `isError` 가 아닌데
측정값은 실패 경로의 시간이었다. `structuredContent` 는 `ToolResult` 의 필드가 아니라 `raw` 안에 있다
(`core/src/client.ts` 가 SDK 결과 전체를 `raw` 로 싣는다).

`threw` 의 `detail` 은 `measure` 가 만든다. 오류 메시지의 첫 줄을 잡고, 그 안의 `https?://[^\s"'<>]+` 를 전부
`displayUrl`(§5.5, `src/url.ts`)로 바꾸고, `MAX_DETAIL_CHARS` 에서 자르고 잘렸으면 `…` 를 붙인다. 타임아웃이면 문장은
`호출이 {timeoutMs}ms 안에 끝나지 않았습니다` 다.

`ok` 가 0 인 케이스는 통계 필드가 없고 기준선 비교에서 "측정 불가" 다(§7.3).

### 5.5 URL 표기

리포트·기준 파일·진단 문장·오류 문장의 URL 은 전부 다음 모양이다.

```
<host>[:port]<pathname>[?<name>=…[&<name>=…]]
```

스킴·userinfo·fragment 를 지우고 쿼리는 **이름만** 원래 순서대로 남기며 값은 `…` 로 바꾼다. 파싱할 수 없는
문자열은 `[URL]` 로 바꾼다. 요청 키(§6.2)는 내부적으로 원문 URL 과 본문 해시를 쓰지만 어디에도 출력하지 않는다.
헤더·본문은 추적 파일(임시, 실행 뒤 삭제)에만 있다.

## 6. 진단 규칙

두 규칙 모두 **종료 코드를 바꾸지 않는다.** 보안 발견이 아니라 제안이고, 같은 코드가 네트워크 조건에 따라
다르게 관측될 수 있어 CI 를 막을 근거가 못 된다. 종료 코드는 기준선 회귀(§7)만 바꾼다.

### 6.1 의존 판정

요청 `later` 가 앞선 요청 `earlier` 에 의존하는지를 세 값 중 하나로 답한다: `dependent`, `independent`, `unknown`.

```
tokens(text) =
  JSON 으로 파싱되면: 모든 문자열 값과 숫자 값을 String(v) 로 바꾼 것 중 길이 ≥ 4
                      (불리언·null 은 제외. 키는 넣지 않는다)
  아니면:             /[A-Za-z0-9_.\-]{8,}/g 의 매치

outputs(earlier) =
  tokens(earlier.responseBody) ∪ { earlier.responseHeaders.location } (있으면)
  − JSON.stringify(call.input) 에 부분 문자열로 들어 있는 토큰       (입력 반향 제외)
  − decodeURIComponent(earlier.url) 또는 earlier.requestBody 에 들어 있는 토큰  (자기 요청 반향 제외)

inputs(later) =
  decodeURIComponent(later.url) + " " + (later.requestBody ?? "") + " " + later.requestHeaders 의 값들을 " " 로 이은 것

judge(later, earlier):
  earlier.responseBody 가 없거나 responseBodyTruncated 이면 → unknown
  later.requestBodyUnknown 이면                             → unknown
  outputs(earlier) 중 하나라도 inputs(later) 의 부분 문자열이면 → dependent
  아니면                                                    → independent
```

- 숫자 값을 넣는 이유: 앞 응답의 좌표·id 같은 숫자를 다음 URL 에 넣는 체인이 흔한 의존 모양이다. 숫자만
  넘기는 서버에서 숫자를 빼면 그 체인이 거짓 독립으로 판정된다(`live-weather-server` 의 `get_forecast` 는 좌표와
  함께 timezone 문자열도 넘겨 어느 쪽으로도 잡힌다). 조사 하네스도 숫자를 넣었고 그 규칙으로
  실제 의존 3건(weather·hn·pubmed)을 확인했다. 길이 4 미만의 작은 정수는 우연 일치가 많아 뺀다.
- 입력 반향과 자기 요청 반향 제외가 조사 §4 의 거짓 의존 반례에 대한 답이다.
- 요청 헤더는 §4.3 이 고른 것(인증·쿠키·`x-*`)만 입력에 들어간다. `accept: application/json` 같은 고정 헤더를
  넣으면 앞 응답의 흔한 토큰과 맞아 거짓 의존이 나고 그 서버에서는 규칙이 영영 안 난다. Bearer 토큰으로 넘어가는
  의존은 이 범위로 잡힌다(조사 §5-2).
- 숫자 경로의 한계: 응답 값이 `52.52` 인데 서버가 `52.5200` 처럼 다시 포맷하면 놓친다. 그 경우 거짓 독립 경고가
  난다. 받아들이고 각주 대신 이 문서에 적는다.

### 6.2 규칙

**`perf/sequential-independent` (순차 독립 요청)**

호출 하나에서 외부 대기에 들어간 요청을 `t0` 순(같으면 `seq` 순)으로 놓는다. `i ≥ 1` 인 요청 `e_i` 가 **앞선
모든 요청이 끝난 뒤에 시작했으면**(`e_i.t0 ≥ max(end(e_j) for j < i) − 1`) 순차 요청이다. 순차 요청 `e_i` 의
판정은 앞선 모든 요청에 대한 `judge` 를 모아 하나라도 `dependent` 면 `dependent`, 아니면 하나라도 `unknown` 이면
`unknown`, 전부 `independent` 면 `independent` 다. 이 셋의 개수를 케이스 단위로 더한 것이 `CaseResult.dependency`
다.

- 발동: `ok` 반복의 **과반**(`m > n / 2`)에서 `independent` 순차 요청이 1건 이상이다. 과반인 이유는 네트워크
  지터로 한 번 겹쳐 보인 반복이 판정을 뒤집지 않게 하기 위해서다.
- 단축 상한: 발동한 반복마다 의존 그래프의 임계 경로를 구해 외부 대기에서 뺀다.
  ```
  len(i)    = min(end(e_i), c.t1) − e_i.t0
  pred(i)   = { j < i : e_i.t0 ≥ end(e_j) − 1  그리고  judge(e_i, e_j) ∈ {dependent, unknown} }
  finish(i) = len(i) + max(0, max(finish(j) for j in pred(i)))
  saving(c) = external(c) − max(finish(i) for all i)
  ```
  `savingUpperBoundMs` 는 발동한 반복들의 `saving(c)` p50 이다. 의존이 아닌 요청을 전부 병렬로 보내도 응답 시간은
  임계 경로보다 짧아질 수 없으므로 이 값은 실제 단축의 상한이다. `unknown` 을 의존으로 보는 것은 단축을 작게
  잡는 보수적 방향이다. 겹쳐 나간 요청은 `pred` 에 들지 않아 그대로 병렬로 취급된다.
- 문장(세 줄):
  1. `'{tool}' 호출 안에서 독립 요청 {k}건이 순차로 나갑니다 ({n}회 중 {m}회): {요청 표기}`
  2. `병렬로 보내면 최대 약 {ms}ms 줄일 수 있습니다 (p50 기준 상한).`
  3. `Promise.all 로 한 번에 보내고, 상대 API 의 동시 요청 한도와 429 백오프를 함께 두세요.`
  `k` 는 발동한 반복들의 독립 순차 요청 수의 p50. `{요청 표기}` 는 독립 순차 요청들을 `{METHOD} {displayUrl}` 로
  적고, 같은 표기는 첫 등장 순서로 한 번만 두고 `×{횟수}`(한 반복 안 횟수의 p50, 1이면 생략)를 붙이며, 종류가 3을
  넘으면 셋까지만 적고 `외 {r}종` 을 붙인다. 구분자는 `, `.
- `unknown` 때문에 발동하지 못한 케이스가 있으면 진단 절 끝에 한 줄:
  `판정 불가: {c}개 케이스는 응답이나 요청 본문을 못 보는 경로(node:http·http2·undici, 스트림 본문)라 독립 여부를 가리지 못했습니다.`
  "발동하지 못한" 은 `ok` 반복의 과반에서 `unknown` 순차 요청이 1건 이상이고 이 규칙이 발동하지 않은 케이스다.

**`perf/repeated-request` (반복 요청)**

요청 키 `key(e) = method + " " + url + " " + sha256(requestBody ?? "")`. `requestBodyUnknown` 인 요청은 키가 없고
이 규칙에서 제외한다. 본문이 다른 GraphQL·JSON-RPC 요청이 같은 키로 보이는 오탐을 막기 위해서다. 응답 지문
`fingerprint(e) = status + ":" + sha256(responseBody)` 는 응답 본문이 보이고 잘리지 않았을 때만 있다.

- (a) 호출 안 중복: 한 호출에서 같은 키가 2번 이상이고, 그 키의 첫 요청의 `status` 가 200 이상 300 미만이다.
  `ok` 반복의 과반에서 성립하면 발동. status 조건은 429·5xx 뒤 재시도를 "응답을 재사용하라" 로 잘못 말하지 않기
  위해서다. status 가 없는 경로(http2·undici)는 (a) 에서 제외한다. 문장(두 줄):
  1. `'{tool}' 호출 한 번에 같은 요청을 {k}번 보냅니다 ({n}회 중 {m}회): {METHOD} {displayUrl}`
  2. `첫 응답을 호출 안에서 재사용하세요.`
  `k` 는 발동한 반복에서 그 키의 횟수 p50.
- (b) 케이스 간 반복: 같은 키가 **서로 다른 케이스 2개 이상**의 `ok` 반복에 나타나고, 그 키의 모든 관측에
  지문이 있고 서로 같다. 서로 다른 케이스를 요구하는 이유는 같은 입력을 반복하면 본 요청도 같은 응답이 나오는
  것이 정상이기 때문이다. 케이스가 하나뿐인 도구에는 발동하지 않는다. 같은 키가 여러 도구에 걸치면 도구 이름을
  사전순으로 `', '` 로 잇는다. 문장(두 줄):
  1. `'{tools}' 가 입력이 달라도 매 호출 같은 요청에 같은 응답을 받습니다 (케이스 {c}개, 호출 {m}회, p50 {ms}ms): {METHOD} {displayUrl}`
  2. `프로세스 안에서 캐시하거나 시작할 때 한 번만 받으세요.`
  `{m}` 은 그 키가 나타난 `ok` 반복 수, `{ms}` 는 그 키 요청들의 길이 p50.

(a) 와 (b) 는 같은 키에 동시에 날 수 있다. 둘 다 낸다.

### 6.3 진단의 순서

`findings` 는 (1) 규칙 id 사전순, (2) 케이스 id 사전순(케이스 간 규칙은 사전순 첫 케이스 id), (3) 요청 표기
사전순이다. 사람용 리포트는 그 순서 그대로다. 시각·관측 순서를 쓰지 않는다.

## 7. 기준선과 회귀 게이트

### 7.1 기준 파일

```ts
export interface PerfBaseline {
  readonly schemaVersion: typeof PERF_SCHEMA_VERSION;
  readonly generator: { readonly name: "@mcpeak/perf"; readonly version: string };
  readonly settings: { readonly repeat: number; readonly intervalMs: number };
  /** 케이스 id 사전순. ok 반복이 0 인 케이스는 넣지 않는다. 수치는 소수 첫째 자리 반올림. */
  readonly cases: readonly {
    readonly id: string;
    readonly tool: string;
    readonly n: number;
    readonly insideP50: number;
    readonly externalP50: number;
    readonly totalP50: number;
    readonly requestsP50: number;
  }[];
}
```

파일은 `JSON.stringify(baseline, null, 2) + "\n"` 이다. `observation` 이 `"none"` 인 리포트에서는 `insideP50`·
`externalP50`·`requestsP50` 을 알 수 없으므로 `--update-baseline` 을 거절한다(§8.5).

`--update-baseline` 은 측정이 끝난 뒤 이 파일을 쓰고 비교하지 않으며 종료 코드 0 이다(파일이 없어도 된다).
`--baseline` 만 있고 파일이 없으면 종료 코드 1 과 §8.5 의 문장이다. `--update-baseline` 은 `--baseline` 없이는
거절한다.

### 7.2 회귀 판정

기준과 현재에 모두 있는 케이스마다:

```
limit             = base.insideP50 × (1 + thresholdPct / 100) + thresholdMs
insideRegressed   = inside.p50   > limit
requestsRegressed = requests.p50 > base.requestsP50
```

둘 중 하나면 회귀. 기본 `thresholdPct = 50`, `thresholdMs = 20`. `inside.p50` 과 `requests.p50` 은 반올림 전 값이다.

- 50% 는 조사에서 같은 서버를 반복 호출했을 때 `inside` 가 반복 사이에 2배 안쪽에서 흔들린 것을 덮기 위한
  값이고, 20ms 는 GC 한 번과 이벤트 루프 지연의 크기라 1ms 가 3ms 가 된 것을 회귀로 부르지 않기 위한 바닥이다.
  둘 다 **추정**이다. T6a 가 `serial-server` 를 10회 연속 측정해 `inside` p50 의 최대/최소 비를 보고서에 적고,
  그 비가 1.5 를 넘으면 기본값을 다시 정한다. 바꾸면 이 절과 §8.4 기본값을 함께 바꾼다.
- 외부 요청 수는 바닥 없이 **하나라도 늘면** 회귀다. 요청 수는 네트워크와 무관하게 코드가 정한다. 조건부로
  요청 수가 달라지는 서버(캐시 적중 여부)는 기준 파일에서 사용자가 그 케이스를 빼는 것으로 둔다.
- 응답 시간·외부 대기는 비교해서 **보여주기만** 한다.

### 7.3 비교 결과와 종료 코드

| 상황 | 문장 | 종료 코드 기여 |
|---|---|---|
| 회귀 없음 | `회귀 없음. 서버 안 p50 은 기준의 {factor}배+{thresholdMs}ms 안이고 외부 요청 수는 기준 이하입니다.` | 0 |
| 서버 안 회귀 | `'{id}' 서버 안 p50 {now}ms, 기준 {base}ms (허용 {limit}ms 초과)` | 2 |
| 요청 수 회귀 | `'{id}' 호출당 외부 요청 {now}건, 기준 {base}건` | 2 |
| 기준에 있고 지금 측정 불가 | `'{id}' 는 기준에 있지만 이번에는 성공한 호출이 없습니다 ({사유})` | 2 |
| 기준에 있고 이번 명세에 없음 | `'{id}' 는 기준에 있지만 이번 명세에 없습니다.` | 0 |
| 지금 있고 기준에 없음 | `'{id}' 는 기준에 없습니다. --update-baseline 으로 기준을 갱신하세요.` | 0 |
| 설정 다름 | `기준은 반복 {a}회·간격 {b}ms 로 쟀고 이번은 반복 {c}회·간격 {d}ms 입니다. 조건이 달라 비교가 느슨합니다.` | 0. **비교는 계속하고**, 다른 줄의 회귀는 그대로 2 다 |

- `{factor}` 는 `String(Math.round((1 + thresholdPct / 100) * 100) / 100)` 이다(50 → `1.5`, 0 → `1`, 125 → `2.25`).
- `{now}`·`{base}`·`{limit}` 은 `Math.round`. `{사유}` 는 그 케이스의 outcomes 를 `threw 5회` 처럼 0 이 아닌 것만
  §5.4 표 순서로 `, ` 로 이은 것.
- 회귀 줄이 하나라도 있으면 마지막에 `이 변경이 의도된 것이라면 --update-baseline 으로 기준을 갱신하세요.` 를
  한 번 붙인다. "회귀 없음" 줄은 회귀 줄이 없을 때만 낸다. 안내 줄(0 기여)은 둘 중 어느 경우에도 뒤에 붙는다.
- 줄 순서: 회귀 줄(케이스 id 사전순, 같은 케이스는 서버 안 → 요청 수 → 측정 불가) → 회귀 없음 또는 갱신 안내 →
  설정 다름 → 기준에 없음·명세에 없음(케이스 id 사전순).

```ts
export const PERF_SCHEMA_VERSION = 1 as const;

/** 측정할 호출 하나. CLI 가 명세에서 뽑는다. perf 는 명세 형식을 모른다. */

  readonly caseId: string;
  readonly tool: string;
  readonly input: Readonly<Record<string, unknown>>;
  readonly timeoutMs: number;
}

export interface PerfPlan {
  /** 명세 순서. */
  readonly calls: readonly PerfCall[];

  readonly intervalMs: number;
}

export type TraceVia = "fetch" | "node:http" | "http2" | "undici";

/** 자식 프리로드가 쓰는 한 줄. 시각은 epoch 밀리초(소수). */
export type TraceEntry =
  | { readonly kind: "hello"; readonly pid: number; readonly ppid: number; readonly node: string; readonly t: number }
  | {
      readonly kind: "start";
      readonly pid: number;
      readonly seq: number;
      readonly via: TraceVia;
      readonly method: string;
      readonly url: string;
      /** §4.3 이 고른 헤더만. 이름은 소문자. */
      readonly requestHeaders?: Readonly<Record<string, string>>;
      readonly requestBody?: string;
      readonly requestBodyUnknown?: true;
      /** undici 항목이 fetch 래퍼 안에서 생겼으면 그 fetch 의 seq. */
      readonly parentFetch?: number;
      readonly t0: number;
    }
  | {
      readonly kind: "end";
      readonly pid: number;
      readonly seq: number;
      readonly status?: number;
      readonly finalUrl?: string;
      readonly responseHeaders?: { readonly location?: string };
      readonly responseBody?: string;
      readonly responseBodyTruncated?: true;
      readonly bytes?: number;
      readonly tHeaders?: number;
      readonly tEnd: number;
      /** false 면 tEnd 가 본문 끝이 아니라 close·오류 시각이다. */
      readonly bodyEnd: boolean;
      readonly error?: string;
    };

/** start 와 end 를 합친 요청 하나. end 가 없으면 끝 필드가 없다. */
export type ObservedRequest = Omit<Extract<TraceEntry, { kind: "start" }>, "kind"> &
  Partial<Omit<Extract<TraceEntry, { kind: "end" }>, "kind" | "pid" | "seq">>;

export type CallOutcome = "ok" | "isError" | "empty" | "threw" | "skipped" | "missingTool";

/** 부모가 잰 호출 하나. skipped·missingTool 은 t0 === t1 이고 호출하지 않았다. */
export interface PerfMeasurement {
  readonly caseId: string;
  readonly tool: string;
  readonly iteration: number;
  readonly t0: number;
  readonly t1: number;
  readonly outcome: CallOutcome;
  /** threw 일 때만. §5.4 규칙을 거친 문장. */
  readonly detail?: string;
  /** threw 가 타임아웃이었으면 true. 측정 중단의 근거다(§3.2 5항). */
  readonly timedOut?: true;
}

export interface Percentiles {
  readonly p50: number;
  readonly p95: number;
  readonly min: number;
  readonly max: number;
}

export interface RequestSummary {
  /** "{METHOD} {displayUrl}". */
  readonly display: string;
  readonly via: TraceVia;
  /** ok 반복 전체에서 본 횟수. */
  readonly count: number;
  readonly durationP50: number;
}

export interface CaseResult {
  readonly id: string;
  readonly tool: string;
  /** ok 반복 수. */
  readonly n: number;
  /** 여섯 키가 모두 있다. */
  readonly outcomes: Readonly<Record<CallOutcome, number>>;
  /** 첫 threw 의 detail. */
  readonly firstError?: string;
  /** n 이 0 이면 없다. */
  readonly total?: Percentiles;
  /** n 이 0 이거나 observation 이 none 이면 아래 여섯은 없다. */
  readonly external?: Percentiles;
  readonly inside?: Percentiles;
  readonly requests?: Percentiles;
  readonly maxConcurrency?: number;
  readonly externalLowerBound?: boolean;
  readonly afterResponse?: number;
  /** observation 이 none 이면 0, 0, 0. */
  readonly dependency: { readonly dependent: number; readonly independent: number; readonly unknown: number };
  /** display 사전순. observation 이 none 이면 빈 배열. */
  readonly requestSummaries: readonly RequestSummary[];
}

export type PerfRuleId = "perf/sequential-independent" | "perf/repeated-request";

export interface PerfFinding {
  readonly ruleId: PerfRuleId;
  readonly caseIds: readonly string[];
  readonly tools: readonly string[];
  /** 사람용 줄들. "→ " 없이. 렌더러가 붙인다. */
  readonly lines: readonly string[];
  readonly evidence: {
    readonly observed: number;
    readonly of: number;
    readonly requests: readonly string[];
    readonly savingUpperBoundMs?: number;
  };
}

export interface BaselineComparison {
  readonly path: string;
  readonly settingsMismatch: boolean;
  /** §7.3 의 줄 순서 그대로. "→ " 없이. */
  readonly lines: readonly string[];
  readonly regressedCaseIds: readonly string[];
}

export interface PerfReport {
  readonly schemaVersion: typeof PERF_SCHEMA_VERSION;
  readonly generator: { readonly name: "@mcpeak/perf"; readonly version: string };
  readonly server: { readonly command: string; readonly toolCount: number };
  readonly settings: {
    readonly repeat: number;
    readonly intervalMs: number;
    readonly caseCount: number;
    readonly observation: "preload" | "none";
  };
  readonly coldStart: { readonly connectMs: number; readonly listToolsMs: number };
  /** 명세 순서. */
  readonly cases: readonly CaseResult[];
  /** §6.3 순서. observation 이 none 이면 빈 배열. */
  readonly findings: readonly PerfFinding[];
  /** unknown 때문에 발동하지 못한 케이스 수(§6.2). */
  readonly undecidedCases: number;
  /** 타임아웃으로 측정을 끝냈으면 그 호출. 첫 timedOut 측정의 caseId 와 plan 의 timeoutMs. 아니면 null. */
  readonly aborted: { readonly caseId: string; readonly timeoutMs: number } | null;
  readonly baseline?: BaselineComparison;
  readonly exitCode: 0 | 2;
}
```

### 8.3 렌더러 규칙

`renderReport` 는 색을 쓰지 않고 같은 리포트에 같은 문자열을 낸다. §3.3 이 그 모양의 예시다.

1. 머리 네 줄:
   - `mcpeak perf 결과`
   - `서버 {command} · 도구 {toolCount}개 · 관측 Node 프리로드(fetch, node:http, http2, undici)` (none 이면 마지막
     항목이 `관측 안 함(Node 프리로드가 실리지 않음)`)
   - `설정 반복 {repeat}회 · 호출 간격 {intervalMs}ms · 케이스 {caseCount}개 (callTool 중 거절 기대 제외)`
   - `콜드 스타트 기동+핸드셰이크 {connectMs}ms · tools/list {listToolsMs}ms`
   - 빈 줄.
   (머리는 위 네 줄이고 그 뒤 빈 줄 하나다.)
2. 표: 열은 `케이스`, `n`, `응답 p50`, `p95`, `외부 대기 p50`, `서버 안 p50`, `외부 요청/호출`. none 이면 뒤의 세
   열이 빠진다. 열 너비는 머리글과 값 중 가장 긴 것(문자 수)에 맞추고, `케이스` 열은 왼쪽 정렬, 나머지는 오른쪽
   정렬, 열 사이 공백 2. 숫자는 `Math.round`, 천 단위 구분 없음. `externalLowerBound` 면 외부 대기 값 앞에 `≥`.
   행 끝 비고(열 사이 공백 2 뒤):
   - n 이 0 이면 숫자 칸은 공백으로 채우고 비고 `측정 안 됨: {사유}. 첫 오류: {firstError}` (firstError 가 없으면
     `. 첫 오류: …` 부분 없음). `{사유}` 는 §7.3 과 같은 규칙.
   - n 이 0 이 아니고 실패가 있으면 비고 `실패 {k}회({사유})`.
   - 표 뒤 빈 줄. `aborted` 가 있으면 이어서
     `측정 중단: '{caseId}' 호출이 {timeoutMs}ms 안에 끝나지 않아 남은 호출을 하지 않았습니다. 케이스의 timeoutMs 를 올리거나 --tool 로 케이스를 나누세요.`
     한 줄과 빈 줄.
3. 진단 절: 관측이 있으면 `진단 {k}건 (종료 코드에 영향 없음)` 또는 `진단 없음`, 이어서 findings 의 줄들을 `→ `
   를 붙여 순서대로, `undecidedCases` 가 0 이 아니면 §6.2 의 판정 불가 줄을 `→ ` 없이. 관측이 없으면
   `진단 없음: 외부 호출을 관측하지 못해 분해와 진단을 하지 않았습니다. Node 서버가 아니거나 NODE_OPTIONS 가 전달되지 않았습니다.`
   한 줄. 뒤에 빈 줄.
4. 기준선 절(baseline 이 있을 때만): `기준선 비교 ({path})`, 이어서 `lines` 를 `→ ` 를 붙여. 뒤에 빈 줄.
5. 각주: 관측이 있으면 §3.3 의 세 문장. 없으면 첫 두 문장 대신 `분해와 진단은 Node 서버에 프리로드가 실릴 때만 합니다.`
   그리고 셋째 문장.
6. 출력은 줄들을 `\n` 으로 잇고 끝에 `\n` 하나.

### 8.4 CLI 옵션

| 옵션 | 기본 | 뜻 |
|---|---|---|
| `<suite.json>` | 필수 | `test` 와 같은 명세. `callTool` 중 거절 기대가 아닌 케이스를 쓴다 |
| 대상 옵션 | 필수 | `--`, `--command`/`--arg`/`--env`. `parseTestCommand` 와 같다. `--url`·`--header-env` 는 거절 |
| `--repeat <n>` | 5 | 케이스당 호출 수. 1 이상 100 이하 정수 |
| `--interval-ms <ms>` | 0 | 호출 사이 대기. 0 이상 60000 이하 정수. 리포트 설정 줄에 표시 |
| `--tool <name>` | 없음 | 반복 가능. 그 도구의 케이스만 |
| `--baseline <path>` | 없음 | 기준 파일. 있으면 비교, `--update-baseline` 과 함께면 쓰기 |
| `--update-baseline` | 꺼짐 | 측정 결과로 기준 파일을 쓴다. 비교하지 않는다 |
| `--threshold-pct <n>` | 50 | §7.2. 0 이상 1000 이하 정수 |
| `--threshold-ms <n>` | 20 | §7.2. 0 이상 60000 이하 정수 |
| `--json` | 꺼짐 | stdout 에 `JSON.stringify(report, null, 2) + "\n"` 하나만 |

값을 받는 옵션은 `--x v` 와 `--x=v` 를 모두 받고, 값 자리가 `--` 로 시작하면 값 누락으로 거절한다(`optimize` 의
`--out` 과 같은 규칙). `--tool` 외에는 두 번 주면 거절한다. `test` 전용 옵션(`--junit`, `--repair-bundle`,
`--determinism`, `--reset-cmd`, `--stderr-lines`, `--session`, `--record-session`)은 `지원하지 않는 perf 옵션 '{이름}'입니다.`
로 거절한다.

`--interval-ms` 기본 0 은 서버의 레이트리미터 대기가 `inside` 로 보일 수 있다는 뜻이다. 어떤 양수도 그 서버의
한도를 아는 척하는 값이라 기본을 0 으로 두고 설정 줄에 적어 읽는 사람이 판단하게 한다.

종료 코드: `0` 측정 완료(진단 유무 무관), `2` 기준선 회귀, `1` 사용 오류·연결 실패·명세 오류·기준 파일 오류.
측정 중 서버 프로세스가 죽으면(`callTool` 이 연결 상실로 거부) 그 반복은 `threw` 이고, 남은 호출도 같은 이유로
`threw` 가 되어 리포트를 낸 뒤 종료 코드는 기준선 판정을 따른다.

### 8.5 오류 문장

모든 사용 오류는 `오류 [CLI_USAGE]: {문장}` 과 `해결: {사용법}` 두 줄이고, 사용법 줄은 `PERF_USAGE_HINT`
(`help.ts`)다. 기준 파일 오류는 `PerfError` 의 `code` 앞에 CLI 가 `PERF_` 를 붙인다.

| 상황 | stderr |
|---|---|
| `--url`·`--header-env` | `오류 [CLI_USAGE]: perf 는 원격(Streamable HTTP) 서버를 지원하지 않습니다.`<br>`→ 측정은 서버 프로세스 안에 관측 코드를 실어야 하는데, 우리가 띄우지 않은 프로세스에는 실을 수 없습니다.`<br>`해결: mcpeak perf <suite.json> -- <서버 명령>` |
| 측정할 케이스 없음(`--tool` 없음) | `오류 [CLI_USAGE]: 측정할 케이스가 없습니다. 명세의 callTool 케이스 중 거절(isError: true)을 기대하지 않는 것이 없습니다.`<br>`해결: mcpeak generate 로 성공 케이스를 만들거나 명세를 확인하세요.` |

| `--update-baseline` 만 있음 | `오류 [CLI_USAGE]: --update-baseline 은 --baseline <path> 와 함께 써야 합니다.` + 사용법 줄 |
| 관측 없이 `--update-baseline` | `오류 [PERF_BASELINE_UNAVAILABLE]: 외부 호출을 관측하지 못해 기준 파일을 쓰지 않았습니다.`<br>`→ Node 서버인지, NODE_OPTIONS 가 서버까지 전달되는지 확인하세요.` (리포트는 먼저 stdout 에 내고 종료 코드 1) |

| 명세 읽기·JSON·검증 오류 | `mcpeak test` 의 같은 입력에 대한 stderr 와 바이트 단위로 같다 |
| 연결 실패, `tools/list` 실패 | `mcpeak optimize` 의 같은 대상에 대한 `MCP_CONNECTION_FAILED`·`MCP_LIST_TOOLS_FAILED` 문장과 진단 블록과 같다. 단 사용법 줄은 `PERF_USAGE_HINT` |

`PERF_BASELINE_MISSING`·`PERF_BASELINE_UNAVAILABLE` 은 CLI 가 직접 만드는 코드다. 기준 파일 확인(없음·형식)은
**측정 전에** 한다. 측정을 다 하고 나서 기준 파일 오타로 버리지 않기 위해서다.

명세 오류와 연결 실패 문장을 만드는 함수는 `test-command.ts`·`optimize-command.ts` 의 비공개 함수다. 그 파일은
다른 서브커맨드의 것이라 export 를 위해 고치지 않는다. `perf-command.ts` 가 같은 문장을 자기 안에 만들고,
§10.2 의 동등성 테스트가 두 명령의 stderr 를 비교해 어긋남을 잡는다.

### 8.6 CLI 의존성 주입

```ts
// packages/cli/src/perf-command.ts
import type { McpStdioConnection } from "@mcpeak/core";

export interface PerfCommandDependencies {
  connectStdio(options: {
    command: string;
    args: readonly string[];
    env?: Readonly<Record<string, string>>;
  }): Promise<McpStdioConnection>;
  readEnv(name: string): string | undefined;
  /** test 의 주입점과 같은 바이트 반환. 명세 인코딩 오류 문장을 test 와 같게 내려면 바이트가 필요하다. */
  readFile(path: string): Promise<Uint8Array>;
  writeFile(path: string, text: string): Promise<void>;
  makeTempDir(prefix: string): Promise<string>;
  removeDir(path: string): Promise<void>;
  now(): number;
  sleep(ms: number, signal?: AbortSignal): Promise<void>;
  readonly validateSuite: typeof import("@mcpeak/runner").validateMcpSuite;
  readonly perf: Pick<
    typeof import("@mcpeak/perf"),
    "measure" | "readTrace" | "analyze" | "compareBaseline" | "toBaseline" | "parseBaseline" | "renderReport" | "childEnvironment"
  >;
  /** 리포트의 generator.version. `@mcpeak/perf` 의 패키지 버전. 읽는 방식은 optimize 와 같다. */
  readonly generatorVersion: string;
  writeStdout(text: string): void;
  writeStderr(text: string): void;
}

export function parsePerfCommand(argv: readonly string[]): PerfCommandInput;
export function runPerfCommand(argv: readonly string[], deps: PerfCommandDependencies): Promise<number>;
```

`PerfCommandInput` 은 `{ suitePath, target, repeat, intervalMs, tools, baselinePath?, updateBaseline, thresholdPct,
thresholdMs, json }` 이고 모든 필드가 readonly 다. `index.ts` 는 `nodePerfDependencies(core, runner, perf)` 를
`nodeOptimizeDependencies` 와 같은 모양으로 두고, `@mcpeak/perf` 는 `perf` 명령일 때만 동적 import 한다. 정적
import 하면 `test` 경로가 그 패키지를 함께 로드한다. `makeTempDir` 의 접두는 `join(tmpdir(), "mcpeak-perf-")`,
`removeDir` 는 `rm(path, { recursive: true, force: true })`, `now` 는 `performance.timeOrigin + performance.now()`
(§2.1 과 같은 시계), `sleep` 은 `setTimeout` Promise 이고 `signal` 의 abort 에서 `clearTimeout` 한다. 기준 파일은
`readFile` 의 바이트를 `new TextDecoder("utf-8").decode` 로 읽는다.

## 9. 패키지 경계와 배선

### 9.1 의존 방향

```
dashboard → cli → perf → core
```

`perf` 는 `@mcpeak/core` 의 타입(`McpClient`)만 쓴다. 명세 검증(`validateMcpSuite`)은 `cli` 가 `runner` 로 하고
`PerfPlan` 으로 바꿔 넘긴다. `perf` 가 `runner` 에 의존하지 않는 이유는 측정 입력이 명세 한 종류에 묶이지
않게 하기 위해서다(대시보드가 다른 모양으로 넘길 수 있다). `record` 를 쓰지 않는다(§4.1).

### 10.3 E2E (직렬 웨이브)

픽스처 서버 `packages/perf/tests/fixtures/serial-server.mjs`: `@modelcontextprotocol/sdk` 의 `McpServer`(저수준
`Server` 도 된다)와 `globalThis.fetch`, 그리고 `http` 도구만 `node:http` 를 쓰는 stdio 서버. 외부 주소는 환경 변수
`MCPEAK_PERF_FIXTURE_ORIGIN` 으로 받는다. 이 변수는 `MCPEAK_` 접두라 `--env` 로 넘길 수 없으므로, E2E 는 CLI 를
거치지 않는 경로(`connectStdio` + `measure` + `analyze`, `perf-e2e.test.ts`)와, 서버 명령 앞에
`env MCPEAK_PERF_FIXTURE_ORIGIN=…` 을 붙이는 CLI 경로(`cli/tests/perf-e2e.test.ts`)로 나눈다. 테스트가 루프백
`node:http` 서버를 띄워 그 주소를 넘기고, 응답 지연은 `?ms=` 로 서버가 준다. 지연 상수 `DELAY_MS = 100` 은
픽스처 서버 파일이 export 하고 단언이 그 값을 읽는다.

루프백 서버의 응답 본문 규칙. 케이스 간 반복 규칙 (b) 가 의도한 곳에서만 나게 하는 것이 목적이다.

| 경로 | 응답 |
|---|---|
| `/config` | 고정 `{"config":"v1"}` |
| `/first` | 고정 `{"id":48213}` |
| `/flaky` | 이 서버가 받은 `/flaky` 요청 중 홀수 번째는 429 `{"retry":true,"n":<카운터>}`, 짝수 번째는 200 `{"ok":true,"n":<카운터>}` |
| 그 밖 | 200 `{"path":"<pathname>","n":<카운터>}`. `<카운터>` 는 서버가 받은 전체 요청 수로 요청마다 오른다 |

그 밖 경로는 매번 본문이 달라 지문이 같아질 수 없으므로, `serial`·`parallel`·`http` 가 같은 `/a`·`/b` 를 써도
(b) 가 나지 않는다.

| 도구·케이스 | 외부 호출 | 기대 |
|---|---|---|
| `serial` | `GET /a?ms=DELAY_MS` 뒤 `GET /b?ms=DELAY_MS` 순차, 응답 서로 무관 | sequential-independent 발동, external p50 ≥ `DELAY_MS × 2` |
| `parallel` | 같은 둘을 `Promise.all` | 미발동, external p50 < `DELAY_MS × 2` |
| `dependent` | `GET /first?ms=50` 의 본문 `{"id":48213}`(숫자) 를 `GET /second/48213?ms=50` 에 사용 | 미발동, dependency.dependent ≥ 1 |
| `repeat` | `GET /settings?ms=20` 두 번 뒤 `GET /data?ms=20` | repeated-request (a), (b) 없음 |
| `retry` | `GET /flaky?ms=20` 이 첫 번에 429, 같은 요청 재시도에 200 | (a) 미발동 |
| `prefetch` (케이스 `prefetch-1`, `prefetch-2`, 입력 `id` 1·2) | `GET /config?ms=20` 뒤 `GET /item?id=<input.id>&ms=20` | repeated-request (b) 정확히 하나, caseIds `["prefetch-1","prefetch-2"]`, tools `["prefetch"]` |
| `http` | `node:http` 로 `GET /a?ms=DELAY_MS`, 본문을 끝까지 읽는다 | external p50 ≥ `DELAY_MS`, `externalLowerBound` false |
| `local` | 없음 | requests p50 0 |
| `fails` | 없음, `isError: true` | n 0, outcomes.isError = repeat |

명세 `packages/perf/tests/fixtures/serial-server.suite.json` 이 위 케이스를 담는다. 단언은 하한과 구조를 쓴다.
상한은 `parallel` 의 external p50 < `DELAY_MS × 2` 하나이고, 지연 100ms 두 개에 대해 CI 지터가 100ms 를 먹지
않는다는 가정이다. 흔들리면 `DELAY_MS` 를 키운다.

## 13. 임의로 정한 것과 열린 질문

임의로 정한 것(검토에서 뒤집혀도 다른 절이 깨지지 않는 것):

1. 측정 입력을 `test` 명세에서 가져온다. `audit` 의 자리값 인자나 별도 계획 파일이 아니다. §3.1.
2. 케이스를 연속 반복한다(라운드 로빈 아님). §3.2.
3. `--interval-ms` 기본 0. §8.4.
4. `--repeat` 기본 5. p95 는 n 이 작으면 최대값이라 `n` 을 표에 함께 낸다. §5.3.
5. 회귀 임계 50%+20ms 와 요청 수 1건. 임계는 추정이고 T6a 실측으로 확인한다. §7.2.
6. 진단은 종료 코드를 바꾸지 않는다. §6.
7. fetch 와 undici 중복을 `AsyncLocalStorage` 귀속으로 지운다. §5.2.
8. 리포트의 URL 은 쿼리 값을 전부 가린다. 민감 키 목록(record 의 규칙)을 가져오지 않기 위해서다. §5.5.
9. 콜드 스타트는 수치만 내고 진단하지 않는다(조사 §3.1 의 mediawiki 1,509ms 같은 경우는 숫자로 보인다).
10. 타임아웃이 나면 측정 전체를 끝낸다. §3.2.
11. 명세·연결 오류 문장을 다른 서브커맨드 파일에서 export 하지 않고 복제하며 동등성 테스트로 묶는다. §8.5.
