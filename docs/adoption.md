## 1. 적용 이력

### 1.1 `examples/weather-server` — 자체 제작, CI 상시

우리가 만든 예제 서버다. **§10 이 말하는 "적용 저장소" 에는 넣지 않는다.** 우리 도구가 다루기
가장 쉽도록 설계돼 있어(고정 데이터 · 인증 불필요 · 저수준 `Server` 사용) 외부 서버의 난이도를
대표하지 못한다. 그럼에도 회귀를 막는 최저선이라 기록한다.

CI(`.github/workflows/ci.yml`)가 매 실행 두 경로로 돈다.

| 경로 | 무엇을 지키나 |
|---|---|
| `pnpm --filter ohmymcp test:e2e` | 빌드 산출물 `dist/cli.mjs` 가 실제로 도는지. 번들링·exports·shebang 결함은 소스 테스트로는 안 잡힌다 |
| `--junit junit-dogfood.xml` → `dorny/test-reporter` | 우리가 내보낸 XML 을 실제 CI 리포터가 읽는지 |

### 1.2 외부 서버에서 무슨 일이 날 것인가 — 예측과 실측 대조

§10 은 공개된 외부 MCP 서버 3~5개를 요구한다. **적용 완료는 6개**다(§1.4). 이 표는 착수 전에
세운 예측이고, 붙여 본 결과로 갱신한다. 표본은 고유 서버 8개 · 6개 적용이다.

**행마다 근거가 다르므로 갱신할 때 등급을 함께 적는다.**

| 실제 서버의 특성 | 지금 어떻게 될 것으로 보나 | 근거 |
|---|---|---|
| 스키마에 `$ref` · `anyOf` 포함 | **그 툴만 거절된다.** `mcp-server-git` 이 `anyOf` 로 3툴을 잃었고 남은 9툴로 적용됐다. PR #145 전에는 서버 전체가 막혔다 | 2026-08-17 **실측** (§1.4.3) |
| Streamable HTTP 전송 | **CLI 로는 못 붙는다.** `core` 는 `connectHttp` 를 내보내지만 CLI 에 `--url`·`http` 배선이 0건이다 | #16 · ADR-0020 · 2026-08-17 **CLI 배선 점검** (#137) |
| stdout 에 로그를 섞어 뱉음 | 여전히 **겪어 본 적 없음.** 고유 서버 8개 전부 로그를 stderr 로만 보냈다(`server-everything` 의 `Starting default (STDIO) server...` 도 stderr) | 2026-08-17 **실측** (§1.4) — 재현 못 함 |
| 툴 20~50개 | **해당 서버를 못 만났다.** 최대가 14개(`server-filesystem`)다. 다만 이제 `generate` 가 통과하므로 실행 시간은 측정 가능해졌다 — 14툴 54케이스가 수 초 안에 끝났다 | 2026-08-17 **실측** (§1.4) — 구간 밖 |

**근거의 등급이 행마다 다르다.** 1행은 2026-08-17 에 **ADR 근거에서 실측으로 올라갔다**. 2행은
여전히 **CLI 소스를 읽어 확인한 사실**(배선 0건)까지이고 서버에 붙여 본 적은 없다. 3·4행은
**서버에 붙여 봤으나 그 조건을 못 만난 것**이다.

3·4행은 표본이 2개에서 8개로 늘었지만 **「사실로 확인됨」이 된 것은 아니다.** 붙여 본 서버가 그
특성을 갖지 않았을 뿐이고, 그런 서버에서 무슨 일이 나는지는 여전히 모른다.
**"재현 못 함" 과 "일어나지 않는다" 는 다르다.**

> **1행의 초기 관측 (2026-08-17 오전).** 처음 붙였을 때는 **`$ref`·`anyOf` 에 닿기도 전에
> `$schema` 하나로 막혔다**(#135). 문턱이 이 행의 상정보다 낮았다. #135 를 고친 뒤에야 `anyOf`
> 거절이 실제로 관측됐다.

2행도 확인한 것은 **배선이 없다는 것까지**다. 배선이 없어 시도 자체가 불가능했으므로
**원격 서버에 실제로 연결해 본 적은 없고, 그 동작은 여전히 미측정이다.** 이 구분을 흐리지 않는다 —
소스를 읽은 것과 서버에 붙여 본 것은 다른 근거이고, 이 표에서 "실측" 은 후자에만 쓴다.

> **2행 정정 (2026-08-17).** 처음에 "연결됨 (2026-08-14 해소)" 이라고 적었다. **틀렸다.** 이슈 #16 이
> 닫힌 것은 `core.connect()` 범위이고, 사용자가 CLI 로 원격 서버에 붙는 경로는 열린 적이 없다.
> 패키지에 기능이 있는 것과 사용자에게 닿는 것을 내가 뭉갰다.
>
> **#74 와 같은 패턴이다** — `renderJUnit` 이 runner 에 있는데 CLI 로 안 나와 쓸 수 없던 그 건이고,
> 아래 §4 에 내가 직접 적어 둔 것이다. 같은 착각을 같은 문서 안에서 반복했다. 이 표에 "해소됨" 을
> 적을 때는 **사용자가 실제로 그 경로를 탈 수 있는지**를 기준으로 한다.

`generate` 가 스키마 단계에서 막혀(#135) 명세를 만들지 못했다. **이 시점의 적용 저장소 수는 0이다.**

> `mcp-server-git`)을 붙여 TS 3 : Python 3 이 됐다. **두 SDK 의 오류 본문 형식이 실제로 달랐다** — TS 는
> `MCP error -32602:` 접두어를 본문 문자열에 새기고 Python 은 안 새긴다. 같은 구현을 공유한
> 결과였다는 위 추정이 맞았다. 관측 34건은 #89 에 적었다. Go·Rust SDK 서버는 여전히 0개다.

#### 1.4.1 `--arg` 우회가 필요했다 (해소)

**앞 넷**을 붙일 때는 `test` 에 `--arg=-y` 형태를 써야 했다. 공백 형태(`--arg -y`)를 `test` 가
거절했다. §2.5 의 결함이고 PR #145 에서 고쳤다. **뒤 둘(`server-filesystem` · `mcp-server-git`)은
공백 형태로 붙였다** — 수정이 실사용에서 작동하는 것을 그 자리에서 확인했다.

#### 1.4.2 `server-everything` 은 부분 생성이 있어야 적용된다

이 서버는 툴 13개 중 `get-resource-links` 의 `maximum` 과 `gzip-file-as-resource` 의 `format`
때문에 PR #145 **전에는 0개**가 생성됐다(§2.5). 부분 생성으로 11개가 생성됐고, 처음에는 그 브랜치
빌드로 확인했다. **PR #145 는 2026-08-17 에 머지됐으므로 지금은 `main` 기준 실적이다.**

실패 4건은 전부 `simulate-research-query` 툴이다. 원인을 직접 호출로 확인했다.

```text
MCP error -32601: Tool simulate-research-query requires task augmentation (taskSupport: 'required')
```

서버가 그 툴을 MCP tasks 기능 필수로 선언했고 우리 클라이언트는 그것을 지원하지 않는다.
**서버 결함도 명세 오류도 아니다.** 다만 우리 화면은 이 사실을 말해 주지 못하고
`MCP 작업이 protocol 오류로 거절되었습니다` 까지만 보여준다. 서버가 알려준 이유를 우리가 버리는
#106 · #136 과 같은 유형이라 §2.5 에 결함으로 적었다.

#### 1.4.3 `server-filesystem` · `mcp-server-git` — PR #145 머지 뒤 재시도

둘 다 `main` 에서는 **0개**가 생성되던 서버다(`minItems` · `anyOf`). PR #145 가 머지된 `main`
빌드로 다시 붙여 적용됐다. **부분 생성이 후보를 실제로 늘렸다는 증거이고, ADR-0036 이 노린
효과가 여기서 관측됐다.**

| 서버 | 건너뛴 툴 | 사유 |
|---|---|---|
| `server-filesystem` | `read_multiple_files` | `paths.minItems` |
| `mcp-server-git` | `git_log` · `git_create_branch` · `git_branch` | 각각 `anyOf` |

**`server-filesystem` 의 실패 8건은 전부 도메인 값 문제였다.** `synthesizeValue` 가 만든
`"example"` 을 경로 자리에 넣어 `ENOENT` 가 났다. 샌드박스 실제 경로로 고치면 통과한다. 값을
고치는 과정에서 **경로가 겹치면 뒤 케이스가 깨진다**는 것도 관측했다 — `write_file` 이 만든
파일과 `create_directory` 가 만들 디렉터리에 같은 경로를 주면 `EEXIST` 가 난다. **우리 도구나
서버의 결함이 아니라 값을 고른 사람의 실수이므로 결함으로 세지 않는다.** 다만 부작용이 있는 툴을
한 스위트에서 함께 돌릴 때 값끼리 간섭할 수 있다는 사실은 남긴다.

**둘 다 같은 입력으로 2회 연속 실행해 판정이 같았다. 다만 두 서버의 조건이 다르다.**

| 서버 | 실행 전 상태 복원 | 2회 판정 | 무엇을 말할 수 있나 |
|---|---|---|---|
| `server-filesystem` | **매 실행 전 복원함.** `rm -rf fs-sandbox` 뒤 `a.txt` · `movable.txt` 재생성 | 54/54 · 54/54 | 같은 초기 상태에서 같은 결과가 나온다 |
| `mcp-server-git` | **복원하지 않음.** 1회차가 만든 커밋이 남은 채로 2회차를 돌렸다 | 40/40 · 40/40 | **"두 실행 모두 40/40" 까지만이다.** 초기 상태가 달랐으므로 결정론성 판정이 아니다 |

`mcp-server-git` 쪽을 결정론성 확인으로 읽으면 안 된다. 상태를 바꾸는 툴(`git_commit` ·
`git_add` · `git_reset` · `git_checkout`)을 실행했고 그 결과가 2회차의 입력이었다. 같은 판정이
나온 것은 **그 케이스들이 누적 상태에 둔감했다**는 뜻이지 같은 조건을 두 번 준 것이 아니다.

단계 7(결정론성 확인)이 자동화할 검사는 이보다 엄격해야 한다. `server-filesystem` 쪽이 그 검사의
모양에 가깝고, 상태 복원 수단(`generate` 의 `--reset-cmd` 같은 것)이 `test` 에는 없다는 것도
이 실행에서 드러났다.

**부작용 있는 툴을 실제로 실행했다.** `git_commit` · `git_add` · `git_reset` · `git_checkout` 과
`write_file` · `create_directory` · `move_file` 이 그렇다. 전용 샌드박스(`git-sandbox` ·
`fs-sandbox`)에서만 돌렸고 저장소나 사용자 파일은 건드리지 않았다.

### 1.5 외부 서버에서 발견한 결함 — `mcp-server-time`, PR 미제출

`uvx mcp-server-time` 이 기동 즉시 죽었다. **원인에 도달하기까지 세 계층을 거쳤고, 계층마다 받은
정보가 다르다.** 이 차이 자체가 §2.5 셋째 결함의 근거라 계층을 나눠 적는다.

| 계층 | 무엇을 실행했나 | 무엇을 받았나 |
|---|---|---|
| 1. CLI | `ohmymcp generate --command uvx --arg mcp-server-time` | `오류 [GENERATE_FAILED]: baseline suite를 생성하거나 저장하지 못했습니다.` **원인 없음** |
| 2. 라이브러리 | `core.connectStdio` 를 직접 호출하는 임시 스크립트 | `PROCESS_EXITED 요청 완료 전 MCP 서버가 종료되었습니다.` 서버가 죽었다는 사실까지 |
| 3. 서버 | `uvx mcp-server-time --help` | 아래 traceback. **여기서야 원인이 나왔다** |

```text
ImportError: cannot import name 'McpError' from 'mcp.shared.exceptions'.
Did you mean: 'MCPError'?
```

Python `mcp` 2.x 가 `McpError` 를 `MCPError` 로 개명했는데 서버가 구 이름을 import 한다.
`--with "mcp<2"` 로 고정해 우회했다. **우리 결함이 아니라 그 저장소의 결함이다.**

**1계층에서 멈췄으면 이 결함을 못 찾았다.** `test` 는 같은 상황에서
`MCP_CONNECTION_FAILED/PROCESS_EXITED` 로 core 의 코드를 그대로 싣는데 `generate` 만 뭉갠다.
그래서 §2.5 셋째 행을 결함으로 세었고 PR #145 가 `GENERATE_CONNECT_FAILED/<code>` 로 고쳤다.

§10 의 "외부 저장소에 보낸 PR" 후보이지만 **아직 보내지 않았다.** 한 줄 수정이라 비용은 낮고,
동결 전에 보낼지는 결정하지 않았다. 보내면 이 칸을 갱신한다.

### 2.4 잘못 등록하고 철회한 것 — 2026-08-17 (#138, 닫힘)

`required` 가 빈 툴에 누락 위반 케이스를 만들어 오탐이 난다고 등록했다가 **철회했다.**

`contract-axes.ts:101` 이 `required` 배열을 순회하며 축을 만들기 때문에 `required` 가 비면
누락 케이스가 애초에 생기지 않는다. 실제로 돌려서도 확인했다. **제안한 동작이 이미 구현돼 있었다.**

**서버 응답만 관찰하고 우리 구현을 확인하지 않은 채 결함으로 옮긴 것이 원인이다.**
관측(`{}` 로 성공하는 툴이 있다)은 사실이었으나 거기서 결함으로 넘어간 연결이 추론이었다.

여기 남기는 이유는 **결함 수를 세는 이 파일에서 오등록이 가장 비싼 종류의 오류**이기 때문이다.
§1.2 가 세운 근거 등급 구분이 왜 필요한지를 이 건이 보여 준다 — 등급을 나눠 적기 시작하자마자
자기 항목 하나가 등급 미달로 걸러졌다.

| 무엇 | 어디서 드러났나 | 상태 |

**첫 행이 §10 의 실질적 병목이었다.** `server-everything` 은 13개 툴 중 **11개**가 지원 범위인데

단일 툴 서버라 부분 생성으로 살릴 수 없다.

> **#135 와 다른 결함이다.** #135 는 "`$schema` 를 지원 목록에 넣어야 한다"(지원 범위)이고,
> 이것은 "미지원 키워드를 만났을 때의 실패 반경"(정책)이다. #135 를 고친 뒤에도 `maximum` 을
> 쓰는 서버는 여전히 0개가 생성됐으므로 같은 건으로 셀 수 없다.

까지만 말하고 서버가 준 `requires task augmentation` 을 버린다. #106 · #136 과 같은 유형이고,
**MCP tasks 지원 여부와 별개로 이유를 보여주는 것은 가능하다.**

#### 2.5.1 세는 단위 — 고유 서버 수와 실행 횟수는 다르다

이 절과 §1.4 의 숫자는 전부 **고유 서버 수**다. 같은 서버를 여러 번 실행한 것은 세지 않는다
(`server-everything` 은 PR #145 전후로 두 번, `mcp-server-time` 은 값 교정 전후로 두 번 돌렸다).
분모가 섞이지 않게 항목을 나눠 적는다.

| 항목 | 수 | 어느 서버 |
|---|---|---|
| 2026-08-17 에 붙여 본 **고유 서버** | 8 | 아래 ①②③ 의 합 |
| ① 처음부터 지원 범위였던 서버 | 3 | `server-memory` · `mcp-server-sqlite` · `mcp-server-time` |
| ② 미지원 키워드가 있었으나 **부분 생성으로 적용** | 3 | `server-everything`(`maximum`·`format`) · `server-filesystem`(`minItems`) · `mcp-server-git`(`anyOf`) |
| ③ 부분 생성으로도 **적용 못 함** | 2 | `server-sequential-thinking`(`maximum`) · `mcp-server-fetch`(`exclusiveMaximum`) |
| §10 목표(3~5) 대비 | **6** = ① + ② | 전부 `main` 기준 |

**"5개가 전멸" 의 분모는 ② + ③ 이다.** 다섯 서버가 툴 하나의 키워드로 0개 생성이었고, PR #145
이후 그중 셋(②)이 적용됐다.

**③ 이 여전히 안 되는 이유는 툴이 1개뿐이기 때문이다.** 두 서버 모두 단일 툴 서버라 그 툴을
건너뛰면 남는 케이스가 0이고, ADR-0036 이 정한 대로 종전처럼 던진다. **부분 생성의 설계 한계이지
결함이 아니다.** 실제 화면은 이렇다.

```text
오류 [UNSUPPORTED_SCHEMA]: 모든 툴(1개)의 스키마를 지원하지 않아 생성할 케이스가 없습니다.
첫 원인: 지원하지 않는 JSON Schema 키워드 'maximum'가 있습니다.
```

이 둘을 붙이려면 부분 생성이 아니라 **키워드 지원 확대**가 필요하다(ADR-0004 가 예고한 후속).
`maximum` · `exclusiveMaximum` 은 실제 제약이라 무시하면 잘못된 입력을 만든다.

> **#141 전과 후도 다른 실행이다.** §1.3 의 두 서버(`server-everything` · `server-memory`)는
> #141 전에 `$schema` 로 막힌 것이고, 같은 서버를 #141 이후 다시 돌린 것이 §1.4 다. §1.3 의
> "2개" 와 여기 "8개" 를 더하면 안 된다 — 겹친다.

1. **#135 를 고친다.** 확인한 두 서버는 툴 전부가 `$schema` 를 갖는다 — **여기가 안 뚫리면
   이 둘은 적용 완료로 못 간다.** 적용 저장소 수가 0에서 안 움직이는 첫 번째 원인이다.
   다만 **이걸 고치면 끝나는 서버와 아닌 서버가 갈린다** — `server-memory` 는 다른 미지원 키가
   없어 #135 만으로 뚫리고, `server-everything` 은 `get-resource-links`(`minimum`·`maximum`) ·
   `gzip-file-as-resource`(`format`) 두 툴이 남는다. 그 셋의 지원 여부는 #135 와 **별건으로 따로
   추적한다**(§2.2). **표본이 2개뿐이라 "대부분의 서버가 그렇다" 로 넓히지 않는다.**
2. **#136 이 머지되면 나머지 서버를 붙인다.** 지금은 실패할 때마다 `generate` 소스를 읽어야 해서
   서버당 비용이 크다. 순서를 이렇게 잡은 이유가 §2.3 이다.
3. **비-TypeScript-SDK 서버를 최소 1개 붙인다.** §1.3 의 표본 한계 때문이다. 지금 표본 2개가
   같은 SDK 를 공유해서, 서버 동작에 대한 어떤 일반화도 근거가 없다. #89 가 이것 때문에 보류다.
4. **§1.2 3·4행의 조건을 갖춘 서버를 의도적으로 고른다.** 우연히 만나기를 기다리면 안 된다.
   툴 20개 이상인 서버, stdout 에 로그를 섞는 서버를 찾아서 붙여야 그 두 행이 닫힌다.
5. **#71 을 닫으려면 npm 배포 담당이 남았다.** 도그푸딩 담당만 정해졌다.

**#137(원격 서버 지원)은 이 목록에 없다.** 동결까지 머지될지 반반이고 ADR 이 붙는 규모라,
원격 서버를 도그푸딩 후보에 넣는 계획은 그 일정에 기대지 않는다. stdio 서버만으로 §10 을 채운다.

외부 저장소에 PR 을 보낼 때는 상대 프로젝트의 기여 규칙을 먼저 읽는다. **홍보성 PR 로 보이면
역효과다** (§10).

`generate --provider claude` 를 승인 화면까지 실제로 돌렸다. 자동으로는 못 돌리는 부분이다.

- 시험 실행 8건에서 미확인 **6건**. 설계 §9 예고값과 같다. 판정은 통과 7 · 실패 1 로 종전
  그대로이고, 미확인 6건은 전부 **통과한** 케이스다. 종료 코드도 안 바뀌었다.
- 미확인 목록이 케이스 id 와 응답 한 줄로 나왔다. 응답은 전부 이 서버가 손으로 쓴 거절 문장이다
  (`→ 'city' 는 문자열이어야 합니다.` 류). SDK 검증 지문이 아니라서 지문 셋에 안 걸린다.

  요청할까요?`). 실제 `claude` CLI(haiku)가 돌았고 6건 전부 `거절로 보임` 으로 답했다. 관찰
  기록의 결론(확인 못 한 16건의 정체는 전부 정상 거절)과 같은 방향이다.
- 참고 문장("이 진단은 참고입니다. 케이스 판정과 저장 여부를 바꾸지 않습니다.")이 붙었고, 진단
  뒤에도 입력값 교정과 저장 흐름이 그대로 이어졌다.
- `test` 명령에서도 요약 아래 고지 줄이 나오고 종료 코드는 0 그대로였다.
