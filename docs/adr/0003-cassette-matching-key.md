## 배경

`@ohmymcp-hsu/record`는 MCP 툴 호출 결과를 카세트 파일로 저장하고, 같은 요청이 다시
들어왔을 때 저장된 응답을 재생해야 한다. 이때 같은 입력은 항상 같은 카세트 매칭
결과를 만들어야 하므로, 요청 객체의 필드 순서나 실행 시점에 따라 결과가 달라지면
안 된다.

카세트는 dry run 승인 게이트와 CI 실행을 동시에 받친다. 실제 서버의 읽기 전용 툴도
임베딩 API, LLM 호출, 유료 시세 API처럼 비용이 들거나 실행마다 응답이 바뀔 수 있다.
첫 실행에서 녹화하고 이후에는 재생해야 외부 호출 없이 같은 바이트를 검증할 수 있다.

현재 `record(options)`와 `replay(cassette)` 스텁은 이 용도를 표현하지 못한다. 녹화할
대상 `McpClient`가 없고, 재생된 응답을 `callTool` 호출자에게 돌려줄 경로도 없다.
따라서 `McpClient` 인터페이스를 수정하지 않고 감싸는 데코레이터가 필요하다.

또한 MCP 응답의 `raw`에는 타임스탬프, 요청 ID, 세션 ID처럼 실행할 때마다 달라지는
값이 들어갈 수 있다. 이런 값이 계약 스냅샷에 그대로 남으면 실제 동작은 같아도
테스트가 실패한다. 반대로 너무 많은 값을 제거하면 실제 계약 변경을 놓칠 수 있다.

마지막으로 카세트 파일은 저장소에 커밋될 수 있으므로 인증 헤더, API 키, 토큰 같은
비밀값이 섞이지 않도록 기본 마스킹 규칙이 필요하다. 매칭 키 자체도 파일에 남으므로
요청 인자를 그대로 문자열로 저장하면 안 된다.

## 선택지

- A안: 호출 순서만으로 매칭한다.
  - 구현은 가장 쉽지만, 테스트 순서가 바뀌거나 같은 툴을 여러 번 호출하면 잘못된
    응답을 재생할 수 있다.
- B안: 요청 객체를 `JSON.stringify`한 문자열로 매칭한다.
  - 별도 규칙은 적지만, 객체 키 순서가 바뀌면 같은 요청도 다른 키가 된다.
  - 요청 인자에 비밀값이 있으면 키 문자열을 통해 카세트에 남는다.
- C안: 툴 이름과 정규화된 인자(stable JSON)를 SHA-256 hex로 해시해 매칭한다.
  - 같은 의미의 요청을 안정적으로 같은 키로 만들 수 있고, 파일에 원본 인자가 키로
    새지 않는다.
- D안: 사용자가 완전히 직접 매칭 함수를 제공하게 한다.
  - 가장 유연하지만 첫 버전 API가 커지고, 패키지 간 통합 전에 결정해야 할 것이
    많아진다.

같은 키가 여러 번 등장할 때의 재생 방식도 함께 검토했다.

- 포인터 방식: 같은 키의 상호작용 배열을 호출 순서대로 소비한다.
  - 케이스 하나만 다시 돌리거나 실행 순서가 바뀌면 포인터가 어긋난다.
- 키 단위 조회 방식: 같은 키는 하나의 응답만 가진다.
  - 같은 요청에 다른 응답이 오는 서버는 비결정 서버로 드러난다.

비결정 필드 처리 방식도 함께 검토했다.

- 자동 추론 방식: 실행마다 바뀌는 값을 자동으로 찾아 제거한다.
  - 편리하지만 실제 계약 변경까지 숨길 위험이 있다.
- 고정 제외 목록 방식: 자주 등장하는 비결정 필드 이름만 제거한다.
  - 놓치는 필드가 있을 수 있지만, 어떤 값이 사라지는지 예측하기 쉽다.

## 결정

첫 구현은 C안을 기본으로 한다.

카세트 매칭 키는 `toolName`과 stable JSON으로 정규화한 `args`를 함께 넣은 구조를
SHA-256 hex로 해시해 만든다. stable JSON은 객체 키를 사전순으로 정렬하고, 배열 순서는
그대로 유지한다. 객체의 `undefined` 필드는 제거한다. 배열의 `undefined` 원소는 배열
위치를 보존하기 위해 JSON과 같은 `null`로 다룬다. 순환 참조와 sparse array는 카세트로
안전하게 표현할 수 없으므로 에러를 낸다.

같은 키는 포인터로 소비하지 않고 키 단위로 조회한다. 녹화 중 같은 키에 다른 응답이
오면 기존 응답을 덮어쓰지 않고 경고한다. 같은 요청에 매번 다른 응답이 오는 서버는
카세트가 숨겨야 할 차이가 아니라 별도로 고쳐야 할 비결정성이다.

`record` 패키지는 `McpClient`를 구현하는 데코레이터를 export한다.

```ts
export type CassetteMode = "record" | "replay" | "auto";

export interface CassetteClientOptions {
  cassette: Cassette | null;
  mode?: CassetteMode;
  cassettePath?: string;
  onFlush?: (cassette: Cassette) => Promise<void>;
  onWarning?: (message: string) => void;
}

export function cassetteClient(inner: McpClient, options: CassetteClientOptions): McpClient;
```

모드는 다음처럼 동작한다.

- `record`: 항상 실제 `inner`를 호출하고 새 카세트를 만든다.
- `replay`: 항상 카세트에서만 응답한다. 키가 없으면 에러를 낸다.
- `auto`: 카세트에 키가 있으면 재생하고, 없으면 실제 호출 뒤 카세트에 추가한다.

`mode`를 생략하면 `auto`로 동작한다. `cassettePath`는 파일 IO를 직접 하지 않는
`cassetteClient`가 실패 메시지에 경로를 표시할 수 있도록 받는 표시용 값이다.

`listTools`도 카세트에 저장한다. 재생 모드에서 `listTools`만 실제 서버로 나가면 서버가
떠 있지 않은 상황을 검증할 수 없고, 입력 계약 대조가 쓰는 `inputSchema`도 재현되지
않는다.

카세트 상호작용은 다음 정보를 저장한다.

```ts
export interface CassetteInteraction {
  key: string;
  request: {
    toolName: string;
    args: unknown;
  };
  response: {
    content: unknown;
    isError: boolean;
    raw: unknown;
  };
}

export interface Cassette {
  version: 1;
  interactions: CassetteInteraction[];
  tools?: ToolDef[];
}
```

> **철회됨 — ADR-0047.** 이 함수는 구현·배포됐지만 어느 패키지도 부르지 않았고,
> 카세트 저장 경로도 이 함수를 타지 않았다. 그 사이 ADR-0038 이 같은 문제에 반대
> 방향의 답(차이를 지우지 않고 보고한다)을 냈고 `runner` 가 그것을 구현했다. 0047 이
> 이 문단을 철회했다. **아래는 철회 전 원문이다 — 현재 계약이 아니라 기록으로 남긴다.**

계약 스냅샷(`snapshotContract`)은 `ToolResult.raw`를 기준으로 만들고, 기본적으로 아래
이름의 필드는 깊게 순회하며 제거한다.

- `id`
- `requestId`
- `sessionId`
- `timestamp`
- `createdAt`
- `updatedAt`
- `expiresAt`

비밀값은 카세트 저장 전에 문자열 `"[redacted]"`로 마스킹한다. 기본 마스킹 대상은
아래 목록이다. 대소문자와 구분자(`-`·`_`)는 무시한다.

- `authorization`
- `apiKey`
- `accessToken`
- `refreshToken`
- `token`
- `secret`
- `password`
- `cookie` (ADR-0039)

**판정은 이름 포함이 아니라 접미 단어열 일치다 (ADR-0039).** 키를 구분자와 카멜케이스
경계로 쪼갠 뒤, 뒤에서부터 이어붙인 조합이 목록과 정확히 일치할 때만 민감으로 본다.
`accessToken` 은 접미 `token` 이라 걸리고, `tokenCount` 는 접미가 `count` 라 안
걸린다. `Set-Cookie` 는 접미 `cookie` 로 걸리므로 목록에 `setcookie` 를 따로 넣지
않는다. 꼬리 숫자는 뗀다 — `apiKey0` 은 여전히 걸린다.

요청 `args`는 interaction 생성 시점에 먼저 마스킹한다. 저장된 request를 사람이 열어도
요청 비밀값 원문이 남지 않게 하기 위해서다. 응답 `content`/`raw`와 `tools`는 런타임
내부 카세트에서 원문을 유지하되, `onFlush`에는 마스킹된 저장용 카세트만 넘긴다. MCP
응답의 `content[].text`처럼 값이 JSON 문자열 자체로 들어오는 경우에는 그 문자열을
JSON으로 파싱할 수 있을 때만 구조화해 마스킹한 뒤 stable JSON 문자열로 저장한다. 이는
카세트 파일이나 flush 콜백에 비밀값이 남지 않는 것을 우선한 선택이며, 런타임 내부
카세트의 응답 원문은 바꾸지 않는다.

**`tools` 는 위와 다른 규칙을 쓴다 (ADR-0040).** `content`/`raw` 처럼 필드 이름으로
값 전체를 마스킹하면, `tools` 안의 `properties.<name>` 은 값이 아니라 선언 대상의
이름이라 스키마 자체가 부서진다(`{ type: "string", default: "sk-..." }` →
`"[redacted]"`). `onFlush` 시점에 `tools` 는 구조를 보존한 채 `default` ·
`examples` · `const` · `enum` 처럼 값이 들어가는 자리만 마스킹한다. 판정 키 목록은
위와 같고, 민감도는 `properties` 를 타고 내려가며 상속된다 — 감싸는 이름이 비밀값이면
그 안의 이름 없는 값도 비밀값이다. `properties`·`items` 만 재귀하며, ADR-0004 가
해석하지 않는 `allOf`·`anyOf`·`oneOf` 등은 재귀도 마스킹도 하지 않는다.

> **개정 제안 중 — ADR-0041.** 응답 마스킹이 `onFlush` 에서만 걸리므로 `record` 실행은
> 원문을, `replay` 실행은 마스킹된 값을 돌려준다. 0041 은 "런타임 내부 원문 유지"는
> 그대로 두고 **`callTool` 과 `listTools` 두 반환 경계**를 추가하는 방향이다.
> `listTools` 도 `replay` 는 카세트의 `tools` 를, `record` 는 실서버 원문을 돌려주므로
> 같은 비대칭을 갖는다.

첫 버전에서는 사용자 정의 매칭 함수, 사용자 정의 ignore 목록, TTL, 부분 매칭,
사용자 정의 마스킹 규칙을 제공하지 않는다.

## 이유

호출 순서 기반 매칭은 구현은 쉽지만 결정론성을 충분히 보장하지 못한다. 같은 테스트가
병렬화되거나 호출 순서가 조금만 바뀌어도 다른 응답을 재생할 수 있기 때문이다. 포인터
방식도 같은 문제를 가진다. 사용자가 케이스 하나만 다시 돌릴 때 재생 결과가 달라지면
카세트는 캐시가 아니라 숨은 상태가 된다.

`JSON.stringify`만 사용하는 방식도 부족하다. JavaScript 객체는 작성 방식에 따라 키
순서가 달라질 수 있고, 그러면 의미상 같은 요청이 다른 문자열이 된다. 또한 매칭 키가
그대로 파일에 저장되면 `apiKey`, `authorization`, `token` 같은 값이 request 마스킹을
우회해 남을 수 있다. 해시 키는 이 누출 경로를 닫는다.

완전 사용자 정의 매칭 함수는 나중에 필요할 수 있지만, 첫 버전에는 과하다. 현재
목표는 W3의 `--record`에서 `--replay`까지 왕복 성공이므로, 기본 규칙을 먼저 작고
명확하게 고정한다.

비결정 필드는 제거 목록을 작게 시작한다. 모든 동적 값을 자동으로 추론하려고 하면
실제 계약 변경까지 숨길 수 있다. 따라서 자주 등장하는 필드만 기본 제외하고,
부족한 부분은 후속 ADR 또는 옵션 설계로 확장한다.

비밀값 마스킹은 정확성보다 안전을 우선한다. 예를 들어 `tokenCount`처럼 `token`이라는
단어를 포함하지만 비밀값이 아닌 필드가 마스킹될 수 있다. 첫 버전에서는 일부 과한
마스킹을 감수하고, 카세트 파일에 비밀값이 남지 않는 것을 우선한다.

> **개정 제안 중 — ADR-0039.** 이 트레이드오프는 비용이 "카세트 파일이 지저분하다"일
> 때 성립했다. ADR-0041 이 마스킹을 테스트가 보는 값에까지 닿게 하면 비용이 "테스트가 그
> 필드를 영영 못 본다"로 바뀐다.

## 결과

- `record` 패키지는 `stableStringify`, `matchKey`, `redact`,
  `loadCassette`, `saveCassette`, `cassetteClient`를 공개 API로 제공한다.
  (`snapshotContract` 는 [ADR-0047](./0047-계약-스냅샷-api-철회.md) 에서 철회됐다.)
- `matchKey()`는 원본 인자로 계산하지만 반환값은 SHA-256 hex라서 파일에 비밀값이
  남지 않는다.
- `CassetteInteraction.key`는 필수다. 저장된 `request.args`는 마스킹될 수 있으므로
  카세트를 로드한 뒤 키를 재계산하지 않는다.
- `replay` 모드는 외부 호출 0회를 강제한다. 카세트에 없는 `callTool` 또는 저장되지
  않은 `listTools`는 에러다.
- `auto` 모드는 기존 카세트에 없는 호출만 실제 서버에 위임한다.
- `mode`를 생략하면 기본값은 `auto`다.
- `record` 모드는 기존 카세트를 덮어쓸 새 카세트를 만든다.
- 실서버 호출은 성공했지만 응답이나 tools를 JSON 카세트로 복제할 수 없으면 호출 결과는
  그대로 돌려주고, `close()`가 녹화 실패와 값 경로를 보고하며 `onFlush`는 호출하지 않는다.
- `onFlush`가 받는 카세트는 `request.args`, `response.content`, `response.raw`, `tools`의
  민감값을 마스킹한 저장용 값이다.
- `saveCassette()`는 상호작용과 `tools`를 모두 마스킹한 뒤 stable JSON으로 저장한다.
- `close()`는 `onFlush`가 있으면 카세트를 넘겨 저장 기회를 준 뒤 `inner.close()`를
  호출한다.
- 배열 순서는 의미 있는 입력으로 보고 유지한다. 배열 순서가 다르면 다른 요청으로
  취급한다.
- 순환 참조가 포함된 입력은 JSON 카세트로 저장할 수 없으므로 에러를 낸다.
