# ADR-0003: 카세트 매칭 키 설계와 비결정 필드(타임스탬프 등) 처리

- 상태: 제안
- 날짜: 2026-08-11
- 작성자: @ddxng5 (record파트)

## 배경

`@mcptest/record`는 MCP 툴 호출 결과를 카세트 파일로 저장하고, 같은 요청이 다시
들어왔을 때 저장된 응답을 재생해야 한다. 이때 같은 입력은 항상 같은 카세트 매칭
결과를 만들어야 하므로, 요청 객체의 필드 순서나 실행 시점에 따라 결과가 달라지면
안 된다.

또한 MCP 응답의 `raw`에는 타임스탬프, 요청 ID, 세션 ID처럼 실행할 때마다 달라지는
값이 들어갈 수 있다. 이런 값이 계약 스냅샷에 그대로 남으면 실제 동작은 같아도
테스트가 실패한다. 반대로 너무 많은 값을 제거하면 실제 계약 변경을 놓칠 수 있다.

마지막으로 카세트 파일은 저장소에 커밋될 수 있으므로 인증 헤더, API 키, 토큰 같은
비밀값이 섞이지 않도록 기본 마스킹 규칙이 필요하다.

## 선택지

- A안: 호출 순서만으로 매칭한다.
  - 구현은 가장 쉽지만, 테스트 순서가 바뀌거나 같은 툴을 여러 번 호출하면 잘못된
    응답을 재생할 수 있다.
- B안: 요청 객체를 `JSON.stringify`한 문자열로 매칭한다.
  - 별도 규칙이 적지만, 객체 키 순서가 바뀌면 같은 요청도 다른 키가 된다.
- C안: 툴 이름과 정규화된 인자(stable JSON)를 조합해 매칭한다.
  - 구현 난이도는 조금 올라가지만, 같은 의미의 요청을 안정적으로 같은 키로 만들 수
    있다.
- D안: 사용자가 완전히 직접 매칭 함수를 제공하게 한다.
  - 가장 유연하지만 첫 버전 API가 커지고, 패키지 간 통합 전에 결정해야 할 것이
    많아진다.

비결정 필드 처리 방식도 함께 검토했다.

- 자동 추론 방식: 실행마다 바뀌는 값을 자동으로 찾아 제거한다.
  - 편리하지만 실제 계약 변경까지 숨길 위험이 있다.
- 고정 제외 목록 방식: 자주 등장하는 비결정 필드 이름만 제거한다.
  - 놓치는 필드가 있을 수 있지만, 어떤 값이 사라지는지 예측하기 쉽다.

## 결정

첫 구현은 C안을 기본으로 한다.

카세트 매칭 키는 `toolName + stable JSON args`로 만든다. stable JSON은 객체 키를
사전순으로 정렬하고, 배열 순서는 그대로 유지한다. `undefined` 값은 JSON에 저장하지
않는다. 같은 툴 이름과 같은 인자 구조는 항상 같은 매칭 키를 가져야 한다.

카세트 상호작용은 다음 정보를 저장하는 방향으로 설계한다.

```ts
type CassetteInteraction = {
  key: string;
  request: {
    toolName: string;
    args: unknown;
  };
  response: {
    content: unknown;
    isError: boolean;
    raw: unknown;
  };
};
```

계약 스냅샷(`snapshotContract`)은 `ToolResult.raw`를 기준으로 만들고, 기본적으로
아래 이름의 필드는 제거한다.

- `id`
- `requestId`
- `sessionId`
- `timestamp`
- `createdAt`
- `updatedAt`
- `expiresAt`

비밀값은 카세트 저장 전에 문자열 `"[redacted]"`로 마스킹한다. 첫 버전의 기본
마스킹 대상은 아래 이름을 포함하는 필드다.

- `authorization`
- `apiKey`
- `accessToken`
- `refreshToken`
- `token`
- `secret`
- `password`

첫 버전에서는 사용자 정의 매칭 함수, 사용자 정의 ignore 목록, 사용자 정의 마스킹
규칙을 제공하지 않는다.

## 이유

호출 순서 기반 매칭은 구현은 쉽지만 결정론성을 충분히 보장하지 못한다. 같은 테스트가
병렬화되거나 호출 순서가 조금만 바뀌어도 다른 응답을 재생할 수 있기 때문이다.

`JSON.stringify`만 사용하는 방식도 부족하다. JavaScript 객체는 작성 방식에 따라 키
순서가 달라질 수 있고, 그러면 의미상 같은 요청이 다른 문자열이 된다. `record`
패키지의 핵심 목적이 재현 가능한 녹화와 재생이므로, 매칭 키 생성 단계에서 정규화가
필요하다.

완전 사용자 정의 매칭 함수는 나중에 필요할 수 있지만, 첫 버전에는 과하다. 현재
목표는 W3의 `--record`에서 `--replay`까지 왕복 성공이므로, 기본 규칙을 먼저 작고
명확하게 고정한다.

비결정 필드는 제거 목록을 작게 시작한다. 모든 동적 값을 자동으로 추론하려고 하면
실제 계약 변경까지 숨길 수 있다. 따라서 자주 등장하는 필드만 기본 제외하고,
부족한 부분은 후속 ADR 또는 옵션 설계로 확장한다.

비밀값 마스킹은 정확성보다 안전을 우선한다. 예를 들어 `tokenCount`처럼 `token`이라는
단어를 포함하지만 비밀값이 아닌 필드가 마스킹될 수 있다. 첫 버전에서는 일부 과한
마스킹을 감수하고, 카세트 파일에 비밀값이 남지 않는 것을 우선한다.

## 결과

- `record` 패키지는 stable JSON 정규화 함수를 가져야 한다.
- `snapshotContract()`의 첫 구현은 `ToolResult.raw`를 깊게 순회하면서 비결정 필드를
  제거해야 한다.
- 카세트 저장 로직은 응답을 쓰기 전에 비밀값 마스킹을 적용해야 한다.
- 같은 이름의 툴을 같은 인자로 여러 번 호출하면 같은 매칭 키가 만들어진다. 이 경우
  첫 구현은 같은 키의 상호작용 배열을 순서대로 재생하는 방식까지 고려해야 한다.
- 배열 순서는 의미 있는 입력으로 보고 유지한다. 배열 순서가 다르면 다른 요청으로
  취급한다.
- 순환 참조가 포함된 입력은 JSON 카세트로 저장할 수 없으므로 에러를 내야 한다.
- 첫 버전에서는 사용자 정의 매칭 함수와 사용자 정의 마스킹 규칙을 제공하지 않는다.
  특수한 서버 응답 구조를 가진 사용자는 후속 옵션 설계가 필요할 수 있다.
