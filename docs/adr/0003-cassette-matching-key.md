# ADR-0003: 카세트 매칭 키 설계와 비결정 필드(타임스탬프 등) 처리

- 상태: 제안
- 날짜: 2026-08-11
- 작성자: record 오너

## 해결하려는 문제가 무엇인가요?

`@mcptest/record`는 MCP 툴 호출 결과를 카세트 파일로 저장하고, 같은 요청이 다시
들어왔을 때 저장된 응답을 재생해야 한다. 이때 같은 입력은 항상 같은 카세트 매칭
결과를 만들어야 하므로, 요청 객체의 필드 순서나 실행 시점에 따라 결과가 달라지면
안 된다.

또한 MCP 응답의 `raw`에는 타임스탬프, 요청 ID, 세션 ID처럼 실행할 때마다 달라지는
값이 들어갈 수 있다. 이런 값이 계약 스냅샷에 그대로 남으면 실제 동작은 같아도
테스트가 실패한다. 반대로 너무 많은 값을 제거하면 실제 계약 변경을 놓칠 수 있다.

마지막으로 카세트 파일은 저장소에 커밋될 수 있으므로 인증 헤더, API 키, 토큰 같은
비밀값이 섞이지 않도록 기본 마스킹 규칙이 필요하다.

## 왜 해야 하나요?

이 프로젝트의 핵심 가치는 결정론성이다. 같은 입력은 항상 같은 결과를 만들어야 하고,
녹화·재생 기능은 네트워크나 실제 MCP 서버 상태에 의존하지 않고 테스트를 재현하기
위해 존재한다.

매칭 키와 비결정 필드 처리 규칙이 없으면 다음 문제가 생긴다.

- 같은 요청인데 객체 키 순서만 달라져 다른 카세트로 인식될 수 있다.
- 호출 순서가 바뀌면 잘못된 응답을 재생할 수 있다.
- `timestamp`, `requestId` 같은 값 때문에 실제 계약 변경이 없어도 스냅샷 테스트가
  실패할 수 있다.
- 인증 토큰이나 API 키가 카세트 파일에 저장될 수 있다.
- `record`, `replay`, `snapshotContract` 구현자가 서로 다른 기준으로 데이터를 다루게
  된다.

따라서 첫 구현 전에 카세트 매칭 키, 스냅샷 정규화, 비밀값 마스킹의 기본 규칙을
문서로 고정한다.

## 어떻게 해결했나요?

첫 구현은 C안을 기본으로 한다.

카세트 매칭 키는 `toolName + stable JSON args`로 만든다. stable JSON은 객체 키를
사전순으로 정렬하고, 배열 순서는 그대로 유지한다. `undefined` 값은 JSON에 저장하지
않는다. 같은 툴 이름과 같은 인자 구조는 항상 같은 매칭 키를 가져야 한다.

카세트 상호작용은 다음 정보를 저장하는 방향으로 설계한다.

```ts
type CassetteInteraction = {
  key: string;
  request: {
    toolName: string;
    args: unknown;
  };
  response: {
    content: unknown;
    isError: boolean;
    raw: unknown;
  };
};
```

계약 스냅샷(`snapshotContract`)은 `ToolResult.raw`를 기준으로 만들고, 기본적으로
아래 이름의 필드는 제거한다.

- `id`
- `requestId`
- `sessionId`
- `timestamp`
- `createdAt`
- `updatedAt`
- `expiresAt`

비밀값은 카세트 저장 전에 문자열 `"[redacted]"`로 마스킹한다. 첫 버전의 기본
마스킹 대상은 아래 이름을 포함하는 필드다.

- `authorization`
- `apiKey`
- `accessToken`
- `refreshToken`
- `token`
- `secret`
- `password`

## 이 PR의 한계 & 트레이드오프

이 초안은 첫 구현을 위한 기본 규칙만 정한다. 사용자 정의 매칭 함수, 사용자 정의
ignore 목록, 사용자 정의 마스킹 규칙은 아직 제공하지 않는다.

이 선택은 API를 작게 유지하고 W3 목표인 `--record` → `--replay` 왕복 성공에 집중할
수 있다는 장점이 있다. 대신 특수한 서버 응답 구조를 가진 사용자는 첫 버전에서 기본
규칙을 우회하기 어렵다.

비결정 필드 제거 목록도 작게 시작한다. 모든 동적 값을 자동으로 추론하면 실제 계약
변경까지 숨길 위험이 있기 때문이다. 그 대신 자주 등장하는 필드만 제거하고, 부족한
부분은 후속 ADR 또는 옵션 설계로 확장한다.

## 기존 기능에 미치는 영향

현재 `@mcptest/record`는 `record`, `replay`, `snapshotContract` 스텁만 존재하므로
실제 런타임 동작 변경은 없다.

다만 이 ADR이 채택되면 이후 구현은 아래 제약을 따른다.

- `snapshotContract()`는 `ToolResult.content`가 아니라 `ToolResult.raw`를 기준으로
  동작한다.
- `record()`는 카세트를 저장하기 전에 비밀값 마스킹을 적용해야 한다.
- `replay()`는 호출 순서만이 아니라 매칭 키를 기준으로 응답을 찾아야 한다.
- 같은 툴 이름과 같은 인자 구조는 같은 매칭 키를 만들어야 한다.

## Edge Case & 실패 시나리오

- 같은 툴을 같은 인자로 여러 번 호출하는 경우
  - 같은 매칭 키가 여러 번 생길 수 있으므로, 첫 구현은 같은 키의 상호작용 배열을
    순서대로 재생하는 방식을 고려해야 한다.
- 인자 객체의 키 순서가 다른 경우
  - stable JSON 정규화를 통해 같은 키로 취급한다.
- 배열 순서가 다른 경우
  - 배열은 의미 있는 입력으로 보고 순서를 유지한다. 따라서 배열 순서가 다르면 다른
    요청으로 취급한다.
- `undefined` 값이 포함된 경우
  - JSON에 저장하지 않는다. 카세트 파일이 JSON 기반이기 때문에 재생 가능한 값만
    남긴다.
- 순환 참조가 포함된 경우
  - JSON 카세트로 저장할 수 없으므로 에러를 내야 한다. 조용히 누락하면 재현성이
    깨질 수 있다.
- 비밀값 필드가 중첩 객체 안에 있는 경우
  - 깊게 순회하면서 마스킹한다.
- `tokenCount`처럼 `token`이라는 단어를 포함하지만 비밀값이 아닌 필드
  - 첫 버전의 단순 포함 규칙에서는 마스킹될 수 있다. 보수적으로 비밀 유출 방지를
    우선한다.

## 검토한 대안과 선택 이유

호출 순서만으로 매칭하는 안을 검토했다. 구현은 가장 쉽지만, 테스트 순서가 바뀌거나
같은 툴을 여러 번 호출하면 잘못된 응답을 재생할 수 있어 제외했다.

요청 객체를 `JSON.stringify`한 문자열로 매칭하는 안도 검토했다. 별도 정규화 규칙이
적다는 장점은 있지만, 객체 키 순서가 바뀌면 같은 요청도 다른 키가 되므로 결정론성이
부족하다.

사용자가 직접 매칭 함수를 제공하는 안도 검토했다. 가장 유연하지만 첫 버전 API가
커지고, 패키지 간 통합 전에 정해야 할 것이 많아진다. 현재 목표는 기본 녹화·재생
왕복 성공이므로 후속 확장 후보로 남긴다.

최종적으로 툴 이름과 정규화된 인자(stable JSON)를 조합하는 방식을 선택했다. 구현
난이도는 조금 올라가지만, 같은 의미의 요청을 안정적으로 같은 키로 만들 수 있기
때문이다.
