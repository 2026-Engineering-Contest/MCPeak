# ADR-0004: 생성 테스트의 자동화 범위

- 상태: 제안
- 날짜: 2026-08-12
- 작성자: @sunghoon0303(generate 오너)

## 배경

`@ohmymcp/generate`는 `ToolDef[]`의 `inputSchema`를 분석해 실행 가능한 MCP 테스트 초안을 생성한다. 그러나 JSON Schema만으로는 입력값의 비즈니스 의미나 정상 응답의 구체적인 내용을 알 수 없다. 예를 들어 날씨 도구의 입력이 도시 이름이라는 사실은 알 수 있어도 어떤 도시가 실제로 유효한지, 정상 응답의 온도가 얼마여야 하는지는 스키마만으로 결정할 수 없다.

자동 생성기가 이를 추측하면 실행 환경에 따라 테스트가 실패하거나, 실제 동작을 검증하지 못하는 거짓 확신을 줄 수 있다. 반대로 모든 JSON Schema 기능과 비정상 입력까지 처음부터 지원하면 `$ref`, 조합 스키마, 순환 참조 등으로 구현 범위가 지나치게 커진다. 따라서 첫 버전에서 자동 생성할 범위와 사람이 작성할 범위를 명확히 구분해야 한다.

또한 같은 툴 정의에서 항상 같은 소스가 생성되어야 코드 리뷰와 재생성이 가능하므로, 생성 값은 랜덤값·현재 시간·시스템 로케일에 의존하지 않아야 한다.

## 선택지

- A안: JSON Schema에서 생성 가능한 happy-path 테스트만 자동 생성하고, 비정상 입력·응답 내용·비즈니스 의미 검증은 사용자가 작성한다.
- B안: happy path와 invalid input 테스트를 모두 자동 생성하고 응답 내용도 스키마와 설명에서 추론한다.
- C안: 입력값 합성을 하지 않고 툴별 빈 테스트 템플릿만 생성해 모든 입력과 assertion을 사용자가 작성한다.

## 결정

첫 버전은 A안을 채택한다.

### 자동 생성 범위

- 툴마다 정상 입력을 사용하는 happy-path 테스트를 1개 생성한다.
- 입력 스키마의 루트는 객체인 경우만 지원한다.
- 객체 입력에는 `required`로 선언된 프로퍼티만 포함한다.
- `type`, `required`, `properties`, `items`, `enum`, `const`, `default`, `examples`와 이를 사용한 중첩 객체·배열을 지원한다. 이 목록에 없는 JSON Schema 키워드가 있으면 생성 전에 지원하지 않는 스키마로 거절한다.
- 위 목록과 별도로 `description`, `title`, `$schema`를 허용한다. 셋 다 annotation이라 어떤 값이 오든 합성될 입력이 달라지지 않으므로, 거절해도 얻는 것이 없고 서버만 막힌다. 값이 문자열이 아니면 거절한다.

  `description`과 `title`은 구현에는 처음부터 있었으나 이 문서에 적히지 않아 어긋나 있었다. `$schema`는 2026-08-17 도그푸딩에서 이 누락이 드러나 함께 정리했다 — 공식 TypeScript SDK가 zod에서 스키마를 뽑을 때 기본으로 붙이는 키라, 막아 두는 동안 `server-everything` 13개 툴과 `server-memory` 9개 툴이 **전부** 첫 키에서 거절됐다 (`docs/adoption.md` §2.2 · 이슈 #135).

  `minimum`, `maximum`, `format`은 여기 해당하지 않는다. 실제 제약이라 무시하면 잘못된 입력을 만든다. 이 셋의 거절은 유지하며 회귀 테스트로 고정했다.
- 객체는 필수 프로퍼티를 재귀적으로 생성한다.
- 배열은 `items` 스키마에서 원소 1개를 재귀적으로 생성한다.
- 생성된 테스트는 도구 호출 결과가 오류 응답이 아닌지, 즉 `isError`가 `false`인지만 검증한다.
- 응답 본문의 필드나 구체적인 값은 자동으로 추측하거나 검증하지 않는다.

### 값 선택 규칙

입력값은 다음 우선순위에 따라 결정론적으로 선택한다.

1. `const`
2. `default`
3. `examples[0]`
4. `enum[0]`
5. 타입별 고정값

타입별 고정값은 다음과 같다.

| 타입 | 값 |
|---|---|
| `string` | `"example"` |
| `number`, `integer` | `0` |
| `boolean` | `true` |
| `object` | 필수 프로퍼티를 재귀 생성한 객체 |
| `array` | `items`에서 원소 1개를 재귀 생성한 배열 |
| `null` | `null` |

빈 `examples`는 입력 후보가 없는 것으로 보고 다음 우선순위로 진행한다. 빈 `enum`은 만족 가능한 값이 없으므로 생성 전에 지원하지 않는 스키마로 거절한다.

우선순위에서 처음 선택한 후보는 JSON 값이어야 하며, 해당 위치의 재귀 스키마 전체를 검증해 `type`, `enum`, `const`, `required`, `properties`, `items` 등 모든 지원 제약을 만족해야 한다. 따라서 `default`나 `examples[0]`도 같은 검증을 통과해야 한다. 선택한 후보가 제약과 모순되면 다음 후보로 대체하거나 임의로 보정하지 않고 지원하지 않는 스키마로 처리한다.

### 자동 생성하지 않는 범위

- 비정상 입력과 오류 응답 테스트
- 응답 본문의 구체적인 값이나 비즈니스 규칙 검증
- 툴 설명이나 이름에서 도메인 입력값을 추론하는 기능
- 선택 프로퍼티를 임의로 입력에 포함하는 기능
- `$ref`, `oneOf`, `anyOf`, `allOf`, 순환 구조 등 첫 버전에서 명시적으로 지원하지 않는 JSON Schema 기능
- 랜덤값, 현재 시간 또는 시스템 로케일에 의존하는 값 생성

지원하지 않는 스키마를 발견하면 TODO나 유효하지 않은 테스트를 억지로 생성하지 않는다. 파일을 쓰기 전에 생성을 중단하고 툴 이름, 스키마 경로와 지원하지 않는 이유를 포함한 명확한 오류를 반환한다. 여러 파일을 생성할 때는 모든 툴의 분석·합성·렌더링·검증을 먼저 메모리에서 완료한 후 파일 쓰기를 시작해, 스키마 오류로 일부 파일만 생성되는 상황을 방지한다.

### 출력 파일과 재생성 정책

- 툴마다 `<정규화된-도구-이름>.generated.ts` 파일 하나를 생성한다.
- 파일명은 영문 소문자, 숫자와 하이픈 중심으로 정규화하고 Windows 예약 이름, 빈 결과와 정규화 충돌에는 결정론적 해시 또는 접미사를 사용한다.
- 계산한 최종 경로가 반드시 `outDir` 내부인지 파일을 쓰기 전에 검사한다.
- 생성 파일에는 자동 생성 파일이며 직접 수정하지 말라는 주석을 포함하고, 사람이 작성하는 테스트는 별도 파일에 둔다.
- 기본값에서는 기존 생성 대상 파일을 덮어쓰지 않는다. 대상이 하나라도 존재하면 어떤 파일도 쓰기 전에 `OUTPUT_FILE_EXISTS` 오류로 중단한다.
- 사용자가 재생성을 명시적으로 승인한 `overwrite: true`일 때만 기존 생성 파일을 교체한다.
- 덮어쓰기 파일은 심볼릭 링크를 따라가지 않는 방식으로 원자적으로 열며, 대상이 심볼릭 링크이거나 플랫폼이 이를 지원하지 않으면 파일을 변경하지 않고 실패한다.

### 생성 결과와 Runner 연동

생성 결과는 MCP 서버 연결 방법이나 `McpClient` 생성 방법을 포함하지 않는다. 실제 client 생성과 수명주기 관리는 CLI 또는 사용자의 별도 실행 진입점이 담당한다.

생성 테스트는 Runner의 선언형 `TestSuiteSpec`을 사용하고, 각 happy-path 케이스는 `callTool` 작업과 `{ type: "isError", expected: false }` assertion으로 표현하는 방향을 제안한다. 생성한 명세는 파일을 쓰기 전에 Runner의 공개 validator로 검증한다.

compile·repair 요청을 준비할 때는 [Runner 설계의 Generate 요청 검증 계약](../superpowers/specs/2026-08-11-runner-design.md)에 따라 `tools[].inputSchema`를 redaction보다 먼저 runtime `ReadonlyJsonValue`로 검증한다. 비 JSON 값은 preview·binding·provider 호출 전에 동기 `GenerateRequestValidationError`로 거절하며, 오류 코드는 `INVALID_TOOL_INPUT_SCHEMA`를 사용한다.

다만 `generate → runner → core` 의존 방향과 `@ohmymcp/generate`의 Runner workspace dependency 추가는 이 ADR만으로 확정하지 않는다. Runner 담당과 팀의 별도 승인을 받은 뒤 의존성과 구체적인 생성 파일 형식을 구현한다. 승인 전에는 Runner 계약을 generate 내부에 복사하지 않는다.

## 이유

happy path 한 개와 최소 assertion은 스키마 기반 자동화가 신뢰할 수 있는 범위다. 이 범위만으로도 모든 툴을 실제로 호출할 수 있는 테스트 초안을 빠르게 제공하면서, 생성기가 알 수 없는 도메인 의미를 추측하지 않는다.

고정된 값 선택 우선순위와 타입별 기본값은 동일한 입력에서 항상 동일한 결과를 만든다. 이는 생성 파일의 불필요한 변경을 줄이고 리뷰, 재생성 및 회귀 테스트를 단순하게 한다.

지원하지 않는 스키마에서 사전 실패하는 정책은 조용히 잘못된 입력을 만들거나 실행되지 않는 테스트를 성공한 것처럼 남기는 것보다 안전하다. 비정상 입력과 응답 내용 검증을 사용자에게 남기면 첫 버전의 구현 범위를 통제하면서도 사람이 작성한 테스트로 필요한 검증을 확장할 수 있다.

선언형 `TestSuiteSpec`을 목표로 하면 generate가 서버 실행과 client 수명주기를 알 필요가 없고, CLI와 다른 실행 환경도 같은 테스트 명세를 사용할 수 있다. 단, 패키지 간 의존성은 공개 계약이므로 구현 전에 별도로 합의한다.

## 결과

- generate는 JSON Schema 검사, 결정론적 입력값 합성, 테스트 명세 구성, 소스 렌더링과 안전한 파일 저장에 집중한다.
- 사용자는 생성 파일을 초안으로 사용하고, 비정상 입력·응답 내용·비즈니스 의미 검증을 별도 파일에 작성한다.
- 지원 범위를 벗어난 스키마는 파일 쓰기 전에 실패하므로, 스키마 검증 오류로 인한 부분 결과를 남기지 않고 명확한 오류로 드러난다.
- 같은 `ToolDef[]`와 옵션은 항상 같은 테스트 소스를 생성해야 한다.
- 첫 버전은 완전한 JSON Schema 구현을 목표로 하지 않으며, 제외된 키워드는 실제 사용 사례와 별도 ADR 또는 후속 결정에 따라 확장한다.
- Runner 연동이 승인되면 generate 패키지 의존성 변경과 공개 기능 추가를 changeset에 기록한다.
