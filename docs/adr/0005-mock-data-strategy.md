# ADR-0005: 목 데이터 생성 전략 — 사람이 작성 vs 스키마 기반 생성

- 상태: 채택
- 날짜: 2026-08-11
- 작성자: @storyrago (③ mock server 파트)

> 원래 제목은 "스키마 기반 랜덤 vs 고정 시드" 였다. 검토 과정에서 **제3의 선택지(사람이 직접 작성)**
> 가 실제 사용 시나리오의 주력임이 드러나 제목을 넓혔다.

## 배경

`@ohmymcp-hsu/mock` 은 실제 MCP 서버 없이, MCP 를 사용하는 프로그램을 테스트하게 해준다.
그러려면 목이 툴 호출에 **무슨 값을 돌려줄지** 정해야 한다.

자동 생성이 원리적으로 가능하다. `ToolDef.inputSchema` 가 JSON Schema 이므로 타입에 맞는
값을 만들어낼 수 있다. 실제로 `outputSchema` 가 있다면 응답도 같은 방식으로 만들 수 있다.

그런데 두 가지 제약이 있다.

1. **결정론성이 이 프로젝트의 핵심 가치다** (CLAUDE.md). 같은 입력에 항상 같은 결과가
   나와야 하고, 타임스탬프·랜덤값에 의존하는 코드를 넣지 않는다.
2. **목을 쓰는 이유가 "특정 상황의 재현"이다.** 실제 서버로는 만들어내기 어렵거나 비용이
   드는 상황 — 외부 API 가 특정 오류를 돌려주는 경우, 계절·시간·외부 상태에 종속된 값,
   호출마다 요금이 발생하는 경로 — 을 원하는 대로 세워두고 그 위에서 검증하려는 것이다.

2번이 결정적이다. 사용자가 원하는 것은 "스키마에 맞는 아무 값" 이 아니라 **"내가 지정한 그 값"** 이다.

## 선택지

**A. 스키마 기반 랜덤 생성**
faker 계열로 스키마 타입에 맞는 임의값을 만든다. `number` 필드는 호출할 때마다 다른 숫자가 된다.

**B. 스키마 기반 고정 시드 생성**
같은 스키마 + 같은 시드 → 항상 같은 값. 결정론적이다.

**C. 사람이 직접 작성 (수동 주입)**
사용자가 툴 이름과 인자 조합별로 돌려줄 응답을 직접 명시한다.

**D. C + B 병행**
직접 주입을 우선 조회하고, 없으면 시드 기반 생성으로 폴백한다.

## 결정

**C 를 먼저 낸다.** A 는 폐기한다. B 는 폐기하지 않고 보류하며, 필요해지면 D 형태로 붙인다.

응답은 **툴 이름 + 인자 조합**을 키로 주입한다. 인자를 키에 포함하는 이유는, 툴 이름만으로는
같은 툴을 인자만 바꿔 부르는 경우를 구분할 수 없기 때문이다.

공개 API 의 구체적인 형태와 사용법은 `packages/mock/README.md` 를 따른다. 이 문서는 결정과
근거만 다룬다.

## 이유

**A 를 폐기한 이유.** 랜덤은 CLAUDE.md 가 명시적으로 금지한다. 같은 테스트가 어제는 통과하고
오늘은 실패하면 테스트 도구로서 실격이다. 논의할 것이 없다.

**B 를 먼저 내지 않은 이유.** B 는 결정론적이지만 **어떤 값이 나올지 사용자가 미리 알 수 없다.**
어떤 숫자가 나올지, 어떤 문자열이 나올지를 시드가 정한다. 그러면 테스트를 쓰려면 일단 한 번
돌려서 나온 값을 베껴 와야 하고, 그렇게 쓴 단언은 "이 상황을 검증하겠다" 는 의도를 표현하지
못한다. 배경 2번의 요구를 B 로는 충족할 수 없다.

**C 를 고른 이유.** 의도가 코드에 그대로 드러난다. 사용자가 적어 넣은 값 자체가 "이 상황을
검증하겠다" 는 선언이 되므로, 테스트를 읽는 사람이 의도를 되짚을 필요가 없다.
구현도 가장 싸다 — 매칭 키 → 응답의 `Map` 하나이며 새 의존성이 필요 없다.
A·B 는 JSON Schema 를 해석해 값을 만드는 생성기가 필요하고, 이는 외부 의존성이거나 상당한
분량의 코드다. §11 에서 목 서버는 **3순위 축소 대상**이므로 큰 투자를 선택하기 어렵다.

**B 를 폐기하지 않은 이유.** B 에는 C 가 못 하는 쓸모가 있다. 값이 무엇이든 상관없고 **형태만
맞으면 되는** 경우 — 예를 들어 툴 20개짜리 서버에 대해 "모든 툴이 스키마에 맞는 응답을
돌려주는가" 만 확인하는 스모크 테스트에서는, 20개를 일일이 주입하는 것이 순수한 부담이다.
이 수요가 실제로 나타나면 D 로 확장한다.

## 결과

**얻은 것**

- 사용자가 임의의 상황을 정확히 재현할 수 있다.
- 같은 호출이 항상 바이트 단위로 동일한 응답을 낸다 (테스트로 고정).
- 새 런타임 의존성 0개.

**받아들인 비용**

- **모든 호출에 명시적 주입이 필요하다.** 주입하지 않은 호출은 `isError: true` 와 함께
  무엇이 등록돼 있는지 알려주는 메시지를 돌려준다. 툴이 많은 서버를 상대할 때 번거롭다.
  이것이 D 를 검토하게 만드는 신호가 된다.
- **인자 매칭이 완전 일치다.** 부분 일치·와일드카드가 없다. 같은 툴을 인자만 바꿔
  10번 부르면 10번 주입해야 한다.

**후속 과제**

  같은 문제다. 두 패키지가 다른 규칙을 쓰면 사용자가 혼란스럽다. ADR-0003 결정 후 정합을 맞춘다.~~
  → **해소(2026-08-13).** ADR-0003 이 `toolName + stable JSON args`(객체 키 사전순, 배열 순서
  유지, `undefined` 값은 저장하지 않음)로 결정됐고, `stableKey` 를 거기에 맞췄다. 원래 `stableKey`
  는 값이 `undefined` 인 키를 `null` 로 남겨서 `on(tool, { a: 1, b: undefined }, ...)` 로 주입한
  응답이 실제 호출 `{ a: 1 }` 과 다른 키가 됐다 — JSON-RPC 를 건너온 인자에는 `undefined` 가
  있을 수 없으므로 영영 잡히지 않는 주입이었다. 이제 두 패키지가 같은 규칙을 쓴다.
- D(시드 폴백) 도입 여부는 실사용 후 판단한다. 스모크 테스트 수요가 확인되기 전에는 만들지 않는다.
- `outputSchema` 를 선언하는 서버가 흔해지면 B 의 구현 난이도가 크게 낮아진다. 그때 재검토한다.
