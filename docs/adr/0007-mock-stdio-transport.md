# ADR-0007: 목 서버의 두 번째 트랜스포트 — stdio 진입점을 낼 것인가

- 상태: 채택
- 날짜: 2026-08-12
- 작성자: @storyrago (③ mock server 파트)

## 배경

ADR-0005 에서 목 데이터 전략을 정하면서 목 서버는 **Streamable HTTP** 로 뜨기로 했다.
목의 사용자는 "MCP 를 사용하는 프로그램" 이고 그들은 HTTP 로 붙기 때문이다.

그런데 구현을 마치고 나니 문제가 하나 남았다. **우리 도구 중 아무것도 목 서버에 붙지 못한다.**

- `core.connect()` 는 `{ command, args, env, cwd }` 만 받는다. URL 을 넣을 자리가 없다 (#16)
- `cli test` 도 `--command` 기반이다
- 결과적으로 `@ohmymcp/mock` 을 import 하는 코드가 저장소 전체에 **0곳**이었다

CONTRIBUTING §6 은 *"우리 도구로 우리를 검증한다"* 를 요구하는데, 목 경로에서만 그것이
성립하지 않는 상태다. 만들어놓고 아무도 쓰지 않는 패키지는 마감 때 잘릴 후보가 된다
(§11 에서 목 서버는 3순위 축소 대상이다).

## 선택지

**A. #16 을 기다린다 — `core.connect()` 가 HTTP 를 지원할 때까지**
`core` 가 URL 분기를 받으면 그대로 붙는다. 목 쪽은 손댈 것이 없다.

**B. 목을 stdio 로 바꾼다 — HTTP 를 버린다**
`core` 와 트랜스포트가 일치하므로 지금 당장 붙는다. ADR-0005 의 결정을 뒤집는다.

**C. stdio 진입점을 하나 더 낸다 — HTTP 는 그대로 둔다**
`serveStdio(definition)` 과 `ohmymcp-mock` 실행 파일을 추가한다. 두 트랜스포트를 모두 낸다.

## 결정

**C 를 채택한다.** HTTP(`createMockServer`)는 그대로 두고 stdio 진입점을 추가한다.

```
createMockServer(options) -> { url, on, close }   외부 프로그램용 (HTTP, 기존)
serveStdio(definition)                            우리 도구용 (stdio, 신규)
ohmymcp-mock <definition.json>                    위를 실행 파일로 노출
```

응답 매칭 규칙은 **두 진입점이 공유한다.** 인자를 지정한 응답이 우선하고, `ANY`(정의
파일에서는 `args` 생략)가 나머지를 받는다.

## 이유

**A 를 기다리지 않은 이유.** #16 은 다른 파트(① MCP 서버 테스트) 소유이고 **담당자가
배정되지 않은 채 열려 있다.** 마감이 8/27, 코드 동결이 8/24 다. 남의 파트의 미배정
작업에 우리 패키지의 검증 가능 여부를 걸어둘 여유가 없다. #16 은 여전히 필요하지만
(외부 프로그램이 HTTP 로 붙는 시나리오를 우리가 테스트하려면 결국 있어야 한다),
그것을 기다리는 동안 목이 검증 불가 상태로 남는 것은 별개 문제다.

**B 를 고르지 않은 이유.** ADR-0005 의 판단은 여전히 유효하다. 목을 쓰는 외부 프로그램은
HTTP 로 붙는다. stdio 로 바꾸면 우리 편의를 위해 사용자의 경로를 없애는 셈이다.

**C 의 실제 비용이 작았다.** 요청 핸들러(툴 목록 응답, 매칭, 실패 메시지)를 함수 하나로
빼내면 두 트랜스포트가 그것을 공유한다. 추가된 것은 `StdioServerTransport` 연결과
정의 파일 파싱뿐이다. 새 런타임 의존성은 없다.

**stdio 는 선언적일 수밖에 없다.** HTTP 는 띄운 뒤 `mock.on()` 으로 주입하지만, stdio 는
프로세스가 곧 서버라 밖에서 메서드를 부를 수 없다. 그래서 `MockDefinition` 을 미리
넘기는 형태가 된다. 이 차이는 트랜스포트의 성질에서 오는 것이지 설계 취향이 아니다.

**두 진입점의 매칭 규칙을 일부러 통일했다.** stdio 정의 파일에서 `args` 생략을 허용하면
"파일로 쓸 때는 되는데 코드로 쓸 때는 안 되네" 가 된다. 그래서 `ANY` 를 `on()` 에도 넣었다.
ADR-0005 의 "받아들인 비용" 에 적어둔 *"같은 툴을 인자만 바꿔 10번 부르면 10번 주입해야
한다"* 가 이것으로 완화된다.

## 결과

**얻은 것**

- `ohmymcp test suite.json --command ohmymcp-mock --arg def.json` 이 동작한다.
  우리 CLI 로 우리 목 서버를 테스트해 3/3 통과를 확인했다. §6 이 목 경로에서 성립한다.
- 목이 처음으로 소비자를 갖는다.
- `ANY` 로 반복 주입이 줄었다.

**받아들인 비용**

- **진입점이 둘이라 문서와 테스트가 두 벌이다.** 매칭 규칙이 갈리지 않도록 핸들러를
  공유하지만, 트랜스포트별 동작(포트 할당 vs stdin 종료)은 따로 검증해야 한다.
- **stdio 는 실행 중 주입이 안 된다.** 시나리오 도중 응답을 바꾸려면 HTTP 를 써야 한다.
- **`ANY` 가 과용되면 목이 느슨해진다.** 인자를 안 보고 다 받으면 "잘못된 인자로 불렀는데
  통과" 하는 테스트가 생긴다. 기본은 인자 지정이고 `ANY` 는 예외로 쓴다.

**후속 과제**

- #16(`core.connect()` 의 HTTP 지원)은 여전히 필요하다. 이 ADR 은 그것을 대체하지 않는다.
  외부 프로그램이 HTTP 로 붙는 경로를 **우리가 테스트하려면** 결국 있어야 한다.
- CI 의 E2E 잡에 이 경로를 넣을지는 `examples/` 오너가 정해지면 함께 정한다.
  현재 §2.1 오너 표에 `examples/` 가 빠져 있다.
- ~~매칭 키 정규화는 `record` 의 ADR-0003 과 같은 문제다 (ADR-0005 후속 과제와 동일).~~
  → **해소(2026-08-13).** ADR-0003 의 결정에 `stableKey` 를 맞췄다. 근거는 ADR-0005 후속 과제 참조.
  두 진입점(HTTP·stdio)이 이 함수를 공유하므로 양쪽 다 같이 바뀐다.
