# ADR-0010: 응답 스키마는 JSON Schema의 고정된 부분집합만 지원한다

- 상태: 제안
- 날짜: 2026-08-13
- 담당: runner
- 작성자: @seodduu (runner 파트)
- 승인: 미승인
- 참조: `docs/superpowers/specs/2026-08-13-response-body-assertion-design.md` §4, §6, §10.5,
  `docs/superpowers/plans/2026-08-13-response-body-assertion-implementation.md` §4

## 배경

`bodyMatchesSchema` 단언은 사용자가 스위트 파일에 적은 스키마로 MCP 응답 본문을 검사한다.
이때 "스키마"가 무엇인지 정해야 한다. JSON Schema 2020-12 전체를 받으면 사용자에게 익숙한
표기를 그대로 쓸 수 있지만, 우리가 평가기를 직접 구현해야 하고 조합자와 `$ref`까지 다뤄야 한다.

이 프로젝트는 실패 메시지가 곧 제품이다. `oneOf`의 세 번째 분기가 왜 실패했는지를 사람이
읽을 수 있는 한국어 한 문장으로 만드는 일은 지원 키워드가 늘어날수록 급격히 어려워진다.
결정론성도 함께 걸려 있다. 평가 순서가 정해져 있지 않으면 같은 응답에 다른 보고서가 나온다.

## 선택지

- A안: JSON Schema 2020-12 전체를 지원한다. 검증은 외부 라이브러리에 맡긴다.
- B안: 고정된 부분집합만 지원하고, 목록 밖 키워드는 명세 검증 단계에서 거부한다.
- C안: 부분집합만 평가하되 목록 밖 키워드는 조용히 무시한다.
- D안: 스키마 대신 사용자 콜백 함수를 받는다.

## 결정

B안을 택한다. 지원 키워드를 아래 13개로 고정하고, 그 밖의 키워드가 나오면
`UNSUPPORTED_SCHEMA_KEYWORD` 이슈로 명세 검증 단계에서 거부한다.

```
type, const, enum,
required, properties, additionalProperties,
items, minItems,
minLength, maxLength, stringContains,
minimum, maximum
```

`oneOf` `anyOf` `allOf` `not` `$ref` `pattern`은 지원하지 않는다.

키워드는 `type`과 짝을 이룰 때만 쓸 수 있다. `minimum`은 `"type": "number"` 또는
`"type": "integer"`가 같은 스키마에 있어야 하고, `required`는 `"type": "object"`가 있어야
한다. 짝이 없으면 `SCHEMA_KEYWORD_REQUIRES_TYPE`으로 거부한다.

이 짝 요구는 공개 JSON Schema(`MCP_SUITE_JSON_SCHEMA`)에는 표현하지 않는다. `if`/`then`이
필요한데 parity 평가기가 지원하지 않는 키워드이고, 이를 위해 평가기 범위를 넓히면 검증 대상보다
검증 도구가 복잡해진다. 설계 문서 §10.5의 결정이며, 이 의도적 불일치는
`spec-schema.test.ts`의 "타입 짝 요구는 대조 대상이 아니다" 테스트로 고정한다.

## 이유

- 실패 메시지를 키워드마다 손으로 쓸 수 있는 규모로 유지한다. 13개는 각각 한 문장씩 쓸 수 있다.
  조합자를 넣으면 "어느 분기에서 왜"를 설명해야 하고 그 문장은 사람에게 도움이 되지 않는다.
- 목록 밖 키워드를 조용히 무시하면(C안) 사용자는 검사되고 있다고 믿는데 실제로는 검사되지 않는다.
  이 도구의 존재 이유와 정면으로 충돌한다. 거부가 유일하게 정직한 동작이다.
- 외부 검증 라이브러리(A안)는 목록에 없는 런타임 의존성 추가이고, 오류 문안을 우리가 통제할 수
  없어 실패 메시지 품질이 라이브러리에 종속된다.
- 콜백(D안)은 스위트를 직렬화할 수 없게 만든다. 녹화·재생과 baseline 생성이 불가능해진다.
- `type` 짝 요구는 `{"minimum": 0}` 같은 스키마가 문자열 응답에 조용히 통과하는 일을 막는다.
  키워드가 어떤 타입에 적용되는지 사용자가 명시하게 만들면 평가 규칙도 결정론적으로 단순해진다.

## 결과

- `SuiteValidationIssueCode`에 `UNSUPPORTED_SCHEMA_KEYWORD`와 `SCHEMA_KEYWORD_REQUIRES_TYPE`
  두 개가 추가됐다. 이 코드를 소비하는 쪽(`cli` 보고서 렌더링)은 다음 웨이브에서 대응한다.
- 사용자가 익숙한 JSON Schema 키워드를 쓰다 거부당할 수 있다. 대신 힌트 문장에 지원 키워드
  전체 목록을 넣어 무엇으로 바꿔 쓸지 바로 보이게 했다.
- 지원 키워드를 나중에 넓히는 것은 열려 있다. 넓히는 방향은 기존 스위트를 깨지 않는다.
  좁히는 방향은 깨뜨리므로 처음부터 좁게 시작했다.
- 새 키워드를 추가할 때 갱신해야 하는 곳은 네 군데다. `spec/types.ts`의 `ResponseSchema`,
  `spec/validation.ts`의 `RESPONSE_SCHEMA_KEYWORDS`와 `KEYWORD_TYPES`,
  `spec/json-schema.ts`의 `responseSchema` $defs, 그리고 `tests/helpers/schema-evaluator.ts`의
  평가 범위다. 네 군데가 어긋나면 `spec-schema.test.ts`의 parity 테스트가 깨진다.
