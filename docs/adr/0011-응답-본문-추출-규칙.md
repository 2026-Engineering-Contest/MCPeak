# ADR-0011: 응답 본문은 JSON 객체와 배열만 구조로 해석한다

- 상태: 제안
- 날짜: 2026-08-13
- 담당: runner
- 작성자: @seodduu (runner 파트)
- 승인: 미승인
- 참조: `docs/superpowers/specs/2026-08-13-response-body-assertion-design.md` §5,
  `docs/superpowers/plans/2026-08-13-response-body-assertion-implementation.md` §4-7,
  [ADR-0010](0010-응답-스키마-부분집합-경계.md)

## 배경

`bodyMatchesSchema` 단언은 `callTool` 응답의 "본문"을 검사한다. 그런데 MCP의 `ToolResult`는
`{ content: unknown; isError: boolean; raw: unknown }`이고 `content`는 블록 배열이다. 스키마가
검사할 단일 값이 무엇인지는 계약에 없다. Runner가 정해야 한다.

`core`의 `ToolResult`는 5인 병렬 작업의 기준점이라 변경 금지다. 따라서 추출 규칙은 전적으로
Runner가 소유한다.

핵심 갈림길은 `JSON.parse`가 스칼라도 파싱한다는 점이다. text 블록의 내용이 `"21"`이면 숫자
21이 되고 `"null"`이면 `null`이 된다.

## 선택지

- A안: `JSON.parse` 성공이면 결과를 그대로 본문으로 쓴다. 실패하면 문자열로 쓴다.
- B안: `JSON.parse` 결과가 객체나 배열일 때만 구조로 쓰고, 그 외는 원본 문자열을 본문으로 쓴다.
- C안: 항상 원본 문자열을 본문으로 쓴다. 구조 검사는 사용자가 별도 키워드로 요청한다.
- D안: `content` 배열에서 text 블록만 골라 이어 붙인다. 비 text 블록은 무시한다.

## 결정

B안을 택한다. 추출 규칙은 여섯 줄이다.

1. `content`가 배열이 아니면 실패(`CONTENT_NOT_ARRAY`).
2. 원소가 정확히 1개가 아니면 실패(`CONTENT_BLOCK_COUNT`).
3. 그 원소가 text 블록이 아니면 실패(`CONTENT_BLOCK_NOT_TEXT`). plain object이고 `type`이
   `"text"`이며 `text`가 문자열일 때만 text 블록으로 인정한다.
4. `text` 문자열을 `JSON.parse`한다.
5. 파싱 결과가 객체나 배열이면 그 값이 본문이다(`form: "json"`).
6. 그 외는 모두 `text` 문자열 자체가 본문이다(`form: "text"`).

한 줄로 줄이면, JSON 객체나 배열이면 구조로 보고 그 외는 문자열로 본다.

비 text 블록은 무시하지 않는다(D안 기각). 추출 실패는 `skipped`가 아니라 `failed`로 다룬다.

## 이유

- **실패 진단이 사용자를 옳은 곳으로 보낸다.** A안에서는 서버 오류 메시지가 우연히 `null`이나
  `1`일 때 본문이 문자열이 아니게 된다. 진단은 `기대: string, 실제: null`이 되는데 원인은 추출
  규칙에 있고 메시지에는 드러나지 않는다. B안에서는 오류 메시지가 항상 문자열이라 이런 일이
  없다. 대가로 응답 전체가 맨 스칼라인 서버에서 `{"type":"number"}`가 실패하지만, 그때 진단은
  `기대: number, 실제: string ("5")`가 되어 무엇을 고칠지 즉시 보인다. 두 규칙 모두 어딘가에서
  어색하므로, 어색할 때 진단이 사용자를 옳은 곳으로 보내는 쪽을 택했다.
- **조용한 통과를 만들지 않는다.** D안의 무시는 서버 응답 구조가 바뀐 사실을 감춘다. 이 도구의
  존재 이유와 충돌한다. 모호하면 진단을 낸다.
- **C안은 구조 검사를 포기하는 것이다.** `required`와 `properties`를 쓸 수 없으면 이번 작업의
  목표인 "`temp`를 `temperature`로 개명하면 실패한다"가 성립하지 않는다.
- **추출 실패가 `failed`인 이유.** Runner 설계 원칙 4번의 `skipped`는 선행 결과가 없어 검사할
  수 없는 경우를 뜻한다. 추출 실패는 응답이 도착했으나 모양이 계약과 다른 것이므로 결과는
  실패다.

## 결과

- `form` 필드가 계약에 남는다. 진단 문장이 `json`과 `text`를 구분해 쓸 수 있다.
- `{"__proto__":1}` 같은 입력은 `form: "json"`으로 통과한다. `JSON.parse`는 `__proto__`를 일반
  자기 키로 만들고 프로토타입은 `Object.prototype`이므로 `plainObject` 판정을 지난다. 의도한
  동작이며 `body.test.ts`가 고정한다. 평가기가 키 존재를 `Object.hasOwn`으로 보므로 프로토타입
  오염 경로가 생기지 않는다.
- text 블록이 여러 개인 서버는 이 단언을 쓸 수 없다. 필요해지면 블록 선택 키워드를 나중에
  추가한다. 지금 넓히지 않는 이유는 ADR-0010과 같다. 넓히는 방향은 기존 스위트를 깨지 않는다.
- `plainObject`와 `typeName`은 `schema-match.ts`가 export하고 `body.ts`가 가져다 쓴다. 두 파일이
  같은 4줄을 각자 두지 않는다. 참조 방향은 `body.ts` → `schema-match.ts` 한쪽으로 고정한다.
- 추출은 `bodyMatchesSchema` 단언이 있는 케이스에서만 케이스당 한 번 수행한다. 같은 케이스의
  여러 단언이 결과를 공유한다. 이 시점 규정은 T3의 executor 통합이 지킨다.
