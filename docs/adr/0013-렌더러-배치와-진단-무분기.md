# ADR-0013 렌더러 배치와 진단 무분기

상태: 초안
날짜: 2026-08-13
관련 설계: `docs/superpowers/specs/2026-08-13-cli-report-rendering-design.md` §3, §6

## 배경

응답 본문 단언 웨이브가 `RunnerDiagnostic` 에 `message`, `hint`, `violations[]` 를 채워 넣었다.
그 문장이 사용자에게 닿지 않는다. `ohmymcp test` 가 `RunnerReport` 를 JSON 으로 덤프하기
때문이다. 사람이 읽는 출력을 만들려면 보고서를 문자열로 그리는 코드가 필요하고, 그 코드를 어느
패키지에 둘지, 진단마다 다른 모양을 어떻게 처리할지, 서버 응답에서 온 제어 문자를 누가 막을지를
정해야 했다.

## 선택지

1. 렌더러를 `cli` 에 둔다. 출력은 CLI 의 일이라는 관점이다. 이스케이프 함수도 이미 `cli` 에
   있으므로 재사용이 쉽다.
2. 렌더러를 `runner` 에 두고, 진단 `code` 로 `switch` 를 돌려 코드마다 전용 레이아웃을 그린다.
3. 렌더러를 `runner` 에 두고, 진단 코드로 분기하지 않고 `message` / `violations[].message` /
   `hint` 를 정해진 자리에 배치만 한다. 이스케이프 함수는 `runner` 안에 다시 구현한다.

## 결정

선택지 3을 택한다.

- `packages/runner/src/reporter.ts` 에 순수 함수 `renderReport(report, options?)` 를 둔다.
- 렌더러는 `switch (diagnostic.code)` 를 쓰지 않는다. 유일한 조건은 `violations` 배열의 존재
  여부이며 그것은 옵셔널 필드 처리다.
- `escapeTerminalText` 를 `runner` 안에 다시 구현한다. `cli` 의 것을 가져오지 않는다.

## 이유

**배치.** `CONTRIBUTING.md` §2.1의 오너 표가 `runner` 의 책임을 "공개 API 설계, matcher, 실패
메시지 품질, 리포터, JUnit XML" 로 규정한다. `RunnerReport` 타입을 소유한 쪽이 렌더도 소유하면
타입이 바뀔 때 한 패키지 안에서 끝난다. 나중에 JUnit XML 리포터를 붙일 자리도 같은 디렉터리다.

**무분기.** 모든 `RunnerDiagnostic` 이 `{ code, message, hint }` 를 갖고, 위반 원소도 각자
완성된 `message` 를 갖는다. 그래서 렌더러가 할 일은 배치뿐이다. 분기를 넣으면 진단 코드가 늘 때마다
렌더러를 같이 고쳐야 하고, 문안 소유권이 `diagnostics.ts` 와 `reporter.ts` 로 쪼개진다. 렌더러
테스트가 문안을 다시 단언하면 문장 하나를 고칠 때 두 파일이 깨진다.

**이스케이프 중복.** `cli` 의 `escapeTerminalText` 를 import 하면 `runner` 가 `cli` 를 참조하게
되어 의존 방향(`cli` → `runner` → `core`)이 뒤집힌다. 여섯 줄 중복이 순환 위험보다 싸다.
`packages/core` 로 올리는 방법도 있었지만, 그러면 다섯 사람의 공유 계약 패키지에 이번 웨이브
사정으로 API 를 추가하게 된다. 지금 사용처가 둘뿐이므로 중복을 택했다. 셋째 사용처가 생기면
`core` 로 올리는 것을 다시 검토한다.

## 결과

- 진단이 늘어나도 렌더러를 고치지 않는다. `listTools` 의 `inputSchema` 단언이나 `expectFailure`
  가 추가돼도 배치 규칙은 그대로다.
- 문안 단언은 `body-diagnostics.test.ts` 한 곳에 남는다. `reporter.test.ts` 는 배치, 정렬,
  이스케이프, 결정론성만 본다.
- 이스케이프 규칙이 두 곳에 있다. `packages/cli/src/test-command.ts` 의 것과 값이 어긋나면 stdout
  과 stderr 의 방어 수준이 달라진다. 규칙을 고칠 일이 생기면 두 곳을 함께 고쳐야 한다.
- 색상 판정은 렌더러 밖에 남는다. `renderReport` 는 `process` 와 `isTTY` 를 읽지 않고 `color`
  불리언만 받는다. 덕분에 렌더러 테스트가 터미널을 위장하지 않아도 되고, 같은 보고서가 항상 같은
  바이트를 낸다.
