# ADR-0014 진단 출력 채널

상태: 초안
날짜: 2026-08-14
관련 설계: `docs/superpowers/specs/2026-08-13-cli-process-diagnostics-design.md` §4.1, §4.2, §11

## 배경

서버가 죽으면 사용자에게 가는 단서가 없었다. `core` 는 이미 stderr 를 모으고 있다.
`NodeControlledStdioTransport` 가 `BoundedStderr` 로 수집하고 `McpStdioConnection.getDiagnostics()`
가 종료 코드·시그널·stderr 를 돌려준다. CLI 는 `connectStdio()` 의 반환값을 손에 들고 있으면서도
그것을 읽지 않았다.

가장 분명한 모순은 연결 실패 경로였다. 기동 즉시 죽는 서버에 대해 CLI 가 내는 문장은 이것이다.

```
오류 [MCP_CONNECTION_FAILED/PROCESS_EXITED]: 요청 완료 전 MCP 서버가 종료되었습니다.
해결: exit code, signal, bounded stderr를 확인하세요.
```

힌트가 세 가지를 확인하라고 지시하는데 CLI 는 그 셋을 어디에도 보여주지 않았다. 사용자가 지시를
따를 방법이 없었다. 수집은 끝나 있고 표시할 곳만 정하면 되는 상태였다. 그 "어디에" 가 이 결정이다.

## 선택지

1. `RunnerReport` 에 진단 필드를 추가한다. 보고서가 실행의 전모를 담게 되고 `--json` 소비자도
   같은 것을 받는다.
2. stdout 에 보고서와 함께 출력한다. 스키마는 건드리지 않고 사람용 출력 뒤에 블록을 붙인다.
3. stderr 채널로 분리한다. stdout 은 보고서 전용으로 남긴다.

## 결정

선택지 3을 택한다. 진단 블록은 `dependencies.writeStderr` 로만 나간다. stdout 은 사람용 렌더 결과든
`--json` 의 JSON 이든 보고서만 담는다. 판정과 종료 코드는 블록의 유무와 무관하다
(`report.status === "passed" ? 0 : 1`, 실패 경로 1).

렌더러는 `packages/cli/src/process-diagnostics.ts` 의 순수 함수로 두고, 어디에 쓸지는 호출부인
`test-command.ts` 가 정한다.

## 이유

**선택지 1은 결정론성 계약을 깬다.** Runner 설계의 완료 조건은 "동일한 suite 와 결정론적 fake
client 를 두 번 실행한 `RunnerEvent[]` 와 `RunnerReport` 가 deep equality 를 만족한다" 이다.
서버 stderr 에는 타임스탬프·PID·절대 경로가 섞인다. 그것을 보고서에 넣는 순간 같은 입력의 두 실행이
달라지고, 이 프로젝트가 녹화·재생 기능을 만드는 이유 자체가 무너진다. 비결정적인 것은 보고서 밖에
둔다. 덧붙여 `RunnerReport` 스키마는 `runner` 오너의 소유라 CLI 작업으로 늘릴 것이 아니다.

**선택지 2는 `--json` 소비자를 깬다.** `--json > report.json` 을 하는 사람이 있고, 저장소 안에도
`packages/cli/tests/dist-cli-e2e.mjs` 가 stdout 을 `JSON.parse` 로 판정한다. 진단이 stdout 에
섞이면 그 파싱이 실패한다. ADR-0012 에서 `--json` 의 출력 바이트를 이전과 동일하게 유지하겠다고
약속한 것과도 어긋난다.

**사람 경험은 나빠지지 않는다.** 터미널에서는 stdout 과 stderr 가 함께 보인다. 분리는 사용자가
`2> server.log` 로 명시적으로 요구할 때만 일어나고, 그때는 분리되는 것이 맞다.

## 결과

- 지금까지 오류 한 줄로 끝나던 실패 경로(`RUNNER_EXECUTION_FAILED`, `RUNNER_FINALIZATION_FAILED`,
  프로세스 종료로 인한 `MCP_CONNECTION_FAILED`)에 종료 코드·시그널과 stderr 꼬리가 붙는다.
  위 배경의 모순이 해소됐다.
- `--json` 의 stdout 바이트는 변하지 않는다. `--stderr-lines 0` 은 블록을 완전히 끄는 탈출구이고,
  그때 stdout·stderr 바이트가 변경 전과 같다. CI 에서 바이트 비교가 필요한 경우를 위한 것이다.
- 진단은 `RunnerReport` 에 없으므로 보고서의 deep equality 계약이 그대로 유지된다.
- 잘림을 숨기지 않는다. 줄 수 제한으로 버린 줄과 `core` 의 수집 상한(`maxStderrBytes`)에 걸린
  잘림을 헤더에 적는다. 사용자가 무해한 꼬리 몇 줄만 보고 "서버 stderr 에 문제 없음" 으로 오판하는
  것을 막는다.

### 구현하며 하나 더 결정한 것: 정보가 없는 블록은 쓰지 않는다

처음에는 "케이스가 실패하면 블록을 붙인다" 로 두고, 빈 진단 생략은 연결 실패 경로에만 적용하려
했다. 실제로 구현해 보니 그 규칙이 기존 테스트 5건과 충돌했다. 원인은 붙는 블록의 내용이었다.

```
서버 프로세스 진단
  종료 코드: 0  시그널: 없음
  stderr: (비어 있음)
```

단언이 틀려서 케이스가 실패했지만 서버 자체는 멀쩡히 정상 종료한 실행, 즉 이 도구의 가장 흔한 실패
모양에서 매번 이 블록이 붙는다. 정보량이 0이고, 실패 원인은 단언 진단이 이미 문장으로 설명하고
있다. 기존 테스트들이 그 경로에서 stderr 가 비어 있다고 단언하고 있었던 것은 낡은 기대가 아니라
"서버에 문제가 없으면 서버 이야기를 하지 않는다" 는 옳은 기대였다. 그래서 `stderr` 가 빈 문자열이고
`isAbnormalExit` 이 거짓이면 블록을 쓰지 않는 규칙을 모든 경로의 공통 조건으로 올렸다.

이 판정은 렌더러가 아니라 호출부에 둔다. `renderProcessDiagnostics` 는 요청받은 것을 그대로 그리고,
무엇을 그릴 값어치가 있는지는 CLI 가 판단한다. 렌더러를 순수 함수로 유지하는 ADR-0013 의 배치와
같은 이유다.
