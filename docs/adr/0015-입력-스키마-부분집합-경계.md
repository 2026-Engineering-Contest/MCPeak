# ADR-0015: 서버 입력 스키마는 해석 가능한 부분집합만 검사하고 나머지는 침묵한다

- 상태: 제안
- 날짜: 2026-08-14
- 담당: runner
- 작성자: @seodduu (runner 파트)
- 승인: 미승인
- 참조: `docs/superpowers/specs/2026-08-14-input-contract-check-design.md` §4, §6, §11, §12,
  `docs/adr/0010-응답-스키마-부분집합-경계.md`

## 배경

입력 계약 대조는 테스트 명세의 입력이 서버가 선언한 `ToolDef.inputSchema`를 지키는지 본다.
이때 읽는 스키마는 우리 것이 아니다. 타입이 `unknown`이고, 남의 서버가 자기 마음대로 쓴
임의의 JSON Schema다. `anyOf`, `$ref`, `patternProperties`, `if`/`then`, `dependentRequired`
같은 것이 얼마든지 올 수 있고 우리는 그것을 통제할 수단이 없다.

여기서 오탐이 나는 경로가 설계 문서 §4.1에 있다. 서버가 이렇게 선언했다고 하자.

```json
{
  "type": "object",
  "properties": { "city": { "type": "string" } },
  "anyOf": [
    { "required": ["city"] },
    { "required": ["lat", "lon"] }
  ]
}
```

`anyOf`를 무시하고 `properties`만 보면 `{ "lat": 37.5, "lon": 127 }` 입력이
`UNDECLARED_FIELD` 2건으로 잡힌다. 명세는 맞는데 승인이 차단된다.

## 선택지

- A안: 미지원 키워드를 무시하고 아는 것만 검사한다. 구현이 가장 쉽다.
- B안: 완전한 JSON Schema 검증기를 도입한다. 조합자와 `$ref`까지 정확히 다룬다.
- C안: 해석 가능한 부분집합만 검사하고, 해석하지 못한 부분은 침묵한다.

## 결정

C안을 택한다. 정규화 단계(`normalizeInputSchema`)를 두고, 스키마를 우리가 이해하는 구조로
줄이되 줄이는 과정에서 정보를 잃으면 그 부분의 검사를 포기한다.

- 루트에 조합자·참조 계열 키워드가 하나라도 있거나 루트가 객체 스키마가 아니면 그 툴은
  해석 불가다. `SCHEMA_NOT_ANALYZABLE` 한 건만 내고 그 툴을 쓰는 모든 케이스의 입력 검사를
  건너뛴다.
- 개별 필드에 그런 키워드가 있으면 그 필드만 타입·enum 검사를 건너뛰고, 나머지 필드와
  `required` 검사는 계속한다.
- `additionalProperties`가 정확히 `false`일 때만 `UNDECLARED_FIELD`를 낸다. JSON Schema의
  기본값이 "허용"이므로 값이 없거나 `true`이거나 스키마 객체이면 검사하지 않는다.

## 이유

- 이 결과는 `generate` 승인 화면에서 차단 근거로 쓰인다. 그래서 오탐 1건이 미탐 1건보다
  비싸다. 미탐은 우리가 잡아주지 못한 것에 그치지만, 오탐은 사용자가 맞는 명세를 의심하게
  만들고 도구 자체의 신뢰를 깎는다. 한 번 헛경고를 본 사용자는 다음 경고도 무시한다.
- A안은 구현이 가장 쉽지만 위 `anyOf` 예시가 그대로 오탐이 된다. 우리가 못 읽은 키워드가
  바로 "이 필드는 없어도 된다"를 말하고 있는 키워드일 수 있고, 그것을 무시하면 스키마의
  뜻이 뒤집힌다.
- B안은 새 런타임 의존성이 필요한데 프로젝트 지침상 목록 밖 의존성의 임의 추가는 금지다.
  그것을 떠나서도, 우리가 통제하지 못하는 코드가 사용자의 승인을 차단하는 권한을 갖게 된다.
  실패 메시지가 곧 제품인 프로젝트에서 그 문안과 판정 기준을 외부 라이브러리에 넘기는 것은
  제품의 핵심을 넘기는 것과 같다.
- ADR-0010과 뿌리는 같지만 대상이 다르다. 응답 스키마는 우리가 정의하고 사용자가 쓰는
  것이라 지원 범위를 우리가 정하면 끝이고, 목록 밖 키워드를 거부하는 것이 정직한 동작이었다.
  입력 스키마는 남의 서버가 쓰고 우리가 읽기만 하는 것이라 거부할 상대가 없다. 그래서
  "무엇을 지원할지"가 아니라 "못 읽었을 때 어떻게 행동할지"를 정해야 했고, 별도 ADR로 남긴다.

## 결과

- 미탐이 생긴다. 조합자를 쓰는 서버의 툴은 입력 검사를 통째로 받지 못한다. 이것은 감수한
  비용이고, 나중에 정규화가 다룰 수 있는 키워드를 넓히는 방향은 열려 있다. 넓히는 방향은
  기존 결과를 깨지 않는다.
- `SCHEMA_NOT_ANALYZABLE`을 조용히 삼키지 않고 finding으로 내보낸다. 삼키면 finding 0건이
  "검사했는데 깨끗함"과 "검사를 못 했음" 두 가지를 동시에 뜻하게 되고, 소비자는 둘을 구분할
  방법이 없다. 후자를 전자로 착각하는 것이 이 기능이 만들 수 있는 가장 나쁜 거짓 신호다.
  설계 문서 §12의 거짓 신호 표에 이 항목이 들어 있는 이유가 그것이다.
- `SCHEMA_NOT_ANALYZABLE`의 severity는 `advisory`다. 서버의 위반이 아니라 우리 한계의
  고백이므로 사용자에게 잘못을 돌리는 강조를 붙이지 않는다.
- 정규화가 정보를 잃는 지점(루트 포기, 필드 포기, `type` 배열)은 테스트로 고정해야 한다.
  여기서 조용히 부분 성공을 허용하면 오탐 0이라는 이 ADR의 전제가 무너진다.
