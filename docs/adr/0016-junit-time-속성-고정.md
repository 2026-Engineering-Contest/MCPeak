# ADR-0016: JUnit XML 의 `time` 속성을 `0` 으로 고정한다

- 상태: 제안
- 날짜: 2026-08-14
- 작성자: @endl24 (runner 파트)
- 관련 설계: [CLI 보고서 렌더링 설계](../superpowers/specs/2026-08-13-cli-report-rendering-design.md) §9.3
- 관련 결정: [ADR-0002](./0002-matcher-strategy.md) — 결과 소비를 우리 리포터가 맡기로 한 전제

## 배경

CI 도구가 테스트 결과를 화면에 렌더하려면 JUnit XML 이 필요하다. `CONTRIBUTING.md` §2.1 이 이를
`runner` 책임으로 규정했고, CLI 보고서 렌더링 설계 §9.3 이 `junit.ts` 와
`renderJUnit(report): string` 자리를 비범위로 열어 두었다. 이 ADR 은 그 자리를 채우면서 만난
결정을 기록한다.

JUnit XML 스키마는 `<testsuite>` 와 `<testcase>` 에 `time` 속성을 기대한다. 값은 초 단위 실행
시간이며, CI 도구가 "가장 느린 테스트" 같은 화면을 그리는 근거다.

그런데 **`RunnerReport` 에는 시간 정보가 없다.** 실수가 아니라 확정된 설계다. Runner 설계의 확정
사항이 보고서를 "결정론적인 이벤트 순서와 시간 필드를 제외한" 것으로 정의한다. 같은 입력에 항상
같은 결과를 낸다는 것이 이 프로젝트의 핵심 가치이고(`CLAUDE.md`), 녹화·재생 기능의 존재 이유도
그것이기 때문이다. `OperationResult.timeoutMs` 가 있지만 이는 **설정된 제한값**이지 경과 시간이
아니다.

즉 포맷이 요구하는 값을 우리 데이터가 갖고 있지 않다. 무엇을 내보낼지 정해야 했다.

## 선택지

### A. `time="0"` 으로 고정한다

모든 `time` 속성에 `0` 을 쓴다.

- 장점
  - `RunnerReport` 를 건드리지 않는다. 파급이 없다.
  - 속성이 존재하므로 `time` 을 필수로 기대하는 파서에서도 문서가 유효하다.
  - `renderJUnit` 이 순수 함수로 남는다.
- 단점
  - CI 화면에 모든 테스트가 "0초"로 표시된다. 사실이 아닌 값을 내보낸다.
  - 소요 시간 기반 기능(느린 테스트 정렬 등)이 무의미해진다.

### B. `time` 속성을 쓰지 않는다

- 장점
  - 없는 정보를 지어내지 않는다. 부재가 곧 "모른다" 의 표현이다.
- 단점
  - **파서 호환성을 확인하지 못했다.** 도구에 따라 `0` 으로 간주할 수도, 경고할 수도, 문서를
    거부할 수도 있다. 확인하지 않은 것을 근거로 삼을 수 없다.

### C. `RunnerReport` 에 경과 시간을 추가한다

- 장점
  - 정확한 시간을 낼 수 있다. 터미널 렌더러도 함께 활용할 수 있다.
- 단점
  - **파급이 가장 크다.** `RunnerReport` 는 `--json` 출력의 계약이다. 시간을 넣으면 같은 서버를
    두 번 테스트한 `--json` 바이트가 달라진다.
  - `renderReport` 의 결정론성 테스트(같은 보고서를 두 번 렌더하면 동일)가 깨진다.
  - 녹화·재생이 전제하는 재현성이 흔들린다.
  - 결정론성을 지키려고 뺀 필드를, JUnit 하나 때문에 되돌리는 것이 된다.

### D. `cli` 가 측정해 렌더 옵션으로 넘긴다

`renderJUnit(report, { elapsedMs })` 형태로 시간을 주입한다.

- 장점
  - 렌더러는 순수하게 남는다. 같은 인자에 같은 바이트를 낸다.
  - `RunnerReport` 를 건드리지 않는다.
  - CLI 보고서 렌더링 설계 §3.2 가 세운 원칙("렌더러는 `Date` 를 읽지 않는다. 환경 판정은 전부
    `cli` 가 한다")과 같은 구조다.
- 단점
  - 지금 `cli` 는 경과 시간을 재지 않는다. 재게 하려면 `packages/cli/src/test-command.ts` 를
    고쳐야 하고, 그러면 이 변경이 `runner` 와 `cli` 두 패키지에 걸친다.
  - 해당 파일은 CLI 보고서 렌더링 웨이브가 방금 크게 바꾼 곳이다. 같은 PR 에 섞으면 리뷰
    단위가 커진다.

## 결정

**A안을 채택한다. 그리고 D안을 확장 경로로 예약한다.**

1. `renderJUnit` 이 내는 모든 `time` 속성값은 `0` 이다. `<testsuites>` · `<testsuite>` ·
   `<testcase>` 에 동일하게 적용한다.
2. `0` 의 의미를 코드와 문서에 명시한다. **"0초 걸렸다" 가 아니라 "시간 정보를 갖고 있지 않다"** 다.
3. `RunnerReport` 를 변경하지 않는다. `renderJUnit` 은 시간을 측정하지도, 생성하지도 않는다.
4. 실제 경과 시간이 필요해지면 `JUnitRenderOptions` 에 선택 필드를 더해 주입받는다. 그 시점에
   `RunnerReport` 를 고치는 선택지는 다시 검토하지 않는다 — C안은 이 ADR 에서 배제됐다.

## 이유

**C안이 가장 자연스러워 보이지만 파급이 가장 크다.** `RunnerReport` 는 JUnit 만의 것이 아니라
`--json` 출력, 터미널 렌더러, 앞으로의 녹화·재생이 함께 서 있는 공유 계약이다. 리포터 하나의
포맷 요구 때문에 그 계약을 비결정론적으로 만드는 것은 꼬리가 몸통을 흔드는 일이다. 결정론성은
이 프로젝트가 기존 도구와의 차별점으로 README 에 적어 둔 항목이며, 포기 대상이 아니다.

**B안은 근거가 없어서 못 고른다.** "없는 정보를 지어내지 않는다" 는 원칙적으로 옳지만, 그 대가로
어떤 CI 도구가 어떻게 반응하는지 확인하지 않았다. 검증하지 않은 가정 위에 공개 출력 포맷을 세울
수 없다. 속성이 있는 쪽이 없는 쪽보다 거부당할 확률이 낮다는 것이 현재 판단이며, 이것도 가정이므로
아래 결과에 검증 항목으로 남긴다.

**D안이 옳은 방향이지만 지금이 아니다.** 이 웨이브의 범위는 `runner` 한 패키지다. `cli` 를 함께
건드리면 `CONTRIBUTING.md` §5-4 의 크기 기준과 리뷰 단위가 모두 나빠지고, 방금 크게 바뀐
`test-command.ts` 와 충돌 위험도 생긴다. A 로 시작해도 D 로 가는 비용이 싸다는 점이 결정적이었다.
`JUnitRenderOptions` 에 선택 필드를 더하는 것은 기존 호출부를 하나도 깨뜨리지 않는 minor 변경이다.
반대로 C 로 시작하면 되돌리는 데 공유 타입 변경과 전 패키지 조정이 필요하다. **되돌리기 싼 쪽으로
시작한다.**

**무엇을 포기했는지 분명히 한다.** A 의 대가는 CI 화면에서 소요 시간을 볼 수 없다는 것이다. 느린
테스트를 찾는 용도로 이 리포트를 쓸 수 없다. 이 비용을 알면서 치르며, 그 대신 `RunnerReport` 의
결정론성과 `runner` 패키지 경계를 지킨다.

## 결과

- `renderJUnit` 은 `RunnerReport` 와 명시적으로 넘긴 `JUnitRenderOptions` 만 읽는 순수 함수로
  유지된다. `process` · `Date` · 로케일 · 난수를 읽지 않으므로 같은 인자에는 항상 같은 바이트를
  낸다. 시간을 스스로 측정하거나 생성하지 않는다는 뜻이며, 옵션을 받지 않는다는 뜻이 아니다.
- CI 도구에서 소요 시간 기반 기능을 쓸 수 없다. 느린 테스트 탐지가 필요한 사용자는 당분간
  터미널 출력이나 별도 수단을 써야 한다. **(2026-08-16 정정 — 실측 결과 "시간이 안 보인다" 가
  아니라 "`0ms` 로 보인다" 였다. 아래 실측 항목 참조.)**
- 확장 경로는 `JUnitRenderOptions` 다. `cli` 가 경과 시간을 재게 되면 선택 필드를 더한다.
  `RunnerReport` 변경은 이 ADR 이 폐기되기 전까지 선택지가 아니다.
- **[해소됨 · 2026-08-16] A 와 B 중 어느 쪽이 실제 CI 파서와 잘 맞는지가 결정 시점에는 검증되지
  않았다.** 도그푸딩에서 확인할 항목으로 남겼고, GitHub Actions 에 리포트를 실제로 물려 보아
  `time="0"` 을 이상하게 다루는 도구가 발견되면 이 결정을 재검토하기로 했다. **아래 실측으로
  이 항목은 닫혔다 — A 를 유지한다.**

  **실측 완료 (2026-08-16). A 를 유지한다.** `build` 잡이 `--junit` 으로 리포트를 내보내고
  `dorny/test-reporter` 의 `java-junit` 파서에 물리도록 CI 를 구성했다(PR #124). 첫 실행
  결과는 다음과 같다.

  - **파서가 거부하지 않았다.** 경고도 없었다. 케이스 3건이 그대로 렌더됐고 한글 이름도
    깨지지 않았다.
  - **`time="0"` 은 `0ms` 로 표시된다.** 집계 줄도 `3 tests were completed in 0ms` 다.

  간접 근거도 같은 방향이었다. 파서가 실제로 깨지는 경로는 `time="0"` 이 아니라 **`time` 이
  아예 없는 경우**다 — pantsbuild 가 그 입력에서 `could not convert string to float` 로
  실패한 사례가 이에 해당한다. 또 pytest-xdist 는 병렬 실행에서 `time` 을 0 으로 내보내므로
  주요 파서는 0 인 리포트를 이미 일상적으로 받고 있다. **B(속성 생략)가 A 보다 위험하다.**

  **다만 대가는 예상과 다른 모양이었다.** 위 「결과」에 "CI 도구에서 소요 시간 기반 기능을
  쓸 수 없다" 고 적었는데, 실제로는 시간이 *안 보이는* 게 아니라 **`0ms` 라고 보인다.**
  이 ADR 이 `0` 에 부여한 의미는 "시간 정보를 갖고 있지 않다" 인데, 화면에 오는 문장은
  "0ms 만에 끝났다" 로 읽힌다. **파서는 이 구분을 표현할 방법이 없다.**

  이것이 결정을 뒤집을 사유는 아니다. B(속성 생략)로 가면 파서가 깨지는 쪽이고, 그건 오해보다
  나쁘다. 그러나 **사용자가 리포트를 오독할 수 있다는 것은 이제 가정이 아니라 관측된 사실**
  이므로, 실제 시간이 필요하다는 요구가 오면 「결과」의 확장 경로(`JUnitRenderOptions` 에
  선택 필드 추가)를 앞당길 근거로 삼는다.
- `packages/core/src/types.ts` 의 동결 타입과 의존 방향(`cli → runner → core`)에 영향이 없다.
  `--json` 출력 바이트도 이 변경 전후로 동일하다.

### 승인 상태

- 상태: **미승인.** 이 ADR 을 담은 PR 에서 검토 중이다.
- 확정 방법: [ADR-0002](./0002-matcher-strategy.md) 가 세운 절차를 따른다. 머지만으로 승인
  처리하지 않으며, 파트 ① 밖 오너 최소 1명의 명시적 승인(§5-2)을 확인한 뒤 상태를 `승인` 으로
  바꾸고 승인일과 승인한 오너를 적는다.
