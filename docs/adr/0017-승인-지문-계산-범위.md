# ADR-0017: 승인 지문은 파싱된 명세 객체에서 approval 블록을 통째로 뺀 값으로 계산한다

- 상태: 제안
- 날짜: 2026-08-14
- 담당: cli
- 작성자: @seodduu (cli 파트)
- 승인: 미승인
- 참조: `docs/superpowers/specs/2026-08-14-approval-fingerprint-design.md` §3, §4, §11,
  `docs/adr/0009-generate가-runner에-의존하는-예외.md`

## 배경

`generate`는 사람이 승인한 명세를 파일로 저장하고, `test`는 그 파일을 읽어 실행한다. 두 시점
사이에 파일이 바뀌어도 지금은 아무도 모른다. 테스트가 실패했을 때 서버가 바뀐 것인지 명세가
바뀐 것인지 구분할 근거가 없고, 통과했을 때도 그 초록불의 근거가 승인 시점의 것과 같은지 알 수
없다.

이것을 지문 하나로 답하기로 했다. 그런데 지문을 만드는 순간 서로 얽힌 판단 셋이 한꺼번에
나온다. 무엇을 해싱할지, 그 값을 어디에 둘지, 그리고 지문을 파일 안에 두면 다음 계산의 대상
안에 지문 자신이 들어가는 자기참조를 어떻게 피할지다. 셋이 서로를 제약하므로 한 문서로 묶는다.

## 선택지

**무엇을 해싱하나**

- A안: 파일 바이트를 그대로 해싱한다. 구현이 가장 짧다.
- B안: 파싱된 명세 객체를 canonical JSON으로 직렬화해 해싱한다.
- C안: 명세 객체와 서버가 선언한 툴 목록을 함께 해싱한다. "서버 선언도 그때와 같음"까지
  보증한다.

**지문을 어디에 두나**

- D안: 명세 파일 안에 넣는다. 자기참조를 처리해야 한다.
- E안: 사이드카 파일(`suite.json.approval` 같은 것)에 따로 둔다. 자기참조가 없다.

**자기참조를 어떻게 피하나**

- F안: 계산에서 `approval.fingerprint` 필드 하나만 제외한다.
- G안: `approval` 블록 전체를 제외한다.

## 결정

**B안 + D안 + G안**을 택한다.

```
지문 = sha256(canonicalJson(suite에서 approval 키를 제거한 객체))
```

값은 소문자 hex 64자이고 알고리즘 접두사를 붙이지 않는다. 파일의 `schemaVersion`이 알고리즘을
고정하고 있어 접두사는 같은 정보를 두 곳에 두는 것이다.

## 이유

- **A안을 버린 이유.** 들여쓰기 변경, 줄 끝 문자 변경(CRLF↔LF), 에디터 자동 포맷, 키 순서
  정렬이 전부 "명세가 바뀌었다"로 잡힌다. 그러면 경고가 일상이 되고 사용자는 그 줄을 읽지
  않게 된다. 지문이 답해야 하는 질문은 "테스트의 의미가 바뀌었나"이지 "바이트가 바뀌었나"가
  아니다. `canonicalJson`은 키를 정렬하고 배열 순서는 보존하므로 이 요구를 이미 만족한다.
  배열 순서를 보존하는 것도 옳다. 케이스 순서가 바뀌면 상태를 바꾸는 서버에서 결과가 달라지고
  그것은 의미 변경이다.
- **C안을 버린 이유.** 서버 선언을 얻으려면 서버를 켜야 한다. 지문 확인이 서버 기동에 묶이면
  파일만으로는 아무것도 판정하지 못한다. 그리고 사용자는 자기 MCP 서버를 개발하는 중이라
  선언이 바뀌는 것은 정상적인 개발이다. 매번 불일치가 뜨면 신호가 죽는다. 선언 변경이 명세와
  어긋나는지는 입력 계약 대조가 이미, 그것도 어느 필드가 어떻게 어긋나는지까지 답한다.
- **E안을 버린 이유.** 사이드카는 복사·이동·머지에서 본체와 어긋나고, 어긋난 것을 아무도
  모른다. 지문이 답해야 할 질문에 지문 자신이 신뢰할 수 없는 답을 내놓게 된다. 명세 하나가
  파일 하나라는 성질도 잃는다.
- **F안을 버린 이유.** 이 블록에 나중에 붙을 후보가 이미 보인다. 승인 시점에 서버가 선언한 툴
  목록의 지문, 케이스별 승인 상태 같은 것이다. 필드 단위로 제외하면 제외 규칙이 항목 수만큼
  늘어나고, 규칙을 늘리는 것을 한 번이라도 잊으면 승인 검증이 조용히 깨진다. 블록 하나로
  묶으면 "`approval` 전체를 제외한다" 한 줄로 영원히 끝난다. 지금 필드가 하나뿐인 대가로 그
  규칙을 고정한다.

## 결과

- `approval`이 없는 명세와 있는 명세는 나머지가 같으면 같은 지문을 낸다. 승인 이전에 계산한
  값과 저장 이후에 계산한 값이 같아야 하므로 이것이 성립해야만 기능이 성립한다.
- 지문이 없는 명세도 정상이다. 손으로 쓴 명세와 이 기능 이전에 만든 명세가 그렇고, 실패로
  취급하지 않는다.
- 제외 규칙의 소유자는 `suiteFingerprint` 함수 하나다. 이 함수 밖에서 지문을 계산하면 두 벌이
  갈라지는 순간 승인 검증이 조용히 깨진다. `cli`의 지역 구현을 지우고 `@ohmymcp/runner`에서
  가져오도록 바꾼 이유가 이것이다.
- `canonicalJson`과 `sha256`이 `generate`에서 `runner`로 옮겨간다. `test` 실행 경로는 `cli`와
  `runner`만 쓰는데 의존 방향이 `generate → runner`라 `runner`가 `generate`를 부를 수 없기
  때문이다. ADR-0009의 승인 심볼 목록이 함께 늘어난다.
- 저장 직후 왕복 재검증은 두 가지를 본다. 다시 읽은 명세로 계산한 지문, 그리고 파일에 적힌
  지문이다. 첫째만 보면 `approval`을 제외해 계산하므로 파일에 적힌 값이 틀려도 통과한다.
- 파일 바이트가 바뀌어도 의미가 같으면 지문이 같다. 즉 이 지문은 파일 무결성 검사가 아니다.
  변조 탐지가 필요해지면 그것은 별도의 수단이어야 한다.
