# ADR-0018: 입력 계약 대조는 값 치환 이전에 돌리고, 위반은 거부가 아니라 재확인으로 다룬다

## 배경

`runner` 가 `checkInputContract` · `checkAssertionSubstance` · `describeSpecFinding` 을 export
하지만 아무도 부르지 않았다. 구현과 테스트가 있는데 소비자가 없어 사용자에게는 아무 변화가
없었다. 이 문서는 두 소비자(`generate` 승인 화면, `cli test` 출력)에 배선하면서 갈린 판단을
남긴다.

배선은 함수 호출 한 줄로 끝나지 않았다. 검사에 넣을 명세와 툴 목록이 경로마다 이미 가공돼
있었고, 검사 결과를 어디에 실을지가 승인 지문 계약과 얽혀 있었고, 위반을 발견했을 때 진행을
막을지가 검사의 정확도와 얽혀 있었다. 넷이 서로를 제약하므로 한 문서로 묶는다.

## 선택지

**검사를 어디서 돌리나**

- A안: `generate` 안에서, `redactAuthoringSuite` 호출 이전 객체로 돌린다.
- B안: `cli` 가 candidate 를 받은 뒤 `runner` 를 직접 부른다. `generate` 는 무수정이다.
- C안: `applyAuthoringChanges` 시점에 돌린다. 차단 지위가 자연스럽다.

**위반을 어떻게 다루나**

- D안: 거부한다. 위반이 있는 후보는 저장하지 않는다.
- E안: 표시하고 확인을 한 번 더 받는다. 진행은 열어 둔다.

**검사 결과를 candidate 의 어디에 두나**

- F안: `result` 안에 `specFindings` 로 넣는다. 후보 객체가 한 덩어리로 유지된다.
- G안: `result` 밖, candidate 의 형제 필드로 둔다.

**문장을 누가 만드나**

- H안: `runner` 의 `describeSpecFinding` 만 만든다. 소비자는 배치만 한다.
- I안: 화면마다 문장을 짓는다. 화면 맥락에 맞는 표현을 쓸 수 있다.

## 결정

**A안 + E안 + G안 + H안**을 택한다.

`generate` 는 값 치환 이전 객체로 검사하고, provider 경로는 치환 이전 툴 목록
(`unredactedTools`)을 요청 상태에 따로 보관해 대조에만 쓴다. 결과는 `result` 밖의
`specFindings` 필드로 실린다. `cli` 의 두 화면은 `describeSpecFinding` 결과에 머리글과
들여쓰기만 붙이고, 위반이 있으면 확인을 한 번 더 받되 거부하지 않는다.

## 이유

- **B안을 버린 이유.** candidate 에 실린 suite 는 치환본이다. `redactAuthoringSuite` 가
  `operation.input` 의 민감 값을 `[REDACTED]` 문자열로 바꾸므로, 숫자 필드가 치환되면 값이
  문자열이 되어 서버가 선언한 `type: "number"` 와 어긋난다. `TYPE_MISMATCH` 거짓 양성이다.
  치환 이전 객체를 `cli` 로 넘기려면 어차피 `generate` API 를 고쳐야 하니 "무수정" 이라는
  유일한 이득이 사라진다.
  같은 함정이 툴 목록에도 있다. provider 로 보내는 `state.tools` 는 치환된 사본이고,
  `TOOL_CONTRACT_PATHS` 가 지키는 것은 `[i].name` 뿐이라 `inputSchema` 안의 `enum` 값은 바뀔
  수 있다. 그것으로 대조하면 정상 입력이 `ENUM_MISMATCH` 로 뒤집힌다. 그래서 원본을 따로
  보관하고 검사에만 쓴다. 원본은 provider 로 나가지 않고 payload 크기 계산에도 들어가지 않는다.
  이 프로젝트에서 실패 메시지는 곧 제품이고, 거짓 양성은 그 메시지를 안 읽게 만드는 가장 빠른
  길이다.
- **C안을 버린 이유.** 사용자가 diff 를 다 읽고 승인을 누른 뒤에야 경고를 본다. 판단에 쓸
  정보를 판단 이후에 주는 것이다.
- **D안을 버린 이유.** 이 검사는 100% 정확하지 않다. 서버가 `additionalProperties` 를 닫지
  않거나 `required` 를 비워 두면 옳은 명세도 `UNDECLARED_FIELD` 로 걸린다. 느슨한 선언은
  서버 쪽 사정이고 사용자가 고칠 수 있는 것이 아니다. 거부하면 옳은 명세를 저장할 길이 막힌다.
  그래서 진행은 열어 두고 손이 한 번 더 가게 한다. ADR-0015 의 "모르면 침묵한다" 와 같은 선이다.
- **F안을 버린 이유.** 후보 지문은 `result` 로 계산된다(`sha256(result)` 와
  `sha256(frozenSuite)`). 안에 넣으면 이미 승인된 지문이 전부 어긋나고, 서버 선언이 바뀔 때마다
  같은 명세의 지문이 달라진다. 진단은 명세의 내용이 아니라 명세에 대한 관찰이므로 해싱 대상이
  아니다. ADR-0016 이 `approval` 블록을 계산에서 뺀 것과 같은 이유다.
- **I안을 버린 이유.** 문장을 소비자가 지으면 같은 명세에 대해 두 화면이 다른 말을 한다.
  둘 중 하나가 틀렸을 때 어느 쪽이 틀렸는지도 알기 어렵다.
  다만 경계가 있다. **문장은 `runner` 소유이고 머리글은 화면 소유다.** 승인 화면은 여러 change
  를 한 번에 훑는 집계 화면이라 `입력 계약 위반 N건 (선택한 변경 기준)` 처럼 개수를 먼저 낸다.
  `cli test` 는 실패한 케이스를 하나씩 보는 진단 화면이라
  `참고: <caseId> 의 입력이 서버 선언과 다릅니다` 처럼 케이스별 블록을 낸다. 같은 정보라도
  읽는 자리가 다르면 형태가 다른 편이 낫다. 갈리지 않아야 하는 것은 finding 한 건을 설명하는
  문장이다.

## 결과

- ADR-0009 의 `generate → runner` 허용 심볼 목록이 셋 늘었다.
  `checkInputContract` · `checkAssertionSubstance` · `SpecFindingsResult` 다. 목록을 고정하는
  테스트가 함께 갱신됐다.
- 지문 불변을 `generate` 의 두 경로(로컬 후보, provider 후보) 양쪽에서 테스트로 고정했다.
  `specFindings` 를 `result` 안으로 옮기는 변경은 그 테스트가 먼저 깨져 알린다.
- 두 화면은 finding 코드를 `Record<SpecFindingCode, FindingGroup>` 표로 그룹에 대응시킨다.
  `runner` 가 `SpecFindingCode` 를 늘리면 두 표에서 타입 오류가 나므로 누락은 막힌다.
  **엉뚱한 그룹에 넣는 실수는 막지 못한다.** 새 코드를 더할 때 그 코드가 위반인지 건너뜀인지,
  고칠 곳이 입력인지 단언인지를 사람이 판단해야 하고, 그 판단이 틀리면 읽는 사람이 엉뚱한 곳을
  고치러 간다. 코드를 늘리는 PR 은 두 화면의 표와 각 그룹의 머리글 문안을 함께 리뷰해야 한다.
- `SCHEMA_NOT_ANALYZABLE` 은 위반이 아니라 건너뜀이다. 두 화면 모두 위반 개수에서 빼고 따로
  알린다. 재확인 프롬프트의 근거에도 들어가지 않는다.
- 판정과 exit code 는 이 배선으로 바뀌지 않는다. `cli test` 의 참고 문장은 실패한 케이스에만
  붙고, `listTools()` 가 던지거나 빈 배열이면 입력 계약 대조를 조용히 건너뛴다. 비차단 진단이
  실행을 깨뜨리면 안 된다.
- `--json` 의 `spec.findings` 는 문장을 담지 않고 한 배열로 둔다. 사람이 읽는 출력에서 머리글을
  몇 갈래로 나누든 기계가 읽는 출력은 `code` 로 분기하면 되므로 나눌 이유가 없다.
