# ADR-0021: 거절을 기대하는 케이스는 입력 계약 대조에서 제외한다

- 상태: 제안
- 날짜: 2026-08-15
- 담당: runner
- 작성자: @seodduu (runner 파트)
- 승인: 미승인
- 참조: `docs/superpowers/specs/2026-08-15-contract-axis-coverage-design.md` §6.3, §11.1,
  `docs/adr/0015-입력-스키마-부분집합-경계.md`,
  `docs/adr/0018-입력-계약-대조-소비자-배선.md`

## 배경

`checkInputContract` 는 명세의 `callTool` 입력을 서버가 선언한 `inputSchema` 와 대조해
`REQUIRED_MISSING` · `UNDECLARED_FIELD` · `TYPE_MISMATCH` · `ENUM_MISMATCH` 를 낸다. 그 결과가
`generate` 승인 화면의 차단 근거이고 `cli test` 출력에도 실린다(ADR-0018).

단계 5+6 이 위반 케이스를 기본으로 생성한다. 필수 필드를 뺀 입력, 타입을 어긴 입력, enum 밖 값을
넣은 입력을 만들고 `isError expected true` 로 단언한다. 그 입력들은 정의상 서버 선언을 어긴다.

그대로 두면 도구가 스스로 만든 케이스를 스스로 고발한다.

```
입력 계약 위반 6건 (선택한 변경 기준)
  → 3 add-missing-a
     필수 필드 'a' 가 입력에 없습니다
...
위반 6건이 남아 있습니다. 그래도 적용합니까?
```

사용자는 자기가 무엇을 잘못했는지 알 수 없다. 위반 케이스를 기본 생성으로 정한 순간 이 화면은
모든 실행에서 뜬다. 툴 30개짜리 서버면 경고가 100건을 넘는다.

## 선택지

- A안: 명세에 의도 필드를 넣는다(`intent: "contractViolation"`). 가장 명시적이다. 대신
  `TestCaseSpec` 확장이라 `runner` 스펙 변경과 `MCP_SUITE_JSON_SCHEMA` 변경, 파일 형식 변경이
  따라온다. 손으로 쓴 명세는 그 필드를 안 쓰므로 거기서는 여전히 오탐이 난다.
- B안: `isError expected true` 를 신호로 쓴다. 파일 형식이 안 바뀌고 손으로 쓴 명세에도 적용된다.
- C안: `cli` 승인 화면에서 걸러낸다. `runner` 를 안 고쳐도 되지만 `test` 경로에 같은 오탐이 남고
  필터가 두 소비자에 중복된다.
- D안: 위반 케이스를 옵션으로 돌려 기본 화면에서 안 보이게 한다. 단계 5+6 의 목표(미확인 상태로
  승인되는 케이스를 0으로)를 포기한다.

## 결정

B안을 택한다. `isError expected true` 단언이 있는 케이스에서는 아래 넷을 내지 않는다.

```
REQUIRED_MISSING · UNDECLARED_FIELD · TYPE_MISMATCH · ENUM_MISMATCH
```

계속 내는 것이 둘이다.

- `TOOL_NOT_DECLARED`. 서버가 모르는 툴 이름은 거절 기대와 무관하게 오타다.
- `SCHEMA_NOT_ANALYZABLE`. 위반이 아니라 "검사를 못 했다" 는 보고다. 삼키면 ADR-0015 가 막아 둔
  거짓 신호가 되살아난다.

한 케이스에 `expected` 가 서로 다른 `isError` 단언이 둘 있으면 침묵시키지 않는다. 그런 명세는
모순이고, 어느 쪽으로 읽어도 틀린다. 모순을 임의로 한쪽으로 해석하면 그 사실이 숨는다.

침묵은 정렬·절단·합산 이전에 적용하고 `totalFindings` 도 침묵 후 개수로 센다. 침묵시킨 것을
총합에만 남기면 소비자가 "위반 N건이 있는데 목록은 비어 있다" 를 보고 버그로 읽는다.

## 이유

- 신호가 이미 명세 안에 있고 의미가 정확하다. "거절을 기대한다" 는 곧 "이 입력은 선언을 어길
  것이다" 다. 새 필드를 만들어 같은 뜻을 두 번 적을 이유가 없다.
- 의미상으로도 이것이 맞다. 입력 계약 대조의 전제는 "명세의 입력은 서버 선언을 지켜야 한다"
  인데, 그 전제는 정상 응답을 기대하는 케이스에만 성립한다. 거절을 기대하는 케이스에서 선언을
  어긴 입력은 결함이 아니라 그 케이스의 목적이다.
- 두 소비자(`generate` 승인 화면, `cli test`)가 코드를 안 고쳐도 함께 고쳐진다. C안은 같은
  필터를 두 곳에 두고, 한쪽만 고치는 실수가 언제든 가능하다.
- A안의 비용은 파일 형식 변경이다. 이미 승인된 명세 파일과 지문 계약(ADR-0017)에 영향을 주고,
  그 대가로 얻는 것은 손으로 쓴 명세에서는 작동하지 않는 신호다.

## 결과

- 미탐이 하나 생긴다. 사용자가 `isError: true` 를 쓴 케이스에 진짜 오타를 넣어도 조용하다.
  ADR-0015 가 "오탐 1건이 미탐 1건보다 비싸다" 를 이미 결정했고, 여기서 오탐은 위반 케이스
  수만큼 매 실행마다 나오므로 비교가 되지 않는다.
- 커버리지 판정(`matchCoveredAxes`)은 이 침묵과 무관해야 한다. `checkInputContract` 의 출력을
  재료로 쓰면 커버리지가 판정해야 하는 바로 그 케이스들이 사라져 커버리지가 영원히 1/N 로
  굳는다. 그래서 두 함수는 `analyzeInputSchema` 와 `judgeField` 를 공유하되 출력만 다르게 낸다.
  `packages/runner/tests/contract-axes.test.ts` 의 "checkInputContract 가 침묵하는 케이스에서도
  축을 낸다" 가 이 성질을 고정한다.
- ADR-0018 개정이 아니라 신규다. 0018 은 결과를 어디에 싣고 누가 차단하는지의 배선 결정이고,
  이것은 검사 대상 자체의 경계 결정이다.
- 나중에 오류 본문 단언이 생기면(단계 4 repair 가 요구로 올릴 수 있다) "거절했다" 와 "서버가
  다른 이유로 실패했다" 를 구분할 수 있게 된다. 그때 이 신호를 더 좁힐 여지가 있다.
