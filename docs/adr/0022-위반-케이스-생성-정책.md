# ADR-0022: 위반 케이스는 기본으로, 필드마다, 상한 없이 만든다

- 상태: 제안
- 날짜: 2026-08-15
- 담당: generate
- 작성자: @seodduu (generate 파트)
- 승인: 미승인
- 참조: `docs/superpowers/specs/2026-08-15-contract-axis-coverage-design.md` §5, §9, §11.2,
  `docs/adr/0021-거절-기대-케이스의-입력-계약-대조-제외.md`,
  `docs/adr/0004-generation-scope.md`

## 배경

`generate` 는 서버가 선언한 `inputSchema` 에서 계약 축을 도출하고, 축마다 그것을 어긴 입력을
만들어 `isError expected true` 로 단언하는 케이스를 합성한다. 축은 넷이다. 선언을 지킨 입력에
정상 응답(`HAPPY_PATH`), 필수 필드 누락 거절(`REQUIRED_OMITTED`), 선언 type 위반 거절
(`TYPE_VIOLATION`), 선언 enum 밖 값 거절(`ENUM_VIOLATION`).

이 기능을 넣기 전까지 baseline 은 툴당 정상 케이스 하나만 만들었다. 그것은 "서버가 죽지 않는다"
까지만 확인하고, 서버가 잘못된 입력을 **거절하는지**는 아무것도 확인하지 않았다. 입력 검증이
빠진 서버는 초록불을 받는다.

여기서 다르게 갈 수 있었던 판단이 셋이다. 셋 다 "명세 파일이 얼마나 커지는가" 와 "빈틈을 얼마나
남기는가" 의 교환이라 한 ADR 에 묶는다.

## 선택지

- A안: 위반 케이스를 기본으로 생성한다. 필드마다 하나씩. 상한 없음.
- B안: `--with-violations` 같은 옵트인으로 둔다.
- C안: 필드마다가 아니라 축마다 대표 케이스 하나만 만든다(예: 필수 필드를 전부 뺀 `{}` 하나).
- D안: 툴당 위반 케이스 상한(예: 8)을 둔다.

## 결정

A안을 채택한다. 셋을 각각 적는다.

1. **기본 생성한다.** 옵션 없이 baseline 에 포함한다.
2. **필드마다 하나씩 만든다.** 필수 필드가 둘이면 누락 케이스도 둘이다.
3. **상한을 두지 않는다.** 대신 케이스 수가 1500을 넘으면 `cli` 가 고지한다.

## 이유

**B안(옵트인)을 배제한다.** 옵트인은 옵션을 아는 사용자만 혜택을 받는다. 로드맵의 목표가
"미확인 상태로 승인되는 케이스를 0으로" 인데, 기본값이 미확인이면 그 목표는 옵션 문서를 읽은
사람에게만 성립한다. 입력 검증이 빠진 서버를 쓰는 사용자가 정확히 그 옵션을 켜지 않을 사람이다.

대가는 둘이다. 명세 파일이 3배 이상 커진다. 그리고 서버가 잘못된 입력을 일부러 거절하지 않는
설계라면 사용자가 그 케이스를 지워야 한다. 승인 화면에서 케이스별로 빼는 흐름이 이미 있어
(AI 후보 승인과 같은 경로) 그 대가가 감당 가능하다.

**C안(축마다 대표 하나)을 배제한다.** 서버 코드가 필드별로 갈리기 때문이다.

```js
if (!args.a) throw new Error("a is required");
// b 검사를 빼먹었다
```

이것이 정확히 우리가 잡으려는 결함이다. 대표 필드 하나만 쓰면 `a` 쪽에 걸려 통과하고 `b` 의
누락은 영영 안 보인다. 필수 필드를 전부 뺀 `{}` 하나로 합치면 서버가 거절은 하지만 **어느 필드
검사가 빠졌는지 못 짚는다.** 실패 메시지가 제품이라는 원칙에서 나와야 하는 문장은
`'b' 를 뺀 입력을 거절하지 않았습니다` 이고, 그것은 필드마다 케이스가 있을 때만 나온다.

**D안(상한)을 배제한다.** 상한의 근거는 조합 폭발인데 축 수가 선형이라 애초에 폭발이 없다.

```
축 수 = 1 + |required| + |type 이 있는 필드| + |enum 이 있는 필드|
```

툴당 상한 8을 기본값으로 두면 필드 20개짜리 툴을 가진 사용자는 영구히 미검증 33개를 안고 산다.
그 상태가 화면에 정직하게 표시된다는 것은 위안이 못 된다. **사용자가 할 수 있는 조치가 없다.**
목표가 빈틈 없는 명세인데 도구가 스스로 빈틈을 만드는 것은 목적과 반대다.

실재하는 벽은 상류가 아니라 하류에 있다. `runner` 의 보고서 상한이 1MB 이고 **올릴 수 없다**
(`resolvePayloadLimits` 가 기본값을 최대치로 쓴다). 넘으면 테스트 실패가 아니라
`RunnerPayloadLimitError` 로 죽는다. 케이스당 보고서가 300~600 바이트이므로 벽은 2000 케이스
근처다. 그래서 생성을 막는 대신 1500에서 고지한다. 고지는 새 상한이 아니라 **이미 존재하는
상한을 보이게 하는 것**이다. 지금은 벽에 부딪히면 이유를 모르는 예외만 뜬다.

## 결과

- `BASELINE_POLICY_VERSION` 이 `"schema-baseline-v1"` 에서 `"schema-baseline-v2"` 로 올랐다.
  이 값이 `baselineFingerprint` 계산에 들어가므로 **기존에 승인된 지문이 전부 바뀐다.** 정책이
  바뀐 사실이 지문에 남는 것이 이 승격의 목적이다.
- `fixtures/tools-list.sample.json` 의 두 툴이 케이스 8개를 만든다. 이전에는 2개였다.
  `get_weather` 가 3개(정상·필수 누락·타입 위반), `add` 가 5개다.
- 위반값은 표로 고정한다. 같은 서버에서 항상 같은 지문이 나와야 한다.
  `string`→`0`, `number`→`"example"`, `integer`→`1.5`, 그 밖은 `"example"`.
  enum 위반값은 `"__ohmymcp_invalid_enum__"` 이고, 선언 type 이 수 계열이면 `max + 1` 이다.
- **필수 필드가 정상 입력에 없으면 그 케이스를 만들지 않는다.** 뺄 것이 없어 입력이 정상 케이스와
  같아지고, 단언만 반대인 케이스는 서버가 옳은데도 항상 실패한다. 그 축은 케이스 없이 남고
  커버리지가 미검증으로 보고한다. 그것이 정직한 상태다.
- 커버리지가 `generate` 실행 화면에 표시된다. 축을 다 덮으면 한 줄이고, 미검증이나 해석 불가가
  있으면 툴별로 펼친다.
- ADR-0021 이 이 결정의 전제다. 위반 케이스를 기본 생성하면 `checkInputContract` 가 우리 케이스를
  매 실행마다 위반으로 신고한다. 그 규칙 변경 없이는 이 ADR 을 실행할 수 없다.
- 상한을 두지 않기로 했으므로 단계 3(dry run 전량 실행)의 호출 수가 케이스 수만큼 늘어난다.
  위반 케이스는 서버가 입력 검증에서 거절하면 외부 API 까지 가지 않아 정상 케이스보다 싸지만,
  검증이 없는 서버에서는 그대로 나간다. 즉 **비용이 가장 큰 경우가 결함이 있는 경우**다. 이
  사실을 단계 3 설계에 전달한다.
- 재검토 조건: 실사용에서 명세 파일 크기나 dry run 비용이 문제로 올라오면 D안(상한)이 아니라
  "축 종류별 옵트아웃"(예: enum 축만 끄기)을 먼저 검토한다. 상한은 어느 축이 빠지는지 사용자가
  고를 수 없어 같은 크기를 줄이면서 정보를 더 잃는다.
