# ADR-0023: 시험 실행 전 서버 초기화를 옵션 훅으로 제공한다

## 배경

승인 전 시험 실행(dry run)은 후보 명세를 실제 서버에 한 번 돌려 각 케이스를 통과·서버 결함·명세
오류로 분류하는 단계다. 이 단계가 있어야 AI 가 선언만 보고 지어낸 기대값이 오라클 지위를 얻기
전에 검증된다. 착수에 앞서 정해야 할 것이 서버 상태 처리다.

서버 중에는 호출이 상태를 남기는 것이 있다. `add_todo` 를 부르면 항목이 늘고 그 결과가
`list_todos` 의 응답을 바꾼다. 시험 실행이 남긴 잔여물은 서버가 살아 있는 동안 그대로 남는다.

카세트(`cassetteClient`)가 이 문제의 상당 부분을 이미 닫는다. `auto` 모드는 키가 맞으면 녹화본을
재생하고 없을 때만 실제로 호출한다. 그래서 케이스를 고쳐 가며 반복 실행해도 서버를 때리는 것은
새 케이스뿐이다. 같은 키에 다른 응답이 오면 `onWarning` 이 상태 의존을 알린다.

**닫히지 않는 것은 재녹화 시점이다.** 서버 코드를 고쳐 옛 카세트를 버리고 처음부터 다시 녹화할
때, 서버 상태는 최초 녹화 때와 다르다. 이전 실행들이 남긴 항목이 쌓여 있고 지운 항목은 없다.
그 상태에서 녹화하면 두 종류의 거짓말이 나온다.

```
✗ list_todos/목록 조회
    → 항목 개수가 다릅니다. 기대: 4, 실제: 7      ← 잔여물이 쌓인 것
✗ delete_todo/삭제 성공
    → 정상 응답을 기대했지만 오류 응답을 받았습니다
      받은 오류: "id 't-1' 를 찾을 수 없습니다"    ← 지난 실행이 이미 지운 것
```

서버는 멀쩡한데 화면은 결함이라고 말한다. 사용자가 "서버 결함" 으로 분류하면 존재하지 않는
버그가 회귀 테스트로 굳는다. "명세 오류" 로 분류해 기대값을 7로 고치면 다음 재녹화에서 10이 된다.
실패 메시지가 제품이라는 원칙에서 가장 나쁜 종류의 실패다.

## 선택지

- A안: 훅을 만들지 않는다. 상태를 되돌리는 것은 사용자가 서버를 재시작해 알아서 한다.
- B안: 초기화 명령을 받는 옵션(`--reset-cmd`)을 제공한다. 안 주면 A안과 동일하게 동작한다.
- C안: 상태를 바꾸는 케이스를 명세에서 배제하거나 `mock` 서버 상대로만 시험 실행한다.

## 결정

B안을 채택한다. 세부 넷을 함께 고정한다.

1. **`--reset-cmd <command>` 를 `cli` 에 추가한다.** 주지 않으면 아무 동작도 하지 않는다.
2. **실행 시점은 서버를 접촉할 수 있는 패스의 맨 앞 1회다.** 케이스마다가 아니다.
   `record` 와 `auto` 에서 실행하고, `replay` 에서는 건너뛴다.
3. **초기화가 실패하면 시험 실행을 시작하지 않는다.** 종료 코드가 0이 아니면 중단하고 명령·종료
   코드·stderr 꼬리를 보여준다.
4. **명령은 CLI 인자와 설정 파일에서만 받는다.** 명세 파일에서는 받지 않는다. 실행은 셸을 거치지
   않는다.

## 이유

**C안을 배제한다.** 승인의 조건 중 하나가 "실제 서버에 한 번 이상 실행돼 결과가 사람에게 보였다"
이다. 상태를 바꾸는 케이스를 실행에서 빼면 그 케이스는 이 조건을 영영 못 채워 승인 불가가 된다.
즉 `delete_*` 류가 명세에 못 들어간다. 회귀 테스트가 가장 필요한 곳을 정의가 스스로 막는다.
`mock` 상대 실행은 상태는 통제되지만 실서버가 아니라서 "AI 추측이 실제와 일치" 라는 보증 자체가
약해진다. 시험 실행의 존재 이유가 사라진다.

**A안 대신 B안을 고른 이유는 가짜 실패의 성격이다.** A안에서 사용자가 할 수 있는 조치는 재녹화
전에 서버를 손으로 되돌리는 것인데, 그것을 문서에 적어두면 아무도 안 한다. 그리고 잊었을 때
나오는 것이 위의 화면이다. 도구가 서버를 잘못 고발하는 것은 이 프로젝트가 감수할 수 없는 종류의
오류다. 반대로 B안의 비용은 `cli` 안의 파일 하나와 호출 한 줄이다. 상태 없는 서버 사용자는 옵션을
안 쓰면 되고 동작이 지금과 완전히 같다.

**초기화 방법을 우리가 알 수 없어 사용자에게 받는다.** 서버마다 시드 스크립트, 마이그레이션, DB
truncate, 파일 삭제로 다 다르다. MCP 규격에도 초기화 개념이 없다. 우리가 추측해 만들면 틀린다.

**`auto` 에서도 도는 것이 핵심이다.** 이렇게 하면 녹화된 모든 항목이 같은 출발점을 공유한다는
불변식이 선다. 최초 녹화분도 초기화 직후 상태이고 나중에 추가된 케이스의 녹화분도 초기화 직후
상태다. 어느 시점에 녹음됐는지와 무관하게 카세트 한 벌이 일관된다. `auto` 를 건너뛰면 캐시된
항목과 새로 녹화된 항목이 서로 다른 상태를 반영해 카세트 안에서 모순이 생긴다. `replay` 는
`inner.callTool` 을 아예 부르지 않으므로 초기화할 대상이 없다.

**실패 시 중단하는 이유는 모르는 상태로 녹화한 카세트가 쓰레기이기 때문이다.** 경고만 하고
진행하면 그 카세트가 오라클 지위를 얻고, 나중에 원인을 추적할 단서가 남지 않는다. 초기화를 건너뛰고
싶은 사용자는 옵션을 빼면 된다. 그 선택은 명시적이어야 한다.

**명세 파일에서 안 받는 이유는 임의 코드 실행이다.** 명세 파일은 AI 가 쓰고 사람이 승인하는
물건이며, 남이 만든 명세를 받아 돌리는 것도 정상 사용이다. 거기에 셸 명령을 넣을 수 있으면 명세
파일 하나로 임의 코드가 실행된다. `--reset-cmd` 는 사용자가 자기 손으로 타이핑한 것만 인정한다.
같은 이유로 셸을 거치지 않고 인자 배열로 실행한다. `--reset-cmd "a && b"` 가 안 되는 것은 의도된
제약이고, 필요하면 사용자가 스크립트 파일을 만들어 그것을 부른다.

## 결과

- `cli` 한 패키지만 바뀐다. `record` 도 `runner` 도 `core` 도 건드리지 않는다. 초기화는 카세트
  클라이언트를 조립하기 전에 `cli` 가 실행하는 사전 단계라 의존 방향에 영향이 없다.
- 초기화 실행 사실은 `RunnerReport` 에 넣지 않는다. 소요 시간과 출력이 보고서에 섞이면 "같은
  suite 를 두 번 실행한 `RunnerEvent[]` 와 `RunnerReport` 가 deep equality" 라는 결정론성 계약이
  깨진다. 화면에는 진행 줄 한 줄만 찍는다.
- 실패 문안은 원인·조치·회피를 함께 보여준다. `renderProcessDiagnostics`(ADR-0014)와 같은 채널
  정책을 따른다.
- **우리 E2E 로는 이 결정을 검증할 수 없다.** `examples/` 에 있는 서버는 `weather-server` 하나이고
  상태가 없다. 훅이 도는지(명령 실행, 실패 시 중단, `replay` 에서 건너뜀)는 인메모리 테스트로
  덮이지만, 잔여물이 만드는 가짜 실패가 실제로 사라지는지는 상태 있는 예제 서버가 생겨야 확인된다.
  이 공백을 단계 3 설계서에 적고, 상태 있는 예제 서버 추가를 별도 항목으로 올린다.
- ADR-0022 가 위반 케이스를 상한 없이 기본 생성하므로 시험 실행의 호출 수가 케이스 수만큼 늘어난다.
  초기화 훅은 그 호출들이 모두 같은 출발점에서 나가도록 보장하는 장치이기도 하다.
- 재검토 조건: 상태 있는 서버 사용자에게서 "초기화 명령을 매번 타이핑하기 번거롭다" 가 올라오면
  설정 파일 키로 승격한다. 반대로 훅 사용이 실사용에서 관찰되지 않으면 A안으로 되돌린다. 지운
  뒤에도 이 문서가 왜 만들었는지를 남긴다.
