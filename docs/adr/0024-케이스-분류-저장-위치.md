# ADR-0024: 케이스 분류는 `approval.cases` 에 저장하고 `test` 는 참고 문장으로만 쓴다

## 배경

승인 전 시험 실행은 후보 명세를 실제 서버에 한 번 돌리고, 실패한 케이스를 사용자가 **서버
결함**(명세가 옳다) 또는 **명세 오류**(추측이 틀렸다)로 분류하게 한다. ADR-0023 이 그 실행의
전제 조건(서버 상태 초기화)을 정했다. 남은 것은 분류 결과 자체를 어떻게 다루느냐다.

세 가지를 정해야 한다. 분류를 명세 파일의 어디에 적을 것인가, 그 분류가 `ohmymcp test` 의 종료
코드를 바꿀 것인가, 사용자가 "명세 오류" 로 고른 케이스를 파일에 남길 것인가. 셋 다 다르게 갈
수 있었고, 어느 쪽을 고르느냐가 이 도구의 빨간불이 무엇을 뜻하는지를 바꾼다.

## 선택지

**1. 분류의 저장 위치**

- A안: `approval.cases` 배열에 `{ id, status }` 로 넣는다.
- B안: `cases[]` 의 각 케이스 안에 필드로 넣는다.
- C안: 명세 파일 옆의 별도 사이드카 파일에 넣는다.

**2. `serverDefect` 와 `test` 종료 코드**

- D안: 종료 코드를 바꾸지 않는다. 참고 문장 한 줄만 덧붙인다.
- E안: `serverDefect` 로 표시된 케이스의 실패를 통과로 친다(알려진 결함 면제).

**3. `specError` 의 저장**

- F안: 저장하지 않는다. 미분류와 마찬가지로 저장 자체를 막는다.
- G안: 화면에 표시하고 파일에도 `specError` 로 남긴다.

## 결정

**A안 · D안 · F안**을 채택한다.

1. 분류는 `approval.cases` 에 `{ id: string, status: "passed" | "serverDefect" }` 배열로 적고,
   순서는 명세 `cases` 순서와 같게 쓴다. 타임스탬프와 실행 환경은 넣지 않는다.
2. `serverDefect` 케이스가 `test` 에서 실패하면 케이스 블록 뒤에 참고 문장 한 줄을 붙이되
   **종료 코드는 그대로 둔다.** 지문이 불일치면 그 문장도 찍지 않는다.
3. `specError` 는 파일에 남기지 않는다. 하나라도 있으면 저장이 막히고 사용자가 명세를 고쳐야
   한다. 미분류(`?`)도 같다.

## 이유

**B안을 배제한 이유는 지문이다.** ADR-0017 이 지문 계산에서 `approval` 블록을 통째로 뺐고, 그
근거로 "단계 3 이 케이스별 승인 상태를 더할 때 제외 규칙이 항목 수만큼 늘어나는 것을 막기 위해"
를 미리 적어 두었다. 분류를 `cases[]` 안에 넣으면 그 필드가 지문에 들어가고, 분류를 고치는 것이
명세를 고치는 것과 구분되지 않는다. 서버 결함 표시를 지웠다는 이유로 지문 불일치가 뜨면
사용자는 명세가 바뀐 줄 안다. 제외 규칙을 필드 단위로 늘려 막을 수는 있지만, 그것이 ADR-0017 이
피하려던 바로 그 비용이다.

**C안을 배제한 이유는 두 파일이 갈라지기 때문이다.** 사이드카는 커밋에서 빠지고, 리네임에서
따라오지 않고, 명세만 받은 사람에게 도착하지 않는다. 분류는 "이 명세를 왜 이 상태로 승인했는가"
의 일부라 명세와 같은 파일에 있어야 한다. 승인 지문이 이미 같은 파일에 있으므로 저장 위치를
나눌 이유가 없다.

**E안을 배제한 이유는 빨간불의 의미다.** 서버 결함으로 분류한 케이스를 통과로 치면 CI 가
초록이 되고, 초록이 되는 순간 서버를 고칠 이유가 사라진다. 회귀 테스트로 남긴다는 말은 고쳐질
때까지 빨간불로 남는다는 뜻이다. 분류가 주는 것은 면제가 아니라 **원인의 구분**이다. 사용자가
알고 싶은 것은 "이 실패가 새로 생긴 것인가, 승인 시점에 이미 알던 것인가" 이고, 참고 문장 한
줄이 그 답을 준다. 종료 코드까지 바꾸면 그 정보로 실패를 숨기는 것이 된다.

**지문 불일치일 때 참고 문장을 찍지 않는 이유**는 판정의 유효 범위다. 승인 시점의 "서버 결함"
은 그때의 케이스 정의에 대한 판단이다. 명세가 바뀌었으면 같은 id 라도 다른 케이스일 수 있고,
그때 옛 판정을 화면에 옮기면 틀린 근거를 제공한다. 지문 불일치 자체는 이미 별도로 보고된다.

**F안을 고른 이유는 게이트의 목적과 정반대이기 때문이다.** `specError` 는 "이 케이스는 틀렸다"
는 사용자의 선언이다. 그것을 파일에 남기면 "틀린 줄 알면서 저장한 케이스" 가 명세 안에 생기고,
그 케이스도 `test` 에서 돌아 빨간불을 낸다. 이 게이트의 존재 이유가 "명세는 옳다" 를 실제로
참으로 만드는 것인데, G안은 그 전제에 예외를 파 넣는다. 고칠 때까지 막는 쪽이 비용은 크지만
파일에 남는 것이 전부 옳다는 성질을 지킨다.

## 결과

- `runner` 의 명세 타입에 `SuiteCaseApproval` 과 `CaseApprovalStatus` 가 추가된다. 검증과 JSON
  Schema 도 함께 늘어난다. `runner` 에서 바뀌는 것은 이것뿐이고 matcher 와 실행기는 그대로다.
- **`approval.cases[].id` 가 `cases[].id` 에 실재하는지는 검증하지 않는다.** 케이스를 지우는
  정상 편집이 명세 파일을 깨진 것으로 만들면 안 된다. 반대 방향(케이스에 있는데 분류에 없음)도
  침묵한다. `test` 는 양쪽에 다 있는 id 에 대해서만 참고 문장을 쓴다.
- `approval.cases` 는 지문에 안 들어가므로, 분류가 실려도 기존 승인 상태 검증 조건이 그대로
  성립한다. 이 성질은 테스트로 고정한다.
- 저장 시 `cases` 키는 분류가 한 건이라도 있을 때만 쓴다. 빈 배열은 "시험 실행을 했는데 케이스가
  0개" 와 "시험 실행을 안 했다"(`--no-dry-run`)를 구분하지 못한다.
- `--json` 출력에는 `spec.cases` 키로 판정을 그대로 싣는다. 화면에서 종료 코드를 안 바꾸는 것과
  별개로, 기계가 읽는 출력에서까지 정보를 감출 이유는 없다.
- 재검토 조건: `serverDefect` 가 오래 쌓여 빨간불이 상시화되면 "알려진 결함" 을 별도 집계해
  보여주는 화면을 후속으로 낸다. 그때도 종료 코드는 건드리지 않는다. 반대로 분류가 실사용에서
  거의 `passed` 뿐이면 저장 자체를 생략하는 쪽을 검토한다.
