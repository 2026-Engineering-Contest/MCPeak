# ADR-0027: `isError` 진단이 서버 응답 본문을 함께 싣는다

  `docs/adr/0011-응답-본문-추출-규칙.md`,

## 배경

입력값 교정(ADR-0025)을 배선하고 나서 AI 제안 단계가 실제로는 거의 돌지 않는다는 것이
드러났다. 사슬은 이렇다.

1. 생성기가 만드는 정상 케이스의 단언은 `{ type: "isError", expected: false }` 하나뿐이다
   (`generate/src/render.ts`). 본문 단언을 붙이지 않는다.
2. 그 케이스가 실패하면 `isErrorMismatchDiagnostic` 이 도는데, 이 진단이 담는 것은 고정 문장
   하나와 `expected`·`actual` 두 불리언뿐이다. 서버가 무엇이라고 거절했는지는 한 글자도 담기지
   않는다.
3. `DryRunCaseOutcome.detail` 은 리포터 출력을 케이스별로 자른 것이라 진단에 없는 값이 생길 수
   없다.
4. 교정 대상 판별이 뽑는 `serverMessage` 는 항상 빈 문자열이 되고, 그러면 provider 를 부르지
   않고 곧바로 사람 입력으로 간다(설계 §4.4).

`get_weather` 에 `{"city":"example"}` 를 보내면 `examples/weather-server` 는 이렇게 답한다.

```
→ 'example' 의 날씨 데이터가 없습니다. 사용 가능한 도시: 서울, 부산, 제주
→ 이 예제 서버는 고정 데이터만 가지고 있습니다.
```

답이 응답 안에 있는데 화면까지 오는 길이 없어서, 도구는 그 문장을 못 본 채로 사람에게 값을
묻는다.

이것은 교정 기능만의 문제가 아니다. **실패 메시지가 곧 제품인 프로젝트에서, 실패 화면이 서버가
말해 준 이유를 버리고 있었다.**

## 선택지

1. `isError` 진단이 응답 본문을 함께 싣는다. 리포터가 위반 줄과 같은 `→ ` 형식으로 찍고,
   교정 단계는 그 줄을 근거로 쓴다.
2. 생성기가 정상 케이스에 본문 단언을 함께 붙인다. 본문 단언이 실패하면 지금도 `→ ` 줄에 서버
   값이 실린다.
3. `OperationResult` 가 `ToolResult` 를 통째로 나른다. 소비자가 알아서 꺼내 쓴다.
4. 그대로 둔다. 교정은 언제나 사람 입력으로 간다.

## 결정

1번을 고른다.

- `RunnerDiagnostic` 에 `notes?: string[]` 을 더한다. 리포터는 `violations` 와 같은 `→ ` 형식으로
  줄마다 찍는다.
- `assertIsError` 가 실패할 때 응답 본문을 `notes` 에 싣는다. 본문이 여러 줄이면 줄마다 항목
  하나다. 본문은 이미 executor 가 케이스당 한 번 계산하는 `extractResponseBody` 결과를 그대로
  쓴다. 두 번째 추출 구현을 만들지 않는다(ADR-0011).
- 본문에는 승인 화면과 같은 redaction 을 적용하고, `MAX_VALUE_STRING_CHARS` 로 자른다. 진단이
  이미 쓰는 규칙을 그대로 쓴다.
- 추출이 실패하면(본문이 우리가 아는 모양이 아니면) `notes` 를 붙이지 않는다. 모양을 모르는
  값을 짐작해 찍지 않는다.

## 이유

2번은 단언의 뜻을 바꾼다. 지금 정상 케이스는 "오류 없이 응답하기만 하면 통과" 이고, 본문 단언을
붙이면 "응답 모양까지 맞아야 통과" 가 된다. 서버가 필드를 하나 늘렸을 뿐인데 실패하는 테스트가
대량으로 생긴다. 교정 화면에 문장 하나를 싣자고 낼 값이 아니다. ADR-0022 가 위반 케이스를
정하면서 정상 케이스의 단언 구성을 이미 고정한 것도 근거다.

3번은 공유 계약을 넓힌다. `OperationResult` 는 다섯 패키지가 보는 자리이고, 여기에 응답 전문을
실으면 리포트 크기와 redaction 경계가 소비자마다 달라진다. 필요한 것은 실패한 단언 하나가
"무엇을 받았는지" 를 말하는 것뿐이다.

4번은 교정 기능의 AI 제안 절반을 죽은 코드로 남긴다. 그리고 애초의 문제, 즉 실패 화면이 이유를
안 보여준다는 것이 그대로 남는다.

1번을 고르면 세 가지가 한 번에 풀린다. 실패 화면이 서버의 말을 그대로 보여주고, 교정의 AI
제안이 근거를 얻고, `cli` 는 한 줄도 안 고쳐도 된다. 교정 대상 판별은 이미 `→ ` 줄을 읽고 있다.

## 결과

- **응답 본문이 터미널에 찍히고, 교정 제안 요청에 실려 외부 provider 로 나간다.** 노출 경계는
  ADR-0008 의 redaction 규칙을 따르되 **이 경로에서만 한 가지를 좁힌다.** `sanitizeJsonValue` 는
  값 전체가 `sensitiveValues` 와 같을 때만 치환하는데, 서버 오류 문장은 값이 문장 속에 박혀
  나온다(`토큰 sk-abc 이 만료되었습니다`). 그래서 이 줄에는 부분 일치까지 치환한다. 치환은
  자르기보다 먼저 한다. 전역 `sanitizeJsonValue` 의 의미는 바꾸지 않는다. 다섯 패키지가 쓰는
  함수를 부분 일치로 넓히면 정상 값이 잘려 나가는 자리가 생긴다.
- **`sensitiveKeys` 는 이 경로에서 안 걸린다.** 문장에는 키가 없기 때문이다. 서버가 오류 문장에
  비밀을 담는데 그 값을 `sensitiveValues` 로 알려주지 않으면 막을 수단이 없다.
- 실패 화면의 줄 수가 는다. `isError` 로 실패한 케이스마다 `→ ` 줄이 붙고, 본문이 여러 줄이면
  줄 수만큼 붙는다.
- `assertIsError` 의 시그니처가 바뀐다. 본문 접근자(`() => BodyExtraction | undefined`)와
  redaction 옵션을 받는다. 값이 아니라 함수인 이유는 통과한 케이스에서 응답을 읽지 않기
  위해서다. `runner` 안의 호출부는 executor 하나다.
- `isError` 로만 실패하던 베이스라인 케이스가 이제 `serverMessage` 를 갖는다. 교정 화면이
  §8.6.1(근거 없음)에서 §8.6(근거 있음)으로 바뀐다. 설계 문서의 두 화면 모두 살아 있다.
- `notes` 는 선택 필드다. 안 채우면 지금과 같이 동작하므로 다른 진단은 손대지 않는다.
