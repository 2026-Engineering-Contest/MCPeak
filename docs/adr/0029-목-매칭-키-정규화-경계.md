# ADR-0029: 목 매칭 키 정규화 경계

- 상태: 채택
- 날짜: 2026-08-15
- 작성자: @storyrago (③ mock server 파트)

## 배경

`@ohmymcp/mock` 은 `toolName + stableKey(args)` 로 주입된 응답을 찾는다. `stableKey` 는
`record` 의 `stableStringify`(ADR-0003)와 같은 정규화 규칙을 쓰지만, 정규화만으로는
막을 수 없는 입력이 있다.

순환 참조가 있는 객체는 `stableKey` 가 무한 재귀에 빠진다. 희소 배열(`[1, , 3]`)은 빈
자리와 `undefined` 원소를 구분하지 못한다. `NaN`·`Infinity`는 둘 다 `JSON.stringify` 를
거치면 `null` 이 되어 서로 다른 주입이 같은 키로 뭉친다. `Date`·함수·심볼·`BigInt`·`Map`
처럼 JSON 이 아닌 값은 `JSON.stringify` 가 값마다 다르게(무시하거나, 빈 객체로, 던지거나)
처리해 키가 불안정하다.

이 값들의 공통점은 **MCP 호출로는 절대 나타나지 않는다**는 것이다. JSON-RPC 를 건너오는
`arguments` 는 JSON 파서를 거치므로 순환도 `NaN` 도 함수도 될 수 없다. 그런데
`mock.on(tool, args, result)` 의 `args` 는 사용자가 코드로 직접 쓴 JS 값이라 이 제약을
받지 않는다. 그대로 두면 주입은 **성공한 것처럼 보이는데** 실제로는 그 인자로 오는
호출이 존재하지 않아 영영 맞지 않거나(희소 배열), 서로 다른 의도의 주입이 같은 키가
되어 나중에 넣은 쪽이 조용히 앞선 쪽을 덮어쓴다(`NaN`/`Infinity`).

같은 문제를 `record` 는 이미 풀었다(ADR-0003). 그 결정을 그대로 가져다 쓸지, 어디까지
같게 하고 어디부터 다르게 할지 정해야 했다.

## 선택지

- **A안: `record` 처럼 매칭 키를 해시한다.** `stableKey` 의 출력을 SHA-256 hex 로 바꾼다.
  두 패키지의 매칭 키 형태가 완전히 같아진다.
- **B안: 정규화 규칙만 공유하고 직렬화는 각자 둔다.** 거부 판정(순환·희소·비유한수·비JSON)은
  `record` 와 같은 집합으로 맞추되, 매칭 키 문자열 자체는 해시하지 않고 그대로 둔다.
- **깊이 처리를 어디서 할지도 함께 검토했다.** 주입 경로(`assertKeyable`)와 조회 경로
  (`stableKey`) 양쪽에 다 두는 안, 조회 경로에만 두는 안, 어느 쪽에도 상한을 두지 않고
  `record` 처럼 명시적 프레임 스택으로 재귀를 없애는 안.

## 결정

**B안을 택한다.** 거부 집합(순환 참조·희소 배열·`NaN`/`Infinity`·JSON 이 아닌 값)은
`record` 의 `stableStringify`(ADR-0003)와 동일하게 맞추지만, 매칭 키는 해시하지 않는다.

검사는 두 곳에 나눈다. 위 네 부류는 주입 경로(`assertKeyable`, `mock.on()`·정의 파일
`responses`)에서 막는다 — 와이어로는 도달할 수 없는 값이므로 여기서 막아도 정상 사용을
해치지 않는다. 중첩 깊이는 조회 경로(`stableKey`)에서도 상한(`MAX_KEY_DEPTH = 512`)으로
막는다 — 깊이는 실제 호출 인자도 도달할 수 있는 값이라, 주입 시점 검사만으로는 조회 때
서버가 죽는 것을 막지 못한다.

깊이는 상한으로만 막고, 반복문으로 재작성해 상한을 없애는 일은 지금 하지 않는다.

## 이유

**해시하지 않은 이유(A 를 버림).** ADR-0003 이 `matchKey` 를 SHA-256 hex 로 정한 이유는
결정론성이 아니라 **비밀값 누출**이다 — 카세트는 파일로 저장되고 매칭 키 문자열은
`redact()` 를 거치지 않으므로, 해시하지 않으면 인자에 담긴 토큰·이메일 같은 값이 그대로
디스크에 남는다. `mock` 의 키는 디스크에 가지 않으므로 이 구멍이 없다. 반대로 `mock` 의
키는 **실패 메시지에 그대로 찍히는 사용자 화면**이다(`missMessage`). 여기를 해시로
바꾸면 `→ 이 툴에 주입된 인자: 3f2a9c...` 가 되어, 사용자가 자신이 넣은 인자와 실제
호출 인자 중 무엇이 다른지 눈으로 비교할 수 없다. "실패 메시지가 곧 제품이다"(CLAUDE.md)
에 정면으로 어긋난다. 두 패키지가 마주한 위협이 다르므로 같은 도구(해시)를 같은 이유로
쓸 수 없다 — 정규화 규칙(무엇이 키가 될 수 있는가)은 공유하되, 직렬화(그 값을 어떻게
문자열로 남기는가)는 각자의 노출면에 맞춘다.

**검사를 두 곳에 나눈 이유.** 네 부류(순환·희소·비유한수·비JSON)를 조회 경로에도 넣지
않은 것은 낭비를 피하기 위해서다 — MCP 클라이언트가 보내는 `arguments` 는 JSON-RPC 를
거치므로 이 값들이 될 수 없다. 조회마다 도달 불가능한 경로를 검사하는 비용을 치를
이유가 없다. 반대로 깊이를 주입 경로에서만 막으면, 주입 시점에는 얕았던 호출이라도
실제 클라이언트가 깊게 중첩된 인자로 부르면 `stableKey` 가 재귀 중 스택을 터뜨린다.
도달 가능한 값은 도달 가능한 경로에서 막아야 한다.

**깊이 상한을 고르고 재작성을 미룬 이유.** `record` 의 `stableStringify` 는 명시적
프레임 스택으로 재귀를 없애 상한이 없다(약 40줄). `mock` 의 `stableKey`/`findKeyViolation`
은 8줄 안팎의 재귀다. 같은 방식으로 다시 쓰면 상한을 완전히 없앨 수 있지만, 지금 고쳐서
값어치가 있는 것은 "4000 단계까지 지원"이 아니라 "그보다 훨씬 얕은 곳에서 읽을 수 없는
스택 오버플로로 죽는 것"이다. 512 는 재귀가 실제로 터지는 지점(측정값 약 4000)에서
충분히 멀리 떨어져 있어 Node 버전·스택 여유 차이에 흔들리지 않으면서도, 상한을 넘는
호출은 예외 대신 `isError: true` 응답으로 사용자에게 보여준다. §11 의 범위 축소 순서상
목 서버는 3순위 축소 대상이라 재귀 재작성 같은 구조적 투자보다 지금 당장의 안정성을
우선한다.

## 결과

**얻은 것**

- 두 패키지(`record`·`mock`)가 "무엇이 매칭 키가 될 수 있는가"에 대해 같은 답을 준다.
  같은 인자를 두 패키지에 각각 넘겼을 때 한쪽만 거부하는 혼란이 없다.
- `mock` 의 실패 메시지가 여전히 사람이 읽을 수 있는 실제 값을 보여준다.
- 깊게 중첩된 호출 인자가 목 서버 프로세스를 죽이지 않는다.

**받아들인 비용**

- 두 패키지의 매칭 키 **직렬화**는 여전히 다르다(해시 vs 평문). 두 패키지의 코드를 같이
  읽는 사람은 "왜 여기는 해시하고 저기는 안 하나"를 문서 없이는 알 수 없다 — 그래서 이
  ADR 이 필요하다.
- 깊이 512 는 임의의 상한이다. 512 단계를 실제로 필요로 하는 호출이 나오면(가능성은
  낮다고 본다) 그때 반복문 재작성을 다시 검토한다.

**후속 과제**

- `record` 의 거부 규칙이 ADR-0003 이후 바뀌면 `mock` 도 같이 맞춘다.
- 반복문 기반 `stableKey`/`findKeyViolation` 재작성은 512 단계 상한이 실사용에서
  걸리는 사례가 나오면 시작한다.
