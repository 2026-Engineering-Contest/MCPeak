# ADR-0037: 설치로 해결되는 결핍 때문에 건너뛴 테스트는 CI 에서 실패로 올린다

- 상태: 제안
- 날짜: 2026-08-18
- 담당: cli
- 작성자: @seodduu
- 참조: `CLAUDE.md`("우리 도구로 우리를 검증한다"), `docs/adoption.md` §1.5, 이슈 #153, 이슈 #119
- 후속 결정: [ADR-0054](./0054-node-js-최소-지원-버전을-22-18로-올린다.md)는 Node 20용 `mock`
  stdio skip을 제거한다. 아래 Node 20 서술은 이 ADR을 작성할 당시의 배경이며, 설치 결핍과 런타임
  미지원 결핍을 구분하는 일반 원칙은 그대로 유지한다.
- 갱신 (2026-08-24): 승격 스위치의 이름이 `OHMYMCP_REQUIRE_E2E` 에서 `MCPEAK_REQUIRE_E2E` 로
  바뀌었다. [ADR-0050](./0050-mcpeak-으로의-개명과-npm-스코프-이전.md) 의 개명이 남긴 잔재이고,
  그 ADR 의 「기계적 치환에서 제외하는 문자열」 표는 환경변수를 다루지 않았다. 아래 「결정」의
  이름을 새 것으로 고쳤다 — ADR 은 기록물이지만 이 줄은 **읽는 사람이 그대로 따라 치는 배선**
  이라, 옛 이름을 남기면 기록이 아니라 오답이 된다. 판정 기준 자체는 바뀌지 않았다.

## 배경

`packages/cli/tests/fetch-server-e2e.test.ts` 는 실서버(`mcp-server-fetch`)를 띄워
"미지원 키워드를 가진 진짜 스키마에서 케이스가 1개 이상 나온다" 를 판정한다. 이 서버는
Python 이라 `uvx` 로 띄우는데, `uvx` 가 없으면 테스트가 skip 된다.

skip 은 초록으로 보인다. 러너 요약에서 유일한 신호는 `1 skipped` 한 줄이고, CI 요약에는
그것도 안 남는다. 즉 이 저장소가 원칙으로 건 "우리 도구로 우리를 검증한다" 가 아무도 모르게
안 도는 상태가 만들어진다. `CLAUDE.local.md` 의 거짓 신호 표가 같은 계열을 이미 적고 있다:
"유닛테스트 녹색, 실행 시 실패 → 픽스처·인메모리만 검증".

한편 저장소에는 성격이 다른 skip 도 있다. `packages/mock/tests/stdio.test.ts` 는
`node --experimental-strip-types` 를 쓰므로 타입 스트립이 없는 런타임에서 건너뛴다.
Node 20 에는 그 기능이 없고, Node 20 은 `ci.yml` 의 verify 매트릭스에 들어 있다.

## 선택지

- A안: `fetch-server-e2e` 한 곳만 고친다. 판정 기준은 세우지 않는다. 세 번째 skip 이
  생겼을 때 각자 방식으로 짜게 되고, 게이트가 여러 종류로 갈린다.
- B안: "건너뛴 테스트는 CI 에서 전부 실패로 올린다" 를 규칙으로 세운다. 이러면 위
  `mock` 의 skip 도 실패가 되고, Node 20 매트릭스가 영구히 빨갛다. 해소 방법은 Node 20
  지원을 접는 것뿐인데 그것은 별개의 팀 결정이다(`ci.yml` 주석, CONTRIBUTING §6).
- C안: 건너뛰는 **사유**로 나눈다. 설치하면 해결되는 결핍만 실패로 올리고, 런타임이
  원리적으로 지원하지 않는 것은 skip 을 유지한다.

## 결정

C안. 판정 기준은 다음 두 줄이다.

- **설치로 해결되는 결핍**(`uvx` 없음 등) 때문에 건너뛰면, CI 에서 실패로 올린다.
  고칠 주체가 우리이고 고치는 방법이 정해져 있으므로, 안 돈 것은 환경의 한계가 아니라
  우리의 태만이다.
- **런타임이 원리적으로 미지원**(Node 20 의 타입 스트립 부재 등)이라 건너뛰면, skip 을
  유지한다. 지원 런타임 목록을 바꾸는 것은 별도 결정이고, 그 결정 전까지 빨간 CI 는
  정보를 주지 않는다.

배선은 이렇게 한다.

- 승격 스위치는 환경변수 `MCPEAK_REQUIRE_E2E=1` 이다. 기본값은 꺼짐이라 `uv` 없는
  기여자도 나머지 테스트를 그대로 돌린다. (작성 당시 이름은 `OHMYMCP_REQUIRE_E2E` 였다.
  위 「갱신」 참조.)
- 승격된 실행에서 결핍이 확인되면 **실패하는 테스트 케이스 하나**로 표현한다. 파일 로드
  시점에 던지지 않는다.
- CI 에서는 이 스위치를 verify 매트릭스가 아니라 **Node 22 단일 `e2e` 잡**에서만 켠다.
- Python 서버를 띄울 때 `uvx --with "mcp<2"` 고정을 유지한다. `mcp` 2.x 는 `McpError`
  임포트가 깨져 서버가 시작조차 못 하고, 그것을 우리 도구 결함으로 오진하기 쉽다.

## 이유

- 실패 메시지가 곧 제품이라는 이 저장소의 원칙이 표현 방식을 정한다. 실패 케이스로 두면
  원인(`uvx` 없음), 영향(완료 조건 §1.1-3 미검증), 해결(`uv` 설치)이 러너 출력에 그대로
  찍힌다. 로드 시점 throw 는 "수집 실패" 로 보여 우리 코드 버그처럼 읽히고, CI 스크립트에서
  `uvx --version` 을 확인하는 방식은 로컬에서 재현되지 않는다.
- Node 버전에 민감한 층은 이미 매트릭스로 덮여 있다. `packages/core/tests/stdio-integration-e2e.test.ts`
  가 실제 자식 프로세스 spawn, stdio 왕복, 종료와 좀비 잔존을 20/22/24 전부에서 본다.
  fetch E2E 가 추가로 보는 것은 상대가 Python 프로세스라는 점 하나이고, 거기서 버전 차이가
  나면 core 쪽이 먼저 깨진다. 몇 분짜리 E2E 를 3회 돌릴 값어치가 없다.
- 사유로 나누면 지금 저장소의 모든 skip 이 규칙을 만족한다. `mock` 은 코드를 한 줄도 안
  고쳐도 되고, 다른 오너의 패키지를 건드릴 일이 없다.

## 결과

- `uv` 가 깔린 CI `e2e` 잡에서 실서버 E2E 가 반드시 돈다. 안 돌면 그 실행은 빨갛다.
- 로컬 `pnpm test` 는 종전과 같다. `uv` 가 없으면 skip 되고 사유가 경고로 찍힌다.
- 세 번째 skip 이 추가될 때 판단 기준이 남는다. 새 skip 을 넣는 사람은 그것이 설치로
  해결되는지 자문하고, 그렇다면 같은 스위치를 읽어야 한다.
- 런타임 미지원 skip 은 여전히 조용하다. 이 ADR 작성 시점에 Node 20 에서 `mock` stdio 가
  안 도는 사실은 이 규칙이 아니라 지원 런타임 결정이 다룰 문제로 남겼고, ADR-0054 가 최소
  버전을 22.18.0 으로 올리면서 그 skip 을 제거했다. 규칙 자체는 그대로다 — 런타임 미지원
  skip 은 이 규칙이 아니라 지원 런타임 결정이 다룬다.
- 실행 격리(이슈 #119, 실서버 스펙의 직렬 실행)와는 독립이다. 저쪽은 **어떻게** 도느냐이고
  이쪽은 **도느냐**다.
