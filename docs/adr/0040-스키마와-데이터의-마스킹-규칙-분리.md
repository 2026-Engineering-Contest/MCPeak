# ADR-0040: 스키마는 데이터와 다른 마스킹 규칙을 쓴다 (ADR-0003 개정)

- 상태: 제안
- 날짜: 2026-08-18
- 담당: record
- 작성자: @ddxng5 (② replay/record 파트)
- 승인: 미승인
- 참조: `docs/adr/0003-cassette-matching-key.md` (개정 대상),
  `docs/adr/0039-민감-키-목록과-매칭-경계.md`,
  `docs/adr/0018-입력-계약-대조-소비자-배선.md`,

## 배경

`prepareCassetteForWrite` 는 `tools` 에도 `redact` 를 건다. 그 결과 저장된
`tools.inputSchema` 가 파괴된다.

```
{ properties: { apiKey: { type: "string", default: "sk-schema-secret" } } }
          ↓
{ properties: { apiKey: "[redacted]" } }
```

프로퍼티 **정의 객체**가 문자열이 됐다. 값이 가려진 것이 아니라 스키마가 부서진 것이다.
`packages/record/tests/index.test.ts` 가 이 동작을 기대값으로 고정해두고 있다.

**원인은 `sensitiveKey` 가 키 이름을 본다는 데 있다.** 데이터에서 `apiKey` 는 "비밀값이 담긴
자리"지만, **스키마에서 `apiKey` 는 값이 아니라 선언 대상의 이름**이다. 스키마의 비밀값은
거기가 아니라 `default` · `examples` · `const` 처럼 값이 들어가는 자리에 있다. 데이터용
규칙을 스키마라는 다른 종류의 문서에 그대로 적용한 것이 결함의 정체다.

**파급이 조용하다.** 망가진 스키마로 입력 계약 대조를 돌리면 결과가 "위반 없음"과 구분되지
않는다. `packages/cli/src/test-command.ts` 는 `tools.length === 0` 이면 대조를 건너뛰고,
대조가 throw 하면 `catch` 에서 빈 배열을 돌려준다. 세 경로 모두 같은 출력을 낸다. ADR-0041 이
다루는 값 불일치는 테스트가 깨져서 드러나지만, 이건 드러나지 않는다.

## 선택지

1. **현행 유지.** 스키마도 데이터와 같은 규칙으로 마스킹한다.
2. **`tools` 를 마스킹에서 통째로 제외한다.** 스키마에는 비밀값이 없다고 본다.
3. **스키마 전용 규칙을 만든다.** 구조는 보존하고 값이 들어가는 자리만 마스킹한다.
4. **`tools` 를 카세트에 저장하지 않는다.** 재생 시 스키마를 쓰지 않는다.

## 결정

**선택지 3 을 고른다.**

- `properties.<name>` 의 이름은 선언 대상이므로 건드리지 않는다. 스키마 구조를 보존한다.
- **값이 들어가는 자리만** 마스킹 대상으로 본다 — `default`, `examples`, `const`, `enum`.
  `enum` 은 배열이므로 원소 전체를 가린다. 허용값 목록에 실제 키가 들어 있는 경우가 있다.
- **`properties` 와 `items` 는 재귀한다.** 중첩된 객체·배열 스키마도 같은 규칙을 받는다.
  마스킹 여부는 그 자리까지 내려온 프로퍼티 이름으로 판단한다.
- **ADR-0004 가 지원하지 않는 키워드(`allOf` · `anyOf` · `oneOf` 등)는 대상이 아니다.**
  해석하지 않는 구조에 마스킹만 거는 것은 근거가 없다. 지원 범위가 늘어나면 그때 함께 넓힌다.
- 마스킹 여부를 판단하는 키 목록 자체는 ADR-0039 를 따른다.

ADR-0039 다음, ADR-0041 이전에 구현한다.

## 이유

**선택지 2 는 유출 경로를 연다.** 스키마에 비밀값이 없다는 전제가 틀렸다. 지금 테스트가 쓰는
예시가 정확히 `default: "sk-schema-secret"` 이고, 실제 서버가 기본 API 키를 스키마에 적어
두는 일은 드물지 않다. 구조를 지키자고 값을 흘리면 문제를 맞바꾼 것뿐이다.

**선택지 4 는 재생을 망가뜨린다.** `replay` 모드는 카세트의 `tools` 로 `listTools` 를
응답한다. 저장하지 않으면 서버 없는 재생 자체가 성립하지 않는다(ADR-0028).

**선택지 1 을 유지할 수 없는 이유는 침묵이다.** 이 프로젝트는 "우리 도구로 우리를 검증한다"를
가치로 내걸었는데, 검증이 사라진 것을 감지할 방법이 없는 상태가 그 가치와 정면으로 어긋난다.
값이 달라지는 결함보다 검사가 사라지는 결함이 더 위험하다.

**문서 종류를 구분하는 것이 예외가 아니라 규칙이다.** 카세트에는 성격이 다른 두 종류가 함께
들어 있다 — 주고받은 **데이터**(`request.args`, `response`)와 서버가 선언한 **스키마**
(`tools`). 하나의 규칙으로 둘을 다루려 한 것이 애초에 무리였다.

## 결과

- ADR-0003 의 "`tools` 의 민감값을 마스킹한다" 부분을 개정한다.
- **스키마가 보존되어** `replay` 와 `generate --cassette` 경로에서 입력 계약 대조가 실제로
  의미를 갖는다. 지금은 대조가 돌아도 판정 근거가 부서진 상태다.
- `packages/record/tests/index.test.ts` 의 `loadedSchema?.properties?.apiKey` 기대값이
  바뀐다. ADR-0003 이 승인한 동작을 고정한 단언이므로 결정 변경에 해당한다.
- 카세트 포맷과 `CASSETTE_VERSION` 은 바뀌지 않는다. 다만 저장되는 스키마의 **구조**가
  달라지므로 구형 카세트와는 내용이 어긋난다. 호환성 계약은 ADR-0039 의 「카세트 호환성 계약」
  절에 있다.
- `listTools` 반환값에도 이 규칙이 적용된다. 경계 정의는 ADR-0041 에 있다.
- **이 ADR 이 닫지 않는 것.** `test-command` 가 입력 계약 대조 실패를 조용히 삼키는 세 지점은
  `cli` 소관이라 별도 이슈다. 스키마를 고쳐도 그 `catch` 들이 남아 있으면 다음 번 조용한
  실종은 또 생긴다. `replay` 서브커맨드가 애초에 대조를 부르지 않는 문제는 ADR-0018 소관이다.
