# ADR-0045: 민감 키 목록에 `key` 합성어를 넣고 복수형을 조회에서 흡수한다 (ADR-0039 개정)

## 배경

ADR-0039 가 마스킹 매칭을 부분일치에서 접미 단어열 일치로 좁히면서 `tokenCount` ·
`secretariat` 오탐을 없앴다. 규칙은 옳았지만 **목록이 그 규칙을 못 따라갔다.** 접미 조합이
목록과 *정확히* 일치해야 하므로, 목록에 없는 형태는 전부 통과한다.

실제로 넣어 확인한 결과다.

```
통과: apiKeys, tokens, accessTokens, refreshTokens, secrets, secretKey,
     passwords, passwd, cookies, privateKey, private_key, signingKey,
     sessionKey, credential, credentials
```

두 부류다.

**복수형.** `refreshToken` 은 가려지는데 `refreshTokens` 는 안 가려진다. 같은 필드의 배열
버전만 새는 꼴이고, 토큰·비밀값 목록이 배열로 오는 응답은 오히려 흔하다.

**`key` 로 끝나는 합성어.** `privateKey` · `signingKey` · `sessionKey` 가 목록에 없다.
`secretKey` 는 더 나쁘다 — `secret` 이 목록에 있는데도 접미 조합이 `key` · `secretkey` 라
어디에도 안 걸린다. ADR-0039 가 `X-Api-Key` 때문에 `apikey` 를 따로 열거해야 했던 것과
**같은 구멍이 반복된 것**이다.

이것이 지금 문제인 이유는 ADR-0003:35 가 마스킹의 전제로 깔아 둔 문장 그대로다. 카세트 파일은
저장소에 커밋된다. 그리고 ADR-0041 이 정한 네 경계 중 "사용자 표시" 는 CI 로그로 나간다.

## 선택지

1. **복수형을 목록에 개별 항목으로 넣는다.** `tokens` · `secrets` · `cookies` …
2. **`key` 를 단독 항목으로 넣는다.** `privateKey` 계열이 한 번에 걸린다.
3. **`key` 합성어를 열거하고, 복수형은 조회 시점에 흡수한다.**
4. **사용자 정의 목록을 연다.** 기본값을 사용자가 채우게 한다.

## 결정

**선택지 3 을 고른다.**

**목록에 여섯 항목을 추가한다.** `privatekey` · `secretkey` · `signingkey` ·
`sessionkey` · `credential` · `passwd`.

**복수형은 `sensitiveKey` 조회에서 흡수한다.** 접미 조합이 목록에 없고 꼬리가 `s` 이면, `s`
를 뗀 형태로 한 번 더 조회한다. 목록 자체는 단수형만 담는다.

**`auth` · `pwd` · `bearer` 는 넣지 않는다.**

| 키 | 뺀 이유 |
|---|---|
| `auth` | `auth: { token, type }` 의 하위 트리를 통째로 `"[redacted]"` 로 만든다. ADR-0041 이후 마스킹은 테스트가 보는 값에도 적용되므로, 구조를 영영 못 보게 된다. `auth.token` 은 이미 `token` 으로 걸린다. |
| `pwd` | 파일시스템 MCP 서버가 작업 디렉터리를 이 이름으로 돌려준다. 실제 값이 가려지면 그 필드를 검증할 수 없다. `passwd` 만 넣는다. |
| `bearer` | `bearerToken` 은 `token` 으로 이미 걸린다. 단독 `bearer` 키를 쓰는 서버를 확인하지 못했다. |

**`key` 단독은 여전히 넣지 않는다.** ADR-0039 의 판단을 유지한다.

**사용자 정의 마스킹 규칙은 여전히 제공하지 않는다.** ADR-0003 · ADR-0039 의 이 부분을
유지한다. 기본값이 새는 상태에서 확장 통로부터 열면, 각자 자기 목록을 관리하다 각자 다르게
샌다. 나중에 열더라도 기본 목록을 **덮어쓰는** 것이 아니라 **추가하는** 통로여야 한다.

## 이유

**복수형을 항목으로 넣으면 목록이 두 배가 된다.** 항목 수에 비례해 오탐이 는다는 것이
ADR-0039 가 부분일치를 버린 이유였다. 같은 논리가 목록 길이에도 적용된다. 조회에서 흡수하면
항목은 그대로 두고 형태만 덮는다.

**꼬리 `s` 완화는 넓어 보이지만 좁다.** 목록 단어에 `s` 를 붙여 만들어지는 영어 단어는 전부
그 비밀값의 복수형이다 — `token`+s, `secret`+s, `cookie`+s 중 다른 뜻을 갖는 것이 없다.
그리고 머리 명사는 건드리지 않으므로 `tokenCounts` · `secretariats` · `cookieCounts` ·
`credentialTypes` 는 계속 통과한다. 제안 구현으로 회귀 표본을 돌려 **새로 걸리는 항목이 0
개**임을 확인했다.

**`key` 단독 대신 합성어 열거를 고르는 이유는 비대칭이다.** `key` 를 넣으면 `sortKey` ·
`cacheKey` · `partitionKey` 처럼 비밀값이 아닌 흔한 이름이 전부 걸린다. 반대로 `privatekey`
계열을 빠뜨렸을 때의 손해는 개인키 평문이다. 손해의 크기가 다르므로 좁게 열거하고, 새 형태가
발견되면 항목을 늘린다.

**빠진 것을 채우는 것과 규칙을 넓히는 것은 다르다.** 이 ADR 은 ADR-0039 의 접미 규칙을
그대로 두고 목록만 손본다. 규칙을 넓히면 오탐이 계열 전체로 번지지만, 목록은 넣은 만큼만
는다.

## 결과

- ADR-0039 의 목록 문단을 개정한다. 접미 단어열 규칙과 `key` 단독 배제는 유지한다.
- **카세트 파일 내용이 바뀐다.** 위 열다섯 형태가 새로 가려진다. 포맷과
  `CASSETTE_VERSION` 은 바뀌지 않으므로 기존 카세트는 그대로 로드된다. ADR-0039 의
  **카세트 호환성 계약**(0039 · 0040 · 0041 공통 절)이 이 개정에도 그대로 적용된다 —
  구형 카세트는 재녹화 전까지 옛 마스킹 결과를 갖고, 되돌릴 수 없다.
- **이미 커밋된 카세트에 누출은 없다.** 저장소의 `*.json` 을 조회해 확인했다. 예제 서버가
  비밀값을 다루지 않아서이지 규칙이 막아서가 아니다. 실서버에 붙이는 순간 드러난다.
- 저장 경계를 파일 바이트로 고정하는 테스트를 추가한다. 이 구멍의 결과가 "평문이 파일로
  굳는다" 이므로, 단위 함수 반환값이 아니라 `saveCassette` 가 쓴 내용으로 단언한다.
- 한계를 남긴다. 목록은 여전히 열거이고 영어 합성명사를 전제한다. `credentialsBlob` 처럼
  머리가 목록 밖인 이름, 영어가 아닌 키는 걸리지 않는다. `auth` · `pwd` · `bearer` 를 뺀
  판단은 위 표의 근거가 바뀌면 다시 볼 수 있다.
