# ADR-0046: 대시보드는 로컬 웹서버로 만들고 CLI 커맨드 함수를 재사용한다

- 상태: 제안
- 날짜: 2026-08-19
- 담당: dashboard, cli
- 작성자: @seodduu
- 승인: 미승인
- 참조: `docs/2026-08-19-대시보드-설계.md`,
  `docs/plans/2026-08-19-대시보드-구현계획.md` §3 · §4 · §5,
  `packages/cli/src/commands.ts` (`ohmymcp/commands` 공개 면),
  `packages/dashboard/src/server/wiring.ts`,
  `packages/cli/src/index.ts` (`run()` 분기),
  `CLAUDE.md` (의존 방향, 실패 메시지가 곧 제품)

## 배경

이 프레임워크의 화면은 지금까지 터미널 하나였다. `test` 는 리포트를 찍고 끝나지만
`generate` 와 `repair` 는 사람에게 묻고 답을 받아 진행하는 대화형 플로우다. 그 대화가
터미널에만 있으면 세 가지가 막힌다. 후보 명세와 실행 결과를 나란히 두고 볼 수 없고,
카세트를 눈으로 훑어 고칠 방법이 없으며, 실패한 케이스에서 곧바로 `repair` 로 넘어가는
동선이 사람의 기억에만 남는다.

동시에 지켜야 할 것이 있다. 판정 로직이 두 벌이 되면 안 된다. 대시보드가 스위트를 따로
읽고 따로 실행하기 시작하면 CLI 와 화면의 결과가 갈리는 날이 오고, 그날 사용자는 어느
쪽을 믿을지 알 수 없다. 결정론성이 핵심 가치인 도구에서 이것은 기능 추가가 아니라 손실이다.

## 선택지

**A안: 정적 리포트.** 실행이 끝난 뒤 HTML 파일 하나를 내보낸다. `--junit` 옆에 `--html` 을
더하는 모양이다. 서버가 필요 없고 CI 산출물로 붙이기 쉽다.

**B안: CLI 프로세스 래핑.** 웹서버가 `ohmymcp` 실행 파일을 자식 프로세스로 띄우고
stdout/stdin 을 중계한다. CLI 를 블랙박스로 두므로 패키지 경계를 안 건드린다.

**C안: 바닐라 JS 프론트.** 서버는 두되 프론트는 프레임워크 없이 DOM API 로만 만든다.
새 의존성이 거의 없다.

**D안: 데스크톱 앱.** Electron 이나 Tauri 로 감싸 설치형 앱으로 낸다. 파일 접근과 프로세스
실행이 자연스럽고 로컬 포트를 안 쓴다.

**결정: 로컬 웹서버 + `ohmymcp/commands` 재사용.** Node 내장 `http` 로 서버를 띄우고,
`packages/cli` 가 새 서브패스 `ohmymcp/commands` 로 커맨드 함수를 공개한다. 대시보드는 그
함수들을 직접 호출하되 `writeStdout` · `writeStderr` · `reviewIO` 세 자리만 웹용 구현으로
바꿔 끼운다. 프론트는 React + Vite 이며 전부 devDependency 로 두어 번들에만 들어간다.

## 이유

**A안은 대화형 플로우를 담지 못한다.** 정적 파일은 `generate` 의 승인 화면이나 `repair` 의
확인 질문을 받을 수 없다. 이 대시보드를 만드는 이유의 절반이 그 대화이므로 A안은 목표를
비껴간다. 리포트 내보내기는 이미 `--junit` 이 하고 있고, 필요하면 그쪽을 넓히는 편이 맞다.

**B안이 가장 그럴듯해 보였고 실제로 가장 위험하다.** 자식 프로세스를 쓰면 대화를 stdin 으로
중계해야 하는데, CLI 의 프롬프트는 사람이 읽는 문장이지 기계가 파싱할 프로토콜이 아니다.
질문 문구가 바뀔 때마다 대시보드가 조용히 깨지고, 그 깨짐은 "답이 안 먹는다" 는 증상으로만
나타난다. `ReviewIO` 는 이미 그 대화를 인터페이스로 뽑아 둔 자리다. 있는 이음매를 두고
텍스트를 다시 파싱하는 것은 계약을 버리고 지문을 읽는 일이다.

**C안은 절약하는 곳이 틀렸다.** 이 대시보드의 화면은 SSE 로 들어오는 이벤트 스트림에 붙어
계속 다시 그려진다. 그 갱신을 손으로 관리하면 코드가 늘고, 늘어난 코드는 전부 우리가
유지해야 한다. React 는 런타임 의존성이 아니라 빌드 산출물에 포함되는 devDependency 이므로
사용자의 설치 트리에 새 패키지가 얹히지 않는다. 절약할 대상은 사용자의 의존성 트리이지
우리 코드의 명료함이 아니다.

**D안은 배포 비용이 값에 안 맞는다.** 데스크톱 앱은 플랫폼별 빌드와 서명, 자동 업데이트를
데려온다. 이 도구의 사용자는 이미 터미널 앞에 있는 개발자이고, `npx` 한 줄로 뜨는 로컬
서버가 설치형 앱보다 진입이 짧다. 브라우저 자동 오픈조차 크로스플랫폼으로 하려면 의존성이
붙어서, 지금은 URL 을 출력하고 사용자가 열게 두었다.

**재사용의 경계를 함수 단위로 그은 것이 이 결정의 핵심이다.** 대시보드는 스위트를 읽지도,
서버에 붙지도, 리포트를 렌더하지도 않는다. 그 일은 전부 `runCli` · `runGenerateCommand` ·
`runReplayCommand` · `runRepairCommand` 안에 있고 대시보드는 IO 세 자리만 바꾼다. 판정
로직이 한 벌로 남는다는 뜻이며, 화면과 터미널의 결과가 갈릴 여지가 구조적으로 없다.

## 결과

- **의존 방향에 층이 하나 새로 얹혔다.** 지금까지는 `cli` → `runner`/`generate`/`record`/`mock`
  → `core` 였다. 여기에 `dashboard` → `cli` 가 붙어 `dashboard` 가 최상단이 된다. 단방향은
  유지되고 순환도 없지만, `CLAUDE.md` 에 적힌 의존 방향 문장은 이 층을 아직 담고 있지 않다.
  그 문장을 갱신하는 것이 이 결정의 후속이다.
- **`ohmymcp/commands` 가 새 공개 계약이 됐다.** 재export 만 있는 파일이고 로직이 없다.
  여기 적힌 이름을 지우거나 시그니처를 바꾸면 대시보드가 깨진다. `packages/cli` 는 이제
  자기 내부를 고칠 때 이 면을 함께 봐야 한다.
- **CLI 의 의존성 조립 블록이 두 곳에 있다.** `packages/cli/src/index.ts` 의 `run()` 분기가
  각 커맨드에 넘기는 의존성 객체를 `packages/dashboard/src/server/wiring.ts` 가 항목 단위로
  복제한다. 같은 목록이 두 벌이므로 **cli 쪽 조립을 바꾸면 dashboard 쪽도 같이 봐야 한다.**
  특히 `repair` 는 cli 가 `nodeRepairDependencies(generate)` 라는 헬퍼로 조립하는데 그
  헬퍼가 `ohmymcp/commands` 로 재export 되어 있지 않아, dashboard 가 같은 내용을 손으로 다시
  적어 두었다. 이 복제는 의도한 것이 아니라 갚아야 할 빚이다. 조립 헬퍼를 전부 재export 해
  dashboard 가 그것만 부르게 바꾸는 것이 정리 방향이고, 그전까지는 cli 의 조립을 고칠 때마다
  `wiring.ts` 를 함께 열어야 한다.
- 대시보드 서버는 상태를 메모리에만 둔다. run 레지스트리는 프로세스와 함께 죽는다. 영속화는
  범위 밖이며, 그래야 "같은 입력에 같은 결과" 를 흔들 저장소가 애초에 생기지 않는다.
- SSE 이벤트에는 시각이나 일련번호를 싣지 않는다. 같은 실행을 두 번 하면 이벤트 원문이
  바이트까지 같아야 하고, `packages/dashboard/tests/dashboard-e2e.test.ts` 가 그것을 단언한다.
- React 는 devDependency 다. 배포되는 것은 Vite 가 만든 정적 산출물이므로 사용자가 설치하는
  런타임 의존성은 workspace 패키지뿐이다.
- 재검토 조건: `ohmymcp` 를 라이브러리로 쓰는 외부 사용자가 생기면 `ohmymcp/commands` 는
  대시보드 전용 면이 아니라 공개 API 가 된다. 그때 이름과 안정성 보장 범위를 다시 정한다.
