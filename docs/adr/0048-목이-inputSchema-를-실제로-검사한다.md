# ADR-0048: 목이 `inputSchema` 를 실제로 검사하되, 주입된 응답이 검사보다 우선한다

- 상태: 채택
- 날짜: 2026-08-19
- 담당: mock
- 작성자: @storyrago (③ mock server 파트)
- 승인: 승인 (2026-08-19, @storyrago · 파트 ③ 오너)
- 참조: #181, #180, `docs/adr/0005-mock-data-strategy.md`,
  `docs/adr/0015-입력-스키마-부분집합-경계.md`,
  `docs/adr/0021-거절-기대-케이스의-입력-계약-대조-제외.md`,
  `docs/adr/0003-cassette-matching-key.md`

## 배경

목은 `tools/list` 로 `inputSchema` 를 광고하지만 `tools/call` 인자를 그 스키마로 검사하지
않는다. 매칭은 인자 문자열 비교(exact) 와 `ANY` 폴백뿐이다. 선언은 장식이고 아무도 지키지
않는다.

그 결과가 `generate` 의 위반 케이스와 정면으로 부딪힌다. `buildViolationCases` 는 옵션 없이
네 축의 위반 케이스를 만들고 전부 `isError: true` 로 단언한다.

- 목 정의에 `ANY` 폴백이 있으면 위반 인자도 성공 응답을 받아 **거절 기대 케이스가 전원 실패**한다.
- `ANY` 를 빼면 위반 인자가 매칭 미스가 되어 `isError: true` 로 **우연히 통과**한다. 통과의
  근거가 검증이 아니라 "표에 없음" 이라 `runner` 가 `rejectionUnverified` 로 경고한다.

이 상태가 우리 CI 에 박제돼 있다. `packages/cli/tests/dist-cli-e2e.mjs` 의 목 E2E 는
`rejectionUnverified: 1` 을 정상값으로 단언한다.

**다만 이 경고 자체는 이 ADR 로 없어지지 않는다.** `runner` 의 `classifyRejectionBasis` 는
거절이 SDK 입력 검증에서 나온 것인지를 오류 문장 **접두어 화이트리스트**(`MCP error -32602:` ·
`Input validation error:` · FastMCP 패턴)로 판별하고, 목의 거절문은 거기 없다 — 검사를 하든
안 하든 `unverified` 로 떨어진다. 여기서 고치는 것은 **"우연히 통과"** 쪽이지 근거 확인 쪽이
아니다. 후자는 "결과" 절에 남긴다.

대상 사용자는 MCP 서버를 구현하기 **전에** 목과 `generate` 로 설계를 검증하는 사람이다.
그 사람은 위 두 가지를 구분할 수 없다. 명세가 틀린 것인지 목이 검사를 안 한 것인지 알 수 없다.

## 선택지

- **A안: 현행 유지 + 문서로 경고.** "`ANY` 는 거절 케이스를 무력화한다" 를 README 에 적는다.
  가짜 통과는 그대로 남는다.
- **B안: JSON Schema 평가기를 의존성으로 추가.** 정확하다. `CLAUDE.md` 의 목록 밖 의존성 금지와
  충돌하고, 실패 문안과 판정 기준을 외부 라이브러리에 넘기게 된다 (ADR-0015 가 같은 이유로 기각).
- **C안: `runner` 의 `checkInputContract` 를 import.** 의미론이 자동으로 일치한다. 의존 방향
  (`mock → core` 만 허용) 을 어긴다.
- **D안: 목 안에 소형 판정을 자체 구현한다.** 축을 정해서 좁게 만든다.

## 결정

D안을 택한다. 네 가지를 함께 정한다.

### 1. 검사 축은 넷이다 — `required` · `type` · `enum` · `range`

이슈 #181 본문은 "`generate` 위반 케이스가 보는 축이 정확히 `required` 와 `type` 둘" 이라고
적었으나 이는 사실과 다르다. `buildViolationCases` 는 `REQUIRED_OMITTED` · `TYPE_VIOLATION` ·
`ENUM_VIOLATION` · `RANGE_VIOLATION` 넷을 조건 없이 만든다.

두 축만 검사하면 `enum` · `range` 위반 케이스는 그대로 `ANY` 로 떨어져 가짜 통과가 절반 남는다.
사용자에게는 "같은 위반 케이스인데 어떤 것은 되고 어떤 것은 안 됨" 으로 보여 지금(전원 실패)보다
진단이 어렵다.

`enum` 은 포함 검사 한 줄이고 `range` 는 여덟 키워드(`minimum` · `maximum` · `exclusiveMinimum` ·
`exclusiveMaximum` · `minLength` · `maxLength` · `minItems` · `maxItems`) 비교라 평가기가 필요없다.

**중첩 객체와 배열 원소 내부는 보지 않는다.** 최상위 필드만이다. `generate` 의 위반 케이스가
최상위 필드 하나만 고쳐서 만들어지므로 그 이상은 지금 쓰이지 않는다.

### 2. 주입된 응답(exact)이 스키마 검사보다 우선한다

`tools/call` 처리 순서를 이렇게 고정한다.

```
① exact 히트          → 그 응답을 낸다 (검사하지 않는다)
② 스키마 위반         → 거절한다 (새 동작)
③ ANY 히트            → 그 응답을 낸다
④ 아무것도 없음       → 기존 미스 진단문
```

이슈 본문은 "레지스트리 조회 없이 거절" 을 제안했으나 순서를 뒤집는다.

### 3. 검사를 끄는 스위치를 만들지 않는다

②의 순서가 곧 탈출구다. 위반 인자에 응답을 주입하면 ①에서 이긴다. 정의 전체를 끄는
`"validate": false` 는 만들지 않는다.

### 4. 해석할 수 없는 스키마는 검사하지 않고, 시작할 때 한 번 고지한다

ADR-0015 의 규칙을 그대로 쓴다.

- 루트에 조합자·참조 계열(`anyOf` · `oneOf` · `allOf` · `not` · `$ref` · `if`) 이 있거나 루트가
  객체 스키마가 아니면 **그 툴 전체**의 인자 검사를 건너뛴다.
- 개별 필드에 그런 키워드가 있으면 **그 필드만** 건너뛰고 나머지 필드와 `required` 검사는 계속한다.
- `additionalProperties` 는 보지 않는다. 선언되지 않은 필드는 위반으로 치지 않는다.

`runner` 는 이 사실을 `SCHEMA_NOT_ANALYZABLE` finding 으로 낼 수 있지만 목에는 그 채널이 없다.
`stdout` 은 stdio 트랜스포트의 JSON-RPC 채널이라 쓸 수 없다. **서버를 띄울 때 `stderr` 로 한 번**
고지한다. 호출마다가 아니다 — 툴 목록은 기동 시 고정이므로 한 번이면 충분하고, 호출마다 내면
`stderr` 가 진단으로 오염된다.

### 5. 위반이 여럿일 때의 순서를 고정한다

결정론성 때문에 순서를 못 박는다.

1. `required` 누락 전부 — `required` 배열의 선언 순서대로
2. 그다음 필드별로 한 건씩 — `properties` 의 선언 순서대로

한 필드에서 여러 축이 동시에 어긋나면 `type` → `enum` → `range` 중 **첫 하나만** 낸다. 타입이
어긋난 값에 `enum` 포함 여부나 범위를 따지는 것은 의미가 없고, 문장이 서로 모순돼 보인다.

## 이유

- **축을 넷으로 잡은 것**: 이 기능의 존재 이유가 `generate` 위반 케이스와의 상성인데, 두 축만
  하면 그 목적을 절반만 달성하면서 진단은 더 어렵게 만든다. 추가 비용(20줄 안쪽)이 그 대가보다
  훨씬 싸다.
- **주입 우선**: 표는 사람이 손으로 쓴다. `record` 처럼 녹화된 것이 아니다. 그래서 스키마를 어기는
  줄이 실수가 아니라 의도일 수 있다 — "잘못 부르면 서버가 이렇게 답한다" 를 설계에 넣는 것은
  #180 이 `isError` 주입을 허용한 것과 같은 동기다. 검사를 먼저 돌리면 그 줄이 죽고, 살리려면
  스위치를 새로 만들어야 한다. 순서를 뒤집으면 설정 없이 같은 결과가 나온다.
- **기존 동작을 깨지 않는 범위**: 새로 거절되는 경로는 정확히 하나다 — *주입되지 않았고 `ANY`
  폴백으로 성공하던 호출*. 그것이 이 ADR 이 지목한 결함 자체다. 이미 주입된 응답은 전부 그대로 나간다.
- **오탐이 미탐보다 비싸다** (ADR-0015 와 같은 근거). 목이 정상 호출을 거절하면 사용자는 자기
  명세를 의심한다. 못 읽은 키워드가 바로 "이 필드는 없어도 된다" 를 말하고 있을 수 있다.
- **평가기를 안 들이는 이유**는 ADR-0015 와 같다. 실패 메시지가 곧 제품인 프로젝트에서 판정
  기준과 문안을 외부 라이브러리에 넘기는 것은 제품의 핵심을 넘기는 것이다.

## 결과

- **동작이 바뀐다.** `ANY` 폴백에 기대어 위반 인자를 성공시키던 정의는 이제 거절을 받는다.
  이것이 이 변경의 목적이지만, 그런 정의를 쓰던 사용자에게는 깨짐으로 보인다. `0.3.0` 에
  minor 로 싣고 CHANGELOG 에 마이그레이션 한 줄(위반 인자를 `responses` 에 명시하면 종전대로
  동작한다)을 적는다.
- **미탐이 남는다.** 조합자를 쓰는 스키마의 툴은 검사를 통째로 받지 못하고, 중첩 객체·배열 내부는
  어떤 스키마에서도 검사하지 않는다. 감수한 비용이고 넓히는 방향은 열려 있다. 넓히는 변경은
  기존 결과를 깨지 않는다.
- **`runner` 와 판정이 갈릴 수 있다.** 같은 인자를 `checkInputContract` 는 위반으로 보고 목은
  통과시키는 (또는 그 반대) 경우가 생길 수 있다. 코드를 공유하지 않기로 한 대가다. 두 곳의
  의미론이 갈리면 사용자가 혼란스러우므로, `range` 경계 해석(특히 `exclusiveMinimum` 과
  `integer` 의 소수 경계)은 `runner` 의 `contract-range` 를 **읽고 맞춘다**. import 하지 않는다.
- **`stderr` 고지는 `ohmymcp test` 성공 경로에서 사용자에게 안 보일 수 있다.** CLI 의 프로세스
  진단은 비정상 종료나 연결 실패에서 렌더된다. 그래도 내는 이유는 HTTP 경로에서는 사용자의
  터미널에 그대로 보이고, 조용히 건너뛰는 것보다 낫기 때문이다. 이 한계를 여기 적어둔다.
- **`rejectionUnverified` 경고는 남는다.** 목의 거절문이 `runner` 의 접두어 화이트리스트에
  없기 때문이다(배경 절 참조). 없애려면 둘 중 하나를 골라야 하고 둘 다 이 ADR 밖이다 —
  목의 문장을 `runner` 의 화이트리스트에 넣거나(`runner` 파트 결정), 목이 `isError` 대신
  `McpError(InvalidParams)` 를 던져 SDK 가 `MCP error -32602:` 를 만들게 하거나(이 ADR 의
  응답 표현 결정을 뒤집는 것이라 개정 대상). 인자 스키마 위반을 툴 오류로 볼지 프로토콜
  오류로 볼지의 판단이 걸려 있어 별도로 다룬다.
- 위반 문안 네 개는 이 결정의 산출물이자 계약이다. `generate` 의 진단이나 `runner` 의 실패
  메시지가 이 문장을 인용하게 되면 그때부터는 바꾸는 비용이 오른다.
