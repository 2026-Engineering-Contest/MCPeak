# ADR-0049: provider 로 보내는 자유 텍스트에는 값 치환을 적용하지 않는다 (ADR-0033 확장)

- 상태: 채택
- 날짜: 2026-08-20
- 담당: generate, cli
- 작성자: @endl24 (파트 ① · generate)
- 승인: 승인 (2026-08-20, @endl24 · 파트 ① 오너)
- 참조: [ADR-0033](./0033-stderr-외부-전송-경계.md) — 같은 판단을 stderr 한 곳에 내린 결정,
  [ADR-0008](./0008-승인-화면-redaction-범위.md) — redaction 범위를 넓히지 않는다,
  [ADR-0034](./0034-provider-진단-통로-분리.md),
  `docs/superpowers/specs/2026-08-18-rejection-basis-verification-design.md` §6.2 · §6.3,
  이슈 #165

## 배경

`generate` 의 거절 근거 진단(#89)이 provider 로 보내는 것 중 하나가 `responseBody` 다. 서버가
거절하면서 돌려준 응답 본문이고, **남의 서버가 자유롭게 쓴 텍스트**다.

지금까지 이 자리에는 `sanitizeRedactable` 이 걸려 있었고, 계약 주석과 설계서 §6.2 가 그것을
"redaction 이 적용된 값" 이라고 적고 있었다. **그 문장이 참이 아니다.**

`sanitizeRedactable` 의 방어는 둘인데 자유 텍스트에는 둘 다 닿지 않는다.

- **키 기반 치환**은 객체의 키를 본다. `responseBody` 는 루트 문자열이라 이 분기에 아예 안
  들어간다.
- **값 기반 치환**은 완전 일치다. `sensitiveValues` 에 등록된 문자열과 통째로 같을 때만 바뀐다.
  비밀값이 문장 안에 박혀 오면 그대로 나간다.

여기에 더해 **CLI 실경로에서는 이 호출이 항상 무동작이었다.** CLI 에는 `RunnerRedactionOptions`
를 만드는 경로가 없다 — 플래그도 기본값도 없고, `askRejectionDiagnosis` 는
`prepare({ cases })` 로 `redaction` 없이 부른다. `sensitiveValues` 가 늘 비어 있으므로 루트
문자열에 걸릴 규칙이 하나도 남지 않는다.

즉 **실제로는 아무것도 안 가리면서, 계약과 문서는 가린다고 말하는 상태**였다. ADR-0033 이
stderr 에서 이미 같은 함정을 다뤘고, 그 결정을 이 자리에 물려받을지가 이 ADR 의 판단이다.

## 선택지

- A: 지금대로 둔다. 완전 일치 한 경우만 치환되는 상태를 유지하고 문서만 고친다.
- B: 정규식 부분 문자열 치환을 도입한다. 토큰처럼 보이는 문자열을 찾아 바꾼다.
- C: 값 치환을 걷어내고, **적용하지 않는다는 사실**을 계약·문서·화면에 적는다. 상한·확인·
  기본 거부로 다룬다.

## 결정

C 를 채택한다. `RejectionDiagnosisRequest.responseBody` 에는 redaction 을 적용하지 않는다.
구조화된 `input` 에는 종전대로 키·값 치환을 그대로 건다.

`responseBody` 를 다루는 장치는 셋이고, 셋 다 이미 있다.

| 장치 | 현재 |
|---|---|
| 길이 상한 | `clampObservedText` 200 코드 포인트 (`MAX_VALUE_STRING_CHARS`) |
| 사용자 확인 | 미확인 목록이 본문을 한 줄씩 보여준 뒤 승낙을 묻는다 |
| 기본 거부 | 확인 질문이 `[y/N]` 이라 명시적으로 승낙하지 않으면 안 보낸다 |

ADR-0033 이 stderr 에 건 셋과 **같은 자리**를 채우되, 세 번째가 다르다. stderr 는 기본으로
실리고 `--no-stderr` 로 빼는 **옵트아웃**이고, 여기는 승낙하지 않으면 안 나가는 **기본 거부**다.
자유 텍스트를 다루는 방식으로는 이쪽이 더 센 기본값이라 그대로 둔다. 용어를 stderr 쪽에서
그대로 빌려 오면 기본값이 반대로 읽히므로 여기서는 "기본 거부" 로 적는다.

빠져 있던 것은 **"치환하지 않는다" 는 명시** 하나이고, 이 결정이 그것을 채운다.

## 이유

**못 하는 것을 한 척하지 않는다.** ADR-0033 의 이유를 그대로 쓴다. 부분적인 방어를 완전한
방어처럼 보이게 만드는 것이 원래 위험보다 나쁘다. 사용자는 "redaction 이 적용된 값" 이라는
문장을 근거로 내용을 확인하지 않고 보낸다. A 는 그 상태를 유지하는 선택이라 기각한다.

**B 는 ADR-0033 이 이미 기각했고, 그 근거가 여기에도 그대로 적용된다.** 정규식 치환은 무엇을
잡았는지도 무엇을 놓쳤는지도 말해 주지 못하면서 화면에는 "치환했습니다" 를 띄운다. 게다가
`responseBody` 는 AI 가 거절 문구를 읽고 판단하는 재료라, 문구를 뭉개면 진단 자체가 쓸모를
잃는다(ADR-0033 이 E2 를 기각한 것과 같은 이유).

**같은 종류의 데이터에 규칙이 두 벌 남으면 안 된다.** stderr 와 `responseBody` 는 "우리가 내용을
통제할 수 없는 남의 텍스트" 로 성격이 같다. 규칙이 갈라지면 다음에 한쪽만 고쳐지고, 그때 어느
쪽이 최신인지 알 방법이 없다.

**실익이 없다.** 위 배경대로 CLI 경로에서 이 호출은 무동작이었다. 걷어내도 실제로 가려지던 것이
줄지 않는다. 남는 차이는 계약이 사실을 말하느냐뿐이다.

## 결과

- `responseBody` 는 provider 로 **원문 그대로** 나간다. 라이브러리 사용자가
  `redaction.sensitiveValues` 를 직접 넘겨도 이 필드에는 걸리지 않는다. 그것이 의도이고,
  계약 주석과 설계서 §6.2 가 그렇게 적는다.
- 경계를 테스트가 고정한다. 같은 문자열이 `input` 에서는 `[REDACTED]` 가 되고
  `responseBody` 에서는 남는 대조 테스트가
  `packages/generate/tests/rejection-diagnosis.test.ts` 에 있다. 한쪽만 바뀌면 깨진다.
- `input` · `inputSchema` 는 그대로다. `input` 은 구조화된 값이라 키 기반 치환이 제대로 돌고,
  `inputSchema` 는 치환하면 AI 가 대조할 계약이 사라진다.
- **후속: 승낙 화면 문장.** "서버가 자유롭게 쓴 텍스트라 값 치환을 적용하지 않는다" 를 승낙을
  묻는 자리에 적어야 이 결정이 사용자에게 닿는다. `repair` 의 stderr 문장과 같은 계열로 맞춘다.
  `cli` 변경이라 별도 PR 로 나간다.
- **후속: CLI 가 `sensitiveValues` 를 받게 되면 재논의한다.** 지금은 CLI 에 redaction 옵션을
  만드는 경로 자체가 없다. 사용자가 비밀값을 직접 등록하는 통로가 생기면 "등록된 값만큼은
  자유 텍스트에서도 가린다" 가 다시 선택지가 된다. 그때는 이 ADR 을 개정한다.
- 앞으로 provider 로 자유 텍스트를 보내는 통로가 또 생기면 이 ADR 을 가리킨다. ADR-0033 은
  stderr 에 대한 결정으로 두고, 일반 규칙은 여기에 둔다.
