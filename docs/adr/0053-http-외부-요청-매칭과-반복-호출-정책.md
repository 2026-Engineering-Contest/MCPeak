## 배경

Replay가 저장된 외부 응답을 안전하게 돌려주려면 현재 요청이 Record 때의 어느 요청과 같은지
판정해야 한다. 너무 엄격하면 의미가 같은 요청이 miss가 되고, 너무 느슨하면 실제 외부 서비스가
다르게 처리할 요청에 잘못된 응답을 돌려주는 false hit가 된다. 테스트 도구에서는 false hit가
성공처럼 보일 수 있어 단순 miss보다 위험하다.

HTTP 요청에는 매칭에 적합하지 않은 값도 많다. `Authorization`·`Cookie`는 저장해서는 안 되고,
`User-Agent`·trace ID·요청 시각 계열 헤더는 실행마다 달라질 수 있다. 반대로 method, URL,
`Content-Type`, body를 무시하면 서로 다른 API 작업이 같은 키가 될 수 있다.

같은 요청이 한 세션에서 여러 번 발생할 수도 있다. 첫 응답을 계속 재사용하면 페이지 진행,
polling, 상태 변화처럼 호출 순서가 의미 있는 응답을 재현하지 못한다. 반대로 모든 호출의 전체
순서를 하나로 강제하면 서로 무관한 요청이 하나 추가됐을 때 뒤의 Replay가 전부 밀린다.

매칭과 반복 소비, miss, 사용하지 않은 interaction의 의미를 구현 전에 고정해야 한다.

## 선택지

### A안: 네트워크에 기록된 HTTP 바이트를 가능한 그대로 매칭한다

헤더 순서와 런타임이 자동 추가한 값까지 포함한다. false hit는 적지만 실행 환경이 조금만 달라져도
miss가 되고 비밀값 저장 위험이 크다.

### B안: 고정된 보수적 정규화 규칙과 헤더 allowlist를 사용한다

서버 동작을 구분하는 데 필요한 값만 매칭하되, 의미가 확실하지 않은 순서와 body는 과도하게
합치지 않는다. false hit를 줄이고 결과가 부족하면 명시적 miss로 드러낸다.

### C안: 사용자 정의 matcher와 부분 매칭을 1차 버전부터 제공한다

다양한 API를 맞출 수 있지만 같은 세션이 설정에 따라 다르게 재생되고, 실패 메시지가 사용자 코드에
의존한다. 결정론적 기본 동작을 검증하기 전에 확장 면이 먼저 고정된다.

## 결정

B안을 선택한다. H1·H2의 논리 프로토콜은 `http`, HTTP interaction schema version은 `1`로
시작한다. 모든 interaction은 `protocol + interactionSchemaVersion`을 저장한다. 이 version은
요청 정규화, 민감 키 목록, matchKey, outcome 저장·복원 의미를 함께 고정한다.

부모·자식 통신 형식을 나타내는 Coordinator wire schema version은 ADR-0052가 소유하는 별도
축이다. wire version 변경은 저장된 세션의 의미를 바꾸지 않고, interaction version 변경은
Coordinator endpoint 형식을 바꾸지 않는다.

### 요청 매칭 값

matchKey는 다음 정규화 값과 External domain, interaction schema version을 묶은 envelope의 stable
JSON을 UTF-8로 인코딩해 SHA-256으로 계산한다.

```ts
/**
 * matchKey 계산에만 쓰는 재료. **자식 프로세스 밖으로 나가지 않는다.**
 * 정확한 pathname 을 담으므로 이 값이 저장되면 경로에 든 비밀이 함께 저장된다.
 */
interface HttpMatchMaterialV1 {
  readonly method: string;
  /** 정확한 URL. scheme·host 정규화와 민감 query 마스킹만 적용된 상태. */
  readonly url: string;
  readonly headers: Readonly<Record<string, readonly string[]>>;
  readonly body: HttpBody;
}

interface HttpMatchKeyEnvelopeV1 {
  readonly domain: "mcpeak.external.http";
  readonly schemaVersion: 1;
  readonly match: HttpMatchMaterialV1;
}

/**
 * 경로 제거를 통과했다는 표식. 붙이는 곳은 노출 마스킹 함수 하나뿐이다.
 * symbol 키는 `JSON.stringify` 에 실리지 않으므로 저장 형식도 matchKey 입력도 바뀌지 않는다.
 */
declare const pathRedacted: unique symbol;

/**
 * 노출 마스킹을 통과한 값. 진단에 쓰는 표시용이며 **매칭에 쓰지 않는다.**
 * matchKey 가 이미 계산된 뒤이므로 여기서 무엇을 가려도 매칭 정확도는 변하지 않는다.
 * **직렬화 전, 자식 프로세스 안에서만 쓰는 타입이다.**
 */
interface HttpDisplayV1 {
  readonly [pathRedacted]: true;
  readonly method: string;
  /** `https://host/<redacted>?page=2` — 경로만 지우고 scheme·host·query 는 남긴다. */
  readonly url: string;
  readonly headers: Readonly<Record<string, readonly string[]>>;
  readonly body: HttpBody;
}

/**
 * 위 값이 JSON 이 된 모양. symbol 키는 직렬화되지 않으므로 **브랜드가 없다.**
 * wire 와 Store 에서 실제로 오가는 것은 이쪽이다.
 */
type WireHttpDisplayV1 = Omit<HttpDisplayV1, typeof pathRedacted>;

/**
 * Coordinator wire 와 Store 에 실리는 요청 전체. **매칭 재료에 해당하는 필드가 없다.**
 * 필드가 없다는 것 자체가 계약이다. 여기에 `match` 를 더하는 변경은 이 결정을 조용히 무효로
 * 만든다.
 */
interface WireHttpRequestV1 {
  readonly protocol: "http";
  readonly interactionSchemaVersion: 1;
  readonly matchKey: string;
  readonly display: WireHttpDisplayV1;
}
```

`WireHttpRequestV1`에 `match` 필드가 **없다**는 것을 저장 형식과 wire 형식의 계약으로 둔다.
후속 구현의 Coordinator 요청 타입과 Store 행은 이 모양을 따라야 하며, 매칭 재료를 실을 자리를
아예 두지 않는다. "자식이 보내지 않는다"는 행동 규칙보다 "받을 자리가 없다"는 형식 규칙이
검증하기 쉽다.

**현재 구현은 이 계약을 만족하지 않는다.** `NormalizedExternalRequest`에는 아직 `match`가 있고,
버전 필드 이름도 `interactionSchemaVersion`이 아니라 `schemaVersion`이다. 구현 PR이 `match`를
없애면서 그 필드 이름도 함께 맞춘다. 둘은 같은 축(HTTP interaction schema version)의 같은 값이라
이름만 바뀌고 의미는 바뀌지 않으며, 저장된 세션의 해석도 달라지지 않는다. 이 문단이 현재 코드의
서술이 아니라 **후속 구현의 규범**이라는 것을 여기 적어 둔다 — 그렇지 않으면 문서만 읽고 지금
경계가 안전하다고 오해할 수 있다.

`HttpMatchMaterialV1`과 `HttpDisplayV1`은 브랜드를 빼면 필드가 같다. TypeScript는 구조적 타입
시스템이므로 **이름만 나눠서는 경계가 지켜지지 않는다** — 필드가 같으면 매칭 재료가 display 자리에
그대로 들어가고 컴파일러는 아무것도 말하지 않는다. 그래서 `HttpDisplayV1`에만 `unique symbol`
브랜드를 필수 필드로 둔다. 이 필드를 붙이는 단언은 노출 마스킹 함수 한 곳에만 두고, 다른 곳에서는
`HttpDisplayV1`을 만들 수 없다.

브랜드가 사는 곳은 **직렬화 전까지**다. `JSON.stringify`는 symbol 키를 버리므로 wire 와 Store 에
실리는 것은 브랜드 없는 `WireHttpDisplayV1`이고, 부모가 `JSON.parse`로 얻는 값에도 브랜드가 없다.
그래서 타입을 둘로 나눈다 — 하나로 두면 "wire JSON 의 모양"과 "타입이 요구하는 모양"이 어긋나고,
받는 쪽은 단언 없이는 그 타입을 만들 수 없다. 브랜드의 일은 **자식 안에서** 매칭 재료가 display
자리에 들어가는 것을 막는 것이고, 경계를 넘은 뒤의 보장은 아래 부모의 재구성·거부가 맡는다.

브랜드는 컴파일 타임 방어일 뿐이라 실행 시점에는 지워진다. 계약의 실제 집행자는 테스트다.
Coordinator로 나가는 직렬화 결과와 Store에 저장된 행에 **요청 pathname 문자열이 없다**를 회귀
테스트로 고정한다. 타입이 아니라 이 검사가 "매칭 재료는 자식 밖으로 나가지 않는다"를 지킨다.

domain은 legacy Tool 카세트와 External의 해시 입력 공간을 구조적으로 분리한다. legacy matchKey의
입력과 version은 변경하지 않으며, 두 로더는 상대 형식을 받아들이지 않는다.

`HttpBody`는 tagged union이다.

```ts
type HttpBody =
  | { readonly kind: "none" }
  | { readonly kind: "json"; readonly value: JsonValue };
```

`null | JsonValue`로 두지 않는 이유가 tag의 존재 이유다. `JsonValue`가 이미 `null`을 포함하므로
그렇게 두면 **본문 없음**과 **JSON literal `null`**이 같은 matchKey가 되어 false hit가 된다.
H1이 지원하지 않는 본문(비JSON 문자열, 임의 바이트, stream, multipart)은 이 union에 들어오지
않고 Adapter가 실제 호출 전에 미지원으로 실패시킨다. 지원 범위를 넓힐 때는 union에 kind를
더하고 HTTP interaction schema version을 올린다.

정규화 규칙은 다음과 같다.

- method는 대문자로 정규화한다.
- URL은 절대 `http` 또는 `https` URL이어야 한다.
- scheme과 host는 소문자로 만들고 기본 포트(`http:80`, `https:443`)와 fragment는 제거한다.
- pathname과 query의 순서 및 percent-encoding은 **matchKey 계산에서** 1차 버전 그대로 보존한다.
  순서를 바꿔도 같다고 가정해 false hit를 만드는 것보다 miss로 드러내는 쪽을 선택한다.
- **pathname은 저장하지 않는다. 지우는 것은 경로뿐이다** — `HttpDisplayV1.url`은 scheme, host,
  그리고 아래 규칙으로 마스킹한 query를 그대로 유지하고 pathname만 `<redacted>`로 바꾼다
  (`https://host/<redacted>?page=2&token=[redacted]`). query를 함께 버리지 않는 이유는 경로와
  달리 **이름으로 판정할 수 있기 때문**이다. 민감한 값은 이름 규칙이 이미 가리므로 통째로
  버려서 얻는 것이 없고, 진단에서 같은 endpoint의 서로 다른 호출을 구분할 단서만 잃는다.
  matchKey를 계산한 뒤에 적용한다. 경로 세그먼트에는 마스킹 판정에 쓸 이름이 없어 무엇이
  비밀인지 가릴 수 없고, webhook 형태(`/services/T…/B…/XXXX`)는 경로 자체가 자격증명이다.
  가리는 시점이 **해싱 뒤**이므로 매칭 정확도는 그대로다 — `/hooks/AAA`와 `/hooks/BBB`는
  여전히 다른 matchKey다.
- 이름이 민감 키 규칙에 걸리는 query parameter 값은 matchKey 계산과 display에서 모두
  `"[redacted]"`로 바꾼다.
- 매칭 헤더 이름은 소문자로 만들고 값 앞뒤의 선택적 공백만 제거한다. 같은 이름의 값 순서는
  보존한다.
- H1의 고정 헤더 allowlist는 `accept`, `accept-language`, `content-type`, `range`다.
- `authorization`, `proxy-authorization`, `cookie`, `set-cookie`와 allowlist 밖 헤더는 match에
  들어가지 않는다. display에는 이름만 남기고 값은 마스킹하거나 생략한다.
- H1 request body는 없음 또는 UTF-8 JSON만 지원한다. JSON 객체 키는 정렬하고 민감 키의 값은
  마스킹한 뒤 matchKey 계산과 display에 사용한다.
- JSON이 아닌 문자열, 임의 바이트, stream, multipart body는 조용히 통과시키지 않고 지원 범위
  밖이라고 실패한다.
- request와 response body 상한은 각각 1 MiB다. 상한은 원본 bytes 기준이며 초과 시 일부만
  저장하지 않고 전체 interaction을 실패 처리한다.

### 민감 키 마스킹의 두 목적과 적용 지점

민감 키 판정 알고리즘은 [ADR-0039](./0039-민감-키-목록과-매칭-경계.md)의 접미 단어열 일치와
[ADR-0045](./0045-민감-키-목록의-복수형과-key-합성어.md)의 복수형 흡수를 그대로 쓴다. 키를
camelCase 경계·`-`·`_`로 단어열로 쪼개고, 소문자화와 꼬리 숫자 제거 뒤 접미 단어열이 목록과
정확히 일치할 때만 민감으로 본다. 부분 문자열 포함이 아니다. `X-Api-Key`는 걸리고
`tokenCount`는 걸리지 않는다.

`shared`는 이 순수 판정 알고리즘과 이미 배포된 값을 바꾸지 않는 version별 민감 키 목록을
제공한다. 마스킹에는 목적이 다른 두 적용 지점이 있다.

**1. 매칭 마스킹 — External 세션의 재현성을 위한 것이다.**

- Record는 지금 만드는 session의 HTTP interaction schema version에 묶인 목록을 쓴다.
- Replay는 source session에 저장된 HTTP interaction schema version의 목록을 쓴다.
- query parameter 이름과 JSON 객체 키에 같은 판정을 적용한 결과로 matchKey를 계산한다.
- 이미 배포된 version의 목록은 항목을 더하거나 빼지 않는다. 목록을 바꾸려면 `shared`에 새
  스냅샷을 추가하고 새 HTTP interaction schema version에서 채택한다. 기존 세션은 자기 version의
  목록으로 계속 해석한다. External은 `latest` 목록을 매칭에 사용하지 않는다.
- JSON body는 중첩 객체와 배열 요소까지 재귀로 훑는다. 배열 인덱스 자체는 키로 보지 않고,
  민감 키의 값이 객체나 배열이면 그 하위 트리 전체를 `"[redacted]"` 한 값으로 대체한다.
- 같은 이름의 query parameter가 여러 번 오면 순서를 보존한 채 각각을 개별적으로 마스킹한다.
  중복을 합치거나 마지막 값만 남기지 않는다.
- miss 진단에는 protocol과 interaction schema version을 포함한다. 사용자 값은 절대 포함하지
  않고, 필요한 경우 원문 키 대신 `request.body.*(api-key)` 같은 정규화된 민감 분류만 표시한다.

**2. 노출 마스킹 — 현재 보안 정책을 적용하기 위한 것이다.**

- 값이 자식 프로세스 밖으로 나가기 전, Session Store에 저장되기 전, 그리고 Store에서 읽어
  화면·리포트·번들·로그·오류 메시지로 나가기 전에 현재 런타임의 최신 목록을 쓴다.
- 순서는 항상 `matchKey 계산 → 노출 마스킹`이다. 노출 마스킹은 이미 계산한 matchKey를 바꾸지
  않는다.
- **URL pathname 제거는 이 순서에 기대는 규칙이다.** 이름 기반 판정이 닿지 않는 값이라 매칭
  마스킹으로는 다룰 수 없고, 해싱 전에 가리면 서로 다른 endpoint가 같은 키가 된다. 해싱 뒤
  노출 마스킹에서 제거하면 두 성질이 동시에 성립한다. 요청의 `display.url`과 저장 outcome의
  `url` 모두에 적용한다.
- 매칭 재료(`HttpMatchMaterialV1`)는 자식 프로세스 안에서만 존재하며 matchKey를 얻은 즉시
  버린다. Coordinator로 보내지 않고 Store에도 넣지 않는다. 그 값이 경계를 넘는 순간 이 규칙은
  무의미해진다.
- 자식 Adapter는 매칭 마스킹과 Coordinator 전송 전 최초 노출 마스킹의 권위 있는 적용자다.
  구조화된 요청과 outcome의 원문은 Coordinator로 전달하지 않는다.
- **부모는 자식이 보낸 요청을 그대로 신뢰하지 않는다.** `WireHttpRequestV1`의 알려진 필드만
  뽑아 새 값으로 재구성한 뒤 저장한다. 순서는 `재구성 → 위반 발견 시 실패`다. 재구성만으로는
  부족하다 — 모르는 필드를 조용히 버리면 값은 안전해지지만 자식이 계속 매칭 재료를 보내도
  아무도 모른다. 그래서 재구성 중 `match` 계열 필드나 알려지지 않은 필드를 발견하면 버리는
  데서 그치지 않고 **세션을 실패 처리한다.** 같은 package/build의 자식과 부모가 다른 형식을
  쓴 것이므로 아래 쓰기 직전 재검사와 같은 protocol/security 불변조건 위반으로 다룬다.
  진단에는 package/build와 schema version, 그리고 **고정된 위반 분류**(`match-field`,
  `unknown-field`)만 싣는다. 위반한 필드의 **이름도 값도 싣지 않는다.** 값이 지우려던 경로인 것은
  물론이고, 이름 역시 자식이 만든 값이라 `"https://api.example/hooks/SECRET"` 같은 키가 그대로
  올 수 있다. 값만 가리면 같은 것이 키 쪽으로 새어 나간다.
- 부모는 Store 쓰기와 외부 출력 경계의 최종 집행자다. 쓰기 직전 재검사에서 값이 추가로
  마스킹되면 같은 package/build의 자식과 부모가 다른 결과를 낸 protocol/security 불변조건
  위반이다. 원문을 저장하지 않고 세션을 실패 처리하며, 진단에는 package/build와 schema version,
  정규화된 민감 분류만 싣는다. 기대값·수신값·token·사용자 값은 싣지 않는다. ADR-0052의
  핸드셰이크가 먼저 막아야 하는 상황이므로 사용자 설정 문제가 아니라 패키지 구성 또는 구현
  오류라고 명시한다.
- 읽기 직전 재검사에서 추가 마스킹이 생기는 것은 녹화 뒤 최신 목록이 확장된 정상 상황이다.
  마스킹된 값만 반환하고 Store 원본을 되쓰지 않는다. 저장본 변경은 사용자가 후속 세션 관리
  명령으로 명시적으로 재마스킹할 때만 수행한다. 진단은 조회가 저장본을 바꾸지 않았음을 밝히고,
  해당 명령이 제공되기 전에는 안전한 최신 녹화를 만들도록 안내한다.

[ADR-0041](./0041-마스킹의-적용-경계.md)은 legacy에서 런타임 내부 원문을 유지하고 값이 프로세스
밖으로 나가는 경계에서 마스킹한다고 정했다. External은 적용 지점을 하나로 당기는 것이 아니라
서로 다른 목적으로 **두 번 적용한다**. 자식 Adapter가 matchKey 계산 전에 세션 version으로 매칭
마스킹하고, 값이 Coordinator·Store·출력 경계로 나가기 전에 최신 목록으로 노출 마스킹한다.
첫 번째는 세션 재현성, 두 번째는 현재 보안 정책을 소유한다. 0041의 legacy 적용 경계는 이 ADR이
바꾸지 않는다.

헤더 allowlist, version별 민감 키 목록, body 지원 범위는 HTTP interaction schema version의
일부다. 기본값을 조용히 바꿔 기존 session의 매칭 의미를 변경하지 않는다.

### stable JSON의 canonical 규칙

위에서 정규화하고 마스킹한 `HttpMatchKeyEnvelopeV1`을 문자열로 만드는 규칙이다. matchKey의
재현성이 여기에 달려 있으므로 아래 목록 자체를 HTTP interaction schema version 1의 고정 계약으로
둔다. 이 ADR이 정의를 소유하며, 다른 문서나 기존 구현을 정본으로 참조하지 않는다.

구현은 ADR-0051이 정한 `legacy → shared ← external` 관계를 따른다. 같은 규칙을 두 번 쓰지 않도록
stable JSON과 민감 키 판정 알고리즘은 `shared`에서 공유하되 계약은 경계마다 따로 고정한다.
stable JSON 알고리즘을 바꾸려면 영향을 받는 legacy 카세트와 External interaction version을 함께
검토한다. 민감 키 **목록**은 기존 스냅샷을 수정하지 않고 새 version을 추가하므로 legacy와
External의 version을 동반 상향하지 않는다. External은 어느 경우에도 legacy 진입점을 import하지
않는다.

- **객체 키 순서**: UTF-16 코드 단위 오름차순으로 정렬한다.
- **`undefined` 필드**: 객체에서 제거한다. `JSON.stringify`와 같다.
- **배열**: 순서를 보존한다. 원소의 `undefined`는 `null`로 쓴다. sparse array는 거부한다.
- **숫자**: `JSON.stringify`의 표기를 그대로 쓴다. 따라서 `-0`은 `0`으로 직렬화되며 **두 값을
  구분하지 않는다.** `NaN`과 `Infinity`는 저장 전에 실패시킨다.
- **문자열 escape**: `JSON.stringify`의 규칙을 그대로 쓴다.
- **중복 키**: JSON 본문을 파싱한 시점에 마지막 값만 남는다(`JSON.parse` 동작). 파싱 이후의
  객체에는 중복 키가 존재할 수 없으므로 별도 처리를 두지 않는다. 이 동작을 계약으로 고정한다.
- **순환 참조**: 거부한다.
- **해시 입력**: 직렬화 결과를 UTF-8 바이트로 인코딩해 SHA-256에 넣는다.

### 저장과 복원

- HTTP 4xx·5xx는 `throw`가 아니라 정상 `Response` 반환으로 기록한다.
- fetch 자체의 네트워크·TLS·abort 오류는 `throw` outcome으로 기록하되 런타임이 만든 자유 텍스트
  `message`, `stack`, `cause`는 저장하지 않는다. 자유 텍스트에는 키 기반 마스킹이 작동하지 않고,
  자동 저장 경로에는 ADR-0033·0049가 쓴 사용자 확인과 기본 거부가 없기 때문이다.
- HTTP interaction schema version 1의 `throw` outcome은 아래 안전한 envelope만 허용한다.

```ts
interface StoredHttpThrowV1 {
  readonly kind: "throw";
  readonly failureKind:
    | "abort"
    | "timeout"
    | "dns"
    | "connection"
    | "tls"
    | "network"
    | "unknown";
  readonly name: "Error" | "TypeError" | "AbortError";
  readonly code?:
    | "ABORT_ERR"
    | "CERT_HAS_EXPIRED"
    | "DEPTH_ZERO_SELF_SIGNED_CERT"
    | "EAI_AGAIN"
    | "ECONNREFUSED"
    | "ECONNRESET"
    | "ENOTFOUND"
    | "ERR_TLS_CERT_ALTNAME_INVALID"
    | "ETIMEDOUT"
    | "SELF_SIGNED_CERT_IN_CHAIN"
    | "UNABLE_TO_VERIFY_LEAF_SIGNATURE"
    | "UND_ERR_CONNECT_TIMEOUT";
}
```

- 오류 분류는 Adapter가 소유한 timeout·abort 상태와 런타임 오류의 구조화된 `name`, 최상위
  `code`, `cause.code`만 입력으로 쓴다. 문자열 `message`, `stack`, `cause` 본문은 판정하거나
  저장하지 않는다. 여러 단서가 동시에 있으면 아래 표의 위쪽 항목을 선택한다.

| 우선순위 | `failureKind` | 허용된 판정 단서 |
|---:|---|---|
| 1 | `timeout` | Adapter가 만든 timeout 표식, `name === "TimeoutError"`, `ETIMEDOUT`, `UND_ERR_CONNECT_TIMEOUT` |
| 2 | `abort` | timeout이 아닌 요청 `AbortSignal`의 중단, `name === "AbortError"`, `ABORT_ERR` |
| 3 | `dns` | `EAI_AGAIN`, `ENOTFOUND` |
| 4 | `tls` | `CERT_HAS_EXPIRED`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `ERR_TLS_CERT_ALTNAME_INVALID`, `SELF_SIGNED_CERT_IN_CHAIN`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE` |
| 5 | `connection` | `ECONNREFUSED`, `ECONNRESET` |
| 6 | `network` | 요청 정규화·지원 범위 검증을 통과한 뒤 네이티브 `fetch`가 낸 `TypeError`이며 위 단서가 없음 |
| 7 | `unknown` | 위 allowlist에 해당하는 구조화된 단서가 하나도 없음 |

timeout이 abort로도 보이는 런타임 차이를 흡수하기 위해 timeout을 먼저 둔다. 선택된
`failureKind`와 같은 행에 속한 `code`만 저장하고, 다른 행의 code는 생략한다. `name`도 위
allowlist로 정규화한다. 같은 failureKind의 허용 code가 최상위 `code`와 `cause.code`에 모두 있으면
최상위 값을 저장하고, 최상위 값이 선택된 kind에 속하지 않을 때만 `cause.code`를 쓴다. 둘 다 선택된
kind에 속하지 않으면 code를 생략한다. 입력 `TimeoutError`는 저장 시 `Error`로 낮춘다. Replay
message는 오직
`failureKind`에 대응하는 MCPeak 고정 문장으로 만든다. Record에서는 원래 오류를 MCP 서버 코드에
다시 던지지만, Replay에서 원본 message 텍스트에 의존하는 서버 동작은 H1·H2 지원 범위가 아니다.
- response는 status, statusText, headers, 최종 URL, UTF-8 JSON body를 저장한다. 이 다섯 필드는
  모두 Replay 복원 계약이며 statusText를 진단 전용으로 낮추지 않는다. 최종 URL의 민감
  query, 민감 header 값, JSON body의 민감 키 값은 Coordinator 전송 전에 최신 목록으로 노출
  마스킹한다.
- interaction에 **녹화 시각**(`begin` 도착 시점, UTC ISO 8601)을 함께 저장한다. 세션이 언제
  만들어졌고 얼마나 낡았는지는 진단의 기본 정보이며, 아래 §결과의 드리프트 비목표를 나중에
  다룰 때의 입력이기도 하다. 다만 **matchKey 입력에는 넣지 않는다.** 넣으면 같은 요청이
  실행마다 다른 키가 되어 Replay가 전부 miss가 되고, 결정론성도 함께 깨진다. 시각은
  표시·진단용 메타데이터다.
- 상태 코드는 body 지원성보다 먼저 관찰하되, status만으로 outcome 종류를 바꾸지 않는다. Adapter는
  실제 응답을 clone해 `application/json` 또는 `application/*+json` content type과 UTF-8 JSON parse를
  확인한 뒤에만 `complete`한다. JSON인 4xx·5xx는 2xx와 같은 정상 `Response` outcome으로 저장한다.
  status와 무관하게
  비-JSON·잘못된 UTF-8·parse 실패·stream·redirect 응답은 `UnsupportedHttpResponseError`
  (`UNSUPPORTED_HTTP_RESPONSE`)로 실패하고 interaction을 incomplete, 현재 Record session을 `failed`로
  둔다. 실제 응답 원문을 서버 코드에 반환하거나 unsupported outcome을 저장하지 않는다.
- **redirect 판정은 상태 코드로 한다.** `response.redirected`는 런타임이 자동으로 따라간 경우에만
  `true`다. 서버 코드가 `redirect: "manual"`로 호출하면 301·302·303·307·308 응답이
  `redirected === false`인 채로 돌아오고, JSON 본문을 달고 있으면 위 검사를 모두 통과해 정상
  outcome으로 저장된다. 그 응답의 `Location` 값은 **경로가 든 절대 URL**이라 이 ADR이 지운 경로가
  응답 쪽으로 되돌아온다. 그러므로 이 다섯 상태 코드는 `redirected` 값과 무관하게
  `UNSUPPORTED_HTTP_RESPONSE`로 거부한다. `redirected === true`도 함께 거부한다 — 자동 추적된
  경우를 덮는 검사다. **3xx 전체가 아니라 이 다섯 개다.** `300`과 `304 Not Modified`는
  리다이렉트가 아니므로 이 규칙의 대상이 아니다. 다만 `304`는 본문이 없어 위의 JSON 본문
  규칙에서 따로 걸린다. 본문 없는 응답의 지원은 이 개정의 범위가 아니고 HTTP interaction
  schema 확장 검토 대상이다.
- **URL을 담는 응답 헤더에도 같은 경로 제거를 적용한다.** `location`과 `content-location`은 이름
  기반 민감 키 판정에 걸리지 않아 원문 그대로 저장된다. 저장 outcome의 `url`과 같은 규칙으로
  `https://host/<redacted>`로 만든다. 이 둘까지 넣어야 §결과가 말하는 **표준 URL 필드 넷**이
  채워진다. 값 **안에** URL을 담는 `Link`·`Refresh`는 문법이 달라 아래 별도 항목으로 다룬다.
- **두 헤더는 절대 URL이 아닐 수 있다.** RFC 9110은 상대 참조를 허용하므로 `201 Created`가
  `Location: /hooks/SECRET`을 보낼 수 있고, 이 응답은 3xx가 아니라 위 redirect 거부 규칙에
  걸리지 않는다. 상대 참조를 **거부하지 않고 응답 URL을 기준으로 해석한 뒤 경로를 제거한다.**
  거부하면 상대 `Location`을 쓰는 정상적인 생성 응답이 통째로 실패하는데, 그건 이 개정이 사려던
  것이 아니다. 해석은 저장 전 노출 마스킹 단계에서 하므로 matchKey에는 영향이 없다.
  protocol-relative(`//other.host/p`)도 해석하면 host가 제대로 잡힌다.
- **값 안에 URL을 담는 헤더 — `Link`·`Refresh` — 는 문법을 해석해 URL 부분만 경로를 지운다.**
  2026-08-22 개정은 이 둘을 범위 밖으로 두고, "`Link` 헤더로 자격증명을 넘기는 API가 흔하다고
  드러나면" 다시 다루기로 했다. [#301](https://github.com/2026-Engineering-Contest/MCPeak/issues/301)
  에서 그 조건을 판단했다. **"흔하다"는 사례 통계로는 답하지 못했고, 답할 필요도 없었다.**
  근거는 통계가 아니라 헤더의 정의다. pagination `Link`(`rel="next"`·`rel="prev"`)는 서버가
  **요청 URL을 되돌려 만든다** — 요청 경로에 자격증명이 있으면 그 응답의 `Link`에 같은 경로가
  반드시 실린다. Slack·Discord webhook처럼 경로가 자격증명인 endpoint가 `Link`로 pagination하는
  순간 이 개정이 지운 경로가 응답 쪽으로 되돌아오고, 그것은 API의 유행이 아니라 `Link`가 무엇인지에서
  따라 나오는 결과다. `Refresh`는 `url=`에 URI를 담으므로 `Location`과 같은 부류다. 두 헤더의
  값은 이름으로 판정할 수 없다는 앞 개정의 진술은 맞지만, **이름이 아니라 문법으로 URL 자리를
  찾을 수 있다**는 것이 그때 보지 않은 점이다.
  - 세 선택지를 봤다. (A) 그대로 둔다 — 잔여 유출 경로가 남고 README가 한계를 계속 이고 간다.
    (B) 두 헤더를 통째로 `[redacted]` — 가장 싸지만 `rel="next"`가 사라져 "이 응답이 다음
    페이지를 가리켰는가"라는 pagination 진단을 잃는다. (C) 문법을 해석해 URI 부분만 지우고
    파라미터는 남긴다. **C를 고른다.** `Link` 문법(쉼표 구분 link-value, `<URI>` 뒤 `;` 구분
    파라미터, quoted-string)은 작은 토크나이저로 충분하고, 해석에 실패하는 값은 B와 같이
    통째로 가리면 되므로 C의 실패 모드가 B보다 나쁘지 않다.
  - `Link` 파라미터는 **`rel` 하나만, 그것도 값이 등록된 고정 집합(`next`·`prev`·`previous`·
    `first`·`last`·`self`·`alternate`·`canonical`·`collection`·`item`·`up`·`related`·`describedby`·
    `edit`·`hub`·`search`·`service`·`via`) 안일 때만** 원문으로 남기고, 그 밖의 `rel` 값과 다른
    파라미터는 전부 `이름=[redacted]`로 쓴다. 처음 초안은 `rel`·`type`·`hreflang`·`media`·
    `title`·`title*`를 이름 허용 목록으로 원문 보존했는데, 리뷰가 짚었듯 파라미터 **값**은 문법상
    임의 문자열이다 — `title="sk_live_…"`나 `rel="Bearer TOKEN"`도 문법에 맞는다. 이름으로도
    문자 집합으로도 토큰을 가려낼 수 없으므로, 남길 수 있는 것은 값 자체가 유한 집합인 것뿐이다.
    진단이 필요로 하는 "이 응답이 다음 페이지를 가리켰는가"는 그 집합으로 답해진다. `anchor`는
    URI-Reference를 담고 확장 파라미터는 무엇이든 담을 수 있으므로 애초에 후보가 아니다. 리뷰에서 "거부 목록은 다음에 또 같은 헤더가 새로
    생긴다"는 지적이 있었다. 헤더 **이름** 쪽은 여전히 `location`·`content-location`·`link`·
    `refresh` 네 개를 명시하는 목록이다 — 응답 헤더 전체를 허용 목록으로 바꾸면 Replay가 돌려줄
    헤더가 사라져 ADR-0041의 "마스킹은 테스트가 보는 값에만 닿는다"를 넘어선다. 대신 새 헤더
    하나를 넣는 비용을 `storedHeaderValue` 한 함수의 분기 하나로 낮추고, 자식의 최초 저장과
    부모의 재검사가 그 함수를 **공유**하게 해 두 곳의 규칙이 갈라질 수 없게 했다.
  - `Refresh`는 HTML 명세 문법(지연 초, 선택적 `;`/`,` 뒤 `url=` 과 따옴표 허용 URL)을 따른다.
    지연 초는 남기고 URL만 위 규칙으로 지운다. `url=`이 없으면 지연 초만 저장한다.
  - 두 변환 모두 **자기 출력에 다시 적용하면 같은 값**이어야 한다. ADR-0052의 Store 직전
    재검사는 부모가 자식의 출력에 마스킹을 한 번 더 걸어 바이트 비교하는 것이라, 멱등이 깨지면
    자식이 올바르게 한 출력을 위반으로 잘못 잡는다.
- 저장 outcome의 `url`에도 요청과 같은 pathname 정책을 적용한다. 응답의 `url`은 요청 URL을
  그대로 반영하므로, 요청에서만 경로를 지우면 응답 쪽으로 같은 값이 새어 나간다.
- Adapter는 Replay에서 `Response`의 `status`, `statusText`, 마스킹된 `headers`, 마스킹된 UTF-8 JSON
  `body`, 관찰 가능한 `url`을 복원해야 한다. 복원되는 `url`은 저장본과 같은 경로 제거 상태이며,
  **서버 코드가 `response.url`의 경로를 읽어 동작을 바꾸면 Replay와 실제 실행이 갈린다.** 그런
  서버는 1차 지원 범위 밖이다. 복원 결과가 녹화된 `url`, `status`, `statusText`, `ok`,
  header 값과 JSON body를 노출하고 `instanceof Response`를 유지하는 것을 테스트 가능한 계약으로
  둔다. 복원 메커니즘은 구현 PR에서 선택한다. 대상 런타임에서 이 계약을
  만족할 수 없으면 비슷한 값을 조용히 반환하지 않고 `ReplayRuntimeUnavailableError`
  (`REPLAY_RUNTIME_UNAVAILABLE`)를 낸다. 이 오류는 저장 outcome이 정상이고 match도 성공했지만 현재
  런타임이 위 `Response` 복원 계약을 제공할 수 없는 경우에만 쓴다. 필요한 occurrence가 없는 경우는
  `ReplayMissError`, 저장 interaction의 필수 필드 누락·형식 위반·incomplete 상태는 손상 오류로
  구분하고 런타임 미지원으로 낮추지 않는다. 서버 코드가
  `response.url`을 읽는데 빈 문자열이 오면 그것은 Replay가 아니라 조용한 오답이다.
- Record에서는 실제 응답 원문을 MCP 서버 코드에 반환하지만 저장본은 마스킹 경계를 통과한다.
  Replay에서는 Store에서 읽은 outcome에 현재 노출 마스킹을 적용한 값을 반환한다. 기존 세션의
  matchKey와 occurrence 호환성은 유지되지만, 보안 목록이 확장되면 Replay의 관찰 가능한 응답
  일부가 추가로 마스킹될 수 있다. 현재 보안 정책이 과거 응답의 완전한 동일성보다 우선한다.
  비밀 응답 값에 의존하는 서버 동작은 H1·H2 지원 범위가 아니며 이 제한은 실행 전에 표시한다.
  읽기 중 Store 원본은 수정하지 않는다.

### 반복 호출과 순서

반복 소비 키는 `sourceSessionId + protocol + matchKey`다. 같은 키의 Record 호출마다
`occurrence`를 `0`부터 하나씩 부여하고, Replay에서도 `0`부터 순서대로 소비한다.

Record는 실제 외부 호출 전에 Coordinator에서 interaction 자리를 예약한다.

```text
요청 정규화
  → Coordinator begin: ordinal·occurrence·interactionId 예약
  → 실제 fetch
  → 결과 encode·마스킹
  → Coordinator complete: 저장
```

이 순서로 해야 외부 호출은 성공했는데 Coordinator가 이미 죽어 기록할 수 없는 상황을 호출 전에
막고, 응답 완료 순서가 아니라 호출 시작 시점에 occurrence를 정할 수 있다. begin 뒤 자식이
죽으면 interaction은 incomplete이고 source session은 성공한 Replay 원본으로 선택할 수 없다.

순서의 기준은 두 값이 다르다.

- `occurrence`는 같은 `sourceSessionId + protocol + matchKey` 안에서의 번호다. 같은 matchKey의
  동시 호출은 아래에서 지원하지 않으므로, 이 키 안에서는 호출 시작 순서와 Coordinator 도착
  순서가 같다. 매칭에 쓰는 값은 이것뿐이다.
- `ordinal`은 세션 전체의 순서이고, 기준은 **Coordinator가 begin을 받은 도착 순서**다. `begin`은
  비동기 loopback 통신이고 client sequence를 싣지 않으므로, 서로 다른 matchKey의 동시 호출에서는
  서버 코드가 호출을 시작한 순서와 다를 수 있다. `ordinal`은 진단·표시용이며 매칭 입력이 아니다.
  Coordinator가 도착 시점에 단조 증가 값을 원자적으로 부여한다.

동일 matchKey의 호출이 앞 호출의 complete 전에 다시 begin되는 동시 호출은 H1·H2에서
지원하지 않는다. Coordinator가 실제 외부 호출 전에 명시적 오류를 반환한다. 서로 다른
matchKey의 호출은 동시에 진행할 수 있다.

### Replay hit와 miss

- Replay source session ID는 사용자가 명시한다. `최근 성공 세션`을 자동 선택하지 않는다.
- hit이면 해당 occurrence의 저장 outcome을 반환하고 소비 표시한다.
- 필요한 occurrence가 없으면 실제 외부 호출 없이 `ReplayMissError`(`REPLAY_MISS`)로 실패한다.
- 구조적으로 유효하지만 현재 런타임이 지원하지 않는 protocol 또는 interaction schema version은
  `ReplaySchemaUnsupportedError`(`REPLAY_SCHEMA_UNSUPPORTED`)로 실패한다. 필수 필드 누락·형식 오류·
  incomplete interaction은 `ReplayDataCorruptionError`(`REPLAY_DATA_CORRUPT`)로 실패한다. 어느 경우도
  miss로 낮추거나 최신 version으로 fallback하지 않는다.
- source session에 남은 미사용 interaction은 실행 실패로 만들지 않는다. 녹화 때와 다른 테스트
  명세도 일부 interaction을 재사용할 수 있어야 하기 때문이다.
- 미사용 interaction은 세션 종료 시 protocol, 표시 가능한 요청, 남은 occurrence 수를 포함한
  경고로 요약한다.
- Replay session 안에서 같은 저장 occurrence를 두 번 반환하지 않는다.

사용자 정의 matcher, 단일 응답 무한 재사용, miss의 실제 네트워크 fallback, `auto` 모드는
H1·H2에서 제공하지 않는다.

## 이유

보수적 정규화는 같은 것으로 확신할 수 있는 요청만 합친다. query나 opaque body를 공격적으로
정규화하면 hit율은 올라가지만 실제 서버가 다르게 처리할 요청을 같은 것으로 볼 수 있다. Replay의
목적은 빠른 응답이 아니라 같은 외부 조건의 재현이므로 miss가 false hit보다 낫다.

헤더 allowlist는 비밀값과 실행별 잡음을 기본적으로 배제한다. 사용자가 matcher 코드를 넣게 하지
않으므로 같은 session과 요청은 어느 환경에서도 같은 키를 만든다. 지원할 헤더가 늘면 HTTP
interaction schema version을 통해 명시적으로 확장한다.

반복 응답을 순서대로 소비하면 polling과 상태 변화를 재현할 수 있다. 전체 session ordinal이 아니라
matchKey별 occurrence를 쓰므로 무관한 외부 요청이 추가돼도 다른 키의 Replay가 전부 밀리지 않는다.
source session을 명시하게 하는 것도 같은 이유다. 자동으로 최근 값을 고르면 같은 명령이 실행
시점에 따라 다른 데이터를 읽는다.

남은 interaction을 실패로 만들지 않는 이유는 이 기능의 목적 자체가 **코드를 바꾼 뒤의 재실행**
이기 때문이다. MCP 서버 코드가 바뀌면 호출하는 외부 요청의 집합도 줄거나 달라지는데, 그때마다
"녹화 때 쓰던 요청이 남았다"를 실패로 만들면 세션은 녹화 시점의 코드에서만 쓸 수 있는 일회용이
된다. 그래서 남은 것은 경고로 요약한다. 반대로 필요한 interaction이 없는 miss는 실제 네트워크로
빠지는 순간 Replay가 아니므로 반드시 실패한다.

## 결과

- **표준 URL 필드와 URL을 담는 헤더에서 경로가 사라진다.** 보장 범위는 요청 `display.url`, 저장
  outcome의 `url`, `location`·`content-location` 헤더 값, 그리고 `link`의 각 `<URI>`와 `refresh`의
  `url=`이다. 경로에 자격증명을 담는 endpoint를 녹화해도 이 자리로는 그 값이 저장되지 않는다.
  `link`의 등록된 `rel` 값과 `refresh`의 지연 초는 원문으로 남으므로 pagination 진단은 잃지
  않는다. 그 밖의 `link` 파라미터 값(이름 불문)과, 문법으로 해석되지 않는 `link`·`refresh` 값
  전체는 `[redacted]`다.
- **JSON body 안의 URL은 이 개정이 다루지 않는다.** pagination의 `next`, HATEOAS 링크 같은
  문자열은 이름으로도 문법으로도 URL 자리를 가릴 수 없어 그대로 저장된다. 그러므로 **"세션 파일
  어디에도 경로가 없다"고 말하지 않는다.** 말할 수 있는 것은 위 자리까지다.
  [#256](https://github.com/2026-Engineering-Contest/MCPeak/pull/256)이 "경로는 안 가려진다"를
  한계로 문서화하려다 닫힌 것과는 다른 판단이다. 그때 미룬 것은 **주된** 유출 경로였고, 여기서
  남기는 것은 표준 필드와 헤더를 모두 막은 뒤의 **잔여** 경로다. `Link`·`Refresh`는 2026-08-22
  개정에서 이 잔여에 속했다가 2026-08-23 개정에서 결정으로 다시 다뤘다(§결정). JSON body의
  URL도 같은 길을 갈 수 있다 — 예컨대 body 안 URL 문자열을 값의 **형태**(절대 URL로 파싱됨)로
  찾아 지우는 것이 매칭·Replay를 깨지 않는다고 드러나면 — 그때도 한계가 아니라 결정으로 다룬다.
- **진단이 약해진다.** miss·incomplete 메시지가 `GET https://api.example.com/<redacted>`까지만
  말한다. 같은 host의 여러 endpoint를 구분하려면 함께 표시하는 matchKey를 봐야 한다. 진단에 싣는
  앞 12자는 **식별 힌트일 뿐 유일 식별자가 아니다.** 해시 앞자리는 충돌하지 않는다는 보장이 없어
  서로 다른 두 호출이 같은 앞자리로 보일 수 있다. 확실히 구분해야 하면 함께 제공하는 전체
  matchKey를 본다.
- 축약 길이를 세션 내용에 따라 늘리는 방식은 **쓰지 않는다.** miss 진단은 Record 실행 **중**에
  나오는데 그 시점에는 세션의 matchKey 집합이 아직 확정되지 않아, 같은 실행이라도 진단이 나온
  시점에 따라 다른 문자열이 된다. 고엔트로피 세그먼트 휴리스틱을 거절한 것과 같은 이유다 —
  결정론성이 이 기능의 존재 이유다.
- **녹화한 요청을 실서버에 다시 보낼 수 없다.** 정확한 URL이 없기 때문이다. legacy `verify`가
  하는 드리프트 확인을 External에 그대로 옮기는 경로가 막힌다. 이미 요청 body의 민감 값이
  마스킹되어 legacy `verify`도 그런 요청을 `skipped`로 보고하므로 새로 생기는 손실은 "경로에
  비밀이 없는 URL도 재검증 불가" 하나다. 드리프트 확인이 필요해지면 재검증이 아니라
  **재녹화**로 다룬다.
- 매칭 재료가 자식 밖으로 나가지 않는다는 것은 **구현 불변조건**이고, 방어가 세 겹 필요하다.
  타입을 나누는 것만으로는 막지 못하기 때문이다 — 구조적 타입이라 필드가 같으면 그대로 대입된다.

  | 겹 | 무엇을 막나 | 어긋나면 |
  |---|---|---|
  | `WireHttpRequestV1`에 `match` 자리 없음 | 실을 곳 자체가 없다 | — |
  | `HttpDisplayV1`의 `unique symbol` 브랜드 | 자식 안에서 매칭 재료를 display 자리에 대입 | 컴파일 오류 |
  | 부모의 재구성 뒤 위반 거부 | 자식이 그래도 보낸 경우 | 세션 실패 |

  여기에 직렬화 결과와 저장 행에 요청 pathname이 없다는 회귀 테스트를 더한다. 세 겹 중 앞의 둘은
  컴파일 타임에만 살아 있으므로, 실행 시점을 지키는 것은 부모의 거부와 이 테스트다.
- **이 개정 전에 만든 세션 파일은 마이그레이션하지 않고 삭제하고 다시 녹화한다.** 기술적으로는
  마이그레이션이 가능하다 — matchKey가 이미 저장돼 있어 `match`를 떼고 `display.url`을 지워도
  Replay는 계속 동작한다. 그래도 재녹화를 택하는 이유는 두 가지다. 그 파일은 **이미 유출된
  파일**이라 커밋됐다면 삭제해도 git 히스토리에 남고, 한 번 쓰고 버릴 변환 도구를 만드는
  값어치보다 다시 녹화하는 쪽이 싸다.
- **파일을 지우는 것으로 끝나지 않는다.** 경로에 들어 있던 자격증명은 이미 노출된 값이므로
  폐기하고 재발급한다. 이 안내가 없으면 사용자는 파일만 지우고 안전해졌다고 믿는다.
- 경로를 **해싱 전에** 가리는 변경은 서로 다른 endpoint를 같은 matchKey로 만든다. 회귀
  테스트가 그 등가성을 금지한다.
- H1·H2는 Node 내장 `fetch`의 GET·POST와 JSON API에 집중한다.
- binary, 일반 text, stream, multipart, redirect 지원은 HTTP interaction schema 확장 검토
  대상이다.
- 같은 URL이라도 query 순서나 JSON이 아닌 body가 다르면 자동으로 합쳐지지 않는다.
- 비밀값 마스킹으로 인해 서로 다른 자격증명 요청이 같은 키가 될 수 있으므로 source session은
  하나의 격리된 테스트 계정·환경에서 만든다는 전제가 생긴다.
- 동시 동일 요청은 1차 미지원이며 직렬 호출로 바꾸라는 진단을 제공해야 한다.
- Coordinator에 begin·complete 두 단계와 incomplete interaction 상태가 필요하다.
- Replay 종료 보고에 미사용 interaction 경고가 추가된다.
- **이 기능은 외부 API 자체의 드리프트를 감지하지 않는다.** Replay는 저장된 응답을 돌려주므로,
  실제 API가 바뀌어도 세션이 낡았다는 사실은 드러나지 않고 테스트는 계속 통과한다. H1·H2의
  비목표로 두고, 감지 수단은 후속 결정으로 남긴다. 저장된 녹화 시각이 그 판단의 입력이 된다.
- 테스트는 query 순서, 헤더 allowlist, JSON key 순서, version별 민감 목록 불변성, 매칭·노출
  이중 마스킹, External hash domain, 반복 호출, strict miss, 미사용 interaction, 동일 키 동시
  호출, 안전한 `throw` envelope, 복수 오류 단서의 분류 우선순위·같은 kind의 최상위 code 우선·
  `unknown` fallback, JSON·비-JSON 4xx·5xx, 읽기 무변경,
  `Response` 복원의 `url`·`status`·`statusText`·`ok`·마스킹된 headers·UTF-8 JSON body·
  `instanceof Response`, 복원 계약을 만족할 수 없는 런타임의 `ReplayRuntimeUnavailableError`·
  `REPLAY_RUNTIME_UNAVAILABLE`, Coordinator 직렬화 결과와 저장 행에 요청 pathname이 없음,
  자식이 `match` 계열 또는 미지의 필드를 보냈을 때 부모가 재구성 뒤 세션을 실패시킴,
  그 진단에 동적 필드 이름이 나오지 않고 고정 분류만 나옴,
  `location`과 `content-location` **각각**에 대해 상대 참조(`/p`, `//other.host/p`)가 응답 URL
  기준으로 해석된 뒤 저장값에서 경로가 제거됨 — 한 헤더만 처리해도 통과하는 조건을 두지 않는다,
  `link`의 각 `<URI>`(상대 참조 포함)에서 경로가 제거되고 등록된 `rel` 값은 남으며 그 밖의 `rel`
  값과 다른 파라미터 값은 이름이 무엇이든 가려짐(`title`·`title*`·확장 파라미터에 실린 토큰이
  저장본에 없음), 문법에 맞지 않는 `link`가 통째로 가려짐, `refresh`의 지연 초가 남고
  `url=`의 경로가 제거됨, `link`·`refresh` 저장값에 재검사를 다시 적용해도 같은 값임,
  `redirected === false`인 301·302·303·307·308의 거부, `300`·`304`가 redirect 규칙으로는 거부되지
  않음, `location`·`content-location`의 경로 제거, 그리고 occurrence 없음·schema 미지원·저장 손상을
  서로 구분하고 어느 경우도 최신 version으로 fallback하지 않는 오류 분류를 각각 고정해야 한다.
- 이 ADR 번호는 병합 직전에 다시 확인하고 충돌 시 파일명, 제목, 색인 링크를 함께 재번호한다.
