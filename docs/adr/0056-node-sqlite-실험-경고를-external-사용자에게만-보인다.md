# ADR-0056: `node:sqlite` 실험 경고는 External 사용자에게만 보이고, 그 이상 숨기지 않는다

- 상태: 채택
- 날짜: 2026-08-22
- 담당: record, cli
- 작성자: @ddxng5 (② replay/record 파트)
- 승인: 승인 (2026-08-22, @ddxng5)
- 선행 결정:
  [ADR-0052](./0052-coordinator가-engine과-session-store를-소유한다.md),
  [ADR-0054](./0054-node-js-최소-지원-버전을-22-18로-올린다.md)
- 참조: 이슈 [#228](https://github.com/2026-Engineering-Contest/MCPeak/issues/228)

## 배경

[ADR-0054](./0054-node-js-최소-지원-버전을-22-18로-올린다.md)가 이 결정을 열어 두었다.

> SQLite의 런타임 경고를 없애기 위해 프로세스의 전체 warning listener를 제거하지 않는다.
> 경고 정책이 필요하면 SQLite 구현과 함께 별도로 결정한다.

SQLite Session Store가 들어오면서 그 시점이 됐다. 실측한 사실은 다음과 같다.

| 런타임 | `node:sqlite` 로드 시 |
|---|---|
| Node 22.18.0 | `node:sqlite` 를 처음 로드할 때 stderr 에 `ExperimentalWarning: SQLite is an experimental feature and might change at any time` |
| Node 24.16.0 | 아무것도 찍지 않는다 |

측정한 것은 위 **두 버전**이다. "Node 24 이상은 조용하다" 로 일반화하지 않는다 — 경고가 어느
패치에서 빠졌는지 확인하지 않았다. `tsdown@0.22.14` 가 요구하는 `>=24.11.0` 은 **빌드 도구의
지원 범위**이지 이 측정과 무관하다.

CI 의 22.18 잡 로그에서 확인했고, 저장소의 최소 버전이 22.18 이므로 **지원 범위 안에서 뜨는 경고**다.

그리고 처음 배선했을 때는 이 경고가 **External 을 쓰지 않는 실행에도 붙었다.** `cli` 가 배선
모듈을 정적 import 했고 그것이 `node:sqlite` 를 모듈 로드 시점에 끌어왔기 때문이다. `build`
잡의 `dist-cli-e2e`("빌드된 CLI 는 stderr 에 아무것도 쓰지 않는다")가 이것을 잡았다.

## 선택지

- **A안**: 그대로 노출한다. 아무것도 하지 않는다.
- **B안**: 프로세스 전역 warning 을 끈다(`--no-warnings`, listener 제거).
- **C안**: 그 경고 한 줄만 골라 거른다.
- **D안**: 최소 런타임을 Node 24 로 올린다.
- **E안**: External 을 실제로 쓸 때만 모듈을 불러 경고 범위를 좁히고, 그 이상은 숨기지 않는다.

## 결정

**E안**을 택한다.

1. `cli` 는 `@mcpeak/record/external` 을 **동적으로 불러온다.** 세션 옵션(`--session`,
   `--record-session`)이 실제로 쓰일 때만 로드한다. 그 결과 경고를 보는 사람은 External 을
   직접 켠 사용자뿐이다.
2. **그 이상 숨기지 않는다.** 경고 필터를 넣지 않고, `--no-warnings` 를 붙이지 않으며,
   ADR-0054 대로 프로세스 전역 warning listener 도 건드리지 않는다.
3. `record` 패키지는 프로세스 전역 상태를 **어느 경우에도** 바꾸지 않는다. 라이브러리가
   호출자의 전역을 조작하지 않는다는 경계를 유지한다.
4. 이 경고는 사용자 데이터의 위험 신호가 **아니라는** 사실을 문서에 적는다. `node:sqlite` 가
   만드는 파일은 헤더가 `SQLite format 3` 인 표준 SQLite 파일이며, Node 의 API 표면이 바뀌어도
   그 파일은 그대로 읽힌다.
5. 최소 런타임을 Node 24 로 올리는 것은 이 경고를 이유로는 하지 않는다.

## 이유

**External 을 쓰지 않는 사용자는 이 경고의 수신자가 아니다.** 그는 SQLite 가 쓰인다는 사실조차
모르고, 끌 수도 없고, API 가 바뀌어도 그의 실행은 무관하다. 행동으로 옮길 수 없는 경고는
정보가 아니라 소음이다. 처음 배선이 그에게까지 경고를 보냈고, 그것이 이 결정을 필요하게 만든
문제다.

**External 을 켠 사용자는 수신자가 맞다.** 그는 실험적 기능 위에서 도는 저장소에 자기 녹화를
남기기로 선택한 사람이고, 그 사실을 아는 것이 그의 판단에 들어간다. 그래서 범위를 좁히는 것과
완전히 숨기는 것은 다른 결정이며, 여기서는 앞의 것만 택한다.

**그런데 문구는 사용자 데이터가 불안정하다고 읽힌다.** "experimental … might change at any
time" 을 본 사람은 자기 녹화가 위험하다고 이해한다. 실제로는 표준 SQLite 파일이라 안전하다.
잘못 읽히는 경고를 관계없는 사람에게까지 보내는 것이 가장 나쁜 조합이라, 범위를 좁히는 것이
먼저다.

**그럼에도 완전히 숨기지 않는 이유는 우리가 그 위험을 대신 지기 때문이다.** 경고를 지우는
것은 "이 API 가 바뀌어도 우리가 책임진다" 는 선언이다. 그 책임을 실제로 지는 장치는 계약
테스트(`session-store-contract.test.ts`, 21개 스펙 × 2 구현)이며 22.18·24 양쪽 매트릭스에서
돈다. 다만 그 장치가 있다고 해서 **사용자가 자기 런타임의 상태를 아는 것까지 막을 이유는
없다.** 켠 사람에게 한 줄 보이는 비용은 작고, 지웠을 때 잃는 것은 "지금 실험적 기능 위에서
돌고 있다" 는 사실 자체다.

B안을 버린 이유는 명확하다. 전역 warning 을 끄면 사용자 서버가 쓰는 다른 experimental 기능의
경고까지 삼킨다. 그것은 사용자가 행동할 수 있는 정보다. C안은 그보다 좁지만 여전히 우리가
사용자 대신 판단하는 것이고, E안이 이미 문제의 대부분(관계없는 사람에게 가는 것)을 해소한 뒤
남는 이득이 작다.

D안은 비용이 맞지 않는다. Node 22 는 2027년까지 LTS 이고, 최소 버전을 22.18 로 올린
[#231](https://github.com/2026-Engineering-Contest/MCPeak/pull/231)이 방금 나갔다. 경고 한 줄을
이유로 연속 breaking 릴리스를 내고 지원 범위를 좁히는 것은 사용자에게 더 큰 비용이다.

## 결과

- `cli` 의 External 배선은 동적 import 를 쓴다. 정적 import 로 되돌리면 경고가 전체 실행으로
  번지며, `build` 잡의 `dist-cli-e2e` 가 그것을 잡는다.
- 경고는 프로세스가 `node:sqlite` 를 **처음 로드할 때 한 번** 나온다. 세션 수와 무관하다 —
  모듈 로드가 프로세스당 한 번이기 때문이다. `mcpeak test` 한 번은 프로세스 하나이므로
  세션 옵션을 쓴 실행당 최대 한 줄이 된다.
- 22.18.0 에서 나오고 24.16.0 에서 나오지 않는 것을 실측했다. 그 사이 버전은 재지 않았으므로
  "22 대는 나오고 24 대는 안 난다" 로 일반화하지 않는다.
- 이 두 가지는 `packages/record/README.md` 와 `mcpeak help test` 에 적었다 — 경고를 남겨
  두기로 한 이상, 그것이 무엇이고 무엇이 아닌지는 설명되어 있어야 한다.
- 경고를 거르는 코드가 저장소에 없다. 나중에 필요하면 이 ADR 을 개정한다.
- `node:sqlite` 의 동작 변화는 계약 테스트가 잡는다. 그 테스트가 22.18 매트릭스에서 빠지면
  이 결정의 근거도 함께 사라지므로, 매트릭스에서 22.18 을 뺄 때 이 ADR 을 함께 검토한다.
- 세션 파일이 표준 SQLite 라는 사실은 사용자에게 유용한 정보다. 다른 도구로 열어 볼 수 있고,
  이 프로젝트가 사라져도 녹화가 잠기지 않는다. 문서에 적는다.
