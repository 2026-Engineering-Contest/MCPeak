# ADR-0060: MCPeak 목의 `inputSchema` 거절을 고정 접미어로 확인한다

- 상태: 채택
- 날짜: 2026-08-23
- 담당: runner
- 작성자: @sunghoon0303 (① MCP 서버 테스트 파트)
- 승인: 승인 (2026-08-23, @sunghoon0303 · 파트 ① 오너)
- 선행 결정:
  [ADR-0021](./0021-거절-기대-케이스의-입력-계약-대조-제외.md),
  [ADR-0048](./0048-목이-inputSchema-를-실제로-검사한다.md)
- 참조: 이슈 [#221](https://github.com/2026-Engineering-Contest/MCPeak/issues/221),
  이슈 [#89](https://github.com/2026-Engineering-Contest/MCPeak/issues/89)

## 배경

`runner` 는 거절을 기대한 케이스가 `isError: true` 를 받았을 때, 서버의 입력 검증이 만든
거절임을 알려진 응답 본문 지문으로 확인한다. 모르는 본문은 `unverified` 로 두어 서버 크래시가
정상 거절로 숨지 않게 한다.

기존 지문은 TypeScript SDK, Python SDK, FastMCP의 검증 오류 접두어뿐이다. MCPeak 목은
ADR-0048에 따라 `inputSchema` 를 직접 검사하고 올바르게 거절하지만 자체 진단문을 사용하므로,
목으로 만든 모든 위반 케이스가 `unverified` 경고를 받는다. 우리가 안내하는 첫 사용 경로에서
통과한 케이스가 실패처럼 보이는 상시 경고가 생긴다.

목의 스키마 위반 본문은 첫 줄이 툴·필드·값마다 달라지고, 마지막 두 줄은 다음과 같이 고정돼
있다.

```text
→ 이 툴이 tools/list 로 선언한 inputSchema 가 그렇게 요구합니다.
→ 거절이 의도한 것이면 responses 에 이 인자를 넣어 응답을 지정하세요.
```

매칭 미스와 사용자가 주입한 거절에는 이 두 줄이 없다. 목 테스트는 두 줄을 완전 일치 계약으로
고정하고 있어 문장 변경이 `runner` 모르게 지나가지 않는다.

## 선택지

- **A안: 현행 유지.** 안전하지만 목을 사용하는 정상 경로에서 경고가 항상 나온다.
- **B안: 목이 SDK 오류 접두어를 흉내낸다.** 저수준 서버에서 프로토콜 오류를 던지면 툴 오류가
  아니라 operation failure가 되어 지금 통과하는 케이스가 실패한다. 출처도 거짓으로 표시한다.
- **C안: 목의 고정 접미어를 `runner` 화이트리스트에 추가한다.** 자체 검증의 출처를 유지하면서
  스키마 위반만 좁게 확인할 수 있다.
- **D안: 모든 `isError: true` 를 확인된 거절로 본다.** 매칭 미스와 서버 결함까지 숨기므로
  #89의 안전 방향을 뒤집는다.

## 결정

C안을 택한다.

본문의 바깥쪽 공백을 제거한 뒤, 고정된 두 안내 줄이 본문의 **정확한 끝**인지 확인한다. 두 줄
앞에는 최소 한 줄이 있어야 하고, 앞의 모든 줄이 현재 툴 이름을 포함한 목의 위반 진단 형식과
일치해야 한다. 따라서 안내 두 줄만 있는 본문, 임의 오류에 안내를 붙인 본문, 안내 뒤에 다른 오류가
붙은 본문, 매칭 미스, 사용자가 주입한 임의 거절은 계속 `unverified` 다.

접두어 규칙과 접미어 규칙은 모두 화이트리스트다. 알려지지 않은 서버의 자체 검증은 종전처럼
`unverified` 로 남긴다.

## 이유

- 목이 실제로 수행한 `inputSchema` 검증을 그 출처에 맞는 지문으로 확인한다.
- 매칭 미스는 스키마 거절이 아니므로 고정 접미어가 없고 확인 대상으로 새지 않는다.
- 사용자가 주입한 `isError` 본문은 임의 문자열이라 신뢰하지 않는다.
- 위반 문장의 구조만 확인하고 툴명·필드명·값은 동적으로 대조해 위반 축이 달라도 판정한다.
- 끝 두 줄을 정확히 요구해 일부 문구 포함만으로 확인되는 범위를 넓히지 않는다.

## 결과

- MCPeak 목이 만든 스키마 위반 케이스는 `verified` 가 되고 `rejectionUnverified` 경고에서
  빠진다. 케이스의 통과/실패 판정과 종료 코드는 바뀌지 않는다.
- 자체 검증하는 다른 MCP 서버는 계속 `unverified` 다. 일반화할 근거가 생기면 서버별 지문을
  별도로 검토한다.
- 목이 고정 안내문이나 위반 진단 형식을 바꾸려면 목의 완전 일치 테스트와 이 지문을 함께
  변경해야 한다.
- 공개 함수의 타입이나 호출 형태는 바뀌지 않고 분류 결과만 바로잡히므로 `runner` patch로
  배포한다.
