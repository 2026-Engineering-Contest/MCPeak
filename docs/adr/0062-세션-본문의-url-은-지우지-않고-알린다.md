# ADR-0062: 세션 본문의 URL 은 지우지 않고 알린다

## 배경

External 세션의 마스킹은 **이름으로 판정한다**(ADR-0039). 이름이 없는 자리는 그 판정이
닿지 않는다. ADR-0053 과 그 개정이 URL 의 **표준 자리**(요청 `display.url`, 저장 outcome
`url`, `location`·`content-location`·`link`·`refresh` 헤더)를 경로 제거로 덮었지만,
**JSON body 안의 URL 문자열과 자유 텍스트는 여전히 범위 밖**이다.

이 자리가 진짜로 새는지는 [#301](https://github.com/2026-Engineering-Contest/MCPeak/issues/301)
이 `Link` 헤더에 쓴 판단 방법을 그대로 적용하면 답이 나온다. 그때 근거는 사례 통계가 아니라
**헤더의 정의**였다 — pagination `Link` 는 서버가 *요청 URL 을 되돌려 만들기 때문에*, 요청
경로에 자격증명이 있으면 응답의 `Link` 에 같은 경로가 **반드시** 실린다.

**body 도 같다.** JSON API 의 `links.next`, HAL 의 `_links.self`, HATEOAS 의 자기 참조 URL 은
전부 요청 URL 을 되돌려 만든다. Slack·Discord webhook 처럼 **경로 자체가 자격증명**인
endpoint 가 그런 응답을 내면, ADR-0053 이 표준 자리에서 지운 경로가 body 로 되돌아온다.
유행이 아니라 그 필드가 무엇인지에서 따라 나오는 결과다.

그래서 `Link` 때와 같은 결론이 나올 것 같지만, **한 가지가 다르다.**

### body 는 표시용이 아니다

`Link` 나 요청 `display.url` 은 **표시용**이다. 매칭은 자식 프로세스 안에만 있는 매칭 재료로
따로 계산하므로, 표시용 값에서 경로를 지워도 재생 동작은 변하지 않는다.

**body 는 그렇지 않다. 저장한 body 가 곧 재생에서 서버가 받는 값이다.**

- `runtime.mjs` 의 `bytesAsJson` 이 파싱 직후 `redactJson` 을 걸어 **마스킹된 body 를 저장한다.**
- `restoreHttpOutcome` 은 `new Response(JSON.stringify(outcome.body), …)` 로 **그 저장본을 그대로**
  서버에게 돌려준다.

즉 body 에서 지우는 값은 재생에서 서버가 볼 수 없는 값이다. 이름으로 걸리는 자격증명
(`token`·`apiKey`)에는 그 대가가 맞다 — 테스트가 살아 있는 자격증명을 다시 쓰는 것에 기대면
안 된다. **URL 에는 맞지 않는다. 링크를 따라가는 것은 서버의 정상 동작이다.**

## 선택지

- **A안**: 그대로 둔다. 범위 밖으로 두고 README 의 한계 문구를 유지한다.
- **B안**: 저장 직전에 body 안의 URL 문자열을 찾아 표준 자리와 같은 규칙으로 경로를 지운다.
- **C안**: 탐지하면 녹화를 실패로 닫는다. 자격증명이 파일에 남는 것 자체를 막는다.
- **D안**: 지우지 않는다. 대신 **탐지해서 알리고**, 무엇을 해야 하는지를 함께 말한다.

## 결정

**D안 — 지우지 않고 알린다.**

1. **body 안의 URL 문자열은 계속 원문으로 저장한다.** URL 경로 마스킹을 **얹지 않는다**는
   뜻이고, **기존 키 기반 마스킹은 그대로 먼저 적용된다.** `redactJson` 은 중첩 객체·배열까지
   훑어 `token`·`apiKey`·`accessToken` 같은 이름의 값을 `[redacted]` 로 바꾸며(ADR-0039 ·
   ADR-0045), 이 결정은 그 동작을 **한 글자도 바꾸지 않는다.** 원문으로 남는 것은 **그 마스킹을
   통과한 뒤에도 남아 있는 URL 문자열**뿐이다 — 이름이 민감 키인 자리에 URL 이 실려 있으면
   지금도 값째로 가려진다.
2. **녹화 실행이 끝날 때 탐지 결과를 알린다.** 갈래 둘을 나눈다.
   - **되돌아온 경로**(확실): body 의 문자열이 **그 요청의 실제 경로를 담고 있다.** 자식은
     매칭 재료로 정확한 경로를 알고 있으므로 이 판정에는 추측이 없다. ADR-0053 이 표준 자리에서
     지운 값이 body 로 되돌아왔다는 뜻이다. **요청 body 와 응답 body 를 모두 본다** — 되돌아옴
     자체는 응답의 성질이지만, 콜백 URL 을 담아 보내는 등록 요청처럼 요청 body 로도 같은 값이
     나가고 그것도 세션에 저장된다.
   - **그 밖의 URL 문자열**(약한 신호): 되돌아온 경로는 아니지만 URL 로 해석되는 문자열이 있다.
3. **진단에는 값도 원문 키 이름도 싣지 않는다.** 개수와 고정된 분류만 싣는다(ADR-0053 의 진단
   규칙과 같다 — 원문 키 대신 정규화된 분류만). 진단이 유출 경로가 되면 고치려던 것을 그 자리에서
   다시 만든다.
4. **저장 형식은 바꾸지 않는다.** 탐지 결과는 세션에 쓰지 않고 Coordinator 프로토콜로만 흘려
   종료 요약에 싣는다. `HTTP_INTERACTION_SCHEMA_VERSION` 을 올리지 않으므로 **기존 세션 파일과
   그것을 읽는 소비자(`loadSession` 을 쓰는 dashboard)는 영향받지 않는다.** 종료 요약에 필드가
   느는 것은 소비자가 모르면 무시하는 방향의 변화라 기존 CLI 표시도 깨지지 않는다.
5. **세션 파일에 자격증명이 들어갔을 때의 정리 절차는 그대로 유효하다** — 파일 삭제로 끝내지
   말고 자격증명을 폐기·재발급한다. README 의 그 절이 이 결정의 짝이다.

### 탐지 규칙

결정론성이 이 프로젝트의 핵심 가치이므로(`CLAUDE.md`), "URL 문자열" 과 "N건" 이 실행 가능한
규칙으로 고정돼야 한다. 같은 세션을 두 번 훑으면 같은 숫자가 나와야 한다.

- **훑는 범위는 `redactJson` 과 같다** — 중첩 객체와 배열 요소까지 재귀로 내려가 **문자열 값**만
  본다. 키 이름은 대상이 아니다.
- **URL 판정은 문자열 전체가 절대 URL 로 파싱될 때만이다.** 문장 안에 URL 이 섞인 값은 대상이
  아니다 — 그것은 자유 텍스트이고, 자유 텍스트를 범위 밖으로 둔 이 ADR 의 결정과 같은 자리다.
- **"되돌아온 경로" 는 `URL` 파서가 돌려준 `pathname` 이 정확히 같을 때만이다.** 그 요청의 매칭
  재료가 담은 pathname 과 **문자열로 비교한다.** `URL` 은 percent-encoding 을 정규화하지 않으므로
  (`/a%7Eb` 와 `/a~b` 는 서로 다르게 남는다 — 실측) **인코딩이 다른 표기는 다른 경로로 본다.**
  그래야 하는 이유는 `%2F` 와 `/` 가 RFC 3986 상 실제로 다른 자원이기 때문이다 — 디코딩해서
  맞추면 서로 다른 경로를 같다고 말하게 된다. **query 와 fragment 는 비교에서 뺀다** —
  pagination 은 경로를 그대로 두고 query 만 바꿔 되돌아오므로, query 를 비교에 넣으면 정작
  잡아야 할 것을 놓친다.
- **집계 키는 `URL` 파서가 돌려준 `href` 이고, 세는 단위는 세션 안에서 서로 다른 `href` 의
  개수다.** 같은 URL 이 반복 호출로 여러 번 나와도 1건이다 — 사람이 확인해야 할 자리의 수가
  그것이기 때문이다.
- **분류는 "되돌아온 경로" 가 우선하고, 한 번이라도 성립하면 그쪽이다.** 같은 `href` 가 어떤
  interaction 에서는 그 요청 경로와 맞고 다른 interaction 에서는 안 맞을 수 있다. **먼저 본
  쪽을 쓰면 interaction 순서에 따라 숫자가 달라진다** — 그건 결정론성이 깨진 것이다. 세션
  전체를 훑은 뒤 합집합으로 판정하므로 순서와 무관하다. 한 `href` 는 정확히 한 갈래에만 센다.
- **탐지는 녹화 경로에서만 돈다.** 재생은 저장본을 읽을 뿐이라 이 판정을 돌리지 않는다.

## 이유

**B안(자동 마스킹)을 버린 이유는 그것이 재생을 깨뜨리기 때문이다.** 그것도 **body 에 URL 이
들어 있는 서버**, 즉 이 개정이 지키려던 바로 그 서버들을 깨뜨린다.

```
녹화  GET https://hooks.example.com/services/T00/B00/SECRET?page=1
      → body {"next": "https://hooks.example.com/services/T00/B00/SECRET?page=2"}

B안으로 저장하면
      body {"next": "https://hooks.example.com/<redacted>?page=2"}

재생  서버가 next 를 따라간다
      → GET https://hooks.example.com/<redacted>?page=2
      → 녹화된 적 없는 경로라 matchKey 가 어긋나 REPLAY_MISS
```

원문을 남기면 재생이 되고 파일이 샌다. 지우면 파일은 안전하고 재생이 깨진다. **둘 다 가질 수
없다** — 저장본이 곧 재생 입력이기 때문이다. 그리고 이 도구에서 재생이 깨지는 것은 부수 피해가
아니라 제품이 없어지는 것이다.

**C안(탐지 시 실패)을 버린 이유는 둘이다.**

첫째, **확실한 탐지만 써도 정상 API 대부분을 막는다.** "되돌아온 경로" 는 오탐이 없지만, 경로를
되돌려 담는 것 자체는 REST API 의 정상 동작이다 — `/api/v1/users?page=2` 를 되돌려 담는 응답과
`/services/T00/B00/SECRET` 을 되돌려 담는 응답을 **우리는 구분할 수 없다.** 구분할 수 없어서
표준 자리의 경로를 전부 지운 것이 ADR-0053 이었다. 같은 무지가 여기서는 "전부 실패시킨다" 가
된다. ADR-0057 이 같은 자리에서 적었다 — *오탐으로 멀쩡한 스위트가 빨개지면 사용자는 경고를
고치지 않고 기능을 끈다.*

둘째, **종료 시점의 실패는 이미 쓴 파일을 되돌리지 못한다.** 자격증명은 실패를 표시하기 전에
이미 디스크에 있다. 막지 못하는 것을 실패로 표시하는 것은 안전을 주지 않으면서 신뢰만 깎는다.
이것도 ADR-0057 이 범위 밖 호출에 대해 내린 판단과 같다.

**A안(그대로 둔다)을 버린 이유는 문제가 유출 자체가 아니라 침묵이기 때문이다.** 지금 이
한계에 대한 대응은 README 한 줄 — *"녹화한 세션 파일을 커밋하기 전에는 내용을 확인해라"* —
뿐이다. 세션은 SQLite 라 눈으로 훑을 수도 없다. **사람의 수동 확인을 전제한 안전장치는
안전장치가 아니다.** 우리가 확실히 아는 사실(이 세션에는 되돌아온 경로가 N건 있다)을 쥐고도
말하지 않는 것이 고칠 부분이다.

**D안이 이 저장소의 기존 패턴이다.** ADR-0057 이 범위 밖 호출에 대해 정확히 이 모양을 택했다 —
막을 수 없다는 것을 인정하고, 대신 종료 요약으로 가능성을 알린다. 여기서는 그때보다 나은
재료가 있다. 범위 밖 호출은 우리 눈에 안 보여서 "0건" 이라는 간접 신호로 추측해야 했지만,
**되돌아온 경로는 자식이 정확한 경로를 쥐고 직접 판정한다.** 추측이 아니라 사실을 말할 수 있다.

## 결과

- **이 결정으로 유출 경로가 닫히지 않는다.** body 에 실린 자격증명은 여전히 세션 파일에 원문으로
  남는다. 바뀌는 것은 **사용자가 그 사실을 아는가** 하나다. 이 ADR 은 그 이상을 주장하지 않는다.
- **경로가 자격증명인 endpoint 는 세션 파일을 커밋하면 안 된다.** 되돌아온 경로 알림이 뜬 세션은
  그렇게 다뤄야 한다. README 의 한계 절과 정리 절차를 이 결정에 맞춰 다시 쓴다.
- **옵트인 마스킹은 만들지 않는다 — 지금은.** "재생이 깨져도 좋으니 지워 달라" 는 요구는
  자기 링크를 되돌려 주기만 하고 따라가지는 않는 서버에서 실제로 성립한다. 다만 우리는 서버가
  링크를 따라가는지 **알 수 없으므로**, 그 플래그는 켜 보기 전에는 재생이 깨지는지 알 수 없는
  스위치가 된다. 실측된 요구가 나오면 별도 ADR 로 다시 본다.
- **"되돌아온 경로" 는 놓칠 수 있다.** 인코딩이 다른 표기를 다른 경로로 보기 때문에, 서버가
  요청과 다르게 인코딩해 되돌려 주면(`/a~b` 를 `/a%7Eb` 로) 확실한 갈래에 안 걸린다. 그래도
  **URL 문자열이기는 하므로 약한 갈래("그 밖의 URL 문자열")에는 잡힌다** — 알림이 통째로
  사라지지는 않고 확신도만 낮아진다. 반대 방향(없는 유출을 있다고 말하는 것)이 나지 않는 것을
  더 중요하게 봤다.
- **지문 개수에 상한이 있다.** 1 MiB 를 통과하는 정상 body 가 고유 URL 을 5만 개 가까이 담을
  수 있어(실측), 지문을 전부 wire 에 실으면 Coordinator payload 상한을 넘겨 **정상 녹화가
  실패한다** — 알리자고 만든 것이 녹화를 깨뜨린다. 그래서 `MAX_BODY_URL_FINGERPRINTS`(512)를
  넘으면 잘라내고 "잘렸다" 를 함께 알린다. 그때 개수는 정확한 값이 아니라 **최소값**이고,
  화면에도 "N건" 이 아니라 "N건 이상" 으로 나가야 한다. 그 자리에서 필요한 답은 정확한 수가
  아니라 "많다" 라고 봤다.
- **알림이 새 유출 경로가 되지 않게 한다.** 값도 원문 키 이름도 싣지 않는다는 결정 3번이 그
  방어다. 이 규칙을 어기면 이 ADR 은 문제를 옮겼을 뿐이다.
- **탐지 비용은 녹화 경로에만 든다.** 재생은 저장본을 읽을 뿐이라 이 판정을 돌리지 않는다.
  상한(1 MiB, ADR-0053)이 이미 걸린 body 를 한 번 더 훑는 비용이다.
- **자유 텍스트는 이 결정의 범위 밖이다.** 오류 문구·설명 필드에 섞인 토큰은 "되돌아온 경로"
  판정에 걸리지 않고, URL 로도 해석되지 않는다. `fetch` 가 던진 오류의 자유 텍스트를 아예
  저장하지 않기로 한 ADR-0053 의 결정이 그 갈래의 답이고, 응답 body 안의 자유 텍스트는 남는다.
- 이 결정이 뒤집히려면 **저장본과 재생 입력을 분리할 방법**이 나와야 한다. 그러면 B안의 대가가
  사라진다. 지금 구조에서는 `restoreHttpOutcome` 이 저장본을 그대로 서버에게 주므로 분리가 없다.
