# ADR-0064: 사전보완 제안 값을 JSON 문자열로 받는다

- 상태: 제안
- 날짜: 2026-08-23
- 담당: generate
- 작성자: @endl24 (① MCP 서버 테스트 파트)
- 승인: 미승인. 아래 '승인' 절 참조
- 선행 결정: [ADR-0007](./0007-provider-전송-스키마-분리.md)
- 참조: [#284](https://github.com/2026-Engineering-Contest/MCPeak/issues/284)

## 배경

AI 사전보완이 codex 에서 한 번도 성공하지 않았다. 원인은 인증도 모델도 아니고 **우리가 만들어
보내는 출력 스키마**다. `buildOutputSchema` 가 제안 값을 빈 스키마로 두는데,

```ts
// 값의 타입은 필드마다 다르다. 여기서 좁히면 정수 필드에 문자열을 받을 수 없다.
value: {},
```

codex 가 이것을 400 으로 거절한다. #284 가 잡은 응답 본문 그대로다.

```
"code": "invalid_json_schema",
"message": "Invalid schema for response_format 'codex_output_schema':
  In context=('properties', 'proposals', 'items', 'properties', 'value'),
  schema must have a 'type' key."
```

주석의 의도는 맞다. 제안 값의 타입은 필드마다 다르므로 좁히면 안 된다. 다만 **좁히지 않는 것을
빈 스키마로 표현할 수 없다.** 요청이 API 에 닿지도 못하므로 사전보완 통로 전체가 죽어 있다.

## 선택지

- **A안**: `{"type":["string","number","boolean","object","array","null"]}` 로 타입을 전부 나열한다.
- **B안**: 스칼라만 허용한다 — `{"type":["string","number","integer","boolean","null"]}`.
- **C안**: 값을 `valueJson` 문자열로 받고 로컬에서 파싱한다.
- **D안**: 제안 대상 필드의 선언 타입으로 요청마다 `value` 를 좁힌다.

## 결정

**C안을 채택한다.**

전송 스키마의 `value: {}` 를 `valueJson: { type: "string" }` 으로 바꾼다. provider 는 값을 JSON 으로
직렬화해 보내고, `validatePreFillResult` 가 파싱해 `PreFillProposal.value` 로 되돌린다.
결과 타입은 바뀌지 않는다 — `cli` 가 읽는 `{ caseId, field, value }` 는 그대로다.

값의 형식은 스키마 대신 **프롬프트 본문으로 알린다.** ADR-0007 이 `suiteJson` 에 쓴 방식과 같다.

`valueJson` 이 JSON 으로 읽히지 않으면 **날것 문자열을 그대로 값으로 본다.** 문자열 값에 따옴표를
빼고 보내는 것이 provider 의 흔한 실수인데, 그 하나로 정상 제안을 통째로 버리면 이 통로가 있으나
마나 해지기 때문이다. 관대하게 읽어도 잘못된 값이 명세에 실리지는 않는다 — 되돌린 값이 서버 선언을
어기는지는 `violatesDeclaration` 이 그대로 판정한다. 정수 필드에 `abc` 가 오면 문자열 `"abc"` 로 읽히고
바로 다음 줄에서 선언 위반으로 버려진다.

## 이유

**A안은 `object` 에서 막힌다.** ADR-0007 배경 절이 이미 기록해 둔 벽이다 — 임의 JSON 객체는 strict
structured output 이 요구하는 "모든 객체에 `additionalProperties: false`, 전 property `required`" 를
만족시킬 수 없다. 타입 목록에 `object` 를 넣는 순간 같은 요구에 걸린다. 400 메시지만 바뀌고
사전보완은 여전히 안 돈다. 우리가 한 번 부딪혀 문서로 남긴 벽에 다시 걸어 들어갈 이유가 없다.

**B안은 기능을 줄인다.** 사전보완 대상은 최상위 필드이고, 객체·배열 필드도 안쪽 값에 근거가 없으면
대상이 된다(`provenance.ts` 가 안쪽으로 내려가며 세는 이유가 그것이다). 스칼라만 허용하면 그 필드들은
제안을 받을 길이 없어지고, 사용자는 왜 어떤 필드만 조용히 빠지는지 알 수 없다.

**D안은 결정론성과 상충하지 않지만 값이 비싸다.** 제안은 `proposals` 배열의 동일한 항목 모양으로
오므로, 필드마다 다른 `value` 타입을 표현하려면 `caseId`+`field` 로 갈리는 조합자가 필요하다.
ADR-0007 이 최상위 조합자를 못 쓴다고 정한 이유가 그대로 여기에도 걸리고, 케이스 수만큼 분기가
늘어난다. 얻는 것은 하류에서 이미 하고 있는 타입 검사다.

**C안은 검증 강도를 낮추지 않는다.** 파싱 뒤 경로가 전부 그대로 돈다 — 요청에 없는 케이스, 그 케이스에
없는 필드, 근거 있는 값을 덮어쓰는 제안, 서버 선언을 어기는 값은 지금과 똑같이 사유와 함께 버려진다.
제안 값의 최종 판정은 원래도 스키마가 아니라 `checkInputContract` 였다.

## 결과

- 전송 스키마에서 빈 서브스키마가 사라진다. 회귀를 막기 위해 스키마를 재귀로 훑어 빈 객체가 하나도
  없음을 확인하는 테스트를 둔다.
- `PreFillOutputSchema` 의 모양이 바뀐다. `generate` 의 공개 타입이므로 breaking 이다. 소비자는
  `generate` 안뿐이라 영향 범위는 이 패키지에 갇힌다.
- 파싱 실패가 별도 실패 사유로 드러나지 않는다. 날것 문자열로 읽히거나, 선언을 어겨 `violatesSchema`
  로 버려지거나 둘 중 하나다. 사유 목록을 하나 늘리는 것보다 제안이 살아남는 쪽을 택했다.
- **codex 실측은 아직이다.** 이 저장소의 개발 머신에 codex 가 설치돼 있지 않아, 400 이 실제로
  사라지는 것까지는 확인하지 못했다. 근거는 두 가지다 — #284 가 잡은 codex 응답 본문이 거절 사유를
  `value` 하나로 지목한 것, 그리고 같은 제약 아래 있는 `PROVIDER_OUTPUT_SCHEMA` 의
  `suiteJson: { type: "string" }` 이 authoring 통로에서 실제로 통과하고 있다는 것이다.
  codex 가 있는 환경에서 한 번 돌려 확인해야 한다.

## 승인

- 상태: 미승인.
- 필요한 승인: `generate` 오너. 공개 타입 `PreFillOutputSchema` 의 모양이 바뀐다.
- 확정 방법: PR 이 머지되면 이 결정이 코드로 확정된다. 그때 이 절과 문서 머리의 `상태` 를 `채택` 으로
  바꾸고 승인일과 승인한 오너를 적는다.
- 되돌리는 조건: 두 CLI 가 임의 JSON 값을 표현할 수 있는 스키마를 받아들이게 되면 A안을 다시 본다.
  그때는 `valueJson` 파싱 단계가 통째로 사라진다.
