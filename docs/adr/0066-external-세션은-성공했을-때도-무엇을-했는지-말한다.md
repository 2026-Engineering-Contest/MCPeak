# ADR-0066: External 세션은 성공했을 때도 무엇을 했는지 말한다

## 배경

External 세션의 종료 알림은 지금까지 **이상할 때만** 말했다. `externalSessionNotice` 의 갈래를
전부 늘어놓으면 이렇다 — 녹화 0건, 재생 원본 0건, 하나도 재생 안 됨, 일부 미재생. 그 넷 중
어디에도 안 걸리면 함수는 `undefined` 를 돌려주고 화면에는 아무것도 안 나간다.

**성공한 실행이 침묵한다는 뜻이다.** 그리고 그것이 실제로 무엇을 뜻하는지 대시보드에서
확인했다. 같은 스위트를 `--record-session` 으로 한 번, `--session` 으로 한 번 돌렸다.

| | 녹화 실행 | 재생 실행 |
|---|---|---|
| origin 실제 호출 | 1 | 0 |
| 화면에 흐른 이벤트 | 2건 | 2건 |

```
외부 HTTP 를 부르는 서버  (1 case)

✓ seoul-weather  서울 날씨를 외부 API 에서 가져온다

1 passed  (1 total)
```

**두 실행의 출력이 바이트까지 같았다.** 방금 본 초록색이 실제 외부 API 를 부른 결과인지 석 달
전 녹화본을 재생한 결과인지, 화면만 봐서는 구분할 방법이 없다. 터미널도 마찬가지다 — 대시보드는
CLI 의 stdout/stderr 를 그대로 중계할 뿐이므로(ADR-0046) 이것은 화면의 문제가 아니라 **CLI 가
말을 안 하는 문제**다.

이 도구에서 이 침묵은 특히 비싸다. 판정이 같아도 **그 판정의 근거는 다른 사실**이기 때문이다.
재생으로 통과한 초록은 "이 서버가 지금도 그렇게 동작한다" 를 증명하지 않는다 — 녹화 시점의
외부 응답에 대해서만 증명한다. 사용자가 그 차이를 알아야 할 자리에서 우리가 아무 말도 안 했다.

## 선택지

**A안: 그대로 둔다.** 사용자는 자기가 친 명령을 안다. `--session` 을 붙인 것은 자기이므로
재생인 줄도 안다.

**B안: 기존 `externalSessionNotice` 의 침묵 갈래를 성공 문장으로 채운다.** 함수 하나가 모든
갈래를 말한다.

**C안: 결과 보고를 별도 함수로 분리하고, 기존 경고와 배타로 둔다.**

**D안: 리포트 헤더에 모드를 박는다.** `외부 HTTP 를 부르는 서버 (1 case) [재생]` 처럼 stdout
리포트 자체를 바꾼다.

## 결정

**C안 — `externalSessionOutcome` 을 따로 두고 `externalSessionNotice` 와 정확히 배타로 만든다.**

```
→ 외부 호출 3건을 녹화했습니다: tmp/weather.db
→ 녹화된 외부 호출 3건을 재생했습니다: tmp/weather.db
```

함께 고정한 것 넷.

1. **채널은 stderr.** 기존 세션 알림 셋과 같은 자리다. stdout 리포트와 `--json` 출력은 한 글자도
   안 바뀐다.
2. **세션 경로를 싣는다.** 세션이 여러 개일 때 어느 파일인지가 개수보다 먼저 필요한 정보다.
   경로는 다른 세션 문장과 같이 `escapeTerminalText` 를 거친다.
3. **범위 한계(ADR-0057)를 여기서 반복하지 않는다.** `EXTERNAL_SCOPE_NOTE` 가 경고 갈래마다 이미
   그것을 말한다.
4. **배타성은 테스트가 지킨다.** 두 함수의 갈래 조건은 서로를 보지 않고 각자 판정하므로, 매트릭스
   테스트가 모든 조합에서 "둘 중 정확히 하나" 를 단언한다.

## 이유

**A안을 버린 이유는 명령을 친 사람과 결과를 보는 사람이 같지 않기 때문이다.** 대시보드가 그
분리를 이미 만들었고(ADR-0046), CI 로그를 나중에 읽는 사람도 같은 처지다. 그리고 이 프로젝트의
기준은 "사용자가 알아낼 수 있는가" 가 아니라 **"화면이 말해 주는가"** 다 — `CLAUDE.md` 가
`expected true, got false` 를 금지하는 것과 같은 기준이다.

**B안을 버린 이유는 그 함수의 계약이 배타적 갈래이기 때문이다.** `externalSessionNotice` 는
"무엇이 잘못됐는가" 를 갈래 하나로만 말하도록 설계됐고, 그 배타성이 경고가 두 번 찍히는 것을
막는다(`replay(3,0,3)` 이 "하나도 재생 안 됨" 과 "3건 중 3건 미재생" 두 조건에 동시에 걸리는
자리가 이미 있다). 성공 보고는 축이 다르다 — 잘못이 아니라 사실이다. 같은 함수에 넣으면 그
함수는 "경고" 도 "보고" 도 아닌 것이 되고, 이름이 내용을 설명하지 못하게 된다.

**축이 다르면 따로 낸다는 것은 이 저장소의 선례다.** ADR-0062 의 `bodyUrlNotice` 가 같은 이유로
분리돼 있고, 그 주석이 근거를 이미 적어 두었다. 이번 결정은 그 선례를 따르는 것이지 새로 만드는
것이 아니다.

**D안을 버린 이유는 결정론 계약을 건드리기 때문이다.** stdout 리포트는 `--json`·JUnit 과 스냅샷
테스트가 물고 있는 면이다. 모드 표시 하나를 위해 그 면을 흔드는 것은 값이 비용에 안 맞는다.
stderr 는 이미 진단 채널이고, 대시보드도 그 채널을 렌더한다(`LogPanel`).

**성공 문장에 범위 한계를 안 붙인 것은 판단이 갈릴 수 있는 자리다.** 재생이 성공해도 지원 범위
밖 호출(`node:http`·axios·Python·Go 서버)은 실제 네트워크로 나간다(ADR-0057). 그래서 "재생했습니다"
만 보고 네트워크가 완전히 차단됐다고 읽을 위험이 있다. 그럼에도 안 붙인 것은, 정상 경로에서까지
매번 같은 단서를 붙이면 그 문장이 읽히지 않는 배경 소음이 되기 때문이다 — 경고 갈래에서 말할 때
읽히게 하는 편이 실제로 전달된다. **이 판단이 틀렸다는 신호는 "재생이니까 네트워크는 안 나갔다"
고 오해한 사용자 보고다.** 그때는 이 문장에 단서를 붙인다.

## 결과

- **성공한 External 실행이 stderr 에 한 줄을 낸다.** 세션 옵션이 없는 실행은 한 글자도 안
  바뀐다 — `runCli` 가 세션 배선 자체를 만들지 않는 경로 그대로다.
- **대시보드가 이 변경만으로 녹화·재생을 구분해 보여준다.** `LogPanel` 이 `stderr` 이벤트를 이미
  렌더하므로 `dashboard` 패키지는 손대지 않았다. 계획서 P10 의 dashboard 연동 중 "무엇을 했는지
  보인다" 부분이 cli 쪽 문장 하나로 닫힌다.
- **여전히 대시보드에서 녹화를 켤 방법은 없다.** [Home.tsx](../../packages/dashboard/web/src/screens/Home.tsx)
  가 argv 를 `suitePath`·`--command`·`--arg` 로만 조립해서, 세션 옵션은 API 를 직접 부를 때만
  들어간다. **이 ADR 은 그것을 고치지 않는다** — `dashboard` 는 공동 소유라 별도 PR·별도 오너의
  일이다(CONTRIBUTING §2.1).
- **녹화된 세션을 목록으로 보거나 열어보는 면은 여전히 없다.** 그쪽은 SQLite store 와 묶여 있고
  (구현계획 §C-1 — 세션 간 교차 조회는 dashboard 연동에서 처음 필요해진다) 로드맵상 뒤다.
- **두 함수의 배타성이 새 불변조건이다.** 어느 한쪽의 갈래 조건을 고치면 다른 쪽도 함께 봐야
  한다. 매트릭스 테스트가 그것을 강제하지만, 갈래를 **추가**할 때는 매트릭스에 그 조합을 넣는
  것을 잊지 않아야 한다.
- 재검토 조건: 위에 적은 오해 보고가 실측되면 재생 문장에 범위 단서를 붙인다. 그리고 세션 목록
  화면이 생기면 이 한 줄이 그 화면으로 가는 링크를 대신하고 있었다는 뜻이므로, 그때 문장의 역할을
  다시 본다.
