## 배경

대시보드 run 화면이 **도는 run 과 없는 run 을 글자 하나 다르지 않게** 그렸다. 둘 다 "대기" 였다.

`RunStatus` 에 "대기" 라는 값은 없다(`running` · `waiting-input` · `done` · `failed`). 즉 "대기" 는
상태가 아니라 **모른다는 뜻인데 아는 척한 문구**였다. 서버는 두 정보를 다 갖고 있었다 —
`GET /api/runs/:id` 는 `status` 를 주고, 404 본문에는 `{"error":"그런 run이 없습니다."}` 가
실려 있었다. 화면이 둘 다 버렸다.

원인은 둘이다.

1. `useRunEvents` 가 status 를 **SSE 이벤트로만** 만들었다. 그런데 `mcpeak test` 는 끝날 때까지
   stdout 을 뱉지 않으므로 실행 내내 이벤트가 0건이고, 그동안 status 가 계속 `null` 이었다.
2. `EventSource` 에 `onerror` 가 없었다. 404 로 연결이 실패해도 상태에 흔적이 남지 않았다.

여기서 두 가지를 정해야 했다. **상태를 어떻게 알아내는가**, 그리고 **`EventSource` 가 응답 본문을
주지 않는데 404 와 정상 종료를 어떻게 가르는가.**

## 선택지

**상태를 알아내는 방법**

1. 주기 폴링. `GET /api/runs/:id` 를 N초마다 부른다.
2. **마운트 때 1회 조회 + 스트림 영구 실패 시 1회.**
3. 서버가 구독 직후 현재 status 를 이벤트로 흘린다.

**실패 판정**

1. `onerror` 가 뜨면 실패로 본다.
2. **`readyState === CLOSED(2)` 일 때만 영구 실패로 본다.**
3. 판정하지 않고 재시도만 한다(지금과 같음).

**`CLOSED` 상수를 어디서 읽는가**

1. 전역 `EventSource.CLOSED` 를 읽는다.
2. **스펙 고정값 `2` 를 우리 상수로 둔다.**

## 결정

**상태는 2번, 실패 판정은 2번, 상수는 2번.**

`refresh()` 하나를 두 자리에서만 부른다 — 마운트 직후, 그리고 `readyState === CLOSED` 인
`onerror` 에서. 성공하면 `status` 가 **아직 비어 있을 때만** 채우고, 실패하면 서버 문장에
서버가 알 수 없는 두 줄을 덧붙여 화면으로 옮긴다.

```
그런 run이 없습니다.
→ 대시보드는 실행 이력을 메모리에만 둡니다. 서버를 다시 시작했다면 이전 run 은 남아 있지 않습니다.
→ 홈 화면의 최근 실행 목록에서 살아 있는 run 을 고르거나, 새 실행을 시작하세요.
```

**성공 경로는 `error` 를 건드리지 않는다.** 화면 컨트롤 이름도 부르지 않는다.

## 이유

**폴링을 버린 이유.** 타이머는 결정론성을 흔든다 — `CLAUDE.md` 가 금지하는 항목이고, 재생·E2E
테스트가 간헐 실패하는 전형적인 원인이다. 그리고 필요가 없다: `running` → `waiting-input` →
`done` 전이는 **전부 SSE 이벤트로 온다.** 모르는 구간은 "첫 이벤트가 오기 전" 하나뿐이므로
한 번이면 메워진다.

**서버가 status 를 흘리는 안(3번)을 버린 이유.** `RunEventInput` 에 새 kind 를 추가하는
**공개 계약 변경**이다. major 없이 못 무른다. 클라이언트 쪽 한 번의 조회로 되는 일에 그 값을
지불할 이유가 없다. 이 안을 고르면 서버도 바뀌는데, 2번은 **서버 0줄**이다.

**`readyState` 로 가르는 이유.** 스펙이 두 경우를 나눠 뒀다. 200·`text/event-stream` 이 아니면
"fail the connection" → `CLOSED`, **재시도 없음.** 네트워크 끊김·스트림 종료는 "reestablish" →
`CONNECTING`, 브라우저가 알아서 다시 붙는다. 이슈 본문의 네트워크 로그(`404`, 요청 1건, 재시도
없음)가 그 `CLOSED` 경로를 실측으로 확인해 준다.

정상 종료는 애초에 이 갈래를 타지 않는다 — 서버가 스트림을 닫지 않으므로(`handleRunEvents` 에
`response.end()` 가 없다) 종료는 언마운트의 `source.close()` 뿐이고 그때는 `onerror` 가 뜨지
않는다.

**상수를 우리가 갖는 이유.** 전역 `EventSource` 를 스텁하는 테스트가 그 static 을 갖지 않을 수
있다. 그러면 `undefined !== undefined` 가 false 가 되어 **판정이 조용히 뒤집힌다** — 항상
영구 실패로 보게 된다. 스펙 고정값이라 우리가 들고 있어도 갈릴 일이 없다.

**성공 경로가 `error` 를 안 건드리는 이유.** `EventSource` 의 404 는 즉시 실패하고 초기 조회는
왕복이 있다. SSE 가 먼저 문장을 세운 뒤 초기 조회가 늦게 성공해 `error` 를 지우면, **두 요청의
도착 순서에 화면이 좌우된다.** 결정론성 위반이다. `INITIAL_STATE` 가 이미 `null` 이므로 성공
경로는 아무것도 쓸 필요가 없다.

## 결과

- **서버가 완전히 죽으면 화면이 아무 말도 하지 않는다.** 스펙상 `CONNECTING` 으로 영원히
  재시도하므로 이 판정을 안 탄다. #295 가 고치려는 증상("화면이 아무 말도 안 한다")과 같은
  모양의 다른 원인이 하나 남는다. 알면서 남긴 구멍이다.
- **`CLOSED` 인데 조회가 200 을 주는 경우**(프록시 오설정 등)에는 여전히 아무 말도 하지 않는다.
  그 상황을 위한 별도 문안을 두려 했으나, 도달 경로가 사실상 없어 죽은 코드가 되므로 뺐다.
- 테스트 fake 세 곳(`run-stream` · `run-view` · `repair-review`)에 `readyState` 와 `onerror` 를
  붙여야 하는 부채가 생긴다.
- **마운트마다 fetch 가 한 번 는다.** 이 패널을 렌더하는 테스트 네 파일이 전부 fetch 를 URL 로
  갈라 스텁해야 한다. 스텁이 없으면 상대경로 fetch 가 실제로 나가 `act()` 밖 setState 가 된다.
- 서버가 준 문장을 화면이 그대로 옮기므로, **그 문장이 곧 계약**이 된다. `routes.test.ts` 가
  발원지에서 그것을 못박는다.
- **조회 실패를 404 와 그 밖으로 갈라야 한다.** `apiGet` 은 모든 non-OK 에서 reject 하므로
  상태를 보지 않으면 5xx·네트워크 오류까지 run-없음 안내로 묶이고, **살아 있는 run 에 거짓을
  말한다.** 그래서 `api.ts` 에 HTTP 상태를 들고 다니는 `ApiRequestError` 를 두었다.
  `Error` 를 상속하므로 `err.message` 만 쓰는 기존 호출자는 그대로다.
- **SSE 이벤트가 도착하면 앞선 조회 실패 안내를 걷는다.** 이벤트가 흐른다는 것이 곧 그 run 이
  있다는 증거다. 안 걷으면 살아 있는 run 화면에 "확인할 수 없음" 이 붙어 남는다.
