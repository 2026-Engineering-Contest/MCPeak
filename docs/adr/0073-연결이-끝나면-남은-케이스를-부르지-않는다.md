# ADR-0073: 연결이 끝나면 남은 케이스를 부르지 않는다

- 상태: 초안
- 날짜: 2026-08-24
- 담당: runner
- 작성자: @endl24 (① MCP 서버 테스트 파트)
- 참조: [#279](https://github.com/2026-Engineering-Contest/MCPeak/issues/279), [#222](https://github.com/2026-Engineering-Contest/MCPeak/issues/222)

## 배경

러너는 케이스를 다 돌기 전에 멈출 수 있고, 그 사실을 `RunnerReport.stopReason` 으로 말한다.
사유는 둘뿐이었다 — 타임아웃과 외부 취소. **서버가 죽는 것은 사유에 없었다.**

그래서 실행 도중 서버 프로세스가 죽어도 남은 케이스를 계속 호출했다. #279 가 관측한 형태는
원인 하나(서버 사망)가 화면에 실패 5건으로 부풀고, 뒤 4건이 `Not connected` 복사본이 되는
것이다. 타임아웃일 때는 제대로 멈춘다. 프로세스 사망은 타임아웃보다 확정적인 상태인데 안 멈췄다.

판정 재료는 이미 있었다. `core` 는 프로세스 종료를 관측한 뒤의 호출을 전부
`McpClientError { code: "PROCESS_EXITED" }` 로 던진다(`packages/core/src/index.ts` 의
`operationFailureKind`). 러너가 그 코드를 안 읽고 모든 거절을 `OPERATION_FAILED` 진단으로
뭉갠 것이 결함의 자리다.

## 선택지

- **A안**: 오류 메시지 문자열로 판정한다. `Connection closed` · `Not connected` 를 찾는다.
- **B안**: `core` 에 프로세스 사망 신호를 새로 추가하고 러너가 구독한다.
- **C안**: `core` 가 이미 붙여 놓은 오류 **코드**로 판정하고, `stopReason` 에 사유 하나를 더한다.

사유를 어디까지 넓힐지도 함께 갈렸다.

- **좁게**: `PROCESS_EXITED` 만.
- **넓게**: `PROCESS_EXITED` · `TRANSPORT_FAILED` · `HTTP_SESSION_LOST` 셋.

## 결정

**C안을 채택하고, 사유는 넓게 잡는다.**

`stopReason` 에 `{ type: "connectionLost", caseId, cause, exitCode?, signal? }` 변종을 더한다.
`cause` 는 `processExited` · `transportFailed` · `httpSessionLost` 셋이다. 판정은
`packages/runner/src/connection-loss.ts` 의 순수 함수 하나가 갖는다.

멈춘 케이스는 새 status 를 만들지 않고 `failed` 로 남는다. 보고서 `status` 도 `failed` 다.
`aborted` 는 사용자가 요청한 취소의 뜻이고 CLI 종료 코드가 거기 걸려 있다.

우선순위는 **타임아웃 · 취소 → 연결 상실** 이다. 앞의 둘은 우리가 정한 중단이고 이것은 서버 쪽
사정이라, 같은 케이스에서 겹치면 우리가 정한 쪽을 사유로 남긴다.

## 이유

**A안은 SDK 판본에 결과가 매인다.** `Connection closed` 는 우리가 만든 문장이 아니라
`@modelcontextprotocol/sdk` 가 만든 문장이다. 1.x 로 고정돼 있어도 patch 하나에 문구가 바뀌면
판정이 조용히 멈춘다. 반면 오류 코드는 `core` 가 우리 어휘로 붙인 값이다.

**B안은 없는 문제를 푼다.** 필요한 신호가 이미 `McpClientError` 에 실려 있다. `McpClient`
인터페이스는 5명의 병렬 작업 기준점이라 동결돼 있는데(CONTRIBUTING §3), 여기를 건드릴 이유가
전혀 없다.

**클래스가 아니라 구조로 판정한다.** 러너가 받는 client 는 `core` 가 만든 것일 수도, `record`
의 재생 client 나 목일 수도 있어 `instanceof McpClientError` 가 성립하지 않는다. `core` 자신도
같은 이유로 구조 검사를 쓴다(`client.ts` 의 `isCoreError`).

**넓게 잡은 첫째 이유는 셋 다 종착 상태이기 때문이다.** `TRANSPORT_FAILED` 는 transport 가
`failed` 로 넘어갔을 때만 나오고, `HTTP_SESSION_LOST` 는 `core` 자신이 "재연결은 지원하지
않으므로 다시 connect 하세요" 라고 안내한다. 어느 쪽이든 다음 케이스가 성공할 길이 없다.

**둘째 이유는 첫 실패의 경합이다.** SDK 는 stdout EOF 에서 요청을 거절하고 종료 코드는 child 의
`exit` 이벤트에서 채워진다. **두 사건의 순서는 보장되지 않는다.** 순서가 뒤집히면 죽음을 만나는
첫 호출이 `TRANSPORT_FAILED` 로 분류되고, `PROCESS_EXITED` 만 보는 판정은 케이스 하나를 더 돌고
두 번째에서 멈춘다. 사용자에게는 여전히 원인 1건이 2건으로 보인다.

관측으로는 이 저장소의 e2e(`connection-loss-e2e.test.ts`)에서 첫 호출도 `PROCESS_EXITED` 로
왔다 — 종료 코드 42 까지 실려 왔다. 그러니 이것은 **관측된 결함이 아니라 보장되지 않은 순서**다.
보장이 없는 것에 판정을 걸지 않는다는 뜻으로 셋을 함께 넣는다. 같은 이유로 e2e 는 종료 코드가
실렸는지를 단언하지 않고 문장까지만 고정한다.

**`OPERATION_FAILED` 는 넣지 않는다.** 서버가 살아서 오류를 돌려준 것이므로 다음 케이스는 여전히
유효하다. 여기서 멈추면 툴 하나가 오류를 낼 때마다 스위트가 통째로 안 돈다. 지금 고치는 결함의
정반대 형태다.

**사유를 문자열 하나가 아니라 discriminator 로 둔 것은 문장 때문이다.** 세 사유의 원인이 다르고,
이 저장소에서 실패 메시지는 제품이다. `httpSessionLost` 에 "서버 프로세스가 종료되어" 를 붙이면
프로세스가 없는 원격 서버를 두고 프로세스를 말하게 된다.

## 결과

- `mcpeak test` 가 이슈의 기대 형태로 답한다.

  ```
  중단: 서버 프로세스가 종료되어 실행을 멈췄습니다. (종료 코드 42)

  1 failed, 4 not run  (5 total)
  ```

- 종료 코드도 시그널도 관측하지 못했으면 괄호를 만들지 않는다. `(없음)` 은 관측하지 못한 것을
  관측했다고 말하는 것이다.
- **거절 근거 미확인 경고(#221 계열)가 대부분 함께 사라진다.** 거절을 기대한 케이스가 `notRun`
  이 되면 `notApplicable` 이라 §5.1 집계에서 빠진다. 다만 **죽은 케이스 자체가 거절 기대였다면
  1건은 남는다** — 본문이 없으면 `unverified` 다. 그 1건은 이 ADR 의 범위 밖이다.
- **`stopReason.type` 을 분기하는 코드는 전부 손봐야 한다.** `packages/runner/src/junit.ts` 는
  같은 PR 에서 고쳤다. 마지막 `return` 이 외부 취소 전용이라, 그냥 두면 CI 로그가 서버 사망을
  "외부 취소 신호를 받았습니다" 라고 말했다.
- **`packages/cli/src/dry-run.ts` 의 `stopDetail` 이 같은 형태로 남아 있다.** 새 사유가 취소
  갈래로 떨어져 분류 화면에 "실행이 중단됐습니다" 라고만 뜬다. `cli` 는 공동 소유라 별도 PR 로
  뗀다(CONTRIBUTING §2.2).
- `schemaVersion` 은 1 을 유지한다. 기존 키의 값이 하나도 안 바뀌고 선택 필드에 값이 하나 는
  것뿐이다. 다만 TypeScript 로 `stopReason` 을 망라 분기하던 소비자는 컴파일 오류를 본다.
- 같은 PR 에서 `controlled` 의 unhandled rejection 을 함께 고쳤다. 이미 취소된 상태로 들어오면
  요청 promise 에 핸들러를 붙이기 전에 반환해서, 떠 있던 호출이 나중에 거절되면 아무도 받지
  않았다. 취소는 곧 client 를 닫는다는 뜻이고 닫으면 떠 있던 호출이 거절되므로 드문 경로가
  아니다. 이 결함은 이 ADR 이전부터 있었고, 우선순위 테스트를 쓰다 드러났다.

## 승인

- 상태: 초안. ① 파트 검토 전이다.
- 되돌리는 조건: `TRANSPORT_FAILED` 로 멈추는 것이 실사용에서 너무 넓다고 판단되면
  `CAUSE_BY_CODE` 에서 그 줄만 뺀다. 판정 구조와 문장은 그대로 둔다.
