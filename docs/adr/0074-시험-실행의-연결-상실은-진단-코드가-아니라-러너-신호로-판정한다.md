# ADR-0074: 시험 실행의 연결 상실은 진단 코드가 아니라 러너 신호로 판정한다

- 작성자: @endl24
- 참조: `docs/adr/0073-연결이-끝나면-남은-케이스를-부르지-않는다.md`,
  `CONTRIBUTING.md` §2.2 (공용 패키지),

## 배경

`generate` 의 승인 직전 시험 실행(`runDryRun`)은 연결이 끊겼는지를 **스스로 짐작했다.**
`firstConnectionLoss` 가 보고서를 훑어 진단 코드가 `OPERATION_FAILED` 인 첫 케이스를 찾고,
거기서 결과를 잘라 "연결이 끊겼습니다" 라고 말했다.

이 휴리스틱은 ADR-0073 이전에 쓸 수 있는 유일한 재료였다. 그때는 러너가 서버 사망에 멈추지
않았고, 죽은 뒤의 호출이 전부 같은 오류로 채워지는 것을 `cli` 가 스스로 알아채야 했다.

ADR-0073 이 그 전제를 없앴다. 러너가 `core` 의 오류 코드(`PROCESS_EXITED` ·
`TRANSPORT_FAILED` · `HTTP_SESSION_LOST`)로 판정해 `stopReason: { type: "connectionLost",
cause, exitCode?, signal? }` 로 알려 준다. 그런데 `OPERATION_FAILED` 는 **서버가 살아서 낸
평범한 툴 오류에도 붙는 코드다.** ADR-0073 이 `CAUSE_BY_CODE` 에서 그 코드를 뺀 이유가 이것이다.

그래서 두 가지가 동시에 어긋나 있었다.

1. 휴리스틱이 러너 신호를 **앞질러 먹었다.** 연결 상실로 멈춘 케이스의 진단은 언제나
   `OPERATION_FAILED` 이므로(`executor.ts` 의 `failed`), 새 `stopReason` 을 분기하는 코드는
   어떤 보고서에서도 실행되지 않는다.
2. 툴 하나가 오류를 내면 **멀쩡한 실행이 거기서 잘렸다.** 서버는 살아 있는데 뒤 케이스의
   판정을 통째로 버리고 "연결이 끊겼습니다" 라고 말했다. 저장도 막혔다.

## 선택지

- **A. 신호 기반으로 교체한다.** `firstConnectionLoss` 를 지우고 `stopReason.type ===
  "connectionLost"` 만 연결 상실로 본다.
- **B. 신호 우선, 휴리스틱은 fallback.** 러너가 안 멈춘 경우에만 `OPERATION_FAILED` 를 읽는다.
- **C. 1번만 고치고 휴리스틱은 둔다.** `stopReason` 분기를 넣되 순서를 그대로 둔다.

## 결정

**A안.** 연결이 끝났는지는 러너만 말한다. `cli` 는 보고서의 진단 코드로 그것을 되짚지 않는다.

중단 사유 문장도 러너의 어휘를 그대로 쓴다 — `서버 프로세스가 종료됐습니다` ·
`서버와의 연결이 끊겼습니다` · `서버가 세션을 잃었습니다`. `reporter.ts` · `junit.ts` 와 같은
낱말이다. 종료 코드·시그널 괄호도 같은 규칙으로, 둘 다 관측하지 못했으면 만들지 않는다.

## 이유

- **C안은 죽은 코드를 낳는다.** 휴리스틱이 먼저 걸리므로 새 분기가 실행될 보고서가 없다.
  화면은 한 글자도 바뀌지 않으면서 "고쳤다" 는 착각만 남는다.
- **B안은 오분류를 남긴다.** 툴 오류 하나에 실행이 잘리는 결함이 그대로다. 그리고 두 판정
  경로가 공존하면 같은 화면 문장이 어디서 나왔는지에 따라 달라진다.
- **판정 재료는 한 곳에 있어야 한다.** ADR-0073 이 "SDK 문장이 아니라 우리 코드를 읽는다" 로
  판정 위치를 `runner` 로 못 박았다. `cli` 가 보고서를 다시 해석하면 그 결정이 두 곳으로 갈린다.
- **결정론성.** 진단 코드 훑기는 케이스 순서에 결과가 매인다 — 앞선 툴 오류가 뒤의 실제
  연결 상실을 가렸다. 러너 신호는 그런 순서 의존이 없다.

## 결과

- 승인 화면이 사유와 종료 코드를 말한다. 취소 신호와 구분된다.

  ```
  ✗ 시험 실행을 마치지 못했습니다. 3/8 케이스에서 연결이 끊겼습니다.
    → 케이스 'add 케이스 c' 에서 서버 프로세스가 종료됐습니다 (종료 코드 42). 남은 케이스는 실행되지 않았습니다.
  ```

- **살아 있는 서버의 툴 오류는 더 이상 중단이 아니다.** 그 케이스는 `failed` 로 분류 화면에
  가고, 뒤 케이스도 전부 돈다. 이것이 이 ADR 이 고치는 오래된 결함이다.
- **코드 없는 오류를 던지는 client 는 끝까지 돈다.** `record` 의 재생 client 나 목이 그렇다.
  제품 경로(`connect-target`)는 `core` 가 만든 client 라 코드가 붙으므로 영향이 없다. 이런
  client 가 실제로 서버 사망을 흉내 내야 한다면 `core` 와 같은 모양의 오류를 던지면 된다 —
  판정이 클래스가 아니라 구조라서 그것으로 충분하다(ADR-0073).
- `DryRunResult` · `DryRunAbortReason` 은 그대로다. `reason` 세 값이 유지되므로
  `generate-command` 의 `writeDryRunAborted` 와 `pre-fill-wiring` 은 손대지 않았다.
- 남은 `stopReason` 소비자: `packages/cli/src/test-command.ts` 의 2회차 판정은 `status ===
  "aborted"` 로 먼저 거른다. 연결 상실은 `failed` 라 그 갈래로 오지 않으므로 이번 범위 밖이다.
- 이슈 #279 의 나머지 두 항목(`executor.ts` 의 중복 hint, 전부 실패일 때의 거절 근거 경고)은
  `runner` 패키지라 별도 PR 로 뗀다(CONTRIBUTING §2.2).

## 승인

  나오면, 그때는 이 파일의 휴리스틱을 되살리는 대신 그 client 가 코드를 붙이도록 고친다.
