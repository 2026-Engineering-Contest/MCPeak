# ADR-0075: 실패 안내는 오류를 낸 층이 갖고, 러너는 그것을 덮지 않는다

- 상태: 채택
- 날짜: 2026-08-24
- 담당: runner
- 작성자: @endl24 (① MCP 서버 테스트 파트)
- 참조: `docs/adr/0073-연결이-끝나면-남은-케이스를-부르지-않는다.md`,
  `CLAUDE.md` (실패 메시지가 곧 제품),
  `packages/core/src/errors.ts` (`resolveHint`),
  `packages/runner/src/executor.ts` (`failed`),
  이슈 #279 (`## 함께` · `## 곁다리`) · 이슈 #222

## 배경

러너는 호출이 던진 모든 오류를 `OPERATION_FAILED` 진단으로 감싸면서 **안내를 자기 한 문장으로
덮었다.**

```ts
hint: "MCP 서버 프로세스와 연결 상태를 확인하세요.",
```

이 문장은 두 자리에서 틀린다.

1. **서버가 죽었을 때** — 화면 맨 아래 프로세스 진단 블록이 종료 코드·시그널·stderr 전문을 이미
   보여준다. 확인하라고 하는 그것이 이미 출력돼 있다. #222 가 `core` 에서 같은 지적으로 닫혔는데,
   `runner` 에 같은 형태가 남아 있었다(#279 의 `## 함께`).
2. **서버가 살아서 툴 오류를 냈을 때** — 프로세스도 연결도 멀쩡하다. 확인할 것은 툴과 인자인데
   엉뚱한 데를 가리킨다.

그런데 재료는 이미 오류 안에 있었다. `core` 의 `McpClientError` 는 코드별 안내를 갖고 있고
(`errors.ts`), `PROCESS_EXITED` 는 stderr 가 비었을 때 종료 코드를 짚는 변형까지 만든다
(`resolveHint` — #222 가 고친 그 자리). 러너가 그것을 버리고 있었다.

## 선택지

- **A. 오류가 들고 있는 안내를 승계한다.** 구조 검사로 `hint` 를 읽어 그대로 쓰고, 없으면 기본
  문장으로 떨어진다.
- **B. 러너가 사유별 문구를 자체로 갖는다.** `processExited` · `transportFailed` ·
  `httpSessionLost` · 그 밖 네 갈래를 러너가 직접 쓴다.
- **C. 한 문장만 갈아끼운다.** 구조는 그대로 두고 문장만 바꾼다.

## 결정

**A안.** 안내는 그 사실을 관측한 층이 만든다. 러너는 그것을 옮기기만 한다.

읽는 방식은 `classifyConnectionLoss` 와 같은 **구조 검사**다(`instanceof` 를 쓰지 않는다).
값은 client 가 준 관찰 문자열이므로 다른 서버 출력과 같은 상한·치환(`clampObservedText`)을 거친다.
안내를 안 들고 오는 client(목·재생)에는 기본 문장이 붙고, 그 문장은 `core` 가
`OPERATION_FAILED` 에 쓰는 것과 같다 — `요청한 tool과 서버 기능 및 진단을 확인하세요.`

## 이유

- **문장을 두 곳에서 관리하지 않는다.** B안을 고르면 같은 상황의 안내가 `core` 와 `runner` 에
  각각 있게 되고, #222 처럼 한쪽만 고쳐지면 사용자는 경로에 따라 다른 말을 듣는다.
- **구체성이 살아난다.** `resolveHint` 는 stderr 가 비었는지까지 보고 문장을 바꾼다. 러너는 그
  진단을 갖고 있지 않으므로 같은 문장을 만들 수 없다.
- **C안은 2번을 못 고친다.** 서버가 살아서 낸 툴 오류에 프로세스를 확인하라고 하는 것은 문장을
  바꿔도 한 문장으로는 갈라지지 않는다.
- **이미 출력된 것을 확인하라고 하지 않는다.** `CLAUDE.md` 가 실패 메시지에 요구하는 것은
  "어떻게 고치는지" 다. 승계한 문장들은 전부 할 일을 말한다.

## 결과

- 서버 사망 케이스의 `해결:` 줄이 `서버 stderr에 나온 오류를 수정한 뒤 다시 실행하세요.` 로
  바뀐다. 아래 진단 블록과 같은 말을 반복하지 않는다. 실프로세스 e2e 로 고정했다 — 가짜 client
  로는 "core 의 안내가 실제로 여기까지 오는가" 를 증명할 수 없다.
- **함께: 연결이 끊긴 케이스는 거절 근거 판정 대상이 아니다**(#279 의 `## 곁다리`). 호출이
  거절로 끝나 읽을 응답 본문이 아예 없는데 `unverified` 로 세면, 사용자를 없는 응답을 보러
  승인 화면으로 보낸다. 안 돈 케이스를 `notApplicable` 로 두는 규칙을 그대로 적용한다.
  ADR-0073 이 "범위 밖" 으로 남겨 둔 1건이 이것이다.
  - 넓히지 않는다. **서버가 살아서 낸 실패**의 거절 근거는 그대로 `unverified` 로 센다. 그
    자리에 응답이 있을 수 있고, 거기서 크래시가 초록으로 숨는 것이 #89 가 막으려던 것이다.
- `schemaVersion` 은 1 을 유지한다. 키가 늘지 않고, 값이 바뀌는 것은 위 두 자리뿐이다.
- 안내 문자열을 정확히 단언하던 소비자는 문장이 바뀐 것을 본다. 저장소 안에서는
  `reporter.test.ts` · `junit.test.ts` 의 손으로 만든 진단 픽스처가 옛 문장을 들고 있는데,
  렌더링만 검증하는 자리라 판정에 영향이 없어 그대로 뒀다.

## 승인

- 상태: 승인 (2026-08-24, @endl24 · ① MCP 서버 테스트 파트 오너가 검토하고 결정).
  `runner` 단일 패키지 결정이라 다른 파트 오너의 승인이 필요하지 않다(CONTRIBUTING §2.1).
- 되돌리는 조건: client 가 준 `hint` 가 실제로 화면을 어지럽히는 사례(길거나 우리 어휘와
  어긋나는 문장)가 나오면, 승계를 `code` 가 우리가 아는 값일 때로 좁힌다. 기본 문장과 거절 근거
  규칙은 그대로 둔다.
