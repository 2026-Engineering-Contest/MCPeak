# ADR-0078: 명세 검증 문안은 코드별 표가 갖고, 호출 지점이 문맥을 얹는다

- 상태: 제안
- 날짜: 2026-08-25
- 담당: runner
- 작성자: @endl24 (① MCP 서버 테스트 파트)
- 참조: `CLAUDE.md` (실패 메시지가 곧 제품),
  `packages/runner/src/spec/validation.ts` (`issue` · `issueWith` · `ISSUE_TEXT`),
  `docs/adr/0075-실패-안내는-오류를-낸-층이-갖는다.md`,
  이슈 #352 · #276 · #343

## 배경

`validateSuite` 의 `issue()` 헬퍼가 **모든 코드에 같은 문장 하나를 붙였다.**

```ts
const issue = (issues, code, path) =>
  issues.push({
    code,
    path,
    message: `명세 필드 '${path}'가 유효하지 않습니다.`,
    hint: "명세 계약에 맞게 필드와 값을 확인하세요.",
  });
```

이 헬퍼가 13개 코드, 약 40개 호출 지점에서 쓰였다. 그래서 필드가 **없는** 것과 값이 **틀린** 것과
단언이 operation 과 **안 맞는** 것이 화면에서 구분되지 않았다. 사용자는 대괄호 안의 코드 이름을
읽고 스스로 해석해야 했다 — 없는 필드에 "유효하지 않습니다" 라고 말하고, 두 결함의 해결 안내가
글자까지 같았다.

두 가지가 이미 있었다는 점이 이 결정의 출발이다.

1. **확장점은 이미 있다.** 같은 파일의 `issueWith()` 가 코드별 전용 문안을 받는다. 스키마 키워드
   진단 두 자리가 그 통로로 이미 제대로 된 문장을 낸다. 옛 통로만 안 갈아졌다.
2. **재료도 이미 호출 지점에 있다.** `unknowns()` 는 그 자리가 받는 필드 목록(`allowed`)을 손에
   쥐고 있고, `validateAssertions` 는 operation 종류와 `ALLOWED_ASSERTIONS` 를 둘 다 갖고 있다.
   대조의 양쪽이 다 있는데 문장이 그것을 안 실었다.

## 선택지

- **A. 코드별 문안 표를 두고, 호출 지점은 선택적 문맥만 얹는다.** `issue()` 는 남기고 네 번째
  인자로 `IssueDetail`(`expects` · `actual` · `operation`)을 받는다. 문장은 코드별 함수가 만든다.
- **B. 호출 지점 40개를 전부 `issueWith()` 로 펼친다.** 각 자리가 자기 문장을 직접 쓴다.
- **C. 표만 두고 문맥은 안 받는다.** 코드별 문장은 갈리지만 `path` 밖의 정보는 못 싣는다.
- **D. 이슈가 지목한 두 코드만 고친다.** `MISSING_REQUIRED_FIELD` 와 `INCOMPATIBLE_ASSERTION`.

## 결정

**A** 를 택한다.

- 문장은 `ISSUE_TEXT` 한 표가 소유한다. 키가 `SuiteValidationIssueCode` 유니온인 `Record` 라서,
  코드를 새로 넣으면 문안을 빠뜨린 것을 **타입 검사가 막는다.**
- 호출 지점은 이미 손에 쥔 값만 넘긴다. 안 넘기면 문장이 한 단계 일반화될 뿐 깨지지 않는다.
- 한 자리에서 원인이 여럿으로 갈리면(`json()` 의 유한하지 않은 수 · 옮길 수 없는 타입 · 순환 참조)
  기존대로 `issueWith()` 로 각자 문장을 쓴다. 두 통로는 경쟁하지 않고 역할이 다르다.
- 진단(**받은 값**)은 `message`, 고치는 법(**받는 값**)은 `hint` 로 가른다. 두 줄이 같은 말을
  하지 않는다.

## 이유

**B 는 지금 상태를 되돌린다.** 문장이 40군데로 흩어지면 다음 사람이 새 검사를 넣을 때 옆자리를
복사한다. `issue()` 의 고정 문안이 40번 복제된 것이 정확히 이 이슈다. 표가 있으면 빠뜨림이
컴파일 오류로 잡힌다.

**C 는 이슈가 요구한 것을 못 준다.** #352 가 이름을 붙여 요구한 두 가지 — "넣어야 할 값"과
"무엇과 무엇이 안 맞는지" — 는 `path` 만으로는 못 만든다. `schemaVersion` 이 `1` 하나를 받는다는
사실도, `listTools` 가 `toolExists` 만 허용한다는 사실도 호출 지점에 있다.

**D 는 나머지 11개 코드를 같은 문장에 남긴다.** 이 이슈의 불만은 두 코드가 부실하다는 것이 아니라
**모든 코드가 서로 구분되지 않는다**는 것이다. 두 개만 고치면 화면에서 그 둘만 튀고 나머지는
그대로다.

**값을 어디까지 실을지는 따로 정했다.** 타입이 틀린 자리는 타입 이름만 싣는다 — 값을 실어도 읽는
사람이 할 일이 안 바뀐다. 값이 틀린 자리는 값을 싣되 **33자 이상이면 타입 이름으로 줄인다.** 명세는
사용자 자신의 파일이라 서버 응답보다 안전하지만, 한 줄이 값 하나에 먹히면 나머지 진단이 안 보인다.
승인 지문(64자)은 값을 아예 싣지 않고 형식만 말한다.

## 결과

- `SuiteValidationIssue` 의 구조와 `SuiteValidationIssueCode` 목록은 **안 바뀐다.** `message` ·
  `hint` 문자열의 내용만 달라진다. CLI 는 `issues` 를 그대로 렌더하므로 `cli` 변경이 없다
  (#352 본문의 판단과 같다). `core/src/types.ts` 는 건드리지 않았다.
- 새 검사를 넣는 사람은 문안을 **표에서 고르거나 `IssueDetail` 로 문맥을 얹는다.** 아무것도 안
  넘겨도 코드에 맞는 문장은 나온다.
- **회귀 방지의 축이 옮겨간다.** 기존 테스트는 대부분 `code` 와 `path` 만 단언했다. 이 이슈의
  본질이 문안이므로 "13개 코드가 저마다 다른 문장을 낸다" 를 테스트로 고정했다. 표본이 13개 코드를
  다 덮는지도 같은 테스트가 함께 고정한다 — 안 덮으면 통과해도 의미가 없기 때문이다.
- **남는 것:** `issueWith()` 로 쓴 기존 문안 몇 개는 `path` 를 문장에 안 싣는다(예: "지원하지
  않는 스키마 키워드입니다."). CLI 가 앞에 경로를 붙여 주므로 화면에서는 문제가 없지만, 표를 쓰는
  새 문안과 문체가 다르다. 통일은 이 PR 범위 밖으로 둔다.
- 한국어 조사는 경로 뒤에 붙이지 않는다. `path` 가 ASCII 라 받침을 알 수 없어
  `'schemaVersion'이/가` 를 고를 수 없다. `'${path}' 필드가` 처럼 **한국어 명사를 하나 끼워**
  조사가 그 명사에 붙게 한다. 새 문안도 이 규칙을 따른다.
