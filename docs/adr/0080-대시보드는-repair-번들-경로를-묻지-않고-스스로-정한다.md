# ADR-0080: 대시보드는 repair 번들 경로를 묻지 않고 스스로 정한다

- 상태: 제안
- 날짜: 2026-08-25
- 담당: dashboard (공용)
- 작성자: @seodduu
- 참조: `docs/2026-08-25-대시보드-repair-번들-자동-관리-설계.md`,
  `docs/2026-08-25-대시보드-홈-실행-폼-설계.md` §2 목표 4, §3 비범위,
  `packages/cli/src/repair-bundle.ts`, `packages/dashboard/web/src/screens/RunView.tsx`

## 배경

repair 는 test 실행이 `--repair-bundle <path>` 로 남긴 번들 파일을 입력으로 받는다.
대시보드는 그 경로를 두 번 사용자에게 물었다. 홈 옵션에서 "어디에 만들지", 실행 뷰에서
"어디서 읽을지". 사용자는 실패를 보기 전에 첫 질문에 답해야 하고, 디렉터리를 손으로
만들어야 하고, 실패한 뒤 같은 경로를 다시 쳐야 했다. 대시보드는 run 의 argv 를 안 남겨서
"이 run 에는 번들이 없다" 를 말하지도 못했다.

같은 날 머지된 홈 실행 폼 설계는 목표 4 로 "기본값 폼의 argv 는 지금과 바이트 단위로
같다" 를 두었다. 번들을 항상 켜면 이 목표가 깨진다.

## 선택지

1. **항상 켠다.** 홈의 모든 test 실행에 `--repair-bundle <대시보드 관리 경로>` 가 붙는다.
   경로는 프론트가 스위트 경로에서 결정론적으로 만든다. 서버는 디렉터리를 만들고 run 의
   argv 를 보관해 실행 뷰가 경로를 채운다. `Repair 번들` 칸은 덮어쓰기용으로 남긴다.
2. **옵트인 유지, 마찰만 제거.** 사용자가 켠 run 에 한해 서버가 argv 를 보관하고 실행
   뷰가 경로를 채우며 디렉터리를 만든다. 안 켠 run 은 `repair 시작` 대신 이유를 적는다.
3. **2 위에 재실행 버튼.** 번들 없는 실패 run 에서 `번들 켜서 다시 실행` 을 누르면
   대시보드가 같은 argv 에 번들을 붙여 한 번 더 돌린다.
4. **서버가 argv 에 끼워 넣는다.** 프론트는 그대로 두고 `wiring.ts` 가 test 요청의 argv 에
   `--repair-bundle` 을 덧붙인다.

## 결정

1 을 택한다. 4 는 택하지 않는다.

## 이유

- 번들은 사용자의 산출물이 아니라 대시보드의 내부 입력이다. JUnit 리포트는 CI 가 읽으니
  경로가 사용자 몫이 맞지만, 번들은 대시보드가 repair 에 넘기려고 만든다. 자기가 읽을
  파일의 위치를 사용자에게 묻는 것이 근본 오류였다. 2·3 은 그 질문을 남긴 채 답하기
  쉽게 만드는 것이라 첫 벽(실패 전에 켜기)이 그대로다.
- 목표 4 는 "옵션 섹션을 더하면서 기존 실행이 **조용히** 다른 명령이 되지 않게" 였다.
  이 변경은 조용하지 않다. 미리보기에 `--repair-bundle .mcpeak/repair/...` 가 항상
  보이고, 옵션 패널의 설명이 그 이유를 말한다. 목표 4 의 뜻은 지키고 글자는 깬다.
- 4 를 택하지 않는 이유는 `wiring.ts` 의 "argv 를 가공 없이 `runCli` 에 넘긴다" 가 이
  대시보드의 검증 근거이기 때문이다. 미리보기가 곧 실행되는 명령이라는 약속이 거기서
  나온다. 서버가 끼워 넣으면 미리보기와 실제가 달라지고, 그것을 맞추려면 미리보기도
  서버에 물어야 한다. 프론트가 폼 값으로 넣으면 `buildTestArgv` 도 `wiring.ts` 도
  그대로다.
- 경로를 `runId` 가 아니라 스위트 경로에서 만드는 이유는 `runId` 가 POST 응답에서야 오기
  때문이다. 프론트가 미리보기를 그리는 시점에 알 수 있는 값이어야 한다. 같은 스위트의
  다음 실행이 덮어쓰는 것은 감수한다. repair 는 마지막 실패를 고친다.
- 루트 `.gitignore` 대신 `.mcpeak/.gitignore` 에 `*` 를 쓰는 이유는 대시보드가 어느
  저장소에서 떠도 사용자 저장소의 파일을 고치지 않기 위해서다. 자기 디렉터리 안에 자기
  규칙을 둔다.

## 결과

- 홈 설계 §2 목표 4 와 §3 비범위("`RunSummary` 에 argv 를 남기지 않는다") 를 이 설계가
  덮어쓴다. 홈 설계 문서에 그 사실을 한 줄로 적는다.
- `RunSummary.argv` 가 생긴다. 메모리 안에서만 살고 재시작하면 사라지는 것은 같다.
- 통과한 run 의 출력 끝에 CLI 의 `repair 번들: 실패한 케이스가 없어 파일을 만들지
  않았습니다.` 한 줄이 늘어난다. 대시보드가 지우지 않는다. CLI 로 같은 명령을 친 사람과
  화면이 같아야 한다.
- 사용자 프로젝트에 `.mcpeak/repair/` 가 생긴다. `.mcpeak/.gitignore` 가 함께 생겨
  추적되지 않는다.
- CLI 가 `--repair-bundle` 의 부모 디렉터리를 만들지 않는 것은 그대로다. 대시보드가 자기
  관리 경로만 만든다. 사용자가 직접 적은 경로의 디렉터리는 CLI 와 같은 의미로 사용자
  몫이다. CLI 쪽 `mkdir -p` 는 `packages/cli` 오너에게 제안한다.
- 외부 클라이언트가 번들 없이 POST 한 run 은 실행 뷰에서 `repair 시작` 대신 이유를 본다.
  그 run 을 "번들 켜서 다시 실행" 하는 버튼(선택지 3)은 후속이다.
