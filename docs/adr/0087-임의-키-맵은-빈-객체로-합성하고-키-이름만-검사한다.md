# ADR-0087: 임의 키 맵은 빈 객체로 합성하고 후보값의 키 이름만 검사한다

- 상태: 제안
- 날짜: 2026-09-08
- 담당: generate
- 작성자: @seodduu
- 참조: ADR-0004(생성 테스트의 자동화 범위), ADR-0036(미지원 스키마 툴의 부분 생성),
  ADR-0086(조합·참조·pattern 스키마는 갈래를 골라 합성한다), 이슈 #425

## 배경

`propertyNames` 는 객체의 **키 이름**에 붙는 제약이다. `z.record(...)` 와 `dict[str, X]` 가
이 키를 낸다. 같은 자리의 `additionalProperties` 는 그 키에 들어갈 **값**의 스키마다. 둘이 짝을
이뤄 "이름이 이런 꼴인 키를 원하는 만큼, 값은 이 타입으로" 를 뜻한다.

지금 `generate` 는 `propertyNames` 를 `SUPPORTED_SCHEMA_KEYS` 밖으로 보므로 그 툴을 통째로
건너뛴다(ADR-0036). 2026-09-08 실측에서 이 손실이 크다는 것이 드러났다. 자격 증명 없이 기동되는
공개 MCP 서버 20개(툴 227개)에 `mcpeak generate --baseline-only` 를 돌렸더니, #389 머지 뒤 남은
미지원 12툴 가운데 11툴이 `propertyNames` 였다.

문제는 "지원한다" 가 무엇을 뜻하느냐다. 우리는 **선언된 키만 만든다**(ADR-0004). 임의 키 맵에는
선언된 키가 없다. `required` 가 비어 있으므로 우리가 반드시 넣어야 할 키가 하나도 없다. 즉
이 키워드를 받아들이기로 해도 "그래서 무슨 값을 만드는가" 라는 질문이 따로 남는다.

## 선택지

**(a) 빈 객체 `{}` 를 만들고, 후보값의 선언 밖 키 이름만 검사한다.** 필수 키가 없으니 만들 것도
없다는 해석이다. `propertyNames` 는 값 합성에 쓰이지 않고, `const`·`default`·`examples[0]` 이
직접 적어 온 키 이름을 검사할 때만 읽힌다.

**(b) 임의 키를 하나 지어 넣는다.** `propertyNames` 를 만족하는 최소 문자열을 키 이름으로
합성하고(`pattern.ts` 가 이미 그 일을 한다) 값은 `additionalProperties` 로 만든다. 기각한다.
키 이름을 우리가 지어내야 한다. 결정론은 지켜지지만 `{"a": 0}` 같은 값은 도메인에서 아무 뜻이
없고, 서버가 그 키를 실제 파라미터 이름으로 해석하면 무엇을 검증한 것인지 알 수 없는 케이스가
된다. 선택 프로퍼티를 임의로 채우지 않는다는 ADR-0004 의 규칙과도 어긋난다. 우리는 `required`
가 아닌 것을 넣지 않기로 이미 정했고, 임의 키 맵의 키는 전부 선택이다.

**(c) 무시하고 annotation 으로 받는다.** `description` 처럼 값 형식만 보고 지나간다. 기각한다.
합성값은 (a) 와 같지만 후보값이 키 제약을 어겨도 통과한다. 서버가 `default: { "BAD KEY": 1 }`
을 적어 두고 `propertyNames` 로 소문자만 받겠다고 선언했으면 그 둘은 모순이고, 우리가 그
`default` 를 그대로 보내면 실행이 실패한다. 검사를 넣는 비용은 선언 밖 키마다 문자열 하나를
검사하는 것뿐이라 (a) 와 차이가 거의 없다.

**(d) 안쪽 스키마를 `validateSchema` 로 재귀 검증한다.** 기각한다. ADR-0086 이
`additionalProperties` 에 내린 판단과 같다. 우리가 쓰지 않는 선언의 모순 제약이
`INVALID_SCHEMA_CONSTRAINT` 로 **전체 생성을 중단**시킨다. 툴 하나를 건너뛰는 것과 서버 전체를
막는 것은 반경이 다르고, ADR-0036 은 그 반경을 줄이는 방향으로 정해져 있다.

## 결정

(a) 를 택한다.

- `propertyNames` 를 `SUPPORTED_SCHEMA_KEYS` 에 `additionalProperties` 바로 뒤로 넣는다.
- 값 형식만 검사한다. 스키마 객체가 아니면 `UNSUPPORTED_SCHEMA`, 경로는 `${path}.propertyNames`
  다. 안쪽은 검증하지 않는다.
- `object` 가 아닌 `type` 에 붙어 있어도 거절하지 않는다. 뜻이 없을 뿐 합성값이 달라지지 않아
  annotation 과 같은 범주다. `additionalProperties` 와 같은 규칙이다.
- 합성은 바뀌지 않는다. `required` 키만 만든다. 임의 키 맵은 `{}` 다.
- `valueMatchesSchema` 는 후보값의 **선언 밖** 키 이름을 `propertyNames` 로 검사한다. 키 이름은
  문자열이므로 그 스키마로 문자열 값을 검사하는 것과 같은 코드다. 값은 종전대로
  `additionalProperties` 부분스키마로 본다. 둘 다 있으면 이름은 앞의 것, 값은 뒤의 것이다.
- **`properties` 에 선언된 키에는 `propertyNames` 를 적용하지 않는다.** JSON Schema 사양은
  적용하라고 하지만 우리는 하지 않는다. 이유는 아래에 적는다.

## 이유

빈 객체가 정직한 답이다. 임의 키 맵에서 우리가 아는 것은 "키가 어떤 꼴이어야 하는가" 뿐이고
"어떤 키가 있어야 하는가" 는 모른다. 모르는 것을 지어내지 않는 것이 이 도구의 기본 규칙이고,
그 규칙 덕분에 생성 결과가 서버 구현이 아니라 선언만 반영한다.

후보값 검사를 함께 넣는 이유는 실패 메시지가 곧 제품이기 때문이다. 서버가 자기 선언 안에서
모순을 적어 뒀으면 그것을 실행 전에 알려 주는 편이, 실행해서 서버가 거절하는 것을 보는 것보다
원인이 가깝다.

선언된 키에 `propertyNames` 를 적용하지 않는 것은 사양과 어긋나는 선택이라 따로 적는다. 사양대로
적용하면 `properties: { BAD: {...} }` 와 `propertyNames: { pattern: "^[a-z]+$" }` 를 함께 적은
스키마에서 우리가 `BAD` 를 거절하게 된다. 그 스키마는 사양상 실제로 모순이다. 하지만 이 자리에서
우리가 하는 일은 "사용자 선언의 무모순성 판정" 이 아니라 "실행 가능한 입력 하나 만들기" 다.
서버가 `properties` 에 이름을 적어 뒀다면 그것은 그 이름을 받겠다는 뜻이고, 우리가 그것을
거절하면 사용자는 자기가 선언한 필드를 우리 도구로 못 쓰게 된다. 얻는 것(모순 고지)보다 잃는
것(툴 손실)이 크다. 이 판단은 뒤집을 수 있다. 뒤집으려면 모순을 `UNSUPPORTED_SCHEMA` 로 그 툴만
건너뛰게 하는 것이 아니라 별도 경고 경로가 필요한데, 지금 그런 경로가 없다.

## 결과

- 2026-09-08 실측 기준으로 `firecrawl-mcp@3.24.0` 9툴, `@playwright/mcp@0.0.80` 1툴,
  `@antv/mcp-server-chart@0.9.10` 1툴이 살아난다. `firecrawl` 은 자기 툴의 36% 를 이 키워드
  하나로 잃고 있었고, 중첩 안쪽(`scrapeOptions.jsonOptions.schema`)에 있어 툴이 통째로 날아갔다.
- 임의 키 맵 필드의 정상 케이스 입력은 `{}` 다. 그 필드에 대해서는 "서버가 빈 맵을 받아들이는가"
  만 검증된다. 키가 있는 경우의 동작은 검증되지 않으며, 그것이 필요하면 사람이 케이스를 더한다.
- 만들 키를 고를 수 없는 경우는 `minProperties` 가 미지원이라 자연히 막힌다. 그 키가 있는 툴은
  종전대로 `UNSUPPORTED_SCHEMA` 로 건너뛰어지므로, "한 개 이상의 키가 필요한데 빈 객체를 보낸다"
  는 상태가 생기지 않는다.
- `patternProperties` 는 여전히 미지원이다. 그것은 키 이름의 꼴에 따라 **값 스키마가 갈리는**
  키워드라 이 결정으로 덮이지 않는다.
- `runner` 는 이 필드의 위반 축을 만들지 않는다(ADR-0015). `UNDECLARED_FIELD` 축은 후속이다.
