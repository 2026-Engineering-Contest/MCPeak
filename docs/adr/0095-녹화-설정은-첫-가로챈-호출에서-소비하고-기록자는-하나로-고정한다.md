## 배경

Coordinator 는 자식에게 설정 환경변수 여섯 개와 `NODE_OPTIONS` 의 `--import=<bootstrap.mjs>` 를
함께 준다. `bootstrap.mjs` 는 모듈이 로드되는 즉시 그 환경변수를 읽고 지운다. 세션 하나에
기록하는 프로세스를 하나로 고정하려는 것이고, 그 보증이 결정론성의 뿌리다. 재생은
`(protocol, matchKey, occurrence)` 로 찾으므로 두 프로세스가 같은 세션에 섞여 쓰면 `occurrence`
번호가 실행마다 달라진다.

`npx` 처럼 런처를 거치면 이 규칙이 엉뚱한 프로세스를 고른다. 최소 재현의 출력이 근거다.

```
--- 직접 실행 ---
TARGET sees MCPEAK_EXTERNAL_MODE = "record"
TARGET sees NODE_OPTIONS = undefined
--- shim(=npx 구조) 경유 ---
TARGET sees MCPEAK_EXTERNAL_MODE = undefined
TARGET sees NODE_OPTIONS = "--import=file:///.../packages/record/src/external/child/bootstrap.mjs"
```

둘째 줄이 이 결정의 출발점이다. `NODE_OPTIONS` 는 손자까지 살아서 가고, 진짜 서버도
`bootstrap.mjs` 를 로드한다. 다만 설정 값이 중간에서 사라진 뒤라 아무것도 설치하지 않고 조용히
지나간다. 그러므로 고칠 것은 설정을 손자에게 전달하는 방법이 아니다(전달은 이미 되고 있다).
고칠 것은 체인에 있는 여러 Node 프로세스 중 누가 이 세션의 임자인가를 정하는 방법이다. 지금
규칙은 "가장 먼저 뜬 Node 프로세스" 이고, `npx` 를 쓰면 그것이 서버가 아니라 런처다. 결과는
녹화 0건이며, 화면은 범위 안에 있는 서버에게 지원 범위를 의심하라고 말한다.

## 선택지

1. **지연 소비 + 단일 기록자 확정.** (채택) 설정 소비를 모듈 로드 시점에서 첫 가로챈 호출
   시점으로 옮기고, Coordinator 가 처음 도착한 식별자를 그 세션의 기록자로 고정한다.
2. **(A) 런처 허용 목록.** `bootstrap.mjs` 가 `process.argv[1]` 이 `npx-cli.js` 류면 건너뛴다.
   기각한다. 목록 밖 런처에서 같은 결함이 그대로 재현되고, npm 내부 파일명에 의존하게 된다.
3. **(B) `npx <패키지>` 를 우리가 실행 파일 경로로 해석해 spawn 한다.** 기각한다. `-y` 의 설치,
   버전 해석, 캐시 경로를 다시 구현해야 하고 그러고도 `pnpm dlx` · `uvx` 는 또 깨진다.
4. **(C) 삭제만 없앤다.** 결정 1에서 결정 2를 뺀 것이다. 기각한다. 단일 기록자 보증이 사라져
   `occurrence` 번호가 실행마다 달라진다.
5. **(D) 문구만 고친다.** 기각한다. 오진은 막지만 녹화는 여전히 0건이고, 공개 서버 데모의
   녹화·재생 장면 자체가 성립하지 않는다.

## 결정

**설정 소비를 첫 가로챈 호출로 옮긴다.** `bootstrap.mjs` 는 환경변수를 읽되 지우지 않는다.
지우는 일은 어댑터가 실제로 가로챈 첫 `globalThis.fetch` 호출 안에서 한다.

| 프로세스 | 설정을 보는가 | 어댑터 | 소비 시점 |
|---|---|---|---|
| `npx` | 본다 | 설치된다 | 가로챈 호출이 없어 소비하지 않는다 |
| 진짜 서버 (npx 의 자식) | 본다 | 설치된다 | 첫 호출에서 소비한다 |
| 서버가 첫 호출 뒤에 띄운 자식 | 못 본다 | 설치되지 않는다 | 해당 없음 |

**Coordinator 가 단일 기록자를 확정한다.** 각 자식은 자기 식별자를 만들어 모든 Coordinator
요청에 헤더로 싣고, Coordinator 는 처음 도착한 식별자를 그 세션의 기록자로 고정한다. 다른
식별자의 요청은 `WRITER_CONFLICT` 로 거절하고 그 수를 센다. 이것이 서버가 자기 첫 호출보다 먼저
띄운 자식이라는 남는 틈을 막는다.

**식별자는 세션에 저장되지 않는다.** 와이어에만 산다. 저장되면 실행마다 다른 값이 녹화본에 들어가
재생 바이트가 달라진다.

거절당한 프로세스의 처리는 모드마다 다르다.

| 모드 | 거절당한 프로세스가 하는 일 | 이유 |
|---|---|---|
| record | 원래 `fetch` 로 그대로 내보낸다. 녹화하지 않는다 | 지금도 그 호출은 녹화되지 않았다. 던지면 진단 때문에 멀쩡한 서버를 죽인다 |
| replay | 던진다. 네트워크로 내보내지 않는다 | 재생의 계약은 "실제 네트워크는 호출하지 않았습니다" 다. 지금은 이 호출이 조용히 실제 네트워크로 나간다 |

**기록하지 못한 호출 수를 요약에 싣는다.** `RecordSessionSummary` 와 `ReplaySessionSummary` 에
`otherProcessCalls?: number` 를 더하고 Coordinator 가 `finish()` 에서 얹는다. `outOfScope` 와
의미가 다르다. `outOfScope` 의 `undefined` 는 "못 셌음" 이지만, `otherProcessCalls` 는 부모가
자기 거절을 직접 센 값이라 못 셀 일이 없다. 그래서 필드가 없으면 0이다.

## 이유

결정론성 보증의 세기는 같고, 보증하는 자리가 자식의 환경변수에서 부모의 상태로 옮겨간다. 지금은
"프로세스가 하나뿐이니 안전하다" 였고, 바뀐 뒤에는 "여럿일 수 있지만 하나만 통과한다" 가 된다.
부모에 두는 편이 낫다. 자식이 강제 종료되거나 환경을 만져도 보증이 깨지지 않기 때문이다.
환경변수에 기댄 보증은 그 값을 볼 수 있는 모든 프로세스가 공범이라 자식 쪽의 사고가 곧 보증의
사고였다.

## 결과

- **`npx` 가 `globalThis.fetch` 를 쓰기 시작하면 런처가 임자가 된다.** 결정 1은 npm 의 레지스트리
  클라이언트가 `node:http` 계열이라는 전제에 기대는데, 그것은 npm 내부 구현이라 우리가 고정할 수
  없다. 걸리면 런처가 레지스트리를 부르며 임자가 되고 서버의 호출은 전부 `WRITER_CONFLICT` 로
  거절되어, 결과는 오늘과 같은 녹화 0건이 된다. 다른 점은 화면이 이유를 안다는 것이다. 0건 알림의
  기록자 경합 갈래가 `otherProcessCalls` 를 숫자로 적는다. 침묵이 진단으로 바뀌는 것이 이 결정이
  최악의 경우에도 남기는 것이다. 통합 게이트에서 실제 `npx` 로, 캐시가 있는 상태와 없는 상태
  두 번 확인한다.
- **범위 밖 호출 관측(`outOfScope`)은 런처 환경에서 여전히 부정확하다.** `ENV_OBSERVER_PATH` 는
  지금처럼 로드 시점에 지우므로, 런처를 거치면 관측 사이드카가 런처 프로세스에 설치되고 서버의
  `node:http` 호출은 세어지지 않는다. 이번 변경이 이것을 나쁘게 만들지는 않는다. 다만 오늘은
  어댑터도 함께 죽어 재생 자체가 성립하지 않았고, 고친 뒤에는 재생이 되면서 숫자만 틀린 상태가
  된다. 숫자가 틀린 채로 초록이 나오는 쪽이 더 위험하므로 후속 이슈로 올린다. 제안하는 방향은
  관측 보고를 프로세스마다 다른 파일로 나누고 Coordinator 가 합치는 것이다. 이번에 넣지 않는
  이유는 원인 갈래가 재생 전용으로 다르고, 넣으면 변경이 두 배가 되기 때문이다.
