# ADR-0098: generate 승인 화면은 실패한 케이스만 AI 에 보낸다

- 상태: 제안
- 날짜: 2026-09-12
- 담당: cli, runner
- 작성자: @seodduu
- 참조: `docs/2026-09-12-generate-승인-화면은-실패한-케이스만-AI-에-보낸다-설계.md`,
  `docs/superpowers/specs/2026-08-18-rejection-basis-verification-design.md` (이하 "#89 설계") §5.2 · §6,
  [ADR-0049](./0049-provider-자유-텍스트-값-치환-경계.md)

## 배경

`mcpeak generate` 가 시험 실행을 켜고 provider 를 붙이면 승인 화면이 네 단계로 흐른다. 1 단계는
전체 케이스의 시험 실행 결과, 2 단계는 통과한 거절 케이스 중 `unverified` 인 것의 목록, 3 단계는
같은 건에 대한 AI 진단 전송 확인과 판정 목록, 4 단계는 실패 케이스의 입력값 교정이다. 2 · 3 은
#89 설계가 넣었고, `runner` 는 화이트리스트(TS SDK `-32602`, Python SDK, FastMCP pydantic, MCPeak
목 고정 문장)에 걸리는 것만 `verified` 로 찍는다. 2026-09-12 실측은 그 화이트리스트가 예외가
아니라 기본값 밖임을 보여 준다. `@supabase/mcp-server-supabase@0.12.0` 은 거절 케이스 31건 중
`verified` 0건, `examples/live-weather-server` 는 43건 중 `verified` 0건이고, 둘 다 핸들러 안에서
직접 검증해 자기 문장으로 거절한다. 즉 서버 개발자가 거절 문장을 손으로 쓰는 순간 전부 미확인이
되며, 그것이 대다수 서버다. 그 결과 기본 화면에 수십 줄이 오르고 그 전부가 정상 거절이라 사람이
확인할 것이 없으며, 거절이 오지 않은(`isError: false`) 실패 케이스까지 `unverified` 로 섞인다.
같은 화면의 AI 사전보완 요약도 baseline 과 제안이 둘 다 실패한 갈래를 "baseline 값이 이미 통과"
라고 찍어 사실과 다른 말을 한다.

## 선택지

1. **미확인 목록과 AI 진단을 플래그 뒤로 옮기고, 거절이 없던 케이스는 runner 가 판정 대상에서
   뺀다.** (채택)
2. **(A) 목록은 두고 AI 전송만 옵션으로.** 43줄이 그대로 남아 소음 문제가 안 풀린다.
3. **(B) 같은 본문은 한 번만 보낸다.** live-weather 는 43 에서 19 로 줄지만, 필드 경로가 본문에
   들어가는 Zod 계열 서버는 31 에서 29 로 거의 안 준다. 근본이 아니다.
4. **(C) Zod · Ajv 모양을 `verified` 로 본다.** 본문 형식으로는 못 가른다는 #89 관찰과 부딪히고,
   크래시가 검증 오류 모양으로 포장되는 경우(FastMCP 사례)를 다시 연다.
5. **(D) 거절이 아닌 케이스를 cli 에서만 거른다.** `--json` 과 `test` 요약의 집계가 계속 틀린다.

## 결정

**1. 거절이 오지 않은 케이스는 판정 대상이 아니다 (runner).** `classifyRejectionBasis` 가
`rejected: boolean`(실제 응답의 `isError` 가 `true` 였는가)을 받고, `expectsRejection && !rejected`
면 `notApplicable` 이다. 거절이 없었으니 확인할 근거도 없고, 그 케이스는 이미 `isError` 단언
실패로 빨간색이다. cli 는 그 위에 한 번 더 `status === "passed"` 로 거른다.

**2. 미확인 목록과 AI 진단은 `--diagnose-rejections` 뒤로 (cli).** 값 없는 플래그를 더하고 기본은
꺼짐이다.

| 상태 | 2 단계(목록) | 3 단계(AI 진단) |
|---|---|---|
| 플래그 없음 | 한 줄 고지만 | 안 한다 |
| 플래그 있음, provider 없음 | 지금과 같은 목록 | 안 한다 (지금도 provider 없으면 안 한다) |
| 플래그 있음, provider 있음 | 지금과 같은 목록 | 지금과 같은 전송 확인 → 진단 |
| 플래그 + `--no-dry-run` | 사용 오류 | |

한 줄 고지는 미확인이 1건 이상일 때만 찍으며, 문구는 "확인하지 못했습니다" 가 아니라 "확인하지
않았습니다" 다. 안 한 것과 못 한 것을 같은 말로 쓰면 플래그를 켠 뒤의 문장과 구분이 안 된다.

**3. 사전보완 요약은 네 갈래를 말한다 (cli).** `ApplyPreFillResult` 에 `held`(baseline 도 제안도
실패해 분류 화면으로 가는 수)를 더하고, 요약은 `미채택 (notAdopted - held)` 과 `보류 held` 를
나눠 찍는다. `보류` 줄은 0 이면 찍지 않는다.

## 이유

#89 설계 §6.1 은 "호출은 사용자가 시작한다" 로 문턱을 전송 확인에 두었다. 이 결정은 그 문턱을 한
단계 앞으로 옮겨 목록조차 사용자가 켤 때만 나오게 한다. 근거는 실측이다. 기본 서버에서 목록이
수십 줄이고 그 전부가 서버가 무엇이 왜 틀렸는지 말한 정상 거절이라, 기본 화면에 두면 신호가
아니라 소음이다. 소음이 기본이면 사용자는 그 줄을 읽지 않게 되고, 정말 크래시인 한 건도 같이
묻힌다.

거절 여부 판정을 cli 가 아니라 runner 에 두는 것은 runner 가 낸 값이 뜻과 맞아야 `--json` 보고서와
`test` 요약의 `거절을 기대한 케이스 N건` 이 함께 맞기 때문이다. cli 에서만 거르면 화면과 집계가
갈린다. cli 에 같은 필터를 한 번 더 두는 것은 두 패키지가 같은 시각에 바뀌므로 어느 한쪽만 먼저
들어가도 화면이 틀리지 않게 하기 위해서다.

화이트리스트는 넓히지 않는다. 본문 형식으로 정상 거절과 크래시를 가를 수 없다는 #89 의 관찰을
뒤집을 새 관찰이 없고, 형식 판정을 더하면 크래시가 검증 오류 모양으로 포장된 경우를 `verified`
로 찍어 조용히 숨기게 된다. 목록을 줄이는 값이 판정을 틀리게 만드는 값보다 작다.

## 결과

- **사용자 표면이 셋 바뀐다.** 기본 실행에서 미확인 목록과 전송 확인 대신 한 줄 고지가 나오고,
  `--diagnose-rejections` 가 생기며(`--no-dry-run` 과 함께 쓰면 사용 오류), 사전보완 요약에 `보류`
  줄이 생긴다. `test` 요약 문장 자체와 AI 진단의 요청·응답 계약은 그대로다.
- **남는 갈래 둘.** 대시보드 generate 폼에서 이 플래그를 켤 방법이 없다(후속 태스크). 화이트리스트가
  좁은 것은 그대로라 플래그를 켠 사용자는 여전히 수십 줄을 본다.
- **되돌리는 조건.** 플래그 없이 돌린 사용자의 화면에서 실제 크래시가 정상 거절 사이에 초록으로
  숨어 사용자가 놓친 사례가 나오면 기본값을 다시 논의한다. 근거는 "불안해서" 가 아니라 놓친
  실제 사례여야 한다.
