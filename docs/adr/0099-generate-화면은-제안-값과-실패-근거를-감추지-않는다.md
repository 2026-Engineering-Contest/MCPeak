# ADR-0099: generate 화면은 제안 값과 실패 근거를 감추지 않는다

- 상태: 제안
- 날짜: 2026-09-13
- 담당: cli, dashboard
- 작성자: @seodduu
- 참조: `docs/2026-09-13-generate-화면은-제안-값과-실패-근거를-감추지-않는다-설계.md`,
  `docs/plans/2026-09-13-generate-화면은-제안-값과-실패-근거를-감추지-않는다-구현계획.md`,
  `docs/superpowers/specs/2026-08-15-dry-run-input-repair-design.md` (이하 "원본 교정 설계") §8.6 · §8.6.1,
  [ADR-0098](./0098-generate-승인-화면은-실패한-케이스만-AI-에-보낸다.md),
  [실측 기록](../2026-09-11-공개서버-직접조작-데모-실측-문제.md) §4

## 배경

`mcpeak generate` 의 승인 화면을 `live-weather-server` 데모로 손수 밟은 2026-09-13 실측에서 다섯
가지가 나왔다. 전부 같은 계열이다. 화면이 숫자나 문장은 찍는데, **그 숫자가 어디서 나왔고 무엇이
실패했는지는 화면 어디에도 없다.**

ADR-0098 이 만든 `보류 N` 줄은 "baseline 값도 제안 값도 실패했다" 는 뜻인데, AI 가 무슨 값을 냈고
서버가 뭐라고 답했는지를 안 싣는다. 실측에서 `evaluate_expression` 이 보류 1로 나왔고, 같은
실행의 뒤 단계에서는 같은 AI 가 `2 + 2` 를 제안해 통과했다. 두 단계가 왜 달랐는지 알 데가 없다.
`targetIds` 에 못 들어간 제안(`callTool` 이 아니거나 입력이 객체가 아니거나 명세에 없는 케이스)은
채택에도 미채택에도 안 세어져 화면에서 그냥 사라진다. 실측 문서 §4 의 관측 "둘" 이 이것이다.

교정 화면은 더 나쁘다. `input-repair.ts` 의 `FAILURE_LINE` 이 고정 문장이고, 그 상수의 주석은
"대상 판별이 `isError` 단언 실패만 통과시키므로 이것 말고 나올 수 없다" 고 적었다. 그 전제가
틀렸다. `convert_units` 를 실서버로 돌린 결과다.

```
✗ convert-units-success  convert_units가 오류 없이 응답한다
    툴 'convert_units' 호출 중 오류가 발생했습니다.
    → 원인: MCP error -32602: Structured content does not match the tool's output schema: data must have required property 'converted'
    해결: 요청한 tool과 서버 기능 및 진단을 확인하세요.
    isError                         (건너뜀) MCP 작업 결과가 없어 assertion을 검사할 수 없습니다.
    해결: 먼저 MCP 작업 실패 원인을 해결하세요.
    structuredContentMatchesSchema  (건너뜀) MCP 작업 결과가 없어 assertion을 검사할 수 없습니다.
    해결: 먼저 MCP 작업 실패 원인을 해결하세요.
```

`repair-target.ts` 의 `failedByIsError` 는 본문 줄이 `isError` 로 시작하기만 하면 실패로 읽는데,
위 블록의 그 줄은 **건너뛴 단언**이다. 실패는 호출 자체가 던진 것이고 입력값과 무관하다. 그래서
화면은 `정상 응답을 기대했지만 오류 응답을 받았습니다` 라고 말하고 같은 실행의 실패 목록은
`MCP error -32602` 라고 말한다. 두 화면이 서로를 반박하며, 어떤 값을 넣어도 못 고치는 케이스에
대해 사용자에게 `value` · `from` · `to` 를 세 번 묻는다. 필드 질문 자체도 제안이 있을 때와 없을 때
형식이 갈려, 제안이 있으면 `value: [1]` 한 줄뿐이라 툴 이름도 현재 값도 선언 타입도 없다.

## 선택지

1. **제안 값·제외 사유·실제 진단을 화면에 싣고, 호출이 던진 케이스는 구조화된 필드로 골라
   교정 대상에서 뺀다.** (채택)
2. **`(건너뜀) ` 문자열로 교정 대상을 판별한다.** 한 줄이면 끝난다. 버렸다. 렌더 문안이 바뀌면
   조용히 깨지고 깨진 것을 알아채는 곳이 없다. 이번 결함이 정확히 그 방식의 결과이며, 구조화된
   `operation.status` 가 이미 `RunnerReport` 에 있다.
3. **보류 케이스를 설명 없이 교정 단계로 바로 넘긴다.** 버렸다. 두 단계가 다른 값을 제안할 수
   있고(실측이 그랬다) 사용자는 여전히 왜 달랐는지 모른다. 보류는 `--no-repair` 경로에도 생긴다.
4. **`selectRepairTargets` 의 반환 타입을 그대로 두고 `thrown` 을 별도 함수로 뺀다.** 버렸다.
   호출 측이 같은 앞단 조건을 두 번 쓰게 되고, 조건이 갈리면 어느 케이스가 양쪽에 다 들어가거나
   어디에도 안 들어간다.
5. **필드 질문에서 툴 이름을 뺀다.** 머리줄에 케이스 이름이 있으니 중복이라는 주장이다. 버렸다.
   케이스 이름은 `evaluate_expression가 오류 없이 응답한다` 같은 사람 문장이라 툴 이름을
   기계적으로 못 뽑고, 값 재사용 고지가 이미 `get_weather.city` 형식을 쓴다.

## 결정

**1. 보류 케이스는 제안 값과 서버 위반 줄을 화면에 적는다 (cli).** `ApplyPreFillResult.cases` 의
각 항목이 보류일 때만 `proposedFields`(`{ field, value }` 배열)와 `serverMessage`(AI 회차에서
서버가 낸 위반 줄)를 싣고, 요약이 보류 줄 아래에 케이스마다 블록을 하나 찍는다. 보류만 싣는
것은 채택된 값은 명세 파일에 저장돼 사용자가 읽을 수 있고 미채택은 baseline 이 이미 통과했기
때문이다. 보류만 화면에도 파일에도 없는 상태다.

**2. `targetIds` 에서 빠진 제안은 사유와 함께 `제외` 로 센다 (cli).** `ApplyPreFillResult` 에
`excluded: readonly PreFillExclusion[]` 을 더한다. 제안 하나(케이스 하나의 필드 하나)마다 한
항목이고 사유는 `명세에 없는 케이스` · `callTool 이 아닌 케이스` · `입력이 객체가 아닌 케이스`
셋뿐이다. 개수만 세지 않는 것은 `버림` 줄과 같은 규칙이다. 조기 반환 경로에서도 채운다.

**3. 호출이 던진 케이스는 교정 대상이 아니다 (cli).** 판정을 렌더된 텍스트가 아니라
`operation.status !== "completed"` 로 한다. `DryRunCaseOutcome` 에 `operationFailed` 와
`failureLine` 을 더하고, `selectRepairTargets` 는 `{ targets, thrown }` 을 돌려준다. `thrown` 은
교정 화면 맨 앞에서 한 번 고지하며, 그 판별은 `targets` 와 같은 앞단 조건을 공유한다.

**4. 교정 머리말은 고정 문장이 아니라 그 케이스의 실제 진단이다 (cli).** 상수 `FAILURE_LINE` 을
지우고 `RepairTarget.failureLine` 을 쓴다. 서버가 준 위반 줄도 함께 찍는다. 번호는 `[1]` 이
아니라 `[1/4]` 로 전체 수를 붙여 사용자가 몇 번을 더 답해야 하는지 알게 한다.

**5. 필드 질문은 제안 유무와 무관하게 한 형식이다 (cli).** 괄호 안에 필드 진행도, 선언 타입,
현재 값, 엔터의 뜻을 순서대로 넣고 필드 이름 앞에 툴 이름을 붙인다.

```
      convert_units.value (필드 1/3, number, 현재 0, 엔터 = 제안 값 1): 
      convert_units.value (필드 1/3, number, 현재 0, 엔터 = 현재 값 유지): 
```

선언 타입을 못 읽은 필드는 그 자리만 뺀다. 없는 타입을 지어내지 않는 기존 규칙 그대로다.

곁들여 대시보드도 둘 바뀐다. `WebReviewIO.answer()` 가 답을 `stdout` 이벤트로 되비추고(터미널의
readline 이 하는 일을 웹에서 대신한다. CLI 쪽은 두 줄이 나므로 안 건드린다), generate 폼 4단계에
`--diagnose-rejections` 토글이 생긴다.

## 이유

ADR-0098 은 **무엇을 보일지**를 줄이는 결정이었다. 기본 화면의 미확인 목록 수십 줄이 전부 정상
거절이라 소음이었기 때문이다. 이 ADR 은 반대 방향이다. 남은 줄이 **자기 근거를 달고 나오게**
한다. 소음을 줄인 화면에서 남은 한 줄이 근거 없이 숫자만 말하면, 사용자는 그 줄도 읽지 않는다.

판정을 렌더된 문자열이 아니라 구조화된 필드로 옮기는 것이 이번 회차의 핵심이다. `failedByIsError`
가 `(건너뜀) ` 접두사를 못 본 것은 실수 하나가 아니라 방식의 결과다. 화면 문안은 사람 읽기 좋게
계속 바뀌는데 그것을 판정 입력으로 쓰면 바뀔 때마다 조용히 틀린다. `RunnerReport` 의
`operation.status` 와 `assertions[].status` 가 이미 있으므로 텍스트를 다시 파싱할 이유가 없다.

반대로 **화면에 찍는 문장은 `renderReport` 가 만든 줄을 그대로 옮긴다.** 새 문장을 지으면 같은
실패를 `test` 에서 볼 때와 `generate` 에서 볼 때 낱말이 갈린다. 판정은 구조로, 표시는 원문으로
가 이 결정의 규칙이다.

교정 대상에서 빼는 것이 "덜 돕는" 선택으로 보일 수 있으나 반대다. 입력값을 어떻게 바꿔도 서버의
`outputSchema` 불일치는 안 고쳐진다. 세 번 묻고 세 번 실패시키는 것은 시간을 뺏는 일이고, 더
나쁘게는 "입력값이 거절된 것으로 보입니다" 라고 틀린 원인을 가르친다. 이 케이스들은 분류 화면과
사후수리(`repair` 명령)가 받을 몫이고 그 경로는 이미 있다.

## 결과

- **이 ADR 이 원본 교정 설계 `docs/superpowers/specs/2026-08-15-dry-run-input-repair-design.md`
  의 §8.6 · §8.6.1 을 대체한다.** 그 두 절이 고정한 교정 머리말과 필드 질문 문안은 더 이상 맞지
  않는다. 새 문안은 2026-09-13 설계 문서 §4.3 · §4.4 · §4.5 에 있다. 원본 문서에는 그리로
  가리키는 정정 인용 블록이 들어가 있다. 교정 회차 수·캐시·되돌리기 규칙(원본 §4)은 그대로다.
- **사용자 표면이 다섯 바뀐다.** 사전보완 요약에 보류 블록과 `제외` 줄이 생기고, 교정 단계 앞에
  `교정 대상이 아닌 실패 N건` 고지가 생기며, 교정 머리말이 실제 진단을 찍고, 필드 질문이 한
  형식으로 합쳐지고, 대시보드가 답을 로그에 되비추며 `--diagnose-rejections` 토글을 갖는다.
- **실측 문서 §4 의 관측 둘이 모두 닫힌다.** 관측 "하나" 는 ADR-0098 결정 3, 관측 "둘" 은 이
  ADR 의 결정 2 다.
- **남는 갈래 둘.** `--determinism` 에서 SDK 가 던지는 케이스의 단언 상태가 1회차 `skipped`,
  2회차 `passed` 로 흔들리는 문제는 runner 소유라 별도 이슈다. 사후수리(`repair` 명령)의 화면은
  이번 범위가 아니라 교정 단계와 문안이 갈린 채로 남는다.
- **되돌리는 조건.** `operationFailed` 로 대상에서 뺀 케이스 중 실제로 입력값으로 고쳐지는 것이
  나오면 결정 3 의 판정 조건을 다시 논의한다. 근거는 "빠질 것 같아서" 가 아니라 실제 사례여야
  한다.
