# ADR-0103: 한 번에 검증은 승인 질문에 자동으로 답하고 생성과 실행을 잇는다

- 상태: 제안
- 날짜: 2026-09-28
- 담당: cli · dashboard
- 작성자: @seodduu
- 참조: ADR-0046(대시보드는 cli 커맨드 함수를 부른다), ADR-0098(승인 화면은 실패한 케이스만 AI 에 보낸다),
  ADR-0089(시험 실행이 꺼지면 사전보완도 건너뛴다), `docs/benchmark/token-comparison/results.md`

## 배경

`mcpeak generate` 는 사람이 단계마다 보는 흐름이다. 사전보완 전송, 시험 실행, 실패 분류, 교정 값
입력, 재검증, 저장을 각각 묻는다. 그 문턱은 ADR-0098 이 의도한 것이고 사람에게는 옳다.

토큰 비교 실험(`docs/benchmark/token-comparison/`)이 그 흐름을 에이전트에게 그대로 시켰을 때
무슨 일이 생기는지 보여 줬다. 도구 2·3·6개 서버 세 곳에서, `generate` 와 `test` 를 단계별로 부르는
에이전트는 md 지침만 받고 클라이언트를 직접 짠 에이전트보다 비용을 10~40% 더 썼다. 검출률은
같았다. 원인은 단계마다 에이전트 턴이 생기고 턴마다 컨텍스트 4~5만 토큰이 다시 읽히기 때문이다.
턴 하나가 케이스 수백 개를 코드로 쓰는 분량이다. 케이스를 대신 만들어 주는 이득이 왕복 비용에
묻힌다.

같은 실험에서 판단을 도구 안으로 옮기고(자리값 분류를 좁은 LLM 호출 하나로) 생성부터 보고서까지
명령 하나로 묶은 시험 버전은 전 과정에서도 비용이 48~49% 줄었다. 검출률은 그대로였다.

대시보드에는 이미 사전보완과 provider 배선이 있고(ADR-0046 대로 `cli` 함수를 부른다), 사람이 세
번 승인하는 것만 다르다.

## 선택지

1. **`ReviewIO` 구현 하나로 승인 질문에 정해진 정책으로 답한다(`autoReviewIO`). 대시보드는 그것으로
   `generate` 를 돌리고 저장된 명세로 `test` 를 잇는 `verify` 플로우를 둔다.** (채택)
   판정 로직은 한 줄도 새로 쓰지 않는다. 질문마다 어떤 답을 고르는지만 정한다.
2. `generate` 에 `--approve auto` 플래그를 넣어 흐름 안에서 질문을 건너뛴다.
   기각. 질문 지점이 3천 줄 파일 안 열 곳에 흩어져 있어 각각에 분기가 생긴다. 사람용 흐름과 자동
   흐름이 한 함수 안에서 얽히고, 질문을 하나 더할 때마다 두 갈래를 다 고쳐야 한다.
3. 실험용 래퍼(`mcpeak-agent.mjs`)를 그대로 제품에 넣는다.
   기각. 자리값 분류기를 자체 LLM 호출로 다시 짠 것인데, 제품에는 선언 위반 검사까지 하는
   사전보완(ADR-0064)이 이미 있다. 같은 일을 두 번 만들 이유가 없다.

## 결정

- `cli` 가 `autoReviewIO(sink)` 를 `@mcpeak/cli/commands` 로 내놓는다. 정책은 다음과 같고 고른
  답은 `▸ 자동 승인: <질문> → <답>` 으로 화면에 남긴다.

  | 질문 | 답 |
  |---|---|
  | 검토 메뉴 | 처음 `save`, 그 뒤 `cancel` (저장이 되돌아오면 반복하지 않고 끝낸다) |
  | 확인 전부 | 예. 단 "그래도 적용합니까"(선언 위반이 남은 후보의 적용)는 아니오 |
  | 실패 분류 `선택:` | `s` 서버 결함. 교정 뒤에도 남은 실패는 명세가 옳고 서버가 틀린 것으로 기록한다 |
  | 교정 값 입력 | 엔터. 제안이 있으면 제안 값, 없으면 현재 값 |

- `dashboard` 는 `verify` 플로우를 둔다. generate argv 를 받아 `autoReviewIO` 로 `generate` 를
  돌리고, 0 이면 같은 대상 인자와 `--out` 파일로 `test` 를 잇는다. 종료 코드는 `test` 의 것이다.
  `RunIo.reviewIO` 는 `WebReviewIO` 클래스가 아니라 `ReviewIO` 인터페이스로 받는다.
- generate 마법사 마지막 단계에 "한 번에 검증" 버튼을 둔다. 기존 "생성 시작" 은 그대로다.

## 이유

사람의 승인 문턱은 없애는 것이 아니라 **선택**으로 만든다. 승인을 원하는 사람은 지금 흐름을 그대로
쓴다. 자동 흐름을 IO 한 장으로 두면 질문이 늘어도 정책표 한 줄이 늘 뿐이고, 어떤 결정이 자동으로
내려졌는지가 로그에 전부 남는다.

남은 실패를 서버 결함으로 두는 이유는 보류(`?`)가 저장을 막기 때문이다. 자동 흐름에서 막히면
아무것도 얻지 못한다. 결함으로 기록해 두면 `test` 가 그 케이스를 빨간색으로 보여 주고, 사람은 그
화면에서 명세가 틀렸는지 서버가 틀렸는지를 판단한다. 판단이 사라진 것이 아니라 뒤로 옮겨진 것이다.

## 결과

- 실측(`examples/weather-server/server.broken-demo.mjs`, provider claude): 사전보완이 `city`
  자리값을 `서울` 로 고쳐 픽스처로 저장하고, 남은 4건을 서버 결함으로 분류해 저장한 뒤 `test` 가
  정확히 그 4건만 실패로 찍었다. 사람 질문은 0회였다.
- 대시보드를 Claude Code 세션 안에서 띄우면 `CLAUDECODE` 환경변수가 자식 `claude` 에 상속돼
  provider 가 `providerFailed` 로 끝난다. 사용자 터미널에서는 생기지 않는다. 실험 환경의 함정으로
  README 에 적는다.
- 자리값 실패인데 사전보완이 없거나 실패하면 서버 결함으로 기록된다. `test` 화면에 그대로 드러나므로
  숨겨지지는 않지만, "자리값이 의심되면 결함 표에 그렇게 표시" 하는 개선은 후속 과제다.
- 에이전트가 부를 CLI 진입점(`mcpeak verify`)은 이 결정의 자연스러운 다음 단계지만 이 ADR 의 범위
  밖이다.
