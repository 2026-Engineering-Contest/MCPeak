# ADR-0105: 대시보드가 케이스 꼬리표를 직접 매기고, 중계 통로를 run 과 나눈다

## 배경

4 단계 「실제 응답」은 케이스마다 AI 를 하나씩 **동시에** 띄운다. 중계기는 stateless 라
접속을 구분할 식별자가 없고, 기록 줄은 한 채널로 섞여 나온다. 꼬리표를 URL 로 나르기로 한
것(설계 §2-4)까지는 정해져 있었으나, **그 꼬리표의 값을 누가 정하는가**와 **통로를 어디에
두는가**는 열려 있었다. 구현 중에 두 판단이 더 확정됐다 — 중계기 자식에게 넘기는 환경의
폭과, `pnpm test` 가 이 기능을 실제로 돌리는지.

## 선택지

**꼬리표.**
1. 사용자의 케이스 id 를 그대로 URL 에 싣는다.
2. 대시보드가 짧은 자체 꼬리표(`c1` · `c2` …)를 매기고 원래 id 를 따로 나른다.
3. 케이스마다 중계기를 따로 띄운다(꼬리표 자체를 없앤다).

**통로.** ① 기존 `POST /api/runs` 에 flow 를 하나 더한다 ② 중계기 전용 통로 셋을 판다.

**자식 환경.** ① `{ ...getDefaultEnvironment(), ...candidateEnv }`(중계기 자신의 최소
환경 위에 후보 값만 얹는다) ② `{ ...process.env, ...candidateEnv }`(대시보드 프로세스의
환경 전체 위에 얹는다).

**`pnpm test` 범위.** ① 루트 `vitest.config.ts` 의 `e2e` 갈래에 그대로 둔다 ② 패키지 로컬
`vitest.e2e.config.ts` + CI `build` 잡으로 뺀다.

## 결정

꼬리표는 **대시보드가 매긴다**(선택지 2). 통로는 **따로 판다**. 자식 환경은
**`{ ...process.env, ...candidateEnv }`**. `pnpm test` 는 이 기능의 E2E 를 **돌리지 않는다** —
패키지 로컬 `vitest.e2e.config.ts` + CI `build` 잡으로 옮긴다.

## 이유

**꼬리표.** 사용자 케이스 id 는 `readCaseTag`(`packages/mock/src/relay-log.ts`)의 길이·문자
상한에 걸려 **조용히 사라진다.** 사라진 꼬리표는 오류를 내지 않고 그 케이스의 줄을 「꼬리표
없음」으로 떨어뜨려, 화면이 칸을 못 가르는데 아무도 이유를 모른다. 대시보드가 매기면 항상
상한 안이고 항상 안전한 문자다. 화면 칸 제목은 사용자가 아는 이름이어야 하므로 `RelayCase`
가 `id` 와 `tag` 를 둘 다 나른다 — 나르는 값과 보이는 값을 가른다. 케이스마다 중계기를
따로 띄우면(선택지 3) 사용자의 서버가 N 벌 뜬다. 상태를 가진 서버에서 그것은 다른 실험이다.

**통로.** 중계기는 **스스로 끝나지 않는 유일한 실행**이다. 「그만」이라고 말하는 길이
필요한데 `RunRegistry` 에는 취소가 없고 `RunSummary` 는 끝나는 실행을 전제한 모양이다.
얹으면 그 타입들이 전부 「끝나지 않을 수도 있는 실행」을 담게 된다.

**자식 환경 — 좁히지 않는다.** 중계기는 사용자의 서버 명령을 **다시 spawn** 한다. `PATH` ·
`HOME` · 프록시 설정처럼 서버가 정상 동작에 필요로 하는 값이 무엇인지 우리는 알 수 없으므로,
`getDefaultEnvironment()` 위에만 후보 값을 얹으면 `mcpeak test` 로는 잘 뜨던 서버가 중계기
뒤에서는 이유 없이 죽는 사례가 생긴다. `{ ...process.env, ...candidateEnv }` 를 쓰고,
후보 값이 그 위를 덮는다(`/api/runs` 경로의 `readEnv` 와 같은 우선순위,
`packages/dashboard/src/server/wiring.ts:111`). **대가는 마스킹이 필요해졌다는 것이다** —
기동 실패 진단에 자식 stderr 마지막 줄을 실을 때, 그 환경(부모 `process.env` 포함)의 값이
그대로 찍혀 있을 수 있다. `packages/dashboard/src/server/relay-session.ts` 의
`diagnosticTail` 이 알려진 값을 문자열 치환으로 가리며, 임계값(`MIN_MASK_VALUE_LENGTH`)은
20 이다 — `packages/record/src/external/origin-redaction.ts` 의 `MIN_SECRET_LENGTH`
(R4, ADR-0097)와 같은 선이다. 근거는 다르다(그쪽은 "비밀처럼 생겼나"를 접두사 모양으로
재고, 여기는 "이미 아는 값을 가릴지"를 잰다) — 다만 같은 저장소 안에서 "짧은 값은 비밀
취급하지 않는다"는 문턱을 두 자리에 따로 두지 않으려고 값을 맞췄다.

**`pnpm test` 범위 — E2E 를 뺀다.** 이 기능의 E2E(`packages/dashboard/tests/relay-e2e.test.ts`)
는 `relayBinPath()` 로 **빌드된** 중계기를 자식으로 띄운다. CI 의 `verify` 잡은
`pnpm build` 없이 돌고, vitest 워크스페이스 별칭이 패키지를 **소스로** 해석하므로, `dist/`
가 없는 상태에서 이 스펙을 루트 `e2e` 갈래에 두면 이유 없이 빨개진다. `mock` · `cli` ·
`record` 의 기존 "Verify built …" CI 스텝들과 같은 판단이다 — 산출물을 실제로 띄우는
스펙은 빌드 뒤에만 의미가 있으므로, 빌드가 보장되는 자리(패키지 로컬 `test:e2e` + CI
`build` 잡)로 옮긴다.

## 결과

- `RelayCase.tag` 가 공개 면에 생긴다. 브라우저와 서버가 같이 쓴다.
- `DELETE /api/relay/:id` 가 **닫힌 것을 확인하고 나서** 응답한다. 브라우저의
  `[실행 시작]` 이 그 응답을 기다린다 — 안 그러면 같은 서버가 두 벌 뜬다.
- `dashboard` 가 `@mcpeak/mock` 에 의존한다(`relayBinPath()`). 의존 방향표에 이미 허용된
  아래 방향이라 경계는 유지된다.
- `generate` 의 공개 면은 더 넓어지지 않는다. MCP 를 여는 argv 는 대시보드에만 산다
  (ADR-0104).
- 중계기 자식 환경에 부모 프로세스의 전체 환경이 실린다. 값은 argv 에도 HTTP 응답에도
  싣지 않지만, 기동 실패 시 stderr 되찍기 경로에서는 새 나갈 수 있어 마스킹이
  `relay-session.ts` 에 상주한다 — 이 마스킹을 지우면 이 결정 전체를 다시 봐야 한다.
- `pnpm test` 가 초록이어도 `packages/dashboard/tests/relay-e2e.test.ts` 는 돌지 않았다는
  뜻이다. 그 스펙을 확인하려면 `corepack pnpm build && corepack pnpm --filter
  @mcpeak/dashboard test:e2e` 를 따로 돌려야 하고, CI 에서는 `build` 잡의 "빌드된 중계기
  위에서 대시보드 중계 배선 E2E 를 돌린다" 스텝이 그 자리다.
