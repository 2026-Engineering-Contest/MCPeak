# ADR-0106: 토큰 탭의 "MCP 수정하기" 는 결정론 치환으로만 소스를 고친다

- 상태: 제안
- 날짜: 2026-10-03
- 담당: dashboard
- 작성자: @seodduu
- 참조: ADR-0046, ADR-0102, `docs/plans/2026-10-03-analyze-토큰탭-MCP-수정.md`

## 배경

토큰 탭은 분석 결과를 오버레이 파일로 저장하고 프록시(`mcpeak-optimize-proxy`)로 쓰라고 안내했다.
ADR-0102 가 프록시를 고른 이유는 "남의 서버는 고칠 수 없다" 였다. 그런데 지금 대시보드를 쓰는 사람은
자기 서버를 만드는 개발자다. 고칠 수 있는 서버에 프록시를 한 겹 더 두라는 안내는 맞지 않는다.
사용자가 저장 버튼 대신 "현재 고른 서버를 고치는" 버튼을 요청했다.

제약이 하나 있다. 압축 변경의 상당수는 소스에 글자로 없다. `$schema` 는 SDK 가 zod 스키마를 JSON
Schema 로 바꾸며 붙인다. 예제 서버 셋을 실측하면 live-weather 는 10건 전부가 그렇고, audit-target 은
4건 전부가 소스의 `properties: {}` 이며, zod-notes 는 4건 중 1건(`.describe("…")`)만 소스에 있다.

## 선택지

- **A. 결정론 치환 + 미리보기.** 서버 스크립트 파일에서 변경에 대응하는 글자 패턴을 찾아 지우거나
  바꾼다. 찾은 개수가 변경 건수와 같을 때만 고친다. 적용 전에 파일 diff 를 보이고 확인을 받는다.
- **B. LLM 이 소스를 고친다.** repair 처럼 provider 에 소스와 변경 목록을 준다.
- **C. 안내만.** 파일을 쓰지 않고 어디를 어떻게 고치라고만 보인다.

## 결정

A 로 간다. 오버레이 저장은 화면에서만 빼고 서버 라우트(`PUT /api/overlays/`)와 CLI `--out` 은 둔다.

## 이유

- 같은 입력에 같은 결과가 이 프로젝트의 핵심 가치다. B 는 결과가 매번 달라질 수 있고, 사용자 소스를
  고치는 일이라 틀렸을 때 비용이 크다.
- C 는 안전하지만 사용자가 요청한 "수정" 이 아니다. A 는 미리보기와 확인을 두어 C 의 안전을 대부분
  가져간다.
- "개수가 같을 때만" 규칙은 어느 출현이 어느 도구의 것인지 몰라도 안전하다. 전부 같은 처리를 받기
  때문이다. 개수가 다르면 도구 정의가 아닌 글자(데이터, 주석)가 섞였다는 뜻이라 건드리지 않는다.
- 못 고치는 변경을 숨기지 않는다. "SDK 가 만드는 값이라 소스에서 고칠 수 없다" 는 문장이 곧 제품이다.
  그런 변경이 필요하면 프록시가 여전히 답이고, 그래서 라우트를 지우지 않는다.

## 결과

- 대시보드가 처음으로 사용자의 **서버 소스**를 쓴다. 쓰는 대상은 실행 명령에서 찾은 프로젝트 루트 안의
  스크립트 파일 하나로 한정하고(`node_modules` 제외), mtime 충돌 검사를 거친다.
- 진입 스크립트가 import 하는 다른 파일의 정의는 고치지 못한다. "찾지 못함" 으로 보인다.
- 지원 패턴은 좁다(설명 문자열, `.describe()`, `description:` 속성, 빈 `properties`·`required`,
  `additionalProperties: true`, 문자열 값의 `$schema`·`$id`·`$comment`·`title`). 넓히려면 이 ADR 을 고친다.
- HTTP 서버는 소스 위치를 알 수 없어 대상이 아니다.
