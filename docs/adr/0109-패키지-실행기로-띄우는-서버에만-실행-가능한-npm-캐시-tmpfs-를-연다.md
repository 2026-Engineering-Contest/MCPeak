# ADR-0109: 패키지 실행기로 띄우는 서버에만 실행 가능한 npm 캐시 tmpfs 를 연다

- 상태: 제안
- 날짜: 2026-10-04
- 담당: audit
- 작성자: @seodduu
- 참조: ADR-0107, ADR-0108, `docs/reports/2026-10-04-sandbox-N1.md`

## 배경

`mcpeak audit --sandbox -- npx -y <패키지>` 가 격리 안에서 뜨지 않았다. 격리 컨테이너는 루트 파일 시스템과
홈(`/home/node`)이 읽기 전용이고 쓸 수 있는 자리는 `/tmp` 하나다. npm 은 받은 패키지를 `~/.npm` 에 두는데 그
디렉터리를 만들지 못해 `ENOENT: mkdir '/home/node/.npm'` 으로 죽고, CLI 는 "서버에 붙지 못했습니다" 를 냈다.
MCP 서버를 `npx` 로 띄우는 것은 가장 흔한 설치 방식이라, 이 경로가 막히면 격리 점검을 쓸 수 있는 서버가
로컬 `node` 서버로 좁아진다.

쓰기만 열어서는 풀리지 않는다. `npx` 는 받은 패키지의 bin 을 캐시 안에서 **실행**하고, Docker 의 `--tmpfs` 는
기본이 `noexec` 다.

## 선택지

- (가) `/tmp` 를 `exec` 로 열고 캐시를 그리로 돌린다. 기각. `/tmp` 는 모든 서버가 쓰는 자리다. `node` 로 띄운
  서버까지 "받아서 쓰고 실행하는" 자리를 갖게 된다.
- (나) `npm_config_cache=/tmp/.npm` 으로 캐시 자리만 돌린다. 기각. 실측에서 패키지는 받아지지만
  `sh: 1: mcp-server-everything: Permission denied` 로 죽었다. `noexec` tmpfs 를 `~/.npm` 에 얹어도 같다.
- (다) 호스트에서 패키지를 미리 받아 읽기 전용으로 붙인다. 기각. 설치 스크립트와 실행기의 코드가 격리 밖인
  사용자 머신에서 돈다. 격리의 목적과 어긋난다. 호스트와 컨테이너의 플랫폼이 다르면 네이티브 모듈도 맞지 않는다.
- **(라) 원래 명령의 basename 이 `npx`·`npm` 일 때만 target 컨테이너에
  `--tmpfs /home/node/.npm:rw,exec,size=512m,uid=1000` 을 더한다.** (채택)

## 결정

(라)로 간다. 판정은 명령의 basename 으로 하고(`/opt/homebrew/bin/npx` 도 `npx` 다) 인자는 보지 않는다. `node`
로 띄우는 서버에는 더하지 않는다. `/tmp` 는 어느 명령에서도 `noexec` 그대로다. `--read-only`, `--cap-drop ALL`,
`no-new-privileges`, 읽기 전용 마운트 셋은 바꾸지 않는다. 마운트 자리는 읽기 전용 바인드 아래라 Docker 가
만들 수 없으므로, 백엔드가 임시 홈에 자리 파일(`.npm/.mcpeak-mount`)을 써서 디렉터리를 미리 만든다. tmpfs 가
덮어 컨테이너에서는 보이지 않는다.

잡음 표에는 `npm-cache` 행을 더한다. 명령이 `npx`·`npm` 일 때 `start` 단계의 `/home/node/.npm/` 아래 쓰기
열기와 지우기·옮기기만 뺀다. 호출 단계의 같은 경로는 빼지 않는다.

## 이유

- 실행 가능한 쓰기 영역은 격리를 넓히는 것이라 필요한 실행에만 연다. `npx` 로 띄운 서버는 어차피 방금 받은
  코드를 실행하는 것이 전제다. 그 전제가 없는 `node` 서버의 격리는 전과 같다.
- 자리를 `~/.npm` 하나로 좁히면 잡음 표도 접두 하나(`/home/node/.npm/`)로 좁게 쓸 수 있다.
- tmpfs 는 컨테이너와 함께 사라진다. 받은 패키지가 호스트에 남지 않고, 실행마다 빈 캐시에서 시작해 이전
  실행의 캐시가 다음 판정에 섞이지 않는다.

## 결과

- `npx`·`npm` 으로 띄우는 서버가 격리 안에서 뜬다. 실측에서 `@modelcontextprotocol/server-everything` 이
  `initialize` 에 답했고, 채집한 기록의 `start` 단계에서 `/tmp`·`/home/node/.npm` 밖 쓰기는 없었다.
- 한계 1: 캐시가 512MB 를 넘는 패키지는 받다가 `ENOSPC` 로 죽는다. tmpfs 는 컨테이너 메모리 한도(1GB)에도
  잡힌다.
- 한계 2: 서버가 호출 중에 그 자리에 파일을 쓰고 실행하는 것은 **막지 못한다.** 관측으로만 드러난다
  (`behavior/write-outside`, `behavior/child-process`).
- 한계 3: `start` 단계에는 실행기와 서버의 시작 코드가 함께 돈다. 사건에 PID 를 싣지 않으므로 서버가 시작하면서
  그 자리에 쓴 것은 실행기의 것과 가르지 못하고 함께 빠진다.
- 한계 4: 캐시가 매번 비어 있어 실행마다 패키지를 새로 받는다. 시작이 느리다(실측 약 9초). 접속 제한 시간과의
  관계는 보고서에 적었다.
