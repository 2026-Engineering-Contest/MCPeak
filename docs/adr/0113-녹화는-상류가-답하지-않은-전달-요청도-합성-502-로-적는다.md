# ADR-0113: 녹화는 상류가 답하지 않은 전달 요청도 합성 502 로 적는다

- 상태: 제안
- 날짜: 2026-10-04
- 담당: audit
- 작성자: @seodduu
- 참조: ADR-0107, `docs/plans/2026-10-04-audit-오탐과-재생-비대칭-수정-구현계획.md` §2·§4·§5.2,
  `docs/plans/2026-10-03-audit-샌드박스-행위-관측-구현계획.md` §3·§6·§3.7

## 배경

`mcpeak audit --sandbox` 는 `--sandbox-session` 으로 네트워크 왕복을 녹화하고 `--sandbox-replay` 로
재생한다. 약속은 두 `--json` 출력이 `sandbox.network` 값 하나만 다르다는 것이다. 이 약속은 상류가
응답하는 서버에서만 지켜졌다.

게이트웨이(`sandbox/gateway/forward.mjs`)는 상류가 실제로 응답을 끝냈을 때만 카세트에 적었다. 상류
이름을 풀지 못했거나 접속하지 못하면 게이트웨이가 스스로 502 를 답하고 아무것도 적지 않는다. 그런
요청은 재생에서 카세트에 없어 `network/replay-miss` 가 된다. 예제 표적 서버의 `sync_settings` 가
응답 없는 호스트로 POST 하는 것이 정확히 이 경우다. 녹화 발견 7건, 재생 발견 8건으로 어긋났다.
유출 시도는 죽은 목적지로 가는 일이 흔하므로, 약속이 가장 필요한 자리에서 깨지고 있었다.

## 선택지

| 항목 | 채택 | 버린 것 |
|---|---|---|
| 비대칭을 없애는 자리 | 녹화 단계. 응답 없이 끝난 전달 요청을 고정 문구의 502 로 카세트에 적는다 | (가) 현행 유지. 재생에만 `replay-miss` 가 남는다. (나) 리포트 후처리로 `undeclared-destination` 과 겹치는 `replay-miss` 를 억제. 원인을 가리고 규칙 사이에 숨은 결합이 생긴다 |
| 세션 스키마 | 그대로. 녹화기에 넣는 값만 늘린다 | 항목에 "합성" 표지나 요청 분류를 싣기. 스키마 버전을 올려야 한다 |
| 중복·덧붙음 방지 | 요청마다 깃발 하나. 상류가 응답을 시작했거나 합성 502 를 한 번 적었으면 더 적지 않는다 | 계획서 초안 그대로 `error` 마다 적기. Node 는 응답이 시작된 뒤의 소켓 오류도 요청의 `error` 로 내므로 답한 요청에 502 가 덧붙는다 |
| 게이트웨이가 끊은 접속 | 상류가 응답을 시작하지 않았으면 적는다(클라이언트가 먼저 떠난 경우 포함) | 클라이언트에게 실제로 502 를 써 보낸 경우만 적기. 타임아웃으로 먼저 끊는 서버에서 `replay-miss` 가 남는다 |
| `blocked`·SNI 불일치 | 적지 않는다 | 적기. 재생에서 `replay-hit` 로 바뀌어 `internal-destination` 발견이 사라지는 역비대칭이 생긴다 |

## 결정

- 녹화 모드에서 `served: "live"` 로 전달한 요청이 상류 응답 없이 끝나는 두 경로(이름 풀이 실패, 접속
  오류)에서 `{ status: 502, content-type: text/plain, 고정 문구 본문 }` 을 그 요청의 키로 적는다.
- 관측(`note("live")`)과 클라이언트에게 가는 응답은 바꾸지 않는다. 발견은 관측에서 나온다.
- 한 요청에 합성 응답은 많아야 한 번 적힌다. 상류가 응답을 시작한 요청에는 적지 않는다.
- 세션 스키마(`SESSION_SCHEMA_VERSION`, `MatchKey`, `SessionEntry`)와 `createRecorder`·`createReplayer`·
  `parseSession` 의 꼴은 그대로다.

## 이유

- 재생의 `replay-hit` 와 녹화의 `live` 는 network 규칙에서 똑같이 declared/undeclared 로만 갈린다.
  카세트에 항목만 있으면 양쪽 발견이 같아진다. 가장 작은 변경으로 약속을 유출 목적지까지 넓힌다.
- 합성 응답은 고정 문자열이다. 오류의 종류(ECONNREFUSED, ETIMEDOUT)나 문구가 카세트에 실리지 않아
  같은 입력을 두 번 녹화하면 세션 파일이 바이트까지 같다.
- 녹화 때 클라이언트가 받은 것도 같은 502 이므로, 재생이 그 502 를 돌려주는 것은 서버 입장에서 같은
  세계다. 후처리 억제와 달리 리포트 규칙을 건드리지 않는다.

## 결과

- 예제 표적 서버의 녹화·재생 `--json` 이 `sandbox.network` 한 줄만 다르다. Docker E2E 가 이를
  고정하고, 재생에 `network/replay-miss` 가 없다는 것도 함께 단언한다.
- 한계 1(N2). 호스트명이 내부 주소로 풀려 녹화에서 `blocked` 가 되는 요청은 재생에서 이름 풀이를 하지
  않으므로 같은 분류를 낼 수 없다. 대칭을 맞추려면 세션에 요청 분류를 실어야 하므로 스키마 버전을
  올리는 별도 ADR 로 미룬다. 예제 표적 서버의 내부 접속은 IP 리터럴이라 이 경로를 밟지 않는다.
- 한계 2. 상류가 응답을 시작한 뒤 끊긴 요청은 적지 않는다. 끊긴 지점의 바이트가 실행마다 다를 수 있다.
- 한계 3. 세션을 거두는 시점에 아직 매달려 있는 요청(응답도 오류도 없음)은 카세트에 없어 재생에서
  `replay-miss` 가 된다. 키를 계산하기 전에 실패한 요청의 502 도 녹화하지 않는다.
- 한계 4. 클라이언트가 먼저 떠나 게이트웨이가 접속을 끊은 요청은 녹화 때 502 를 받지 못했지만 재생에서는
  받는다. 발견은 같고 서버가 보는 응답만 다르다. 클라이언트의 중단과 상류 응답이 경합하는 서버는
  녹화 자체가 실행마다 달라질 수 있고, 이것은 이 결정이 만든 문제가 아니라 그 서버의 비결정성이다.
