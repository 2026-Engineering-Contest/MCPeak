# ADR-0117: Analyze 는 점검 옵션 없이 격리를 자동으로 시도하고, 서버 선택 뒤 축 카드로 결과를 고른다

- 상태: 제안
- 날짜: 2026-10-19
- 담당: dashboard
- 작성자: @seodduu
- 참조: ADR-0116, ADR-0110, ADR-0111, `docs/2026-10-18-analyze-통합-대시보드-설계.md` §3,
  `docs/reports/2026-10-19-analyze-C3.md`, `docs/reports/2026-10-19-analyze-simplify.md`

## 배경

ADR-0116 의 Analyze 는 대상 영역(접속 폼과 점검 옵션) → 축 카드 셋 → 고른 축의 상세였다. C3 실환경
확인(2026-10-19)에서 세 가지가 드러났다. 점검 옵션(호출 정책·기준 파일·Docker 격리·허용 호스트)은
대시보드에서 쓰는 사람이 없고 폼만 길어진다. 처음 화면에 결과가 없는 카드 셋과 "아직 분석하지 않았습니다"
안내가 먼저 깔려, 서버를 고르는 단계와 결과를 보는 단계가 한 화면에 섞인다. 보안 결과는 발견 목록만 보여
"검사했는데 깨끗했다" 와 "검사하지 않았다" 를 구분할 수 없다.

## 선택지

- **(a) 점검 옵션 유지, 카드 유지.** ADR-0116 그대로.
- **(b) 점검 옵션 제거, 카드 줄 제거, 두 상세 상시 펼침, 보안 상세에 "안전" 구획.**
- **(c) 점검 옵션 제거, 카드 구조 유지, 서버 선택 → 결과 두 단계, 보안 카드·상세에 "안전".** 기준 파일·
  호출 정책은 CLI `mcpeak audit` 에서만 고른다. 격리는 고르지 않는다. 처음 결정은 "사용자 환경에서 기본
  정책으로 점검" 이었고, 사용자 결정(2026-10-19)으로 "격리를 자동으로 시도하고 못 하면 로컬 readonly" 로
  바꿨다(결정 5).
- **(d) 점검 옵션은 "고급" 접힘 안에 남긴다.**

## 결정

(c) 를 고른다. 처음 구현은 (b) 였고, 사용자 확인 뒤 카드 부분을 (c) 로 바꿨다. 다섯 결정이다.

1. **점검 옵션 제거.** 사용자가 고르는 옵션이 없다. 보안 요청 본문은 `{ argv, serverId? }` 이고, 격리할 수
   있는 대상이면 결정 5 의 두 필드만 더한다. 서버 API(`AnalyzeSecurityRequest` 의 선택 필드와
   `prepareSecurityRun` 의 가둠)는 그대로 둔다. 기준 파일·호출 정책은 CLI `mcpeak audit` 에서만 고른다.
   사용자 모드 사전 점검(`PreCheck`)의 격리 기능은 이 결정 밖이다.
2. **카드 구조 유지와 두 단계 흐름.** ADR-0116 의 축 카드 셋(보안, 비용 최적화, 성능 효율성 비활성)과
   `role="tablist"`·`tab`·`tabpanel`, `#/analyze/<pillar>` 라우트, 카드를 누르면 그 축 상세가 카드 아래
   펼쳐지는 구조는 그대로다. 그 위에 두 단계를 얹는다.
   - **서버 선택 단계**: 두 축 상태가 모두 idle 이면 화면은 머리말과 대상 영역(접속 폼·"분석하기")뿐이다.
     카드 줄도 상세도 빈 안내도 없다. 주소가 `#/analyze/security` 처럼 축을 가리켜도 상세를 그리지 않고
     해시는 그대로 둔다.
   - **결과 단계**: 어느 축이든 idle 을 벗어나면(분석하기를 눌렀으면) 대상 영역 아래 카드 셋이 붙는다.
     상세는 라우트에 축이 있을 때만 펼쳐진다. 둘 다 시작에 실패해도 결과 단계다(카드가 실패를 보인다).
     "대상 바꾸기" 로 폼을 다시 펼쳐도 카드는 남는다. 두 훅에 idle 로 돌아가는 전이가 없어 한 번 넘어가면
     서버 선택 단계로 돌아가지 않는다. 단계는 따로 상태를 두지 않고 두 축 상태에서 읽는다.
   축 상태 독립, 같은 틱 동시 시작, 최초 성공 시 대상 영역 접기, `rememberCommand` 1회는 그대로다.
3. **보안 상세의 "안전" 구획.** `@mcpeak/audit` 가 공개하는 규칙 목록 상수(DESC·SCHEMA·LAUNCH·PROTOCOL·
   SURFACE·SECRET·RESULT·FLOW·BEHAVIOR·NETWORK 순) 중 family 가 `report.skipped` 에 없고 ruleId 가
   `report.findings` 에 없는 규칙을 "발견 없이 통과한 검사" 로 센다. behavior·network family 는 격리가 실제로 돈
   실행(`report.sandbox.status === "ran"`)에서만 센다. audit 는 격리를 요청하지 않은 실행에서 두 family 를
   `skipped` 에 넣지 않으므로, skipped 에 없다고 돈 것이 아니다. 계산은 대시보드 서버
   (`server/passed-rules.ts`)가 하고 응답 `passedRules` 로 싣는다. 브라우저는 `@mcpeak/audit` 를 값으로
   import 하지 않기 때문이다. 순서는 상수 나열 순서, 상수 안 순서 그대로다. 구획은 보안 상세에서 발견 목록
   바로 다음, "검사하지 않은 것" 위에 온다. `SecurityResult` 의 선택 prop `passedChecks` 로 끼우고, 사전
   점검은 넘기지 않아 그 화면은 바뀌지 않는다.
4. **보안 카드의 "안전" 칩.** 설계 §6.1 의 다섯 칩(심각·주의·낮음·정보·흐름 경고) 뒤에 여섯째 칩
   `안전 N`(done 톤, N 은 `passedRules` 길이)을 붙인다. 판정 배지는 바꾸지 않는다.
5. **격리 자동 시도, 못 하면 로컬 readonly.** "분석하기" 는 격리할 수 있는 대상(stdio 이고 실행 명령의
   basename 이 `node`·`npx`·`npm`, 즉 격리 이미지가 실행하는 명령)이면 보안 요청에
   `sandbox: { compareHost: false, allowHosts: [] }` 와 `sandboxOptional: true` 를 싣는다. 원격 서버와 그 밖의
   명령은 싣지 않는다.
   - **격리 안의 호출 정책.** 대시보드는 `probe` 를 보내지 않는다. CLI `audit-command.ts` 의
     `sandboxOptions` 는 `--probe` 가 없으면 격리 안을 `all`, 격리 밖을 `readonly` 로 돌린다(ADR-0107).
     컨테이너 안의 쓰기 도구 호출은 호스트에 닿지 않으므로 이것이 의도와 같다. 대시보드가 고칠 것은 없다.
   - **Docker 를 못 쓸 때.** audit `startSandbox` 가 `backend.detect()` 로 판정해 격리 없는 경로(`auditDirect`,
     `options.probe` = readonly)로 돌고 `report.sandbox` 에 `{ status: "unavailable", reason }` 을 싣는다.
     대시보드는 Docker 를 대신 켜지 않는다.
   - **격리 범위를 정하지 못할 때.** CLI 는 audit 를 부르기 전에 마운트 범위를 정한다. 서버 인자가 범위
     (대시보드 루트에서 가장 가까운 `pnpm-workspace.yaml`·`.git` 디렉터리) 밖의 파일이거나 범위가 홈이면
     서버를 띄우기 전에 `CLI_USAGE` 로 끝난다. `sandboxOptional` 이면 대시보드 서버가 격리 플래그만 뺀
     argv 로 한 번 더 돌고, 거절 문장의 첫 줄을 응답 `sandboxFallbackReason` 에 싣는다. `sandboxOptional`
     이 없는 요청(사전 점검)은 전처럼 거절이 곧 결과다. 사용자가 격리를 골랐는데 조용히 격리 없이 돌면 안
     된다.
   - **실행 방식 표시.** 보안 카드 요약 줄의 앞과 보안 상세 머리에 어디서 돌았는지를 보인다. 격리됨은
     "격리 실행(Docker)", Docker 를 못 썼으면 "로컬 실행(readonly): <sandboxLine 첫 줄>", 범위 판정에서
     거절됐으면 "로컬 실행(readonly): <sandboxFallbackReason>", 격리를 싣지 않은 대상이면 "로컬
     실행(readonly): 격리할 수 없는 대상입니다". 마지막 문장만 대시보드가 정한다(응답에 사유가 없다).
     판정은 순수 함수 `security-execution.ts` 이고, 괄호 안은 리포트의 `probe` 다.

## 이유

(a) 는 C3 에서 본 문제를 그대로 둔다. (d) 는 옵션을 접어도 `SecurityForm`·`SecurityOptions`·검증
문장·요청 조립 갈래가 전부 남아, 대시보드가 CLI 옵션을 두 번째로 구현하는 자리가 된다. 그 옵션이 필요한
사람은 터미널에서 `mcpeak audit` 를 쓰는 사람이다.

(b) 와 (c) 의 차이는 사용자 결정이다. 서버 선택 단계는 서버를 고르는 일만 하고, 결과는 축 카드에서 골라
본다. (b) 처럼 두 상세를 늘 펼치면 결과가 없을 때도 빈 상세 둘이 깔리고, 결과가 있을 때는 보안 상세가 길어
비용 상세가 화면 아래로 밀린다. 카드는 두 축의 판정과 집계를 한 줄에 나란히 두고, 읽을 축만 펼치게 한다.
빈 카드가 처음부터 깔리던 ADR-0116 의 문제는 두 단계로 푼다. 결과가 없으면 카드를 그리지 않는다.

안전 칩: 상세를 열기 전에도 "얼마나 검사했고 깨끗했는가" 가 카드에서 보여야 안전 구획이 있다는 것을 안다.
판정은 CLI `exitCode`·`counts` 를 따르는 규칙(ADR-0116)이라 칩은 판정에 쓰지 않는다.

건너뛴 family 를 통과로 세지 않는 이유: 돌지 않은 검사는 "발견 없음" 이 아니라 "모름" 이다. `skipped`
는 조용한 통과를 막는 장치(`@mcpeak/audit` types.ts)이고, 안전 구획이 그것을 통과로 바꾸면 장치가
무너진다. 그래서 통과 목록은 "검사하지 않은 것" 구획과 서로 배타다.

문구: 규칙 summary 는 "…이 있는지 본다" 같은 탐지 대상 서술이라 통과 목록에 그대로 두면 발견 목록처럼 읽힌다. 그래서
제목 아래에 "아래 항목을 검사했고 해당하는 것이 없었습니다." 한 줄을 늘 보이고, 줄마다 "해당 없음" 배지를 앞세우며,
목록(규칙 30여 건)은 "검사 항목 N건 보기" 접힘 안에 둔다. 실서버 확인(live-weather-server, 34건)에서 정한 것이다.

격리 자동 시도: 처음 결정(사용자 환경에서만 점검)은 서버 코드를 사용자 머신에서 그대로 실행하고, 행위
관측(파일·프로세스·나가는 요청)을 통째로 버린다. 격리 옵션을 되살리면 결정 1 이 없앤 폼이 돌아온다. 그래서
고르지 않고 늘 시도하며, 못 하면 지금까지와 같은 로컬 readonly 로 간다. 시도가 실패해도 분석이 실패하지 않아야
옵션이 없다는 약속이 지켜진다. 범위 판정 거절을 다시 돌리는 것이 그 때문이다.

결정론: 같은 서버라도 Docker 가 켜져 있는가에 따라 행위·네트워크 가족이 돌거나 건너뛰어 결과가 달라진다. 입력에
"이 머신의 Docker 상태" 가 하나 늘어난 것이다. 이를 숨기지 않고 카드와 상세 머리에 실행 방식을 글자로 보여, 두
결과가 다를 때 사용자가 원인을 바로 본다. 글자는 응답만으로 정해지므로 같은 응답이면 같은 글자다.

## 결과

- 대시보드의 보안 점검은 격리할 수 있는 대상이면 Docker 컨테이너 안에서 돌고, 안에서는 쓰기 도구도
  호출한다(probe `all`). 격리할 수 없거나 Docker 를 못 쓰면 서버 코드를 사용자 머신에서 그대로 실행한다(probe
  `readonly`). 어느 쪽이었는지는 화면이 말한다.
- 첫 실행 비용: 격리 이미지가 없으면 처음 한 번 만든다. 수 분이 걸릴 수 있고, 그동안 보안 카드는 "점검 중…"
  이며 진행은 상세의 진행 로그(SSE)로 본다. 새 타이머는 두지 않았다. 범위 판정에서 거절된 실행은 진행 로그에
  그 `CLI_USAGE` 문장이 먼저 찍힌 뒤 격리 없는 실행의 진행이 이어진다.
- `AnalyzeSecurityRequest` 에 `sandboxOptional`, `AnalyzeSecurityResponse` 에 `sandboxFallbackReason` 이
  늘어난다. `PrepareSecurityOutcome` 은 `fallbackArgv` 를 함께 낼 수 있다.
- 서버 선택 단계에서 축 주소로 들어오면 상세 대신 서버 선택만 보인다. 분석하기를 누르면 그 주소의 축
  상세가 바로 펼쳐진다.
- `AnalyzeSecurityResponse` 에 `passedRules` 가 늘어난다. 사용자 모드 `PreCheck` 는 이 필드를 쓰지
  않는다(화면 변경 없음). `sandboxFallbackReason` 도 쓰지 않는다(사전 점검은 `sandboxOptional` 을 보내지 않아 늘 null 이다).
- 지운 것: `SecurityOptions.tsx`. 원래 문장 `REMOTE_SANDBOX_HINT` 는 `sandbox-hint.ts` 로 옮겼다(사전 점검이
  쓴다). `PillarBadge` 는 `PillarBadge.tsx` 로 옮겨 카드·상세 머리·안전 구획이 함께 쓴다. `PillarCard.tsx`,
  `analyze/types.ts`, `PILLARS`·`PillarDescriptor`, `firstLine` 은 (b) 에서 지웠다가 (c) 에서 되살렸다.
  `build-security-request.ts` 는 그대로 두고 `buildAnalyzeRequests` 가 격리할 수 있는 대상이면
  `{ ...INITIAL_SECURITY_FORM, sandbox: true }`, 아니면 `INITIAL_SECURITY_FORM` 으로 부른다.
- 결과 단계의 접힌 대상 바에는 "분석하기" 가 없다(사용자 결정 2026-10-19). 다시 분석하려면 "대상 바꾸기" 로
  폼을 펼쳐 그 안의 "분석하기" 를 누른다. 도는 동안의 비활성과 사유 문장도 펼친 폼에서만 보인다.
- 보안 판정 배지의 "낮음·정보만" 을 "조치 불필요(참고 N건)" 으로 바꿨다(사용자 결정 2026-10-19). N 은 낮음 + 정보
  건수다. 판정 조건은 그대로다.
