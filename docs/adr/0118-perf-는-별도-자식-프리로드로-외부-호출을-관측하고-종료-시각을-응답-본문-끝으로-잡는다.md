# ADR-0118: perf 는 별도 자식 프리로드로 외부 호출을 관측하고 종료 시각을 응답 본문 끝으로 잡는다

- 상태: 제안
- 날짜: 2026-10-19
- 담당: perf
- 작성자: @seodduu
- 참조: ADR-0013, ADR-0095, ADR-0097, ADR-0100, `docs/perf/2026-10-18-perf-지연-분해-설계.md` §2·§4·§6·§7·§12,
  `docs/perf/2026-10-18-perf-지연-분해-방법론-조사-실험.md` §4·§5, `docs/perf/plans/2026-10-18-perf-지연-분해-구현계획.md` §9

## 배경

`mcpeak perf` 는 도구 호출 하나의 응답 시간을 외부 HTTP 대기와 서버 안 시간으로 나눕니다. 나누려면 서버
프로세스가 밖으로 보낸 요청의 시작과 끝 시각을 알아야 합니다.

조사(§4)에서 실제 서버 19개를 재고 반박 검증을 했더니, "무거운 서버 처리" 로 나온 진단 3건이 전부 측정
오류였습니다. `http.client.response.finish` 는 응답 헤더를 받은 시점에 발생해서, 본문을 내려받는 시간이
서버 처리로 들어갔습니다(airbnb 602ms 가 실제로는 22~38ms). 종료 시각을 응답 본문 끝으로 바꾸자 독립 측정
세 건이 1ms 안에서 일치했습니다. 그래서 관측은 **어디서**, 종료 시각은 **언제로** 잡을지를 정해야 했습니다.

## 선택지

- **(a) record 의 External 어댑터를 확장해 시각을 싣는다.** 이미 `NODE_OPTIONS=--import` 로 자식에 실리는
  프리로드가 있다.
- **(b) 프록시로 바깥에서 잰다.** 서버의 나가는 요청을 HTTP 프록시로 보내 프록시에서 시각을 찍는다.
- **(c) perf 전용 프리로드를 따로 둔다.** 주입 방식은 record 와 같지만 파일이 다르고, 관측만 하고 아무것도
  바꾸지 않는다.

## 결정

(c) 를 고릅니다. 외부 요청의 종료 시각은 모든 경로에서 **응답 본문 끝**으로 잡습니다(fetch 는 서버가 읽은 본문의 끝으로
같은 fetch 의 undici trailers 시각, `node:http` 는 응답 스트림 `end`, http2 는 stream close, undici 는 trailers).

## 이유

(a) 는 소유와 목적이 다릅니다. record 의 어댑터는 녹화·재생이 목적이라 요청을 Coordinator 로 보내고 재생 때
네트워크를 막습니다. perf 는 서버 동작을 바꾸지 않아야 합니다. 한 파일에 두면 재생 경로에 관측 코드가 섞여
한쪽의 결함이 다른 쪽에 번지고, record 오너(② 파트)의 파일을 perf 가 고치게 됩니다.

(b) 는 요청의 시각은 보이지만 그 요청이 **어느 도구 호출 안에서** 나갔는지, 요청 사이에 서버가 무엇을 했는지
가르지 못합니다. 의존 판정에 필요한 응답 본문과 호출 귀속(`AsyncLocalStorage`)도 프로세스 밖에서는 보이지
않습니다. HTTPS 를 보려면 인증서도 바꿔야 해서 측정이 서버 동작을 바꿉니다.

(c) 는 서버 프로세스 안에서 진단 채널과 fetch 래퍼로 시각을 찍고, 본문은 서버가 읽는 스트림을 지나가는 그대로
세어 원래 응답의 소비를 바꾸지 않습니다. 처음에는 응답을 복제(`clone()`)해 끝까지 읽었는데, 최종 리뷰에서 복제(tee)가
서버의 `cancel()` 을 본문 끝까지(끝없는 스트림이면 영원히) 막고 서버가 안 읽은 본문을 통째로 메모리에 쌓는 것을
실측해 통과 스트림으로 바꿨습니다. 그 대가로 서버가 본문을 읽지 않은 요청은 끝 시각이 없고 외부 대기가 하한으로
표시됩니다. 포기한 것은 Node 가 아닌 서버의 분해입니다. Python 서버 등에는 프리로드가 실리지 않아
응답 시간과 콜드 스타트만 내고 "관측 안 함" 으로 표기합니다.

## 결과

- 진단은 종료 코드를 바꾸지 않고, 기준선 회귀만 바꿉니다. 진단은 고칠 자리를 알리는 문장이고, 회귀 게이트
  (`--baseline`, 종료 코드 2)는 서버 안 시간과 외부 요청 수에만 겁니다.
- 외부 대기는 게이트에 넣지 않습니다. 같은 서버의 p50 659ms 대 p95 6,519ms 처럼 네트워크 변동이 커서 서버
  코드와 무관하게 흔들리기 때문입니다. 비교해서 보여주기만 합니다.
- 요청은 두 줄로 기록합니다. 시작할 때 `start` 줄, 끝날 때 `end` 줄을 `(pid, seq)` 로 짝지어 프로세스별
  `${pid}.jsonl` 에 씁니다. worker_threads 도 같은 pid 라 `seq` 를 스레드마다 `threadId × 1_000_000_000 + n` 으로 나눕니다. 끝 줄을 못 쓴 요청(본문을 소비하지 않은 요청, 호출 도중 끝난 프로세스)도 시작 줄이
  남아 외부 대기가 하한으로 표시됩니다.
- 같은 자식에 record 와 perf 의 프리로드를 함께 싣는 조합은 다루지 않습니다. perf 는 `--session`·
  `--record-session` 을 받지 않습니다.
- 남은 일: 녹화한 외부 호출의 소요 시간을 재생해 외부 변동을 없애는 2단계는 record 세션 포맷을 바꾸는 일이라
  record 오너와 따로 정합니다(설계 §13 Q2).
