# ADR-0119: Analyze 성능 축은 명세를 골라 따로 시작하고, 카드는 perf 가 낸 값만 읽는다

- 상태: 제안
- 날짜: 2026-10-20
- 담당: dashboard
- 작성자: @seodduu
- 참조: ADR-0116, ADR-0117, ADR-0118, `docs/2026-10-18-analyze-통합-대시보드-설계.md` §9,
  `docs/2026-10-18-perf-지연-분해-설계.md` §13 Q1,
  `docs/plans/2026-10-20-analyze-성능-카드-perf-연결-구현계획.md`

## 배경

Analyze 화면의 세 번째 카드(성능 효율성)는 자리만 있고 연결되지 않았다(ADR-0116 결과 절). PR #535 가 `mcpeak perf`
를 더해 연결할 재료가 생겼다. 그런데 perf 는 보안·비용 축과 성격이 다르다.

- 보안·비용은 서버에 한 번 붙어 도구 정의를 읽거나 읽기 전용 도구만 부른다. perf 는 **명세(suite) 파일의 성공
  케이스를 그대로 반복 호출**한다. 쓰기 도구도 부르고, 격리 없이 이 컴퓨터에서 서버를 띄운다.
- perf 는 명세 파일이 필수다. 분석 화면은 서버만 고른다(ADR-0117).
- perf 는 원격(HTTP) 서버를 거절한다. 서버 프로세스 안에 관측 코드를 실어야 하기 때문이다(ADR-0118).
- 측정값은 실행마다 다르다. 다른 축이 같은 시각에 Docker 이미지를 빌드하면 CPU 경합으로 서버 안 시간이 부푼다.
- 기준선이 없으면 perf 의 종료 코드는 항상 0 이다. 회귀 판정은 기준선이 있을 때만 나온다.

## 선택지

- **(a) 다른 축과 같이 "분석하기" 한 번에 시작한다.** 명세는 서버 파일 옆의 `*.suite.json` 을 자동으로 고른다.
- **(b) 성능 축만 따로 시작한다.** 상세에서 사용자가 명세(와 반복 횟수, 도구)를 고르고, 시작 전 고지를 본 뒤
  누른다.
- **(c) 성능 축은 CLI 결과 파일을 불러와 보이기만 한다.** 대시보드는 측정하지 않는다.

## 결정

(b) 를 고른다. ADR-0116 의 "축은 한 번에 시작한다" 에서 성능 축만 예외로 둔다.

- 시작 전 고지: 명세의 성공 케이스를 케이스마다 N번 실제로 호출하고 쓰기 도구도 포함된다는 것, 격리 없이 이
  컴퓨터에서 서버를 띄운다는 것, 명세에 승인(approval 블록)이 없으면 그 사실.
- 원격 대상이면 카드는 시작할 수 없다는 사유를 보인다. 결과 판정이 아니다.
- 명세 목록은 홈 마법사의 `matchSuites` 규칙으로 고른 서버에 딸린 명세만 먼저 보이고, 나머지는 "다른 명세 보기" 로
  접는다. 딸린 명세가 없으면 "먼저 명세를 만드세요" 안내와 생성 화면(`#/generate`) 링크를 보인다.
- 다른 축이 도는 동안에는 성능 측정을 시작할 수 없고, 성능이 도는 동안에는 "분석하기" 를 누를 수 없다(R11).
- 카드 배지는 perf 리포트가 가진 값만 읽고, 아래 순서에서 처음 맞는 하나를 보인다.
  관측 안 함 → 측정 중단 → 회귀(기준선이 있을 때) → 진단 N건 → 진단 0건.
  기준선이 없으면 마지막 배지는 "진단 0건(기준선 없음)" 이다. "문제 없음" 은 쓰지 않는다.
- 카드 칩은 측정·미측정·진단 셋이다. 오류 응답이나 타임아웃으로 응답 시간을 하나도 재지 못한 케이스(ok 반복이
  0 인 케이스)는 "미측정 케이스" 로 묶는다. 미측정은 배지 판정을 바꾸지 않는다.
- 성능 상세의 결과는 CLI 원문(`rendered`)을 보이지 않고 보안 상세와 같은 구조로 보인다. 판정 칩(측정 N개·미측정
  N개·진단 N건)과 요약 그리드, 측정 중단 띠, 개선 지점 N건(병렬화·응답 재사용 배지), 케이스별 응답 시간 표,
  미측정 케이스 N개(접힘, CLI 와 같은 사유 문장), 이 측정의 한계 순이다. 하단에 "다시 측정" 과 "명세 바꾸기" 를
  둔다. 측정이 실패하면 오류와 함께 명세 폼을 다시 보인다.
- 카드 헤드라인은 비용 카드와 같은 모양이다. 병렬화 진단(`perf/sequential-independent`)의 단축 상한
  (`savingUpperBoundMs`)을 CLI 와 같은 반올림(`Math.round`)으로 더한 값을 `−N ms` 로, 측정한 케이스의 응답 시간
  중앙값 합계가 얼마로 줄어드는지를 `~현재 → ~개선 후 ms` 로 보인다. 막대 라벨은 "현재 / 개선 후" 다.
- 측정 중 취소는 하지 않는다. run 레지스트리에 취소 API 가 없다.

## 이유

(a) 는 셋 다 깨진다. 같은 버튼 아래에서 보안은 격리하고 성능은 호스트에서 쓰기 도구를 부르게 된다. 명세에는 대상
서버를 가리키는 필드가 없어, `examples/weather-server` 처럼 한 서버 옆에 명세가 둘 이상이면 고를 근거가 디렉터리
나열 순서뿐이다. 다른 축과 동시에 돌면 측정이 그 부하를 함께 잰다.

(c) 는 측정 경로가 안전하지만 사용자가 터미널로 돌아가야 해 분석 화면에 붙인 의미가 없다.

(b) 는 사용자가 명세를 고르고 고지를 본 뒤 시작하므로 홈의 테스트 실행(`mcpeak test`)과 같은 안전 수준이다. 다른
축과 시점이 갈려 부하가 섞이지 않는다.

배지를 perf 가 낸 값에만 거는 이유는 ADR-0116 의 "판정은 CLI 의 것" 과 같다. 기준선 없이 "문제 없음" 을 내면
Node 가 아닌 서버(진단 목록이 늘 비어 있다)나 호출당 수 초 걸리는 도구에도 통과처럼 보인다. 관측하지 못한 상태가
다른 판정을 가리지 않도록 "관측 안 함" 을 맨 앞에 둔다.

헤드라인을 병렬화 단축 합계로 두는 이유는 perf 가 단축 시간을 숫자로 내는 진단이 그것 하나이기 때문이다. 같은 요청
반복(`perf/repeated-request`)은 단축 시간을 내지 않으므로 칩의 진단 수로만 보인다. 합계는 "측정한 케이스를 한 번씩
부를 때" 의 상한이고, 실제 호출 빈도는 모른다.

응답 시간을 못 잰 케이스를 "호출 실패" 로 세지 않고 "미측정 케이스" 로 묶는 것은 확인 루프에서 사용자가 정했다.
"호출 실패 N건" 은 서비스 장애처럼 읽히지만, 실제로는 명세가 오류를 기대하는 케이스이거나 측정 환경의 타임아웃인
경우가 많다. 성능 축이 답하는 것은 "얼마나 빠른가" 이고 "제대로 동작하는가" 는 테스트 실행의 몫이다.

상세에서 CLI 원문 대신 구조화된 구획을 보이는 것은 보안 상세와 읽는 방식을 맞추기 위해서다. 숫자와 문장은 여전히
perf 리포트와 CLI 가 만든 글자이고, 화면은 그것을 나눠 놓기만 한다.

명세 목록을 고른 서버에 딸린 것으로 먼저 거르는 이유는 위 (a) 의 문제와 같다. 명세에는 대상 서버 필드가 없어,
목록 전체를 펼쳐 두면 다른 서버의 명세로 측정하기 쉽다. 축 사이의 상호 차단(R11)은 다른 축과 부하가 섞이지
않게 한다는 (b) 의 이유를 화면에서 강제하는 것이다.

## 결과

- 서버에 `POST /api/analyze/perf`, `GET /api/analyze/perf/<runId>` 가 생긴다. 보안 축과 같은 run + SSE 모양이다
  (perf 설계 §13 Q1). run 종류 `perf` 는 `GET /api/runs` 목록에 실리지 않는다.
- 응답 계약 `AnalyzePerfResponse` 는 `report`·`rendered`·`exitCode` 에 더해 `abortedLine`·`limits` 를 싣는다.
  둘 다 `rendered` 에서 떼어 낸 CLI 글자이고, 보안 응답의 `sandboxLine`·`limits` 와 같은 방식이다.
- `mcpeak perf` 가 측정 도중 호출마다 진행 줄(`측정 중 N/M · <케이스> (i/R회)`)을 stderr 에 쓴다(PR #537).
  대시보드 진행 패널은 이 줄을 흘린다. 신호로 중단된 뒤에는 쓰지 않는다.
- `@mcpeak/cli/commands` 공개 면에 `runPerfCommand`, `PerfCommandDependencies`, `nodePerfDependencies` 가 더해진다.
  대시보드는 `nodePerfDependencies` 를 펼친 뒤 `readEnv`·`readFile`·`writeFile`·`writeStdout`·`writeStderr` 다섯
  자리만 바꾼다. `onSignal`·`killSelf` 는 그대로 써서 대시보드가 신호로 끝날 때 perf 가 추적 디렉터리와 자식 서버를
  먼저 정리한다.
- `@mcpeak/dashboard` 가 `@mcpeak/perf` 에 의존한다(경계 테스트가 이미 허용한다).
- 카드 설명에서 "처리량·동시성 한계" 를 뺀다. perf 는 부하를 거는 도구가 아니다(perf 설계 비범위).
- analyze 설계 §9 의 "일곱 파일 밖은 건드릴 일이 없다" 는 틀렸다. 서버 라우트·실행기·API 타입과 cli 공개 면이
  더 필요했다.
- 포기한 것: "분석하기" 한 번으로 세 축이 다 차는 흐름. 측정 중 취소. 기준선 입력과 그에 따른 회귀 판정(배지 분기만
  두고 화면 입력은 이번에 만들지 않는다). 같은 요청 반복의 단축 시간. 케이스 표의 부분 실패 비고 열. 상세의
  도구 선택 입력. isError 응답의 문장(perf 리포트가 `firstError` 를 threw 에만 담는다).
