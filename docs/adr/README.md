# ADR — 설계 결정 기록 (Architecture Decision Records)

"다르게 갈 수도 있었던" 판단을 한 페이지로 남깁니다. 단순 구현은 대상이 아닙니다.

- 형식: `0001-제목.md`
- 항목: 배경 / 선택지 / 결정 / 이유 / 결과 (CONTRIBUTING §8)
- **오너 1인당 최소 2건**을 마감까지 작성합니다.

아래는 현재 저장소에 있는 ADR 전체 색인입니다. ADR 을 추가하면 이 표에 한 줄을 더하고,
파일 머리의 상태가 바뀌면 표의 상태도 함께 갱신합니다.

**상태** — `채택` 과 `승인` 이 확정된 결정입니다. `제안` 과 `초안` 은 아직 확정되지 않았으므로 이
결정에 기대어 구현하지 마세요. 값은 각 파일 머리의 `상태` 를 그대로 옮긴 것입니다.

두 표기가 섞여 있는 것은 저장소의 기존 상태입니다. `CONTRIBUTING.md` §8 의 템플릿은
`제안 / 채택 / 폐기` 로 적혀 있는데 초기 ADR 몇 개가 `승인` 을 썼습니다. 둘을 하나로 통일하는 것은
전체 ADR 을 훑는 별도 작업이라 여기서는 표기 차이만 명시합니다.

⚠ **0007 번호 중복** — `0007-mock-stdio-transport.md` 와 `0007-provider-전송-스키마-분리.md` 가
같은 번호를 씁니다. 서로 다른 파트가 같은 시점에 번호를 잡아 생긴 충돌이며 **아직 해소되지
않았습니다.**

번호 충돌은 이번이 처음이 아니고 아직 끝나지도 않았습니다. 0014 에서 한 번 났고 뒤에 온 ADR 을
[0016](./0016-junit-time-속성-고정.md) 으로 옮겨 해소했는데, 이 색인이 예고한 대로 승인 지문
ADR 이 머지되면서 그 0016 이 **실제로 다시 충돌했습니다.** 같은 선례를 따라 나중에 main 에
들어온 승인 지문 ADR 을 [0017](./0017-승인-지문-계산-범위.md) 로 옮겨 해소했습니다.

그리고 **그 0017 이 두 브랜치에서 동시에 또 충돌했습니다.** 입력 계약 대조 배선 ADR 과 JUnit
리포터 ADR 이 각자 자기 브랜치에서 0017 을 집은 채 리뷰 중이었는데, 그 사이 승인 지문 ADR 이
0017 로 재번호돼 main 에 먼저 들어왔습니다. 같은 선례를 따라 입력 계약 대조 배선 ADR 을
[0018](./0018-입력-계약-대조-소비자-배선.md) 로 옮겼고, 그 0018 이 머지된 뒤 JUnit 리포터 ADR 은
빈 번호가 또 없어져 [0019](./0019-junit-리포터-cli-노출-방식.md) 로 다시 옮겼습니다. **JUnit
리포터 ADR 하나가 0017 → 0018 → 0019 로 두 번 밀렸습니다.**

재번호는 그때그때의 땜질일 뿐 원인은 그대로입니다. 브랜치마다 독립적으로 다음 빈 번호를 집는
방식이라, 병렬로 도는 브랜치 수만큼 같은 번호가 잡힙니다. 예고한 충돌이 그대로 일어났다는 것이
이 방식으로는 못 막는다는 증거입니다. **번호 충돌을 해소한 PR 이 만든 번호가 다시 충돌했고, 그
해소마저 또 충돌했습니다** — 해소 작업 자체가 새 충돌원이 되는 구조입니다. 리뷰가 하루만 길어져도
같은 일이 반복되므로, 번호 배정 규칙은 이 색인과 별개로 정해야 합니다.

**네 번째입니다.** Streamable HTTP ADR 이 자기 브랜치에서 0019 를 집은 채 리뷰 중이었는데, 그
사이 JUnit 리포터 ADR 이 0019 로 main 에 먼저 들어왔습니다. 같은 선례를 따라 나중에 들어온 쪽을
[0020](./0020-streamable-http-transport.md) 으로 옮겼습니다. 위 문단이 "리뷰가 하루만 길어져도
같은 일이 반복된다" 고 적은 그다음 날 그대로 일어났습니다.
