두 표기가 섞여 있는 것은 저장소의 기존 상태입니다. `CONTRIBUTING.md` §8 의 템플릿은

⚠ **0007 번호 중복** — `0007-mock-stdio-transport.md` 와 `0007-provider-전송-스키마-분리.md` 가
같은 번호를 씁니다. 서로 다른 파트가 같은 시점에 번호를 잡아 생긴 충돌이며 **아직 해소되지
않았습니다.**

번호 충돌은 이번이 처음이 아니고 아직 끝나지도 않았습니다. 0014 에서 한 번 났고 뒤에 온 ADR 을
[0016](./0016-junit-time-속성-고정.md) 으로 옮겨 해소했는데, 이 색인이 예고한 대로 승인 지문
ADR 이 머지되면서 그 0016 이 **실제로 다시 충돌했습니다.** 같은 선례를 따라 나중에 main 에
들어온 승인 지문 ADR 을 [0017](./0017-승인-지문-계산-범위.md) 로 옮겨 해소했습니다.

그리고 **그 0017 이 두 브랜치에서 동시에 또 충돌했습니다.** 입력 계약 대조 배선 ADR 과 JUnit
리포터 ADR 이 각자 자기 브랜치에서 0017 을 집은 채 리뷰 중이었는데, 그 사이 승인 지문 ADR 이
0017 로 재번호돼 main 에 먼저 들어왔습니다. 같은 선례를 따라 입력 계약 대조 배선 ADR 을
[0018](./0018-입력-계약-대조-소비자-배선.md) 로 옮겼고, 그 0018 이 머지된 뒤 JUnit 리포터 ADR 은
빈 번호가 또 없어져 [0019](./0019-junit-리포터-cli-노출-방식.md) 로 다시 옮겼습니다. **JUnit
리포터 ADR 하나가 0017 → 0018 → 0019 로 두 번 밀렸습니다.**

재번호는 그때그때의 땜질일 뿐 원인은 그대로입니다. 브랜치마다 독립적으로 다음 빈 번호를 집는
방식이라, 병렬로 도는 브랜치 수만큼 같은 번호가 잡힙니다. 예고한 충돌이 그대로 일어났다는 것이
이 방식으로는 못 막는다는 증거입니다. **번호 충돌을 해소한 PR 이 만든 번호가 다시 충돌했고, 그
해소마저 또 충돌했습니다** — 해소 작업 자체가 새 충돌원이 되는 구조입니다. 리뷰가 하루만 길어져도
같은 일이 반복되므로, 번호 배정 규칙은 이 색인과 별개로 정해야 합니다.

**네 번째입니다.** Streamable HTTP ADR 이 자기 브랜치에서 0019 를 집은 채 리뷰 중이었는데, 그
사이 JUnit 리포터 ADR 이 0019 로 main 에 먼저 들어왔습니다. 같은 선례를 따라 나중에 들어온 쪽을
[0020](./0020-streamable-http-transport.md) 으로 옮겼습니다. 위 문단이 "리뷰가 하루만 길어져도
같은 일이 반복된다" 고 적은 그다음 날 그대로 일어났습니다.

**다섯 번째입니다.** 목 매칭 키 ADR 이 자기 브랜치에서 0027 · 0028 을 집은 채 구현이 도는 사이,
`isError` 진단 ADR 이 0027 로 main 에 먼저 들어왔습니다. 같은 선례를 따라 나중에 들어온 쪽을
[0029](./0029-목-매칭-키-정규화-경계.md) · [0030](./0030-mock-src-상대-import-확장자.md) 로
옮겼습니다. 이번에는 **두 개를 한꺼번에** 옮겼다는 점만 다릅니다 — 한 브랜치가 ADR 을 여럿 내면
충돌 폭도 그만큼 넓어집니다.

이 이동으로 비었던 0028 은 [replay 서브커맨드 ADR](./0028-replay-서브커맨드의-서버-없는-실행.md)
이 채웠습니다. 번호를 비워 두면 다음 사람이 같은 자리를 다시 집으므로, 빈 번호는 재사용합니다.

**여섯 번째입니다.** 서버 수정 방향(단계 4 repair) 구현 계획서가 자기 문서에서 0028 · 0029 ·
0030 · 0031 을 예약해 뒀는데, 그 사이 목 매칭 키 ADR 두 개가 0029 · 0030 으로 main 에 먼저
들어왔습니다. 착수 시점에 실제 파일 목록을 세어 빈 번호를 다시 잡았고, 그 결과가
[0031](./0031-repair-번들과-json-분리.md) · [0032](./0032-미승인-명세에서의-repair-동작.md) ·
[0033](./0033-stderr-외부-전송-경계.md) 입니다.

**일곱 번째입니다.** 위에서 살아남았던 0028 마저 replay 서브커맨드 ADR 이 main 에 먼저 들어오며
겹쳤습니다. 나중에 들어온 쪽을 옮기는 선례를 따라 provider 진단 통로 ADR 을
[0034](./0034-provider-진단-통로-분리.md) 로 옮겼습니다. 착수 시점에 빈 번호를 확인해도 그
확인과 머지 사이에 다른 브랜치가 같은 번호를 채우면 소용이 없습니다. **번호는 브랜치에서 잡는 한
언제 확인하든 안전하지 않습니다.**

**여덟 번째는 일어나기 전에 피했습니다.** 배열 인자 ADR 이 다음 빈 번호로 0031 을 집으려다,
브랜치를 따기 전에 **열린 PR 들이 잡은 번호**를 조회했습니다. repair 관련 PR 이 0031~0034 를
한꺼번에 들고 있어 [0035](./0035-callTool-인자의-배열-허용-범위.md) 로 갔고, 그 PR 이 먼저
머지되면서 결과적으로 번호가 이어졌습니다.

확인에 쓴 명령을 남겨 둡니다. 파일 목록만 세면 브랜치 안의 번호는 안 보이지만, 이건 보입니다.

```bash
for p in $(gh pr list --state open --json number --jq '.[].number'); do
  gh pr diff $p --name-only | grep "docs/adr/00" | sed "s/^/PR#$p /"
done
```

**다만 위 일곱 번째 문단의 결론을 뒤집지는 못합니다.** 이 조회는 *이미 열린 PR* 만 봅니다.
아직 PR 이 없는 브랜치나, 조회 뒤에 새로 열리는 PR 은 여전히 안 보입니다. 이번에 통한 것은
운이 좋아서이지 방법이 안전해서가 아닙니다. 그리고 이건 규칙이 아니라 **개인이 기억해야 하는
절차**라, 기억하지 않는 사람에게는 아무 효과가 없습니다. 아래 논의가 필요한 이유가 그대로
남아 있습니다.

**아홉 번째부터 열네 번째까지입니다. 전부 릴리스 ADR 두 건 하나가 겪은 일입니다.**

한 작업이 번호를 **네 번** 옮겼습니다. `0037 · 0038` → `0038 · 0039` → `0039 · 0040`
→ `0042 · 0043` → [0043](./0043-배포-tarball-생성을-pnpm으로-고정한다.md) ·
[0044](./0044-npm-스코프-선점에-따른-패키지-개명.md).

1. 처음 잡을 때 로컬 `main` 이 origin 보다 **62 커밋 뒤처져** 있었습니다. `건너뛴 테스트의
   CI 판정` ADR 이 이미 0037 로 들어와 있었지만 **내 `docs/adr/` 에는 정말로 0037 이
   없었으므로** 파일 목록을 세는 것으로는 보이지 않았습니다.
2. 그 재배정을 끝내기 전에 origin 이 **11 커밋 더** 올라가 `결정론성 확인` ADR 이 0038 을
   가져갔습니다.
3. 다시 밀고 나서 push 직전에 확인하니 `docs/masking-rule-adr` 브랜치가 **0039 · 0040 ·
   0041 세 개를 한꺼번에** 들고 있었습니다. 그 위로 넘어가 0042 · 0043 이 됐습니다.

앞의 여덟 건은 *브랜치끼리* 같은 번호를 집어 생겼습니다. 이 네 건은 **시간** 때문입니다.
1·2 는 이미 머지된 ADR 이라 열린 PR 조회로 안 보이고, 3 은 PR 이 아직 없는 브랜치라
역시 안 보입니다 — 위 명령이 스스로 인정한 사각지대 두 개가 같은 작업에서 다 밟혔습니다.

**확인 방법을 더해도 소용이 없다는 것이 이번에 확정됐습니다.** `git fetch` 는 *그 순간*만
보여주고, 열린 PR 조회는 머지된 것과 PR 없는 브랜치를 못 봅니다. 세 번째 재배정은
`git ls-remote` 로 **모든 원격 브랜치의 ADR 파일을 직접 뒤져서** 겨우 찾았습니다. 그
방법조차 아직 push 되지 않은 로컬 브랜치는 못 봅니다.

**네 번째 재배정은 리뷰를 기다리는 동안 났습니다.** PR 을 열어두고 하루가 지나는 사이
main 이 20 커밋 나갔고, 그중 실서버 스펙 직렬화 ADR 이 0042 를 가져갔습니다. 앞의 세 번은
브랜치를 따거나 번호를 고치는 **작업 중**에 났지만, 이번에는 **이미 열려서 CI 까지 초록이던
PR** 이 밀렸습니다. 번호를 잡는 시점을 아무리 늦춰도 리뷰 대기 시간이 남아 있는 한 같은 일이
납니다.

**열다섯 번째입니다.** 계약 스냅샷 API 철회 ADR 이 자기 브랜치(`refactor/record-drop-
snapshot-contract`, PR #188)에서 0046 을 집은 채 리뷰 중이었는데, 그 사이 대시보드
ADR 이 0046 으로 main 에 먼저 들어왔다. 같은 선례를 따라 나중에 들어온 쪽을
[0047](./0047-계약-스냅샷-api-철회.md) 로 옮겼다. 대시보드 ADR 은 이 색인에 행이
없었던 채로 main 에 들어와 있었다 — 이번에 함께 채웠다.

확인 비용이 이 정도로 커졌다는 것 자체가 결론입니다. **번호 배정을 브랜치에서 하는 한,
남은 선택지는 "더 열심히 확인한다" 가 아니라 배정 시점을 옮기는 것뿐입니다.**

번호를 파일명에 박는 한 이 표에 줄이 계속 늘어납니다. 실제로 막으려면 배정 시점을 브랜치가 아니라
main 으로 옮기거나(머지 직전에 번호를 매긴다), 파일명에서 번호를 떼고 색인이 번호를 갖는 쪽으로
바꿔야 합니다. 어느 쪽이든 이 문서만으로는 못 정하므로 별도 논의가 필요합니다.
