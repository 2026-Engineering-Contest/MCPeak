# MCP 보안 테스트 도구 시장조사 (2026-10-03)

사용자가 임의의 MCP 서버를 자기 환경에 붙이기 전에, 우리 도구가 격리된 자리에서 미리 써 보고
이상 여부를 알려 주는 기능("사전 점검 프록시")을 설계하기 위한 선행 조사다. 공개 도구 9개를
리포지터리에서 직접 받아 코드 수준으로 확인했다. 수치는 2026-10-03 기준 GitHub API 값이다.

정리하면 세 갈래다.

1. **설명문 정적 검사**(agent-scan, mcp-shield, Cisco YARA, mcpward security). tools/list 결과의
   문자열을 정규식·YARA 로 본다. 대부분이 여기 속한다.
2. **소스 코드 검사**(mcp-watch, Cisco behavioral/static_analysis). 서버 소스가 있어야 한다.
3. **동적 행위 관측**(mcp-harness, toolhive 의 런타임 격리). 실제로 띄워서 파일·네트워크·프로세스를
   본다. 성숙한 오픈소스가 거의 없다. mcp-harness 는 스타 0 의 MVP 다.

## 2. 도구별 코드 확인 내용

### snyk/agent-scan

- `invariantlabs-ai/mcp-scan` 은 이 리포로 리다이렉트된다. Invariant 가 Snyk 로 흡수됐다.
- 로컬 판정 로직이 **없다**. `inspect.py` 가 설정 파일을 찾아 서버를 띄우고 tools/list 를 받은 뒤
  `verify_api.py` 가 `McpServerRequest`(이름·설정 경로·도구 목록)를 Snyk API 로 보내 `RiskScore`
  를 받아 출력한다. 오프라인·로컬 전용 플래그는 코드에 없다.
- 과거 mcp-scan 의 도구 해시 고정(러그풀 탐지)은 이 리포에서 사라졌다. 해시는 스킬 파일 식별과
  트래픽 캡처 키 생성에만 쓴다.
- `guard.py` 는 Claude Code·Cursor·Codex·Copilot 의 훅에 자기를 끼워 넣어 호출 시점에 다시 API 를
  묻는 구조다. 프록시가 아니라 **클라이언트 훅 기반 런타임 게이트**다.
- stdio 서버를 띄울 때 설정의 `env` 를 그대로 넘긴다. 사용자 토큰이 서버에 전달된다.

### cisco-ai-defense/mcp-scanner

- 분석기가 가장 많다. `yara_analyzer`(로컬 YARA 10개 규칙: tool_poisoning, prompt_injection,
  coercive_injection, command_injection, credential_harvesting, data_exfiltration, code_execution,
  script_injection, sql_injection, system_manipulation), `prompt_defense_analyzer`(방어 문구 **누락**을
  보는 정규식 12범주, 로컬), `protocol_analyzer`(라이브 엔드포인트의 MCPS-001~009: 평문 HTTP, 무인증
  수락, 서명·재생 방지 없음, 도구 정의 무결성 해시 없음, 속도 제한 없음), `api_analyzer`(Cisco),
  `llm_analyzer`, `meta_analyzer`(LLM 으로 오탐만 제거), `virustotal_analyzer`,
  `vulnerable_package_analyzer`(pip-audit), `behavioral/`(tree-sitter 로 10개 언어 AST·taint 추출 후
  LLM 에 "설명과 코드 행위가 일치하는가" 를 묻는 정렬 검사).
- YARA 규칙의 질이 다른 도구보다 높다. 예를 들어 tool_poisoning 은 "also collects", "for caching
  purposes, send", "silently uploads" 같은 **숨은 부차 행위** 문형을 잡고, 메일 검색 도구에서의 오탐을
  주석으로 기록해 두었다. 우리가 규칙을 직접 쓸 때 참고할 가치가 있다(Apache-2.0).
- Docker 는 PyPI·npm 패키지를 받아 설치해 보는 `package_sandbox` 에만 쓴다. 서버 실행 자체를 격리하지
  않는다.
- 의존성이 무겁다(litellm, fastapi, tree-sitter 10종, yara-python). 라이브러리로 끌어올 대상은 아니다.

### stacklok/toolhive

- 스캐너가 아니라 **런타임**이다. 모든 MCP 서버를 컨테이너에서 띄우고 권한 프로필(`NetworkPermissions.Mode`
  none/bridge, `Outbound.AllowHost/AllowPort`)로 아웃바운드를 squid·envoy 프록시로 제한한다.
- "격리 안에서 써 본다" 라는 우리 설계의 **격리 층 레퍼런스**다. 다만 Go 데몬이라 우리 도구에 포함할
  수는 없고, Docker 가 있을 때 사용자 머신에서 같은 모양(컨테이너 + 네트워크 none 또는 허용목록)으로
  띄우는 방식을 따를 수 있다.

### riseandignite/mcp-shield

- 1.5k줄 정규식 4종(숨은 지시, 유출 통로 인자명 `note`/`sidenote`/`feedback` 등, 도구 섀도잉, 민감 파일
  경로 언급)과 교차 출처(다른 서버 이름을 설명에서 언급) 검사. 2025-04 이후 갱신 없음.
- stdio 서버를 띄울 때 `process.env` **전체를 복사**해 넘긴다. 스캐너가 오히려 사용자 비밀을 서버에
  노출한다. 우리가 피해야 할 반례다.

### TsvetanG2/mcpward

- 우리와 가장 닮은 설계다. MCP SDK 로 블랙박스 접속, 검사 다섯 가족(compliance, schema, security,
  drift, behavioral), SARIF·JUnit 출력, **lockfile 기준 드리프트**(정규화한 도구 표면을 해시해 러그풀
  탐지). 정규화는 드리프트 해시 전용이고 보안 검사는 원문을 본다고 주석으로 못 박았다.
- security.ts 는 주입 문형 12개, 제로폭·양방향 제어·혼동 공백 유니코드, 비밀 요구 필드명 11개,
  `readOnlyHint=true` 인데 설명이 파괴적 동사를 쓰는 주석 불일치. "good-server 에서 오탐 0" 을 설계
  원칙으로 적었다.
- 스타 2, 개인 프로젝트. 아이디어는 가져오되 의존할 대상은 아니다.

### jjaram16/mcp-harness

- 유일하게 **"샌드박스가 오라클"** 인 설계다. Docker `--network none`, 읽기 전용 루트, 권한 전부 드롭,
  `strace -f` 로 `connect()`·`execve()` 를 기록하고, 허용 디렉터리 밖에 랜덤 토큰 카나리 파일을 심는다.
  경로 순회·SSRF·명령 주입 페이로드를 보내고 토큰 유출, 아웃바운드 시도, 자식 프로세스를 증거로 판정한다.
  LLM 없음, 결정론적.
- 스타 0, MVP, 라이선스 미표기. 코드를 가져올 수는 없지만 **동적 층의 설계 모범**으로 삼을 수 있다.
  Docker 없는 "local" 모드는 격리·관측이 전혀 없다고 스스로 명시한다.

### 나머지

- mcp-watch: GitHub 리포를 clone 해 소스 줄 단위 정규식. 서버 실행 없음. 바이너리 배포 서버에 무력.
- mcpSafetyScanner: OpenAI 기반 멀티 에이전트가 서버 설정을 읽고 보고서를 쓴다. 논문 동반 코드.

## 3. 시장의 빈자리

| 요구 | 현재 상태 |
|---|---|
| 사용자 설정 파일을 건드리지 않고, 등록 전에 미리 검사 | 모두 "이미 설치된" 서버를 설정 파일에서 찾아 검사한다. 사전 점검 흐름이 없다 |
| 사용자 비밀이 검사 대상 서버로 흘러가지 않음 | agent-scan·mcp-shield·mcpward 모두 env 를 넘긴다 |
| 외부 전송 없이 로컬 판정 | 상위 두 도구(agent-scan, Cisco API 모드)는 클라우드 필수. 로컬 전용은 소규모 개인 프로젝트 |
| 도구 정의 변경(러그풀) 추적 | mcpward 만 lockfile. agent-scan 은 기능을 잃었다 |
| 실제 행위 관측(파일·네트워크·프로세스) | mcp-harness(MVP) 와 toolhive(런타임) 외 없음 |
| 테스트 도구 안에 통합되어 CI 에 들어감 | mcpward·Cisco 가 SARIF 출력. 테스트 프레임워크와 결합한 것은 없음 |

## 4. 우리 설계에 끌어올 것

- **정적 층 규칙 소스.** Cisco YARA(Apache-2.0)의 문형과 mcpward 의 유니코드·필드명·주석 불일치 검사를
  우리 규칙으로 옮긴다. 정규식·유니코드 표 수준이라 의존성 없이 재구현 가능하다. 외부 LLM 판정은 쓰지
  않는다(결정론, 외부 전송 금지).
- **프로토콜 층.** Cisco MCPS 항목 중 전송 암호화, 무인증 수락, 도구 정의 무결성은 `core` 의 HTTP·stdio
  접속 정보로 바로 판정된다.
- **드리프트.** mcpward 처럼 첫 접속의 도구 표면을 정규화해 해시하고 `record` 세션에 보관한다.
- **격리와 비밀 차단.** `core` 가 spawn 을 소유하므로 env 를 비우거나 가짜 토큰으로 바꿔 띄운다. 가짜
  토큰이 응답에 나오면 유출로 판정하는 카나리는 Docker 없이도 된다.
- **동적 층은 Docker 가 있을 때만.** mcp-harness·toolhive 방식(`--network none`, 읽기 전용, 권한 드롭,
  카나리 파일)을 선택 기능으로 둔다. 없으면 "관측 안 함" 을 정직하게 출력한다.
- **"미리 써보기" 는 `optimize` 의 stdio 프록시 구조와 같다.** tools/list 를 가로채 검사·해시하고
  tools/call 을 관측하며 원본으로 넘긴다(ADR-0102).

## 5. 확인하지 못한 것

- agent-scan 의 Snyk API 가 어떤 모델·규칙으로 판정하는지는 서버 측이라 볼 수 없다.
- toolhive 의 Docker 외 런타임(Podman, Kubernetes)에서의 네트워크 제한 동작은 읽지 않았다.
- mcp-harness 는 라이선스 파일이 없어 코드 재사용이 불가하다. 설계만 참고한다.
