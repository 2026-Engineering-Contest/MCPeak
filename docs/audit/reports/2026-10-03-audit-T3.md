## 임의로 판단한 부분

### launch
- 명령의 basename 은 `/`·`\` 둘 다로 자르고 소문자로 비교한다. `cmd.exe` 가 아니면 `.exe` 를 떼므로 `node.exe` 도 `node` 로 본다.
- 셸 플래그: `-c` 는 대소문자를 구분한다(`bash -C` 는 noclobber). `/c`·`-Command`·`-EncodedCommand` 는 Windows 관례에 따라 구분하지 않는다. 인터프리터는 `--eval=…` 형태도 잡는다.
- inline-code 의 위치는 플래그가 있는 `args[i]` 다. 조각은 "플래그 + 다음 인자" 이고, evidence 는 80자에서 자른다(`…`).
- unpinned-package:
  - `pipx run <pkg>` 에서는 `run` 하위 명령을 건너뛴다.
  - 원격 URL(remote-source 몫)과 로컬 경로(`./`·`../`·`/`·`file:`)는 패키지로 보지 않는다. 그래서 `npx https://…` 픽스처에는 remote-source 하나만 걸린다.
  - `pkg@latest` 같은 태그는 고정으로 보지 않는다(`/@\d/`).
  - message·fix 의 `<pkg>` 에는 버전 표기를 뗀 이름을 넣고, 원래 인자는 evidence 에 둔다. fix 의 `<버전>` 은 알 수 없는 값이라 글자 그대로 둔다(`some-pkg@<버전> 처럼…`).
- env-passthrough 의 위치 path 는 `env.<NAME>` 이다. §3.0.1 에는 `args[i]` 예시만 있다.
- `parseLaunchPackage`: http 대상이면 `undefined` 를 낸다. 패키지 실행기가 아니면 `{ command, args }` 만 낸다. npm 태그(`@latest`)는 `version` 에 그대로 기록하고, pypi 는 `==`·`@` 뒤를 `version` 으로 본다. extras(`[x]`)는 뗀다.

### secret
- `planCanaries` 의 이름 순서는 §3.5 고정 목록 순서다. `random()` 이 이미 나온 값을 다시 내면 Error 를 던진다. 어느 이름이 샜는지 가려야 하므로 값이 이름마다 달라야 하기 때문이다.
- 인코딩 대조는 값 쪽을 인코딩해 찾는다.
  - base64 는 앞 바이트 수에 따라 정렬이 0·1·2 세 가지로 갈리므로 세 경우를 모두 만들고, 경계에 걸친 글자를 잘라 낸 가운데 조각을 쓴다. url-safe 변형도 본다.
  - hex·raw·rot13 은 대소문자를 구분하지 않는다. evidence 의 형 우선순위는 raw → base64 → hex → rot13 이다.
- env-echo 도 env-leak 과 같은 네 형으로 본다. §3.5 는 "같은 곳에" 라고만 적었다.
- env-name-in-description:
  - "도구 설명" 은 `kind: "tool"` 이면서 path 가 `description` 이거나 `.description` 으로 끝나는 값 문자열로 보았다.
  - 단어 경계를 둔다(`MY_GITHUB_TOKEN_V2` 는 언급이 아니다).
  - 대상 이름은 카나리 이름과 전달 이름의 합집합이다.
- 모듈 안에서 §3.0 정렬·중복 제거를 한다. secret 의 중복 키는 path 대신 위치 객체 전체를 쓴다. 서로 다른 프롬프트·리소스가 같은 path 를 가질 수 있어서다.

### surface
- 표면 정규화에서 없는 필드는 `null` 로 자리를 남긴다. 필드 해시는 `JSON.stringify(정규화 값)` 의 sha256 이고, 원본에 없는 필드는 `""` 다.
- `surfaceHash` 는 이름순으로 정렬한 도구 해시를 `\n` 으로 이어 해시한다.
- 같은 이름 도구의 필드가 여러 개 바뀌면 필드마다 발견 하나를 낸다. evidence 는 `<name>.<field>` 이고, 추가는 `[name, "added"]`, 삭제는 `[name, "removed"]` 다.
  모든 surface 발견은 path 가 `""` 라서 evidence[0] 이 §3.0 의 중복 제거 키를 가른다.
- 도구 해시는 다른데 필드 해시가 모두 같으면(정규화 규칙이 바뀐 경우) 조용히 넘기지 않고 `정의` high 를 낸다.
- annotations 완화 판정은 §3.5 를 글자 그대로 따른다. 없던 `destructiveHint` 가 true 가 되는 경우는 완화로 보지 않는다(MCP 기본값이 true 다).
- `parseBaseline` 의 오류 메시지는 §6.3 의 `<원인 한 줄>` 자리에 들어갈 한 줄만 담는다. 경로는 받지 않으므로 호출자(T6/T7)가 `기준 파일을 읽을 수 없습니다: <path>` 를 붙인다.
  반환 객체의 키 순서는 §5.1 선언 순서다(`JSON.stringify(…, null, 2)` 를 왕복해 확인). 모르는 키는 버린다.
- `compareBaseline` 의 세 번째 인자 `tools` 는 시그니처 호환을 위해 받기만 하고 쓰지 않는다.
