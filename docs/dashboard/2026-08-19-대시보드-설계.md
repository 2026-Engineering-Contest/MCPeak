# 대시보드 설계

CLI를 사용하지 않는 사용자를 위한 로컬 웹 대시보드의 설계 문서다. 구현 계획이 아니라
설계 확정본이며, 구현 계획은 이 문서를 기점으로 별도 작성한다.

## 배경

OhMyMCP의 모든 기능은 현재 `ohmymcp` CLI로만 접근할 수 있다. 터미널에 익숙하지 않은
사용자도 테스트 생성부터 수정 승인까지 전 과정을 쓸 수 있게 GUI를 제공한다.

## 목표

- CLI 4개 플로우(테스트 실행, generate, record/replay, repair)를 브라우저에서 수행한다.
- 결과 열람만이 아니라 스펙, 카세트 수정과 대화형 승인(dry-run 리뷰, repair 승인)까지 지원한다.
- CLI와 동일한 입력에 동일한 결과를 낸다. 로직을 복제하지 않고 CLI 오케스트레이션을 재사용한다.

## 비범위 (첫 버전)

- 팀 공유 서버, 인증, 동시 편집. 로컬 단일 사용자 전용이다.
- 실행 이력 영속화. 서버 재시작 시 메모리의 run 이력은 사라진다. 파일로 남는
  리포트와 카세트는 유지된다.
- 파일 잠금. 저장 시 mtime 비교로 외부 변경을 경고만 한다.

## 결정 요약

| 항목 | 결정 |
|---|---|
| 형태 | 로컬 웹서버. 별도 bin으로 기동, 접속 URL을 출력한다(자동 오픈은 새 의존성 없이 크로스플랫폼 구현이 지저분해 첫 버전 제외) |
| 패키지 | 새 패키지 `packages/dashboard` (`@ohmymcp-hsu/dashboard`, bin `ohmymcp-dashboard`) |
| 오너 | 공용 |
| 의존 방향 | `dashboard` → `ohmymcp`(cli) → `runner`/`generate`/`record`/`mock` → `core`. 단방향 유지 |
| cli 변경 | cli의 공개 면이 `run` 등 4개뿐이라 커맨드 함수가 패키지 밖으로 안 나온다. 재export 서브패스 `ohmymcp/commands`를 추가한다(로직 이동 없음, cli 오너 협의 필요) |
| 로직 재사용 | cli가 export하는 커맨드 함수(`runGenerateCommand`, `runRepairCommand` 등)에 의존성 객체를 웹 어댑터로 갈아끼워 호출 |
| 서버 | Node 내장 `http`. 런타임 신규 의존성 0 |
| 프론트 | React + Vite + Tailwind CSS. 빌드 시점에만 필요, 산출물을 패키지 `dist/`에 포함해 배포 |
| 스트리밍 | SSE (`EventSource`) |

기각한 대안: CLI 프로세스 래핑(대화형 승인 플로우에 stdin/stdout 프로토콜을 억지로
만들어야 해서 기각), 바닐라 JS(4개 플로우 규모에 유지비용 과다), 팀 공유 서버와
데스크톱 앱(배포 형태 질문에서 로컬 웹서버로 확정).

## 아키텍처

```
packages/dashboard
├── server/   Node http. 정적 SPA 서빙 + /api REST + SSE
├── web/      React + Vite SPA. 빌드 산출물을 server가 서빙
└── adapter/  cli 의존성 인터페이스의 웹 구현
```

- 어댑터가 핵심 계층이다. `writeStdout`/`writeStderr`는 SSE 이벤트로 변환하고,
  `reviewIO`(dry-run 승인, repair 승인)는 "질문 pending" 상태로 REST에 노출한 뒤
  브라우저 응답이 오면 resolve하여 CLI 오케스트레이션을 이어간다.
- 프로젝트 루트(스펙, 카세트 위치)는 CWD 기준이며 CLI와 동일한 규칙을 쓴다.
- 배포 시 런타임 의존성은 workspace 패키지 외 0을 유지한다. React, Vite, Tailwind CSS는
  web 빌드 시점에만 필요하다.

## 서버 API 면

`/api` 아래 JSON. 파일 경로는 프로젝트 루트 기준 상대경로만 허용하고 루트 밖 접근은
차단한다(path traversal 방지).

| 리소스 | 엔드포인트 | 역할 |
|---|---|---|
| 스위트 | `GET /suites`, `GET/PUT /suites/:path` | 테스트 스펙 목록, 열람, 수정 |
| 실행 | `POST /runs`, `GET /runs/:id`, `GET /runs/:id/events` (SSE) | 테스트 실행 시작, 상태, 스트리밍 |
| 생성 | `POST /generate`, `GET/POST /generate/:id/review` | generate 시작, dry-run 리뷰 질문 조회와 응답 |
| 카세트 | `GET /cassettes`, `GET/PUT/DELETE /cassettes/:path` | 카세트 목록, 열람, 편집, 삭제 |
| 재생 | `POST /replay` | 카세트 기반 재생 실행 |
| repair | `POST /repairs`, `GET/POST /repairs/:id/review` | 수정 제안 생성, diff 검토와 승인 |

단독 녹화 엔드포인트는 두지 않는다. CLI의 `record` 서브커맨드가 미구현이고 녹화는
`generate`의 `--record`/`--cassette` 옵션 경유가 현재의 유일한 경로이므로, 대시보드도
같은 경로를 쓴다. generate 시작 요청에 녹화 옵션을 포함한다.

대화형 플로우(generate 리뷰, repair 승인)는 전부 같은 패턴이다. 어댑터가 질문을 상태로
쌓고, 프론트는 SSE로 질문을 수신한 뒤 POST로 응답한다. resolve되면 오케스트레이션이
이어서 진행된다.

## 화면 5개

1. **홈**: 스위트 목록 + 최근 실행 결과 요약. 진입점.
2. **실행 뷰**: 실행 라이브 스트림. 실패 메시지는 터미널 문장 그대로 표시한다
   (실패 메시지가 곧 제품이므로 가공 최소화). 실패 항목에서 repair 시작 버튼.
3. **generate 마법사**: 서버 연결 → 도구 목록 → 생성 옵션 → dry-run 리뷰(케이스별
   승인/제외) → 스펙 저장.
4. **카세트 브라우저**: 카세트 목록, 상호작용 타임라인 열람, 값 편집, 재생 버튼.
5. **repair 리뷰**: 제안 diff 나란히 보기, 항목별 승인/거부.

## 데이터 흐름과 상태

- 진실 원본은 디스크 파일이다. DB 없음. 서버는 진행 중인 run만 메모리에 유지한다.
- run id는 UI 식별용 난수다. 테스트 산출물(리포트, 카세트)에는 들어가지 않으므로
  결정론성과 무관하다.
- 프론트 상태 라이브러리는 추가하지 않는다. `fetch` + `EventSource` + React 내장 상태.

## 에러 처리

- 커맨드 함수가 실패 exit code를 반환하면 run 상태를 `failed`로 두고 stderr 스트림을
  그대로 노출한다. 실패 메시지 문장을 대시보드가 재작성하지 않는다.
- ANSI 컬러 코드는 어댑터에서 HTML로 변환해 색을 유지한다.
- MCP 서버 프로세스 좀비 방지는 기존 cli shutdown 로직을 재사용한다.

## 테스트 전략

- 서버: 유닛테스트 인메모리. 커맨드 함수를 fake로 주입해 HTTP 레이어와 어댑터
  (SSE 변환, reviewIO 브리지, path traversal 차단)를 검증한다. `fixtures/`만 사용한다.
- 프론트: vitest + testing-library로 핵심 인터랙션(리뷰 승인 플로우)만 검증한다.
- E2E: `examples/weather-server` 상대로 대시보드 서버를 띄우고 API 호출로 4개 플로우를
  관통한다. 기존 규칙대로 직렬 전용이며 CI에 편입한다.

## 팀 제약 확인

- 새 패키지 오너는 공용으로 확정했다.
- React, Vite, Tailwind CSS 등 신규 의존성은 사용자가 스택을 직접 결정했으므로 별도 승인
  절차 없음.
  전부 MIT 라이선스로 프로젝트 라이선스와 충돌 없다.
- `core/src/types.ts`의 공유 계약과 타 패키지는 수정하지 않는다.
