## 1. 목표와 비범위

### 1.1 목표

개발자 모드의 Analyze 화면을 **세 축을 한 화면에서 보고, 축을 고르면 상세가 펼쳐지는** 구조로 바꾼다.
축은 보안(Security), 비용 최적화(Cost Optimization), 성능 효율성(Performance Efficiency)이다.

1. 서버를 한 번 고르고 **한 번에 분석** 을 누르면 보안 점검과 토큰 분석이 **동시에** 시작된다. 한쪽의
   실패가 다른 쪽을 막지 않는다.
2. 축마다 카드 하나. 카드는 판정 한 줄, 핵심 숫자 하나, 분포, 집계 칩, 요약 한 줄을 같은 자리에 둔다.
   카드만 보고 "어느 축을 먼저 열어야 하는지" 를 알 수 있어야 한다.
3. 카드를 누르면 그 축의 상세가 카드 아래에 펼쳐지고 주소(`#/analyze/<축>`)에 남는다. 새로 고침·뒤로
   가기·공유한 주소가 같은 축을 연다.
4. 상세는 **지금 두 탭이 보여주는 것을 그대로** 보여준다. 보안은 개발자/사용자 전환, 심각도별/도구별
   묶기, 격리·기준 파일·검사하지 않은 것, 흐름 경고 분리, CLI 원문. 비용은 요약 숫자, 도구별 표와
   원본·압축 비교, 소스 반영. 판정 문장은 지금처럼 CLI 가 만든 것을 보이기만 한다(ADR-0110).
5. 성능 효율성은 **자리만** 만든다. 카드는 "준비 중" 으로 보이고 눌리지 않는다. 뒤에 연결할 때 카드
   하나와 상세 하나를 끼우면 되도록 축의 계약(§5)을 지금 고정한다.
6. 결정론: 같은 응답이면 카드의 글자·숫자·순서가 항상 같다. 카드 요약은 응답에서 순수 함수로만 구하고
   화면이 새 판정을 만들지 않는다. 시각을 읽지 않는다.

### 1.2 비범위

- **서버 API 변경.** `POST /api/analyze/tokens`, `POST /api/analyze/security`,
  `GET /api/analyze/security/:runId` 를 그대로 쓴다. "한 번에" 는 브라우저가 두 요청을 동시에 보내는
  것이지 새 엔드포인트가 아니다. 두 분석을 한 run 으로 묶는 서버 변경은 이유가 생길 때 따로 한다.
- **성능 효율성 축의 내용.** 측정 항목, 패키지, API 는 그 패키지의 설계가 정한다. 여기서는 카드의
  자리와 "준비 중" 상태만 정한다. 목업의 칩(p50·p95 지연, 초당 호출, 동시성)은 예시이고 계약이 아니다.
- **목업의 파생 수치 두 개.** "호출 1,000회당 절감" 과 "소스 반영 가능 N건" 은 현재 응답에 없다. 앞은
  호출 횟수 가정이 들어가고, 뒤는 소스 수정 미리보기 요청을 먼저 보내야 안다. 둘 다 넣지 않는다.
- **사용자 모드의 사전 점검(`#/user/check`).** 별개 화면이고 행동은 바뀌지 않는다. 다만 `PreCheck.tsx` 와
  `precheck.test.tsx` 가 지금 `SecurityPanel.tsx` 에서 `ErrorAlert`·`REMOTE_SANDBOX_HINT`·`SecurityProgress` 를
  import 하므로(2026-10-18 grep), 그 셋이 자기 파일로 옮겨가면 **import 경로 두 줄만** 바뀐다(§8).
- **Reliability, 운영 효율성 축.** 사용자가 세 축만 요청했다. 축 계약(§5)은 늘릴 수 있게 두되 카드를
  만들지 않는다.
- **분석 결과의 저장·이력.** 결과는 지금처럼 화면 상태에만 있고 Analyze 를 떠나면 사라진다. 카드의
  "마지막 분석" 은 이 세션 안의 결과를 가리킨다.

### 1.3 완료 조건

- `#/analyze` 가 세 카드를 보이고 상세는 보이지 않는다. 성능 카드는 `aria-disabled` 이고 눌러도 주소가
  바뀌지 않는다.
- 서버를 고르고 **한 번에 분석** 을 누르면 `POST /api/analyze/tokens` 와 `POST /api/analyze/security`
  가 **같은 렌더 사이클 안에서** 둘 다 나간다(테스트는 fetch 호출 순서와 본문을 단언한다, §10).
- 토큰 응답이 오면 비용 카드가 요약을 보이고, 보안 run 이 끝나 결과를 읽으면 보안 카드가 요약을
  보인다. 한쪽이 실패해도 다른 쪽 카드는 결과를 보인다.
- 카드를 누르면 `#/analyze/security` 또는 `#/analyze/tokens` 가 되고 상세가 펼쳐진다. 주소로 바로
  들어가도 같은 화면이다. 상세에 있는 동안 카드 셋은 그대로 위에 남는다.
- 지금 `analyze-view.test.tsx` 와 `security-panel.test.tsx` 가 단언하는 **상세의 행동**(개발자/사용자 전환,
  묶기, 원본·압축 비교, 소스 반영, 다시 분석, 다시 점검, 실패 문장 원문, 격리·기준 파일·limits 표시)이
  새 구조에서도 전부 통과한다. 단언 내용은 유지하고 진입 경로만 바뀐다. 반면 **단계(Stepper)·탭·"점검
  시작"/"분석 시작" 버튼·"← 서버 다시 고르기" 에 묶인 단언**은 그 요소가 사라지므로 유지할 수 없다. 이들은
  §10.4 의 원칙대로 지우거나 새 구조의 같은 행동으로 다시 쓴다. 테스트 하나하나의 처분은 구현 계획이
  표로 확정한다.
- `pnpm test`, `pnpm typecheck --force`, `pnpm lint` 녹색. 검사 대상 파일 수를 출력에서 확인한다.

## 2. 지금 화면과 바뀌는 점

지금 `AnalyzeView` 는 탭 둘(토큰, 보안)이고, 탭마다 패널(`TokensPanel`, `SecurityPanel`)이 **폼·시작·
진행·결과를 전부 소유**한다. 접속 상태(`useAnalyzeTarget`)만 `AnalyzeView` 가 한 번 만들어 둘에 넘긴다.
그래서 두 축을 한 번에 시작할 자리가 없고, 한 축의 결과를 보는 동안 다른 축의 상태를 알 수 없다.

| 항목 | 지금 | 바뀐 뒤 |
|---|---|---|
| 첫 화면 | 토큰 탭의 서버 선택 폼 | 대상 폼(펼침) + 세 카드(비어 있음) |
| 시작 | 탭마다 버튼(분석 시작 / 점검 시작) | **한 번에 분석** 하나. 축별 다시 분석·다시 점검은 상세 하단에 남는다 |
| 분석 상태의 주인 | 각 패널 | `AnalyzeView`. 패널은 받은 상태를 그리기만 한다 |
| 보안 옵션(호출 정책·기준 파일·격리) | 보안 패널의 폼 | 대상 영역 안의 "보안 옵션" 접이식. 상태는 `AnalyzeView` 가 든다 |
| 라우트 | `#/analyze`(=토큰), `#/analyze/security` | `#/analyze`(개요), `#/analyze/tokens`, `#/analyze/security` |
| 단계 표시(Stepper) | 패널마다 "서버 선택 → 결과" | 없앤다. 단계는 카드의 상태 배지가 대신한다 |
| 성능 효율성 | 없음 | 비활성 카드 |

**바꾸지 않는 것.** `useAnalyzeTarget`, `buildAnalyzeArgv`, `buildSecurityRequest`, `security-view.ts`,
`risk-text.ts`, `tool-diff.ts`, `format.ts`, `SourceEditCard`, `SecurityResult`, `TokensResult` 의 내부.
이들이 만드는 문장과 숫자는 CLI 와 같아야 한다는 기존 계약이 있고, 이 설계는 **배치**를 바꾸는 것이지
내용을 바꾸는 것이 아니다. `SecurityResult`·`TokensResult` 는 상세 패널 안에서 그대로 쓴다.

## 3. 화면 구조

위에서 아래로 네 구획이다. 폭은 지금 `max-w-[800px]` 에서 `max-w-[1040px]` 로 넓힌다. 카드 셋을 한 줄에
두려면 필요하고, 760px 아래에서는 한 열로 쌓는다.

### 3.1 머리

`PageHeader`. 제목 "분석", 설명 "서버에 한 번 붙어 도구 정의를 읽고, 세 축으로 나눠 봅니다. 축을 고르면
상세가 아래에 펼쳐집니다." `aside` 는 두지 않는다. 목업의 "마지막 분석 09:41" 은 시각을 읽어야 하므로
**넣지 않는다**(ADR-0069 와 같은 이유. 같은 상태를 두 번 그리면 글자가 달라진다).

### 3.2 대상 영역

두 모양이 있고 `AnalyzeView` 의 `targetOpen` 하나로 고른다.

- **펼침**: `Card` 안에 `AnalyzeTargetForm`(기존), 그 아래 경계선, "보안 옵션" 구획(지금 `SecurityPanel`
  의 호출 정책·기준 파일·기준 갱신·격리·호스트 비교·허용 호스트 그대로), 맨 아래 **한 번에 분석**
  버튼과 비활성 사유. 처음 들어오면 이 모양이다.
- **접힘**: 한 줄 바. 서버 칸(후보면 `name`, 직접 입력이면 고정 글자 "직접 입력"), 명령 칸(`describeRun("audit",
  argv).server`, 없으면 빈 문자열), 보안 옵션 요약(`probe <정책> · 기준 파일 <경로>` 또는 `기준 파일 없음`,
  격리가 켜졌고 stdio 면 `· 격리`), 오른쪽에 **대상 바꾸기**(펼침으로) 와 **한 번에 분석**. 한 번에 분석의
  두 요청 중 하나라도 시작에 성공하면 이 모양이 된다(§7.4).

"보안 옵션" 구획의 `h2` 글자는 지금 `SecurityPanel` 의 "점검 옵션" 을 그대로 쓴다. 이 문서가 구획을 "보안
옵션" 이라 부르는 것은 설명이고, 화면 글자는 바꾸지 않는다.

대상 바꾸기로 펼쳐도 **결과는 지우지 않는다.** 다음 한 번에 분석이 성공적으로 시작될 때 축별 규칙(§7)
대로 교체된다. 그 사이 카드와 상세가 가리키는 대상이 폼과 다를 수 있으므로 `done` 카드의 요약 줄 앞에
"분석한 대상: <이름> · " 을 **항상** 붙인다(§3.3 의 `foot`). 이름은 그 축이 성공한 요청(토큰은 `analyzed`,
보안은 `sent`)에서 구한다. `serverId` 가 후보 목록에 있으면 그 후보의 `name`, 아니면
`describeRun("audit", argv).server ?? ""` 다. 폼과 같은지 비교하지 않는다. 비교하면 같은 결과를 두 번 그릴
때 글자가 달라진다.

### 3.3 축 카드

세 장, 같은 틀. `role="tablist"` 안의 `role="tab"` 이고 고른 카드는 `aria-selected="true"` 다. 카드는
`<a href="#/analyze/<축>">` 로 만든다. 지금 탭이 링크인 것과 같은 이유다(주소가 상태다).

카드 한 장의 자리와 축별 내용:

| 자리 | 보안 | 비용 최적화 | 성능 효율성 |
|---|---|---|---|
| 눈썹(영문, 대문자) | SECURITY | COST OPTIMIZATION | PERFORMANCE EFFICIENCY |
| 이름 | 보안 | 비용 최적화 | 성능 효율성 |
| 판정 배지 | §6.1 `verdict` | §6.2 `verdict` | "준비 중"(accent 톤) |
| 설명(고정) | 도구 설명·결과·네트워크·비밀값을 점검해 공격 표면과 유출 경로를 찾습니다. | 도구 정의가 매 호출마다 컨텍스트에 실리는 토큰을 재고, 압축 오버레이로 얼마나 줄어드는지 봅니다. | 도구 호출 지연·처리량·동시성 한계를 재고, 부하 변화에 맞게 조정할 지점을 찾습니다. |
| 큰 숫자 | 결함 수(`counts` 합) + "건 발견 · 도구 N개 점검" | `−<percent>%` + "~<before> → ~<after> 토큰" | "—" + "아직 연결되지 않았습니다" |
| 분포 | 심각도 네 칸 막대(비율 = 각 심각도 수 / 결함 수) | 원본·압축 두 줄 막대(압축 폭 = after/before) | 빈 막대 |
| 칩 | 심각 N · 주의 N · 낮음 N · 정보 N · 흐름 경고 N | 도구 N · 공통 파라미터 승격 N | (고정 예시 칩 없음. 빈 칸) |
| 요약 줄(`foot`) | `baselineStatus` 문장, 없으면 `도구 <probedTools.length>개 호출 (probe <probe>)` | "가장 큰 감소: <도구> −<pct>%" , 줄지 않았으면 "줄어든 도구 없음" | "패키지 개발 중" |
| 오른쪽 끝 | "상세 →" | "상세 →" | "연결 예정" |

상태에 따라 큰 숫자 자리가 바뀐다(§5 `PillarState`):

- `idle`: 큰 숫자 자리에 "아직 분석하지 않았습니다", 배지 없음, 막대·칩 비움.
- `running`: 배지 "분석 중…"(보안은 "점검 중…", running 톤), 큰 숫자 자리에 "진행은 상세에서 봅니다".
  보안 상세에는 지금의 `LogPanel` 진행이 그대로 뜬다. 진행 스트림의 구독은 상세가 아니라 훅이 가지므로(§5.4)
  상세를 열지 않아도 run 이 끝나면 카드가 `done` 으로 바뀐다.
- `failed`: 배지 "실패"(failed 톤), 큰 숫자 자리에 오류 문장의 첫 줄, 요약 줄(`foot` 자리)에 고정 글자
  "전문은 상세에서 봅니다". CLI 문장의 "해결:" 줄은 둘째 줄 이후라 카드에서 잘리므로 이 안내가 있어야
  사용자가 상세로 간다. 전문은 상세의 `role="alert"`.
- `done`: 위 표.

색은 `theme.css` 의 기존 토큰만 쓴다. 심각도 색은 `SEVERITY_TONE` 그대로. 색만으로 뜻을 전하지 않는다.
라벨 글자가 항상 함께 있다.

### 3.4 상세

고른 축이 있을 때만 카드 아래에 `Card` 하나. 머리(`<h2>`)는 "<축 이름> 상세"("보안 상세", "비용 최적화
상세")이고 옆에 카드와 같은 판정 배지(`done` 이면 `verdict.label`, `running` 이면 "점검 중…"/"분석 중…",
`failed` 면 "실패", `idle` 이면 배지 없음). 개발자/사용자 전환과 심각도별/도구별 묶기는 지금처럼
`SecurityResult` **안에** 둔다. 상세 머리로 옮기지 않는다(§2 "바꾸지 않는 것" 과 충돌한다. 목업은 머리에
그렸지만 문서가 우선한다). 본문은 축 상태에 따라:

- `idle`: 빈 상태 문장 `<p>`. "아직 분석하지 않았습니다. 위에서 서버를 고르고 한 번에 분석을 누르세요."
- `running`: 보안은 `SecurityProgressView`(훅이 받은 `events`·`progressError` 를 그리기만 한다, §8) 와
  `<p>` "점검은 중단되지 않고 끝까지 돕니다." 비용은 `<p role="status">` "분석 중…".
- `failed`: 오류 문장 전문(`ErrorAlert`, `role="alert"`, CLI stderr 원문 그대로).
- `done`: `SecurityResult` 또는 `TokensResult` 를 `key={state.serial}` 로. `TokensResult` 의 `argv` 는
  `tokens.analyzed?.argv ?? []`, `onReanalyze` 는 `tokens.reanalyze`. 비용 상세는 `done` 본문 위에
  `reanalyzing` 이면 `<p role="status">` "분석 중…", `reanalyzeError` 가 있으면 `ErrorAlert`(지금 `TokensPanel`
  과 같은 배치). 보안 상세는 `done` 본문 위에 `startError` 가 있으면 `ErrorAlert`, 아래 조작 줄에 **다시
  점검**(`sent` 를 그대로 다시 `start`, `running` 이면 비활성). 비용의 소스 반영·다시 분석은 `TokensResult`
  가 이미 가진 것이다.

## 4. 상태 모델과 라우트

### 4.1 라우트

```
#/analyze                → { screen: "analyze", pillar: null }       개요만
#/analyze/tokens         → { screen: "analyze", pillar: "tokens" }   개요 + 비용 상세
#/analyze/security       → { screen: "analyze", pillar: "security" } 개요 + 보안 상세
#/analyze/<그 밖>         → { screen: "analyze", pillar: null }       개요(모르는 축은 개요로)
```

`tokens` 라는 세그먼트는 **유지**한다. 이름을 `cost` 로 바꾸면 기존 링크·테스트·ADR 의 주소가 전부
틀어지고 얻는 것이 없다. 화면 라벨만 "비용 최적화" 다. `performance` 는 아직 상세가 없으므로 개요로
보낸다. 연결할 때 이 줄 하나를 바꾼다.

### 4.2 상태의 주인

`AnalyzeView` 가 든다. 라우트가 `#/analyze*` 안에서 바뀌어도 `App` 은 같은 자리에 같은 컴포넌트를 그리므로
인스턴스가 유지되고 상태가 남는다(지금 두 탭이 접속 상태를 공유하는 것과 같은 성질). Analyze 를 떠나면
사라진다(§1.2).

```
AnalyzeView
├─ target        : AnalyzeTarget            (기존 useAnalyzeTarget)
├─ securityForm  : SecurityForm             (기존 INITIAL_SECURITY_FORM 에서 시작)
├─ targetOpen    : boolean                  (대상 영역 펼침)
├─ tokens        : TokensAnalysis           (§5.3, TokensPanel 에서 추출한 훅)
└─ security      : SecurityAnalysis         (§5.4, SecurityPanel 에서 추출한 훅)
```

두 훅은 지금 패널 안의 로직을 **옮기는** 것이지 새로 쓰는 것이 아니다. 늦게 도착한 결과 버리기
(`awaitedRun`), 결과 serial 로 상세 상태 비우기, 시작 실패 시 앞 결과 유지 같은 규칙이 전부 그대로
따라온다. `rememberCommand` 는 훅이 아니라 부르는 쪽(`AnalyzeView`)이 `start` 의 반환값을 보고 부른다.

한 가지가 패널과 다르다. **보안 run 의 진행 스트림(SSE)은 보안 훅이 구독한다.** 지금은 점검 단계에만
마운트되는 `SecurityProgress` 가 `useRunEvents` 를 열고 끝남을 부모에 알린다. 새 구조에서는 상세를 열지
않아도 카드가 끝남을 알아야 하므로(§1.3), 구독이 상세 컴포넌트에 있으면 상세를 닫은 동안 run 이 끝나도
카드가 "점검 중…" 에서 벗어나지 못한다. 그래서 `useSecurityAnalysis` 가 `useRunEvents(runId)` 를 직접
부르고, 끝남·없음을 자기 상태 전이로 처리한다. 상세의 진행 패널은 훅이 준 `events` 를 그리기만 한다.

### 5.4 두 훅

```ts
// packages/dashboard/web/src/analyze/use-tokens-analysis.ts
export interface TokensAnalysis {
  readonly state: PillarState<AnalyzeTokensResponse>;
  /** 성공한 요청 그대로. 다시 분석과 소스 반영이 이것을 쓴다. 성공 전에는 null. */
  readonly analyzed: AnalyzeTokensRequest | null;
  /**
   * `POST /api/analyze/tokens`. 보내는 순간 running 이 되고 앞 결과는 내려간다(지금 규칙).
   * 응답이 오면 done, 실패하면 failed. 성공이면 true 를 돌려준다. 부르는 쪽이 이 값으로 `rememberCommand` 와
   * 대상 영역 접기를 결정한다(상태를 다시 읽으면 클로저가 낡은 값을 본다).
   */
  readonly start: (request: AnalyzeTokensRequest) => Promise<boolean>;
  /** 같은 요청으로 다시. 실패하면 done 을 유지한 채 `reanalyzeError` 만 채운다(지금 규칙). */
  readonly reanalyze: () => Promise<void>;
  readonly reanalyzing: boolean;
  readonly reanalyzeError: string | null;
}
export function useTokensAnalysis(): TokensAnalysis;

// packages/dashboard/web/src/analyze/use-security-analysis.ts
export interface SecurityAnalysis {
  readonly state: PillarState<AnalyzeSecurityResponse>;
  /** 시작에 성공한 요청 그대로. 다시 점검이 이것을 보낸다. */
  readonly sent: AnalyzeSecurityRequest | null;
  /** running 일 때의 run. 훅이 이 run 의 SSE 를 `useRunEvents` 로 연다. 결과를 읽거나 실패하면 null 로 돌아가 스트림이 닫힌다. */
  readonly runId: string | null;
  /**
   * `POST /api/analyze/security`. 시작에 성공하면 앞 결과가 내려가고 running 이 된다(true).
   * 실패하면(false) `state.kind === "done"` 일 때는 done 을 유지하고 `startError` 만 채운다. 그 밖(idle·failed)
   * 이면 failed { error } 로 간다. 첫 분석의 시작 실패는 카드에 "실패" 로 보여야 하기 때문이다(§7.5).
   */
  readonly start: (request: AnalyzeSecurityRequest) => Promise<boolean>;
  /** 시작 요청 자체의 실패 문장. done 을 유지한 채 옆에 보인다. 다음 start 가 비운다. */
  readonly startError: string | null;
  /** 도는 run 의 진행 이벤트(`useRunEvents(runId).events`). running 이 아니면 빈 배열. 상세가 그린다. */
  readonly events: readonly RunEvent[];
  /** 스트림 조회만 실패한 문장(`useRunEvents(runId).error` 중 missing 이 아닌 것). run 은 살아 있을 수 있어 상태를 바꾸지 않는다. */
  readonly progressError: string | null;
}
export function useSecurityAnalysis(): SecurityAnalysis;
```

두 훅의 본문은 지금 `TokensPanel`·`SecurityPanel` 의 해당 부분을 옮긴다. 옮기면서 바꾸는 것은 상태를
`PillarState` 한 값으로 모으는 것, `start` 가 성공 여부를 돌려주는 것(지금 `SecurityPanel.start` 는 이미
`Promise<boolean>` 이다), 그리고 보안 훅이 SSE 구독을 갖는 것이다. 구독 규칙은 지금 `SecurityProgress`
의 것을 그대로 옮긴다. `useRunEvents(runId)` 의 `status` 가 `done` 또는 `failed` 가 되면 run 당 **한 번만**
`GET /api/analyze/security/<runId>` 를 읽고(`reportedRun` ref 로 run 별 1회), `missing` 이면 한 번만
failed 로 간다. `awaitedRun` 과 다른 run 의 응답은 버린다.

구현 계획의 T2 는 패널의 "← 서버 다시 고르기" 를 살려 두기 위해 두 훅에 임시 `reset(): void` 를 더하고
T3 이 지운다. 이 계약 표에는 넣지 않는다. 임시라서다.

## 6. 카드 요약 규칙

여기가 이 설계에서 판단이 들어가는 유일한 곳이다. 그래서 전량 적는다. 숫자의 식은 `format.ts` 의
`percent`·`tokens` 만 쓴다. CLI 리포트와 같은 식이어야 하기 때문이다.

### 6.1 보안

```ts
export function securitySummary(request, response): PillarSummary {
  const { report } = response;
  const { high, medium, low, info } = report.counts;        // flow 는 세지 않는다(audit 계약)
  const defects = high + medium + low + info;
  const flows = splitFindings(response).flows.length;

  // 판정은 CLI 의 exitCode 를 따른다. 화면이 새 임계값을 두지 않는다.
  // audit.ts: exitCode = high + medium > 0 ? 2 : 0
  // 라벨은 칩과 모순되면 안 된다. 낮음·정보 칩이 0 인데 "낮음·정보만" 이라 쓰면 사용자가 칩을 못 믿는다.
  // exitCode 2 의 식은 audit.ts 의 high + medium > 0 이다. exitCode 1(격리 정리 실패)이어도 counts 는 그대로이므로
  // 같은 식을 함께 본다. 그렇지 않으면 칩 "심각 1" 옆에 "낮음·정보만" 이 뜬다.
  const verdict: PillarVerdict =
    report.exitCode === 2 || high + medium > 0 ? { label: "조치 필요", tone: "failed" }
    : defects > 0 ? { label: "낮음·정보만", tone: "running" }
    : flows > 0 ? { label: "흐름 경고만", tone: "waiting" }
    : { label: "발견 없음", tone: "done" };

  const bar = defects === 0 ? [] : [
    { ratio: high / defects,   tone: "failed",  label: "심각" },
    { ratio: medium / defects, tone: "waiting", label: "주의" },
    { ratio: low / defects,    tone: "running", label: "낮음" },
    { ratio: info / defects,   tone: "info",    label: "정보" },
  ].filter((segment) => segment.ratio > 0);

  const chips = [
    { label: "심각", count: high,   tone: "failed" },
    { label: "주의", count: medium, tone: "waiting" },
    { label: "낮음", count: low,    tone: "running" },
    { label: "정보", count: info,   tone: "info" },
    { label: "흐름 경고", count: flows, tone: "waiting" },
  ];                                                        // 0 이어도 빼지 않는다. 자리가 흔들리면 읽기 어렵다

  return {
    verdict,
    headline: String(defects),
    headlineNote: `건 발견 · 도구 ${report.server.toolCount}개 점검`,
    bar,
    chips,
    foot: baselineStatus(request, response) ?? `도구 ${report.probedTools.length}개 호출 (probe ${report.probe})`,
  };
}
```

`report.server.toolCount` 는 `@mcpeak/audit` 의 `ServerSummary` 에 있는 필드다(`packages/audit/src/types.ts`).
`counts` 와 `exitCode` 도 같은 파일의 `AuditReport` 계약이다. 화면이 세지 않는다.

### 6.2 비용 최적화

```ts
export function tokensSummary(response): PillarSummary {
  const { source, totals, tools } = response.overlay;
  const before = totals.bytesBefore;
  const after = totals.bytesAfterWithInstructions;
  const reduced = before - after;
  const pct = percent(reduced, before);                     // format.ts, 소수 첫째 자리 문자열

  const verdict: PillarVerdict =
    reduced > 0 ? { label: `${pct}% 줄일 수 있음`, tone: "waiting" }
    : { label: "줄일 것 없음", tone: "done" };

  // 도구별 감소 1위. TokensResult 의 sortedTools 와 같은 비교(감소 바이트 내림차순, 같으면 원본 순서).
  const top = tools
    .map((tool, index) => ({ tool, index, reduced: tool.bytes.before - tool.bytes.after }))
    .sort((x, y) => y.reduced - x.reduced || x.index - y.index)[0];

  return {
    verdict,
    headline: reduced > 0 ? `−${pct}%` : "0%",
    headlineNote: `~${tokens(before)} → ~${tokens(after)} 토큰`,
    bar: before === 0 ? [] : [{ ratio: after / before, tone: "accent", label: "압축" }],
    chips: [
      { label: "도구", count: source.toolCount, tone: "info" },
      { label: "공통 파라미터 승격", count: totals.promotedParameters, tone: "info" },
    ],
    foot: top !== undefined && top.reduced > 0
      ? `가장 큰 감소: ${top.tool.name} −${percent(top.reduced, top.tool.bytes.before)}%`
      : "줄어든 도구 없음",
  };
}
```

비용 카드의 막대는 두 줄(원본 100%, 압축 after/before)이다. `bar` 에는 압축 칸 하나만 싣고 원본 줄은
카드가 고정으로 그린다. `otherCapabilities` 주의 문장은 지금처럼 상세(`TokensResult`)에만 둔다.

### 6.3 임계값이 없는 이유

보안 판정은 CLI 의 `exitCode` 가 이미 "조치 필요" 의 경계(high 또는 medium 1건 이상)를 정했다. 비용은
"몇 % 이상이면 줄일 만하다" 는 기준이 사용처마다 달라 화면이 정할 수 없다. 그래서 0 과 0 이 아님만
가른다. 임계값을 두고 싶어지면 그때 ADR 로 정한다.

## 7. 한 번에 분석의 동작 규칙

1. 버튼 비활성 조건과 사유는 지금 두 패널의 것을 합친다. `target.argv` 가 오류면 그 문장. 아니면
   `buildSecurityRequest` 가 던지는 문장. 둘 다 없으면 활성. `tokens.state.kind === "running"` 또는
   `security.state.kind === "running"` 이면 비활성이고 사유는 "분석이 돌고 있습니다". 입력 오류와 동시면 이
   사유가 우선이다(돌고 있는 동안에는 입력을 고쳐도 누를 수 없기 때문이다).
2. 누르면 **같은 틱에** `tokens.start(tokensRequest)` 와 `security.start(securityRequest)` 를 부른다.
   둘을 `await` 로 잇지 않는다. 요청 본문은 지금 각 패널이 만드는 것과 글자 단위로 같다(§10 이 단언).
3. 성공·실패는 축별이다. 토큰이 400 으로 실패해도 보안 run 은 돈다. 반대도 같다.
4. 두 요청 중 하나라도 시작에 성공하면 `targetOpen` 을 `false` 로 하고 `target.rememberCommand()` 를
   한 번 부른다. "시작에 성공" 은 각 훅의 `start` 가 `true` 로 resolve 한 것이다. 둘을 `Promise.all` 로
   기다리지 않고 **각 Promise 에 따로** 후속을 건다. 토큰의 `start` 는 응답이 와야 끝나므로, 보안이 먼저
   시작되면 토큰 결과를 기다리지 않고 바로 접힌다. 두 후속이 모두 `true` 여도 접기와 `rememberCommand` 는
   한 번만 한다(ref 로 가드). 둘 다 `false` 면 펼친 채 두고 각 카드가 `failed` 를 보인다.
5. 결과 교체 규칙은 축별 기존 규칙이다. 토큰은 요청을 보내는 순간 앞 결과가 내려간다(`running`). 보안은
   **시작에 성공한 순간** 앞 결과가 내려간다. 보안의 시작 실패는 앞 결과가 있으면(`done`) 그것이 남고
   `startError` 만 보인다. 앞 결과가 없으면(`idle`·`failed`) 카드가 `failed` 가 된다. 지금 패널은 서버
   선택 단계에서 오류를 폼 아래 보였는데, 그 자리가 카드의 `failed` 로 바뀐 것이다.
6. 상세 하단의 **다시 점검**(보안)·**다시 분석**(비용)은 한 축만 다시 돌린다. 지금과 같다.
7. 취소 API 는 없다. 지금과 같이 "점검은 중단되지 않고 끝까지 돕니다" 를 상세에 적는다.

- "다시 분석이 실패하면 상세에 머물고 CLI 문장을 보인다": 카드는 `done` 그대로(`reanalyzeError` 규칙).

### 10.4 `web/tests/security-detail.test.tsx` (`security-panel.test.tsx` 를 옮김)

- 기존 테스트의 처분 원칙. **상세 안의 결과 표시**(판정 줄, 발견, 근거, 묶기, flow 구획, 격리·기준 파일·
  limits·원문, HTML 미해석)와 **옵션 폼의 행동**(옵션이 본문에 실림, 기준 파일·격리·허용 호스트 토글)은
  단언을 그대로 두고 진입만 "한 번에 분석 → 보안 runId → SSE done → GET 결과 → 보안 상세" 로 바꾼다.
  **Stepper 단계·"점검 시작" 버튼·"← 서버 다시 고르기"·탭 전환** 에 묶인 테스트는 같은 행동을 새 구조의
  요소(카드 상태 배지, "한 번에 분석", "대상 바꾸기", `pillar` prop)로 다시 쓰거나, 개요 테스트가 이미 덮으면
  지운다. 테스트 하나하나의 처분(유지·재작성·삭제)은 구현 계획이 표로 확정하고, 그 표 밖의 삭제는 없다.
- 추가: "run 이 끝나 결과를 읽으면 보안 카드가 요약을 보인다": 카드에 판정 라벨과 결함 수.
- 추가: "GET 결과가 실패하면 보안 카드가 실패이고 상세에 문장 전문이 있다".
- 추가: "run 이 없다고 확인되면 카드가 실패이고 대상 영역은 접힌 채다".
- 추가: "다시 점검은 sent 요청을 그대로 다시 POST 하고 앞 결과를 내린다": 두 번째 POST 본문이 첫 번째와
  `JSON.stringify` 로 같다. 응답 전까지 카드가 "점검 중…".
- 추가: "다시 점검의 시작 요청이 실패하면 앞 결과가 남고 startError 만 보인다".
- 추가: "첫 시작 요청이 실패하면 보안 카드가 실패이고 첫 줄을 보인다"(§7.5 의 idle → failed).
- 추가: "상세를 닫은 채 run 이 끝나도 보안 카드가 요약을 보인다"(§5.4 의 구독 위치. `pillar={null}` 로만
  그린 채 SSE done 을 흘리고 카드에 판정 라벨이 뜨는지).

### 10.5 지우는 테스트

Stepper·탭·"점검 시작"/"분석 시작"·"← 서버 다시 고르기" 에 묶인 테스트 중 개요 테스트가 같은 행동을 덮는
것. 목록은 구현 계획이 확정한다. `analyze-view.test.tsx` 의 "토큰 탭이 기본이고 탭 둘이 tablist 에 있다" 는
그중 하나다.

## 12. ADR 초안 대상

**ADR-0116 (제목 안) Analyze 는 탭이 아니라 축 카드와 상세이고, 축은 한 번에 시작하되 상태는 독립이다.**

- 배경: 로드맵 §0 과 ADR-0111 이 "탭 둘" 로 정했다. 탭은 한 번에 한 축만 보이고 시작도 축마다 따로라,
  "이 서버가 어떤 상태인지" 를 한눈에 못 본다.
- 선택지: (a) 탭 유지 + 탭 라벨에 배지, (b) 축 카드 + 상세(이 설계), (c) 두 결과를 한 run 으로 묶는 서버
  엔드포인트 + 단일 리포트 화면.
- 결정: (b). 서버는 그대로 두고 브라우저가 두 요청을 동시에 보낸다. 축 상태는 독립이다.
- 이유: (a) 는 한눈에 보기가 안 된다. (c) 는 서버 변경과 리포트 포맷 합의가 필요하고, 보안은 run(SSE)
  이고 토큰은 동기 요청이라 수명이 달라 한 run 으로 묶으면 토큰 결과가 보안 끝날 때까지 기다린다.
- 결과: 세 번째 축은 카드·훅·상세 세 파일과 `parseRoute` 한 줄로 끼운다. 판정은 계속 CLI 의 것이다.

## 13. 임의로 판단한 것과 열린 질문

판단한 것(이 문서의 기준으로 확정, 반대 없으면 그대로 간다):

1. 라우트 세그먼트 `tokens` 유지, 라벨만 "비용 최적화". §4.1.
2. "마지막 분석 시각" 을 카드와 머리에서 뺐다. 시각을 읽는 순간 결정론이 깨진다. §3.1.
3. 대상 바꾸기가 결과를 지우지 않는다. 대신 카드 요약 줄에 분석한 대상을 적는다. §3.2.
4. 비용 판정에 임계값을 두지 않았다. 0 과 0 아님만 가른다. §6.3.
5. 흐름 경고를 결함 수에서 빼고 칩에만 넣었다. audit 의 `counts` 계약과 같다. §6.1.
6. Stepper 를 Analyze 에서 걷었다. 단계가 카드 상태로 보인다. §8.
7. 성능 카드 칩의 예시 글자를 넣지 않았다. 그 패키지의 설계가 정할 일이다. §9.
8. (개정 1) 보안 SSE 구독을 훅에 두었다. 상세에 두면 상세를 닫은 동안 카드가 끝남을 모른다. §4.2·§5.4.
9. (개정 1) 보안의 첫 시작 실패는 카드 `failed` 다. 앞 결과가 있을 때만 `startError` 로 옆에 보인다. §7.5.
10. (개정 1) 개발자/사용자·묶기 전환은 `SecurityResult` 안에 그대로 둔다. 목업은 상세 머리에 그렸지만
    `SecurityResult` 를 바꾸지 않는다는 §2 가 우선이다. §3.4.
11. (개정 1) "← 서버 다시 고르기" 가 사라진다. 지금은 도는 run 을 화면에서 버리고 새 점검을 시작할 수
    있었다. 새 구조에서는 run 이 도는 동안 한 번에 분석이 비활성이라(§7.1) 끝날 때까지 기다려야 한다.
    취소 API 가 없어 서버의 run 은 어차피 끝까지 돌았으므로, 화면만 먼저 떠나는 길을 없앤 것이다. 격리
    점검이 길어 불편하면 그때 취소 API 와 함께 ADR 로 정한다.

열린 질문(구현 계획 전에 답이 필요하다):

- Q1. 보안 옵션을 대상 영역 안에 두는 것이 맞는가, 아니면 보안 카드 안에 두는 것이 맞는가. 이 설계는
  대상 영역 안이다. "한 번에 분석" 을 누르기 전에 전부 정해져 있어야 하기 때문이다. 카드 안에 두면
  한 번에 분석이 카드 밖의 버튼인데 설정은 카드 안이라 시선이 갈린다.
- Q2. 성능 효율성 패키지의 API 가 보안처럼 run(SSE) 인지 토큰처럼 동기인지. 어느 쪽이든 §5.3 의
  `PillarState` 로 들어오지만, run 이면 상세에 `LogPanel` 자리가 필요하다. 그 패키지 설계가 정해지면
  §9 에 한 줄 적는다.
