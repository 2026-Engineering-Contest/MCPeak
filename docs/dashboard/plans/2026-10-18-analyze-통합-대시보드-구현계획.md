# Analyze 통합 대시보드 구현계획 (2026-10-18, 개정 1)

개발자 모드의 Analyze 화면을 탭 둘에서 **축 카드 셋 + 고른 축의 상세** 로 바꾼다. 설계는
`docs/dashboard/2026-10-18-analyze-통합-대시보드-설계.md`(개정 1, 이하 설계) 이고 이 계획은 그 설계를 태스크로 나눈
것이다. 목업은 `docs/dashboard/mockups/2026-10-18-analyze-통합-대시보드/analyze-dashboard.html` 이다.

**설계와 이 계획의 우선순위.** 설계 §5(공유 계약)·§6(요약 규칙)·§7(동작 규칙)과 이 계획이 다르면 설계가
우선하고, 다르다는 사실을 `BLOCKED` 로 보고한다. 단 아래는 이 계획이 의도적으로 설계와 다르게 적은
**예외** 이며 BLOCKED 사유가 아니다.

| 예외 | 설계 | 계획 | 이유 |
|---|---|---|---|
| 임시 `reset(): void` | §5.4 계약에 없음 | T2 가 두 훅에 더하고 T3 이 지운다 | T2 는 테스트를 못 고치므로 "← 서버 다시 고르기" 가 살아 있어야 한다 |

## 1. 실행 모델

이 계획은 `finish-plan` 위임 모델로 돈다. CLAUDE.local.md 의 기본(터미널 세션이 오케스트레이터이고 태스크마다
서브에이전트를 스폰)과 다르게, **오케스트레이터는 별도 세션** 이고 각 웨이브의 실행 세션이 직접 구현한다.
네 웨이브가 직렬이라 한 세션 안에서 스폰할 병렬 작업이 없고, 실행 세션을 웨이브마다 빈 컨텍스트로 새로 여는
편이 앞 웨이브의 맥락에 덜 끌려가기 때문이다.

- 오케스트레이터: 프로젝트 루트의 세션 하나. 웨이브 선언, 실행 세션에 프롬프트 전달, 재검증·검토, 수정
  지시, 통합 게이트(§9)를 맡는다. 구현하지 않는다.
- 실행 세션: 웨이브마다 하나. 사람이 프로젝트 루트에서 §8 의 권장 실행 명령으로 열고 블록을 붙여넣는다.
  오케스트레이터가 `finish-plan` 스킬로 빈 idle 세션에 넘겨도 된다. 서브에이전트를 스폰하지 않는다.
- 수정 루프: 오케스트레이터가 같은 실행 세션에 `SendMessage` 로 결함 목록을 보낸다(§9.4).

### 2.5 테스트

`analyze-pillars.test.ts` (새 파일, `// @vitest-environment node`). 픽스처는 파일 안의 인메모리 객체다.

`tokensResponse(...)` 는 `analyze-view.test.tsx` 의 `analyzeResponse()` 를 복사한다(before 1000, after 760,
도구 a 600→400, b 400→360, promotedParameters 2. 복사한 뒤 이 수치가 맞는지 파일에서 확인하고 다르면
테스트의 기대값을 **픽스처에 맞춘다**. 손으로 다시 계산해 보고서에 적는다).

```ts
import type { AuditReport, Finding } from "@mcpeak/audit";
import type { AnalyzeSecurityRequest, AnalyzeSecurityResponse } from "../../src/api-types.js";

function finding(ruleId: string): Finding {
  // severity·location·message 는 요약 함수가 읽지 않는다. 형식만 맞춘다.
  return {
    ruleId, severity: "high", location: { kind: "tool", toolIndex: 0, toolName: "a", path: "name" },
    message: ruleId, evidence: [], fix: "",
  } as Finding;
}
const HIGH_ONLY = finding("desc/hidden-unicode");
const LOW_A = finding("result/oversized");
const LOW_B = finding("result/oversized");
const CHANGED = finding("surface/changed");
const FLOW = finding("flow/toxic-combination");

/** 요약 함수가 읽는 report 필드만 바꾼다. 나머지는 고정이다. */
function securityResponse(overrides: {
  readonly counts?: AuditReport["counts"];
  readonly exitCode?: number;
  readonly findings?: readonly Finding[];
  readonly probedTools?: readonly string[];
} = {}): AnalyzeSecurityResponse {
  const findings = overrides.findings ?? [HIGH_ONLY];
  const counts = overrides.counts ?? { high: 1, medium: 0, low: 0, info: 0 };
  const exitCode = overrides.exitCode ?? 2;
  const report = {
    schemaVersion: 1,
    generator: { name: "@mcpeak/audit", version: "0.0.0" },
    server: { name: "sample", version: "1.0.0", toolCount: 2, promptCount: 0, resourceCount: 0, hasInstructions: false, capabilityKeys: ["tools"] },
    probe: "readonly",
    probedTools: overrides.probedTools ?? ["add"],
    findings,
    skipped: [],
    counts,
    exitCode,
  } as AuditReport;
  return {
    report,
    reportText: "",
    rendered: "",
    views: findings.map(() => ({ where: "서버", tool: null, toolIndex: -1 })),
    sandboxLine: null,
    limits: [],
    exitCode,
    cleanupError: "",
  } as AnalyzeSecurityResponse;
```

### 3.3 옮기는 규칙 (여기가 사양이다. 지금 패널의 주석이 말하는 규칙을 상태 전이로 다시 적은 것)

`useTokensAnalysis`:

| 지금 | 옮긴 뒤 |
|---|---|
| `setAnalyzing(true); setError(null); setResult(null)` 뒤 POST | `state = running`, `reanalyzeError = null` 뒤 POST. 앞 결과는 이 순간 내려간다 |
| 성공: `setResult`, `setAnalyzed(body)`, `serial + 1`, `rememberCommand()` | `state = done { result, serial: 다음 serial }`, `analyzed = body`. **`true` 를 돌려준다.** `rememberCommand` 는 훅이 부르지 않는다 |
| 실패: `setError(CLI 문장)` | `state = failed { error }`. `analyzed` 는 **바꾸지 않는다**. `false` 를 돌려준다 |
| `reanalyze` 시작 | `reanalyzing = true`, `reanalyzeError = null` |
| `reanalyze` 성공 | `state = done { result, serial: 다음 serial }` |
| `reanalyze` 실패 | `state` 는 done 그대로, `reanalyzeError = 문장` |
| "← 서버 다시 고르기": `setResult(null); setError(null)` | `reset()`: `state = idle`, `reanalyzeError = null`. `analyzed` 는 그대로 |

"다음 serial" 은 `useRef<number>(0)` 를 하나 올린 값이다(`state` 에서 읽으면 running 을 거친 뒤라 항상 1 이
된다). 패널(T2)은 `start` 가 `true` 를 돌려주면 `target.rememberCommand()` 를 부른다. 버튼의 "분석 중…" 과
비활성은 `state.kind === "running"` 으로 판정한다. 패널이 보이는 오류 문장은
`state.kind === "failed" ? state.error : reanalyzeError` 이고, 지금처럼 폼 단계와 결과 단계 양쪽의 같은 자리에
`ErrorAlert` 로 그린다.

`useSecurityAnalysis`:

| 지금 | 옮긴 뒤 |
|---|---|
| `start` 성공: `setResult(null); setSent; setRunId; awaitedRun = runId` | `state = running`, `sent = request`, `runId`, `awaitedRun.current = runId`, `reportedRun.current = null`, `startError = null`. **`true`**. `reportedRun` 을 비우는 것은 지금 `SecurityProgress` 가 `key={runId}` 로 재마운트되며 ref 가 새로 생기던 것과 같은 효과다 |
| `start` 실패: `setError` (앞 결과 유지) | `state.kind === "done"` 이면 `startError = 문장` 만. 아니면(`idle`·`failed`) `state = failed { error: 문장 }`, `startError = null`. **`false`** |
| `SecurityProgress` 의 `onFinished` (run 당 1회) | 훅 안에서 `const run = useRunEvents(runId)`. `run.status` 가 `"done"`·`"failed"` 가 되면 `reportedRun.current !== runId` 일 때만 `reportedRun.current = runId` 로 적고 `loadResult(runId)` |
| `loadResult` 성공 (`awaitedRun === id`) | `awaitedRun = null`, `runId = null`, `state = done { result, serial: 다음 serial }`. `runId` 가 null 이 되면 `useRunEvents` 가 EventSource 를 닫는다(지금은 `SecurityProgress` 가 언마운트돼 닫혔다. 기존 테스트 "done 뒤 결과를 읽으면 결과 단계다" 의 `source.closed` 단언) |
| `loadResult` 실패 (`awaitedRun === id`) | `awaitedRun = null`, `runId = null`, `state = failed { error }` |
| `SecurityProgress` 의 `onMissing` (run 당 1회) | `run.missing && run.error !== null` 이면 위와 같은 가드로 `awaitedRun = null`, `runId = null`, `state = failed { error: run.error }` |
| `run.error` 가 있고 `missing` 이 아님 | `progressError = run.error`. 상태는 그대로(지금 "run 조회만 실패하면 진행 유지" 규칙) |
| 늦게 온 결과 (`awaitedRun !== id`) | 무시. 지금과 같다 |
| "← 서버 다시 고르기" `leaveRun()` | `reset()`: `awaitedRun = null`, `runId = null`, `state = idle`, `startError = null`. `sent` 는 그대로 |

`events` 는 `run.events`, `runId === null` 이면 `useRunEvents(null)` 이 빈 배열을 준다. 패널의 `starting`
("점검 중…" 글자와 버튼 비활성)은 훅 계약에 없으므로 패널의 로컬 `useState` 로 `await start()` 앞뒤에 둔다.
패널이 보이는 오류 문장은 `state.kind === "failed" ? state.error : startError` 다. 단계는
`state.kind === "done" ? 2 : runId !== null ? 1 : 0` 이다.

`use-security-analysis.ts` 의 구독부는 이 모양 그대로 쓴다(판단이 갈리는 가드라 코드로 고정한다):

```ts
const awaitedRun = useRef<string | null>(null);
/** 끝남·없음을 보고한 run. start 성공이 null 로 비운다(같은 runId 가 다시 와도 다시 보고하도록). */
const reportedRun = useRef<string | null>(null);
const run = useRunEvents(runId);
const finished = run.status === "done" || run.status === "failed";
const missingMessage = run.missing ? run.error : null;

useEffect(() => {
  if (runId === null || !finished || reportedRun.current === runId) return;
  reportedRun.current = runId;
  void loadResult(runId);
}, [runId, finished, loadResult]);

useEffect(() => {
  if (runId === null || missingMessage === null || reportedRun.current === runId) return;
  reportedRun.current = runId;
  awaitedRun.current = null;
  setRunId(null);
  setState({ kind: "failed", error: missingMessage });
}, [runId, missingMessage]);

const events = runId === null ? [] : run.events;
const progressError = run.missing ? null : run.error;
```

### 4.2 `build-analyze-requests.ts`

```ts
import type { AnalyzeSecurityRequest, AnalyzeTokensRequest, ServerCandidate } from "../../../src/api-types.js";
import { describeRun } from "../run-target.js";
import { buildSecurityRequest, type SecurityForm } from "./build-security-request.js";
import type { AnalyzeTarget } from "./use-analyze-target.js";

/**
 * 한 번에 분석의 두 요청. 버튼 비활성 판정·사유·제출이 같은 함수를 쓴다(기존 두 패널의 규율).
 * 대상 오류가 먼저다. 그 다음 buildSecurityRequest 가 던지는 문장이다. 토큰 요청은 던지지 않는다.
 */
export function buildAnalyzeRequests(
  target: AnalyzeTarget,
  form: SecurityForm,
):
  | { readonly tokens: AnalyzeTokensRequest; readonly security: AnalyzeSecurityRequest }
  | { readonly error: string };

/**
 * 카드의 "분석한 대상: <이름>". 성공한 요청에서 구한다(설계 §3.2). serverId 가 후보에 있으면 그 name,
 * 아니면 describeRun("audit", argv).server, 그것도 없으면 빈 문자열.
 */
export function describeTarget(
  candidates: readonly ServerCandidate[],
  request: { readonly argv: readonly string[]; readonly serverId?: string },
): string;
```

마크업 계약(테스트가 이것을 본다):

- 활성 카드: `<a role="tab" id={`pillar-${id}`} href={`#/analyze/${id}`} aria-selected={selected} aria-controls={`panel-${id}`}>`.
  `aria-controls` 가 가리키는 `panel-<id>` 는 상세가 열렸을 때만 존재한다(§4.3). 접근 가능한 이름이 축 이름으로
  **시작**하게 이름 요소를 DOM 에서 카드 맨 앞에 둔다(눈썹은 `aria-hidden` 이고 CSS `order` 로 위에 그린다.
  Tailwind `order-first`/`order-2`). 이름 요소는 `<span>` 이다. 제목 요소(`h1`~`h6`)를 쓰지 않는다. 상세 안의
  `getByRole("heading", { level: 3 })` 단언과 섞인다.
- 비활성 카드: `<div role="tab" id="pillar-performance" aria-disabled="true" aria-selected="false" tabindex="-1">`. 링크 없음.
  배경은 빗금이다. `style={{ backgroundImage: "repeating-linear-gradient(135deg, var(--line-subtle) 0 6px, transparent 6px 12px)" }}`
  (기존 토큰만 쓴다).
- 상태별 내용은 설계 §3.3. 글자는 정확히: idle `"아직 분석하지 않았습니다"`, running 배지 보안 `"점검 중…"`
  비용 `"분석 중…"`(U+2026), running 본문 `"진행은 상세에서 봅니다"`, failed 배지 `"실패"` 와 `firstLine(error)`
  와 요약 줄 `"전문은 상세에서 봅니다"`, 성능 `"—"`·`"아직 연결되지 않았습니다"`·`"패키지 개발 중"`·`"연결 예정"`·
  배지 `"준비 중"`, 활성 카드의 오른쪽 끝 `"상세 →"`.
- `done`: 배지 `summary.verdict.label`, 큰 숫자 `summary.headline`, 옆 `summary.headlineNote`, 막대
  `summary.bar`(보안은 칸 나열, 비용은 원본 100% 줄 + 압축 줄), 칩 `"<label> <count>"`(count 는 `<b>`),

  로 두고 `<p>{prefix + summary.foot}</p>` 로 그린다. 조각을 나누면 RTL 의 `getByText` 가 foot 만 담은 요소를 찾아

## 9. 통합 게이트 (오케스트레이터, 웨이브마다)

git 쓰기(커밋, 병합, 대장 커밋, 브랜치 삭제)는 **사람이** 한다. 오케스트레이터는 실행할 명령을 그대로 제시하고,
사람이 실행한 뒤 결과를 확인한다. worktree 생성만 실행 세션이 1단계에서 한다.

0. **선언.** 웨이브를 시작하기 전에 사용자에게 웨이브 번호, 태스크, 선행 태스크와 그 대장 SHA, 이 게이트의 통과
   조건을 한 번 선언한다.
1. **재검증.** 실행 세션의 보고를 받으면 그 worktree 에서 `git status --short`, `git diff --check` 를 보고, 해당
   태스크의 표적 검증과 회귀 검증 명령(§2.6·§3.4·§4.7·§5.4)을 오케스트레이터가 **다시 실행한다.**
2. **검토.** 보고서와 허용 Files 의 diff 를 직접 본다. 허용 밖 파일이 바뀌었으면 되돌리게 한다(4 의 수정 루프).
   보고서 파일(`docs/reports/…`)은 허용 Files 안이다. T2 는 `tests/` 와 `src/screens/` 변경이 0 이어야 한다.
3. **태스크별 확인.**
   - T1: `pillars.ts` 의 두 함수가 설계 §6 의 코드와 분기 수까지 같은지 눈으로 대조한다. 테스트 기대값이 구현
     출력을 복사해 넣은 것이 아닌지(`"가장 큰 감소: a −33.3%"`, `"~250 → ~190 토큰"`) 손으로 계산한다.
   - T2: `use-security-analysis.ts` 의 구독부가 §3.3 의 코드와 같은지 본다.
   - T3: 지운 테스트 이름이 §4.6.2·§4.6.4 의 "삭제" 행과 정확히 같은지 본다. "유지" 행의 테스트는 `git diff -M` 에서
     진입 helper 줄, `postedBodies` 호출 줄, 이름 줄, 비고가 적은 교체 줄 외에 바뀐 줄이 없는지 본다. "재작성" 행은
     §4.6.5 의 코드와 같은지 본다. 스크린샷을 연다. `grep -rn "SecurityPanel\|TokensPanel" packages/dashboard/web`
     가 비었는지 본다.
4. **수정 루프.** 1~3 에서 결함이 나오면 같은 실행 세션에 `SendMessage` 로 결함 목록, 고칠 파일, 다시 돌릴 검증
   명령을 보내 고치게 하고 1 로 돌아간다. 세 번 돌아도 남으면 사용자에게 보고하고 멈춘다.
5. **커밋.** 1~3 이 전부 통과하면 사람이 태스크 worktree 에서 허용 Files 만 `git add` 하고 아래 메시지로 커밋한다.
   - T1: `feat(dashboard): analyze 축 계약·라우트·요약 함수 추가`
   - T2: `refactor(dashboard): analyze 패널 로직을 훅으로 추출`
   - T3: `feat(dashboard): analyze 를 축 카드와 상세 화면으로 조립`
   - T4: `docs(dashboard): ADR-0116·색인·로드맵·changeset 추가`
6. **병합.** 사람이 프로젝트 루트에서 `git switch feat/analyze-pillars && git merge --no-ff feat/analyze-pillars-T<n>`
   를 실행한다. 그 뒤 루트에서 C2 를 돌린다. `--force` 와 `Cached: 0 cached` 를 확인한다.
7. **대장.** 병합 직후 `git rev-parse HEAD`(병합 커밋)를 `docs/task-integration-ledger.tsv` 에
   `analyze-T<n>`, SHA, 병합한 날짜(YYYY-MM-DD)를 탭으로 이은 한 행으로 더하고, 사람이 별도 문서 커밋으로 남긴다
   (`docs(dashboard): analyze-T<n> 통합 기록`). 태스크당 한 행이다. 수정 루프 뒤 다시 병합했으면 앞 행을 지우고 새
   행을 넣는다. 다음 프롬프트는 `awk … | tail -1` 로 마지막 행을 읽는다.

## 10. 자체 검토 (plan.md §6)

- 모든 요구사항이 정확히 한 태스크 또는 통합 게이트에 대응하는가: 설계 §1.3 의 완료 조건 여섯 줄은
  G1~G7 과 C2·C3 에, §3 의 화면은 T3 §4.3~4.5 에, §5·§6 은 T1·T2 에, §10 의 테스트는 T1 §2.5·T3 §4.6 에,
  §12 는 T4 에 대응한다. 사전 점검 import 는 T3 §4.1 에 있다.
- 공유 계약이 선행 태스크로 분리되고 병렬 태스크의 쓰기 파일이 겹치지 않는가: 계약(§5)은 T1·T2 가 먼저
  만든다. 병렬 태스크는 없다.
- 각 스폰에 모델과 추론 수준이 명시됐는가: §1 표와 §8 의 각 블록 첫 줄. 상위 모델은 오케스트레이터·T2·T3 이고 사유는
  §1 에 있다. 하위 모델에 설계 판단을 넘기지 않았다(설계 판단은 설계 개정 1 에서 끝냈다).
- 테스트가 격리된 자원만 쓰며 실환경 검증이 직렬로 분리됐는가: 유닛테스트는 인메모리·fetch fake·
  FakeEventSource 만. 실제 서버(`examples/live-weather-server`)는 C3 에서 사람이 한다.
- 구현 뒤 태스크 리뷰, 수정 루프, 최종 전체 리뷰 게이트가 있는가: §9 의 0~4, 9.
- 판단이 필요한 로직의 계약·픽스처·주요 단언이 생략되지 않았는가: 상태 전이(§3.3), 한 번에 분석(§4.3),
  처분 표(§4.6.2·§4.6.4), 새 테스트 전량(§2.5·§4.2·§4.6.3·§4.6.5).
- 모든 명령과 완료 조건이 실행·판정 가능한가: ADR 번호 명령은 `grep` 을 거친다. 기점은 실행자가 출력을
  적어 비교한다. 대장 SHA 는 `cat-file`·`merge-base` 로 확인한다.
