테스트를 고치지 않고는 통과시킬 수 없는 지점은 없었다. §3.3 이 명시한 두 변경(`start` 가 boolean 을 돌려주는 것,

통과하므로 구독은 하나다.

## 임의로 판단한 부분

1. **보안 `start` 실패 분기가 상태를 읽는 방법.** §3.3 은 "`state.kind === "done"` 이면 `startError` 만, 아니면 failed" 라고
   했지만 `useCallback` 안에서 최신 `state` 를 어떻게 읽는지는 적지 않았다. `state` 를 의존성에 넣으면 요청이 나가 있는
   동안 상태가 바뀌었을 때 낡은 클로저를 본다. 렌더마다 갱신하는 `latestState` ref 를 두어 실패 시점의 상태를 읽게 했다.
   `start` 자체는 의존성 없는 안정 함수다.
2. **두 훅의 `start`·`reset`·`reanalyze` 를 `useCallback` 으로 감쌈.** 계획은 `loadResult` 에만 요구했다. 나머지도 감싼 것은
   T3 이 훅의 함수를 effect 나 자식의 의존성으로 넘길 때 재생성으로 흔들리지 않게 하려는 것이다. `reanalyze` 의 의존성은
   `[analyzed, reanalyzing]` 이다(지금 패널의 가드와 같은 값을 읽는다).
3. **보안 `start` 가 `startError` 를 지우는 시점 (오케스트레이터 지시).** 지금 패널은 POST 를 보내기 **전에** `setError(null)`
   로 지우고 설계 §5.4 도 `startError` 를 "다음 start 가 비운다" 고 적었다. 처음 구현은 §3.3 표만 따라 성공 시점에 비웠는데,
   리뷰에서 행동 불변을 위해 **시작 시점에 비우도록** 지시받아 `start` 의 try 앞에 `setStartError(null)` 을 두었다. 성공·실패
   분기의 중복 비움은 지웠다. `failed` 상태의 문장(`state.error`)은 §3.3 표대로 결과가 올 때만 바뀐다(오케스트레이터 결정).
4. **점검 단계 분기의 조건.** 지금 `step === 1 && runId !== null && sent !== null` 을 `step === 1 && sent !== null` 로 줄였다.
   `step === 1` 이 곧 `runId !== null` 이기 때문이다. 결과 단계는 `state.kind === "done"` 을 조건에 넣어 `state.result` 의
   타입을 좁혔다.
5. **`SecurityProgress`(구독형)의 주석에 "Analyze 는 쓰지 않고 PreCheck 용" 한 줄을 더했다.** 왜 구독형과 그리기형이 둘 다
   있는지 다음 사람이 읽을 수 있게.
6. **`ErrorAlert` 의 주석을 새로 썼다.** 원본에는 주석이 없었다. 토큰·보안·PreCheck 가 같은 모양을 쓴다는 것을 적었다.

  §3.3 표를 따른 오케스트레이터 결정이며 테스트에는 걸리지 않는다.
