# 정상 입력도 분기를 밟는다

2026-09-13. 이슈 [#401](https://github.com/2026-Engineering-Contest/MCPeak/issues/401) 을 닫는다.

생성기는 한 툴에 **정상 입력을 하나만** 만든다. enum 은 첫 값, boolean 은 `true`, 객체는
required 필드만이다. 그래서 enum 의 두 번째 값에서만, `false` 에서만, 선택 필드가 있을 때만
나는 결함에는 **어떤 케이스도 도달하지 못한다.** 거절 케이스를 아무리 늘려도 이 빈틈은 안
줄어든다. 실행할 정상 입력 자체가 없기 때문이다.

- 검토 기준 커밋: `c0a1934fd2c1147556080d7f78f8b9e4b0a3f717`
- 같은 계열의 직전 회차: [범위 위반은 상한과 하한을 따로 검증한다](./2026-09-13-범위-위반은-상한과-하한을-따로-검증한다-설계.md)
  (상한 경계 정상 케이스를 더한 것이 이 문서가 말하는 "정상 분기" 의 첫 사례다)

## 1. 문제

`packages/generate/src/synthesize.ts` 의 `synthesizeValue` 는 결정론적으로 값 **하나**를
고른다. 그것이 이 함수의 일이고, 그 자체는 옳다.

```ts
else if (Array.isArray(schema.enum)) value = schema.enum[0] as JsonValue;
...
case "boolean":
  value = true;
  break;
...
case "object": {
  value = Object.fromEntries(required.map((key) => [key, synthesizeValue(...)]));
```

문제는 **그 하나만 실행한다**는 것이다. 세 군데서 분기가 조용히 잘린다.

| 자리 | 실행되는 것 | 실행되지 않는 것 |
|---|---|---|
| `enum: ["celsius", "fahrenheit", "kelvin"]` | `"celsius"` | `"fahrenheit"`, `"kelvin"` |
| `type: "boolean"` | `true` | `false` |
| `required: ["a"]`, `properties: { a, b }` | `{ a }` | `{ a, b }` |

`unit: "fahrenheit"` 일 때만 변환식이 틀린 서버, `verbose: false` 에서만 응답 필드가 빠지는
서버, 선택 필드 `limit` 를 받으면 터지는 서버를 전부 통과시킨다. 화면은 초록이다.

### 1.1 커버리지 숫자는 이 빈틈을 안 보여준다

`HAPPY_PATH` 축은 툴당 하나다. 정상 케이스 하나가 그것을 덮으면 `1/1` 이다. 정상 입력의
분기가 몇 개인지, 그중 몇 개를 실행했는지는 화면 어디에도 없다. **없는 줄은 사용자가 못
읽는다.**

## 2. 결정

정상 입력을 **한 축씩만 바꾼 변형 케이스**로 늘린다. 위반 케이스의 원칙과 같다. 한 케이스는
기준 정상 입력에서 정확히 한 필드, 한 분기만 다르다.

그렇게 해야 실패했을 때 어느 분기 때문인지 좁혀진다. 두 축을 한꺼번에 바꾸면 실패 메시지가
"이 입력이 실패했다" 밖에 말하지 못한다. 이 프로젝트에서 실패 메시지는 곧 제품이다.

### 2.1 케이스 예산: 축별 대표값을 고른다

이슈가 세 가지를 비교하라고 했다. 비교한 결과다.

| 방식 | 케이스 수 | 버린 이유 |
|---|---|---|
| 전조합 | 분기의 곱 | enum 3개 · boolean 2개 · 선택 필드 4개면 한 툴에 96건이다. 폭증한다 |
| 쌍별(pairwise) | 조합적으로 감소 | 실패했을 때 두 축이 동시에 다르므로 원인을 한 축으로 못 좁힌다. §2 의 원칙과 어긋난다 |
| **축별 대표값** | **분기의 합** | 채택 |

축별 대표값이면 케이스 수가 필드 수에 **선형**이다. 위반 케이스가 이미 그렇게 늘어나므로
같은 규모다. 전역 케이스 예산 상수를 따로 둘 필요가 없다.

남는 폭증 위험은 enum 하나다. 국가 코드 200개짜리 enum 이 흔하다. 여기만 규칙으로 자른다.

### 2.2 enum 은 두 번째 값과 마지막 값만 밟는다

기준 정상 입력이 `enum[0]` 을 쓴다. 여기에 더하는 것은 **두 개뿐**이다.

| enum 길이 | 더하는 값 |
|---|---|
| 1 | 없음 (기준 케이스가 유일한 값을 이미 밟았다) |
| 2 | `enum[1]` |
| 3 이상 | `enum[1]` 과 `enum[enum.length - 1]` |

임의의 상한이 아니라 **무엇을 잡으려는지에서 나온 규칙**이다. `enum[1]` 은 "첫 값만 처리하고
나머지는 안 본다" 를 잡고, 마지막 값은 "목록 끝에서 경계를 하나 빠뜨렸다" 를 잡는다. 가운데
값들은 그 둘이 잡는 결함 말고 새로 잡는 것이 없다.

`2` 나 `4` 같은 개수 상한을 쓰지 않는 이유가 이것이다. 개수는 근거가 없어 나중에 아무도 못
고친다. 이 규칙은 무엇을 노렸는지가 이름에 있다.

**밟지 않은 값은 반드시 화면에 적는다.** §5 를 본다.

### 2.3 boolean 은 `false` 하나

기준이 `true` 이므로 `false` 를 더한다. boolean 의 분기는 둘뿐이라 전수다.

### 2.4 선택 필드는 "있는" 쪽을 하나씩

기준 입력은 required 만 담는다. 선언된 선택 필드마다 **그 필드 하나만 채운 케이스**를 더한다.
값은 `synthesizeValue` 가 그 필드 스키마에서 만든 것이다.

선택 필드 전부를 한꺼번에 채운 케이스는 만들지 않는다. §2 의 한 축 원칙을 어기고, 실패했을 때
어느 선택 필드 때문인지 못 좁힌다.

선택 필드가 `enum` 이거나 `boolean` 이면 그 필드의 분기 변형은 만들지 않는다. "있음" 케이스가
`enum[0]` 또는 `true` 를 이미 싣고, 거기서 값을 또 바꾸면 두 축이 동시에 달라진다. 이 사실도
§5 의 미실행 목록에 적는다.

## 3. 무엇을 축으로 보는가

**최상위 필드만이다.** 중첩 객체 안의 enum·boolean·선택 필드는 이번 범위가 아니다
(이슈 #388 이 중첩을 맡는다). 중첩 분기가 있다는 사실은 §5 의 미실행 목록에 적는다.

축을 만들지 않는 것:

- `const` 가 선언된 필드. 분기가 없다
- `enum` 길이 1. 기준이 이미 밟았다
- 조합 키워드(`anyOf` · `oneOf` · `$ref`)가 든 필드. 갈래 선택 규칙이 `synthesizeBranches` 에
  따로 있고, 그것을 여기서 다시 해석하면 두 곳이 갈린다. 미실행 목록에 적는다
- `type` 이 해석되지 않는 필드

## 4. 생성 규칙

기준 정상 입력을 `happyInput` 이라 한다(`synthesizeValue` 의 결과, 지금과 같다).

변형 목록을 **결정론적 순서**로 만든다. 필드는 `properties` 의 선언 순서가 아니라 **UTF-16
코드 단위 오름차순**이다. 서버가 선언 순서를 바꾸는 것만으로 케이스 순서가 흔들리면 안 된다.
한 필드 안에서는 enum → boolean → 선택 필드 있음 순서다.

| 분기 | 조건 | id | name |
|---|---|---|---|
| enum 두 번째 | required 이고 `enum.length >= 2` | `${baseName}-branch-enum-${fieldSlug(field)}-2` | `${tool.name}가 '${field}' 의 다른 선언값에 정상 응답한다` |
| enum 마지막 | required 이고 `enum.length >= 3` | `${baseName}-branch-enum-${fieldSlug(field)}-last` | `${tool.name}가 '${field}' 의 마지막 선언값에 정상 응답한다` |
| boolean false | required 이고 `type === "boolean"` 이고 `happyInput[field] === true` | `${baseName}-branch-false-${fieldSlug(field)}` | `${tool.name}가 '${field}' 가 false 인 입력에 정상 응답한다` |
| 선택 필드 있음 | `properties` 에 있고 required 가 아님 | `${baseName}-branch-with-${fieldSlug(field)}` | `${tool.name}가 선택 필드 '${field}' 를 받아 정상 응답한다` |

전부 정상 케이스다. 단언은 기준 정상 케이스와 **같다.**

```
[{ type: "isError", expected: false }]
```

출력 계약이 지원되면 `structuredContentMatchesSchema` 를 잇는다. 여기서 단언을 약하게 두면
분기를 실행만 하고 결과를 안 보는 셈이 되어, 케이스 수만 늘고 잡는 결함은 안 는다.

### 4.1 값이 기준과 같아지면 만들지 않는다

`enum[1]` 이 `happyInput[field]` 와 같은 경우가 있다. 서버가 `enum: ["a", "a"]` 를 선언하거나,
`default` · `const` 가 기준 값을 `enum[0]` 아닌 것으로 바꿔 놓은 경우다. 값이 같으면 케이스를
만들지 않는다. 입력이 같은데 id 만 다른 케이스는 실행 시간만 쓰고 아무것도 새로 검증하지
않는다.

비교는 `canonicalJson` 으로 한다. `===` 는 배열·객체 enum 값에서 틀린다.

### 4.2 선택 필드 값을 못 만들면 건너뛴다

`synthesizeValue` 가 `UNSUPPORTED_SCHEMA` 로 던지는 선택 필드가 있다(순환 `$ref`, 미지원
키워드). 그때 툴 전체를 건너뛰면 안 된다. **기준 정상 케이스와 위반 케이스는 그 필드 없이도
멀쩡하다.** 그 변형 하나만 안 만들고 미실행 목록에 사유와 함께 적는다.

`GenerateTestsError` 만 삼킨다. 그 밖의 오류는 우리 결함이므로 그대로 올린다.

## 5. 밟지 않은 분기를 화면에 적는다

§2.2 · §3 · §4.1 · §4.2 가 전부 "만들지 않는다" 로 끝난다. **그 사실이 화면에 없으면 이
설계는 커버리지를 늘린 것이 아니라 숨긴 것을 옮긴 것뿐이다.**

`generate` 가 툴마다 미실행 분기 목록을 낸다. `render.ts` 의 `outputContractSkip` 과 같은
계열이고, 같은 자리에서 CLI 로 흘러간다.

```ts
export interface ValidBranchSkip {
  readonly tool: string;
  readonly field: string;
  /** 화면에 그대로 찍는 한 문장. 무엇을 안 밟았고 왜인지가 다 들어 있어야 한다. */
  readonly reason: string;
}
```

`reason` 문안을 표로 고정한다. 값이 흔들리면 지문이 흔들린다.

| 사유 | 문장 |
|---|---|
| enum 가운데 값 | `enum 값 ${total}개 중 ${executed}개만 실행했습니다. 첫 값·두 번째 값·마지막 값만 밟습니다.` |
| 조합 키워드 | `anyOf/oneOf/$ref 가 선언돼 있어 갈래별 정상 입력을 만들지 않았습니다.` |
| 중첩 분기 | `중첩 객체 안의 분기는 아직 생성하지 않습니다.` |
| 선택 필드가 enum·boolean | `선택 필드라 '있음' 케이스만 만들고 값 분기는 만들지 않았습니다.` |
| 값 합성 실패 | `선택 필드 값을 만들지 못했습니다: ${message}` |
| 변형 값이 기준과 같음 | `변형 값이 기준 정상 입력과 같아 케이스를 만들지 않았습니다.` |

CLI 화면은 커버리지 표 아래에 한 덩어리로 찍는다.

```
정상 분기: 툴 3개에서 5개 분기를 실행하지 않았습니다.
  convert_units.unit  enum 값 8개 중 3개만 실행했습니다. 첫 값·두 번째 값·마지막 값만 밟습니다.
  get_weather.filter  anyOf/oneOf/$ref 가 선언돼 있어 갈래별 정상 입력을 만들지 않았습니다.
```

미실행이 하나도 없으면 이 덩어리를 찍지 않는다. 빈 목록을 찍으면 화면만 길어진다.

## 5.5 AI 사전보완이 파생 케이스의 고정값을 덮어쓰면 안 된다

**이 절이 이번 작업에서 가장 조심할 곳이다.** 2026-09-13 에 이슈 #387 구현 중 발견했다.

`packages/generate/src/pre-fill.ts` 의 `isHappyPath` 는 `isError: false` 단언이 있는 케이스를
AI 사전보완 대상으로 고른다. §4 가 만드는 케이스는 **전부 그 조건에 걸린다.**

그리고 채택 규칙은 `baseline 실패 · AI 통과 → AI 채택` 이다. 두 사실을 합치면 이렇게 된다.

| 상황 | 결과 |
|---|---|
| enum 두 번째 값 `"fahrenheit"` 에서만 서버가 틀렸다 | 그 케이스가 실패한다 |
| AI 가 그 케이스의 `unit` 에 `"celsius"` 를 제안한다 | 통과한다 |
| 채택 규칙이 작동한다 | **`"fahrenheit"` 가 `"celsius"` 로 바뀐다** |

우리가 방금 만든 케이스가, 그 케이스가 잡으려던 결함을 지우는 데 쓰인다. 그리고 그 결과는
기준 정상 케이스와 입력이 같은 중복 케이스다. 화면은 초록이다.

이슈 #387 의 상한 경계 정상 케이스도 같은 자리에 있다. 상한에 off-by-one 이 있는 서버에서
`n: 10` 이 실패하면 사전보완이 그 값을 바꾼다.

### 5.5.1 결정: 파생 케이스는 고정 필드를 선언하고, 그 필드의 제안은 버린다

파생 케이스를 사전보완에서 통째로 빼는 대안은 버린다. 뺐다가는 기준 케이스가 `city: "Seoul"`
을 받아 통과할 때 파생 케이스만 `city: "example"` 로 남아 **엉뚱한 이유로 실패한다.** 그러면
사용자는 enum 분기 결함이 아니라 도시 이름 문제를 보게 된다.

케이스가 **자기 정체성을 이루는 필드**를 선언하고, 사전보완이 그 필드의 제안만 버린다.

```ts
export interface GeneratedCase {
  // ... 기존 필드 그대로
  /**
   * 이 케이스를 이 케이스이게 하는 필드. 값이 바뀌면 케이스의 목적이 사라진다.
   *
   * AI 사전보완은 이 필드의 제안을 버린다. `unit` 을 `"fahrenheit"` 로 고정한 케이스에
   * `"celsius"` 를 넣으면 기준 케이스와 같아지고, 그 케이스가 잡으려던 결함이 사라진다.
   * 나머지 필드는 정상적으로 제안을 받는다. `city` 같은 근거 없는 값은 채워져야 한다.
   *
   * 기준 정상 케이스와 위반 케이스는 빈 배열이다.
   */
  readonly pinnedFields: readonly string[];
}
```

| 케이스 | `pinnedFields` |
|---|---|
| 기준 정상 | `[]` |
| enum 두 번째·마지막 | `[field]` |
| boolean false | `[field]` |
| 선택 필드 있음 | `[field]` |
| 상한 경계 정상(#387) | `[field]` |
| 위반 케이스 전부 | `[]` (사전보완이 애초에 안 고른다) |

### 5.5.2 버린 제안을 숨기지 않는다

`pre-fill.ts` 에 `PreFillDiscard` 가 이미 있다. 그것을 쓴다. 새 통로를 만들지 않는다.

버린 제안은 화면에 한 줄 남긴다.

```
  제안 1건을 버렸습니다: convert_units-branch-enum-unit-2 의 'unit'
    이 케이스는 'unit' 을 "fahrenheit" 로 고정해 분기를 검증합니다. 값을 바꾸면 검증이 사라집니다.
```

조용히 버리면 사용자는 AI 가 제안을 안 한 줄 안다. 그리고 그 케이스가 왜 계속 실패하는지
모른 채 값을 손으로 고치려 든다.

### 5.5.3 완료 조건

- enum 두 번째 값 케이스에 그 enum 필드 제안이 오면 버려지고, 같은 케이스의 다른 필드
  제안은 채택된다
- 버린 제안이 `PreFillDiscard` 에 사유와 함께 들어가고 화면에 찍힌다
- `pinnedFields` 가 빈 기준 정상 케이스는 종전대로 모든 필드의 제안을 받는다
- 상한 경계 정상 케이스(#387)의 경계 필드 제안도 같은 규칙으로 버려진다

## 6. 커버리지 축은 늘리지 않는다

`ContractAxisKind` 에 `VALID_BRANCH` 를 더하는 대안이 있었다. 버린다.

축은 **서버 선언에서 도출되는 거절 계약**이다(`contract-axes.ts` 의 주석). "enum 의 두 번째
값에 정상 응답한다" 는 거절 계약이 아니라 정상 동작이고, 그것은 `HAPPY_PATH` 축의 일이다.
여기에 축을 더하면 `HAPPY_PATH` 와 의미가 겹쳐 분모가 무엇을 세는 숫자인지 흐려진다.

정상 분기의 실행 여부는 §5 의 목록이 말한다. 숫자와 목록을 다른 줄에 두고, 커버리지 분모는
지금 의미를 유지한다.

## 7. 완료 조건

전부 실행으로 판정한다.

1. `unit: { enum: ["celsius", "fahrenheit", "kelvin"] }` 에서 정상 케이스의 `unit` 값이
   `"celsius"` · `"fahrenheit"` · `"kelvin"` 세 개다.
2. `enum[1]` 에서만 틀린 답을 내는 목 서버가 생성 스위트에서 **실패한다.**
3. `verbose: { type: "boolean" }` 이 `false` 일 때만 응답 필드가 빠지는 목 서버가 **실패한다.**
4. 선택 필드 `limit` 를 받으면 오류를 내는 목 서버가 **실패한다.**
5. enum 값 8개짜리 필드에서 케이스가 3개(기준 + 2개)이고, 화면에 `enum 값 8개 중 3개만
   실행했습니다` 가 찍힌다.
6. 미실행 분기가 없는 툴에서는 `정상 분기:` 덩어리가 아예 안 찍힌다.
7. 같은 입력으로 두 번 생성한 결과가 바이트 단위로 같다.
8. 필드 선언 순서를 뒤집은 같은 스키마가 같은 케이스 배열을 낸다.

## 8. 비범위

- 중첩 객체·배열 원소 안의 분기(이슈 #388).
- `anyOf` · `oneOf` 갈래별 정상 입력. §3 에 사유를 적었고 §5 가 화면에 표시한다.
- 선택 필드 조합(둘 이상을 함께 채운 케이스). §2.4 에 사유를 적었다.
- 실재하는 값이 필요한 필드(이슈 #390 이 맡는다). 이 설계는 스키마에서 값을 만든다.
