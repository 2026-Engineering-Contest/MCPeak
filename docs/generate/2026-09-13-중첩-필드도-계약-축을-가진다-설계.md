# 중첩 필드도 계약 축을 가진다

2026-09-13. 이슈 [#388](https://github.com/2026-Engineering-Contest/MCPeak/issues/388) 을 닫는다.

`user.name` 을 필수 문자열로 선언해도 우리는 **최상위 `user` 만 본다.** 서버에서 내부 `name`
검사를 통째로 제거해도 생성 스위트 12건이 전부 통과한다. 실행으로 재현했다.

- 검토 기준 커밋: `c0a1934fd2c1147556080d7f78f8b9e4b0a3f717`
- 같은 계열의 직전 회차:
  [범위 위반은 상한과 하한을 따로 검증한다](./2026-09-13-범위-위반은-상한과-하한을-따로-검증한다-설계.md)

## 1. 문제

`packages/runner/src/input-schema.ts` 의 `NormalizedInputSchema` 는 **평면**이다.

```ts
export interface NormalizedInputSchema {
  readonly fields: ReadonlyMap<string, NormalizedField>;
  readonly required: readonly string[];
  readonly rejectsUndeclared: boolean;
}
```

`fields` 의 키는 최상위 프로퍼티 이름 하나다. `user: { type: "object", properties: { name: ... } }`
를 읽으면 `user` 항목 하나가 생기고 `type: "object"` 만 남는다. **`name` 은 그 자리에서
사라진다.** 축도 케이스도 거기서 끝난다.

생성기가 만드는 것은 세 개뿐이다.

| 케이스 | 입력 |
|---|---|
| 정상 | `{ user: { name: "example" } }` |
| 부모 누락 | `{}` |
| 부모 타입 위반 | `{ user: "example" }` |

내부 `name` 검사를 뺀 서버는 셋 다 통과한다. 수동으로 `{ user: {} }` 를 넣으면 잡힌다.
**만들 수 있는 케이스인데 안 만들고 있는 것이다.**

### 1.1 배열 원소도 같다

`tags: { type: "array", items: { type: "string", minLength: 3 } }` 에서 `items` 의 제약은
어떤 축도 만들지 않는다. 원소 하나가 계약을 어긴 입력을 아무도 보내지 않는다.

### 1.2 커버리지가 이 빈틈을 안 센다

`user` 는 `REQUIRED_OMITTED` 축 하나와 `TYPE_VIOLATION` 축 하나를 만들고 둘 다 덮인다.
분모에 `user.name` 이 없으므로 화면은 `2/2` 다. **없는 축은 안 세어지고, 안 세어지는 것은
사용자가 못 읽는다.**

## 2. 결정

**필드 키를 이름에서 경로로 바꾼다.** `NormalizedInputSchema.fields` 를 트리로 만들지 않고
평면을 유지하되, 키가 `user.name` 같은 경로가 된다.

트리로 바꾸지 않는 이유: `ContractAxis.field` 가 `string | null` 이고 `generate` ·
`cli` · `coverage` 가 전부 그것을 문자열로 다룬다. 트리로 바꾸면 축 모델과 커버리지 키와
화면 문안이 동시에 흔들린다. 경로 문자열이면 **축 모델이 한 글자도 안 바뀐다.** `field` 에
들어가는 값의 모양만 넓어진다.

`RANGE_VIOLATION` 축을 `bound` 로 나눈 직전 회차와 같은 판단이다. 정체성을 넓히되 종류는
늘리지 않는다.

### 2.1 경로 문법

| 형태 | 뜻 |
|---|---|
| `user` | 최상위 프로퍼티 |
| `user.name` | 객체 안의 프로퍼티 |
| `tags[]` | 배열의 원소 (모든 원소가 같은 `items` 스키마를 공유한다) |
| `tags[].id` | 배열 원소가 객체일 때 그 안의 프로퍼티 |

**충돌 처리.** 서버가 `"user.name"` 이라는 이름의 최상위 프로퍼티를 선언할 수 있다. JSON
Schema 가 막지 않는다. 그러면 `user` 객체의 `name` 과 경로 문자열이 같아진다.

충돌하면 **그 필드 전부를 해석에서 뺀다.** 경로를 escape 하지 않는다.

- escape 규칙을 넣으면 화면 문안과 커버리지 키와 생성 케이스 이름 세 곳이 동시에 그 규칙을
  알아야 하고, 한 곳만 어긋나면 조용히 다른 필드를 가리킨다
- 점이나 대괄호가 든 프로퍼티 이름은 실제 MCP 서버에서 드물다
- 뺀 필드는 `unanalyzedFields` 에 들어가 화면에 찍힌다. 숨기지 않는다

판정은 **경로 집합 전체를 만든 뒤** 중복이 있는지 보는 것으로 한다. 이름만 보고 미리
거르지 않는다. `"a.b"` 라는 최상위 필드가 있어도 `a` 라는 객체 필드가 없으면 충돌이 아니다.

### 2.2 깊이와 개수 상한

무한 재귀와 폭증을 막는다.

| 상한 | 값 | 근거 |
|---|---|---|
| 최대 깊이 | `3` | `user.address.city` 까지다. 실제 MCP 도구 스키마에서 그보다 깊은 필수 경로는 관측된 적이 없고, 깊어질수록 "이 경로가 왜 실패했는지" 를 사람이 읽기 어려워진다 |
| 툴당 최대 경로 수 | `64` | 위반 케이스가 경로마다 최대 4개(required·type·enum·range) 나므로 툴 하나가 256 케이스를 넘지 않게 묶는다 |

`$ref` 순환은 깊이 상한이 이미 끊는다. 그래도 `active` 집합으로 방문 중인 대상을 따로
막는다. 깊이 상한에만 기대면 순환이 상한까지 케이스를 만들어 내고, 그 케이스들은 서로 같은
것을 검증한다.

**상한에 걸려 뺀 경로는 `unanalyzedFields` 에 넣는다.** 조용히 사라지면 §1.2 의 문제를
그대로 반복한다.

## 3. 어디까지 내려가는가

내려가는 것:

- `type: "object"` 이고 `properties` 가 객체인 필드
- `type: "array"` 이고 `items` 가 객체인 필드

내려가지 않고 그 자리에서 멈추는 것(전부 `unanalyzedFields` 행):

- 차단 키워드(`anyOf` · `oneOf` · `allOf` · `not` · `$ref`)가 든 필드. nullable 형태만 기존
  `resolveNullableField` 로 풀고, 푼 결과에 대해 다시 이 규칙을 적용한다
- `properties` 가 없는 객체. 안에 무엇이 있는지 선언이 말하지 않는다
- `items` 가 배열인 튜플 형태. 원소마다 스키마가 달라 `tags[]` 하나로 못 묶는다
- 깊이·개수 상한 초과

## 4. 축과 케이스

경로마다 기존 네 축을 **그대로** 만든다. 새 `ContractAxisKind` 는 없다.

| 축 | 조건 |
|---|---|
| `REQUIRED_OMITTED` | 그 경로가 부모의 `required` 에 있다 |
| `TYPE_VIOLATION` | 그 경로에 `type` 이 선언돼 있다 |
| `ENUM_VIOLATION` | 그 경로에 `enum` 이 선언돼 있다 |
| `RANGE_VIOLATION` | 그 경로에 범위가 있고 enum 이 없다. `bound` 별로 나뉜다 |

**배열 원소의 `REQUIRED_OMITTED` 는 만들지 않는다.** `tags[]` 는 부모 배열의 `required` 에
들어갈 수 없다. 원소가 없는 것은 `minItems` 위반이고 그것은 이미 `tags` 의
`RANGE_VIOLATION` 축이다.

### 4.1 한 케이스는 한 경로만 어긴다

기준 정상 입력에서 **그 경로의 값 하나만** 바꾼다. 나머지는 전부 정상값이다. 부모도 정상
객체여야 한다. 위반 케이스의 기존 원칙과 같고, 실패했을 때 어느 경로 때문인지 좁히려면
이것이 유일한 방법이다.

`user.name` 의 타입 위반은 이렇다.

```json
{ "user": { "name": 0 } }
```

`{ "user": 0 }` 이 아니다. 그것은 `user` 의 타입 위반이고 이미 다른 케이스다.

`REQUIRED_OMITTED` 는 그 키만 지운다.

```json
{ "user": {} }
```

배열 원소는 **첫 원소만** 바꾼다. 원소가 여럿이면 나머지는 정상값 그대로다. 전부 바꾸면
"서버가 첫 원소만 검사한다" 는 결함을 못 잡는다.

```json
{ "tags": ["ab", "example"] }
```

정상 입력의 배열이 비어 있으면(`maxItems: 0`) 그 경로의 축을 만들지 않는다. 바꿀 원소가 없다.

### 4.2 케이스 id 와 이름

경로를 `fieldSlug` 로 파일명 안전 문자열로 만든다. `.` 과 `[]` 가 슬러그에서 어떻게 되는지는
**`fieldSlug` 의 기존 규칙을 따르고, 서로 다른 경로가 같은 슬러그가 되면** 기존 `uniqueId`
의 `-2` 접미사 규칙이 받는다.

이름에는 슬러그가 아니라 **경로 원문**을 넣는다. 사용자가 자기 스키마에서 찾아야 하는 것은
슬러그가 아니라 경로다.

```
get_user가 필수 필드 'user.name' 누락을 거절한다
get_user가 'user.name' 타입 위반을 거절한다
add_tags가 'tags[]' 의 선언되지 않은 값을 거절한다
```

### 4.3 `UNDECLARED_FIELD` 는 최상위만

`additionalProperties: false` 가 중첩 객체에도 선언될 수 있다. 그래도 이번에는 최상위 축
하나를 유지한다. 축이 `field: null` 로 정의돼 있고(선언 밖 키가 여럿이어도 축은 하나다),
중첩까지 넓히면 그 정의를 바꿔야 한다. 중첩 `additionalProperties: false` 가 있으면
`unanalyzedFields` 가 아니라 **별도 고지 한 줄**로 알린다. 해석 실패가 아니라 미지원이다.

## 5. 미지원을 분모에서 숨기지 않는다

이슈가 요구한 항목이다. `unanalyzedFields` 는 이미 화면에 찍히고 있으므로 **거기에 경로를
넣으면 끝난다.** 새 화면을 만들지 않는다.

들어가는 값은 경로 원문이다(`user.profile`, `tags[]`). 코드 단위 오름차순 정렬은 기존 규칙
그대로다.

사유별 문안은 `cli` 가 붙인다. 경로만으로는 왜 못 읽었는지 모르므로, `unanalyzedFields` 를
경로와 사유의 쌍으로 넓힌다.

```ts
export interface UnanalyzedField {
  /** 경로 원문. user.profile, tags[] 처럼 §2.1 문법이다. */
  readonly path: string;
  readonly reason:
    | "blockingKeyword"   // anyOf/oneOf/allOf/not/$ref
    | "noProperties"      // properties 없는 object
    | "tupleItems"        // items 가 배열
    | "depthLimit"        // 깊이 3 초과
    | "pathLimit"         // 툴당 64 경로 초과
    | "pathCollision"     // 경로 문자열이 다른 필드와 충돌
    | "unknown";          // 그 밖
}
```

**이것이 이번 작업에서 가장 조심할 변경이다.** `unanalyzedFields` 는 지금
`readonly string[]` 이고 `generate` 와 `cli` 가 둘 다 읽는다. 타입이 바뀌므로 세 패키지가
순차로 따라와야 한다.

## 6. 완료 조건

전부 실행으로 판정한다.

1. `user: { type: "object", properties: { name: { type: "string" } }, required: ["name"] }` 에서
   생성 케이스에 `{ user: {} }` 와 `{ user: { name: 0 } }` 가 둘 다 있다.
2. 내부 `name` 필수 검사만 제거한 목 서버가 생성 스위트에서 **실패한다.**
3. 내부 `name` 타입 검사만 제거한 목 서버가 **실패한다.**
4. `tags: { type: "array", items: { type: "string", minLength: 3 } }` 에서 원소 하나만
   짧은 케이스가 있고, 원소 검사를 제거한 서버가 **실패한다.**
5. 커버리지 분모에 `user.name` 축이 들어간다.
6. 깊이 4 짜리 스키마에서 4단계 경로가 `unanalyzedFields` 에 `depthLimit` 으로 들어간다.
7. `"user.name"` 이라는 이름의 최상위 필드와 `user.name` 경로가 함께 있으면 둘 다
   `pathCollision` 으로 빠지고, 화면에 그 사실이 찍힌다.
8. 같은 입력으로 두 번 생성한 결과가 바이트 단위로 같다.

## 7. 비범위

- 중첩 `additionalProperties: false`. §4.3 에 사유를 적었다.
- 튜플 형태 `items`. §3 에 적었다.
- 중첩 경로의 정상 분기(enum 두 번째 값 등). 이슈 #401 이 최상위만 맡기로 했고, 중첩은
  그 뒤의 일이다.
- `patternProperties` · `propertyNames`. 지금도 해석 대상이 아니다.
