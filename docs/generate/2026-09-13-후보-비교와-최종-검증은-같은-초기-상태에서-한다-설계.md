# 후보 비교와 최종 검증은 같은 초기 상태에서 한다

2026-09-13. 이슈 [#399](https://github.com/2026-Engineering-Contest/MCPeak/issues/399) 을 닫는다.
이슈 #398(사전보완 비교)을 여기에 통합한다.

`generate` 는 명세를 저장하기 전에 "이 명세는 실제 서버에서 통과한다" 고 화면에 말한다.
**그 판정의 근거가 두 군데서 샌다.** 둘 다 상태 의존 도구에서만 드러난다.

- 검토 기준 커밋: `c0a1934fd2c1147556080d7f78f8b9e4b0a3f717`
- 초기화 명령 원본 결정: ADR-0023 (`--reset-cmd`)
- 유지해야 할 경계: 이슈 #397 (`--no-dry-run` 과 취소에서 실제 호출을 막는다)

## 1. 문제

### 1.1 사전보완 비교에 초기 상태가 없다

`packages/cli/src/pre-fill-wiring.ts` 다.

```ts
const baselineRun = await run({ client, suite: subsetSuite(baseline, targetIds) });
const aiRun = await run({ client, suite: subsetSuite(baseline, targetIds, aiInputs) });
```

같은 연결에서 연달아 돈다. **둘 사이에 초기화가 없고, 첫 번째 실행 앞에도 없다.**

`create_note` 처럼 상태를 바꾸는 도구를 생각하면 결과가 뒤집힌다.

| 회차 | 입력 | 결과 | 왜 |
|---|---|---|---|
| baseline | `{ title: "example" }` | 실패 | 아직 노트가 없어 참조 무결성 오류 |
| AI | `{ title: "회의록" }` | 통과 | **baseline 실행이 노트를 하나 만들어 놨다** |

채택 규칙은 `baseline 실패 · AI 통과 → AI 채택` 이다. 그래서 **입력값이 좋아서가 아니라
앞 실행이 상태를 바꿔서** AI 값이 채택된다. 사용자에게는 "AI 가 더 나은 값을 찾았다" 로
보인다. 다음에 깨끗한 서버에서 돌리면 그 값도 실패한다.

### 1.2 최종 명세를 처음부터 실행한 적이 없다

입력값 교정(`generate-command.ts` 의 `rerun`)은 **케이스 하나만 담은 스위트**로 재실행한다.

```ts
// 케이스 하나만 담은 스위트로 부른다. 전량을 다시 돌리면 앞서 통과한 케이스가
// 상태 변화로 뒤집힌다(설계 §9).
```

주석의 판단은 그 자리에서는 옳다. 교정 중에 전량을 돌리면 앞 케이스가 뒤집힌다. **문제는
그 뒤다.** 저장할 때 원래 실행 결과와 교정된 케이스의 단독 통과를 **합친다.** 그렇게 합친
결과가 "이 명세 전체가 통과한다" 로 화면에 나간다.

합집합은 실행이 아니다. 케이스 A 가 통과하고 케이스 B 가 단독으로 통과해도, A 다음에 B 를
돌리면 B 가 실패할 수 있다. 그 사실은 **저장 후 사용자가 처음 `mcpeak test` 를 돌릴 때**
드러난다. 우리 도구가 초록이라고 한 명세가 그 사용자의 첫 실행에서 빨강이다.

### 1.3 `--reset-cmd` 성공을 상태 복구로 읽는다

`runResetCommand` 는 명령의 종료 코드만 본다. 그것이 복구한 범위는 아무도 모른다.

| 상태 | `--reset-cmd "rm -rf ./data"` 가 되돌리는가 |
|---|---|
| 디스크 파일 | 그렇다 |
| 서버 프로세스의 메모리 캐시 | **아니다.** 프로세스가 계속 살아 있다 |
| 외부 DB | 명령에 달렸다. 우리는 모른다 |
| 열려 있는 MCP 세션 | **아니다.** 같은 연결을 계속 쓴다 |

명령이 0 으로 끝났다고 초기 상태라고 말하면 안 된다.

## 2. 결정

**"검증했다" 를 세 단계로 나누고, 각 단계가 실제로 무엇을 보장하는지 화면에 그대로 적는다.**

전량 재검증을 붙이는 것만으로는 §1.1 이 안 닫힌다. 두 실행 경로를 각각 고친다.

| 고치는 것 | 닫는 문제 |
|---|---|
| 사전보완 비교 앞과 사이에 초기화를 넣는다 | §1.1 |
| 최종 명세를 처음부터 전량 재실행한다 | §1.2 |
| 초기화가 복원하는 범위를 등급으로 표시한다 | §1.3 |

### 2.1 초기화 등급

`--reset-cmd` 성공을 "초기 상태" 라고 부르지 않는다. 무엇을 했는지만 말한다.

```ts
export type ResetGrade =
  /** 새 프로세스·새 연결 + 초기화 명령 성공. 우리가 제공할 수 있는 가장 강한 것. */
  | "freshProcess"
  /** 같은 연결에 초기화 명령만 성공. 프로세스 메모리는 그대로다. */
  | "commandOnly"
  /** 초기화 수단이 없다. 앞 실행의 상태가 그대로 남아 있다. */
  | "none"
  /** 초기화를 시도했으나 실패했다. 상태를 모른다. */
  | "failed";
```

화면 문안을 표로 고정한다. 값이 흔들리면 지문이 흔들린다.

| 등급 | 문장 |
|---|---|
| `freshProcess` | `초기 상태: 서버를 다시 띄우고 초기화 명령을 실행했습니다.` |
| `commandOnly` | `초기 상태: 초기화 명령만 실행했습니다. 서버 프로세스의 메모리 상태는 그대로입니다.` |
| `none` | `초기 상태: 초기화 수단이 없습니다. 앞 실행이 바꾼 상태가 남아 있을 수 있습니다. --reset-cmd 로 지정하세요.` |
| `failed` | `초기 상태: 초기화 명령이 실패했습니다. 이 실행의 결과를 검증 완료로 보지 않습니다.` |

`none` 과 `failed` 를 가르는 이유: 하나는 **사용자가 아직 안 준 것**이고 다른 하나는
**주었는데 안 된 것**이다. 다음에 할 일이 다르다.

### 2.2 최종 재검증

입력값 교정이 끝난 뒤, 저장 직전에 **최종 명세 전량**을 한 번 더 돌린다.

```
초기화 → 최종 suite 전량 실행 → 그 결과를 저장 판정에 쓴다
```

합집합을 쓰지 않는다. 이 실행의 결과가 곧 판정이다.

**케이스 사이에는 초기화하지 않는다.** 이슈의 마지막 체크 항목이다. 스위트 안의 케이스
순서는 의미가 있다(앞 케이스가 만든 것을 뒤 케이스가 읽는 명세를 사람이 쓸 수 있다).
매 케이스마다 초기화하면 그 의미가 사라지고, 우리가 검증한 것이 사용자가 나중에 실행할 것과
달라진다. 초기화는 **스위트 경계**에서만 한다.

### 2.3 재검증이 부작용을 만들 때

전량 재실행은 실제 호출이다. 메일을 보내는 도구, 결제를 만드는 도구가 한 번 더 실행된다.

**자동으로 반복하지 않는다.** 명시적으로 묻는다.

```
최종 명세를 처음부터 다시 실행해 검증합니다.
  초기 상태: 초기화 명령만 실행했습니다. 서버 프로세스의 메모리 상태는 그대로입니다.
  실행할 케이스: 12건 (실제 서버 호출입니다)
계속할까요?
```

거절하면 **저장을 막지 않는다.** 대신 검증 범위를 사실대로 적는다. 사용자가 부작용을 알고
거절한 것을 우리가 저장 실패로 바꿀 이유가 없다.

```
최종 전량 재검증을 하지 않았습니다. 개별 케이스 통과 기록만 있습니다.
저장 후 `mcpeak test` 로 전체를 한 번 실행해 확인하세요.
```

`--yes` 로 돌면 묻지 않고 재검증한다. 비대화형에서는 묻지 않고 **건너뛴 뒤 위 문장을 찍는다.**
물어볼 수 없는 곳에서 실제 호출을 조용히 늘리지 않는다. #397 의 경계와 같은 규칙이다.

### 2.4 검증 범위는 화면에 적는다. 명세 파일에는 넣지 않는다

처음에는 `approval.cases` 에 `CaseVerification` 을 싣기로 했다. **2026-09-13 실측으로 뺐다.**

`packages/runner/src/spec/validation.ts:578` 이 이렇다.

```ts
unknowns(entry, ["id", "status"], path, issues);
```

`approval.cases[]` 에 키를 더하면 `validateMcpSuite` 가 `UNKNOWN_FIELD` 로 명세를 거절한다.
같은 파일 623행이 `approval` 자신도 `["fingerprint", "cases"]` 로 막는다. 이슈 #401 이
`GeneratedCase.pinnedFields` 로 정확히 같은 자리를 밟았다.

그래서 싣자면 `runner` 의 명세 형식을 넓혀야 한다. **그건 이 이슈의 범위가 아니다.**

- 저장 형식은 다섯 명이 함께 보는 계약이고, **표시용 사실 하나** 때문에 넓힐 것이 아니다
- 넓히면 모든 저장 명세가 그 키를 이고 다니고 `runner` 가 그 값을 검증해야 한다
- 이슈 #399 의 체크 항목이 **"`approval.cases`나 화면에 검증 범위를 사실대로 표시한다"** 로
  적혀 있다. 둘 중 하나면 된다

화면에 적는다. 저장 직전 요약에 한 줄이다.

```
  검증 범위: 12건을 최종 전량 실행에서 확인했습니다.
```
```
  검증 범위: 3건은 개별 실행에서만 확인했습니다. 전량 재검증을 하지 않았습니다.
  저장 후 `mcpeak test` 로 전체를 한 번 실행해 확인하세요.
```

`CaseVerification` 타입은 **메모리 안에서만 산다.** 어느 케이스가 어느 실행에서 통과했는지
세는 데 쓰고, 세고 나면 화면 문장이 된다. 파일에 안 간다.

```ts
/** 이 케이스의 통과가 어떤 실행에서 나왔는가. 화면 문장을 만드는 데만 쓴다(이슈 #399). */
export type CaseVerification =
  /** 최종 전량 재실행에서 통과했다. 가장 강한 근거다. */
  | "fullSuite"
  /** 케이스 하나만 담은 스위트에서 통과했다. 앞 케이스와의 상호작용은 안 봤다. */
  | "isolated";
```

`stale` 은 뺐다. 명세가 바뀌었는지는 `approval.fingerprint` 가 이미 판정하고 화면이 그것을
따로 말한다. 같은 사실을 두 곳에서 세지 않는다.

**한계를 그대로 적는다.** 화면은 스크롤되면 사라진다. 저장된 명세만 보는 사람은 그 실행이
전량 재검증을 거쳤는지 알 수 없다. 그 사실이 필요해지면 그때 `runner` 형식을 넓히는 별도
작업으로 한다. 지금 넓히는 것은 근거가 약하다.

## 3. 무엇을 안 하는가

**`freshProcess` 등급을 이번에 만들지 않는다.** 서버 프로세스를 다시 띄우고 재연결하는 것은
`core` 의 수명주기를 건드리는 작업이고, `generate` 흐름 한가운데서 연결을 바꾸면 그 뒤의
모든 단계가 새 client 를 봐야 한다. 이번에는 **등급 값만 정의하고 `commandOnly` 까지 낸다.**

등급을 미리 정의하는 이유: `commandOnly` 를 "초기 상태" 라고 부르지 않으려면 그보다 강한
것이 있다는 사실이 타입에 있어야 한다. 나중에 붙일 때 화면 문안이 이미 자리를 잡고 있다.

`ResetGrade` 에 `freshProcess` 가 있는데 코드가 그것을 안 내는 것은 **의도된 상태**다.
주석에 그렇게 적는다. 안 적으면 다음 사람이 죽은 값으로 읽고 지운다.

## 4. 순서

```
1. 초기화                  (등급 판정)
2. baseline 후보 실행
3. 초기화                  (등급 판정. 2번이 바꾼 상태를 되돌린다)
4. AI 후보 실행
5. 채택 판정               ← 두 실행이 같은 초기 상태에서 나왔을 때만 신뢰한다
...
6. 초기화
7. 시험 실행 (전량)
8. 입력값 교정             (케이스 단독 재실행. 기존 그대로)
9. 초기화
10. 최종 전량 재검증        ← 저장 판정은 이것이다
11. 저장
```

3번을 못 하면(등급 `none` 또는 `failed`) **채택 판정을 하지 않는다.** 전부 baseline 을
유지하고 화면에 사유를 적는다.

```
사전보완 비교를 건너뜁니다: 두 후보를 같은 초기 상태에서 실행할 수 없습니다.
  초기 상태: 초기화 수단이 없습니다. ... --reset-cmd 로 지정하세요.
  baseline 값을 그대로 유지합니다.
```

이것이 이 설계에서 **가장 중요한 판단**이다. 기존 동작은 "비교해서 더 나은 것을 고른다" 인데,
비교 조건이 안 갖춰졌으면 **고르지 않는 것이 옳다.** 상태 차이를 입력 개선으로 오인해 채택한
값은 재현되지 않는 명세를 만들고, 그것은 이 프로젝트의 핵심 가치인 결정론성을 정면으로
어긴다. 아무것도 안 하는 쪽이 틀린 것을 채택하는 쪽보다 낫다.

10번을 못 하면 §2.3 대로 저장은 하되 범위를 적는다. 채택과 다르다. 채택은 **명세의 내용을
바꾸는 것**이고 최종 검증은 **이미 정해진 명세를 확인하는 것**이다. 확인을 못 했다고 내용을
버릴 이유는 없다.

## 5. #397 의 경계를 유지한다

- `--no-dry-run` 이면 1~10번을 **하나도 하지 않는다.** 초기화 명령도 실행하지 않는다.
  초기화 명령은 사용자 시스템을 바꾸는 실제 동작이다.

  이 경계는 이미 두 겹으로 서 있다(2026-09-13 확인). `generate-command.ts:2220` 이
  `applyPreFill` 앞에서 `return skip` 하고, 같은 파일 536행의 파서가 `--no-dry-run` 과
  `--reset-cmd` 동시 사용을 `UsageError` 로 거절한다. **새 게이트를 만들 것이 아니라 이
  두 겹을 테스트로 고정하는 것이 이번 일이다**
- 확인 화면에서 취소하면 그 지점 이후의 실제 호출이 없다. 재검증 확인(§2.3)에서 거절하면
  재검증 호출이 나가지 않는다
- 재검증 확인은 **`runDryRun` 을 부르기 전에** 묻는다. 부른 뒤에 묻는 자리가 하나라도
  있으면 그 경계가 무너진다

## 6. 완료 조건

상태성 fixture 를 새로 만들어 판정한다. 인메모리 목 서버로 만든다.

1. **fixture A (사전보완):** 도구가 첫 호출에서 실패하고 두 번째 호출부터 성공한다.
   초기화 없이 돌리면 baseline 실패 · AI 통과라 AI 가 채택된다. 초기화를 넣으면 둘 다
   실패해 `held` 가 되고 baseline 이 유지된다. **후자가 되어야 통과다.**
2. **fixture B (최종 재검증):** 케이스 2개. 단독으로는 둘 다 통과하고, 1번 다음에 2번을
   돌리면 2번이 실패한다. 최종 전량 재검증이 그 실패를 잡는다. 합집합만 쓰던 기존 코드는
   못 잡는다.
3. 초기화 수단이 없으면 채택이 0건이고 화면에 §4 의 문장이 찍힌다.
4. 초기화 명령이 실패하면 등급이 `failed` 이고 저장 화면이 검증 범위를 적는다.
5. `--no-dry-run` 에서 초기화 명령이 **한 번도 실행되지 않는다.**
6. 재검증 확인에서 거절하면 서버 호출이 늘지 않고 저장은 된다. **화면**에 전량 재검증을
   하지 않았다는 문장과 개별 확인 케이스 수가 찍힌다.
6-1. 저장된 명세 파일에 새 키가 하나도 안 생긴다. `validateMcpSuite` 가 그 파일을 통과한다.
7. 스위트 내부 케이스 사이에는 초기화 명령이 실행되지 않는다. 호출 횟수로 센다.
8. 비대화형에서 묻지 않고 재검증을 건너뛰며 안내 문장이 찍힌다.

## 7. 비범위

- `freshProcess` 등급의 실제 구현. §3 에 사유를 적었다.
- 외부 DB 상태 판정. 우리는 초기화 명령이 무엇을 했는지 알 수 없고, 알 수 없다는 사실을
  말하는 것이 이번 범위다.
- 케이스별 초기화. §2.2 에 사유를 적었다.
