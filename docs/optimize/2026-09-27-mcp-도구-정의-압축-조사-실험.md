# MCP 도구 정의 압축: 조사와 실험

2026-09-27. "같은 기능을 유지하면서 MCP 서버의 도구 정의가 차지하는 토큰을 줄일 수 있는가"를
문헌 조사와 공개 서버 15개 실측으로 확인한 기록이다. 설계 문서가 아니라 그 앞 단계의
근거 문서다. 실험 재료는 [`benchmark/tool-definition-compression/`](./benchmark/tool-definition-compression/)
에 있다.

## 0. 결론 먼저

- **가능하다. 단, 안전한 방법의 천장은 낮다.** 정보를 지우지 않는 변환만 쓰면 서버 대부분에서
  8~18%, 반복 문구가 많은 서버에서 37~42% 줄었다. 무손실 정규화만으로는 4~9%다.
- **큰 절감(20~75%)은 파라미터 설명을 지울 때 나오는데, 그때 기능이 실제로 깨졌다.**
  chrome-devtools 에서 `navigate_page` 대신 `new_page` 를 골랐고, notion 에서 조회 filter
  인자를 만들지 못했다. 이 단계는 모델 검증 없이 켤 수 없다.
- **안전 프로필은 35개 서버, 모델 선택 테스트 210건, 스키마 동치 표본 약 72,000개로 검증했다.**
  1·2차(15개 서버, 90건)에서는 도구 선택 불일치 0건이었다. 3차(20개 서버, 120건)에서는
  원본을 2회 돌린 기준 편차가 4건이었고, 안전 프로필은 9건이 달랐다. 그중 압축이 만든 실제
  퇴행은 3건(2.5%)이며 **전부 "중복 문장 승격" 단계**에서 나왔다. 무손실 정규화, 잡음 제거,
  공통 파라미터 승격은 도구 선택을 바꾸지 않았다.
- 그래서 안전 프로필에서 **문장 승격은 뺀다.** 뺀 뒤의 감소는 35개 서버 합계 13.9%,
  서버별 중앙값 12.2%다(승격 포함 시 15.9%). 승격은 결함 두 가지를 고친 뒤 옵션으로 되돌린다.
- 인증 없이 로컬에서 도는 서버 5개는 모델이 낸 호출을 실제로 실행해 응답을 비교했다.
  같은 호출은 같은 응답을 냈고, 응답 차이는 전부 인자 표현 차이에서 왔다.
- 그래서 만들 것은 압축기가 아니라 **"어디까지 지워도 되는가"를 서버별로 판정하는 게이트**다.
  절감률은 서버 성격이 정하고, 우리가 보장할 것은 기능 유지다.
- 문헌의 "무손실 50~60%"는 OpenAPI 명세 기준이라 MCP 실물에서 재현되지 않았다. 실제
  `inputSchema` 에는 그만한 메타데이터가 없다.

## 1. 배경: 무엇이 토큰을 먹는가

MCP 클라이언트는 `tools/list` 응답(이름·설명·`inputSchema`)을 모델 컨텍스트에 싣는다.
문헌은 이것을 줄이는 네 갈래를 말한다.

| 접근 | 바꾸는 것 | 보고된 절감 | 위험 |
|---|---|---|---|
| 스키마 정규화(무손실) | `$schema`, `title`, 불필요한 `additionalProperties`, 키 정렬 | 47~64% (SchemaShrink, OpenAPI 기준) | 거의 없음 |
| 설명 압축(손실) | description 축약·삭제, LLM 재작성 | 70~97% (Atlassian mcp-compressor) | 유사 이름 도구 오선택. 정확도 실측이 대부분 없음 |
| 표기법 변환 | JSON 스키마를 LLM 용 텍스트로 컴파일 | 52~57% (TSCG) | MCP 클라이언트가 JSON 스키마를 요구하므로 적용 불가 |
| 지연 로딩·검색·코드 실행 | 정의를 싣지 않고 필요할 때 로드 | 85~98.7% (Anthropic Tool Search, Code Execution) | 호스트 기능. 서버가 지정할 수 없다 |

이 프로젝트가 다룰 수 있는 것은 앞의 둘이다. 넷째는 클라이언트 권한이라는 점이 중요하다.

### 1.1 클라이언트가 결정하는 것과 서버가 결정하는 것

| 항목 | 결정권 | 근거 |
|---|---|---|
| 도구를 미뤄 두고 검색으로 꺼내기 | 클라이언트 | Claude Code 는 MCP 도구 설명이 컨텍스트의 10% 를 넘으면 자동으로 전부 미루고 MCPSearch 로 꺼낸다. Codex 는 전부 앞에 싣는다 |
| 검색 1회에 몇 개를 로드할지 | 클라이언트 | 모델이 `select:이름` 을 쓰면 1개, 키워드를 쓰면 색인에 걸리는 전부. 서버 쪽 상한 없음 |
| `tools/list` 에 무엇을 넣을지 | 서버 | 목록은 서버가 만든다 |
| 서버 `instructions` | 서버 | 단, 클라이언트가 이것을 모델에게 보여 주는지는 제각각 |

MCP 프로토콜에 "이 도구는 지연 로딩하라"는 필드는 없다. 따라서 **서버(또는 프록시)가 할 수
있는 일은 `tools/list` 의 내용을 바꾸는 것까지**다.

### 1.2 지연 로딩 환경에서의 비용 식

MCPLens 파일럿 실측(2026-08-31 설계 문서)이 보여준 것: 지연 로딩에서 도구 하나의 비용은
**정의 무게 × 검색에 끌려온 횟수**다. 로드 0인 도구 43개를 꺼도 첫 턴이 808토큰밖에 안
줄었고, 진짜 오염원은 검색에 딸려 오는 3개였다. 그러므로 서버가 쥘 수 있는 손잡이는 셋이다.

1. **이름**: 모델이 이름만 보고 확신하면 `select:` 로 1개만 로드한다.
2. **설명 어휘**: 형제 도구와 어휘가 겹치면 키워드 검색에 함께 걸린다.
3. **정의 무게**: 딸려 와도 가볍게.

## 2. 설계 원칙

- **서버 코드는 건드리지 않는다.** LLM 에게 보이는 `tools/list` 만 바꾸고 `tools/call` 은
  원본 이름·원본 스키마로 되돌려 보낸다. 산출물은 오버레이 파일 + 얇은 프록시다.
- **사용 데이터를 보지 않는다.** "안 쓰이는 도구"는 사용자마다 달라서 배포 전 도구가 판정할 수
  없다. 그것은 실제 세션을 관측하는 MCPLens 의 영역이다. 이 도구는 정의를 읽고 정의를 내놓는
  순수 변환이다.
- **도구를 빼거나 합치지 않는다.** 둘 다 호출 계약을 바꾼다. `outputSchema` 도 계약이라
  건드리지 않는다.
- **결정론.** 같은 정의에는 항상 같은 결과. LLM 재작성을 쓴다면 결과를 캐시에 고정한다.

## 3. 변환 단계

| 단계 | 건드리는 것 | 성격 |
|---|---|---|
| 1 무손실 정규화 | `$schema`, `$id`, `title`, `additionalProperties:true`, 빈 `required`, 빈 `properties` | 검증 의미 불변 |
| 2 잡음 제거 | URL, "Example:" 이하 블록, 이름을 되풀이하는 파라미터 설명(`database: "Database name"`) | 모델이 도구를 고르는 데 쓰지 않는 정보 |
| 2 중복 승격 | 도구 25% 이상이 공유하는 설명 문장을 서버 `instructions` 로 한 번만 | 자리만 옮김. 클라이언트가 instructions 를 보여 줄 때만 보존 |
| 2b 공통 파라미터 승격 | 3개 이상 도구에 같은 이름·같은 설명으로 반복되는 파라미터 설명을 `instructions` 사전으로 | 같음 |
| 3 손실 | 스키마 안 `description`·`default`·`additionalProperties:false` 전부 제거 | **정보 삭제. 상한 측정용. 기본에서 끔** |

**안전 프로필 = 1 + 2 + 2b.**

### 3.1 예시

1단계 전:
```json
{"$schema":"http://json-schema.org/draft-07/schema#","title":"GetWorkInput","type":"object",
 "properties":{"work_id":{"type":"string","title":"Work Id","description":"OpenLibrary work id"}},
 "required":["work_id"],"additionalProperties":true}
```
후:
```json
{"type":"object","properties":{"work_id":{"type":"string","description":"OpenLibrary work id"}},"required":["work_id"]}
```

2b 예시(mongodb): 27개 도구가 모두 갖는 `connectionId` 의 설명 "The connection to run the
operation against. Use the id returned by one of the connect tools." 를 각 도구에서 지우고
`instructions` 에 `- connectionId: ...` 한 줄로 둔다.

## 4. 게이트

| 게이트 | 묻는 것 | 방법 | 결정론 |
|---|---|---|---|
| A 계약 동치 | 압축 스키마가 원본과 같은 입력 집합을 받나 | 원본 스키마에서 표본 생성(json-schema-faker) + 변이(필드 제거·타입 변경·여분 필드) → ajv 로 양쪽 판정 비교 | 예 |
| C 검색 오염 | 목표 도구를 찾는 질의에 형제가 몇 개 함께 걸리나 | 이름+설명+인자 설명 색인에 BM25. 질의는 도구 이름을 단어로 푼 것 | 예 |
| B 선택 동치 | 모델이 같은 도구를 같은 인자로 부르나 | 원본 정의와 압축 정의를 각각 주고 같은 자연어 요청에 답하게 함 | 아니오 |

A 와 C 는 매 CI 에서, B 는 기준선을 갱신할 때만 돌린다.

## 5. 실험

### 5.1 설정

- 대상: `npx` 로 인증 없이 `tools/list` 를 뽑을 수 있는 공개 서버. 27개를 수집해 토큰 크기
  상위에서 15개를 골랐다. 1차 5개(notion, mongodb, firecrawl, desktop-commander,
  chrome-devtools), 2차 10개(azure, paypal, hubspot, sentry, kubernetes, apify, supabase,
  playwright, github-legacy, playwright-ea).
- 토큰: gpt-tokenizer `o200k_base`. Anthropic 토크나이저는 공개돼 있지 않아 근사치다.
  측정 단위는 `{name, description, input_schema}` 를 compact JSON 으로 직렬화한 합계이며,
  `instructions` 로 승격한 분량은 더해서 셌다.
- 게이트 B: Claude Haiku 4.5. 서버당 요청 6개, 1회 실행. 프롬프트에 서버 `instructions` 를
  포함했다(2b 의 전제를 만족한 조건).

desktop-commander 는 같은 안내 문장이 6개 도구에 반복돼 규칙만으로 37%가 빠졌다.

### 5.5 도구 단위 수치

15개 서버의 도구 411개 각각에 대해 원본·안전 프로필·3단계 토큰을
[`per-tool.csv`](./benchmark/tool-definition-compression/per-tool.csv) 에 남겼다. 열은
`server, tool, orig_tokens, orig_desc_tokens, orig_schema_tokens, safe_tokens, safe_pct, stage3_tokens, stage3_pct`
다. 이 파일의 합계는 `instructions` 로 승격한 분량을 더하지 않은 값이라 5.3절 표보다 감소율이
1%p 안팎 높게 나온다. 서버 단위 판단은 5.3절 표를, 도구 단위 판단은 이 파일을 기준으로 한다.

안전 프로필의 도구별 감소율 분포:

| 최소 | 하위 25% | 중앙값 | 상위 25% | 최대 |
|---|---|---|---|---|
| 0.0% | 8.8% | 17.2% | 32.5% | 74.1% |

- 전혀 줄지 않은 도구 21개(설명이 없고 스키마에 메타데이터도 없는 것).
- 20% 이상 줄어든 도구 186개(전체의 45%).
- 가장 많이 줄어든 도구는 desktop-commander 의 `read_file` (950→246, 74.1%)로, 도구 설명의
  절반 이상이 서버 공통 안내 문장이었다.

### 5.6 3차: 표본 확대, 기준 편차, 실행 비교

새 서버 20개(postman 204 도구, browserstack 46, git-cyan 28, antv-chart 27, astra 19,
airtable 16, filesystem 14, circleci 13, mastra-docs 13, everything 13, browsermcp 12, line 12,
hyperbrowser 10, shadcn 10, pinecone 9, netlify 9, browserbase 9, memory 9, slack-legacy 8,
google-maps 7). 원본 정의로 같은 요청을 2회 돌려 모델 자체의 흔들림을 먼저 잰 뒤 안전
프로필과 비교했다. 게이트 A는 표본 38,712개 불일치 0.

| 비교 (120건) | 같은 도구 | 인자까지 동일 |
|---|---|---|
| 원본 1회차 vs 원본 2회차 (기준 편차) | 116 | 100 |
| 원본 1회차 vs 안전 프로필 | 111 | 100 |

도구가 달라진 9건을 하나씩 분류했다.

| 분류 | 건수 | 내용 |
|---|---|---|
| 기준 편차 안 | 3 | 원본끼리도 다른 요청 (browserstack 2건, netlify 1건) |
| 안전이 개선 | 1 | netlify: 원본은 null, 안전은 도구를 찾음 |
| 동등한 대안 | 1 | mastra-docs: "검색" 요청에 검색 도구를 고름 |
| 모호 | 1 | astra: 원본은 빈 벡터로 HybridSearch, 안전은 null |
| **압축이 만든 퇴행** | **3** | browserstack 1건, circleci 2건. 전부 문장 승격 때문 |

퇴행 3건의 원인은 둘이다.

1. **조각이 남는다.** circleci 의 설명은 개조식 목록이었다. 문장 단위로 공유 부분을 뽑아내자
   `* Project URL:` 같은 빈 항목만 남아 설명이 읽히지 않게 됐고, 모델은 도구를 부르지 못했다.
2. **도구 한정 지침이 전역이 된다.** browserstack 의 "프로젝트 ID 가 없으면 askBrowserStackAI 를
   먼저 부르라"는 문장은 몇 개 도구에만 붙어 있던 조건부 지침이다. 서버 안내문으로 올라가자
   모델이 모든 요청에 적용해 createTestCase 대신 askBrowserStackAI 를 골랐다.

승격을 뺀 안전 프로필의 절감을 35개 서버 전체에서 다시 잰 결과다.

| 프로필 | 원본 합계 | 결과 | 감소 |
|---|---|---|---|
| 무손실 + 잡음 제거 + 공통 파라미터 + 문장 승격 | 286,884 | 241,412 | 15.9% |
| 무손실 + 잡음 제거 + 공통 파라미터 | 286,884 | 247,070 | 13.9% |

승격을 빼면 서버별 감소는 최소 0.9%, 중앙값 12.2%, 최대 37.5%다. 승격이 크게 기여하던
서버는 azure(41.6→22.8%), circleci(34.9→21.7%), desktop-commander(37.3→30.5%),
browserstack(12.5→8.3%) 넷뿐이었다.

**실행 비교.** 인증 없이 로컬에서 도는 서버 5개(filesystem, everything, memory, git-cyan,
mastra-docs)는 게이트 B 가 낸 호출을 실제 서버에 넣어 원본 조건과 안전 조건의 응답을
비교했다. filesystem·everything·memory 는 6건 모두 응답이 바이트 단위로 같았다. git-cyan 은
양쪽 모두 6건이 같은 검증 오류를 냈다(작업 디렉터리 세션이 없어서). mastra-docs 는 인자 표현
차이(`"./"` 와 `"."`)와 위의 동등 대안 1건이 응답 차이로 이어졌다. 같은 호출이 다른 응답을
낸 경우는 없었다.

## 6. 하지 말 것

- **파라미터 설명 일괄 제거.** 20~75% 빠지지만 실제로 오선택과 인자 누락을 냈다.
- **`default` 제거.** 모델이 기본값을 매번 명시해 출력이 오히려 는다.
- **`additionalProperties:false` 제거.** 클라이언트 측 검증 의미가 바뀐다.
- **공유 문장을 그대로 서버 안내문으로 승격.** 3차에서 퇴행 3건을 전부 이것이 냈다. 되돌리려면
  두 조건이 필요하다. 문장이 아니라 문단 단위로만 뽑고, 다른 도구 이름이나 조건문(if, must,
  never)이 들어간 문장은 승격하지 않는다. 고친 뒤에도 게이트 B 를 다시 통과해야 한다.
- **사용 빈도로 도구 제외.** 사용자마다 다르다. MCPLens 의 일이다.
- **형제 도구 병합.** 계약 변경이다.

## 7. 한계

- 게이트 B 는 모델 1종(Haiku 4.5), 서버당 요청 6개다. 3차에서 원본 2회 실행으로 잰 기준 편차가
  120건 중 4건(3.3%)이라, 이 크기의 차이는 압축 탓으로 볼 수 없다. 퇴행 판정은 원본 두 회차가
  일치하는데 안전만 다른 경우로 한정했다.
- 실행 비교는 로컬 서버 5개, 호출 30건이다. 나머지 30개 서버는 자격 증명이 필요해 실행하지
  않았고, 모델이 낸 호출까지만 비교했다.
- 2·2b 의 `instructions` 승격은 클라이언트가 그것을 모델에게 보여 준다는 전제가 있다. 보여 주지
  않는 클라이언트에서는 꺼야 하고, 그러면 감소율은 1단계 수준(4~9%)으로 내려간다.
- 토크나이저는 근사치다. 클라이언트가 정의를 어떤 형식으로 직렬화하는지도 알 수 없어 절대값보다
  비율로 읽어야 한다.
- 게이트 C 의 검색기는 Claude Code 내부와 같지 않다. 경향 판단용이다.

## 8. 이 프로젝트에서의 자리 (제안, 미결)

- `runner`·`generate`·`record` 와 같은 층에 새 패키지 `optimize`. `core` 에만 의존.
- 게이트 A 는 `runner` 의 검증기를, 게이트 B 는 `record` 의 재생을 쓰되 조립은 `cli` 가 한다.
- 출력은 세 가지. 오버레이 파일(도구별 노출 이름·바뀐 설명의 원본과 결과·게이트 결과, 원본
  항상 보존), 클라이언트 프로필별 절감 리포트("전부 로드"와 "지연 로딩"을 따로), `tools/list`
  만 바꾸는 프록시.
- 기본은 안전 프로필을 자동 적용하고, 그 위에 "게이트 B 를 통과한 파라미터만 추가로 지우는"
  공격 모드를 사용자가 켜는 구조.
- MCPLens 와의 관계: 배포 전 예방(이것)과 배포 후 관측(MCPLens). MCPLens 의 `remove` 후보를
  입력으로 받아 우선순위를 정할 수 있다.

## 9. 확인이 필요한 결정

1. 2단계 재작성기를 규칙 기반만으로 시작할지, LLM 재작성(결과 캐시 고정)까지 첫 판에 넣을지.
   규칙 재작성은 게이트 C 를 거의 움직이지 못했으므로, 검색 오염을 줄이는 것이 목표라면 LLM
   재작성이 필요하다.
2. `instructions` 승격을 기본으로 켤지, 클라이언트 프로필별 옵션으로 둘지.
3. 게이트 B 의 표본 크기와 모델 종류를 어디까지 늘릴지.
