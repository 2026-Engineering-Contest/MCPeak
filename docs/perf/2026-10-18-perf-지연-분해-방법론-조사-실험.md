# MCP 서버 응답 지연 분해 방법론 조사·실험

2026-10-18. Azure Well-Architected Framework 의 다섯 기둥 중 "성능 효율성" 을 MCPeak 이 채울 수 있는지
가리기 위한 조사다. 결론은 **성립한다. 단, 측정 종료 시각과 관측 범위에 보정이 필요하다.** 근거 스크립트와
결과표는 `docs/perf/benchmark/perf-latency-decomposition/` 에 있다.

## 1. 가리려 한 것

개발자가 만드는 MCP 서버에 개발 단계에서 우리 도구를 돌리면 **서버 코드를 고치게 되고, 그 결과 배포된
서버의 `tools/call` 응답 시간이 줄어드는가.** 런타임에 끼는 프록시는 범위 밖이다. 토큰 절감(비용 최적화,
`optimize`)과는 다음 선으로 가른다.

| | 비용 최적화 (`optimize`) | 성능 효율성 (이 조사) |
|---|---|---|
| 줄이는 것 | LLM 에 들어가는 `tools/list` 토큰 | 서버가 `tools/call` 을 받아 응답하기까지의 시간 |
| 동작 위치 | 런타임 프록시 | 개발 단계 측정. 배포물에 들어가지 않음 |
| 바뀌는 것 | 도구 정의 | 서버 코드 |
| 단위 | 토큰, 금액 | ms, p50/p95 |

응답 본문 크기가 LLM 처리에 미치는 영향은 비용 쪽에 넘기고, 성능 쪽은 **서버 프로세스 경계 안의 시간만**
책임진다.

## 2. 방법

`@mcpeak/record` 와 같은 방식(`NODE_OPTIONS=--import`)의 프리로드로 서버의 외부 HTTP 호출을 관측하고,
SDK 클라이언트로 도구를 호출해 각 호출 구간 안의 외부 호출을 모은다. 도구 호출 시간을 **외부 대기**(외부
호출 구간의 합집합)와 **서버 처리**(나머지)로 나누고, 외부 호출들의 선후와 응답 본문 값의 재사용 여부로
**의존/독립** 을 판정한다. 대상은 npm 의 공개 Node MCP 서버 19개(API 키 불필요), 도구별 3회 호출.

## 3. 결과

### 3.1 측정 (p50 ms, 보정 후)

| 서버 | 도구 | 총 | 외부 대기 | 서버 처리 | 진단 |
|---|---|---|---|---|---|
| mcp-package-version | check_docker_tags | 4,042 | 4,014 | 35 | 순차 12건, 10건은 팬아웃 가능 |
| mcp-package-version | check_npm_versions | 700 | 약 575 | 60~90 | 순차 독립 5건 |
| hackernews-mcp | get_top_stories | 674 | 673 | 1 | 1+30건, 이미 병렬. N+1 |
| @kazuph/mcp-fetch | imageFetch | 906 | 811 | 125 | robots.txt 를 매 호출 직렬 선조회 |
| mediawiki | get-page | 630 | 623 | 7 | 시작 시 원격 조회로 콜드 스타트 1,509 |
| airbnb | airbnb_search | 1,385 | 약 1,350 | 22~38 | 없음 (파싱 비용 작음) |
| context7, wikipedia, arxiv, github-repo, pera1, webscout, pubmed | 각 조회 | 32~2,384 | 99% 이상 | 1~18 | 없음. 원격 API 대기가 전부 |
| fetch-mcp | fetch_url | 319 | (HTTP/2, 채널 구독 시 관측) | | 하네스 현 구현에서 분해 불가 |

진단이 나온 서버 5개, 고칠 것 없음 7개 이상. 진단 유형은 네 가지다. **순차 독립 호출, 매 호출 반복되는
선조회, 시작 시 원격 조회, N+1 팬아웃.**

### 3.2 팬아웃 효과 (check_docker_tags, 서버 사본을 Promise.all 로 수정, 각 5회)

| | p50 | 상태 |
|---|---|---|
| 원본 (순차) | 3,731 | 200 × 60 |
| 팬아웃 사본 | 893 | 200 × 59, 429 × 1 |

출력은 바이트 단위로 같았다. 요청만 직접 재현한 별도 측정은 3,405 → 1,279 였다. 60~76% 감소.
Docker Hub 익명 한도가 소모되므로 동시성 상한과 429 백오프가 함께 필요하다.

### 3.3 관측 범위 (19개)

| 경로 | 서버 수 | 시간 | 본문(의존 판정) |
|---|---|---|---|
| `globalThis.fetch` | 13 | 보임 | 보임 |

undici 를 직접 쓰는 서버는 없었다. Python 등 다른 런타임은 관측 불가다.

## 4. 반박 팀 검증에서 무너진 것

attacker·runner·defender 세 역할이 독립 재측정했고 교차 반박 뒤 다음이 기각됐다.

- **"무거운 서버 처리" 진단 3건은 전부 측정 오류.** `http.client.response.finish` 는 헤더 수신 시점에 발생해
  본문 내려받기가 서버 처리로 들어갔다(airbnb 602 → 22~38ms, check_npm_versions 429 → 60~90ms).
  npm-helper 의 237ms 는 서버의 `RateLimiter(2 req/s)` 대기이고 드라이버 호출 간격 150ms 가 만든 값이다.
- **npm-search 의 "자식 프로세스라서 관측 불가" 는 틀렸다.** npm 캐시 적중으로 네트워크가 없었던 것이다.
- **youtube-transcript 의 측정은 실패 경로였다.** 3회 모두 빈 결과, timedtext 200 이지만 0바이트. `isError` 가
  아니라 실패로 집계되지 않았다.
- **의존 휴리스틱은 입력값 반향으로 거짓 의존을 내고, 헤더(Bearer, Location)로 넘어가는 의존을 놓친다.**
  합성 반례로 확인. 실제 의존 3건(weather·hn·pubmed)은 이 유형이 아니었다.
- **CPU 와 wall 의 혼동.** `process.cpuUsage` 는 GC 보조 스레드까지 합산하고 TLS·gunzip·디코딩이 네트워크
  구간과 겹친다. 지연에 더해지는 몫은 "마지막 본문 끝 이후 wall" 로 봐야 한다.

살아남은 것: 분해 방식 자체(종료 시각을 본문 끝으로 잡으면 독립 측정 세 건이 1ms 안에서 일치), 진단 네
유형, 팬아웃 효과, 의존 판정 3건, 관측 범위 집계, 프로세스 간 시계 정렬(오차 1ms 미만).

## 5. 설계에 반영할 것

1. 모든 경로의 종료 시각은 응답 본문 끝. `node:http` 는 `response.on("end")`, http2 는 stream close.
2. 요청·응답 헤더(Location, Authorization)를 의존 판정에 넣고, 입력값에서 온 토큰은 매칭에서 제외한다.
3. 케이스 간 호출 간격을 명세에 적고 리포트에 표시한다. 레이트리미터 대기가 서버 처리로 보이는 것을 막는다.
4. 빈 결과·0바이트 응답은 `isError` 가 아니어도 실패 경로로 분리한다.
5. 외부 지연 변동이 크다(같은 서버 p50 659 대 p95 6,519). 전후 비교에는 녹화 지연을 재생하는 모드가 있어야
   서버 코드 변경만의 효과를 잴 수 있다.
6. fetch 와 undici 채널에 같은 요청이 두 번 찍히고, 리다이렉트 대상은 URL 이 달라 중복 제거에서 빠진다.
7. 범위를 Node 서버로 명시한다. 다른 런타임은 콜드 스타트와 총 시간만 제공한다.

## 6. 제안 기능 `mcpeak perf` 와 권장 순서

- 1단계: 지연 분해 리포트(도구별 p50/p95, 외부 대기, 서버 처리, 콜드 스타트)와 회귀 게이트
  `--perf-baseline`. 진단 규칙은 **순차 독립 호출** 과 **반복 요청** 두 개로 시작한다.
- 2단계: 녹화 지연 재생 모드. record 세션 포맷에 외부 호출 소요 시간을 넣어야 하므로 ADR 대상이다.
- 데모: `examples/live-weather-server` 에 독립 호출을 직렬로 짠 도구를 하나 두고, 리포트 → 수정 → 재측정으로
  수백 ms 차이를 CI 로그로 보인다.

## 7. 인용할 자료

- 원격 도구 호출이 에이전트 루프의 임계 경로라는 문제 정의: Cortex (arXiv 2509.17360)
- 독립 호출 병렬화 효과: LLMCompiler (arXiv 2312.04511)
- 상주 프로세스 대 요청별 spawn, 프록시 오버헤드 측정 방식: MCP Bridge (arXiv 2504.08999)
- 같은 조건에서 서버별 시간 비교 프로토콜: MCPBench (arXiv 2504.11094)
- 서버 쪽 코드 지연을 프로파일링하는 MCP 전용 연구는 확인되지 않았다.

## 8. 부수 발견 (범위 밖)

- `npm-search-mcp-server` 는 query 를 셸 명령에 그대로 넣어 셸 인젠션이 성립한다(`dist/index.js:57`).
  audit 의 `launch` 계열 검사 후보다.
- `open-meteo-mcp` 는 IPv6 우선 접속 타임아웃(약 250ms)으로 이 네트워크에서 실패했다. 우리 예제 서버가
  `setDefaultResultOrder("ipv4first")` 로 피한 것과 같은 문제다. 성능이 아니라 신뢰성 진단 후보다.
