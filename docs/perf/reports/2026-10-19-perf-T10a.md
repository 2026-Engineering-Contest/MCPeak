- `defineProperty(..., enumerable: true)` 세 줄을 `dressAs(wrapped, response)` 로 바꿨다. `dressAs(target, source)` 는
  target 에 열거되지 않는 own 속성 다섯 개를 둔다.
  - `url`·`redirected`·`type`: 원본 값.

## 임의로 판단한 것

1. **복제본의 `headers` 도 원본 응답의 같은 `Headers` 객체다.** 프리로드 없는 `clone()` 은 내용이 같은 새 불변 `Headers` 를
   준다. 객체 동일성(`res.headers === copy.headers`)만 다르고 값과 불변성은 같다. 사양 문장("복제본에도 같은 네 속성")을
   그대로 따랐다.
2. **속성 서술자는 `writable: false`, `configurable: true`.** 원래는 프로토타입의 getter 라 엄격 모드 대입이 TypeError 인데,
   쓰기 불가 own 속성도 엄격 모드 대입이 TypeError 라 같다. `configurable: true` 는 서버나 다른 계측 도구가 다시 정의할 여지를
   남기기 위해서다.
3. **원래 clone 은 로드 시점에 잡는다.** 서버가 나중에 `Response.prototype.clone` 을 바꿔도 감싼 응답의 clone 은 원래 의미를
   지킨다.
4. **시험은 리다이렉트 응답 하나로 했다.** url·redirected·type 이 기본값과 모두 다른 경우라 차이가 가장 잘 드러난다.

## 남은 위험

1. `Object.getOwnPropertyNames(res)` 와 `Reflect.ownKeys(res)` 에는 다섯 속성이 보인다(원본은 빈 배열). 열거만 맞췄다.
2. 복제본끼리와 원본 사이의 `headers` 객체 동일성이 프리로드 유무로 다르다(위 1번 판단).
3. 서버가 감싼 응답의 `clone` 을 떼어 다른 `this` 로 부르면 원래 메서드가 TypeError 를 내지만 오류 문장의 스택에
   프리로드의 `clone` 이 한 줄 더 보인다.
