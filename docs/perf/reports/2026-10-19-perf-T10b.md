## 구현 (설계 §5.4, 계획 E31)

`errorDetail` 의 순서: 원인 문장 → 첫 줄 → URL 가림 → 비밀 모양 가림 → 200자 자르기.

1. `causeMessage`: 바깥이 `instanceof McpClientError` 이고 `code !== "OPERATION_FAILED"` 이며 가장 안쪽이 바깥 자신이 아니면
   `{바깥 message}: {가장 안쪽 message}`. 그 밖은 지금처럼 가장 안쪽(`Error` 가 아니면 `String(error)`).
   `McpClientError` 는 `@mcpeak/core` 에서 값으로 import 한다(perf 의 기존 런타임 의존성, 새 의존성 아님).
2. `maskSecrets`: `/Bearer\s+[A-Za-z0-9._~+/=-]+/g` → `Bearer …`(수정 루프 1회차, 아래), `/eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+(?:\.[A-Za-z0-9_-]+)?/g` → `…`,
   `/\b(?:sk|pk|rk)-[A-Za-z0-9_-]{16,}/g` → `…`. 이 순서로 적용한다.
3. **추가 사양(오케스트레이터 후속 지시)** `collapsePrefix`: `/^(MCP error -?\d+: )\1+/` → `$1`. 맨 앞에서 같은 머리말이
   연달아 반복되면 하나만 남긴다. `{바깥}: {안쪽}` 을 잇는 경우는 안쪽 문장에 먼저 적용한다. `Error` 가 아닌 거부의 `String(error)` 에도 적용한다.

## 수정 루프 1회차 (오케스트레이터 결정)

첫 보고의 판단 1(사양 정규식 `Bearer\s+\S+` 가 값 뒤의 `)` 까지 먹는다)을 오케스트레이터가 정했다. Bearer 값을 RFC 6750 token68 문자
`[A-Za-z0-9._~+/=-]+` 로 좁혔다. 그래서 값 뒤의 닫는 괄호·쉼표 같은 문장 부호가 남는다. 테스트 기대를
`upstream 401: Invalid API key … (Authorization: Bearer …)` 로 고쳤다. 다른 Bearer 기대(`Bearer … rejected`, 300자 값)는 그대로 통과한다.
설계 §5.4 의 문장은 오케스트레이터가 고친다.

## 임의로 판단한 부분

1. **Bearer 뒤 닫는 괄호**: 첫 보고에서는 사양 정규식 그대로라 `)` 가 사라졌다. 수정 루프 1회차에서 위처럼 정해졌다.
2. **`Bearer` 뒤 공백 정규화**: `Bearer\t값` 은 `Bearer …` (공백 하나)로 바뀐다. 치환 문자열이 고정이라서다.
3. **비밀 가림 순서**: Bearer → JWT → 키. 겹치는 경우(Bearer 값이 JWT)는 Bearer 가 먼저 값 전체를 가린다.
4. **`collapsePrefix` 의 적용 범위**: 맨 앞 머리말만 본다. `{바깥}: {안쪽}` 에서는 안쪽에만 적용하므로 바깥 문장 뒤에 오는 반복도 줄어든다.

## 남은 위험

- `instanceof McpClientError` 는 perf 와 cli 가 같은 `@mcpeak/core` 인스턴스를 쓸 때만 참이다. npm 설치에서 두 패키지가 서로 다른 core
  버전을 끌어오면 거짓이 되어 분류 문장 없이 가장 안쪽 문장만 남는다(가림은 그대로 동작해 비밀이 새지는 않는다).
- 비밀 모양 가림은 세 모양뿐이다. 그 밖의 서버 문장(예: `password=…` 평문)은 그대로 실린다. 설계 §5.4 가 한계로 적은 범위다.
