  구간도 자기 자신은 센다")은 그대로다. `CallTiming` 의 두 JSDoc 에 이 제외를 적었다.

  (1) 지시의 예 `[99.0, 99.5]`·`[100.3, 150]` → maxConcurrency 1, external 49.7, requests 2.
  (2) `[99.0, 99.5]`·`[99.8, 150]` → maxConcurrency 1, external 49.9, requests 2.
  (1) 은 수정 전에도 1 이었다(두 번째 요청이 100.3 에 시작해 길이 0 구간 `[100.1, 100.1]` 과 겹치지 않는다). 수정을 실제로 가르는 것은

  `expected 2 to be 1` 로 빨강인 것을 확인했다.
- 판정 조건에 `e.t0 < c.t0` 을 함께 둔 것은 임의 판단이다. "호출 시작 전에 이미 끝난 요청" 만 빼고, 호출 안에서 시작한 요청의 길이 0
  규칙을 건드리지 않기 위해서다.

## 임의로 판단한 부분과 관찰

- 설계 첫 시나리오의 B 를 `[102.1, 200]` 으로 바꿨다(위 판정). 대안은 요청을 `[97.0, 99.5]` 로 옮기는 것인데, 그러면 요청이
  점의 여유 창(98.05~)에도 들지 않아 점 제외를 검증하지 못한다.
- `maxConcurrency` 는 시작을 잘라도 관측 가능한 차이가 거의 없다. 지금 `maxOpen` 은 길이 0 구간도 열린 것으로 세므로, 호출 t0 전에
  끝난 요청이 `[c.t0, c.t0]` 로 잘려도 같은 시각에 시작한 요청과 동시로 센다. 그래서 `maxConcurrency` 감소를 단언하는 테스트는 두지
  않았다. 길이 0 구간을 빼는 것은 이 태스크 사양 밖이라 고치지 않았다. 필요하면 후속 태스크로 판단한다.
- 점 판정을 함수 하나(`callsServer`)로 뺐다. 지금은 `assignRequests` 만 쓴다.
