## 임의로 판단한 부분

1. **배정 배열의 3차 정렬 키.** 계획서는 `t0` 오름차순, 같으면 `seq` 오름차순이다. 다른 pid 의 요청이 `t0`·`seq` 까지 같으면
   순서가 입력 순서에 남으므로 `pid` 오름차순을 셋째 키로 더했다. 앞의 두 키를 바꾸지 않는 결정론 보강이다.
2. **중복 줄.** 같은 `(pid, seq)` 의 start 또는 end 줄이 여러 번 오면 처음 것을 쓴다. 사양에 없는 경우다.
3. **`maxConcurrency` 의 계산.** 구간 i 가 시작하는 순간 `s_j ≤ s_i < e_j` 인 j 의 수에 자기 자신을 더한 값의 최대로 셌다.
   "같은 시각의 끝은 시작보다 먼저" 와 같은 결과이고, 길이 0 구간(끝이 시작과 같은 요청)도 자기 자신은 1로 센다.
   이벤트 정렬 방식이면 길이 0 구간이 0 으로 사라지기 때문이다.
4. **끝이 시작보다 앞선 기록.** `min(requestEnd, c.t1)` 가 `t0` 보다 작으면(시계 역행 등) 길이 0 구간으로 본다. 음수 길이가
   합집합을 줄이지 않게 하기 위해서다.
5. **`percentiles` 의 순위 계산.** `ceil(p × n) − 1` 을 정수 백분율 `ceil(50·n / 100)`, `ceil(95·n / 100)` 로 계산한다.
   `0.95 × n` 의 부동소수 오차로 순위가 한 칸 밀리는 것을 막는다. 정의는 같다.
6. **배정 창의 경계.** `e.t0 ≥ c.t0 − 2` 와 `e.t0 ≤ c.t1 + 2` 를 양끝 포함으로 구현했다(설계 §5.1 의 부등호 그대로).
7. **경쟁의 세부.** callTool 을 먼저 부르고(동기 throw 도 거부로 받는다) 이어서 `sleep(timeoutMs, signal)` 을 건다. 승자가
   정해진 직후 `t1 = now()` 를 찍고 그다음 abort 한다. 진 쪽의 늦은 거부가 처리되지 않은 거부로 새지 않게 두 promise 를
   모두 결과 값으로 바꿔 둔다. 주입된 sleep 이 거부하면 타임아웃으로 본다(설계는 "abort 된 sleep 은 resolve 도 reject 도
   하지 않아도 된다" 고만 적어 거부 가능성을 열어 둔다).
8. **skipped 와 missingTool 의 우선.** 타임아웃 뒤에는 목록에 없는 도구도 `skipped` 로 둔다. "남은 호출은 전부 skipped"
   (설계 §3.2 5항)를 문자 그대로 따른 것이다.
9. **empty 판정의 공백.** "text 가 공백뿐" 을 `typeof text === "string" && text.trim() === ""` 로 읽었다. `text` 가 문자열이
   아닌 text 항목은 공백이 아니므로 그 결과는 ok 다.
10. **타임아웃 detail.** 고정 문장 `호출이 {timeoutMs}ms 안에 끝나지 않았습니다` 는 첫 줄·URL·200자 규칙을 거치지 않는다.
    URL 이 없고 200자보다 짧아 결과는 같다.

## 남은 위험

- `callTiming` 의 `maxConcurrency` 는 O(n²) 다. 호출 하나의 요청 수가 수천을 넘으면 느려질 수 있으나 설계 범위(호출당
  수십 건)에서는 무시할 수준이다.
- skipped·missingTool 측정도 배정 후보다(계획서 §5.2). 그 점 창의 ±2ms 안에 들어온 요청은 그 측정에 배정되고 통계에서는
  빠진다. 계획서가 정한 동작이며 T3 의 `analyze` 가 ok 반복만 쓰면 수치에는 영향이 없다.
