## 구현 요약

- `judge`(§6.1): 의사 코드 그대로. 응답 본문 토큰은 요청 객체를 키로 한 `WeakMap` 에 한 번만 파싱해 둔다.
  같은 호출 안에서 뒤 요청 여럿과 비교되기 때문이다. 결과는 입력만으로 정해진다.
- `runRules`(§6.2·§6.3): 외부 대기에 들어간 요청(`t0 ≤ c.t1`)을 배정 순서로 보며 순차 여부, 판정 집계,
  임계 경로(`finish`)를 한 번에 구한다. `end(e)` 는 `requestEnd`, `external(c)` 는 `callTiming` 을 쓴다(E5).
- `analyze`: `mergeTrace` → `assignRequests` → 측정별 `callTiming` → `runRules`. 관측이 없으면 배정·규칙을 건너뛴다.
  E12 의 집계(afterResponse 합, externalLowerBound 하나라도, maxConcurrency 최대)를 따른다. 키 순서는 §8.1 선언 순서.

## 임의로 판단한 부분

1. **`{요청 표기}` 의 `×{횟수}`**: "한 반복 안 횟수의 p50" 을 그 표기가 **나타난** 발동 반복들만으로 구했다. 나타나지
   않은 반복을 0 으로 넣으면 `×0` 이 나올 수 있어서다. 골든과 계획의 단언에는 영향이 없다.
2. **`evidence.requests`**: 문장 첫 줄과 같은 조각을 쓰되 셋에서 자르지 않고 전부 싣는다. 문장은 셋까지와 `외 {r}종`.
   JSON 은 기계가 읽으므로 잘라서 얻는 것이 없다고 봤다.
3. **`savingUpperBoundMs`**: p50 원값을 싣고 문장에서만 `Math.round` 한다. 다른 Percentiles 필드와 같은 방식이다.
4. **반복 요청 규칙의 대상 요청**: (a)·(b) 는 배정된 요청 전부(`afterResponse` 포함)를 본다. 순차 독립 규칙만
   설계가 "외부 대기에 들어간 요청" 으로 범위를 좁혔고, 반복 요청은 범위를 적지 않았다. `requests(c)` 도 `afterResponse` 를 포함한다.
5. **(b) 의 `evidence.of`**: 관련 케이스들의 ok 반복 수의 합. `{m}` 은 그 키가 나타난 ok 반복 수.
6. **(b) 의 `{ms}`**: 요청 길이를 `requestEnd(e, c) − e.t0` 로 잡았다. `requestSummaries.durationP50` 과 같은 정의다.
7. **정렬 동률**: 규칙·첫 케이스·첫 표기까지 같으면 내부 요청 키(원문 URL + 본문 해시)로 가른다. 출력하지 않는다.
   표기는 같고 원문 URL 이 다른 (a) 진단 둘에서만 쓰인다.
8. **`dependency` 집계 범위**: ok 반복만 더한다(통계와 같은 기준).
9. **pred 판정 생략**: 순차가 아니고 먼저 끝나지도 않은 쌍은 어떤 값에도 쓰이지 않아 `judge` 를 부르지 않는다. 결과는 같다.
10. **자기 요청 반향 검사**: URL 과 요청 본문을 따로 검사한다. 둘을 이어 붙이면 경계를 걸친 토큰이 거짓으로 빠질 수 있어서다.
