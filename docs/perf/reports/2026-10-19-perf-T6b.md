## 임의로 판단한 부분

1. **서버 명령의 node**: 계획 §11.2 는 `env … node <serial-server.mjs>` 인데 `node` 대신 `process.execPath`(절대 경로)를 넘겼다. `env` 가 PATH 에서
   다른 Node 를 고르면 테스트 러너와 버전이 갈릴 수 있어서다. 도그푸딩도 같은 이유로 `process.execPath` 다. 다른 cli e2e(`optimize-e2e.test.ts`)의 관례와 같다.
2. **기준선 왕복의 범위**: `--tool` 로 좁히지 않고 픽스처 명세의 측정 대상 케이스 전부로 돌렸다. 설계 §1.3 의 문장이 명세 전체 실행이라서다.
   요청 수는 코드가 정하므로(루프백 `/flaky` 의 429·200 짝도 호출마다 짝으로 맞는다) 두 번째 실행의 종료 코드 0 이 흔들리지 않는다고 봤다.
3. **--json 테스트**: 실행 시간을 줄이려고 `--tool serial` 로 좁혔다. 진행 문장이 `케이스 1개 × 5회`·`호출 5회` 로 정확히 단언된다.
4. **관측 없음의 추가 단언**: `serial` 의 `total.p50 ≥ DELAY_MS × 2` 를 더했다. 관측이 끊겨도 응답 시간은 남는다는 설계 §1.3 문장을 수치로 본다.
5. **도그푸딩의 `n > 0`**: `n` 이 0 인 케이스는 `requests` 가 없어 `requests.p50 === 0` 단언이 비어 버리므로 함께 단언했다.
6. **dist 단계의 래퍼**: 서버를 기존 `stdio-server-wrapper.mjs` 로 감싸 PID 파일로 종료를 확인했다. 래퍼는 서버를 같은 프로세스에서 import 하므로
   프리로드가 실리는 프로세스는 래퍼 자신이다.
7. **`vi.mock`**: `optimize-e2e.test.ts` 처럼 `@mcpeak/core`·`@mcpeak/runner` 를 소스로 돌렸다. `@mcpeak/perf` 는 vitest 별칭이 소스로 잇는다.

## 남은 위험

- `parallel` 상한처럼 지연에 기대는 단언은 이 파일에 없다. 기준선 왕복 2회차의 0 은 서버 안 p50 이 `기준×1.5+20ms` 안이어야 하는데,
  루프백 픽스처의 서버 안 시간이 수 ms 라 바닥 20ms 가 덮는다. 부하가 큰 CI 에서 서버 안 시간이 20ms 넘게 튀면 2 가 날 수 있다.
- 한 실행이 약 5초, 파일 전체가 약 21초다. e2e 갈래는 직렬이라 전체 테스트 시간에 그만큼 더해진다.
