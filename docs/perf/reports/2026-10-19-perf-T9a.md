## 임의로 판단한 것

1. **breaker 사본을 그대로 쓰지 않았다.** `preload2.mjs` 의 undici 오류 처리 패치는 node:http 의 `request.error` 구독에
   들어가 있어 `parentFetch` 가 없는 상태로 동작하지 않는다. 본문 오류는 원본 reader 의 `read()` 가 던지는 것으로
   잡히므로 그 경로를 따로 두지 않았다. 원본 reader 는 첫 `pull` 에서 잡아, 감싸기가 실패해도 원본이 잠기지 않게 했다.
2. **cancel 의 끝 줄에 `error` 를 넣지 않았다.** 설계 §4.3 fetch 3항은 "그 시각을 tEnd, bodyEnd: false" 만 말한다.
   breaker 사본은 `error: "cancelled"` 를 넣었다.
3. **trailers 기록은 Map 에 두고 `FinalizationRegistry` 로 수거 때 지운다.** 작은 본문은 trailers 가 fetch 가 응답을
   돌려주기 전에 온다(아래 위험 1). 그래서 등록 시점을 fetch 쪽에 맞출 수 없고, 서버가 끝내 안 읽는 응답의 기록이
   남지 않게 하려면 수거 시점이 필요했다.
4. **undici 직접 요청 시험은 fetch 안 undici 줄로 했다.** 저장소에 `undici` 패키지가 없고(`undici-types` 만 있다) 의존성
   추가는 금지다. 같은 `undici:request:headers` 구독이 두 경우를 함께 처리하므로 fetch 안 undici 줄의 end 에 status 가
   없음을 단언했다.
5. **배압 판정 기준은 전체의 1/4.** 실측 0.85MB / 50MB 라 여유가 크다. RSS 는 쓰지 않았다.
6. **cancel 시한 1초는 자식 안에서 잰다.** 자식이 `Promise.race` 로 1초를 넘기면 `timeout` 을 내고, 끝없는 스트림에 묶이지
   않게 `process.exit(0)` 으로 끝낸다.

## 남은 위험

1. **작은 본문에서 fetch 끝 줄의 `tEnd` 가 `tHeaders` 보다 앞설 수 있다.** 위 추가 확인에서 `tHeaders 1792397782278.03`,
   `tEnd 1792397782277.74`(0.3ms 앞섬). undici 가 헤더와 본문을 한 번에 받아 trailers 를 내고 난 뒤에 fetch 의
   `await` 가 돌아오기 때문이다. 사양(`tEnd` 는 trailers 시각)대로 두었다. `decompose` 의 구간은 `[t0, tEnd]` 라 길이는
   맞지만 `tEnd − tHeaders` 를 쓰는 소비자가 있으면 음수를 본다. 설계에 `tEnd ≥ tHeaders` 같은 불변식이 필요한지
   오케스트레이터가 판단해야 한다.
2. 서버가 감싼 응답에 `Object.defineProperty` 로 옮긴 `url`·`redirected`·`type` 은 원래 프로토타입 getter 가 아닌 자기
   속성이다. `Object.keys(res)` 나 JSON 직렬화에 세 키가 보인다.
3. 감싼 응답의 `headers` 는 새 `Headers` 다. 원본 응답의 headers 가 불변(immutable guard)이던 것과 달리 서버가 고칠 수
   있다.
4. worker 시험은 Node 24.14 에서만 돌렸다. Node 22.18 에서 `NODE_OPTIONS --import` 가 worker 에 실리는지는 CI 에서 본다.
