## 사양 2: 의존 판정의 반복 계산 (최종 리뷰 🟡)

원인: `rules.ts` 는 순차 요청마다 앞선 모든 요청과 `judge` 를 부른다. 기존 `judge` 는 응답 본문 토큰만 캐시했고, 쌍마다
(1) earlier 의 출력 토큰 전부를 호출 입력·earlier URL·earlier 요청 본문에 대해 다시 걸러 냈고, (2) later 의 입력 문자열을
다시 만들어 토큰마다 훑었다. 요청 본문이 크면 둘 다 본문 길이 × 토큰 수 × 쌍 수다.

바꾼 것(`dependency.ts` 만, export 시그니처 그대로):

1. `outputsOf`: earlier 마다 걸러 낸 출력 토큰 목록을 `WeakMap` 에 한 번만 계산한다. 입력 반향 제외가 호출 입력에 달려 있어
   `JSON.stringify(input)` 을 함께 두고, 다르면 다시 계산한다. 순서(본문 토큰, Location)와 제외 규칙은 그대로다.
2. `inputsOf`: later 마다 입력 문자열과 그 안의 모든 4자 조각 집합을 `WeakMap` 에 한 번만 만든다.
3. `contains`: 토큰의 첫 4자와 끝 4자가 둘 다 입력의 조각이 아니면 훑지 않고 거짓, 아니면 `includes` 로 확인한다.
   들어 있으려면 두 조각이 반드시 입력에 있어야 하므로 거르기만 하고 답을 바꾸지 않는다. 4자보다 짧은 토큰(짧은 Location)은 바로 `includes` 다.

1 만으로는 효과가 절반 정도라고 봤다. 남는 비용이 later 쪽에서 쌍마다 본문을 훑는 것이기 때문이다. 그래서 같은 파일 안에서 2·3 을 더했다.

## 임의로 판단한 부분

1. **later 쪽 조각 거르기**: 지시는 earlier 쪽 캐시였다. 그것만으로는 later 입력을 쌍마다 훑는 비용이 남아 `dependency.ts` 안에 2·3 을 더했다.
   조각 길이 4 는 JSON 토큰의 최소 길이와 같게 했다.
2. **순환 cause 의 답**: 이미 본 Error 를 다시 만나는 자리에서 멈추고, 그 직전(마지막으로 새로 본 Error)을 가장 안쪽으로 본다.
3. **Error 가 아닌 cause**: 거기서 멈추고 그 앞 Error 의 문장을 쓴다(사양의 "cause 가 Error 인 동안").
4. **비교 스크립트**: `old-dependency.ts`(BASE)와 `new-dependency.ts` 사본을 스크래치패드에 두고 `node --experimental-strip-types` 로 돌렸다. 커밋하지 않는다.

## 남은 위험

- later 마다 입력 길이만큼의 4자 조각 집합을 메모리에 둔다(요청 본문 60KB 면 최대 약 6만 개). 분석이 끝나고 요청 객체가
  버려지면 함께 사라지지만, 요청이 매우 많고 본문이 큰 실행에서는 분석 중 메모리가 그만큼 는다.
- 출력 토큰 수 × 쌍 수의 조각 조회는 남는다. N=80 에 2.6초로 N 의 제곱에 가깝게 는다. 진짜 상한을 바꾸려면 출력 토큰 전체를 한 번에
  찾는 다중 패턴 탐색이 필요한데 이번 범위 밖이다.
