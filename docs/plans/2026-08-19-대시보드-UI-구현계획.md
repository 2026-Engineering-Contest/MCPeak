## 1. 기반 계획과의 관계

- 이 계획은 **기반 계획의 Task T4(화면 5개)를 대체한다.** 기반 계획의 T4는 실행하지
  않는다. T0~T3, T5는 기반 계획 그대로다.
- 선행 조건: 기반 계획 Wave 0(T0)과 터미널 B의 **T3**(프론트 스캐폴드,
  `web/src/api.ts`·`web/src/run-stream.ts`·해시 라우팅 골격)이 main에 통합돼 있어야 한다.
  이 계획의 기점 커밋은 T3 통합 커밋이다.
- 기반 계획 T5의 E2E는 API만 관통하므로 이 계획의 영향을 받지 않는다. T4 완료를 전제하던
  `pnpm --filter @ohmymcp-hsu/dashboard build`의 `dist/web/index.html` 생성 확인은 이
  계획의 U4 완료 후로 옮겨진다.
- 의존성 추가 없음. 기반 계획 §3(React, Vite, Tailwind v4, testing-library, jsdom)으로
  전부 충당한다.

## 2. 목표 / 비범위 / 완료 조건

**목표**

1. UI 설계의 화면 5종(Home, RunView, Generate 4단계 마법사, Cassettes, RepairReview)을
   구현한다. 사이드바 라벨은 영어(Home, Runs, Generate, Cassettes, Repair)만 쓴다.

### 4-2. `web/src/theme.ts` (U0 신규, 전량)

```ts
export type ThemeChoice = "light" | "dark" | "system";

const STORAGE_KEY = "ohmymcp-theme";

/** 저장된 선택을 읽는다. 없거나 알 수 없는 값이면 "system". */
export function getThemeChoice(storage: Pick<Storage, "getItem">): ThemeChoice {
  const raw = storage.getItem(STORAGE_KEY);
  return raw === "light" || raw === "dark" ? raw : "system";
}

/**
 * 선택을 적용하고 저장한다. "system"은 data-theme 속성과 저장값을 제거해
 * prefers-color-scheme에 위임한다(theme.css의 media 블록이 받는다).
 */
export function applyThemeChoice(
  choice: ThemeChoice,
  root: Pick<HTMLElement, "setAttribute" | "removeAttribute">,
  storage: Pick<Storage, "setItem" | "removeItem">,
): void {
  if (choice === "system") {
    root.removeAttribute("data-theme");
    storage.removeItem(STORAGE_KEY);
    return;
  }
  root.setAttribute("data-theme", choice);
  storage.setItem(STORAGE_KEY, choice);
}
```

`main.tsx`는 렌더 전에 `applyThemeChoice(getThemeChoice(localStorage), document.documentElement, localStorage)`
를 1회 호출한다(첫 페인트 전 적용, 깜빡임 방지).

### 4-4. `web/src/generate/build-argv.ts` (U3 신규): 폼 → argv 계약

폼 상태 타입과 매핑 규칙을 여기 고정한다. `parseGenerateCommand`
(`packages/cli/src/generate-command.ts`)의 검증 규칙과 어긋나면 대시보드만 다른 제품이
되므로, 이 표가 곧 사양이고 테스트가 이 표를 전량 단언한다.

```ts
export interface GenerateForm {
  readonly command: string;        // 1단계에서 조립된 실행 명령("직접 입력" 포함)
  readonly args: readonly string[];
  readonly suiteId: string;
  readonly suiteName: string;
  readonly outPath: string;
  readonly force: boolean;
  readonly mode: "ai" | "baseline";
  readonly provider: "claude" | "codex";
  readonly model: string;          // 빈 문자열 = 미지정
  readonly dryRun: boolean;        // 기본 true
  readonly repair: boolean;        // 기본 true
  readonly cassettePath: string;   // 빈 문자열 = 녹화 없음
  readonly record: boolean;
  readonly resetCmd: string;       // 빈 문자열 = 미지정
}

/** 위반 시 한국어 메시지로 throw. UI는 이 함수를 단계 검증에도 재사용한다. */
export function buildGenerateArgv(form: GenerateForm): readonly string[];
```

argv 순서는 아래로 **고정**한다(같은 폼이면 항상 같은 배열, 결정론).

| 순서 | 포함 조건 | 산출 |
|---|---|---|
| 1 | 항상 | `--command`, `command` |
| 2 | `args` 각 원소마다 | `--arg`, `<원소>` |
| 3 | 항상 | `--suite-id`, `suiteId` |
| 4 | 항상 | `--name`, `suiteName` |
| 5 | 항상 | `--out`, `outPath` |
| 6 | `force` | `--force` |
| 7 | `mode === "baseline"` | `--baseline-only` (이때 provider·model은 넣지 않는다) |
| 8 | `mode === "ai"` | `--provider`, `provider` |
| 9 | `mode === "ai"` 이고 `model !== ""` | `--model`, `model` |
| 10 | `!dryRun` | `--no-dry-run` |
| 11 | `!repair` | `--no-repair` |
| 12 | `cassettePath !== ""` | `--cassette`, `cassettePath` |
| 13 | `record` | `--record` |
| 14 | `resetCmd !== ""` | `--reset-cmd`, `resetCmd` |

불변식(위반 시 throw, CLI `parseGenerateCommand`의 오류와 동일 조건):

- `!dryRun && !repair`: "시험 실행과 자동 교정을 동시에 끌 수 없습니다."
- `!dryRun && cassettePath !== ""`: "시험 실행을 끄면 카세트를 녹화할 수 없습니다."
- `!dryRun && resetCmd !== ""`: "시험 실행을 끄면 초기화 명령을 쓸 수 없습니다."
- `record && cassettePath === ""`: "재녹화는 카세트 저장 위치가 있어야 합니다."
- `command`·`suiteId`·`suiteName`·`outPath` 중 빈 값: "<필드>를 입력하세요."

UI는 같은 조건을 컨트롤 비활성으로 선반영한다(UI 설계 §5-3): 시험 실행 토글을 끄면
4단계의 카세트·초기화 명령 입력 비활성, 재녹화 체크는 카세트 경로가 있을 때만 활성,
시험 실행·자동 교정 동시 끄기는 나중에 끄려는 토글을 비활성.
