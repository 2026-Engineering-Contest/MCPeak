# 대시보드 repair 번들 자동 관리 구현계획 (2026-08-25)

참조 문서: `docs/2026-08-25-대시보드-repair-번들-자동-관리-설계.md`(이하 "설계"), ADR-0080,
`docs/2026-08-25-대시보드-홈-실행-폼-설계.md`(홈 설계).

> **실행 방식:** 사용자 지시로 오케스트레이터 세션이 직접 구현한다(서브에이전트 위임 없음).
> 전부 `packages/dashboard/**` 안이고 태스크 간 파일이 겹치지 않아 터미널 1개, 직렬이다.
> 아래 §8 의 프롬프트는 다른 세션에 넘겨야 할 때를 위해 남긴다.

## 1. 목표 / 비범위 / 완료 조건

**목표** (설계 §2 그대로)

1. 홈에서 시작한 test 실행이 실패하면 번들이 이미 있다.
2. 실행 뷰의 `repair 시작` 폼에 번들 경로가 채워져 있다.
3. 번들 옵션 없이 시작된 run 에서는 `repair 시작` 대신 이유를 말한다.
4. `.mcpeak/` 산출물이 사용자 저장소에 커밋되지 않는다.

**비범위** (설계 §3 그대로): CLI 의 `mkdir -p`, 번들 파일 존재 확인, 재실행 버튼, 번들
이력, Generate·RepairReview 화면.

**완료 조건**

- `pnpm --filter @mcpeak/dashboard test` 전부 통과. `pnpm typecheck --force` 통과하며
  `Cached: 0 cached`. `pnpm lint` 통과.
- 설계 §6 의 계약(관리 경로 규칙, `RunSummary.argv`, `ensureRepairBundleDir` 동작, 안내
  문장)이 한 글자도 다르지 않다.
- `build-test-argv.test.ts` 가 **수정 없이** 통과한다(`buildTestArgv` 불변의 증거).
- 빌드 산출물로 대시보드를 띄워 실제 확인: 홈 실행 → 실패 → `repair 시작` 폼에 경로가
  채워져 있고 `.mcpeak/repair/<...>.repair-bundle.json` 과 `.mcpeak/.gitignore` 가 있다.
  `git status --short` 에 `.mcpeak` 이 안 뜬다.

## 3. 공유 계약

설계 §6 이 전량이다. 복제하지 않는다. §6-1 관리 경로 함수 셋, §6-2 `RunSummary.argv` 와
`RunRegistry.start` 시그니처, §6-3 `ensureRepairBundleDir` 와 500 문장, §6-4 문자 규칙.

## 4. 태스크

### Task R0 — 서버: argv 보관과 디렉터리 준비

모델: 표준(직접 구현). 사양: 설계 §6-2, §6-3.

- `RunSummary` 에 `argv` 추가. `RunRegistry.start(flow, argv, execute)`. `RunRecord` 가
  보관.
- `files.ts` 에 `REPAIR_BUNDLE_DIR`, `ensureRepairBundleDir(root)`. `mkdir` 은
  `{ recursive: true }`. `.gitignore` 는 `writeFile` 에 `flag: "wx"` 로 써서 있으면 건드리지
  않는다(`EEXIST` 는 삼킨다, 그 밖은 던진다).
- `routes.ts` `handleStartRun`: `flow === "test"` 면 `registry.start` 앞에서
  `ensureRepairBundleDir(options.root)`. 실패 시 설계 §6-3 의 500.

테스트 케이스는 설계 §7 의 `tests/run-registry.test.ts`, `tests/routes.test.ts`,
`tests/files.test.ts` 항목 전량. `routes.test.ts` 의 기존 `POST /api/runs가 runId를 주고
events가 스트림된다` 는 test flow 라 `.mcpeak` 이 생기지만 단언은 손대지 않는다.

### Task R1 — 프론트: 관리 경로, 미리 채움, 안내

모델: 상위(직접 구현). 사유: 안내 문장과 "모르면 모른다" 판정이 이 화면의 실패 메시지다.
사양: 설계 §5 전부, §6-1.

- `repair-bundle-path.ts` 신규. 설계 §6-1·§6-2 의 세 함수와 상수.
- `Home.tsx` `argvResult`: `options` 대신 `{ ...options, repairBundlePath:
  effectiveRepairBundlePath(suitePath, options.repairBundlePath) }`. `saveLastRun` 은 원래
  `options`.
- `TestOptionsPanel.tsx`: `Repair 번들` 칸 placeholder 와 설명 문장(설계 §5-1). placeholder
  에 관리 경로를 넣으려면 스위트 경로가 필요하므로 props 에 `suitePath: string` 을 더한다.
- `RunView.tsx` `RunStreamPanel`: `useRunEvents` 가 주는 것에 argv 가 없으면 `GET
  /api/runs/:id` 로 `RunSummary` 를 한 번 읽는다. `run-stream.ts` 를 고치지 않는다(파일
  목록 밖). 읽은 `argv` 로 `repairBundlePathOf` 를 구해 `bundlePath` 초기값으로 넣는다.
  세 상태(§5-3): 있음 → 채워진 폼, 없음 → 안내 한 줄, 모름 → 아무것도 없음.

테스트 케이스는 설계 §7 의 `web/tests/*` 항목 전량.

### Task R2 — 문서 표시와 게이트

- 홈 설계 문서 머리에 한 줄: `§2 목표 4 와 §3 비범위 세 번째 항목은
  docs/2026-08-25-대시보드-repair-번들-자동-관리-설계.md 가 덮어쓴다(ADR-0080).`
- `pnpm build --force`, `pnpm --filter @mcpeak/dashboard test`, `pnpm typecheck --force`
  (`Cached: 0 cached`), `pnpm lint`.
- 빌드 산출물로 대시보드를 띄워 §1 완료 조건의 실환경 확인. 통과한 run 의 출력 끝에
  `repair 번들: 실패한 케이스가 없어 파일을 만들지 않았습니다.` 가 있는지도 본다.
