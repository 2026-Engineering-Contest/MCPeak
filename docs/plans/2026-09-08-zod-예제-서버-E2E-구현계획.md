# zod 예제 서버와 실서버 E2E 구현계획 (2026-09-08)

참조 문서: `docs/2026-09-08-zod-예제-서버-E2E-설계.md`(이하 "설계"), 이슈 #407,
ADR-0004 · ADR-0036 · ADR-0086 · ADR-0087, `docs/2026-09-08-generate-스키마-키워드-확장-설계.md`,
본보기 E2E `packages/cli/tests/generate-integration-e2e.test.ts`.

> **실행 방식:** 터미널 세션은 오케스트레이터이며 태스크마다 서브에이전트를 스폰해 구현시키고
> 사이사이 리뷰한다(테스트 통과 + 파일 소유권 준수 + 설계 §5.1 서버 코드·§6 단언값 일치). 직접
> 구현하지 않는다. 규약은 `.claude/conventions/plan.md` 와 `.claude/conventions/execution.md` 다.

## 전역 제약

프로젝트 지침과 설계에서 그대로 옮긴 것이다. 모든 태스크에 암묵적으로 포함된다.

- **`core/src/types.ts` 의 `McpClient` · `ToolResult` 는 동결이다.** 건드리지 않는다.
- **다른 오너의 패키지를 수정하지 않는다.** 이 계획은 `examples/zod-notes-server/**`(신규),
  `packages/cli/tests/zod-notes-server-e2e.test.ts`(신규), `examples/README.md`, `docs/adoption.md`,
  `docs/adr/`, `.changeset/`, `pnpm-lock.yaml`(`pnpm install` 결과만) 만 쓴다. `packages/*/src`
  전부와 `packages/generate/tests/**` 는 읽기 전용이다. 실측이 설계 §6 의 값과 다르면 생성기·러너를
  고치는 게 아니라 `BLOCKED` 로 보고한다.
- **의존 방향은 단방향이다.** `cli` → `runner`/`generate`/`record`/`mock` → `core`. E2E 는 `core`
  의 `connectStdio`, `runner` 의 `deriveContractAxes`, `generate` 의 고정 파일(읽기)만 쓴다.
- **`@modelcontextprotocol/sdk` 는 1.x 고정(`catalog:`).** 새 의존성은 예제 패키지의 `zod@4.4.3`
  정확 고정 하나뿐이다(설계 §5.3). `packages/*` 에는 어떤 의존성도 추가하지 않는다.
- **커밋·푸시는 사람이 한다.** 서브에이전트는 git 명령을 실행하지 않는다. `pnpm install` 은 실행한다
  (락파일 갱신이 산출물이다).
- **결정론성.** 서버는 고정 데이터만 쓰고 저장하지 않는다. 타임스탬프·랜덤 금지. E2E 는 같은
  generate 2회의 바이트 동일을 단언한다.
- **실패 메시지가 곧 제품이다.** 서버의 `fail(...)` 문장과 E2E 의 사용자 정의 실패 메시지에 무엇이
  왜 다른지, 어떻게 고치는지가 있어야 한다.
- **실서버 스펙은 `*-e2e.test.ts` 로 짓는다.** 그래야 `vitest.config.ts` 의 `e2e` 프로젝트(직렬)로
  간다. 유닛 갈래에 실프로세스를 넣지 않는다.
- 검증 명령: `pnpm install` · `pnpm build --force` · `pnpm vitest run packages/cli/tests/zod-notes-server-e2e.test.ts`
  · `pnpm test` · `pnpm typecheck --force` · `pnpm lint`.

`.github/pull_request_template.md` 를 따르고 `Closes #407` 을 넣는다. 커밋은 사람이 하며
`feat(cli): zod 예제 서버 실서버 E2E 를 더한다`, `docs(adr): …`, 예제 자체는 scope 없는
`feat(examples): …` 관례(`c54f3a4` 참조)를 따른다. 머지 후 `docs/task-integration-ledger.tsv` 에
SHA 를 적는다. 후속 이슈 둘을 남긴다: weather-server README 의 낡은 문단, CODEOWNERS 의 `examples/`.

## 10. 거짓 신호 점검

| 신호 | 이 계획에서의 함정 | 진실 기준 |
|---|---|---|
| `pnpm test` 녹색 | 새 파일명이 `*-e2e.test.ts` 가 아니면 유닛 갈래에서 병렬로 돌아 가끔 실패하거나, 글롭에 안 걸려 수집 0 | 출력에서 `e2e` 프로젝트 아래 파일명을 확인 |
| E2E 녹색 | `vi.mock` 3줄이 없으면 dist 를 읽는다. dist 가 낡으면 낡은 생성기로 통과한다 | `vi.mock` 존재 + T4 의 `pnpm build --force` 뒤 dist 명령 |
| `rejectionUnverified: 0` | `-32602` 접두를 runner 가 못 읽게 바뀌면 값이 올라간다 | `toEqual` 로 summary 전량 단언(부분 일치 금지) |
| 변이 서버 4건 실패 | 변이가 세 줄보다 많으면 실패가 늘어도 "실패했다" 로 초록 | 실패 id 배열 `toEqual` + `diff` 세 줄 리뷰 |
| 바이트 동일 | 같은 파일을 두 번 읽으면 당연히 같다 | 두 번째 generate 의 `--out` 경로가 다른지 코드 리뷰 |
| `frozen-lockfile` 통과 | 로컬 `pnpm install` 이 다른 미커밋 변경까지 락파일에 실었다 | 락파일 diff 가 새 importer 와 `zod` 해석뿐인지 |
| `typecheck` 녹색 | turbo 캐시 | `--force` 와 `Cached: 0 cached` |
| `listTools` 이름 순서 일치 | SDK 가 등록 순서를 바꾸면 `deriveContractAxes` 합계는 같아도 케이스 순서가 바뀐다 | `EXPECTED_IDS`·`EXPECTED_OPERATIONS` 의 순서 단언 |
