## 전역 제약

모든 태스크에 암묵적으로 포함된다.

- **`core/src/types.ts` 의 `McpClient` · `ToolResult` 는 동결이다.** 건드리지 않는다.
- **의존 방향은 단방향이다.** `dashboard` → `cli` → `runner`/`generate`/`record`/`mock` → `core`.
  역참조와 순환을 만들지 않는다. 이 계획은 새 의존을 하나도 더하지 않는다.
- **`@modelcontextprotocol/sdk` 는 1.x 고정.** 새 의존성을 추가하지 않는다. 설계가 쓰는
  `node:crypto` 는 표준 모듈이다.
- **커밋·푸시는 사람이 한다.** 서브에이전트는 git 명령을 실행하지 않는다(worktree 생성은
  예외이며 1단계에 적힌 한 줄뿐이다).
- **유닛테스트는 인메모리와 `packages/record/tests/fixtures/` 만 쓴다.** `examples/` 의 실제
  서버 프로세스는 띄우지 않는다. E2E 도 픽스처 서버와 인메모리 origin HTTP 서버만 쓴다.
- **네트워크를 타지 않는다.** 실제 `npx` 를 테스트에서 부르지 않는다. 레지스트리와 캐시에
  의존하게 되기 때문이다. 실제 `npx` 확인은 §8 통합 게이트에서 오케스트레이터가 한 번만 한다.
- **결정론성.** 타임스탬프·랜덤·실행 순서에 의존하는 단언을 넣지 않는다. 기록자 식별자는
  실행마다 다른 값이므로 **단언 대상이 아니다.** 단언은 "두 식별자가 다르다" 까지이며 값 자체를
  고정하지 않는다.
- **실패 메시지가 곧 제품이다.** 설계 §4.4 와 §5 의 문자열이 정본이다. 한 글자도 바꾸지 않는다.
- **`packages/*` 를 건드린 브랜치는 그 브랜치에서 changeset 을 새로 만든다.** `.changeset/` 에
  이미 쌓인 파일은 계산에 안 들어간다(ADR-0063).
- 검증 명령: `pnpm install` · `pnpm build --force` · `pnpm test` · `pnpm typecheck --force` ·
  `pnpm lint`.

## 1. 목표 / 비범위 / 완료 조건

**목표** (설계 §2): 중간에 Node 런처가 끼어도 진짜 서버의 외부 호출이 녹화된다. 그러면서 세션
하나에 기록하는 프로세스는 여전히 하나다.

**비범위** (설계 §3): `npx` 를 우리가 미리 해석하는 것, 범위 밖 호출 관측의 런처 환경 정확도,
대시보드 `npx 패키지` 고지, 세션 저장 형식과 `matchKey` 규칙, 실측 문서의 §2 외 나머지 절.

**완료 조건과 대응 태스크**

| 설계 §2 완료 조건 | 태스크 |
|---|---|
| 1 런처를 거친 서버의 외부 호출이 녹화된다 | T1(구현) · T2(증거) |
| 2 한 세션의 기록자는 하나다 | T1 |
| 3 기록자가 아닌 호출이 숫자로 남는다 | T1 |
| 4 재생에서 기록자가 아닌 프로세스가 네트워크로 안 나간다 | T1(구현) · T2(증거) |
| 5 0건 알림이 기록자 경합을 지목한다 | T3 |
| 6 기존 녹화·재생 동작이 그대로다 | T1 · T2 · T3 각각의 회귀 + T5 |
| 7 빌드·테스트·타입체크·린트 | T5 통합 게이트 |

다른 웨이브에 있다. 한 브랜치가 두 패키지를 건드리는 자리는 없다.

## 3. 공유 계약

설계 §5 가 전량이다. 이 계획은 복제하지 않는다. 아래 둘만 계획서에 박는다. 두 터미널이 서로
다른 웨이브에서 이 이름을 쓰기 때문이다.

**요약 필드 이름과 의미** (설계 §4.3 · §5.6)

```ts
readonly otherProcessCalls?: number;
```

`undefined` 와 `0` 은 같은 뜻이다. Coordinator 가 자기 거절을 직접 센 값이라 "못 셌음" 갈래가
없다. `outOfScope` 와 다르며, 그 차이가 이 필드에 달린 유일한 판단이다. CLI 는
`summary.otherProcessCalls ?? 0` 으로 읽는다.

**오류 코드 문자열**

```
WRITER_CONFLICT
```

Coordinator 가 409 로 내보내고 자식 클라이언트가 `error.code` 로 분기한다. 두 자리가 같은
문자열을 써야 하며, 문자열이 어긋나면 **테스트가 아니라 실사용에서만 드러난다.** 자식과 부모
사이에는 `instanceof` 가 없고 코드 문자열만 건너가기 때문이다(`errors.mjs` 의 주석).

## 4. 의존성 그래프와 웨이브

```
Wave 1 (병렬 2 터미널)
  터미널 A: T1 → T2      (record)
  터미널 B: T4           (ADR)

Wave 2 (직렬, A 머지 뒤)
  터미널 C: T3           (cli)   ← record 의 타입이 main 에 있어야 typecheck 가 산다

Wave 3 (직렬, 오케스트레이터)
  T5 통합 게이트: A 머지 → B 머지 → C 머지 → 전량 검증 → 실제 npx 확인
```

Wave 1 의 두 터미널은 쓰는 파일이 완전히 분리돼 있다. 공유 계약은 설계 문서에 고정돼 있어
서로를 기다릴 이유가 없다.

   Node 프로세스라는 것도 함께 보인다. 런처와 서버의 체인이 실제로 그 모양이다.)

   남은 확인은 CLI 를 통과시키는 것이다. 저장소 밖 임시 디렉터리에서
   `packages/cli/dist/cli.mjs` 를 직접 실행한다. 캐시는 위와 같이 임시 디렉터리로 준다.
   사용자의 npm 캐시를 지우지 않는다.

   ```sh
   node <저장소>/packages/cli/dist/cli.mjs test <명세> \
     --command env --arg "MEMORY_FILE_PATH=<임시경로>/mem-sandbox.jsonl" \
     --arg npx --arg -y --arg @modelcontextprotocol/server-memory \
     --record-session <임시경로>/a.json
   ```

   명령 형태는 `docs/2026-09-10-데모-리허설-런북.md` 의 `server-memory` 절과 같다. `env` 로
   감싸는 것은 샌드박스를 주기 위한 것이고, `env` 는 Node 가 아니라서 체인에 영향을 주지 않는다.

   판정은 stderr 의 알림 문장이다.

   | 나오면 | 뜻 |
   |---|---|
   | `서버가 외부 API를 호출했다면 지원 범위를 벗어났는지 확인하세요` | `otherProcessCalls` 가 0이다. **통과** |
   | `다른 프로세스가 먼저 이 세션의 기록을 시작해` | 런처가 임자를 가로챘다. §8.1 이 현실이 된 것이다 |

   `server-memory` 는 외부 API 를 부르지 않으므로 `interactionCount` 는 0이 정상이고 0건 알림이
   나오는 것 자체는 결함이 아니다. 이 단계가 보는 것은 **어느 0건 문장이 나오는가**다. 외부
   호출이 런처를 거쳐 실제로 녹화되는지는 T2 의 E2E 가 판정한다.

   경합 문장이 나오면 머지를 되돌리지 않는다. 화면이 이유를 말하게 된 것 자체가 개선이다.
   그 사실을 실측 문서와 후속 이슈에 적는다.

7. 통합 SHA 를 `docs/task-integration-ledger.tsv` 에 기록하고 별도 문서 커밋으로 보존한다.
8. `docs/2026-09-11-공개서버-직접조작-데모-실측-문제.md` §2 에 처리 결과를 한 문단으로 적는다.
   §1 이 `**(2026-09-11 갱신)**` 으로 적은 것과 같은 형식이다. 원래 관측 문장은 지우지 않는다.

어느 단계라도 실패하면 후속 머지·푸시를 멈추고, 실패한 태스크와 SHA 와 검증 출력을 포함해
`BLOCKED` 로 보고한다.

## 9. 자체 검토

- 설계 §2 의 완료 조건 일곱이 전부 §1 의 표에서 태스크에 대응한다.
- Wave 1 두 터미널의 쓰기 파일이 겹치지 않는다(§2). T4 는 `docs/adr/` 만 쓰고 T1 은
  `packages/record/` 와 `.changeset/` 만 쓴다. `.changeset/` 파일명은 셋 다 다르다.
- 패키지 간 순서 제약은 하나뿐이고(T3 은 T1 뒤) §4 의 웨이브가 그것을 지킨다. 한 브랜치가
  두 패키지를 건드리는 자리는 없다.
- 각 스폰에 모델과 추론 수준이 있다. 상위 모델은 결정론성과 프로토콜 판단이 걸린 T1 · T2 에만
  붙였고 사유를 §5 에 적었다.
- 모든 테스트가 인메모리와 `packages/record/tests/fixtures/` 만 쓴다. 실제 `npx` 와 네트워크는
  §8 의 직렬 단계 하나뿐이고 오케스트레이터가 직접 한다.
- 태스크마다 표적 검증과 전체 회귀 명령이 있고, §8 에 최종 리뷰 게이트가 있다.
- 판단이 갈리는 자리(소비 시점, 판정 위치, 오류 경로, 문안 갈래 순서, 단언 전량)는 설계 문서에
  코드로 전량 적혀 있고, §8.2 가 그중 셋을 사람이 눈으로 보게 만든다.
- `packages/*` 를 건드리는 브랜치 둘에 각각 changeset 이 있고, 안 건드리는 T4 에는 없다.
- `pnpm build --force` 가 터미널 C 의 1단계와 §8 의 5번에 모두 있다. 패키지 간 타입 계약이
  바뀌는 변경이라 낡은 `dist/*.d.ts` 로 초록이 나오는 갈래를 양쪽에서 막는다.
