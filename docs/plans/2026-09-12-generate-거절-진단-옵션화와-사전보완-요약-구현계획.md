## 1. 목표 / 비범위 / 완료 조건

**목표** (설계 §2): 시험 실행 뒤 AI 에 가는 것은 실패한 케이스뿐이다. 통과한 거절 케이스의 근거
확인은 `--diagnose-rejections` 를 켤 때만 한다. 사전보완 요약이 네 갈래를 나눠 말한다.

**비범위** (설계 §3): 화이트리스트 형식 판정, `test` 요약 문장, 대시보드 토글, 진단 계약 변경,

## 3. 공유 계약

설계 §5 가 전량이다. 패키지 경계를 넘는 것은 하나다.

**`RejectionBasis` 의 뜻.** `notApplicable` 에 "거절을 기대했지만 거절이 오지 않음" 이 더해진다.
값의 종류는 늘지 않는다. cli 는 이 값을 읽되 뜻에 기대지 않고 `status === "passed"` 로 다시
거른다.

## 7. T4 통합 게이트 (오케스트레이터 직접)

1. 세 브랜치의 diff 가 §2 의 파일 소유권 표 안에만 있는지 확인한다.
2. 설계 §5 와 실제 코드를 대조한다. 특히 넷을 눈으로 본다.
   - `classifyRejectionBasis` 에서 `!rejected` 검사가 `bodyText === null` 검사 **앞**인가
   - executor 가 `rejected` 를 `result.result.isError === true` 로 넘기고, 거짓이면
     `rejectionBody` 를 싣지 않는가
   - generate 의 `unverified` 필터가 `status === "passed"` 를 포함하는가
   - `renderPreFillSummary` 의 미채택 수가 `notAdopted - held` 인가
3. runner → cli → docs 순으로 머지한다.
4. 통합 브랜치에서 `pnpm install` → `pnpm build --force`(`Cached: 0 cached`) → `pnpm test` →
   `pnpm typecheck --force` → `pnpm lint`.
5. **집계 확인.** `examples/live-weather-server` 의 baseline 스위트로
   `mcpeak test … --json` 을 돌려 `summary.rejectionUnverified` 가 41 이고,
   `summarize-text-missing-text` · `lookup-country-enum-code` 의 `rejectionBasis` 가
   `notApplicable` 인지 본다. 이 서버는 네트워크를 타므로 로컬에서만 한다.
6. **실환경 확인은 사람이 한다.** generate 의 승인 화면은 TTY 가 필요하다. 사용자가 대시보드
   (`examples/` 루트, 7392)의 Generate 탭에서 live-weather-server 를 provider 와 함께 생성해
   설계 §7.3 의 판정 셋을 본다. 오케스트레이터는 그 결과를 받아 적는다.
7. 통합 SHA 를 `docs/task-integration-ledger.tsv` 에 기록하고 별도 문서 커밋으로 보존한다.
8. 실측 문서 §4 를 해소로 갱신한다. 설계 §1.3 과 ADR-0098 을 가리킨다.

어느 단계라도 실패하면 멈추고 `BLOCKED` 로 보고한다.

## 8. 자체 검토

- 설계 §2 의 완료 조건 여덟이 전부 §1 표에서 태스크에 대응한다.
- Wave 1 세 세션의 쓰기 파일이 겹치지 않는다.
- 한 브랜치가 두 패키지를 건드리는 자리가 없다. `core` · `generate` 는 아무도 열지 않는다.
- 상위 모델은 화면 문장이 있는 T2 에만 붙였고 사유를 §5 에 적었다.
- 테스트가 인메모리와 픽스처만 쓴다. live-weather-server 를 부르는 것은 §7 의 5·6 뿐이고
  오케스트레이터와 사람이 한다.
- 두 패키지가 같은 케이스를 두 겹으로 거르는 이유(한쪽만 들어가도 화면이 맞아야 한다)를 설계
  §4.1 과 이 계획 §2 에 적었다.
- 세 브랜치 중 `packages/*` 를 건드리는 둘에 changeset 이 있고 docs 만 건드리는 TA 에는 없다.
