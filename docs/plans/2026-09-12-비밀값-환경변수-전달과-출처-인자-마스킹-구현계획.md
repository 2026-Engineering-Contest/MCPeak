# 비밀값 환경변수 전달과 출처 인자 마스킹 구현계획 (2026-09-12)

참조 문서: `docs/2026-09-12-비밀값은-argv-가-아니라-환경변수로-넘기고-출처-인자는-가린다-설계.md`
(이하 "설계"), ADR-0070 · ADR-0085 · ADR-0039 · ADR-0045 · ADR-0041,
`docs/2026-09-11-공개서버-직접조작-데모-실측-문제.md` §3.

> **실행 방식:** 터미널 세션은 오케스트레이터이며 태스크마다 실행 세션에 넘겨 구현시키고
> 사이사이 리뷰한다. 직접 구현하지 않는다. 규약은 `.claude/conventions/plan.md` 와
> `.claude/conventions/execution.md` 다.

기점 커밋: §6 에서 확정한다. 아래 실행 프롬프트의 `<기점SHA>` 는 오케스트레이터가 설계·계획
문서를 커밋한 뒤 그 SHA 로 **전부 치환해서** 넘긴다. 치환하지 않은 프롬프트는 넘기지 않는다.

## 전역 제약

- **패키지 오너 제한은 이 계획에 적용하지 않는다.** 사용자가 2026-09-11 에 풀었고 2026-09-12 에
  다시 확인했다. 다만 이 계획은 태스크마다 패키지를 하나씩 배정한다(T1 cli, T2 record, T3
  dashboard). **자기 태스크의 패키지 밖을 열어야 할 근거가 생기면 고치지 말고 보고한다.** 막기
  위해서가 아니라 병렬 태스크의 쓰기 파일이 겹치지 않게 하기 위해서다.
- **`core/src/types.ts` 의 `McpClient` · `ToolResult` 는 동결이다.** `core` 는 이 계획에서 한
  글자도 바뀌지 않는다. `options.env` 를 얹는 자리가 이미 있다.
- **의존 방향은 단방향이다.** 새 의존을 하나도 더하지 않는다. `record` 의 신규 모듈은 같은
  패키지의 `shared/sensitive-keys.mjs` 만 import 한다.
- **`@modelcontextprotocol/sdk` 는 1.x 고정.** 새 의존성 추가 금지.
- **커밋·푸시는 사람이 한다.** 실행 세션은 git 명령을 실행하지 않는다. 백그라운드 실행, 하위
  에이전트 스폰, 다른 작업자의 변경 되돌리기도 금지다.
- **테스트에 실제 비밀값을 쓰지 않는다.** 픽스처 값은 `sbp_0123456789abcdef0123` 처럼 모양만
  맞춘 가짜다. 테스트 출력에 환경변수 **값**을 찍는 단언을 두지 않는다(설계 §7.2 의
  `env-echo-server` 는 존재 여부와 길이만 돌려준다).
- **네트워크를 타지 않는다.** Supabase 실환경은 §7 의 직렬 단계 하나뿐이고 오케스트레이터가
  직접 한다.
- **`packages/*` 를 건드린 브랜치는 그 브랜치에서 changeset 을 새로 만든다**(ADR-0063).
- 검증: `pnpm install` · `pnpm build --force` · `pnpm test` · `pnpm typecheck --force` ·
  `pnpm lint`. 캐시 줄(`Cached: 0 cached`)을 확인한다.

## 1. 목표 / 비범위 / 완료 조건

**목표** (설계 §2): 비밀값이 argv 를 지나지 않는 통로(`--env <NAME>`, `.mcp.json` env)를
만들고, 그래도 argv 로 들어온 비밀값은 세션에 저장되기 전에 `[redacted]` 로 가린다.

**비범위** (설계 §3): `--env NAME=VALUE`, `.env` 파일, `${VAR:-default}`, 자식 자신의 argv,
본문 마스킹 규칙 변경, 민감 키 스냅샷 version 상향, `repair`.

| 3 비어 있으면 이름만 말한다 | T1 |

## 6. 기점

오케스트레이터가 설계 문서와 이 계획서를 커밋한 SHA 다. 실행 프롬프트의 `<기점SHA>` 를 그
값으로 전부 치환한 뒤 넘긴다.

사람 몫의 사전 조건 확인은 두 줄이다.

```sh
git log --oneline -1     # 기점 SHA 가 설계·계획 문서를 담은 커밋인지
git status --short       # 깨끗한지
```

worktree 생성과 부트스트랩은 **실행 프롬프트 1단계가 한다.** 사람은 프로젝트 루트에서 터미널을
열고 프롬프트를 붙여넣기만 한다.

## 7. T4 통합 게이트 (오케스트레이터 직접)

보고서와 diff 와 테스트 출력을 직접 확인한 뒤에 진행한다. 실행 세션의 "완료" 선언은 단서다.

1. 네 브랜치의 diff 가 §2 의 파일 소유권 표 안에만 있는지 확인한다.
2. 설계 §5 의 코드와 실제 코드를 대조한다. 특히 다섯 자리를 눈으로 본다. **다섯 다 틀려도
   대부분의 테스트는 통과한다.**
   - `openConnection` 의 합성이 `{ ...forwarded, ...options.env }` 순서인가 (배선이 뒤)
   - `redactOriginArgs` 의 R2 가 다음 토큰을 **`-` 로 시작해도** 가리는가
   - `redactOrigin` 이 `store.createSession` **앞**에서 불리는가 (Store 안이 아니다)
   - `resolveCandidateEnv` 가 확장 실패 키를 **빼는가** (빈 문자열로 채우지 않는다)
   - record 의 `REDACTED_ARG` 와 web 의 `REDACTED_ARG` 가 같은 문자열인가
3. record → cli → dashboard → docs 순으로 머지한다.
4. 통합 브랜치에서 `pnpm install` → `pnpm build --force`(`Cached: 0 cached` 확인) →
   `pnpm test` → `pnpm typecheck --force` → `pnpm lint`.
5. **Supabase 실환경 재확인을 직렬로 한다.** 이 계획의 진짜 판정이다. 저장소 밖 임시
   디렉터리에서 `packages/cli/dist/cli.mjs` 로 한다. 실측 §3 프리플라이트 규칙을 따른다. 읽기
   전용(`--read-only`)이고, 쓰는 것은 임시 디렉터리의 세션 파일 하나다.

   토큰은 이 검증만을 위해 새로 발급하고 끝나면 폐기한다.

   ```sh
   read -rs SUPABASE_ACCESS_TOKEN; export SUPABASE_ACCESS_TOKEN
   node <저장소>/packages/cli/dist/cli.mjs test <명세> \
     --command npx --arg -y --arg @supabase/mcp-server-supabase@0.12.0 \
     --arg --read-only --arg --project-ref --arg <ref> \
     --env SUPABASE_ACCESS_TOKEN \
     --record-session ./supabase.session.json
   ```

   판정 셋.
   - 서버가 뜬다(토큰이 환경변수로 닿았다). `ps` 에 토큰이 없다.
   - 세션 파일의 `sessions.args_json` 에 `sbp_` 가 없다. `--project-ref` 와 그 값은 그대로다.
     ```sh
     node -e 'const {DatabaseSync}=require("node:sqlite");const db=new DatabaseSync("supabase.session.json",{readOnly:true});console.log(db.prepare("select command,args_json from sessions").all())'
     ```
     (`node:sqlite` 가 없는 Node 면 `packages/record` 의 `loadSession` 을 `node --input-type=module` 로 부른다.)
   - **대조군.** 같은 명령을 `--env` 대신 `--arg --access-token --arg "$SUPABASE_ACCESS_TOKEN"`
     로 한 번 더 돌려 `args_json` 이 `"--access-token","[redacted]"` 인지 본다. 이 실행은 토큰을
     argv 에 싣는 실행이므로 **검증 뒤 그 토큰을 반드시 폐기한다.** 대조군을 생략하면 R2 가
     실환경에서 동작하는지 못 본다.
6. 대시보드는 `packages/dashboard/dist/dashboard-cli.mjs` 로 띄워 `.mcp.json` 에
   `env: { "SUPABASE_ACCESS_TOKEN": "${SUPABASE_ACCESS_TOKEN}" }` 를 적은 후보를 고르고, 후보
   카드에 `env 1개를 자식에게 넘깁니다: SUPABASE_ACCESS_TOKEN` 이 보이는지, 실행이 되는지,
   브라우저 개발자 도구의 `/api/servers` 응답에 값이 없는지 본다. Replay 탭에서 5 의 대조군
   세션이 펼쳐진 채 `가려졌습니다` 문장을 보이는지 본다.
7. 통합 SHA 를 `docs/task-integration-ledger.tsv` 에 기록하고 별도 문서 커밋으로 보존한다.
8. `docs/2026-09-11-공개서버-직접조작-데모-실측-문제.md` §3 을 해소로 갱신한다. 설계 문서
   §1.2 와 ADR-0097 을 가리킨다. 갱신 문단에는 이 게이트가 실제로 본 값(실행 형태 두 가지와
   `args_json` 결과)을 표로 남긴다.

어느 단계라도 실패하면 멈추고 `BLOCKED` 로 보고한다.

## 8. 자체 검토

- 설계 §2 의 완료 조건 열이 전부 §1 의 표에서 태스크에 대응한다.
- Wave 1 네 세션의 쓰기 파일이 겹치지 않는다. 패키지가 다르고 docs 도 다르다.
- 한 브랜치가 두 패키지를 건드리는 자리가 없다. `core` 는 아무도 열지 않는다.
- 상위 모델은 판단이 걸린 T1 · T2 에만 붙였고 사유를 §5 에 적었다.
- 테스트가 인메모리와 `tests/fixtures/` 만 쓴다. 실제 `npx` · Supabase 는 §7 의 직렬 단계
  하나뿐이고 오케스트레이터가 직접 하며, 토큰은 그 검증만을 위해 발급하고 폐기한다.
- 과잉 마스킹(R2)을 테스트가 "정확한 값" 으로 고정하지 않는다. 설계 §7.3 의 `["--token",
  "--verbose"]` 케이스는 지금 규칙을 고정하는 것이고, 규칙을 바꾸면 그 케이스를 바꾼다는 것을
