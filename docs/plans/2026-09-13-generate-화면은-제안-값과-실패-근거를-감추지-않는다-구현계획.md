## 0. 실행 모델

- 메인 세션은 오케스트레이터다. 스폰, 리뷰, 머지 게이트, 통합 커밋만 한다. 코드를 쓰지 않는다.
- 태스크 실행은 프로젝트 루트에 있는 idle 피어 세션이 맡는다. 터미널 1개 = worktree 1개 =
  브랜치 1개다.
- 커밋·푸시는 사람이 한다. 실행 세션은 git 명령을 실행하지 않는다(worktree 생성은 예외이며
  프롬프트 1단계가 지시한다).

**구현 지시**

1. `dry-run.ts` 의 `DryRunCaseOutcome` 에 §2 의 `operationFailed` 와 `failureLine` 을 더한다.
   `toResult` 에서 채운다.

   ```ts
   const operationFailed = result.operation.status !== "completed";
   ```

   `failureLine` 은 이렇게 고른다. **렌더된 블록에서 고른다. 문장을 새로 만들지 않는다.**

   - `operationFailed` 면 블록의 첫 본문 줄(들여쓰기 4칸을 벗긴 것). 그것이 작업 진단
     `message` 다. 예: `툴 'convert_units' 호출 중 오류가 발생했습니다.`
   - 아니면 블록에서 **실패한 단언**의 줄. 판정은 구조화된 값으로 한다:
     `result.assertions.find((a) => a.status === "failed")` 의 `spec.type` 으로 시작하면서
     `(건너뜀) ` 을 포함하지 않는 첫 본문 줄을 고른다.
   - 고를 것이 없으면 빈 문자열.

   `status === "passed"` 면 블록이 비어 있으므로 자연히 빈 문자열이다.

2. `repair-target.ts` 를 §2 의 `RepairSelection` 반환으로 바꾼다.

   - `failedByIsError` 를 고친다. 지금은 `line.startsWith("isError")` 만 본다. `(건너뜀) ` 이
     들어간 줄은 실패가 아니다. 다만 **텍스트가 아니라 구조로 판정하는 쪽이 낫다**:
     `toTarget` 에 `outcome.operationFailed` 가 이미 오므로, 그것이 참이면 `thrown` 으로 보낸다.
     `failedByIsError` 는 `operationFailed` 가 거짓인 경우에만 불린다. 그래도 방어적으로
     `(건너뜀) ` 을 포함한 줄은 제외하도록 고쳐 둔다.
   - 한 번 순회해 두 배열로 가른다. 앞단 조건(`status !== "passed"`, `callTool`,
     입력 비어 있지 않음, `origin !== "user"`, `!expectsError(spec)`)은 **둘이 공유한다.**
     그 조건을 통과한 뒤 `operationFailed` 면 `thrown`, 아니면 `failedByIsError` 를 보고
     `targets` 다. `failedByIsError` 도 아니면 어느 쪽도 아니다(본문 스키마 불일치 등).
   - `RepairTarget` 에 `failureLine: outcome.failureLine` 을 싣는다.
   - `ThrownCase` 의 `serverMessage` 는 기존 `serverMessageOf` 를 그대로 쓴다.
   - 반환 배열 둘 다 `outcomes` 순서다. 정렬하지 마라.

3. `input-repair.ts`:

   - 상수 `FAILURE_LINE` 을 지운다.
   - 머리줄을 `${HEAD}[${index + 1}/${options.targets.length}] ${target.caseName}\n` 으로 바꾼다.
   - 그 아래 `${BODY}${target.failureLine}\n` 을 찍는다.
   - 그 아래 `target.serverMessage` 의 빈 줄 아닌 각 줄을 `${BODY}→ ${line}\n` 으로 찍는다.
     `serverMessage` 가 비면 아무 줄도 안 찍는다.

   - `askField` 의 두 형식을 설계 §4.5 한 형식으로 합친다.

     ```ts

       io: ReviewIO,
       options: {
         readonly tool: string;
         readonly field: string;
         readonly index: number;
         readonly total: number;
         readonly current: JsonValue;
         readonly proposed: JsonValue | undefined;
         readonly declared: string | undefined;
       },
     ): Promise<JsonValue> => {
       const fallback = options.proposed ?? options.current;
       const parts = [`필드 ${options.index}/${options.total}`];
       if (options.declared !== undefined) parts.push(options.declared);
       if (options.current !== undefined) parts.push(`현재 ${JSON.stringify(options.current)}`);
       parts.push(
         options.proposed === undefined

       );
       const question = `${BODY}${options.tool}.${options.field} (${parts.join(", ")}): `;
       // 이하 루프는 기존과 같다.
     ```

## 8. 머지 게이트

자식의 "완료" 선언은 단서일 뿐이다. 오케스트레이터가 아래를 **직접** 보기 전에는 머지하지 않는다.

1. 변경 diff 전부. 허용 Files 밖 변경이 있으면 되돌린다.
2. 검증 명령을 오케스트레이터가 다시 실행한 출력. 자식이 붙여넣은 로그를 근거로 쓰지 않는다.
3. 검사 대상 파일 수가 0이 아닌지. 특히 `--project web` 갈래.
4. `pnpm typecheck --force` 가 `Cached: 0 cached` 인지.

통과하면 머지하고 통합 SHA 를 `docs/task-integration-ledger.tsv` 에 기록한다. 대장에 없는 결과는
후속 태스크의 선행 근거로 쓰지 않는다. 선행 확인은 브랜치 존재가 아니라 `git cat-file -e` 와
`git merge-base --is-ancestor` 로 한다.

대장 행 이름은 이렇게 쓴다.

```
T1-screen-prefill	<SHA>	2026-09-13
T2-screen-repair	<SHA>	2026-09-13
T3-screen-dashboard	<SHA>	2026-09-13
TA-screen-adr	<SHA>	2026-09-13
```

## 9. 완주 판정

1. 위 네 행이 `docs/task-integration-ledger.tsv` 에 SHA 와 함께 있다.
2. 프로젝트 루트에서 아래가 전부 녹색이다.
   ```sh
   pnpm test
   pnpm typecheck --force
   pnpm lint
   ```
   `pnpm lint` 의 예외는 추적되지 않는 `examples/live-weather-server/server.suite_mcp*.json`
   format 오류 둘뿐이다. 그 밖의 오류가 있으면 완주가 아니다.

   ```sh
   pnpm build --force
   pnpm vitest run packages/cli/tests/generate-integration-e2e.test.ts
   ```
   녹색이어야 하고 수집 파일 수가 1이어야 한다.
4. `live-weather-server` 로 설계 §6 의 완료 조건 3 을 눈으로 확인한다. 오케스트레이터가 직접 한다.

