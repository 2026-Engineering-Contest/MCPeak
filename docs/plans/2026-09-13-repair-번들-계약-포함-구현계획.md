- `packages/generate/tests/diagnosis-prompt.test.ts`

생성:
- `.changeset/<임의이름>.md`

`packages/cli` 는 T2 의 것이다. 한 줄도 고치지 않는다.

**파일 목록이 실제와 다르면 멈추고 보고해라.** 위 경로는 계획 작성 시점의 것이고, 테스트
파일명은 확인하지 않았다. 실제 테스트 파일이 다른 이름이면 그 파일을 쓰고 보고에 적어라.

### 사양

**1) `McpToolContext` 에 `outputSchema` 를 더한다.**

```ts
export interface McpToolContext {
  readonly name: string;
  readonly description?: string;
  readonly inputSchema: unknown;
  /**
   * 서버가 선언한 출력 스키마. 없으면 키를 만들지 않는다.
   *
   * 진단이 "응답이 계약과 다르다" 를 말하려면 그 계약이 요청에 있어야 한다. 빈 객체를
   * 넣으면 "아무 응답이나 허용" 으로 읽히므로 없을 때는 키 자체를 만들지 않는다(이슈 #393).
   */
  readonly outputSchema?: unknown;
}
```

**선택 필드로 둔다.** 여기는 번들 형식이 아니라 요청 타입이고, `authoring` 통로는
`outputSchema` 를 안 싣는다. 필수로 만들면 그쪽이 깨진다.

**2) 마스킹 경로를 확인만 하고 손대지 않는다.**

`packages/generate/src/redaction.ts` 의 `TOOL_CONTRACT_PATHS` 는 지금
`/^\[\d+\]\.name$/` 다. **이것을 고치지 마라.** 고치면 `authoring` 통로의 마스킹 범위가
함께 바뀌고, 그 변화는 이 이슈가 검토한 적이 없다.

`outputSchema` 가 마스킹 대상인지 **보고에 적어라.** 판단은 내가 한다. 판단에 필요한 것은
"`sanitizeRedactable` 이 `tools` 배열의 어느 경로까지 훑는가" 와 "`TOOL_CONTRACT_PATHS` 가
무엇을 가드하는가" 두 가지다. 코드를 읽고 사실만 적어라. 추측하지 마라.

**3) `DiagnosisProcessDiagnostics` 에 `scope` 를 더한다.**

```ts
  /**
   * 이 stderr 가 무엇의 것인지. 지금은 항상 "suite" 다. 프로세스 전체의 꼬리이지
   * 특정 케이스의 것이 아니다.
   *
   * 값이 하나뿐인 유니온으로 둔다. 나중에 케이스별 수집이 생기면 "case" 가 늘고, 그때
   * 낡은 번들은 형식 버전으로 걸린다. 이 키가 없으면 AI 는 범위를 모른 채 읽는다(이슈 #393).
   */
  readonly scope: "suite";
```

**필수 필드다.** 선택으로 두면 안 실은 요청이 조용히 범위 없이 나간다.

**4) 프롬프트에 stderr 읽는 법을 더한다.** 이 태스크의 핵심이다.

`diagnosis-prompt.ts` 에 `CASE_HISTORY_RULE` 과 **같은 방식으로** 상수를 하나 더 만든다.

```ts
/**
 * stderr 읽는 법. `scope` 는 요청에 실려 있는데 뜻이 프롬프트 어디에도 없으면 AI 가
 * 프로세스 전체의 꼬리를 개별 케이스의 원인으로 읽는다. `CASE_HISTORY_RULE` 이 만들어진
 * 이유(#385)와 같은 계열이다(이슈 #393).
 */
const STDERR_SCOPE_RULE =
  "stderr 읽는 법:\nstderr 는 서버 프로세스 전체에서 모은 꼬리다. 특정 케이스가 낸 것이 아니다.\n어느 케이스의 원인이라고 단정하지 않는다. 케이스와 stderr 를 잇는 근거가 따로 없으면 그 연결을 원인 후보로 내지 않는다.\n여러 케이스가 실패했는데 stderr 에 오류가 하나면, 그 하나가 모든 실패의 원인이라고 보지 않는다.";
```

`diagnosisPrompt` 의 배치에 넣는다. **`processDiagnostics` 가 요청에 있을 때만 넣는다.**
stderr 가 없는 요청에 읽는 법을 적으면 없는 것을 말하는 셈이고, 프롬프트가 길어진 만큼
다른 규칙의 비중이 줄어든다.

배치 순서는 `역할 → CASE_HISTORY_RULE → (STDERR_SCOPE_RULE) → caseId 목록 → CASE_ID_RULE →
스키마 → 요청 → untrusted 경고` 다. 규칙끼리 모아 둔다.

**같은 요청이면 항상 같은 문자열이 나와야 한다.** 조건 분기를 넣었으므로 두 갈래 모두에
대해 결정론성 테스트를 쓴다.

### 테스트

```
describe("stderr 읽는 법")
  it("processDiagnostics 가 있으면 프롬프트에 들어간다")
    - 프롬프트에 "stderr 는 서버 프로세스 전체에서 모은 꼬리다" 가 있다
  it("processDiagnostics 가 없으면 안 들어간다")
    - 그 문장이 프롬프트에 없다
  it("CASE_HISTORY_RULE 다음, 허용 caseId 목록 앞에 온다")
    - 세 문자열의 indexOf 를 비교한다
  it("같은 요청이면 같은 프롬프트가 나온다")
    - processDiagnostics 가 있는 요청과 없는 요청 각각 두 번 만들어 === 로 비교

describe("도구 출력 계약")
  it("outputSchema 가 있으면 요청에 실린다")
  it("없으면 키 자체가 없다")
    - "outputSchema" in tool 이 false. undefined 로 들어가지도 않는다
  it("scope 가 없는 processDiagnostics 는 타입에서 막힌다")
    - 타입 테스트. @ts-expect-error 로 남긴다
```

## T2. 번들 버전 3 과 진단 요청 배선 (`cli`)

선행: T1 이 통합 대장에 SHA 로 기록돼 있어야 한다.

### Files

수정:
- `packages/cli/src/repair-bundle.ts`
- `packages/cli/src/repair-command.ts`
- `packages/cli/tests/repair-bundle.test.ts`
- `packages/cli/tests/repair-command.test.ts`
- `packages/cli/src/test-command.ts` (번들을 만드는 호출부. 실제 위치를 찾아 확인해라)

생성:
- `.changeset/<임의이름>.md`

`packages/generate` 와 `packages/runner` 는 고치지 않는다.

**`buildRepairBundle` 의 호출부를 먼저 찾아라.** `grep -rn "buildRepairBundle" packages/`
로 확인하고, 그 파일이 위 목록에 없으면 **멈추고 보고해라.** 목록을 임의로 늘리지 마라.

### 사양

**1) 버전을 3 으로 올린다.**

```ts
/**
 * 3 은 `tools` · `failures[].assertions` · `target` · `process.scope` 를 더하며 올렸다(#393).
 * 선택 필드로 얹지 않는다. 그러면 낡은 번들이 근거 절반만 실은 채 조용히 통과하고 사용자는
 * 진단이 왜 약한지 모른다. 2 를 올릴 때 적은 이유가 그대로 유효하다.
 */
export const REPAIR_BUNDLE_VERSION = 3;
```

`describeRepairBundleInvalid` 의 `versionMismatch` 문장은 상수를 보간하므로 **안 고쳐도**
맞는 숫자가 나온다. 확인만 해라.

**2) `tools`: 실패한 케이스가 부른 것만.**

```ts
export interface RepairBundleTool {
  readonly name: string;
  readonly inputSchema: JsonObject;
  /** 선언이 없으면 키를 만들지 않는다. 빈 객체는 "빈 스키마" 로 읽힌다. */
  readonly outputSchema?: JsonObject;
  readonly description?: string;
  /** §5 의 크기 상한에 걸려 스키마를 뺐으면 true. 없으면 키를 만들지 않는다. */
  readonly schemasOmitted?: true;
}
```

`buildRepairBundle` 이 `tools: readonly ToolDef[]` 를 **선택 인자로** 받는다. 안 넘기면
빈 배열이다. 대시보드 등 다른 호출부가 있으면 그쪽을 안 고쳐도 컴파일된다.

싣는 기준: **`failures` 배열에 실제로 들어간 케이스의 `tool` 이름 집합.** `maxCases` 로
자르는 것은 `repair` 쪽이므로 여기서는 번들의 `failures` 전량 기준이다.

순서는 **툴 이름 UTF-16 코드 단위 오름차순**이다. 비교는
`(a, b) => (a < b ? -1 : a > b ? 1 : 0)` 이다. `localeCompare` 를 쓰지 마라. 서버가 준
순서를 그대로 쓰면 서버가 순서를 바꾸는 것만으로 번들 바이트가 흔들린다.

**3) `target`: transport 만 싣는다.**

```ts
export interface RepairBundleTarget {
  /** "stdio" 또는 "http". 실행 방식이 다르면 같은 증상도 원인이 다르다. */
  readonly transport: string;
}
```

**실행 명령·URL·서버 이름·버전은 싣지 않는다.** 계획 작성 시점에는 싣기로 했으나 2026-09-13
에 코드를 확인하고 뺐다. 설계 문서 §2.3 에 사유가 있다. 요약하면 이렇다.

- ADR-0097 의 argv 마스킹(`redactOriginArgs`)은 `packages/record/src/external/origin-redaction.ts`
  에 있고 **`@mcpeak/record` 공개 진입점으로 안 나온다.** `cli` 에 같은 규칙을 다시 쓰면
  ADR-0097 의 규칙이 두 벌이 되고, 한쪽만 고쳐지면 녹화본에는 가려진 값이 번들에는 남는다
- 핸드셰이크 결과가 `McpClient` 에 없고 그 인터페이스는 변경 금지다

**`connect-target.ts` 의 `describeTarget` 을 쓰지 마라.** 그 함수는 stdio 에서
`[command, ...args].join(" ")` 을 돌려주고 마스킹을 하지 않는다. 화면에 쓰는 것과 사용자가
AI 에게 보내는 파일에 쓰는 것은 노출이 다르다.

**새 마스킹 함수를 쓰지 마라.** 이것이 이 항목의 핵심 금지다. "적당히 가리는" 코드를 쓰면
위 두 벌 문제가 그대로 생긴다. `transport` 만 싣는 쪽이 반쪽이라도 정직하다.

**4) `assertions`: 케이스가 기대한 것 전량.**

```ts
export interface RepairBundleAssertion {
  readonly type: string;
  readonly status: "passed" | "failed" | "skipped";
}
```

`RunnerReport` 의 `cases[].assertions` 에서 그대로 옮긴다. **단언의 값(기대 스키마 전문
등)은 싣지 않는다.** 깨진 것의 값은 `diagnostics` 의 `expected` · `actual` 에 이미 있고,
안 깨진 단언의 값까지 실으면 번들이 커지는 만큼 진단이 좋아지지 않는다.

`RunnerReport` 의 실제 `status` 값 집합을 **코드에서 확인해라.** 위 세 값과 다르면 그대로
쓰고 보고해라. 임의로 매핑하지 마라.

**5) `process.scope` 와 크기 상한.**

`bundle.process` 에 `scope: "suite"` 를 더한다. 값은 지금 항상 `"suite"` 다.

도구 하나의 `inputSchema` + `outputSchema` 를 `JSON.stringify` 한 길이가 **8192 바이트**를
넘으면 두 스키마를 빼고 `schemasOmitted: true` 를 넣는다.

`8192` 의 근거를 상수 주석에 적는다.

```ts
/**
 * 도구 하나의 스키마 직렬화 상한. 넘으면 스키마를 빼고 schemasOmitted 로 표시한다.
 *
 * 관측된 실제 MCP 도구 스키마는 대부분 1 KiB 아래다. 8 KiB 를 넘는 것은 $defs 가 수십 개
 * 달린 생성 스키마이고, 그런 것은 통째로 실어도 AI 가 원인을 좁히는 데 못 쓰면서 요청
 * 예산만 먹는다. MAX_REQUEST_BYTES 에 걸려 요청 전체가 거절되는 것보다 그 도구만 줄이는
 * 편이 낫다(#393).
 */
const MAX_TOOL_SCHEMA_BYTES = 8192;
```

바이트 수는 `Buffer.byteLength(json, "utf8")` 로 센다. `json.length` 는 UTF-16 코드 단위라
한글·이모지가 든 description 에서 틀린다.

줄인 개수는 기존 `truncated` 에 넣는다.

```ts
readonly truncated?: { readonly failures?: number; readonly toolSchemas?: number };
```

기존 `failures` 를 선택으로 바꾼다. 둘 다 없으면 `truncated` 키 자체를 만들지 않는다.

**6) 검증(`readRepairBundle`)을 넓힌다.** 기준은 종전대로 **읽는 값**이다.

| 새 필드 | 검사 |
|---|---|
| `tools` | 배열. 각 항목의 `name` 이 비지 않은 문자열, `inputSchema` 가 객체. 빈 배열 허용 |
| `failures[].assertions` | 배열. 각 항목의 `type` 이 문자열, `status` 가 세 값 중 하나 |
| `target` | 객체. `transport` 가 문자열 |
| `process.scope` | `process` 가 있을 때만. `"suite"` 여야 한다 |

전부 `missingField` 사유를 쓴다. `describeRepairBundleInvalid` 의 `missingField` 문장에
새 항목을 더한다. 그 문장은 "무엇이 있어야 하는지" 를 나열하고 있으므로 늘어난 것을 적어야
사용자가 자기 파일의 어디를 볼지 안다.

**7) `repair-command.ts` 가 배선한다.** 이 이슈의 원래 증상이 닫히는 자리다.

```ts
-    // 번들에는 도구 선언이 없다. `repair` 는 서버를 띄우지 않으므로 목록을 만들 자리가 없다.
-    tools: [],
+    // 번들이 실어 온 도구 선언을 그대로 넘긴다. `repair` 는 서버를 안 띄우므로 이것이
+    // 유일한 계약 출처다(#393).
+    tools: bundle.tools.map((tool) => ({
+      name: tool.name,
+      inputSchema: tool.inputSchema,
+      ...(tool.description === undefined ? {} : { description: tool.description }),
+      ...(tool.outputSchema === undefined ? {} : { outputSchema: tool.outputSchema }),
+    })),
```

`processDiagnostics` 를 넘기는 자리에 `scope: "suite"` 를 함께 넘긴다.

`renderRepairConfirm` 의 확인 화면에 **보내는 도구 수**를 한 줄 더한다. 사용자가 무엇이
나가는지 보고 승인해야 한다. 문안은 화면의 다른 줄과 같은 형식으로 맞춘다(파일을 읽고
맞춰라). 스키마를 뺀 도구가 있으면 그 수도 적는다.
