### 사양

**1) 초기화 등급.** `reset-hook.ts` 에 둔다.

```ts
/**
 * 초기화가 실제로 무엇을 했는가. `--reset-cmd` 가 0 으로 끝난 것을 "초기 상태" 라고
 * 부르지 않기 위해 있다. 명령이 무엇을 복원했는지 우리는 모른다(이슈 #399).
 */
export type ResetGrade =
  /**
   * 새 프로세스·새 연결 + 초기화 명령 성공. 우리가 제공할 수 있는 가장 강한 것.
   *
   * **이번 회차는 이 값을 내지 않는다.** 프로세스를 다시 띄우는 것은 core 의 수명주기를
   * 건드리고, generate 흐름 한가운데서 연결을 바꾸면 그 뒤 단계가 전부 새 client 를 봐야
   * 한다. 값을 미리 정의하는 이유는, commandOnly 를 "초기 상태" 라고 부르지 않으려면
   * 그보다 강한 것이 있다는 사실이 타입에 있어야 하기 때문이다. 죽은 값이 아니라
   * 의도된 자리다. 지우지 마라(설계 §3).
   */
  | "freshProcess"
  /** 같은 연결에 초기화 명령만 성공. 서버 프로세스의 메모리 상태는 그대로다. */
  | "commandOnly"
  /** 초기화 수단이 없다. 앞 실행이 바꾼 상태가 남아 있다. */
  | "none"
  /** 초기화를 시도했으나 실패했다. 상태를 모른다. */
  | "failed";

/** 등급이 "같은 초기 상태" 를 보장하는가. 후보 비교의 전제다. */
export const resetIsComparable = (grade: ResetGrade): boolean =>
  grade === "freshProcess" || grade === "commandOnly";
```

화면 문안을 표로 고정한다. **상수로 둔다. 호출부에서 문자열을 조립하지 마라.**

| 등급 | 문장 |
|---|---|
| `freshProcess` | `초기 상태: 서버를 다시 띄우고 초기화 명령을 실행했습니다.` |
| `commandOnly` | `초기 상태: 초기화 명령만 실행했습니다. 서버 프로세스의 메모리 상태는 그대로입니다.` |
| `none` | `초기 상태: 초기화 수단이 없습니다. 앞 실행이 바꾼 상태가 남아 있을 수 있습니다. --reset-cmd 로 지정하세요.` |
| `failed` | `초기 상태: 초기화 명령이 실패했습니다. 이 실행의 결과를 검증 완료로 보지 않습니다.` |

**2) 등급을 내는 함수.** 기존 `runResetCommand` 는 **그대로 둔다.** 감싸는 것을 새로 만든다.

```ts
/**
 * 초기화를 시도하고 등급을 돌려준다. 던지지 않는다. 호출부가 등급을 보고 판단한다.
 *
 * `runResetCommand` 를 그대로 두는 이유: 그 함수는 "명령이 실패하면 던진다" 는 계약이고
 * 시험 실행 직전 경로가 그 계약에 의존한다(실패하면 실행을 시작하지 않는다). 등급이
 * 필요한 자리는 판단이 다르다 — 실패해도 진행하되 무엇을 못 했는지 적는다.
 */
export async function attemptReset(
  resetCmd: string | undefined,
): Promise<{ readonly grade: ResetGrade; readonly error?: ResetCommandError }>
```

`resetCmd` 가 `undefined` 면 `"none"`, 성공하면 `"commandOnly"`, `ResetCommandError` 면
`"failed"` 다. 그 밖의 오류는 **던진다.** 우리 결함을 등급으로 위장하지 않는다.

**3) 후보 비교를 같은 초기 상태에서 한다.** `pre-fill-wiring.ts` 의 `applyPreFill` 이다.

지금은 이렇다.

```ts
const baselineRun = await run({ client, suite: subsetSuite(baseline, targetIds) });
const aiRun = await run({ client, suite: subsetSuite(baseline, targetIds, aiInputs) });
```

초기화를 주입점으로 받는다. `dryRun` 을 주입으로 받는 것과 같은 방식이다.

```ts
export async function applyPreFill(options: {
  readonly client: McpClient;
  readonly baseline: TestSuiteSpec;
  readonly preFill: PreFillResult;
  readonly dryRun?: (o: {...}) => Promise<DryRunResult>;
  /**
   * 후보 실행 앞과 사이에 부른다. 없으면 비교하지 않고 전부 baseline 을 유지한다.
   * 테스트가 실제 명령을 실행하지 않게 주입으로 받는다.
   */
  readonly reset?: () => Promise<ResetGrade>;
}): Promise<ApplyPreFillResult>
```

실행 순서:

```
1. reset()  → grade1
2. baselineRun
3. reset()  → grade2
4. aiRun
5. resetIsComparable(grade1) && resetIsComparable(grade2) 일 때만 채택 판정
```

**둘 중 하나라도 비교 불가면 채택을 하지 않는다.** 전부 baseline 을 유지하고 사유를 낸다.
이것이 이 태스크에서 가장 중요한 판단이다. 비교 조건이 안 갖춰졌으면 고르지 않는 것이 옳다.
상태 차이를 입력 개선으로 오인해 채택한 값은 재현되지 않는 명세를 만든다.

`reset` 이 `undefined` 면(주입 안 함) `"none"` 과 같이 다룬다. 비교하지 않는다.

`ApplyPreFillResult` 에 필드를 더한다.

```ts
  /** 비교를 실제로 했는가. false 면 adopted 가 0 이고 skippedReason 이 있다. */
  readonly compared: boolean;
  /** 비교를 못 한 사유. compared 가 true 면 undefined 다. 화면에 그대로 찍는다. */
  readonly skippedReason?: string;
```

`skippedReason` 문안:

```
사전보완 비교를 건너뜁니다: 두 후보를 같은 초기 상태에서 실행할 수 없습니다.
```

그 아래에 §1 표의 등급 문장을 이어 찍는다. 등급이 둘(앞·사이)이면 **더 약한 쪽**을 찍는다.
`failed` 가 `none` 보다 약하다고 보지 않는다. 둘은 다음에 할 일이 다르므로, 둘 다 있으면
**둘 다 찍는다.**

**4) `generate-command.ts` 배선.** `applyPreFill` 호출부에 `reset` 을 넘긴다.

```ts
reset: () => attemptReset(input.resetCmd).then((r) => r.grade),
```

**`--no-dry-run` 경계는 이미 두 겹으로 막혀 있다. 2026-09-13 에 코드로 확인했다.**

| 겹 | 자리 | 내용 |
|---|---|---|
| 1 | `generate-command.ts:2220` | `if (!input.dryRun) { ...안내... return skip; }` — `applyPreFill` 이 아예 안 불린다 |
| 2 | `generate-command.ts:536` | 파서가 `--no-dry-run` 과 `--reset-cmd` 동시 사용을 `UsageError` 로 거절한다 |

**새 게이트를 만들지 마라.** 2번 때문에 `resetCmd` 가 있으면 `dryRun` 은 항상 참이다.
`attemptReset` 이 `--no-dry-run` 경로에서 불릴 길이 문법적으로 없다.

이 사실이 실제로 그런지 **테스트로 고정해라.** 지금 맞다는 것과 앞으로도 맞다는 것은 다르다.

1466~1475행의 기존 시험 실행 직전 초기화는 **그대로 둔다.** 그 자리는 실패 시 실행을
시작하지 않는 계약이고 지금 동작이 옳다.

### 사양

**1) 검증 범위를 명세에 남긴다.** `spec-approval.ts` 다.

```ts
/** 이 케이스의 통과가 어떤 실행에서 나왔는가(이슈 #399). */
export type CaseVerification =
  /** 최종 전량 재실행에서 통과했다. 가장 강한 근거다. */
  | "fullSuite"
  /** 케이스 하나만 담은 스위트에서 통과했다. 앞 케이스와의 상호작용은 안 봤다. */
  | "isolated"
  /** 시험 실행에서 통과했으나 그 뒤 명세가 바뀌었다. */
  | "stale";
```

`approval.cases` 에 이 값을 싣는다. **기존 `CaseApprovalStatus` 를 바꾸지 마라.** 그것은
"사람이 무엇으로 판정했는가" 이고 이것은 "어떤 실행에서 나왔는가" 다. 다른 축이다.

저장 형식이 바뀌므로 **기존 명세를 읽는 경로가 이 키 없이도 돌아야 한다.** 없으면
`isolated` 로 읽는다. 낡은 명세가 `fullSuite` 로 읽히면 안 된다. 확인 안 한 것을 확인했다고
말하는 쪽이 반대보다 훨씬 나쁘다.

**2) 최종 재검증 단계.** 입력값 교정이 끝난 뒤, 저장 직전이다.

```
1. attemptReset  → grade
2. 확인 화면을 찍고 묻는다
3. 승인하면 최종 suite 전량을 runDryRun
4. 그 결과가 저장 판정이다. 합집합을 쓰지 않는다
```

확인 화면:

```
최종 명세를 처음부터 다시 실행해 검증합니다.
  {등급 문장}
  실행할 케이스: {N}건 (실제 서버 호출입니다)
```

**질문은 `runDryRun` 을 부르기 **전에** 한다.** 부른 뒤에 묻는 자리가 하나라도 있으면
#397 의 경계가 무너진다.

| 상황 | 동작 |
|---|---|
| 대화형이고 승인 | 재검증한다. 결과가 판정이다 |
| 대화형이고 거절 | 재검증 안 한다. **저장은 막지 않는다.** §3 문장을 찍는다 |
| `--yes` | 묻지 않고 재검증한다 |
| 비대화형(`--yes` 아님) | 묻지 않고 **건너뛴다.** §3 문장을 찍는다 |

비대화형에서 건너뛰는 이유: 물어볼 수 없는 곳에서 실제 호출을 조용히 늘리지 않는다.
`--yes` 는 "질문에 전부 예" 이므로 그때는 승인으로 본다.

**3) 재검증을 못 했을 때의 문장.** 상수로 둔다.

```
최종 전량 재검증을 하지 않았습니다. 개별 케이스 통과 기록만 있습니다.
저장 후 `mcpeak test` 로 전체를 한 번 실행해 확인하세요.
```

등급이 `none` 또는 `failed` 라서 재검증의 의미가 약한 경우에도 **재검증 자체는 한다.**
채택(T1)과 다르다. 채택은 명세의 내용을 바꾸는 것이고 최종 검증은 이미 정해진 명세를
확인하는 것이다. 확인을 못 했다고 내용을 버릴 이유는 없다. 다만 등급 문장을 함께 찍어
그 확인이 얼마나 강한지 말한다.

**4) 케이스 사이에는 초기화하지 않는다.** 스위트 경계에서만 한다. 스위트 안의 케이스 순서는
의미가 있다(앞 케이스가 만든 것을 뒤 케이스가 읽는 명세를 사람이 쓸 수 있다). 매 케이스마다
초기화하면 우리가 검증한 것이 사용자가 나중에 실행할 것과 달라진다.

**5) 저장 화면.** `fullSuite` 가 아닌 케이스가 하나라도 있으면 그 수를 센다.

```
  검증 범위: 12건 중 12건을 최종 전량 실행에서 확인했습니다.
```
```
  검증 범위: 12건 중 3건만 개별 실행에서 확인했습니다. 전량 재검증을 하지 않았습니다.
```
