### 사양

**1) `contract-range.ts` 에 방향 판정을 더한다.**

```ts
export type ContractRangeBound = "lower" | "upper";

export function violatedBounds(
  range: ContractRange,
  value: JsonValue,
): readonly ContractRangeBound[]
```

판정 규칙은 기존 `violatesRange` 와 정확히 같고 어느 쪽이 참이 됐는지만 나눈다.

| 값의 형태 | lower | upper |
|---|---|---|
| `typeof value === "number" && Number.isFinite(value)` | `minimum !== null && value < minimum` 또는 `exclusiveMinimum !== null && value <= exclusiveMinimum` | `maximum !== null && value > maximum` 또는 `exclusiveMaximum !== null && value >= exclusiveMaximum` |
| `typeof value === "string"` | `minLength !== null && charLength(value) < minLength` | `maxLength !== null && charLength(value) > maxLength` |
| `Array.isArray(value)` | `minItems !== null && value.length < minItems` | `maxItems !== null && value.length > maxItems` |
| 그 밖 | 없음 | 없음 |

반환 순서는 항상 `["lower", "upper"]` 부분열이다. 결정론성 때문이다.

`violatesRange` 는 지우지 말고 `violatedBounds(range, value).length > 0` 로 남긴다.
`input-contract.ts` 가 쓰고 있고 그쪽은 방향을 알 필요가 없다.

**2) `ContractAxis` 에 `bound` 를 더한다.** 기존 필드는 이름도 순서도 그대로다.

```ts
  /**
   * 범위의 어느 쪽 경계를 보는 축인지. RANGE_VIOLATION 에서만 값이 있고 그 밖에는 null 이다.
   * 축 정체성은 이제 (kind, field, bound) 다. 이것을 키에서 빼면 한쪽 경계만 검사한 스위트가
   * 범위 전체를 덮은 것으로 세어진다(이슈 #387).
   */
  readonly bound: ContractRangeBound | null;
```

지역 헬퍼 `axis` 와 모듈 수준 `contractAxis` 는 `bound` 를 **마지막 선택 인자**
(`bound: ContractRangeBound | null = null`)로 받는다. 그래야 RANGE 아닌 호출부를 한 줄도
안 고친다.

**3) `deriveContractAxes` 의 RANGE 블록을 방향별로 민다.**

```ts
for (const [name, field] of analysis.schema.fields) {
  if (field.enumValues !== null || field.range === null) continue;
  if (hasUsableLowerBound(field.range))
    axes.push(axis("RANGE_VIOLATION", name, null, null, field.range, "lower"));
  if (hasUpperBound(field.range))
    axes.push(axis("RANGE_VIOLATION", name, null, null, field.range, "upper"));
}
```

`hasUsableLowerBound` · `hasUpperBound` 는 `contract-range.ts` 에 이미 있다. 새로
만들지 않는다. 필드 순서는 `analyzeInputSchema` 가 이미 코드 단위로 정렬해 둔 Map 순서이므로
다시 정렬하지 않는다. 한 필드 안에서는 lower 가 upper 보다 먼저다.

**4) `violatedAxes` 의 RANGE 블록을 방향별로 민다.**

```ts
else if (
  rangeYieldsViolation(field.range) &&
  !nullSatisfiesField(field, input[name] as JsonValue)
)
  for (const bound of violatedBounds(field.range, input[name] as JsonValue))
    rangeAxes.push(contractAxis(tool, "RANGE_VIOLATION", name, null, null, field.range, bound));
```

`violatesRange` 호출이 `violatedBounds` 로 바뀌었을 뿐 앞의 두 조건은 그대로다. nullable
필드의 null 을 거르는 `nullSatisfiesField` 를 빼지 않는다(#426 회귀).

**5) `index.ts` 에서 `ContractRangeBound` 를 타입으로 내보낸다.** 29행의

### 사양

**1) `rangeViolationValue` 를 방향별 두 함수로 가른다.** 시그니처는 기존과 같고 이름만 다르다.

```ts
function lowerViolationValue(
  range: ContractRange, fieldSchema: unknown, path: string, root: JsonSchema,
): JsonValue | undefined

function upperViolationValue(
  range: ContractRange, fieldSchema: unknown, path: string, root: JsonSchema,
): JsonValue | undefined
```

`lowerViolationValue` 는 위에서부터 첫 번째로 맞는 것을 돌려준다.

| 조건 | 값 |
|---|---|
| `plainObject(fieldSchema) && fieldSchema.type === "integer"` 이고 `integerLowerBound(range.minimum, range.exclusiveMinimum) !== null` | 그 값 `- 1` |
| `range.minimum !== null` | `range.minimum - 1` |
| `range.exclusiveMinimum !== null` | `range.exclusiveMinimum` |
| `range.minItems !== null && range.minItems >= 1` | `arrayOfLength(items, range.minItems - 1, path, root)` |
| `range.minLength !== null && range.minLength >= 1` | `stringOfLength(range.minLength - 1)` |
| 그 밖 | `undefined` |

`upperViolationValue` 도 같은 방식이다.

| 조건 | 값 |
|---|---|
| `plainObject(fieldSchema) && fieldSchema.type === "integer"` 이고 `integerUpperBound(range.maximum, range.exclusiveMaximum) !== null` | 그 값 `+ 1` |
| `range.maximum !== null` | `range.maximum + 1` |
| `range.exclusiveMaximum !== null` | `range.exclusiveMaximum` |
| `range.maxItems !== null` | `arrayOfLength(items, range.maxItems + 1, path, root)` |
| `range.maxLength !== null` | `stringOfLength(range.maxLength + 1)` |
| 그 밖 | `undefined` |

integer 를 먼저 보는 이유는 기존 주석과 같다. `minimum: 1.2` 에 `-1` 하면 `0.2` 가 나와
자기 type 을 어기고, 그러면 그 케이스가 TYPE_VIOLATION 축을 덮어 범위 축이 영원히 미검증으로
남는다. 상한도 대칭이다(`maximum: 1.8` 에 `+1` 은 `2.8`). **이 주석을 두 함수에 각각
남긴다.**

**2) `buildViolationCases` 의 RANGE 분기를 축의 `bound` 로 가른다.**

`axis.bound === "lower"` 면 `lowerViolationValue`, `"upper"` 면 `upperViolationValue` 를
쓴다. `undefined` 면 `continue` 로 그 축의 케이스를 만들지 않는다(기존 동작 유지).

| bound | id | name |
|---|---|---|
| `"lower"` | `uniqueId("range-lower", field)` | `${tool.name}가 '${field}' 하한 미만 값을 거절한다` |
| `"upper"` | `uniqueId("range-upper", field)` | `${tool.name}가 '${field}' 상한 초과 값을 거절한다` |

`uniqueId` 는 `${baseName}-${prefix}-${fieldSlug(field)}` 를 만들고 중복이면 `-2` 를
붙이는 기존 함수다. 그대로 쓴다.

`axis.bound` 가 null 인 RANGE_VIOLATION 축은 T1 이후 나올 수 없다. 그래도 `continue` 로
건너뛰고 케이스를 만들지 않는다. 방향을 모르는 축에 값을 지어내지 않는다.

**3) 상한 경계 정상 케이스를 만드는 함수를 새로 내보낸다.**

```ts
export function buildUpperBoundaryCases(options: {
  readonly tool: ToolDef;
  readonly happyInput: JsonObject;
  readonly baseName: string;
  /** 출력 계약이 지원되면 그 스키마. 아니면 null. 정상 케이스와 같은 단언을 붙인다. */
  readonly responseSchema: ResponseSchema | null;
}): readonly GeneratedCase[]
```

`deriveContractAxes(tool).axes` 를 돌며 `kind === "RANGE_VIOLATION" && bound === "upper"`
인 축마다 아래를 한다.

1. 경계값을 만든다. 못 만들면 그 축은 건너뛴다.

   | 조건 | 값 |
   |---|---|
   | `plainObject(fieldSchema) && fieldSchema.type === "integer"` 이고 `integerUpperBound(range.maximum, range.exclusiveMaximum) !== null` | 그 값 |
   | `range.maximum !== null` | `range.maximum` |
   | `range.maxItems !== null` | `arrayOfLength(items, range.maxItems, path, root)` |
   | `range.maxLength !== null` | `stringOfLength(range.maxLength)` |
   | 그 밖 (`exclusiveMaximum` 만 있는 non-integer 포함) | 만들지 않는다 |

   `exclusiveMaximum` 을 non-integer 에서 만들지 않는 이유를 주석으로 남긴다. 실수에서
   "경계 바로 안쪽" 이 정의되지 않는다. `exclusiveMaximum: 10` 의 정상 최댓값은 `10` 도
   `9` 도 아니다. 지어낸 값이 거절당하면 서버 결함인지 우리 값이 나쁜 건지 구분할 수 없다.

2. `happyInput[field]` 가 그 값과 `canonicalJson` 기준으로 같으면 건너뛴다. 정상 케이스가
   이미 그 경계를 밟고 있다. (하한 없이 상한만 선언된 필드가 여기 해당한다. `synthesize.ts` 가
   상한을 정상값으로 쓴다.) 비교는 `packages/generate/src/canonical.ts` 의 `canonicalJson` 을
   쓴다. `===` 로 비교하면 배열·문자열에서 틀린다.

3. 케이스를 만든다.

   - id: `${baseName}-bound-upper-${fieldSlug(field)}`
   - name: `${tool.name}가 '${field}' 상한 경계값에 정상 응답한다`
   - operation: `{ type: "callTool", tool: tool.name, input: { ...happyInput, [field]: 경계값 } }`
   - assertions: `[{ type: "isError", expected: false }]` 에 `responseSchema !== null` 이면
     `{ type: "structuredContentMatchesSchema", schema: responseSchema }` 를 잇는다

축 순서를 그대로 따르므로 결과 순서는 결정론적이다. id 중복 회피는 `buildViolationCases` 와
별도 `Set` 으로 한다. 접두사가 `bound-upper` 라 `range-*` 와 겹치지 않는다.

**4) `render.ts` 의 `buildSuite` 가 그 함수를 부른다.** `cases` 배열 순서는
`정상 → 상한 경계 정상 → 위반` 이다.

```ts
cases: [
  { /* 기존 ${baseName}-success 케이스 그대로 */ },
  ...buildUpperBoundaryCases({
    tool,
    happyInput: input as JsonObject,
    baseName,
    responseSchema: outputContract?.supported === true ? outputContract.schema : null,
  }),
  ...buildViolationCases({ tool, happyInput: input as JsonObject, baseName }),
],
```

**5) `coverage.ts` 의 축 키에 `bound` 를 넣는다.** 키를 만드는 자리가 **세 곳**이다
(`coveredBy.set` 의 key, `coveredBy.has` 의 key, `coveredBy.get` 의 key). 하나라도 빠지면
조회가 어긋나 전부 미검증으로 찍힌다. 헬퍼로 뽑아 한 군데서 만든다.

```ts
const axisKey = (axis: {
  readonly kind: ContractAxisKind;
  readonly field: string | null;
  readonly bound: ContractRangeBound | null;
}): string => \`\${axis.kind} \${axis.field ?? ""} \${axis.bound ?? ""}\`;
```

`AxisCoverage` 에 `bound` 를 싣고, `derived.axes.map` 에서 `bound: axis.bound` 를 채운다.
`ContractRangeBound` 는 `@mcpeak/runner` 에서 타입으로 가져온다.

### 사양

`AXIS_LABEL` 은 **그대로 둔다.** `ContractAxisKind` 가 안 바뀌었으므로 손댈 곳이 없다.

`axisLabel(kind, field)` 이 세 번째 인자로 `bound: ContractRangeBound | null` 를 받는다.

**기존 형식을 지킨다.** 이 저장소의 현재 형식은 `${field} 의 ${AXIS_LABEL[kind]}` 다
(`filters 의 타입 위반 거절`). 그 뒤에 `bound` 가 있을 때만 ` (하한)` · ` (상한)` 을 붙인다.

| 축 | 문구 |
|---|---|
| `RANGE_VIOLATION` · `n` · `lower` | `n 의 선언된 범위 밖 값 거절 (하한)` |
| `RANGE_VIOLATION` · `n` · `upper` | `n 의 선언된 범위 밖 값 거절 (상한)` |
| `TYPE_VIOLATION` · `filters` · `null` | `filters 의 타입 위반 거절` (안 바뀐다) |
| `UNDECLARED_FIELD` · `null` · `null` | `선언되지 않은 필드 거절` (안 바뀐다) |

**range 축 말고는 한 글자도 바뀌면 안 된다.** 이 이슈는 범위 축을 상·하한으로 가르는 것이지
커버리지 라벨 전체를 다시 디자인하는 것이 아니다. 관계없는 곳까지 바꾸면 그 변경을 아무도
검토한 적이 없게 되고, `docs/superpowers/specs/2026-08-15-contract-axis-coverage-design.md`
와 `docs/reports/task-t9-contract-axes.md` 가 싣고 있는 화면 예시가 낡는다.

`RANGE_BOUND_LABEL` 을 `Readonly<Record<ContractRangeBound, string>>` 으로 둔다. `AXIS_LABEL`
과 같은 이유다. `runner` 가 경계를 늘리면 여기서 컴파일이 깨져야 한다.

1925행 부근의 `tool.axes.some((axis) => axis.kind === "RANGE_VIOLATION" && axis.caseId === null)`
는 그대로 둔다. 어느 쪽이든 미검증이면 참이어야 하고, 이 식이 이미 그렇다.

`axisLabel` 호출부 전부에 `axis.bound` 를 넘긴다. `AxisCoverage` 에 T2 가 이미 넣었다.
