### 사양

**1) 출처 타입.** 설계의 뼈대다. `fixtures.ts` 에 둔다.

> **구현 중 이름을 바꿨다.** `ValueProvenance` 는 `provenance.ts` 가 이미 쓰고 있고
> (`declared` · `placeholder` · `unknownFormat`) `index.ts` 로 나가 있다. 그쪽은 "스키마에
> 근거가 얼마나 있는가" 이고 이쪽은 "값이 어디서 왔는가" 라 뜻이 다르다. 아래 이름으로
> 읽어라: `ValueProvenance` → **`ValueOrigin`**, `FieldProvenance` → **`FieldOrigin`**,
> 그 속성 `provenance` → **`origin`**, 결과 필드 `provenances` → **`fieldOrigins`**
> (기존 `provenance` 와 한 글자 차이라 잘못 읽힌다).

```ts
/** 이 값이 어디서 왔는가. 실패 진단이 "서버 결함인가 데이터 문제인가" 를 가르는 근거다. */
export type ValueOrigin =
  /** 사용자가 픽스처 파일에 적었다. 실재하는 자원을 가리킨다고 사용자가 보증한 값. */
  | "userFixture"
  /** 서버 선언의 const · default · examples · enum 에서 왔다. 서버가 준 값이다. */
  | "schemaDeclared"
  /** 우리가 type·format·pattern 만 보고 지어냈다. 어떤 자원도 가리키지 않는다. */
  | "schemaHint"
  /** AI 가 제안했고 사람이 확인했다. */
  | "aiProposed"
  /** 사람이 교정 화면에서 직접 입력했다. */
  | "humanRepaired";

/** 픽스처 파일 형식. JSON 만 받는다. */
export interface FixtureFile {
  readonly schemaVersion: 1;
  /** tools[도구][최상위 필드] = 값. */
  readonly tools?: Readonly<Record<string, Readonly<Record<string, JsonValue>>>>;
  /** notes[도구][필드] = 사람이 읽을 메모. 값에 영향을 주지 않는다. */
  readonly notes?: Readonly<Record<string, Readonly<Record<string, string>>>>;
}
```

`aiProposed` 와 `humanRepaired` 는 T1 에서 **정의만 하고 안 낸다.** T2·T3 이 쓴다.
죽은 값이 아니라 다음 태스크의 자리다. 주석에 그렇게 적어라.

**2) 파일 해석.** 던지지 않고 결과로 낸다. 화면이 사유를 찍어야 한다.

```ts
export type FixtureRead =
  | { readonly status: "ok"; readonly file: FixtureFile }
  | { readonly status: "invalid"; readonly reason: string };

/** 파일 내용을 읽어 검증한다. `reason` 은 화면에 그대로 찍는 한 문장이다. */
export function readFixtureFile(text: string): FixtureRead
```

`reason` 문안을 표로 고정한다.

| 상황 | 문장 |
|---|---|
| JSON 아님 | `픽스처 파일이 JSON 이 아닙니다. {파서 메시지}` |
| 최상위가 객체 아님 | `픽스처 최상위가 JSON 객체가 아닙니다.` |
| `schemaVersion` 이 1 아님 | `픽스처 schemaVersion 이 1 이 아닙니다: {값}` |
| `tools` 가 객체 아님 | `픽스처의 'tools' 가 객체가 아닙니다.` |
| 도구 항목이 객체 아님 | `픽스처의 'tools.{도구}' 가 객체가 아닙니다.` |
| `notes` 값이 문자열 아님 | `픽스처의 'notes.{도구}.{필드}' 가 문자열이 아닙니다.` |

**조용히 무시하지 마라.** 형식이 깨진 파일을 무시하면 사용자는 값이 왜 안 들어가는지 모른다.

**3) 해석 순서를 `synthesizeValue` 에 넣는다.** 여기가 T1 에서 가장 조심할 곳이다.

기존 순서는 `const → default → examples[0] → enum[0] → 타입별 합성` 이다. 그 **앞에**
픽스처를 넣는다.

```
1. userFixture   ← 새로 앞에 붙는다
2. const / default / examples[0] / enum[0]   → schemaDeclared
3. 타입별 합성                                 → schemaHint
```

1번이 2번보다 앞인 이유를 주석에 적어라. `default` 가 자리값인 서버가 많고, 사용자가 실재
값을 줬는데 서버의 `default` 가 이기면 픽스처 파일이 무의미해진다.

**픽스처는 최상위 필드에만 적용한다.** `synthesizeValue` 는 재귀하므로, 픽스처를 아는 것은
**루트 객체를 만드는 자리 하나**여야 한다. 재귀 안으로 픽스처를 들고 내려가면 중첩 경로
문법(#388)과 뒤엉킨다. 이번 범위는 최상위다.

구현 형태는 둘 중 하나다. **읽고 판단해서 고르고, 고른 이유를 보고에 적어라.**

| 길 | 판단 재료 |
|---|---|
| `synthesizeValue` 에 선택 인자를 더한다 | 호출부가 여럿이라 전부 확인해야 한다 |
| `render.ts` 가 합성 뒤 최상위 필드를 덮어쓴다 | 합성 규칙과 픽스처가 한 자리에서 안 만난다. 검증은 따로 해야 한다 |

어느 쪽이든 **픽스처 값이 스키마를 어기면 거절해야 한다.** 새 오류 코드를 쓴다.

```
오류 [INVALID_FIXTURE_VALUE]: 픽스처 값이 도구 선언을 만족하지 않습니다:
  {도구}.{필드}
  값: {JSON}
  선언: {스키마 JSON}
해결: 픽스처 파일의 해당 값을 선언에 맞게 고치세요.
```

`UNSUPPORTED_SCHEMA` 를 쓰지 마라. 그 코드는 `baseline.ts` 가 툴 단위로 건너뛰는 신호이고
(ADR-0036), 픽스처 오타 때문에 툴이 조용히 건너뛰어지면 안 된다. 사용자가 고칠 곳도
스키마가 아니라 픽스처 파일이다.

`GenerateTestsErrorCode` 는 `packages/generate/src/schema.ts` 의 닫힌 유니온이다
(`INVALID_TOOL` · `UNSUPPORTED_SCHEMA` · `INVALID_SCHEMA_CONSTRAINT` ·
`GENERATED_SUITE_INVALID`). 거기에 `INVALID_FIXTURE_VALUE` 를 더한다. 2026-09-13 확인.

검증은 `valueMatchesSchema` 를 쓴다. 새로 쓰지 마라.

**4) 출처를 케이스와 함께 낸다.**

```ts
export interface FieldOrigin {
  readonly tool: string;
  readonly field: string;
  readonly origin: ValueOrigin;
}
```

`buildGeneratedCases` 와 `baseline.ts` 결과에 `fieldOrigins: readonly FieldOrigin[]` 를
싣는다. `outputContractSkips` 와 **같은 길**이다. 그 코드를 보고 따라 해라.

정상 케이스의 최상위 필드마다 한 건이다. 위반 케이스는 안 센다. 그쪽은 값을 일부러
어긴 것이라 출처를 물을 대상이 아니다.

**6) 픽스처 값이 든 필드를 사전보완에서 뺀다.**

이슈 #401 이 `GeneratedCase.pinnedFields` 를 만들었다. **그것을 재사용한다. 새 통로를
만들지 마라.**

`provenance.ts` 의 `analyzeToolProvenance` 는 스키마만 보므로, 사용자가 픽스처로 `city` 를
준 뒤에도 그 필드를 `placeholder` 로 센다. 그대로 두면 사전보완이 `city` 를 AI 에게 묻고,
픽스처 값이 실패했을 때 AI 값이 채택돼 **사용자가 실재를 보증한 값이 덮인다.** 설계 §2.2 가
`userFixture` 실패를 서버 쪽 문제로 보기로 한 것과 정면으로 어긋난다.

정상 케이스의 `pinnedFields` 에 **출처가 `userFixture` 인 필드**를 넣는다. `#401` 이 만든
`preparePreFillRequest` 의 제외 규칙이 나머지를 알아서 한다.

| 케이스 | `pinnedFields` |
|---|---|
| 기준 정상 | `userFixture` 출처 필드 전부 |
| 파생 정상(#401) | `#401` 의 규칙 + `userFixture` 출처 필드 |
| 위반 케이스 | `[]` (종전대로) |

**위반 케이스는 비워 둔다.** 사전보완이 위반 케이스를 애초에 안 고른다(`isHappyPath`).

### 사양

**0) 파일은 `cli` 가 읽는다. `generate` 는 텍스트만 받는다.**

2026-09-13 확인. `generate` 는 `writeFile`·`mkdir` 만 쓰고 **파일을 읽지 않는다.** `cli` 는
`GenerateCommandDependencies.readFile(path): Promise<Uint8Array>` 주입점을 갖고 있고
`generate-command.ts:1747` 이 이미 그것으로 UTF-8 을 디코드한다. 그 길을 그대로 쓴다.

```ts
new TextDecoder("utf-8", { fatal: true }).decode(await deps.readFile(path))
```

**`node:fs` 를 새로 import 하지 마라.** 주입점을 우회하면 테스트가 실제 파일 시스템을 타고,
`readEnv` 를 주입점으로 만든 ADR-0013 의 결정과도 어긋난다.

**1) `--fixtures <path>` 옵션.** 기본값은 현재 디렉터리의 `mcpeak.fixtures.json` 이다.

| 상황 | 동작 |
|---|---|
| 옵션 없고 기본 경로에 파일 없음 | 조용히 진행한다. 픽스처 없이 종전대로다 |
| 옵션 없고 기본 경로에 파일 있음 | 읽고 **읽었다는 사실을 화면에 한 줄 찍는다** |
| 옵션 있고 파일 없음 | **오류로 끝낸다.** 사용자가 명시했는데 없는 것은 오타다 |
| 파일이 깨졌음 | 오류로 끝낸다. T1 의 `reason` 을 찍는다 |

읽었다는 줄: `▸ 픽스처: {경로} (도구 {N}개, 필드 {M}개)`

**2) 실패 진단이 출처를 말한다.** 이 태스크의 핵심이다.

케이스가 실패했고 그 케이스 입력에 `schemaHint` 출처의 값이 있으면 안내를 붙인다.

```
    ℹ 이 케이스의 '{필드}' 값 {값 JSON} 은 스키마의 type 만 보고 만든 자리값입니다.
      실재하는 자원을 가리키지 않으므로 서버 결함이 아닐 수 있습니다.
      해결: {픽스처 경로} 에 {도구}.{필드} 값을 지정하세요.
```

그 필드에 `notes` 가 있으면 한 줄 더 붙인다.

```
      메모: {notes 값}
```

**필드 이름으로 추측하지 마라.** `city` · `path` · `id` 같은 이름 표를 만들지 마라.
판정 근거는 **그 값을 우리가 지어냈는가** 하나다. 그것은 추측이 아니라 사실이다.

`userFixture` · `schemaDeclared` 출처의 값에는 안내를 **안 붙인다.** 사용자가 실재를
보증했거나 서버가 준 값이므로 서버 쪽을 먼저 봐야 한다.

한 케이스에 `schemaHint` 필드가 여럿이면 **전부 나열한다.** 하나만 찍으면 사용자가 그것만
고치고 다시 실패한다.

**3) 도움말.** `--fixtures` 항목과 함께 §4 의 비밀값 경고를 넣는다.

```
픽스처 파일에 토큰·비밀번호·API 키를 적지 마세요. 이 파일의 값은 생성된 명세에 그대로
들어갑니다. 인증이 필요한 서버는 서버 기동 환경변수로 자격을 넘기고, 픽스처에는 그
자격으로 접근 가능한 자원 식별자만 적으세요.
```

`.gitignore` 에 넣으라고 권하지 마라. 픽스처 파일은 팀이 공유해야 재현된다. 공유할 수 없는
것을 거기 넣지 말라는 것이 규칙이다.

### 사양 0. 교정값의 출처를 어디서 얻는가

**계획서를 쓸 때 빠뜨린 자리다(2026-09-13 발견).** 아래 화면이 `humanRepaired` 와
`aiProposed` 를 갈라 적으라고 하는데, **지금 코드에는 그 구분이 어디에도 없다.**

```ts
// repair-target.ts:41 — 현재
export interface RepairAttempt {
  readonly field: string;
  readonly value: JsonValue;
  readonly passed: boolean;
}
```

`origin` 을 여기 더한다. 값 옆에 두는 것이 맞다. `input-repair.ts` 안에 나란한 지도를
따로 만들면 `attempts` 와 어긋날 수 있고, `repair-target.ts:50` 의 주석이 바로 그런
손 복제를 하지 말라고 적는다.

```ts
  /** 이 값을 누가 정했는가. 픽스처 되돌리기가 화면에 출처를 적는 근거다(#390). */
  readonly origin: "aiProposed" | "humanRepaired";
```

`RepairAttempt` 를 만드는 자리는 **`input-repair.ts` 두 곳뿐이다**(1회차·2회차). 판정 규칙은
이렇다.

| 자리 | origin |
|---|---|
| 1회차이고 그 필드 값이 AI 제안값과 같다 | `aiProposed` |
| 1회차이고 값이 다르다 (사람이 고쳐 넣었다) | `humanRepaired` |
| 2회차 | 항상 `humanRepaired`. `proposed: undefined` 로 부른다 |
| 캐시에서 재사용한 필드 | **값을 준 케이스의 origin 을 그대로 물려받는다** |

값 비교는 `===` 가 아니라 `canonicalJson` 이다. 제안값이 객체나 배열일 수 있다.

마지막 줄 때문에 캐시가 값만이 아니라 `{ value, origin }` 을 담아야 한다. 사람이 AI 제안을
고쳐 넣었는데 뒤 케이스에서 "AI 제안" 으로 찍히면 화면이 거짓말을 한다.

`aiProposed` 를 "(AI 제안, 사람이 확인)" 으로 적는 것은 정확하다. 1회차는 제안값을 채워 놓고
사람에게 묻고, 사람이 그대로 두기로 한 값이다. 사람이 못 본 값이 여기 오지 않는다.

| 상황 | 동작 |
|---|---|
| 픽스처 파일이 **없다** | 기존 원자적 쓰기(`openTemp` → `link`)로 만든다 |
| 픽스처 파일이 **있다** | **안 쓴다.** 병합할 내용을 화면에 픽스처 JSON 조각으로 찍고 사용자가 직접 붙인다 |

`unlink` 후 `link` 로 교체하는 갈래 A 를 버린 이유: 두 연산 사이에 파일이 없는 창이 생기고,
무엇보다 "덮어쓸 수 있는 primitive 를 두지 않는다" 는 결정을 우회하는 것이다. 사용자가 손으로
고쳐 둔 픽스처를 우리가 지우고 다시 쓰는 것은 그 결정이 막으려던 바로 그 일이다.

쓰기를 통째로 빼는 갈래 C 를 버린 이유: 첫 실행에서 파일을 만들어 주는 것만으로도 §1.3 의
절반이 닫힌다. 그다음부터는 사용자가 그 파일을 갖고 있다.

**있을 때 찍는 화면.** 붙여 넣을 수 있는 모양이어야 한다.

```
교정한 값 3건을 픽스처에 반영하려면 {픽스처 경로} 의 "tools" 아래에 붙이세요.
기존 파일이 있어 우리가 고치지 않습니다.

  "read_file": { "path": "./fs-sandbox/a.txt" },
  "get_weather": { "city": "Seoul" }
```

**들여쓰기와 따옴표를 그대로 붙여 넣을 수 있게 낸다.** 사용자가 손으로 JSON 을 고치는 자리라
쉼표 하나가 틀리면 파일이 깨진다. 마지막 줄에 쉼표를 붙이지 않는다.

교정이 끝나면 그 값을 픽스처 파일에 쓸지 묻는다.

```
교정한 값 3건을 {픽스처 경로} 에 저장할까요?
  read_file.path      "./fs-sandbox/a.txt"       (사람이 입력)
  get_weather.city    "Seoul"                    (AI 제안, 사람이 확인)
  create_dir.path     "./fs-sandbox/new-dir"     (사람이 입력)
```

출처 표기는 `humanRepaired` → `(사람이 입력)`, `aiProposed` → `(AI 제안, 사람이 확인)` 다.

| 상황 | 파일 없음 | 파일 있음 |
|---|---|---|
| 대화형이고 승인 | 쓴다 | 안 쓴다. 붙여 넣을 조각을 찍는다 |
| 대화형이고 거절 | 안 쓴다 | 안 쓴다 |
| `--yes` | **안 쓴다.** 안내만 | 안 쓴다. 조각을 찍는다 |
| 비대화형 | **안 쓴다.** 안내만 | 안 쓴다. 조각을 찍는다 |

`--yes` 에서 안 쓰는 이유를 주석에 적어라. 파일을 만드는 것은 사용자 작업 공간을 바꾸는
일이고, `--yes` 는 "질문에 전부 예" 이지 "내 파일을 고쳐도 좋다" 가 아니다.

**기존 파일을 절대 고치지 마라.** 병합 로직을 만들지 마라. 파일이 있으면 화면에 조각만 찍는다.

파일이 없으면 `{ "schemaVersion": 1, "tools": { ... } }` 를 새로 만든다.

**직렬화는 결정론적이어야 한다.** 도구 이름과 필드 이름을 코드 단위 오름차순으로 정렬하고
`JSON.stringify(x, null, 2)` 에 끝 개행 하나다. 순서가 흔들리면 diff 가 매번 커진다.

교정 중 최상위 필드가 아닌 값(중첩 경로)은 **안 쓴다.** 픽스처는 이번 회차에서 최상위만
받는다. 그 사실을 한 줄로 알린다.

## §7. 픽스처가 준 선택 필드는 '있음' 갈래를 또 만들지 않는다 (T1 추가)

구현 중 발견해 T1 범위에 더한 항목이다. 픽스처를 얹으면 기준 정상 입력이 바뀌는데,
`valid-branches.ts` 가 그 사실을 모르고 선택 필드마다 `-branch-with-<field>` 를 만든다.
그 케이스는 `synthesizeValue` 가 지어낸 값을 쓰므로 두 가지가 동시에 깨진다.

- 기준 케이스가 이미 그 필드를 가지고 있어 **같은 것을 두 번 본다.**
- **사용자가 실재를 보증한 값 자리에 실재하지 않는 값이 들어간다.** #401 에서 `parentId` 가
  전 UUID 0 으로 나가 정상 서버를 빨갛게 만든 그 자리와 같다. 픽스처는 정확히 그것을
  막으려고 만든 기능인데 이 경로만 그것을 되돌린다.

선택 필드 갈래에 들어가기 전에 끊는다.

```ts
if (!required.has(field)) {
  // 픽스처가 준 선택 필드는 기준 정상 입력에 이미 있다. '있음' 케이스를 또 만들면 같은
  // 것을 두 번 보고, 게다가 지어낸 값이 사용자가 보증한 값을 덮는다(#390).
  if (Object.hasOwn(happyInput, field)) continue;
```

`skip` 을 넣지 않는다. 안 밟은 분기가 아니라 **기준 케이스가 이미 밟은** 분기다. 화면에
"안 밟았다" 로 찍히면 거짓이다. `const` 를 `continue` 로 넘기는 바로 위 줄과 같은 성격이다.

테스트 둘: 픽스처를 준 선택 필드는 그 케이스가 안 생기고 `validBranchSkips` 에도 안 들어간다.
픽스처가 없으면 종전대로 생긴다(회귀 방어).

| 갈래 중복 | 해당 없음 | `-branch-with-parentid` 가 **안 생긴다.** 기준 케이스가 이미 밟았다(T1 §7) |
| 실패 진단 | 자리값이 실패해도 서버 결함처럼 보인다 | `schemaHint` 값이 든 실패에 "자리값이라 서버 결함이 아닐 수 있습니다" 가 붙는다(T2) |

픽스처 파일은 이 모양이다. `11111111-1111-4111-8111-111111111111` 은 그 서버에 실재하는
노트 id 다(`server.mjs:25`).

```json
{ "schemaVersion": 1, "tools": { "create_note": { "parentId": "11111111-1111-4111-8111-111111111111" } } }
```

이 확인은 실제 서버 프로세스를 띄우므로 **직렬로, 마지막에 한 번** 돌린다. 다른 세션이
테스트를 돌리는 중에 하면 서로 간섭해 거짓 빨강이 난다.
