### 사양

**1) 경로 문법.** 이 문법이 세 패키지의 공용어가 된다. 상수와 헬퍼를 `input-schema.ts` 에
한 벌만 둔다. 문자열을 손으로 이어 붙이는 자리를 만들지 마라.

| 형태 | 뜻 |
|---|---|
| `user` | 최상위 프로퍼티 |
| `user.name` | 객체 안의 프로퍼티 |
| `tags[]` | 배열의 원소 (모든 원소가 `items` 스키마를 공유한다) |
| `tags[].id` | 배열 원소가 객체일 때 그 안의 프로퍼티 |

```ts
/** 자식 프로퍼티 경로. 루트면 부모가 빈 문자열이다. */
export const childPath = (parent: string, name: string): string =>
  parent === "" ? name : `${parent}.${name}`;

/** 배열 원소 경로. */
export const itemPath = (parent: string): string => `${parent}[]`;
```

**2) 상한.** 근거를 주석에 적는다.

```ts
/**
 * 내려가는 최대 깊이. user.address.city 까지다.
 *
 * 실제 MCP 도구 스키마에서 그보다 깊은 필수 경로는 관측된 적이 없고, 깊어질수록 "이 경로가
 * 왜 실패했는지" 를 사람이 읽기 어려워진다. 상한에 걸린 경로는 조용히 사라지지 않고
 * unanalyzedFields 에 depthLimit 으로 들어간다(#388).
 */
const MAX_DEPTH = 3;

/**
 * 툴 하나의 최대 경로 수. 위반 케이스가 경로마다 최대 4개(required·type·enum·range) 나므로
 * 툴 하나가 256 케이스를 넘지 않게 묶는다. 넘은 경로는 pathLimit 으로 표시한다(#388).
 */
const MAX_PATHS = 64;
```

깊이는 **최상위가 1** 이다. `user` = 1, `user.name` = 2, `user.address.city` = 3.
`tags[]` 는 `tags` 보다 한 단계 깊다. `tags[].id` = 3 이다.

**3) `NormalizedInputSchema` 를 경로 기반으로 넓힌다.**

```ts
export interface NormalizedInputSchema {
  /** 키가 §1 의 경로다. 코드 단위 오름차순으로 넣는다. */
  readonly fields: ReadonlyMap<string, NormalizedField>;
  /**
   * 필수인 **경로**. 최상위 required 뿐 아니라 중첩 객체의 required 도 경로로 편다.
   *
   * `user.name` 이 여기 있다는 것은 "user 가 객체로 있으면 그 안에 name 이 있어야 한다" 는
   * 뜻이다. user 자체가 없는 입력은 `user` 경로의 누락이지 `user.name` 의 누락이 아니다.
   * 판정 규칙은 §5 에 있다.
   */
  readonly required: readonly string[];
  /** 루트의 additionalProperties 가 정확히 false 일 때만 true. 중첩은 보지 않는다(설계 §4.3). */
  readonly rejectsUndeclared: boolean;
}
```

`NormalizedField` 는 **그대로 둔다.** 필드가 늘지 않는다.

**4) `unanalyzedFields` 를 경로와 사유의 쌍으로 넓힌다.**

```ts
export type UnanalyzedReason =
  | "blockingKeyword"   // anyOf/oneOf/allOf/not/$ref (nullable 형태는 푼 뒤 다시 본다)
  | "noProperties"      // properties 가 없거나 객체가 아닌 object
  | "tupleItems"        // items 가 배열이라 원소마다 스키마가 다르다
  | "depthLimit"        // MAX_DEPTH 초과
  | "pathLimit"         // MAX_PATHS 초과
  | "pathCollision"     // 경로 문자열이 다른 필드와 충돌 (§6)
  | "noGround";         // type·enum·range 를 하나도 못 읽어 요구할 근거가 없다

export interface UnanalyzedField {
  readonly path: string;
  readonly reason: UnanalyzedReason;
}
```

**`noGround` 는 기존 동작의 이름이다.** 지금 `unanalyzedFields` 에 들어가는 두 경우
(차단 키워드·type 배열 / 근거 없음)를 각각 `blockingKeyword` 와 `noGround` 로 나눈다.
`Array.isArray(field.type)` 도 `blockingKeyword` 로 묶는다. 사용자가 볼 때 "우리가 못 읽는
선언" 이라는 점이 같다. **다르게 묶고 싶으면 나에게 물어라. 임의로 정하지 마라.**

정렬은 `path` 코드 단위 오름차순이다.

**5) 재귀.** `analyzeInputSchema` 가 경로를 만들며 내려간다.

내려가는 조건:

| 조건 | 결과 |
|---|---|
| `type === "object"` 이고 `plainObject(properties)` | 각 프로퍼티로 내려간다 |
| `type === "object"` 이고 `properties` 가 없거나 객체가 아님 | `noProperties` |
| `type === "array"` 이고 `plainObject(items)` | `tags[]` 로 내려간다 |
| `type === "array"` 이고 `Array.isArray(items)` | `tupleItems` |
| `type === "array"` 이고 `items` 가 없음 | 내려가지 않는다. 표시도 하지 않는다(선언이 없다) |
| 깊이가 `MAX_DEPTH` 를 넘음 | `depthLimit`. 그 아래는 안 본다 |
| 경로 수가 `MAX_PATHS` 를 넘음 | `pathLimit`. 이후 경로를 안 만든다 |

**중간 노드도 `fields` 에 들어간다.** `user` 는 `type: "object"` 인 필드로 자기 축
(`TYPE_VIOLATION user`)을 갖고, 동시에 `user.name` 의 부모다. 지금 동작과 같다.

**배열 원소 노드의 `range` 는 `items` 스키마의 것이다.** `tags` 의 `minItems` 는 `tags` 의
range 이고 `tags[]` 의 `minLength` 는 `tags[]` 의 range 다. 섞지 마라.

`$ref` 순환은 깊이 상한이 끊지만, 그것에만 기대면 순환이 상한까지 같은 축을 만들어 낸다.
**방문 중인 스키마 객체를 `Set<object>` 로 들고 다니며 재방문이면 `blockingKeyword` 로
끊는다.** `synthesize.ts` 의 `active` 와 같은 방식이다.

`resolveNullableField` 는 각 노드에서 종전대로 먼저 적용한다. 푼 결과에 대해 다시 이 표를
적용한다.

**6) 경로 충돌.** 설계 §2.1 이다. escape 하지 않는다.

**경로 집합을 전부 만든 뒤에 판정한다.** 이름만 보고 미리 거르지 마라. `"a.b"` 라는
최상위 필드가 있어도 `a` 라는 객체 필드가 없으면 충돌이 아니다.

```
1. 평소대로 경로를 전부 만든다. 같은 경로 문자열이 두 번 나오면 그 경로를 기억한다.
2. 충돌한 경로를 fields 에서 지운다. required 에서도 지운다.
3. 그 경로와 그 아래 모든 경로를 unanalyzedFields 에 pathCollision 으로 넣는다.
```

지우는 것이지 한쪽을 고르는 것이 아니다. 어느 쪽이 맞는지 알 수 없다.

**7) `deriveContractAxes` 는 거의 안 바뀐다.**

`analysis.schema.fields` 의 키가 경로가 됐을 뿐 순회 코드는 그대로다. **`required` 순회만
바뀐다.** 지금은 `[...new Set(schema.required)].sort(byCodeUnit)` 인데 그대로 쓰되, 배열
원소 경로(`[]` 로 끝나는 것)는 축을 만들지 않는다.

```ts
// tags[] 는 부모 배열의 required 에 들어갈 수 없다. 원소가 없는 것은 minItems 위반이고
// 그것은 이미 tags 의 RANGE_VIOLATION 축이다(설계 §4).
for (const path of [...new Set(analysis.schema.required)].sort(byCodeUnit))
  if (!path.endsWith("[]")) axes.push(axis("REQUIRED_OMITTED", path, null, null));
```

`unanalyzedFields` 의 타입이 바뀌었으므로 `ContractAxesResult` 의 그 필드 타입도 바꾼다.

**8) `violatedAxes` 가 경로로 값을 찾는다.** 여기가 T1 에서 가장 조심할 곳이다.

경로로 입력에서 값을 꺼내는 헬퍼를 만든다.

```ts
/**
 * 경로가 가리키는 값들. 배열 원소 경로는 값이 여럿일 수 있다.
 *
 * 중간에 객체가 아니거나 키가 없으면 빈 배열이다. "값이 없다" 와 "값이 null 이다" 는 다르다.
 * 전자는 판정 대상이 아니고 후자는 nullable 판정을 거친다.
 */
function valuesAtPath(input: JsonValue, path: string): readonly JsonValue[]
```

**`REQUIRED_OMITTED` 판정 규칙.** 경로 `p` 의 마지막 조각을 `last`, 그 앞을 `parent` 라 할 때:

```
parent 가 가리키는 값이 있고, 그 값이 객체이고, 그 객체에 last 키가 없으면 위반이다.
parent 가 가리키는 값이 없으면 판정하지 않는다.
```

`{ }` 는 `user` 의 누락이지 `user.name` 의 누락이 아니다. `{ user: {} }` 가 `user.name` 의
누락이다. **이 구분이 없으면 케이스 하나가 축 둘을 덮고 커버리지가 부풀어 오른다.**

`parent` 가 배열 원소 경로면 원소마다 판정하고, **하나라도 위반이면 그 축을 덮은 것으로 낸다.**
축은 경로 하나당 하나다.

`TYPE_VIOLATION` · `ENUM_VIOLATION` · `RANGE_VIOLATION` 도 같다. 경로가 가리키는 값이
여럿이면 하나라도 위반이면 덮은 것이다.

**9) `input-contract.ts` 가 같이 바뀌어야 한다. 안 고치면 정상 케이스마다 오탐이 쏟아진다.**

2026-09-13 에 코드로 확인했다. `input-contract.ts:210` 이 이렇게 돈다.

```ts
for (const name of schema.required) {
  if (Object.hasOwn(input, name)) continue;
  caseFindings.push(... { code: "REQUIRED_MISSING", path: `input.${name}`, expected: name } ...);
}
```

`required` 가 경로가 되면 `Object.hasOwn(input, "user.name")` 은 **항상 false** 다. 입력이
`{ user: { name: "example" } }` 로 완벽해도 `REQUIRED_MISSING input.user.name` 을 낸다.
승인 화면이 정상 명세를 결함으로 보고한다.

경로를 풀어서 판정하게 고친다. **`violatedAxes` 와 같은 규칙**이다(§8).

```
parent 가 가리키는 값이 있고, 그 값이 객체이고, 그 객체에 last 키가 없으면 REQUIRED_MISSING 이다.
parent 가 가리키는 값이 없으면 판정하지 않는다. 그것은 parent 경로의 누락이고 그 축이 따로 있다.
```

`path` 는 지금도 `input.${name}` 이므로 경로가 들어가면 `input.user.name` 이 되어 **저절로
맞는 문장**이 된다. 형식을 바꾸지 마라.

두 곳을 더 본다.

| 자리 | 지금 | 판단 |
|---|---|---|
| 207행 `inputKeys.filter((key) => !schema.fields.has(key))` | 최상위 키를 `fields` 에서 찾는다 | `user` 는 깊이 1 경로로 `fields` 에 있으므로 **그대로 맞다.** 고치지 마라 |
| 208행 `declaredNames = [...schema.fields.keys()]` | 오타 제안(`suggestName`)의 후보 | 경로가 섞이면 `usr` 오타에 `user.name` 을 제안할 수 있다. **깊이 1 경로만 넘겨라** (`.` 도 `[]` 도 없는 키) |

`schema-match.ts:184` 의 `node.required` 는 응답 스키마의 것이다. 이번 작업과 무관하다.
건드리지 마라.


| `reason` | 문장 |
|---|---|

| `depthLimit` | `중첩 깊이 상한(3)을 넘어 더 내려가지 않았습니다.` |

| `pathCollision` | `경로 표기가 다른 필드와 겹쳐 양쪽 다 제외했습니다.` |

## T4. 읽을 수 없는 경로는 축을 만들지 않는다 (`runner`) — 후속

선행: T3 이 통합 대장에 SHA 로 기록돼 있어야 한다.

T1 구현자가 보고한 위험이다. **작은 태스크지만 빼면 영원히 못 채우는 빈틈이 남는다.**

### 문제

`"a.b"` 라는 **최상위** 필드가 있고 `a` 라는 객체 필드가 **없으면** 충돌이 아니다(§6 의 판정이
옳다). 그래서 `fields` 에 `"a.b"` 가 남고 축이 생긴다.

그런데 `valuesAtPath(input, "a.b")` 는 그 경로를 `a` → `b` 로 읽는다. 입력의
`input["a.b"]` 를 못 찾는다. **축은 있는데 어떤 케이스도 그것을 못 덮는다.**

이 저장소는 그런 자리를 명시적으로 피해 왔다. `contract-range.ts` 의 `rangeYieldsViolation`
주석이 그대로 적는다.

> 위반 값을 만들 수 있는 범위인지. 만들 수 없으면 축이 아니다. **못 만드는 축을 분모에 넣으면
> 영원히 못 채우는 빈틈이 생긴다.**

같은 규칙을 경로에도 적용한다.

### Files

수정:
- `packages/runner/src/input-schema.ts`
- `packages/runner/tests/contract-axes.test.ts`

생성:
- `.changeset/<임의이름>.md`

`packages/generate` · `packages/cli` 는 고치지 않는다. 축이 줄기만 하므로 그쪽 기대값이
바뀔 수 있다. **바뀌면 고치지 말고 보고해라.** 내가 범위를 넓힌다.

### 사양

`UnanalyzedReason` 에 값을 하나 더한다.

```ts
  | "unreadablePath" // 이름에 . 또는 [] 가 들어 경로로 읽으면 다른 자리를 가리킨다
```

프로퍼티 **이름 자체**에 `.` 이나 `[` 가 들어 있으면 그 경로를 `fields` 에서 빼고
`required` 에서도 빼고 `unreadablePath` 로 표시한다. 아래로 내려가지도 않는다.

판정은 **경로가 아니라 이름**으로 한다. `childPath` 로 만든 경로에는 당연히 `.` 이 있다.
`visit` 이 받는 그 단계의 **이름**을 보고 정한다.

```
name.includes(".") || name.includes("[")
```

배열 원소 단계(`itemPath`)는 이름이 없으므로 대상이 아니다.

`pathCollision` 과 나누는 이유: 충돌은 **두 선언이 같은 경로를 가리켜** 어느 쪽이 맞는지
모르는 것이고, 이쪽은 **선언이 하나인데 우리가 못 읽는** 것이다. 사용자가 할 일이 다르다.
전자는 둘 중 하나를 고쳐야 하고 후자는 그 이름을 바꾸거나 그 필드의 검증을 포기해야 한다.

### 테스트

```

  it("'a.b' 최상위 필드는 unreadablePath 로 빠진다")
    - properties: { "a.b": { type: "string" } }, required: ["a.b"]
    - fields 에 "a.b" 가 없다
    - REQUIRED_OMITTED · TYPE_VIOLATION 축이 하나도 없다
    - unanalyzedFields 에 { path: "a.b", reason: "unreadablePath" }
    - **§6 의 "'a.b' 최상위 필드만 있고 a 객체가 없으면 충돌이 아니다" 테스트를 이것으로
      바꾼다.** 충돌이 아닌 것은 그대로 맞고, 축이 생기지 않는 것이 새 사양이다
  it("'xs[0]' 처럼 대괄호가 든 이름도 빠진다")

  it("pathCollision 과 다른 사유다")
    - 두 사유가 같은 스키마에서 각각 나오는 것을 확인한다
  it("평범한 이름은 영향이 없다")
```
