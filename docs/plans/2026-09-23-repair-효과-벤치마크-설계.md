# repair 효과 벤치마크 설계

- 작성일: 2026-09-23
- 용도: 공모전 발표용 효과 숫자
- 상태: 설계 승인됨, 구현 계획 전

## 1. 목표

결함이 있는 MCP 서버를 코딩 에이전트에게 고치게 할 때, **mcpeak repair 진단을 함께 주면
수리 결과가 얼마나 좋아지는지**를 MCP 공식 적합성 테스트로 측정한다.

세 조건을 잰다.

| 조건 | 내용 |
|---|---|
| ① 결함 | 결함 서버를 그대로 채점한다 |
| ② 단순 수리 | 에이전트에게 결함 보고 사실만 알리고 고치게 한 뒤 채점한다 |
| ③ 진단 수리 | ②와 같은 프롬프트에 mcpeak repair 진단문을 덧붙여 고치게 한 뒤 채점한다 |

②와 ③은 진단문 유무 말고는 모든 조건이 같다. 따라서 둘의 차이를 mcpeak 진단의 기여로 본다.

## 2. 비범위

- 서버 성능(지연시간, 처리량) 측정
- 에이전트 과업 성공률(MCP-Bench 류) 측정
- 여러 모델·에이전트 간 비교. 에이전트는 하나로 고정한다
- `packages/` 코드 변경. 벤치마크는 제품 코드에 손대지 않고 CLI 를 바깥에서 부른다
- 결과를 README 에 싣는 재현 가능한 공개 벤치마크로 다듬는 일

## 3. 완료 조건

1. 원본 서버에 conformance 를 2회 돌린 결과가 시나리오 단위로 같다.
2. 결함 변형 8개가 각각 **자기 목표 시나리오 하나만** 깨고, 원본에서 통과하던 나머지는 모두 통과한다.
3. 변형 8개 모두에 대해 탐지 파일럿 결과(스위트, 테스트 결과, repair 진단 또는 "실패 없음")가 저장돼 있다.
4. 탐지 게이트(6절)를 통과했다면, 80회 수리 실행의 diff·에이전트 출력·채점 결과가 모두 저장돼 있고
   집계 스크립트가 7절의 표를 만들어 낸다. 게이트에서 멈췄다면 그 사실과 탐지 결과가 보고서에 남는다.
5. 보고서 한 장에 헤드라인 숫자, 변형별 표, 대조 결함 결과, 전제와 한계가 들어 있다.

## 4. 기준 서버와 채점기

### 기준 서버

- 출처: `modelcontextprotocol/conformance` 저장소의 `examples/servers/typescript/everything-server.ts`
- 고정 커밋: `1573ad5fc857d569ef405296e5d61de3ee6f921c`
- 라이선스: MCP 프로젝트는 MIT 에서 Apache-2.0 으로 전환 중이다. 둘 다 허용적 라이선스라 복사해
  쓸 수 있다. 복사본 머리에 출처 URL, 커밋, 라이선스 고지를 남긴다.
- 선택 이유: conformance 서버 시나리오 대부분이 `test_simple_text` 같은 고정 이름의 도구를 부른다.
  일반 서버에 돌리면 "도구 없음"으로 대부분 실패하므로, 시나리오가 전제하는 이 참조 서버를
  기준으로 삼아야 결함이 점수에 반영된다.
- 전송: Streamable HTTP. mcpeak 은 `--url` 로 붙는다.

### 채점기

- `@modelcontextprotocol/conformance@0.1.16`
- 명령: `conformance server --url <URL>` (기본 suite `active`)
- 결과: 시나리오별 `checks.json`. 시나리오 단위로 통과·실패를 집계한다.
  시나리오 안에 check 가 여럿이면 **모두 SUCCESS 일 때만** 그 시나리오를 통과로 본다.
  WARNING 은 통과로 친다.
- 채점 대상 시나리오 집합 **S** 는 0단계에서 원본 서버가 2회 모두 통과한 시나리오로 정한다.
  원본에서도 실패하는 시나리오는 환경 문제이므로 채점에서 뺀다.

## 5. 결함 목록 (mcpeak 실행 전 확정)

변형 하나에 결함 하나다. 모든 변형은 원본 복사본에 이 결함만 넣는다.

| ID | 영역 | 주입 결함 | 목표 시나리오 | 근거가 되는 conformance 판정 |
|---|---|---|---|---|
| F1 | 도구 | `test_audio_content` 의 `mimeType` 을 `audio/mpeg` 로 잘못 쓴다 | tools-call-audio | `Expected mimeType 'audio/wav'` |
| F2 | 도구 | `test_image_content` 응답에서 `mimeType` 을 뺀다 | tools-call-image | `Image content missing mimeType` |
| F3 | 도구 | `test_error_handling` 이 예외를 던지지 않고 정상 text 응답을 돌려준다 | tools-call-error | `isError !== true` 면 FAILURE |
| F4 | 도구 | `test_embedded_resource` 의 `resource.uri` 를 뺀다 | tools-call-embedded-resource | `Resource missing uri field` |
| F5 | 도구 | `test_multiple_content_types` 에서 image 항목을 뺀다 | tools-call-mixed-content | `Missing image content` |
| F6 | 도구 | `json_schema_2020_12_tool` 이 `tools/list` 에 내보내는 입력 스키마에서 `$schema` 와 `$defs` 를 뺀다 | json-schema-2020-12 | SEP-1613 보존 check |
| C1 | 대조 | `test://static-text` 읽기 응답에서 `mimeType` 을 뺀다 | resources-read-text | `Content missing mimeType` |
| C2 | 대조 | `test_prompt_with_arguments` 가 인자를 치환하지 않는다 | prompts-get-with-args | `arg1 not substituted in prompt` |

F1 은 처음에 `test_simple_text` 의 `text` 필드를 빼는 결함이었다. 변형 검증에서 목표 시나리오가
깨지지 않아 바꿨다. conformance 는 이 도구를 인자 없이 부르는데, 도구가 빈 입력 스키마로 등록돼 있어
SDK 가 핸들러 전에 `-32602` 로 거절한다. 그 오류 응답에도 `text` 항목이 있어 판정이 통과하므로,
핸들러 안의 결함은 채점에 닿지 않는다. 원본 서버도 같은 방식으로 이 시나리오를 통과한다.

### 도구 결함과 대조 결함을 나눈 이유

mcpeak 의 `McpClient` 는 `listTools` 와 `callTool` 만 가진다. 따라서 mcpeak 은 리소스와 프롬프트
결함을 원리적으로 볼 수 없다.

- 도구 결함 F1~F6 은 mcpeak 시야 안에 있다. 발표의 주 숫자는 여기서 낸다.
- 대조 결함 C1·C2 는 시야 밖이다. 여기서는 ②와 ③의 차이가 **없어야 정상**이다. 이 결과가
  "효과는 운이나 프롬프트 길이 때문이 아니라 진단 내용 덕"이라는 근거가 된다.
- 결함을 우리가 골랐다는 점은 발표에서 밝힌다. 이 표를 mcpeak 실행 전에 확정해 두는 것이
  사후 선택이 아니라는 증거다. mcpeak 이 도구 결함을 놓쳐도 그 변형은 결과에서 빼지 않는다.

## 6. 실행 단계

### 0단계: 기준선

1. 원본 서버를 띄우고 conformance 를 2회 돌린다.
2. 두 결과의 시나리오별 통과·실패가 같아야 한다. 다르면 멈추고 원인(서버의 타이머 동작 등)을 보고한다.
3. 2회 모두 통과한 시나리오를 S 로 기록한다. F1~F6, C1·C2 의 목표 시나리오가 모두 S 에 들어 있어야 한다.

### 1단계: 변형 검증

각 변형을 띄우고 conformance 를 돌린다. 통과 조건은 다음과 같다.

- 목표 시나리오는 실패한다.
- S 의 나머지 시나리오는 모두 통과한다.

어긋나면 그 결함을 다시 설계하고, 5절 표를 고친 뒤 이 단계를 다시 돈다. 이 단계까지는 mcpeak 을 돌리지 않는다.

### 2단계: 탐지 파일럿

변형마다 다음을 돌리고 산출물을 모두 저장한다.

```
mcpeak generate --out suite.json --url <변형 URL> --provider claude --model claude-sonnet-5   (사람이 대화형으로)
mcpeak test suite.json --url <변형 URL> --repair-bundle bundle.json
mcpeak repair bundle.json --provider claude --model claude-sonnet-5 --yes
```

- 스위트 생성은 **AI 모드**(`--provider claude --model claude-sonnet-5`)로 한다. AI 생성은 대화형 터미널을
  요구하므로 사람이 대상마다 `pnpm generate-ai <id>` 를 직접 실행하고, 나머지(test, repair)는 스크립트가 돈다.
  처음에는 `--baseline-only` 로 했다. 그 스위트는 도구마다 "오류 없이 응답한다"만 검사해, MCP 스키마를 어겨
  SDK 가 거절한 결함(F2, F4)만 잡고 도구 결함 6개 중 2개 탐지로 게이트에 걸렸다(2026-09-23). 그 결과는
  `results/pilot-baseline-only/` 에 보존하고 보고서에 함께 싣는다.
- 스위트는 **결함 서버에서 바로 생성**한다. "처음 보는 고장 서버에 mcpeak 을 쓴다"는 목표와 맞추기 위해서다.
  원본 서버에서 생성하면 진단이 정답을 거의 알려 주게 되어 효과가 부풀려진다.
- 같은 세 명령을 **원본 서버에도 한 번** 돌린다. everything server 의 `test_sampling`·`test_elicitation`
  처럼 mcpeak 클라이언트가 지원하지 않는 기능 때문에 원본에서도 나는 실패가 있을 수 있다. 이 소음을
  알아야 변형의 진단에서 결함 탓인 실패만 골라 탐지 판정을 할 수 있다.
- 변형마다 진단은 **한 번만 생성해 고정**한다. ③의 5회 실행은 모두 같은 진단문을 받는다.
  그래야 ②와 ③의 분산이 수리 에이전트에서만 나온다.
- 탐지 판정은 다음 두 조건을 모두 만족할 때만 "탐지"로 본다.
  1. `mcpeak test` 에 실패가 1건 이상 있다.
  2. repair 진단 원인 중 하나 이상이 목표 결함의 도구를 가리킨다.
  이 판정은 사람이 진단문을 읽고 내린다. 판정 근거가 된 문장을 보고서에 인용한다.

**탐지 게이트**: 도구 결함 F1~F6 중 탐지가 2개 이하면 3단계로 가지 않는다. 멈추고 탐지 결과를
보고한 뒤 방향을 다시 논의한다. 3개 이상이면 진행한다. 기준을 3으로 둔 이유는 도구 결함의
절반을 넘지 못하면 ③이 ②와 거의 같아질 것이 뻔해, 80회 실행 비용을 쓸 근거가 없기 때문이다.

진단이 나오지 않은 변형(실패 없음)도 3단계에 포함한다. 이때 ③은 "mcpeak 이 실패를 찾지 못했다"는
사실만 전달한다. 제품을 실제로 썼을 때 사용자가 받는 정보가 그것이기 때문이다.

### 3단계: 수리 실행

- 실행 수: 변형 8개 × 조건 2개(②③) × 5회 = 80회
- 에이전트: `claude -p --restricted --tools Read,Edit,Write,Glob,Grep --model claude-sonnet-5`
- 허용 도구: `Read`, `Edit`, `Write`, `Glob`, `Grep`. Bash 는 막는다. conformance 와 mcpeak 을
  에이전트가 직접 돌릴 수 없게 하기 위해서다. 서버를 띄워 보는 것도 함께 막히지만 ②③에 똑같이 적용된다.
- 격리: `--restricted` 는 코드 실행 도구를 없애고, 사용자·프로젝트·로컬 설정 파일(훅, 플러그인)을
  무시하며, 파일 도구를 작업 디렉터리 안으로 가둔다. `--strict-mcp-config` 로 MCP 서버도 뺀다.
  본 실행 전에 canary 1회로 이 격리가 실제로 걸렸는지 확인한다.
- 작업 디렉터리: 매 실행마다 저장소 밖 임시 디렉터리에 변형 서버 소스 파일 하나만 복사한다.
  conformance 패키지, 이 설계 문서, 결함 표, 다른 변형은 보이지 않아야 한다. 에이전트가 끝나면
  고친 파일을 벤치마크 작업 디렉터리로 되가져와 채점한다.
- 프롬프트 골격(②③ 공통):

  ```
  이 디렉터리의 everything-server.ts 는 MCP 서버다. 이 서버가 MCP 사양을 위반하는 결함이 있다는
  보고를 받았다. 결함을 찾아 고쳐라. 결함과 관계없는 코드는 바꾸지 마라.
  ```

  ③은 위 골격 뒤에 다음을 붙인다.

  ```
  아래는 테스트 도구 mcpeak 이 이 서버를 검사하고 낸 진단이다.
  <2단계에서 고정한 repair 진단 출력 전문>
  ```

- 저장: 실행마다 원본 대비 diff, 에이전트 JSON 출력(토큰 사용량, 소요 시간 포함), 종료 코드

### 4단계: 채점

수리된 서버마다 conformance 를 돌린다. 서버가 뜨지 않으면(타입 오류, 실행 오류) 그 실행은
수리 실패이며 S 의 모든 시나리오를 실패로 기록한다.

## 7. 지표

- **수리 성공**: 목표 시나리오가 통과하고, S 의 나머지 시나리오가 하나도 깨지지 않은 실행.
  다른 곳을 망가뜨리면 목표를 고쳤어도 실패로 센다.
- **변형별 표**: 변형 × 조건(①②③)마다 수리 성공 횟수(0~5), S 기준 평균 통과 시나리오 수
- **헤드라인**: 도구 결함 합산 수리 성공률. "② X/30 → ③ Y/30"
- **대조 결함**: C1·C2 합산 수리 성공률. ②와 ③을 나란히 보고한다
- **탐지율**: 도구 결함 6개 중 탐지된 수. 대조 결함은 탐지 대상이 아니다
- **비용**: 조건별 실행당 평균 토큰 수와 소요 시간

통계 검정은 하지 않는다. 표본이 작아서 유의성을 주장할 수 없기 때문이다. 발표에서는 원자료
(변형별 0~5)를 함께 보여 주고, 5회 반복이라는 점을 밝힌다.

## 8. 전제와 한계 (발표에서 밝힐 것)

- 결함은 우리가 주입했고, 대상 서버는 공식 참조 서버 하나다
- 수리 에이전트는 Claude Code + Sonnet 5 하나다
- 에이전트는 코드 실행을 못 하는 조건이다
- mcpeak 은 도구 영역만 본다. 대조 결함 결과가 이 한계를 그대로 보여 준다
- 반복 5회라 소수의 우연이 숫자를 흔들 수 있다

## 9. 위치와 의존성

- 위치: 저장소 최상위 `bench/repair-effect/`
- pnpm 워크스페이스·turbo·루트 설정 파일에 넣지 않는다. 루트 `pnpm test`·`pnpm typecheck` 에
  영향을 주지 않아야 한다.
- mcpeak CLI 는 저장소 빌드 산출물(`packages/cli`)을 바깥에서 실행한다.
- 이 디렉터리 전용 의존성. 모두 정확한 버전으로 고정하고 `^` 를 붙이지 않는다.

| 패키지 | 용도 | 라이선스 | 승인 |
|---|---|---|---|
