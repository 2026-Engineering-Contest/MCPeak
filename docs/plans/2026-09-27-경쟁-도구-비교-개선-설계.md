## 1. 목표와 비범위

### 1.1 목표

실측에서 mcpeak 이 경쟁 도구보다 **못했거나 틀린 말을 한** 자리를 고친다. 이 프로젝트에서
실패 메시지는 곧 제품이므로, 실패 종류마다 원인과 다음 행동을 맞게 말하도록 만드는 것이
핵심이다.

1. 실패 종류와 맞지 않는 해결 문구를 실패 종류별로 나눈다(§3.1).
2. 거절 기대가 뚫렸을 때 서버가 **무엇을** 받아들였는지 말한다(§3.2).
3. 승인 뒤 서버 선언이 느슨해진 경우에 사용자에게 입력을 고치라고 하지 않는다(§3.3).
4. 손으로 쓴 명세에 generate 승인 화면을 가리키는 안내를 내지 않는다(§3.4).
5. 값이 여러 개 틀렸을 때 기대와 실제를 −/+ 형식으로 나란히 보여 준다(§3.5).

### 1.2 비범위

- **스냅샷 단언(§4.1)과 프로토콜 적합성 점검(§4.2).** 가져올 만한 기능으로 기록만 한다.
  둘 다 명세 형식이나 새 명령을 늘리는 일이라 별도 설계와 ADR 이 필요하다.
- **명세 형식 변경.** `TestSuiteSpec.schemaVersion` 은 1 그대로 둔다. §3.3 의 근본 해결(승인
  시점 선언 저장)은 명세 형식을 바꾸므로 이번 범위에서 뺀다(§3.3.1).
- `core/src/types.ts` 의 `McpClient`·`ToolResult`. 건드리지 않는다.
- generate 쪽 문안. 메모리의 "generate 미처리 결함 목록" 이 따로 다룬다.
- 경쟁 도구 쪽 결함(mcp-jest 의 `shouldThrow`, validate 거짓 양성 등). 우리 몫이 아니다.

### 1.3 완료 조건

- §3.1~§3.5 의 문안이 이 문서의 표와 **글자 단위로** 같다. 테스트가 완전 일치로 고정한다.
- §5 의 테스트가 모두 통과하고 `pnpm test`, `pnpm typecheck --force`, `pnpm lint` 가 녹색이다.
- 예제 서버 E2E 로 다시 잰다. `examples/weather-server` 의 `server.broken-demo.mjs`,
  `examples/zod-notes-server` 의 `server.mutant.mjs` 에 기존 명세를 돌렸을 때:
  - 검출 수는 그대로다(broken-demo 4/4, mutant 6/6). 문안만 바뀌고 판정은 안 바뀐다.
  - 출력에 `스키마 변경이 의도된 것이라면` 이 값 불일치 실패 옆에 나오지 않는다.
  - mutant 출력에 `아니라면 입력을 확인하세요` 가 나오지 않는다.
- 같은 명세를 2회 실행한 사람용 출력과 `--json` 출력이 바이트 단위로 같다(결정론성 유지).

## 3. 고칠 부분

### 3.1 스키마 불일치 해결 문구를 위반 종류로 나눈다

**현재.** `packages/runner/src/diagnostics.ts` 의 `bodySchemaMismatchDiagnostic` 이 잘리지 않은
경우 항상 `스키마 변경이 의도된 것이라면 테스트를 업데이트하세요.` 를 낸다. 위반 종류를 보지
않는다. `structuredContentSchemaMismatchDiagnostic` 도 같은 구조다.

**분류.** `SchemaViolationCode` 11종을 둘로 나눈다.

| 부류 | 코드 | 뜻 |
|---|---|---|
| 구조 | `TYPE_MISMATCH`, `REQUIRED_MISSING`, `ADDITIONAL_PROPERTY` | 응답의 모양이 다르다 |
| 값 | `CONST_MISMATCH`, `ENUM_MISMATCH`, `MIN_ITEMS`, `MIN_LENGTH`, `MAX_LENGTH`, `STRING_CONTAINS`, `MINIMUM`, `MAXIMUM` | 모양은 같고 값이 다르다 |

**판정 규칙.** 표시된 위반(`result.violations`)에 구조 부류가 **하나라도** 있으면 구조 문구다.
구조가 맞아야 값을 볼 수 있으므로 구조가 먼저다. 전부 값 부류일 때만 값 문구다. 잘린 경우
(`truncated`)의 기존 문구는 그대로 둔다.

**문안 (전량).**

| 경우 | hint |
|---|---|
| 구조 부류 포함 | `응답의 형식이 기대와 다릅니다. 서버의 응답 형식 변경이 의도된 것이라면 테스트의 기대 스키마를 업데이트하세요.` |
| 전부 값 부류 | `응답 형식은 같고 값만 다릅니다. 서버가 돌려준 값이 맞다면 테스트의 기대값을 고치고, 아니라면 서버 로직을 확인하세요. 값이 실행마다 바뀐다면 --determinism 으로 확인하세요.` |
| 잘림 | 기존 `표시된 위반을 고친 뒤 나머지를 다시 확인하세요.` 유지 |

`--determinism` 을 넣는 이유: 값 불일치의 흔한 원인이 시각·외부 API 값이고, 그것을 짚는 기능이
이미 있는데 사용자가 모른다. 경쟁 도구에 없는 기능이라 알릴 가치도 있다.

구조화 응답(`STRUCTURED_CONTENT_SCHEMA_MISMATCH`)도 같은 판정 규칙을 쓴다. 다만 구조 부류의
hint 는 기존 `서버의 outputSchema 또는 structuredContent 변경이 의도된 것인지 확인하세요.` 를
유지한다. 구조화 응답에서는 그 문장이 이미 원인(출력 계약)을 가리키므로 일반 문구로 바꾸면
정보를 잃는다. 값 부류는 위 값 문구를 그대로 쓴다. (T1 구현 중 확인해 고침.)

### 3.2 거절이 뚫리면 서버가 받아들인 위반을 말한다

**현재.** `packages/runner/src/diagnostics.ts` 의 `isErrorMismatchDiagnostic` hint 가 기대 방향과
무관하게 `툴 입력값과 서버의 오류 응답을 확인하세요.` 하나다.

**코드 사실 (설계 시 확인).** 두 가지가 해법의 모양을 정한다.

- `assertIsError` 는 응답과 명세만 받는다. 툴 선언(`tools/list`)을 모르므로 hint 에서 "어떤
  선언을 어긴 입력인지" 를 말할 수 없다.
- 선언 대조는 `checkInputContract`(`input-contract.ts`)가 하고, 거절을 기대하는 케이스에서는
  위반 finding 을 `SUPPRESSED_WHEN_REJECTION_EXPECTED` 로 **지운다.** 위반이 곧 의도이기
  때문이다. 그래서 지금은 "서버가 무엇을 받아들였는가" 를 아는 곳이 없다.

**바꿀 것.** 두 층으로 나눈다. ADR-0078 의 "문안은 코드별 표가 갖고, 호출 지점이 문맥을
얹는다" 와 같은 구조다.

1. **runner 진단 hint.** 거절을 기대했는데(`expected === true`) 정상 응답이 온 경우의 hint 를
   바꾼다. 이 문장은 선언을 모른 채로도 맞아야 한다. generate 와 dashboard 도 이 hint 를 쓴다.
2. **cli `test` 의 참고 블록.** 선언을 아는 자리에서 구체 문장을 낸다. runner 는 억제했던
   위반을 돌려주는 함수(`acceptedViolations`)와 그 문장을 만드는 함수
   (`describeAcceptedRejection`)를 내보내고, cli 는 실패 케이스에 블록 하나를 붙인다.

**runner hint 문안 (전량).**

| 경우 | hint |
|---|---|
| `expected === true` (거절 기대, 정상 응답) | `서버가 거절을 기대한 입력을 받아들였습니다. 입력이 서버 선언을 어긴다면 서버의 입력 검증을, 어기지 않는다면 명세가 기대하는 거절 근거를 확인하세요.` |
| `expected === false` (정상 기대, 오류 응답) | 기존 `툴 입력값과 서버의 오류 응답을 확인하세요.` 유지 |

정상을 기대했는데 오류가 온 경우는 서버 오류 원문이 이미 notes 로 붙고, 실측에서 gleanwork 와
동급이었으므로 바꾸지 않는다.

**`acceptedViolations` 계약.** `input-contract.ts` 에서 내보낸다.

```ts
/**
 * 거절을 기대하는 케이스마다, checkInputContract 가 억제한 선언 위반을 돌려준다.
 * 억제 전의 순서(CODE_ORDER, 그다음 path)를 그대로 쓴다. 상한으로 자르지 않는다.
 * 위반이 없거나 대조를 끝까지 못 한 케이스(툴 미선언, 스키마 해석 불가, 비객체 입력)는
 * 키가 없다. 서버를 호출하지 않는 순수 함수다.
 */
export function acceptedViolations(
  options: InputContractOptions,
): ReadonlyMap<string, readonly SpecFinding[]>;
```

판정 로직을 새로 만들지 않는다. `checkInputContract` 의 케이스 루프를 내부 함수로 빼서 두
함수가 같은 루프를 쓰게 한다. 두 함수가 위반을 따로 계산하면 한쪽만 고쳐졌을 때 서로 다른
위반을 말한다.

**`describeAcceptedRejection` 문안 (전량).** `spec-findings.ts` 에서 내보낸다.
`(findings: readonly SpecFinding[]) => string | undefined`. 억제 대상 코드 다섯 개만 보고,
그 밖의 코드는 무시한다. 남는 것이 없으면 `undefined`. 첫 finding 으로 문장을 고르고, 나머지가
있으면 꼬리를 붙인다. 값 표기는 같은 파일의 `literal`·`describeRange`·`escapeInline` 을 쓴다.
`<path>` 는 `describeSpecFinding` 과 같이 `escapeInline(finding.path)` 다.

| 첫 finding 코드 | 문장 |
|---|---|
| `REQUIRED_MISSING` | `서버가 필수 필드 ${literal(expected)} 가 빠진 입력을 받아들였습니다. 서버의 입력 검증을 확인하세요` |
| `TYPE_MISMATCH` | `서버가 ${path} 에 선언과 다른 타입의 값을 받아들였습니다. 서버 선언: ${literal(expected)}, 명세: ${literal(actual)}. 서버의 입력 검증을 확인하세요` |
| `ENUM_MISMATCH` | `서버가 ${path} 에 선언되지 않은 값 ${literal(actual)} 을 받아들였습니다. 허용: ${literal(expected)}. 서버의 입력 검증을 확인하세요` |
| `RANGE_MISMATCH` | `서버가 ${path} 에 선언된 범위 밖의 값 ${literal(actual)} 을 받아들였습니다. 서버 선언: ${describeRange(expected)}. 서버의 입력 검증을 확인하세요` |
| `UNDECLARED_FIELD` | `서버가 선언하지 않은 필드 ${literal(actual)} 가 든 입력을 받아들였습니다. 서버 스키마는 선언 밖 필드를 거절한다고 선언합니다(additionalProperties: false). 서버의 입력 검증을 확인하세요` |
| 나머지가 n(≥1)건 | 위 문장 뒤에 `. 이 입력의 다른 위반 ${n}건도 함께 받아들여졌습니다` |

`UNDECLARED_FIELD` 는 서버가 `additionalProperties: false` 를 선언했을 때만 생긴다
(`schema.rejectsUndeclared`). 그래서 "선언해 두고 받아들였다" 는 사실을 말한다.

문장 끝에 마침표를 두지 않는 것은 `describeSpecFinding` 의 기존 규칙과 같다. 반환에 줄바꿈이
없다.

**cli 참고 블록.** `packages/cli/src/test-command.ts` 의 참고 출력 루프에서, 통과하지 않은 케이스
중 `rejectionAccepted(item)` 이 참이고 `acceptedViolations` 에 그 케이스가 있으면, 그 케이스의
다른 참고 블록보다 **먼저** 아래 블록을 낸다.

```
참고: <caseId> 는 거절을 기대했지만 서버가 선언 위반 입력을 받아들였습니다
  → <describeAcceptedRejection 결과>
```

`rejectionAccepted` 는 runner 가 내보내는 판정 함수다(`rejection-accepted.ts`, 새 파일).

```ts
/**
 * 거절을 기대한 케이스에 서버가 정상 응답했는가. 보고서만 본다.
 * isError 단언 중 실패했고, 진단 코드가 IS_ERROR_MISMATCH 이며, 진단의 expected 가 true,
 * actual 이 false 인 것이 하나라도 있으면 true 다. 호출이 던졌거나 시간 초과면 false 다.
 */
export function rejectionAccepted(result: TestCaseResult): boolean;
```

보고서만 보는 이유는 cli 가 이미 보고서를 들고 있고, 같은 사실을 명세와 응답에서 다시 계산하면
두 판정이 갈릴 수 있기 때문이다.

### 3.3 승인 뒤 서버 선언이 느슨해진 경우

**현재.** 입력이 현재 선언을 어기지 않는데 거절을 기대하면 `REJECTION_WITHOUT_VIOLATION` 이
나오고, 문장이 `…아니라면 입력을 확인하세요` 로 끝난다. mutant 처럼 **서버가 제약을 지운**
경우에도 사용자에게 입력을 고치라고 한다. 승인 지문(`suiteFingerprint`)은 명세만 해시하므로
`승인 시점과 동일` 로 나와 서버 쪽 변화가 드러나지 않는다.

**핵심 관찰.** 같은 finding 이 두 상황에서 나온다.

| 상황 | 뜻 |
|---|---|
| (가) 서버가 선언 밖 제약으로 여전히 거절한다 | 명세도 서버도 문제없다. 현재 문장이 맞다 |
| (나) 서버가 입력을 받아들였다 (`rejectionAccepted` 참) | 입력이 선언을 안 어기고 서버도 받아들였다. 명세가 서버의 옛 계약을 기억하는 것이다 |

(나)에서 사용자가 입력을 고칠 이유는 없다. 입력은 원래 계약을 어기도록 만든 것이고, 계약이
바뀌었다.

**코드 사실.** `test` 화면은 통과한 케이스의 위반 finding 을 숨긴다(`test-command.ts` 의
`statuses.get(...) === "passed"` 걸러내기). 그래서 `test` 에서는 이 finding 이 실패 케이스에만
나오지만, 실패에는 시간 초과나 호출 오류도 있으므로 실패만으로 (나)라고 단정할 수 없다.
generate 승인 화면은 통과 케이스에도 이 문장을 쓴다. 그러므로 문장을 가르는 기준은 **케이스
결과가 아니라 `rejectionAccepted`** 다.

**바꿀 것.** `describeSpecFinding` 에 선택 인자로 문맥을 받는다(ADR-0078 의 구조).

```ts
export interface SpecFindingContext {
  /** 거절을 기대한 케이스에 서버가 정상 응답했는가. rejectionAccepted 의 결과. */
  readonly rejectionAccepted?: boolean;
}
export function describeSpecFinding(finding: SpecFinding, context?: SpecFindingContext): string;
```

문맥을 안 넘기는 호출(generate)은 지금과 같은 문장을 받는다.

**문안 (전량).**

| 경우 | `REJECTION_WITHOUT_VIOLATION` 문장 |
|---|---|
| 문맥 없음, 또는 `rejectionAccepted` 가 거짓 | 기존 문장 유지 |
| `rejectionAccepted === true` | `거절을 기대하지만 입력이 현재 서버 선언을 어기지 않고, 서버도 이 입력을 받아들였습니다. 명세를 만든 뒤 서버의 입력 제약이 사라졌을 수 있습니다. 의도한 변경이면 이 케이스를 지우고, 아니라면 서버의 입력 스키마와 검증을 확인하세요` |

**머리글.** `FINDING_HEADING.rejectionIntent` 의 `참고: <id> 는 거절을 기대하지만 선언을 어기지
않습니다` 는 사실만 말하므로 그대로 둔다. cli 는 `describeSpecFinding(finding, {
rejectionAccepted: rejectionAccepted(item) })` 로 부르는 배선만 바뀐다.

§3.2 의 참고 블록과 이 문장은 동시에 나오지 않는다. 앞은 억제된 위반이 **있을** 때,
`REJECTION_WITHOUT_VIOLATION` 은 위반이 **없을** 때만 생긴다.

#### 3.3.1 근본 해결은 이번 범위 밖

(나)에서 "선언이 **사라졌다**" 고 단정하려면 승인 시점 선언을 알아야 한다. 선택지는 둘이다.

| 선택지 | 방식 | 비용 |
|---|---|---|
| A | 승인 블록(`SuiteApproval.cases[]`)에 케이스가 근거로 삼은 축(`ContractAxis` 의 kind·field·bound)을 저장하고, 실행 시 현재 선언과 비교해 `서버의 title 제약(최소 1, 최대 80)이 승인 이후 사라졌습니다` 라고 말한다 | 명세 형식 변경, generate·runner 동시 수정, ADR 필요 |
| B | 이번 설계. `rejectionAccepted` 로 문장을 가르고 "사라졌을 수 있습니다" 로 가능성만 말한다 | runner 와 cli 배선에서 끝난다 |

B 를 먼저 한다. 단정하지 못해도 **방향이 맞는 문장**이 방향이 틀린 단정보다 낫고, A 는 명세
형식 버전을 올리는 일이다. A 는 스냅샷(§4.1)과 묶어 schemaVersion 2 ADR 후보로 남긴다.

### 3.4 거절 근거 미확인 고지를 명세 출처로 나눈다

**현재.** `packages/runner/src/reporter.ts` 의 `rejectionNoticeLines` 가 마지막 줄로 항상
`확인: mcpeak generate 의 승인 화면에서 해당 케이스의 응답을 확인하세요.` 를 낸다. 손으로 쓴
명세에는 승인 화면이 없다.

`unverified` 판정 자체는 맞다. weather-server 의 `add` 는 핸들러가 직접 쓴 문장
(`→ 'a' 와 'b' 는 모두 숫자여야 합니다.`)으로 거절하므로 `classifyRejectionBasis` 의 화이트리스트에
안 걸린다. 고칠 것은 판정이 아니라 **어디서 확인하라는 안내**다.

**구분 기준.** 명세에 `approval` 블록이 있으면 generate 승인을 거친 명세로 본다. 없으면 손으로
쓴 명세로 본다. `TestSuiteSpec.approval` 은 이미 선택 필드라 형식 변경이 없다.

**전달 경로.** 보고서(`RunnerReport`)에는 명세의 `approval` 이 없다. `RunnerSummary` 에 필드를
더하면 `--json` 출력이 바뀌므로, 화면 렌더 옵션으로 넘긴다.

```ts
export interface RenderReportOptions {
  color?: boolean;
  /**
   * 명세에 approval 블록이 있는가. false 일 때만 손으로 쓴 명세의 안내를 낸다.
   * 생략하면 지금 문장이다. dry-run 처럼 generate 안에서 부르는 자리는 넘기지 않는다.
   */
  specApproved?: boolean;
}
```

**문안 (전량).** 앞 두 줄은 그대로 두고 셋째 줄만 가른다.

| `specApproved` | 셋째 줄 |
|---|---|
| 생략 또는 `true` | 기존 `확인: mcpeak generate 의 승인 화면에서 해당 케이스의 응답을 확인하세요.` |
| `false` | `확인: --json 출력에서 해당 케이스의 rejectionBody 로 서버가 보낸 거절 문장을 확인하세요.` |

`rejectionBody` 는 `--json` 출력의 `cases[].rejectionBody` 키다(`executor.ts` 의
`TestCaseResult.rejectionBody`, `unverified` 이고 본문을 읽었을 때만 생긴다). 설계 시 확인했다.

cli `test` 는 `specApproved: validated.value.approval !== undefined` 를 넘긴다.

### 3.5 값 불일치가 여럿이면 −/+ diff 를 붙인다

**현재.** `CONST_MISMATCH` 가 필드마다 한 줄씩 `→ $.temp: 값이 다릅니다. 기대: 25, 실제: 21` 로
나온다. 필드가 하나면 이 형식이 충분하다. 여럿이면 줄이 흩어져 전체 모양이 안 보인다.

**자리.** 진단의 `notes` 는 쓰지 않는다. ADR-0027 이 `notes` 를 **서버가 준 값**의 자리로
정했고, 거절 지문과 cli 교정 문안이 그 원문에 기댄다. diff 는 우리가 만든 판정이므로
`RunnerDiagnostic` 에 새 선택 필드를 둔다.

```ts
/** 기대와 실제를 나란히 놓은 줄. 이미 가림 처리가 끝난 값이다. 없으면 키가 없다. */
diff?: string[];
```

**생성 조건.** `bodySchemaMismatchDiagnostic` 이 응답 본문을 추가 인자로 받는다
(`assertBodyMatchesSchema` 가 `extraction.body` 를 넘긴다). 다음을 **모두** 만족할 때만 만든다.

1. 표시된 위반(`result.violations`) 중 `CONST_MISMATCH` 가 2건 이상이다.
2. 표시된 위반이 전부 `CONST_MISMATCH` 다. 다른 위반이 섞이면 기대 객체를 만들 수 없다.
3. 본문이 객체나 배열이다.
4. 각 위반의 기대값과 실제값이 모두 스칼라(문자열, 수, 불리언, null)다. 그래야 두 객체의
   줄 수가 같아 줄 단위로 맞댈 수 있다.
5. 만든 diff 가 60줄 이하다. 넘으면 만들지 않는다. 위반 줄은 그대로 있으므로 정보는 잃지 않는다.
6. 결과가 잘리지 않았다(`totalViolations === violations.length`). 잘리면 숨은 위반이 기대 객체에
   반영되지 않아, 실제로 다른 필드가 같은 줄로 찍힌다.
7. 위반 경로를 하나로 풀 수 있다. `pathKeys` 는 배열 인덱스를 버리므로 쓰지 않고, 인덱스를 아는
   경로 해석기를 `diagnostics.ts` 안에 둔다. 키에 `.`·`[`·`]` 가 있어 경로가 모호하거나 경로를
   따라가다 막히면 만들지 않는다.
8. 위반 경로 중 어느 것도 가림 대상이 아니다(경로의 조상 키 포함). 키 기반 가림은 기대와 실제를
   똑같은 표기로 만들어 차이가 "같음" 으로 보이게 하므로, 그런 diff 는 틀린 말을 한다. 위반 줄은
   그대로 남는다.

조건 6~8 은 T1 구현 중 확인해 더했다.

**만드는 법.**

1. 본문을 `sanitizeJsonValue(body, options)` 로 가린 값을 **실제**로 둔다.
2. 실제의 사본에서 각 위반 경로(`pathKeys(violation.path)`)의 값을, 같은 규칙으로 가린
   `violation.expected` 로 바꾼 것을 **기대**로 둔다.
3. 둘을 `canonical.ts` 의 키 정렬로 2칸 들여쓴 JSON 문자열로 만들고 줄로 나눈다.
4. 같은 번호의 줄이 같으면 `  ` + 줄, 다르면 `- ` + 기대 줄, 이어서 `+ ` + 실제 줄.

`diff` 배열 값(4단계 규칙이 기준이다):

```
["  {", "    \"city\": \"서울\",", "-   \"condition\": \"맑음\",", "+   \"condition\": \"흐림\",", "-   \"temp\": 25", "+   \"temp\": 21", "  }"]
```

렌더 결과는 각 줄 앞에 `${INDENT}`(공백 4칸)를 붙인 것이다.

```
    → $.condition: 값이 다릅니다. 기대: "맑음", 실제: "흐림"
    → $.temp: 값이 다릅니다. 기대: 25, 실제: 21
      {
        "city": "서울",
    -   "condition": "맑음",
    +   "condition": "흐림",
    -   "temp": 25
    +   "temp": 21
      }
```

**렌더.** `reporter.ts` 는 위반 줄 다음, notes 앞에 diff 줄을 `${INDENT}` + 줄로 찍는다. 글머리
`→` 를 붙이지 않는다. 줄마다 `escapeTerminalText` 를 거친다. 색은 넣지 않는다.

키 순서를 정렬하므로 서버가 키 순서를 바꿔도 diff 바이트가 같다(결정론성). 구조화 응답
(`STRUCTURED_CONTENT_SCHEMA_MISMATCH`)은 진단에 이미 `expected`·`actual` 전체가 실리므로 이번에
diff 를 더하지 않는다.

## 4. 가져올 만한 기능 (이번 범위 밖, 기록용)

### 4.1 필드 단위 스냅샷 (mcp-jest)

실측에서 mcp-jest 가 정상 서버에서 녹화하고 broken-demo 에서 재생했을 때 이렇게 나왔다.
```
- content.0.text: "→ 'a' 와 'b' 는 모두 숫자여야 합니다."
+ content.0.text: "{\"sum\":null}"
- isError: true
```
응답 전체를 손으로 받아 적지 않고도 회귀를 잡는다. 도입하려면 다음을 정해야 한다.

- 새 단언 종류(`matchesSnapshot`)와 저장 위치. 명세 파일 안인가, 옆 파일인가.
- 갱신 명령(`--update-snapshots`)과 승인 지문의 관계. 스냅샷이 명세 안에 있으면 갱신이 곧 지문
  변경이다.
- 녹화·재생(`record`)과의 경계. 카세트는 서버의 바깥 호출을, 스냅샷은 서버의 응답을 고정한다.
  사용자가 둘을 헷갈리지 않게 이름과 문서를 정해야 한다.
- 시각·ID 같은 비결정 필드를 스냅샷에서 빼는 방법. `--determinism` 이 찾은 경로를 재사용할 수
  있다.

명세 형식을 바꾸므로 ADR 이 먼저다.

### 4.2 프로토콜 적합성 점검 (mcp-jest validate)

서버가 MCP 규약을 지키는지 한 번에 보는 명령이다. 발상은 쓸 만하지만 mcp-jest 의 구현은 정상
SDK 서버를 `NON-COMPLIANT` 로 판정했다. 공식 SDK 는 없는 툴 호출에
`{"content":[{"text":"MCP error -32602: Tool nope not found"}],"isError":true}` 를 돌려주는데,
이 `isError` 응답을 성공으로 오판했다. resources capability 가 없는 서버에 "Resources Discovery
✅" 도 찍었다.

도입한다면 조건은 하나다. **`isError: true` 응답과 JSON-RPC 오류를 구분하고, capability 를
선언하지 않은 기능은 검사 대상에서 뺀다.** 거짓 양성을 내는 적합성 검사는 없는 것보다 나쁘다.

### 4.3 참고만 할 것

- **테스트별 서버 격리** (gleanwork). 테스트마다 서버를 새로 띄운다. 7건에 3.1초라 느리지만
  상태 누수가 없다. mcpeak 은 한 프로세스에서 순차 실행한다(45건 약 0.2초). 상태를 가진 서버
  대상으로 `--isolate` 같은 선택 옵션을 둘 수 있지만, 실측에서 문제가 된 적은 없다.
- **작성량** (mcp-jest). 기본 테스트가 JSON 9줄로 가장 짧았다(mcpeak 17줄). 대신 필드 단위
  단언을 못 한다. 줄 수를 줄이려고 표현력을 잃을 이유는 없다.

| `값 위반만 있으면 기대값을 고치라는 문구를 낸다` | `CONST_MISMATCH` 1건 → hint 가 §3.1 값 문구와 완전 일치 |
| `범위·길이 위반도 값 부류로 본다` | `MAXIMUM` 1건 + `MIN_LENGTH` 1건 → 값 문구 |
| `잘린 결과는 기존 문구를 유지한다` | `totalViolations > violations.length` → `표시된 위반을 고친 뒤 나머지를 다시 확인하세요.` |
| `구조화 응답은 구조 위반에 출력 계약 문구를 유지한다` | `structuredContentSchemaMismatchDiagnostic` 에 구조 위반 → 기존 `서버의 outputSchema 또는 structuredContent 변경이 의도된 것인지 확인하세요.` |
| `구조화 응답도 값 위반만 있으면 값 문구를 낸다` | 값 위반만 → §3.1 값 문구 |
| `값 불일치가 1건이면 diff 를 만들지 않는다` | `diff` 키 없음 |
| `값 불일치가 2건 이상이면 diff 를 만든다` | 본문 `{"city":"서울","condition":"흐림","temp":21}`, 기대 const `condition:"맑음"`, `temp:25` → `diff` 가 §3.5 의 배열 값과 완전 일치 |
| `잘린 결과는 diff 를 만들지 않는다` | `totalViolations > violations.length` → `diff` 없음 |
| `배열 안의 값 불일치도 인덱스로 짚는다` | 본문 `{"items":[{"t":1},{"t":2}]}`, `$.items[1].t` 와 `$.items[0].t` 위반 → 두 원소의 줄이 각각 -/+ |
| `경로를 풀 수 없으면 diff 를 만들지 않는다` | 키에 `.` 가 든 본문 → `diff` 없음 |
| `다른 위반이 섞이면 diff 를 만들지 않는다` | `CONST_MISMATCH` 2 + `TYPE_MISMATCH` 1 → `diff` 없음 |
| `기대값이 스칼라가 아니면 diff 를 만들지 않는다` | const 가 객체인 위반 포함 → `diff` 없음 |
| `diff 는 서버의 키 순서와 무관하다` | 키 순서만 다른 두 본문 → `diff` 배열 동일 |
| `가림 대상 경로에 위반이 있으면 diff 를 만들지 않는다` | 민감 키(`token`) 위반 1건 + 일반 위반 1건 → `diff` 없음 |
| `diff 의 다른 줄에 있는 민감값도 가린다` | 위반이 아닌 `token` 필드가 든 본문, 일반 위반 2건 → diff 에 원문 토큰 문자열 없음 |

- 오케스트레이터는 상위 모델이다. 이 작업은 전부 **실패 메시지 문안 설계**라 `CLAUDE.local.md`

- 태스크는 구현 계획서 `docs/plans/2026-09-27-경쟁-도구-비교-개선-구현계획.md` 에 있다. runner 두
  태스크는 파일이 겹치지 않아 병렬로 돌고, cli 는 둘이 머지된 뒤에 돈다. 예제 서버 E2E 는 직렬로
  마지막에 오케스트레이터가 돌린다.

## 7. 열린 질문과 처리

설계 초안의 열린 질문은 계획 단계에서 코드로 확인해 닫았다.

1. `rejectionBody` 키 이름: `--json` 의 `cases[].rejectionBody` 가 맞다(§3.4).
2. §3.2 의 "첫 번째 위반" 순서: `checkInputContract` 의 `CODE_ORDER`·path 정렬을 그대로 쓴다.
   `acceptedViolations` 가 같은 루프를 공유하므로 두 자리가 다른 위반을 먼저 말할 수 없다.
3. §3.3.1 선택지 A 의 ADR 화: 이번 범위 밖. 스냅샷(§4.1)과 묶어 schemaVersion 2 설계로 간다.
4. §2.2 발췌의 재측정: 구현 뒤 §1.3 의 E2E 에서 현재 main 기준으로 다시 잰다. 구현 전에 따로
   재지 않는다. 문안이 바뀌는 자리는 코드로 확인했고, 검출 수는 E2E 가 판정한다.

**범위 밖으로 남긴 사본.** `website/` 의 가이드 네 파일(`guide/writing-suites.md`,
`concepts/how-it-works.md` 와 각 `ko/` 판)이 옛 hint 문구를 인용한다. `website/` 는 main 에
커밋되지 않은 디렉터리라(별도 `docs/website` 브랜치) 이번 작업에서 고치지 않는다. 그 브랜치를
합칠 때 새 문구로 맞춰야 한다.
