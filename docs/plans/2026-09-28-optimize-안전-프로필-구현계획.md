## 1. 목표, 비범위, 완료 조건

### 1.1 목표

MCP 서버의 `tools/list`를 읽어, **같은 입력을 받고 같은 호출로 귀결되면서 토큰이 적은 정의**를
내놓는다. 산출물은 오버레이 파일 하나와, 그것을 `tools/list`로 내보내고 `tools/call`은 원본
서버로 그대로 전달하는 stdio 프록시다. 서버 코드는 건드리지 않는다.

채용하는 변환은 세 가지다. 셋 다 정보를 지우지 않거나, 지워도 모델이 도구를 고르거나 인자를
채우는 데 쓰지 않는 것만 지운다.

| 변환 | 건드리는 것 | 실측 근거 |
|---|---|---|
| A 무손실 정규화 | `inputSchema`의 `$schema`·`$id`·`$comment`·`title`, `additionalProperties:true`, 빈 `required`, 빈 `properties` | 표본 약 72,000개 검증 동치 불일치 0 |
| B 잡음 제거 | 설명의 URL, "Example:" 이하 블록, 파라미터 이름을 되풀이하는 3단어 이하 설명 | 210건에서 도구 선택 변화 0 |
| C 공통 파라미터 승격 | 이름·설명이 같은 파라미터가 3개 이상 도구에 반복되면 설명을 서버 `instructions` 사전으로 한 번만 | 210건에서 도구 선택 변화 0 |

기대 감소는 35개 서버 합계 13.9%, 서버별 중앙값 12.2%, 범위 0.9~37.5%다. 절감률은 서버가
정하고 우리가 보장하는 것은 기능 유지다. 그래서 이 도구의 핵심은 변환기가 아니라 **게이트**
(§4)와 **실패 메시지**(§7)다.

### 1.2 비범위

- **공유 문장 승격.** 3차 실험에서 퇴행 3건을 전부 이것이 냈다. 결함 두 가지(조각 잔존,
  도구 한정 지침의 전역화)를 고친 뒤 별도 계획으로 되살린다.
- **파라미터 설명 삭제, `default` 삭제, `additionalProperties:false` 삭제, 도구 제외·병합,
  이름 변경.** 전부 기능이나 계약을 바꾼다.
- **게이트 B(모델 선택 동치)와 게이트 C(검색 오염 점수).** B는 모델 호출이 필요해 결정론성
  원칙과 충돌하고, C는 안전 프로필에서 값이 거의 움직이지 않았다. 둘 다 후속 계획.
- **HTTP 프록시.** 이번 프록시는 stdio 서버로만 뜬다. 상류(원본) 서버는 stdio와 HTTP 둘 다
  붙을 수 있다.
- **tools 외 능력의 전달.** 프록시는 `tools/list`·`tools/call`만 중계한다. resources·prompts는
  능력을 광고하지 않는다. 오버레이 생성 시 원본이 그 능력을 갖고 있으면 리포트에 경고한다.
- **정확한 토크나이저.** 토큰 수는 UTF-8 바이트 ÷ 4 근사치로 보고하고 "근사"라고 표시한다.
  정확한 토크나이저 의존성 추가는 §10의 결정 사항이다.
- `core/src/types.ts`의 `McpClient`·`ToolDef`·`ToolResult`. 건드리지 않는다.
- 대시보드 화면.

## 3. 변환 규칙 (판단이 있는 곳이므로 전량으로 적는다)

입력은 `ToolDef[]`와 서버 `instructions`(없으면 빈 문자열)이다. 출력은 `OptimizeOverlay`(§5.1).
변환은 순수 함수이고 순서는 A → B → C로 고정한다. 순서를 바꾸면 C의 반복 계수가 달라진다.

### 3.1 변환 A: 무손실 정규화 (`normalizeSchema`)

스키마 트리를 재귀로 걷는다. 배열은 원소마다, 객체는 키마다 아래를 적용한다.

| 키 | 조건 | 처리 | 왜 무손실인가 |
|---|---|---|---|
| `$schema`, `$id`, `$comment` | 값 무관 | 제거 | 메타데이터. 검증기가 인스턴스 판정에 쓰지 않는다 |
| `title` | 값 무관 | 제거 | 주석 키워드(JSON Schema §9). 검증에 쓰이지 않는다 |
| `additionalProperties` | 값이 정확히 `true` | 제거 | 생략 시 기본값이 `true`다. `false`나 스키마 객체는 남긴다 |
| `required` | 빈 배열 | 제거 | 빈 `required`는 제약이 없다 |
| `properties` | 빈 객체이고 형제 `additionalProperties`가 `false`가 **아닐** 때 | 제거 | `additionalProperties:false`와 함께 있으면 "아무 속성도 못 받는다"는 뜻이라 남긴다 |
| `properties`, `$defs`, `definitions` | 항상 | 값 객체의 각 항목에 재귀. 키 이름은 건드리지 않는다 | 속성 이름은 계약이다 |
| 그 외 모든 키 | | 값에 재귀 | |

키 순서는 입력 순서를 유지한다. 정렬하지 않는다. 정렬은 캐시 안정화 효과가 있지만 이 프로젝트의
결정론성은 "같은 입력 → 같은 출력"이고 입력 순서 유지가 그것을 만족한다.

도구 `description`과 `inputSchema.description`(루트)이 공백 제거 후 같으면 루트의 것을 지운다.
이것은 변환 A에 속한다(중복이라 정보 손실이 없다).

### 3.2 변환 B: 잡음 제거 (`stripNoise`)

**B-1 도구 설명.** 다음을 순서대로 적용한다.

1. URL 제거: 정규식 `/\s*\(?\bhttps?:\/\/[^\s)]+\)?/g`를 빈 문자열로. 괄호로 감싼 URL은 괄호까지
   지운다.
2. 예시 블록 제거: 정규식 `/\s*(?:\bExamples?|\bExample usage)[:.][\s\S]*$/i`에 걸리는 부분을
   지운다. **`e.g.`는 지우지 않는다.** 도구 설명 본문 중간에 나오는 `e.g.`는 파라미터 값 예시라
   인자 채우기에 쓰인다. 실험의 `EXAMPLE_RE`가 파라미터 설명에는 `e.g.`를 포함했지만 도구
   설명에는 포함하지 않았고, 이 계획은 그 구분을 유지한다.
3. 공백 정리: 연속 스페이스·탭을 하나로, 3개 이상 연속 개행을 2개로, 앞뒤 공백 제거.

**B-2 파라미터 설명.** `properties` 아래 각 속성의 `description`에 적용한다. `$defs`·`items`·
`anyOf` 안쪽의 `description`은 속성 이름을 알 수 없으므로 1·2·3만 적용하고 4는 건너뛴다.

1. URL 제거: B-1의 1과 같다.
2. 예시 제거: `/\s*(?:\bExamples?|\be\.g\.|\bFor example|\bExample usage)[:.][\s\S]*$/i`. 파라미터
   설명에서는 `e.g.` 이하도 지운다. 실험에서 인자 채우기에 영향이 없었다(210건 중 스키마 위반 0).
3. 공백을 하나로 접고 앞뒤 공백 제거.
4. 이름 되풀이 제거: 정리된 설명을 소문자·영숫자·공백만 남겨 단어로 나눴을 때 **단어가 3개
   이하**이고, 설명에서 영숫자만 남긴 문자열이 속성 이름에서 영숫자만 남긴 문자열을 **포함**하면
   `description` 키를 지운다. 예: `database: "Database name"`, `collection: "Collection name"`,
   `id: "The ID"`. 3단어 상한은 실험값이다. 4단어부터는 "The connection to use" 같은 정보가
   섞이기 시작했다.
5. 결과가 빈 문자열이면 키를 지운다.

### 3.3 변환 C: 공통 파라미터 승격 (`promoteCommonParameters`)

B를 거친 도구 목록에서 `inputSchema.properties`의 최상위 속성만 본다(중첩 속성은 보지 않는다).

1. 키 `이름\u0000설명`으로 등장 횟수를 센다. 설명이 문자열이고 **길이 20 이상**인 것만 센다.
   20 미만은 승격해도 절감이 사전 항목 한 줄보다 작다.
2. 횟수가 **3 이상**인 (이름, 설명) 쌍을 공통 파라미터로 삼는다. 2개는 우연히 같을 수 있고,
   실험 데이터에서 3 이상은 전부 서버가 의도한 공통 인자(`connectionId`, `project_id`,
   `pageId`)였다.
3. 공통 파라미터에 해당하는 속성에서 `description`을 지운다. 같은 이름이라도 설명이 다른
   속성은 건드리지 않는다.
4. `instructions`에 아래 블록을 덧붙인다. 원본 `instructions`가 있으면 그 뒤에 빈 줄 하나를 두고
   붙인다. 항목 순서는 **첫 등장 도구의 순서**를 따른다(정렬 아님, 결정론적).

```
Common parameters (shared by several tools):
- <이름>: <설명>
```

공통 파라미터가 하나도 없으면 `instructions`는 원본 그대로다.

### 3.4 하지 않는 것 (코드에서도 막는다)

변환기는 다음을 **절대 만들지 않는다.** §4 게이트 A가 이것을 검사한다.

- 도구의 추가·삭제·이름 변경·순서 변경
- `outputSchema`의 어떤 변경
- `inputSchema`에서 §3.1 표 밖의 키 제거, 값 변경, 키 추가
- `default`, `enum`, `const`, `pattern`, `format`, 숫자 제약의 변경
- `additionalProperties:false`의 제거

## 4. 게이트 A: 구조 동치 검사 (`assertLossless`)

외부 검증기 없이 결정론적으로 판정한다. 원본과 결과를 나란히 걷는다.

**허용되는 차이**는 다음 넷뿐이다. 그 밖의 차이는 전부 실패다.

1. 결과에서 사라진 키가 `$schema`, `$id`, `$comment`, `title` 중 하나다.
2. 결과에서 사라진 키가 `additionalProperties`이고 원본 값이 `true`였다.
3. 결과에서 사라진 키가 `required`이고 원본 값이 `[]`였거나, `properties`이고 원본 값이 `{}`이며
   형제 `additionalProperties`가 `false`가 아니었다.
4. 키가 `description`이고, 결과 값이 없거나(제거) 문자열이다. 값의 내용은 비교하지 않는다.
   description은 검증 의미가 없다.

추가 검사:

- 도구 수, 각 도구의 `name`, 순서가 같다.
- 각 도구의 `outputSchema`가 깊은 비교로 같다.
- 결과 스키마에 원본에 없던 키가 없다.

실패 시 §7.1의 문장으로 `OptimizeError`(code `LOSSLESS_VIOLATION`)를 던진다. 변환기는 자기
출력에 이 게이트를 항상 통과시킨 뒤 반환한다. 통과하지 못하면 오버레이를 쓰지 않는다. 이것은
사용자 입력 오류가 아니라 **우리 결함**이므로 문장이 그렇게 말한다.

## 5. 공유 계약 (전량)

### 5.1 `packages/optimize/src/types.ts`

```ts
import type { ToolDef } from "@mcpeak/core";

/** 오버레이 파일 형식 버전. 필드를 더하거나 뜻을 바꾸면 올린다. */
export const OVERLAY_SCHEMA_VERSION = 1 as const;

/** 한 도구에서 일어난 변경 하나. 리포트와 되돌리기 검토의 단위다. */
export type ToolChange =
  | { kind: "schema-key-removed"; path: string; key: string }
  | { kind: "description-cleaned"; path: string; before: string; after: string }
  | { kind: "description-removed"; path: string; before: string; reason: "restates-name" | "empty" | "duplicate-of-tool-description" | "promoted" };

export interface OptimizedTool {
  /** 원본과 같다. 프록시는 이 이름으로 상류에 전달한다. */
  readonly name: string;
  readonly description?: string;
  readonly inputSchema: unknown;
  /** 원본과 깊은 비교로 같아야 한다(게이트 A). */
  readonly outputSchema?: unknown;
  readonly changes: readonly ToolChange[];
  /** UTF-8 바이트. `{name, description, input_schema}` 를 compact JSON 으로 직렬화한 길이. */
  readonly bytes: { readonly before: number; readonly after: number };
}

export interface OptimizeOverlay {
  readonly schemaVersion: typeof OVERLAY_SCHEMA_VERSION;
  /** 만든 도구. 결정론성을 위해 시각은 넣지 않는다. */
  readonly generator: { readonly name: "@mcpeak/optimize"; readonly version: string };
  /** 원본 서버 식별. 프록시가 시작할 때 상류의 `tools/list` 와 대조하는 근거다. */
  readonly source: {
    readonly toolCount: number;
    /** 원본 도구 이름의 정렬된 목록. 상류가 바뀌었는지 프록시가 판단하는 키다. */
    readonly toolNames: readonly string[];
    readonly instructions: string;
    readonly bytes: number;
    /** 원본 서버가 광고한 tools 외 능력. 프록시가 중계하지 않으므로 리포트가 경고한다. */
    readonly otherCapabilities: readonly ("resources" | "prompts" | "logging" | "completions")[];
  };
  readonly instructions: string;
  readonly tools: readonly OptimizedTool[];
  readonly totals: {
    readonly bytesBefore: number;
    readonly bytesAfter: number;
    /** 위 bytes 에 instructions 증가분을 더한 값. 옮긴 것을 절감으로 세지 않기 위해서다. */
    readonly bytesAfterWithInstructions: number;
    readonly promotedParameters: number;
  };
}

export interface OptimizeInput {
  readonly tools: readonly ToolDef[];
  readonly instructions: string;
  readonly otherCapabilities: OptimizeOverlay["source"]["otherCapabilities"];
}

export type OptimizeErrorCode =
  | "LOSSLESS_VIOLATION"
  | "OVERLAY_INVALID"
  | "OVERLAY_UPSTREAM_MISMATCH"
  | "UPSTREAM_UNAVAILABLE";

export class OptimizeError extends Error {
  constructor(
    readonly code: OptimizeErrorCode,
    message: string,
  ) {
    super(message);
    this.name = "OptimizeError";
  }
}
```

### 5.3 `core` 접근자 (T0)

`McpClient` 인터페이스는 건드리지 않는다. **기존 연결 인터페이스 두 개도 건드리지 않는다.**
`cli` 테스트 여러 곳이 `McpStdioConnection` 객체 리터럴을 직접 만들고 있어(`test-command.test.ts`,
`generate-command.test.ts` 등 5개), 필수 필드를 더하면 `TS2741`이 난다. 대신 서버 정보 타입을
새로 두고 반환 타입을 교차로 넓힌다.

```ts
// packages/core/src/server-info.ts (비공개 모듈)
import type { Client } from "@modelcontextprotocol/sdk/client/index.js";

export interface McpServerInfo {
  /** 서버가 initialize 응답에 실은 instructions. 없으면 undefined. */
  readonly instructions: string | undefined;
  /** 서버가 광고한 능력의 키를 정렬한 목록. 예: ["resources", "tools"]. */
  readonly capabilityKeys: readonly string[];
}

/** 순수 함수. SDK Client 에서 읽기만 한다. 인메모리 트랜스포트로 단언할 수 있게 분리했다. */
export function readServerInfo(sdk: Client): McpServerInfo {
  return {
    instructions: sdk.getInstructions(),
    capabilityKeys: Object.keys(sdk.getServerCapabilities() ?? {}).sort(),
  };
}
```

`packages/core/src/index.ts`에서 `McpServerInfo` 타입을 내보내고, `connectStdio`의 반환을
`Promise<McpStdioConnection & McpServerInfo>`, `connectHttp`의 반환을
`Promise<McpHttpConnection & McpServerInfo>`로 넓힌다. 기존 호출부는 좁은 타입으로 받아도
컴파일되므로 `cli`는 수정하지 않는다. `optimize`·T4는 두 필드를 필수로 읽는다.

테스트(`packages/core/tests/instructions.test.ts`)는 SDK `Server` + `InMemoryTransport`로 연결한
`Client`를 `readServerInfo`에 넣어 instructions 유무와 능력 키를 단언한다. 프로세스를 띄우지 않는다.

`connect()`가 돌려주는 `McpClient`에는 넣지 않는다. 그 인터페이스는 동결이다.

### 5.4 오버레이 파일 위치와 이름

`mcpeak optimize --out <path>`가 필수다. 기본값을 두지 않는다. 서버 이름을 안전하게 파일명으로
바꾸는 규칙을 따로 만들지 않기 위해서다.

## 6. 프록시 동작 (T3)

`mcpeak-optimize-proxy <overlay.json> (-- <executable> [args...] | --url <URL>)` 로 뜬다.
`packages/optimize/src/proxy-stdio.ts`가 진입점이고 `bin` 이름은 `mcpeak-optimize-proxy`다.

1. 오버레이를 `parseOverlay`로 읽는다. 실패하면 stderr에 §7.3 문장, 종료 코드 1.
2. 상류에 `core.connect`로 붙는다. 실패하면 §7.3 `UPSTREAM_UNAVAILABLE` 문장, 종료 코드 1.
3. 상류 `listTools()`의 이름 정렬 목록을 `overlay.source.toolNames`와 비교한다. 다르면
   `OVERLAY_UPSTREAM_MISMATCH` 문장(§7.3)으로 종료 코드 1. **오버레이가 낡은 채로 서비스하지
   않는다.**
4. SDK `Server`를 stdio로 띄운다. 능력은 `tools`만 광고한다. `instructions`는
   `overlay.instructions`. `tools/list`는 `overlay.tools`에서 `name`·`description`·`inputSchema`·
   `outputSchema`만 실어 낸다(`changes`·`bytes`는 내부 필드).
5. `tools/call`은 이름과 인자를 **그대로** 상류 `callTool`에 넘기고, 상류 `ToolResult.raw`를
   그대로 응답한다. 상류가 `isError`면 그대로 `isError`다. 인자 검증을 프록시가 하지 않는다.
   검증은 상류의 몫이고, 프록시가 하면 "원본으로 전달"이 거짓이 된다.
6. stdout에는 JSON-RPC 외에 아무것도 쓰지 않는다. 안내·오류는 stderr. (`mock/src/stdio.ts`와
   같은 규율.)
7. 상류가 죽으면 프록시도 stderr에 한 줄 남기고 같은 종료 코드로 끝난다.

## 7. 실패 메시지와 리포트 문안 (전량. 테스트가 글자 단위로 고정한다)

### 7.1 게이트 A 실패 (`LOSSLESS_VIOLATION`)

```
→ 압축 결과가 원본과 다른 입력을 받게 됩니다. 이것은 mcpeak optimize 의 결함입니다.
→ 도구 '<name>' 의 <path> 에서 '<key>' 가 <사라졌습니다|바뀌었습니다|생겼습니다>.
해결: 오버레이를 쓰지 마세요. 이 메시지와 서버 이름을 이슈로 알려 주세요: https://github.com/2026-Engineering-Contest/MCPeak/issues
```

`<path>`는 `inputSchema.properties.filter.items` 같은 점 경로다. 위반이 여러 개면 둘째 줄을
위반마다 반복하고 최대 5줄, 넘으면 `→ 그 외 N건` 한 줄.

### 7.2 리포트 (`renderReport`)

```
mcpeak optimize 결과
서버 도구 <N>개, instructions <있음|없음>

크기 (UTF-8 바이트, 토큰은 바이트÷4 근사)
  원본            <bytesBefore>  (~<t1> 토큰)
  압축            <bytesAfterWithInstructions>  (~<t2> 토큰, <pct>% 감소)
  instructions 증가분 <delta>  (공통 파라미터 <k>개를 사전으로 옮김)

변환별 기여
  무손실 정규화        -<a> 바이트
  잡음 제거            -<b> 바이트
  공통 파라미터 승격   -<c> 바이트 (사전 +<d> 포함)

가장 많이 줄어든 도구
  <name>  <before> → <after>  (<pct>%)
  (최대 5줄)

전혀 줄지 않은 도구 <m>개

이 오버레이는 tools/list 만 바꿉니다. tools/call 은 원본 이름과 인자로 서버에 전달됩니다.
```

`otherCapabilities`가 비어 있지 않으면 마지막 줄 앞에 다음을 넣는다.

```
주의: 서버가 <resources, prompts> 능력도 광고합니다. 프록시는 tools 만 중계하므로 그 능력은
클라이언트에 보이지 않습니다.
```

퍼센트는 소수 첫째 자리까지, 반올림은 `Math.round(x * 10) / 10`. 토큰 근사는 `Math.round(bytes / 4)`.

### 7.3 프록시 시작 실패

```
→ 오버레이 파일을 읽을 수 없습니다: <path>
→ <원인 한 줄>
해결: mcpeak optimize --out <path> -- <서버 명령> 으로 다시 만드세요.
```

```
→ 오버레이는 도구 <N>개인데 서버는 <M>개를 냅니다.
→ 서버에만 있는 도구: '<a>', '<b>'
→ 오버레이에만 있는 도구: '<c>'
해결: 서버가 바뀌었습니다. mcpeak optimize --out <path> -- <서버 명령> 으로 오버레이를 다시 만드세요.
```

둘째·셋째 줄은 해당 목록이 비어 있으면 생략한다. 이름은 최대 5개, 넘으면 `외 N개`.

```
→ 원본 서버에 붙지 못했습니다: <describeTarget(target)>
→ <core 오류 메시지 첫 줄>
해결: 프록시 없이 같은 명령으로 서버가 뜨는지 먼저 확인하세요.
```

### 7.4 CLI 사용법 오류

`mcpeak optimize`의 사용법 문장:

```
사용법: mcpeak optimize --out <overlay.json> (-- <executable> [args...] | --command <executable> [--arg <value> ...] [--env <NAME> ...] | --url <URL> [--header-env <헤더이름>=<환경변수이름> ...]) [--json]
```

`--out`이 없으면:

```
오류 [CLI_USAGE]: --out <overlay.json> 이 필요합니다. 오버레이를 어디에 쓸지 이 도구는 정하지 않습니다.
해결: mcpeak optimize --out ./server.optimize.json -- <서버 명령>
```

대상 옵션 오류 문장은 `test`·`generate`가 쓰는 `connect-target.ts`의 검증 결과를 그대로 쓴다.
새 문장을 만들지 않는다.
