### 2.1 치환

```bash
git switch -c chore/rename-scope
```

```bash
grep -rl '@ohmymcp/' --exclude-dir=node_modules --exclude-dir=.git --exclude=pnpm-lock.yaml . | xargs sed -i '' 's|@ohmymcp/|@ohmymcp-hsu/|g'
```

- macOS 는 `sed -i ''`, Linux 는 `sed -i` 다.
- `pnpm-lock.yaml` 은 치환하지 말고 아래에서 재생성한다.
- 스코프는 `ohmymcp-hsu` 로 확정됐다 (ADR-0044).

**위 한 줄로는 부족하다.** 실제 실행(PR #173)에서 놓친 것이 나왔다. 정규식 리터럴 안의
스코프는 슬래시를 escape 해서 쓰므로 `@ohmymcp/` 패턴에 걸리지 않는다.

```
packages/generate/tests/dependency-boundary.test.ts
  /^(?:import|export)\s+([^"';]*?)\s+from\s+(["'])@ohmymcp\/runner\2/gm
                                                     ~~~~~~~~~~~~~~~~~~
```

그대로 두면 이 테스트가 **아무것도 수집하지 못한 채** 4 건 실패한다. ADR-0009 의
의존 경계를 코드로 지키는 테스트라, 실패를 "기대값이 안 맞네" 로 넘기면 경계 장치가
통째로 무력화된다. escape 형태를 따로 한 번 더 친다.

```bash
grep -rl '@ohmymcp\\/' --exclude-dir=node_modules --exclude-dir=.git . | xargs sed -i '' 's|@ohmymcp\\/|@ohmymcp-hsu\\/|g'
```

**잔존 확인은 슬래시를 뺀 `@ohmymcp` 로 한다.** 슬래시를 붙여 세면 escape 형태와
`@ohmymcp-examples` 같은 인접 스코프가 안 보인다.

```bash
grep -rn '@ohmymcp' --exclude-dir=node_modules --exclude-dir=.git --exclude=pnpm-lock.yaml . | grep -v '@ohmymcp-hsu'
```

남아야 정상인 것은 `examples/weather-server` 의 `@ohmymcp-examples` 하나다 — 다른
스코프이고 `private: true` 라 발행되지 않으므로 스코프 소유가 필요 없다.

**이름이 길어져 포매터가 다시 감싼다.** import 문이 줄 폭을 넘어 `pnpm lint` 가 실패한다.
`pnpm format` 을 한 번 돌리면 된다 (실제로 3 파일이 바뀌었다). CONTRIBUTING §6 상
포매터 설정이 정답이므로 그대로 따른다.

### 2.3 검증 — 녹색을 봤다고 통과가 아니다

```bash
pnpm build && pnpm typecheck && pnpm lint && pnpm test
```

각각 확인할 것:

- `pnpm test` 출력에 `Test Files ... passed` 줄이 있는지. 스크립트가 없어 즉시 exit 0 이
  나는 경우와 구분한다. **기준값은 개명 직전에 한 번 돌려 직접 잡는다.** 낡은 수를 기준으로
  삼으면 개명이 깬 것과 그 사이 들어온 변경을 구분할 수 없다 — 처음 이 문서를 쓸 때 적은
  1515 는 로컬 main 이 62 커밋 뒤처진 상태의 값이었고, 최신화 후 실제 값은 아래였다.

  ```
  Test Files  82 passed (82)
       Tests  1897 passed | 2 skipped (1899)
  ```

  이 수치도 하루를 못 간다. 처음 1515 로 적었다가 최신화 후 1843 이 됐고, 문서를 쓰는
  사이 origin 이 11 커밋 더 올라가 1897 이 됐다. **그래서 숫자를 믿지 말고 직접 재라는
  것이다.**
- 잔존 참조가 0 인지. `grep -c` 의 종료 코드가 아니라 stdout 건수를 본다:

```bash
grep -rn '@ohmymcp/' --exclude-dir=node_modules --exclude-dir=.git . | wc -l
```

  ADR-0044 이 옛 이름을 의도적으로 인용하므로 **그 파일 안의 건수만 남는 것이 정상**이다.
- 워크스페이스 링크가 새 이름으로 다시 걸렸는지:

```bash
ls -l packages/cli/node_modules/@ohmymcp-hsu/
```

- dist 가 낡지 않았는지. turbo 캐시가 옛 dist 를 복원할 수 있다:

```bash
grep -rl 'ohmymcp-hsu' packages/*/dist/ | head
```

## 3. 배포 런북

### 3.1 사전 준비 (사람)

- [ ] npm 계정 — 이메일 인증 완료, 2FA 활성
- [ ] npm 조직 생성 (이름은 변경 불가)
- [ ] Granular Access Token 발급 — **범위에 다음 여섯이 모두 들어가야 한다.**
      `pnpm release` 는 변경된 공개 패키지 전부를 발행하므로 하나라도 빠지면 그 패키지에서 403 이 난다.

      | 대상 | 비고 |
      |---|---|
      | `ohmymcp` | **무스코프**라 조직 스코프에 안 들어간다. 별도로 포함해야 한다 |
      | `@ohmymcp-hsu/core` `runner` `generate` `record` `mock` | 조직 스코프 선택으로 한 번에 커버된다 |

      - Permissions: **Read and write**
      - Allowed IP ranges: **비운다** (GitHub Actions 러너 IP 는 고정이 아니다)
      - 아직 발행되지 않은 패키지는 선택 목록에 뜨지 않는다. **첫 발행 전에는 "All packages"
        범위가 필요하다.** 발행 후 스코프 단위로 좁힌다.
      - **2FA 관련.** `Require two-factor authentication and disallow tokens` 는 조직 설정이
        아니라 **패키지의 `Publishing access` 설정**이다. 이 설정이 켜진 패키지는 토큰으로
        발행할 수 없다.
      - **이 설정을 내리지 마라.** 보호를 낮추는 방향이다. 토큰 발행이 막히면 대신
        **trusted publishing(OIDC)** 이나 **staged publishing** 으로 간다 (§6 참조).
        첫 발행 전에는 OIDC 설정이 불가하므로, 첫 발행 시점에는 이 설정을 켜지 않은
        상태로 두고 발행 직후 OIDC 로 이전하면서 켜는 순서가 맞다.
      - **교체 절차:** 만료 전에 새 토큰을 발급 → GitHub 시크릿 `NPM_TOKEN` 갱신 →
        release 워크플로 한 번 성공 확인 → npm 에서 옛 토큰 폐기. 순서를 바꾸면 배포가 끊긴다.
- [ ] GitHub 저장소 시크릿 `NPM_TOKEN` 등록
      (Settings → Secrets and variables → Actions)
- [ ] 토큰 값은 어디에도 붙여넣지 않는다 — 시크릿 입력란에 직접

확인:

```bash
npm whoami
```

```bash
npm org ls <조직이름>
```

### 3.2 순서

**⚠️ PR #112 를 그대로 머지하면 안 된다.**

#112(`changeset-release/main`)는 개명 머지 **6 분 전**에 갱신됐다. 그래서 그 브랜치의
`packages/*/package.json` 이 옛 스코프를 들고 있다.

| | 패키지 이름 |
|---|---|
| `main` (개명 후) | `@ohmymcp-hsu/core` v0.2.0 |
| `#112` 브랜치 | `@ohmymcp/core` v0.3.0 ← 개명 이전 |

이대로 머지하면 개명이 되돌려지고, 그 상태로 발행을 시도해 **403** 으로 죽는다
(`@ohmymcp` 스코프는 타인 소유). 일부만 나가고 중간에 실패할 수도 있다.

**남은 순서**

1. **#112 를 닫고 `changeset-release/main` 브랜치를 지운다** — 되살릴 값이 없다.
   changeset 원본은 `main` 의 `.changeset/` 에 그대로 있다.
2. **#171 머지** (본 변경) — publish 가 켜진다. 대기 changeset 이 있으므로 **발행은 아직
   나지 않고**, 액션이 버전 PR 을 새로 만든다.
3. **새 버전 PR 을 눈으로 확인한다** — `packages/*/package.json` 이 `@ohmymcp-hsu/*` 인지,
   버전이 의도한 값인지.
4. **그 PR 머지 → 발행.** 이 시점이 되돌릴 수 없는 지점이다.

> ⚠️ 대기 중인 changeset 이 하나도 없는 상태에서 `main` 을 건드리면 **그 시점의 버전이
> 즉시 발행된다.** 이것이 원래 publish 를 꺼두었던 이유다.
>
> **`.changeset/` 디렉터리가 비어 있는지로 판단하면 안 된다.** 거기에는 `README.md` 와
> `config.json` 이 항상 남아 있어서 "비어 있지 않음" 이 대기 changeset 을 보장하지 않는다.
> 두 파일을 제외한 `.md` 개수를 세야 한다.

```bash
n=$(ls .changeset/*.md 2>/dev/null | grep -cv 'README\.md$'); echo "$n"; [ "$n" -gt 0 ] || echo "★ 대기 changeset 0 — 머지하면 즉시 발행된다"
```

**그리고 대기 changeset 이 가리키는 패키지명이 실재하는지 매번 확인한다.** 개명 이후에도
옛 스코프로 changeset 을 넣는 PR 이 계속 들어온다 — #173 에서 3 개, 그 뒤로 1 개
(`record-boundary-masking.md`)를 더 고쳤다. 존재하지 않는 패키지를 가리키면 changesets 가
버전을 올리려다 실패한다.

```bash
node -e '
const fs=require("fs");
const names=fs.readdirSync("packages").map(d=>JSON.parse(fs.readFileSync(`packages/${d}/package.json`,"utf8")).name);
let bad=0;
for(const f of fs.readdirSync(".changeset").filter(f=>f.endsWith(".md")&&f!=="README.md")){
  const fm=fs.readFileSync(`.changeset/${f}`,"utf8").split("---")[1]||"";
  for(const m of fm.matchAll(/"([^"]+)":\s*(patch|minor|major)/g))
    if(!names.includes(m[1])){ console.log(`★ ${f}: ${m[1]} 는 매니페스트에 없다`); bad++; }
}
console.log(bad?`★ ${bad} 건 — 고치기 전에 발행하지 않는다`:"changeset 패키지명 전부 실재함");
'
```

### 3.4 실패 시

**조건이 발행 후 경과 시간에 따라 다르다.**

| 시점 | `npm unpublish <pkg>@<version>` 조건 |
|---|---|
| **72시간 이내** | 그 버전에 의존하는 다른 패키지가 없으면 된다 |
| **72시간 이후** | ① 의존 패키지 없음 **AND** ② 최근 1주 다운로드 300 미만 **AND** ③ 오너 1명 |

- 조건을 못 채우면 되돌릴 수 없다. `npm deprecate` 로 경고만 붙이고 다음 패치를 낸다.
- **어느 쪽이든 같은 `package@version` 으로 다시 발행할 수 없다.** unpublish 에 성공해도
  그 이름·버전 조합은 영구히 재사용 불가다.
- 그래서 실무상 기대는 "72시간 안에 알아차리면 되돌릴 수 있다" 가 아니라 **"발행은 되돌릴 수
  없다고 보고 그 전에 확인한다"** 다.

## 4. 남은 작업 (배포와 독립)

- **`repository` / `homepage` / `bugs` / `keywords` 필드 6 개** — 각 패키지 오너 담당.
  provenance 생성 자체는 막히지 않지만(npm 이 `GITHUB_REPOSITORY` 환경변수에서 뽑는다)
  npm 페이지에 소스 링크가 안 붙는다. 제안 형태:

  ```json
  "repository": {
    "type": "git",
    "url": "git+https://github.com/2026-Engineering-Contest/MCPeak.git",
    "directory": "packages/<pkg>"
  },
  "homepage": "https://github.com/2026-Engineering-Contest/MCPeak#readme",
  "bugs": "https://github.com/2026-Engineering-Contest/MCPeak/issues"
  ```

- ~~**`ohmymcp-mock --help`**~~ — **고치지 않는다.** 리허설에서 "usage 가 stderr 로 가고
  exit 0" 을 관례 위반으로 적었으나, `packages/mock/src/stdio.ts` 헤더에 의도가 명시돼 있다:
  이 바이너리는 `core.connect()` 가 붙는 stdio 서버이고 **stdout 은 JSON-RPC 채널**이라
  "stdout 에 아무것도 쓰지 않는다" 를 불변식으로 둔다. `--help` 때만 예외를 만들면 지키기
  쉬운 불변식이 조건부가 된다. 종료 코드는 이미 관례대로다(`--help` 0, 인자 없음 1).
  이후에 같은 지적이 다시 나오면 이 문단을 근거로 닫는다.

- **README** — "아직 npm 에 배포되지 않았습니다" 문구 갱신, `npm install` 예시 추가.

### CLI 이름 후보

무스코프 `ohmymcp` 은 `E403`(유사 이름)으로 **쓸 수 없다**(§7.2 ③).

| | 설치 명령 | 라이브러리와의 일관성 | 확실성 |
|---|---|---|---|
| A | `npm i -g @ohmymcp-hsu/cli` | 완전 일치 | **확실** — 스코프 안은 유사 검사를 받지 않는다 |
| B | `npm i -g ohmymcp-cli` | 이름은 통한다 | 높음 (`ohmymcpcli` ≠ `ohmymcp`) |
| D | `npm i -g ohmymcpjs` 등 | 갈린다 | **발행해야 안다** |

세 안 모두 `bin` 은 `ohmymcp` 로 두므로 **설치 후 실행 명령은 `ohmymcp` 로 동일하다.**

실패해도 **이미 나간 6 개는 되돌아가지 않으므로 B·D 를 시도하고 안 되면 A 로 돌아오는 비용은
워크플로 한 바퀴다**(§7.2 ④). 다만 코드 동결이 2026-08-24 이므로 시도 횟수에 여유가 많지 않다.

## 6. 인증 방식과 시한 (2026-08-17 조사)

`npm login` 출력에 뜬 공지를 따라가 확인한 내용이다.

> npm tokens that bypass 2FA are being restricted for account changes and direct publishing.

### 확인된 일정

| 시점 | 내용 |
|---|---|
| 2026-07-31 (적용됨) | 계정·조직·패키지 관리 작업에 대화형 2FA 요구. **발행은 아직 영향 없음** |
| **2027-01 (예정)** | **2FA 우회 토큰이 직접 발행 권한을 잃는다.** 남는 것은 비공개 패키지 읽기와 staged 발행뿐 |

npm 공식 권고: *"You should move automated publishing to trusted publishing (OIDC) or staged publishing."*
이 제한은 npm granular access token 만 대상이다. GitHub PAT·App 토큰·`GITHUB_TOKEN` 은 무관하다.

### 우리 결론

**알파 배포(2026-08)는 NPM_TOKEN 으로 간다.** 직접 발행 제한은 2027-01 예정이라 약 5개월
여유가 있고, 코드 동결(08-24)까지 남은 시간에 새 방식을 검증할 여력이 없다.

**단, 첫 발행 직후 trusted publishing(OIDC)으로 옮긴다.** 이건 선호가 아니라 시한이 있는
필수 이전이다. 첫 발행 전에는 설정할 수 없다 — trusted publisher 는 **패키지가 이미
존재해야** 등록할 수 있어서, 첫 배포는 어떤 경로로든 토큰이 필요하다.

### 이전 시 확인할 것 (미해결)

- **npm CLI 버전.** trusted publishing 은 npm ≥ 11.5.1 · Node ≥ 22.14.0 을 요구한다.
  워크플로의 `node-version: 22` 는 npm 10.x 를 함께 설치하므로 **그대로는 부족하다.**
  이전 시점에 npm 업그레이드 스텝이 필요한지 확인한다.
- **pnpm 경로에서의 OIDC 지원.** 우리 발행 경로는 `changeset publish` → `pnpm publish` 다.
  `npm publish` 기준 문서만 확인했고 pnpm 경로에서 OIDC 가 그대로 동작하는지는 **미확인**이다.
- **staged publishing 검토.** CI 가 2FA 없이 `npm stage publish` 로 올리고 담당자가
  `npm stage approve` 로 승인하는 방식(npm ≥ 11.15.0). "워크플로에서만 배포하되 릴리스
  담당 1명이 관리한다"(§7)는 우리 규약과 개념적으로 가장 잘 맞지만, changesets 가
  `npm stage publish` 를 호출하는 경로를 제공하지 않아 지금은 채택하지 않는다.

출처: [GitHub Changelog 2026-07-31](https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/) ·
[npm trusted publishers](https://docs.npmjs.com/trusted-publishers/) ·
[npm staged publishing](https://docs.npmjs.com/staged-publishing/)

## 7. 실제 발행 경과 (2026-08-18 ~ 08-19)

리허설에서 다 확인했다고 생각했는데 **발행 시도에서 세 번 막혔고, 세 번째가 부분 발행을
남겼다.** 리허설이 재현하지 못하는 것이 무엇인지가 이 절의 요점이다.

### 7.1 세 번의 검증 실패와 그 결과

| # | 오류 | 원인 | 해소 |
|---|---|---|---|
| 1 | `EOTP` | 토큰에 2FA 우회가 꺼져 있었다 | 토큰 재발급 시 `Bypass two-factor authentication` 체크 |
| 2 | `E422` | provenance 검증이 `repository.url` 을 요구 | 7 패키지에 `repository` 추가 (PR #191) |
| 3 | `E403` | `ohmymcp` 이 `oh-my-mcp` 와 유사 이름 | CLI 만 미발행. 이름 재검토 중 |
| 결과 | 부분 발행 | 3 번 때문에 라이브러리 6 개만 나감 | — |

마지막 줄은 네 번째 검증 실패가 아니라 **3 번의 결과**다.

**리허설로는 하나도 재현되지 않았다.** `pnpm pack` → 설치 → 실행은 전부 로컬 파일 경로로
도는 반면, 위 세 오류는 전부 **레지스트리가 받을 때** 판정하는 것이다.

### 7.2 각 실패에서 배운 것

**① 2FA — 토큰의 우회 옵션은 자동이 아니다**

"Granular Access Token 은 2FA 를 우회하도록 설계돼 있다" 고 판단하고 계정 2FA 를
`authorization and publishing` 인 채로 뒀다. 우회는 **토큰 발급 시 체크박스로 켜는 옵션**이다.
켜지 않으면 CI 가 OTP 를 요구받고 `EOTP` 로 죽는다.

**② provenance — `repository` 는 장식이 아니라 검증 대상이다**

`npm/libnpmpublish/lib/provenance.js` 를 읽고 "provenance 는 `GITHUB_REPOSITORY` 환경변수에서
저장소를 뽑으므로 `repository` 필드가 없어도 생성된다" 고 판단했다. **생성은 맞고 검증이 틀렸다.**
레지스트리는 서명된 출처와 `package.json` 의 `repository.url` 을 대조하고, 비어 있으면
`""` 와 실제 URL 이 달라 거부한다.

이슈 #179 에 이 필드가 없다고 적어두고도 "발행을 막지 않는다" 로 분류했다. 그 분류가 틀렸다.

**③ 유사 이름 — 404 는 발행 가능을 뜻하지 않는다**

`registry.npmjs.org/ohmymcp` 가 404 인 것을 보고 "가용" 으로 판단했다. 404 는 **그 이름의
패키지가 없다**는 뜻일 뿐이다. npm 은 발행 시점에 **기존 패키지와의 유사도**를 따로 검사하며,
이 검사는 미리 조회할 방법이 없다.

    ohmymcp     정규화 → "ohmymcp"
    oh-my-mcp   정규화 → "ohmymcp"      ← 충돌

같은 조사에서 `oh-my-mcp` 가 HTTP 200 인 것도 확인했는데 신호로 읽지 못했다.
**`@ohmymcp` 스코프 선점 때와 같은 종류의 오판을 이름에서 한 번 더 했다.**

**④ 부분 발행 — 성공분은 되돌아가지 않지만 changeset 은 이미 소모된 뒤다**

7 개 중 6 개가 나가고 CLI 만 실패했다. changesets 는 성공분을 되돌리지 않고 실패분만 보고한다.

다만 **"버전과 changeset 이 소모되지 않는다" 는 것은 사실이 아니다.** `changeset version` 은
publish 보다 먼저 돌면서 changeset 파일을 소비하고 `package.json` 을 갱신한다. 실패 시점에
`.changeset/` 는 이미 비어 있었고 7 개 버전은 전부 올라가 있었다 — CLI 도 `0.8.0` 인 채로
발행만 실패한 것이다.

그래서 재시도 절차는 이렇다.

- 이미 나간 6 개는 **그대로 둔다.** `changeset publish` 가 이미 발행된 버전을 건너뛴다.
- CLI 만 **이름을 바꿔 현재 버전 그대로** 발행한다. 새 이름에는 아무것도 발행돼 있지 않으므로
  그 버전이 그대로 나간다.
- **`pnpm version-packages` 를 다시 돌리지 않는다.** 소비할 changeset 이 없고, 돌리면 쓸데없이
  버전이 한 칸 더 올라간다.

"잃는 것이 없다" 가 맞는 부분은 **발행된 6 개가 영향을 받지 않는다** 는 것까지다. 이름을 바꿔
재시도하는 비용 자체는 워크플로 한 바퀴다.

### 7.3 리허설을 어떻게 고쳐야 하는가

§1 의 리허설(`pnpm pack` → 빈 디렉터리 설치 → 실행)은 **포장·의존 치환·exports·bin·결정론성**을
검증한다. 그것들은 실제로 한 번도 문제를 일으키지 않았다.

**레지스트리가 판정하는 것은 리허설로 못 잡는다.** 다음 목록은 발행해봐야만 알 수 있다.

- 토큰 권한과 2FA 우회 여부
- provenance 검증 (`repository.url` 대조)
- 이름 유사도 차단
- 스코프 소유 여부

이 중 **이름·스코프는 첫 발행 전에 확정해야 하고**, 나머지는 실패해도 재시도가 가능하다.
따라서 순서는 이렇게 잡는 것이 맞다.

    1. 스코프와 이름을 먼저 확정한다 (되돌릴 수 없음)
    2. 토큰·provenance 는 실패하면 고쳐서 재시도한다 (비용 없음)
