## 구현

`externalSessionNotice` 의 record 갈래 순서는 설계가 정한 그대로다.

1. `interactionCount === 0 && others > 0` (신규): 다른 프로세스가 먼저 기록을 시작했다고 말하고
   녹화하지 못한 호출 수를 싣는다.
2. `interactionCount === 0` (기존 유지): 지원 범위 안내. 한 글자도 바꾸지 않았다.
3. `others > 0` (신규): 부분 녹화 경고.
4. 그 밖: `undefined`.

`EXTERNAL_SCOPE_NOTE` 는 2번에만 붙는다. 경합은 범위 문제가 아니라서 1번·3번에 붙이면 틀린
원인을 가리키게 된다.

`summary.otherProcessCalls` 는 `?? 0` 으로 읽는다. Coordinator 가 자기 거절을 직접 센 값이라
"못 셌음" 갈래가 없고, 그래서 부재와 0 이 같은 뜻이다. 그 근거는 함수 첫 줄 주석에 있다
(`outOfScope` 와 다른 지점이다).

재생 갈래는 한 줄도 건드리지 않았다. `others` 상수는 함수 첫머리에서 계산되지만 재생 경로의
어떤 조건에서도 읽히지 않는다. 이것을 테스트로 고정했다.

## 테스트

설계 §7.4 의 일곱 줄이 다음 케이스로 들어갔다.

| `mode` | `interactionCount` | `otherProcessCalls` | 단언 |
|---|---|---|---|
| record | 0 | 없음 | 기존 `toContain` 둘 + `toBe(RECORD_ZERO_NOTICE)` |
| record | 0 | 0 | `toBe(RECORD_ZERO_NOTICE)` |
| record | 0 | 2 | `다른 프로세스가 먼저` · `2건` 포함, `SCOPE_NOTE` 미포함 |
| record | 3 | 0 | `undefined` |
| record | 3 | 없음 | `undefined` |
| record | 3 | 1 | `외부 호출 1건이 다른 프로세스에서` 포함 |
| replay | 0 | 2 | `toBe(REPLAY_ZERO_NOTICE)` |

"기존 문장" 줄은 기존 단언을 그대로 둔 채 전체 문자열 비교를 더했다. `toContain` 만으로는
문장 앞뒤에 무엇이 붙어도 통과하므로 한 글자도 달라지지 않았음을 못 본다. 그래서 기대 문자열을
테스트 파일에 상수로 적어 두고 `toBe` 로 비교한다.

마지막 줄이 회귀 방어다. `replay(0, 0, 0, 2)` 가 기존 재생 0건 문장과 정확히 같아야 한다.

헬퍼 `record` · `replay` 에 선택 인자 `otherProcessCalls` 를 더했다. 인자를 안 주면 스프레드로
필드 자체를 빼서 "없음" 과 "0" 을 실제로 구분한다. `undefined` 를 그냥 실으면 두 줄이 같은
입력이 돼 표의 두 행이 한 행이 된다.

## 남은 위험

- 이 태스크는 문안만 바꾼다. `otherProcessCalls` 를 실제로 채우는 것은 `record` 쪽
  Coordinator 의 몫이라(ADR-0095), 그쪽이 들어오기 전까지 신규 두 갈래는 실행 경로에서
  발화하지 않는다. 이 worktree 의 단언은 순수 함수 수준까지다.
- 부분 녹화 갈래(`interactionCount > 0 && others > 0`)는 `bodyUrlNotice` · `outOfScopeNotice`
  와 같은 실행에서 함께 나갈 수 있다. 축이 다르므로 의도된 것이지만, 세 알림이 한 화면에
  겹쳤을 때의 실제 출력은 E2E 가 붙은 뒤에 눈으로 확인하는 편이 낫다.
