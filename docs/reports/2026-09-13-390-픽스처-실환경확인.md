# #390 실환경 확인: 픽스처가 지어낸 값을 대신한다

대상 서버는 `examples/weather-server` 다. `examples/zod-notes-server` 로 먼저 시도했다가
바꿨고, 그 이유를 아래 §3 에 적었다. 바꾼 판단 자체가 이 이슈의 요점을 드러낸다.

실행은 T1·T2 가 머지된 `12d9758` 기준이다. T3(되돌리기)은 이 확인에 관여하지 않는다.
픽스처가 **생성에** 먹히는지를 보는 것이기 때문이다.

## 1. 대조군: 픽스처 없이

`get_weather.city` 는 `examples` 도 `enum` 도 없는 순수 문자열이라 생성기가 `"example"` 을
지어낸다. 모양은 맞고 실재하지 않는 값이다.

```
✗ get-weather-success       get_weather가 오류 없이 응답한다
    isError  정상 응답을 기대했지만 오류 응답을 받았습니다.
    → 'example' 의 날씨 데이터가 없습니다. 사용 가능한 도시: 서울, 부산, 제주

7 passed, 1 failed  (8 total)
```

이것이 이슈가 말하는 상태다. 서버는 멀쩡한데 정상 케이스가 빨갛다.

## 2. 실험군: 픽스처로

```json
{
  "schemaVersion": 1,
  "tools": { "get_weather": { "city": "서울" } },
  "notes": { "get_weather": { "city": "서버가 가진 도시는 서울·부산·제주 뿐이다." } }
}
```

```
▸ 픽스처: .../weather.fixtures.json (도구 1개, 필드 1개)
8 passed  (8 total)
```

생성된 명세의 `city` 가 `"example"` 에서 `"서울"` 로 바뀌었고, 같은 서버에서 전건 통과한다.

## 3. zod-notes-server 가 이 확인의 대상이 아닌 이유

처음에는 `create_note.parentId` 로 시연하려 했다. 그 서버는 없는 id 를 받으면
`→ 상위 노트 '...' 가 없습니다` 로 거절하고, 실재하는 노트는 하나뿐이다.

**그런데 대조군에서 `parentId` 가 아예 안 나온다.** 선택 필드이고 기준 정상 입력은 필수
필드만 담기 때문이다. 즉 픽스처가 없으면 그 필드는 틀린 값으로 실패하는 것이 아니라
**시험되지 않는다.**

픽스처를 주면 값이 기준 정상 입력에 들어가고 45개 케이스 중 27개로 퍼진다. 파생 케이스가
전부 그 값을 물려받기 때문이다. 이쪽은 "실패하던 것이 통과한다" 가 아니라 **"안 보던 것을
보게 된다"** 는 다른 이득이다. 둘 다 이 기능의 값어치지만, 이슈의 완료 조건
("잘못된 데이터를 서버 결함과 구분한다") 을 보이는 것은 앞쪽이라 대상 서버를 바꿨다.

`zod-notes-server` 는 도그푸딩 E2E 의 기준이라 baseline 이 전건 통과하도록 만들어져 있다.
통과하도록 만든 서버에서 실패를 시연할 수 없는 것은 당연하다.

## 4. 재현

```sh
node packages/cli/dist/cli.mjs generate --suite-id weather --name Weather \
  --out w.json --command "$(which node)" --arg examples/weather-server/server.mjs \
  --baseline-only --force [--fixtures weather.fixtures.json]
node packages/cli/dist/cli.mjs test w.json --command "$(which node)" \
  --arg examples/weather-server/server.mjs
```

실제 서버 프로세스를 띄우므로 직렬로 돌린다.
