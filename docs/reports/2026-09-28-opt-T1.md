## 4. 임의로 판단한 부분

1. **§3.2 B-2 의 `e.g.` 정규식을 글자 그대로 옮겼다. 계획서 산문과 어긋난다.** 정규식
   `/\s*(?:\bExamples?|\be\.g\.|\bFor example|\bExample usage)[:.][\s\S]*$/i` 는 `e.g.` 뒤에 `[:.]`
   를 한 번 더 요구한다. 그래서 `e.g.: foo` 는 지우고 가장 흔한 `e.g. foo` 는 지우지 않는다. 산문은
   "`e.g.` 이하도 지운다"고 적었다. 정규식을 택한 이유는 두 가지다. 계획서가 정규식을 코드로 못
   박았고, 안전 근거가 된 `safe.mjs` 는 파라미터에도 `e.g.` 를 아예 지우지 않았으므로 덜 지우는
   쪽이 실측 근거에 더 가깝다. 테스트 `파라미터 설명의 'e.g.' 이하는 지운다` 는 `e.g.:` 형태로
   단언하고, `e.g. 'red'` 가 남는다는 사실도 같은 it 안에 주석과 함께 고정했다. **오케스트레이터가
   어느 쪽이 의도인지 정해야 한다.** 산문 쪽이면 정규식을 `\be\.g\.(?=\s)` 식으로 바꾸고 테스트
   입력을 고치면 된다.
2. **기대 오버레이는 파일 글자가 아니라 compact 직렬화로 비교한다.** `pnpm lint`(biome) 가
   `tests/fixtures/*.json` 을 자기 형식으로 다시 써서 `JSON.stringify(x, null, 2)` 와 글자가 달라진다.
   루트 `biome.json` 은 수정 금지라 overrides 를 넣지 못했다. 테스트는
   `JSON.stringify(optimize(...)) === JSON.stringify(JSON.parse(파일))` 로 비교한다. JSON.parse 는 키
   순서를 보존하므로 키 순서와 값은 바이트 단위로 고정되고, 들여쓰기만 풀린다. 파일 글자 비교가
   꼭 필요하면 `biome.json` 에 `packages/optimize/tests/fixtures/**` formatter 끄기 override 를 더하는
   것이 방법이다(`generate/tests/fixtures/sdk-schemas/**` 선례가 있다).
3. **데이터 키워드 안으로 재귀하지 않는다.** §3.1 은 "그 외 모든 키는 값에 재귀"라고 적었지만,
   그러면 `default: { "title": "x" }` 같은 사용자 값 안의 `title` 이 메타 키로 지워져 §3.4(`default`
   변경 금지)를 어긴다. `default`, `enum`, `const`, `examples`, `example` 는 값을 그대로 옮기고,
   게이트도 이 키들은 허용 차이 없이 엄격 비교한다.
4. **이름 사전 키워드를 다섯 개로 넓혔다.** §3.1 표의 `properties`·`$defs`·`definitions` 에
   `patternProperties`·`dependentSchemas` 를 더했다. 같은 "이름 → 스키마" 모양이라, 빼면 패턴 키가
   `title` 인 경우 메타 키로 지워진다. 변환기와 게이트가 같은 집합(`NAME_MAP_KEYS`)을 쓴다.
5. **이름 되풀이 판정은 중첩 `properties` 에도 적용한다.** `$defs.X.properties.label` 처럼 안쪽
   `properties` 사전의 직속 항목은 이름이 있으므로 4를 적용한다(`safe.mjs` 와 같다). 이름을 모르는
   것은 `$defs` 항목 자체, `items`, `anyOf` 원소다. 속성 이름의 영숫자가 비어 있으면(예: `_`) 빈
   문자열이 모든 설명에 포함되므로 판정하지 않는다.
6. **루트 `inputSchema.description` 에도 B-2 의 1·2·3 을 적용한다.** 계획서가 명시하지 않았고
   `safe.mjs` 의 동작을 따랐다.
7. **도구 설명이 정리 후 빈 문자열이면 키를 지운다**(`description-removed`, reason `empty`). B-1 에는
   빈 결과 처리가 없어 B-2 의 5와 맞췄다. 게이트 허용 차이 4에 들어간다.
8. **`changes` 의 경로 규칙.** `schema-key-removed` 는 `path` 가 키를 담은 객체의 경로이고 `key` 가
   따로 있다(§7.1 의 `<path>` 에서 `'<key>'` 와 같은 구조). description 계열은 `path` 가 description
   필드 자체의 경로다(`description`, `inputSchema.properties.id.description`). 배열 원소는 인덱스를
   경로 조각으로 쓴다(`inputSchema.anyOf.0`).
9. **게이트 A 의 도구 단위 위반 문장.** §7.1 은 스키마 위치만 예로 든다. 도구가 빠지거나 생기면
   `→ 도구 'x' 의 tools 에서 'x' 가 사라졌습니다.` 로, 이름 집합은 같고 순서만 다르면
   `→ 도구 'x' 의 tools.<i> 에서 'name' 가 바뀌었습니다.` 로, 도구 최상위 키(`outputSchema` 등)는
   경로 자리에 키 이름을 쓴다. 이름이 바뀐 경우는 사라짐 1줄 + 생김 1줄이다.
10. **바이트 기준.** `{name, description, input_schema}` 에서 description 이 없으면 `""` 로 센다
    (`tok.mjs` 와 같다). `source.bytes` 는 `totals.bytesBefore` 와 같은 값(도구만, instructions 제외)으로
    두었다. §5.1 이 이 필드의 뜻을 적지 않았다.
11. **`parseOverlay` 오류 문장**은 `<sourceLabel>: '<필드>' 값이 형식에 맞지 않습니다. 기대: ..., 실제: ...`
    한 줄이다. §7.3 의 `<원인 한 줄>` 자리에 T3 가 그대로 넣는 것을 전제로 했다. §8 에 이 함수의
    테스트가 없고 허용 테스트 파일에도 자리가 없어 **유닛테스트 없이** 수동 확인만 했다.
12. **픽스처 세부.** `note` 는 get/update/delete 세 도구가 같은 설명(39자)으로 갖고 archive_item 만
    다른 설명이다. §8.1 의 "archive_item 만 note 를 다른 설명으로 가짐" 을 "나머지 셋은 공통 설명"
    으로 읽었다. 그래서 승격이 workspaceId 하나가 아니라 둘이다.

## 5. 남은 위험

- 위 4-1 의 `e.g.` 정규식 문제. 산문 의도대로라면 절감률 추정(13.9%)에 파라미터 `e.g.` 삭제분이
  들어가 있었는지부터 확인해야 한다. `safe.mjs` 기준이라면 들어가 있지 않다.
- 기대 오버레이 비교가 들여쓰기를 보지 않는다(4-2). 결정론성 판정에는 영향이 없다.
- `parseOverlay` 는 유닛테스트가 없다(4-11). T3·T4 가 쓰는 시점에 테스트를 붙이는 편이 안전하다.
- 게이트는 `changes`·`bytes` 필드를 검사하지 않는다. 프록시가 이 둘을 내보내지 않는다는 §6 의
  전제에 기댄다.
- T2 의 리포트 기대 숫자는 이 기대 오버레이(2875 / 2028 / 2177, 승격 2)에 맞춰야 한다(§9.2 대로 T4).
