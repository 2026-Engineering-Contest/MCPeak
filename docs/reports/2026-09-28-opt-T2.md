## 측정 방식

- 도구 크기: `{name, description, input_schema}` 를 `JSON.stringify` 로 compact 직렬화한 UTF-8
  바이트. description 이 없으면 키째 빠진다.
- 잡음 제거: `description-cleaned` 는 전후 문자열의 JSON 직렬화 바이트 차. `description-removed`
  중 reason 이 `restates-name`, `empty` 인 것은
  `"description":<JSON 문자열>` 바이트에 쉼표 1을 더한 값.
- 공통 파라미터 승격: reason 이 `promoted` 인 `description-removed` 를 같은 식으로 센 뒤, 사전 크기
  (`bytesAfterWithInstructions - bytesAfter`)를 뺀 순감소.
- 무손실 정규화: `schema-key-removed` 와 reason 이 `duplicate-of-tool-description` 인
  `description-removed`(계획서 §3.1) 가 여기 속한다. `schema-key-removed` 는 지운 값을 싣지 않아 직접 셀 수 없다. 그래서 도구 전체 감소
  (`bytesBefore - bytesAfter`)에서 잡음 제거와 승격 제거분을 뺀 나머지로 둔다. 이 덕분에 세 줄의
  합은 언제나 `bytesBefore - bytesAfterWithInstructions` 와 정확히 같다.

## 임의로 판단한 부분

1. ~~`duplicate-of-tool-description` 을 잡음 제거로 셌다.~~ 검토에서 반려되어 계획서 §3.1 대로
   무손실 정규화로 옮겼다(아래 "검토 반영" 참고).
2. **삭제 키의 쉼표 1바이트를 항상 더한다.** `description` 이 객체의 유일한 키였으면 1바이트 과대
   계상이고, 그 오차는 무손실 정규화 쪽이 떠안는다(합계는 정확).
3. **퍼센트를 `toFixed(1)` 로 적는다.** `Math.round(x*10)/10` 뒤에 소수 첫째 자리를 항상 찍어
   `10.0%` 처럼 나온다. 분모가 0 이면 `0.0`.
4. **음수 기여는 `+n` 으로 적는다.** 사전이 지운 설명보다 크면 승격 줄이 `+n 바이트` 가 된다.
   `--n` 을 피하기 위해서다.
5. **"가장 많이 줄어든 도구" 에는 감소량이 0 보다 큰 도구만 올린다.** 줄지 않은 도구(늘어난 도구
   포함)는 "전혀 줄지 않은 도구 m개" 로만 센다. 모든 도구가 줄지 않았으면 제목 아래가 비어 있다.
6. **주의 문단 배치.** 계획서의 두 줄 문안(줄바꿈 위치 포함)을 그대로 쓰고, 앞 문단과 마지막 줄
   사이에 빈 줄로 구분해 넣었다. 능력 이름은 `otherCapabilities` 순서대로 `, ` 로 잇는다.
7. **instructions 있음/없음은 원본 `source.instructions` 가 빈 문자열인지로 판정한다.**
8. `measure.ts` 의 `measureToolBytes` 를 공개 함수로 두었다. T1 이 바이트 계산에 재사용할 수 있지만
   `index.ts` 에서 re-export 하지는 않았다(수정 금지).

## 남은 위험

- 기대 리포트는 코드 안에서 만든 합성 오버레이 기준이다. T1 의 실제 `synthetic.expected.overlay.json`
  이 나오면 T4 가 픽스처를 갱신해야 하고, 그때 `changes` 의 path 형식이나 reason 사용이 이 테스트의
  가정과 다를 수 있다.
- T1 이 `bytes` 를 다른 방식(예: 도구 description 의 undefined 처리)으로 계산하면 무손실 정규화 줄이
  그 차이를 흡수해 이상한 값(음수 포함)이 될 수 있다. T1 이 `measureToolBytes` 를 쓰면 사라진다.
