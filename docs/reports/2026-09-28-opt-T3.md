## 프로토콜 판단

### 1. 능력 광고 범위: `tools: {}` 만

- `tools` 만 광고한다. 프록시가 중계하는 메서드는 `tools/list`·`tools/call` 둘뿐이라, 상류가 가진
  `resources`·`prompts`·`logging`·`completions` 를 광고하면 클라이언트가 부를 수 없는 메서드를 약속하게 된다(§1.2, §6.4).
- `tools.listChanged` 도 광고하지 않는다. 오버레이는 고정 파일이라 프록시가 내는 목록은 바뀌지 않는다.
  상류의 `notifications/tools/list_changed` 는 core 의 `McpClient` 가 노출하지 않아 받을 수도 없다.
- `instructions` 는 `overlay.instructions`. **빈 문자열이면 필드를 싣지 않는다.** 원본에 없던 빈 필드를
  새로 만들지 않기 위해서다(판단).
- `serverInfo` 는 `{ name: "mcpeak-optimize-proxy", version: "0.0.0" }`. mock 의 `mcpeak-mock`/`0.0.0` 과 같은 방식이다.
  core 가 상류의 `serverInfo` 를 노출하지 않아 원본 이름을 흉내 낼 수 없고, 흉내 내는 것이 옳은지도 결정된 바 없다(판단).
- `tools/list` 는 한 페이지로 전부 낸다(cursor 없음). `changes`·`bytes` 는 싣지 않고, 없는 `description`·`outputSchema` 는 키째 뺀다.

### 2. 상류 오류 전달 방식

- **도구 실행 오류(`isError: true`)**: 상류의 `ToolResult.raw` 를 그대로 돌려준다. `content`·`isError` 로
  다시 조립하지 않는다. 조립하면 `structuredContent`·`_meta` 같은 나머지 필드가 조용히 사라진다.
  e2e 가 스키마 위반·필수 인자 누락·데이터 없음 세 경우에서 raw 째 동일함을 단언한다.
- **인자 검증 없음**: 프록시는 인자를 보지 않는다. 오버레이에 없는 도구 이름도 그대로 넘긴다.
  "모르는 도구" 판정도 상류의 몫이다(수동 확인: `nope` 호출에 weather-server 의 문장이 그대로 나감).
- **`arguments` 생략은 `{}` 로 바꿔 넘긴다(판단).** core 의 `callTool` 이 객체를 요구하고
  (`INVALID_TOOL_ARGUMENTS`), `McpClient` 는 동결이다. MCP 에서 인자 없는 호출은 보통 빈 객체와 같은 뜻이지만,
  `undefined` 와 `{}` 를 다르게 다루는 서버(zod 로 `arguments` 전체를 파싱하는 경우)에서는 결과가 달라질 수 있다.
- **상류가 JSON-RPC 오류로 답한 경우**: core 가 `McpClientError(OPERATION_FAILED)` 로 감싸고 `cause` 에 SDK 의
  `McpError` 를 둔다. 프록시는 그 `code`·`data` 를 그대로, `message` 는 SDK 가 붙인 `MCP error <code>: ` 접두어를
  떼어 되돌려준다. 떼지 않으면 받는 쪽 SDK 가 한 번 더 붙여 접두어가 두 겹이 된다. 타임아웃(`-32001`)도 같은 경로다.
  **이 갈래는 테스트로 고정하지 못했다.** weather-server 는 모든 실패를 `isError` 결과로 답해 JSON-RPC 오류를 낼 수단이 없다.
- **연결 자체가 끊긴 경우**: 전달할 원본 오류가 없으므로 `-32603 InternalError` 에 `원본 서버 호출 실패: <core 문장>` 을
  싣는다. 프로세스 종료(`PROCESS_EXITED`)면 곧바로 아래 3의 종료 절차를 시작한다.

### 3. 시작·종료 순서

시작:

1. bin 이 인자를 파싱한다. 오버레이를 읽기 **전에** 대상부터 파싱한다. §7.3 첫 문장의 "해결" 줄에 서버 명령을 넣어야 해서다.
2. 오버레이를 읽고 최소 형식을 검사한다(`schemaVersion === 1`, `tools` 배열과 각 항목의 문자열 `name`,
   `source.toolNames` 문자열 배열, `instructions` 문자열). 실패하면 §7.3 첫 문장, 종료 코드 1.
3. `connectStdio`/`connectHttp` 로 상류에 붙는다. 실패하면 §7.3 셋째 문장, 종료 코드 1.
4. `listTools()` 이름 정렬 목록을 `source.toolNames` 정렬본과 비교한다. 다르면 **상류를 먼저 닫고** §7.3 둘째 문장,
   종료 코드 1. 닫지 않으면 자식 프로세스가 bin 의 종료를 붙잡는다.
5. 대조가 통과한 뒤에야 `StdioServerTransport` 를 붙인다. 그래서 시작 실패에서는 stdout 이 0 바이트다(e2e 가 단언).

시작 후 종료는 `watchLifecycle` 한 곳에서 한 번만 돈다.

- **클라이언트가 stdin 을 닫음**: 서버를 닫고, 상류를 정상 종료(`close()`, 실패하면 `forceClose()`)한 뒤 0.
  MCP stdio 규약에서 클라이언트가 서버를 끝내는 첫 수단이 입력 스트림을 닫는 것이다.
- **SIGINT·SIGTERM**: 같은 순서로 상류를 정리하고 `128 + 시그널 번호`(SIGTERM 은 143). 규약상 stdin 닫기 다음 수단이 SIGTERM 이다.
- **상류 프로세스 사망(stdio 만)**: stderr 에 `→ 원본 서버가 끝나서 프록시도 끝냅니다 (종료 코드 N): <명령>` 한 줄,
  상류와 같은 종료 코드(§6.7). 시그널로 죽었으면 `(시그널 X)` 로 적고 `128 + 번호`.
  core 의 stdio 연결은 종료 이벤트를 내보내지 않아 **진단 스냅샷을 100ms 마다 읽어** 알아챈다(unref 된 타이머라
  프로세스를 붙잡지 않는다). 호출 중에 `PROCESS_EXITED` 를 받으면 폴링을 기다리지 않고 바로 시작한다.
  이 간격은 알아채는 시점만 바꾸고 내는 바이트는 바꾸지 않는다.
- **HTTP 상류**: 지켜볼 프로세스가 없다. 호출 실패는 그 호출의 오류로만 답하고 계속 돈다.
- stderr 마지막 줄은 쓰기 콜백 안에서 `process.exit` 한다. macOS 에서 파이프 쓰기는 비동기라 바로 끝내면 잘릴 수 있다.

## 임의로 판단한 부분

1. **`serveProxy` 가 프로세스 수명을 책임진다.** `ProxyOptions` 에 종료 훅이 없고 stdio 를 차지하는 서버라,
   종료 시 `process.exit` 를 이 함수가 부른다. 시작 실패는 `OptimizeError`(`UPSTREAM_UNAVAILABLE`·`OVERLAY_UPSTREAM_MISMATCH`)
   로 던지고 bin 이 stderr·종료 코드로 옮긴다.
2. **내부 함수 `startProxy(options, { overlayPath })` 를 따로 뒀다.** §7.3 의 "해결" 줄에 오버레이 경로가 필요한데
   `serveProxy` 는 파싱된 오버레이만 받는다. 공개 시그니처를 넓히지 않으려고 bin 만 경로를 넘긴다.
   라이브러리로 부르면 그 자리에 `<overlay.json>` 이 찍힌다. `index.ts` 는 건드리지 않았으므로 공개 API 는 그대로다.
3. **bin 은 자기 환경 변수 전부를 상류에 넘긴다.** MCP 클라이언트는 설정의 `env`(API 키 등)를 이 프록시에 싣는데,
   그것은 원래 원본 서버에 주려던 값이다. core 기본값(SDK 허용 목록)만 넘기면 프록시를 끼우는 순간 상류가 키를 잃는다.
   `serveProxy` 자체는 받은 `ConnectOptions` 를 그대로 쓴다.
4. **`--url` 대상의 "해결" 줄**은 `-- <서버 명령>` 대신 `--url <URL>` 로 적는다. 템플릿을 그대로 쓰면 HTTP 서버에 대해
   실행할 수 없는 명령을 안내하게 된다. stdio 대상은 템플릿과 글자 단위로 같다.
5. 서버 명령 표기는 cli `describeTarget` 과 같이 공백으로 잇기만 한다(따옴표 처리 없음). 같은 대상이 도구마다 다르게 적히지 않게 맞췄다.
6. 오버레이 파일 읽기 실패의 원인 줄이 `→ ` 로 시작하면 떼고 붙인다. T4 가 `parseOverlay` 로 바꿀 때 `→ →` 가 되지 않게 미리 막았다.
7. **소스 기준 e2e 배선.** 프록시는 `@mcpeak/core` 를 **런타임에** import 한다(mock 은 타입만). CI verify 는 빌드 없이
   `pnpm test` 를 돌리므로 dist 가 없다. 그래서 `proxy-entry.mjs` 가 `module.registerHooks`(Node 22.15+, 동기 in-thread)
   로 `@mcpeak/core` → `packages/core/src/index.ts`, 상대 `.js` → `.ts` 를 잇는다. mock 의 `register-ts-resolve.mjs` 는
   베어 명세자를 다루지 않고 다른 패키지 파일이라 쓰지 않았다. 또 core 소스에 매개변수 프로퍼티가 있어 strip-only 로는
   `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` 로 죽으므로 자식을 `--experimental-transform-types --no-warnings` 로 띄운다.
   CI 매트릭스의 하한 22.18.0 이 두 기능을 모두 가진다. **저장소에 이 조합의 선례는 없다.** 로컬은 Node 24.14.1 로만 확인했다.
8. 테스트 오버레이는 원본과 **일부러 다르게** 만든다(설명 앞에 `(압축) `, 파라미터 설명 제거). 같으면 프록시가
   오버레이를 냈는지 상류 목록을 흘렸는지 첫 테스트가 가르지 못한다. 그 전제도 단언한다.
9. 상류 사망 테스트는 weather-server 를 `-e` 로 감싸 **`tools/call` 이 들어오는 순간** 종료 코드 3 으로 끝나게 한다.
   시각이 아니라 요청으로 죽여 느린 CI 에서도 순서가 같다. 새 픽스처 파일은 만들지 않았다.

## 남은 위험

1. **JSON-RPC 오류 원형 전달은 테스트가 없다**(위 2). 코드 경로는 SDK 1.30.0 의 `McpError` 형식(`MCP error <code>: `)에
   기대고 있다. 이 형식이 바뀌면 접두어가 두 겹이 된다. T4 의 e2e 나 mock 상류로 고정할 것을 권한다.
2. **상류 stderr 가 보이지 않는다.** core 가 상류 stderr 를 버퍼에만 담고 흘려보내지 않는다. MCP 클라이언트의 서버 로그 창에
   원본 서버의 로그가 안 나온다. 상류가 죽을 때도 §6.7 대로 한 줄만 남긴다. core 에 stderr 전달 옵션이나 종료 이벤트가
   생기면 폴링과 함께 풀린다(core 는 이 태스크의 Files 밖이라 제안만 한다).
3. **중계하지 않는 것**: 진행 알림(`progressToken`), 취소(`notifications/cancelled` 는 프록시 쪽 핸들러만 멈추고 상류 호출은
   계속됨), 상류의 `tools/list_changed`, `logging`. core `McpClient` 가 그 수단을 노출하지 않는다. 상류 호출은 SDK 기본
   60초 타임아웃을 따르며, 넘으면 `-32001` 이 원형대로 전달된다.
4. §7.3 둘째 문장은 이름이 바뀌었을 뿐 개수가 같으면 "오버레이는 도구 2개인데 서버는 2개를 냅니다." 가 된다. 계획서 문안
   그대로 두었다. 개수가 같을 때 첫 줄을 바꿀지는 T4·계획서에서 정할 문제다.
5. §7.3 셋째 문장의 "프록시 없이 같은 명령으로 서버가 뜨는지" 는 `--url` 대상에서는 "명령" 이 맞지 않는다. 문안 그대로 두었다.
