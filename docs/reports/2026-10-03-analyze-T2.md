## 임의로 판단한 부분

1. **`runOptimizeCommand` 를 값으로 import 했다.** §5.1 코드 블록은 `import type { runOptimizeCommand }` 이지만,
   §5.3 이 "기본값은 `@mcpeak/cli/commands` 의 `runOptimizeCommand`" 라고 정하므로 기본 runner 로 쓰려면 값이
   필요하다. `wiring.ts` 가 같은 패키지에서 `runCli` 등을 값으로 정적 import 하는 것과 같은 꼴이다.
   `OptimizeCommandDependencies` 는 타입으로 함께 import 했다.
2. **`analyze.ts` 의 기본 로더**는 `wiring.ts` 의 `defaultLoaders` 와 같은 꼴(`() => import("@mcpeak/core")`,
   `() => import("@mcpeak/optimize")`)로 두고 `{ ...defaultLoaders, ...overrides.loaders }` 로 합친다.
   §5.2 는 `loaders.loadCore()` 만 적고 합치는 방식을 적지 않았다.
3. **routes 테스트의 `.mcp.json` 값 `${API_KEY}`** 를 템플릿 리터럴 안의 이스케이프(`` `\${API_KEY}` ``)로 적었다.
   평문 문자열이면 biome `noTemplateCurlyInString` 경고가 난다. `files.test.ts` 의 `ref()` 와 같은 이유다.
   만들어지는 문자열은 계획서의 `"${API_KEY}"` 와 같다.
4. **routes 테스트 단언을 계획서보다 조금 넓혔다.** 본문이 JSON 이 아님·argv 형식 오류에서도 fake 호출 0회를,
   오버레이 형식 오류에서 파일이 생기지 않았음을 함께 단언한다. 사양과 충돌하지 않는 추가 단언이다.
5. **`ANALYZE_RUNTIME_UNAVAILABLE` 테스트**에 runner 호출 0회 단언을 더했다.
6. 분석 응답의 성공 본문(`ANALYZE_BODY`)은 형식 검사가 없는 fake 값이라 `as unknown as AnalyzeTokensResponse`
   로 캐스팅했다. 라우트는 본문을 해석하지 않고 그대로 넘기므로 실제 오버레이 모양이 필요 없다.

## 남은 위험

- 실제 서버를 대상으로 `overlayText` 가 CLI `--out` 바이트와 같은지(§1.3-1·2)는 이 태스크에서 확인하지 않았다.
  T4 의 E2E 몫이다. 유닛테스트는 `generatorVersion` 출처와 메모리 캡처 배선까지만 단언한다.
- `api-types.ts` 가 이제 `@mcpeak/optimize` 를 타입 import 한다. web 쪽 typecheck(`tsc -p web/tsconfig.json`)는
  녹색이지만, T3 이 웹 번들에서 이 타입을 쓸 때 값 import 가 섞이지 않는지는 T3 리뷰에서 볼 일이다.
- `.mcp.json` 후보 env 의 해석은 기존 `resolveCandidateEnv` 를 그대로 쓴다. 분석 경로만의 새 규칙은 없다.
