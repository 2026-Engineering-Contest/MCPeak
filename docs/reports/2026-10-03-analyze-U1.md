## 임의로 판단한 부분

1. `analyze.test.ts` 의 기존 단언 `expect(seen.deps?.optimize).toBe(optimize.optimize)` 는 감싸기 때문에 성립하지 않는다. 이것을 `renderReport` 동일성 단언으로 바꾸고, `deps.optimize 는 optimize.optimize 에 같은 인자를 넘기고 그 반환값을 돌려준다` 테스트를 새로 더해 위임을 검증했다.
2. 계획서 §4 목록에 없는 `원본을 찾지 못하면 그 자리에 안내 문장을 보인다` 뷰 테스트를 더했다(§3.3 분기 검증).
3. 뷰 픽스처의 도구 `a` 를 `description: "A"`, 압축 `inputSchema: { type: "object" }`, 원본은 거기에 `$schema` 가 붙은 모양으로 바꿨다. 기존 숫자 단언에는 영향이 없다.
4. 레이아웃·클래스:
   - 여섯째 열 폭 `w-32`, 버튼은 `Button size="sm"`, 기본 variant(secondary). `Button` 주석이 새 버튼은 sm·md 중에 고르라고 해서다.
   - 펼침 칸은 `bg-canvas px-4 py-3`, 안쪽은 `grid grid-cols-2 gap-4`, 각 칸 `min-w-0`(표가 `table-fixed` 라 긴 JSON 이 칸을 밀지 않게). 제목은 `text-caption font-medium text-ink-muted`.
   - `<pre>` 는 `overflow-x-auto whitespace-pre rounded-sm border border-line bg-surface px-3 py-2 font-mono text-xs text-ink`.
   - 변경 목록은 `list-disc pl-5 text-sm`, 항목 키는 순서 인덱스(같은 문장이 반복될 수 있음, biome-ignore 주석).
   - `← 서버 다시 고르기` 는 기본 variant 버튼이고 결과 위에 따로 둔다.
5. `aria-controls`/`id` 의 `<index>` 는 정렬 전 인덱스다(React 키와 같은 값). 펼침 상태는 계획서대로 도구 이름 집합이라, 이름이 겹치는 서버면 같은 이름 행이 함께 펼쳐진다.
6. 결과 단계에서 폼을 그리지 않으므로 `StepRunServer` 가 언마운트된다. 상태는 `TokensPanel` 의 `state` 에 있어 돌아와도 유지됨을 테스트로 확인했다.

## 남은 위험

- 실제 브라우저로 화면을 띄워 보지는 않았다. 펼침 칸의 가로 폭(긴 스키마)은 jsdom 으로 검증되지 않는다.
- 이름이 같은 도구가 둘 있으면 펼침이 함께 움직인다(계획서 결정 그대로).
- 응답 본문이 `sourceTools` 만큼 커진다. 결정론은 e2e 의 "같은 요청 두 번 바이트 동일" 이 통과해 유지된다.
