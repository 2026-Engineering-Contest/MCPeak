## 임의로 판단한 부분

1. **LCS 동률 규칙의 방향.** 계획서는 "앞쪽 줄을 먼저 맞춘다" 라고만 적었는데, 원본의 앞 줄인지 압축의 앞 줄인지에 따라 결과가 갈린다(`"a\nb"` 대 `"b\na"`). **원본의 앞쪽 줄을 먼저 맞추는** 쪽으로 정했다. 길이가 같으면 압축 쪽 줄을 added 로 먼저 넘긴다. 테스트 `LCS 가 여럿이면 원본의 앞쪽 줄을 먼저 맞춘다` 가 이 방향을 고정한다. 반대가 의도였다면 `diffLines` 의 비교 한 줄(`>=`)과 그 테스트를 바꾸면 된다.
2. **`<pre>` 안에 감싸는 `<span>` 하나.** 계획서는 `<pre>` 가 줄마다 `<span>` 을 그린다고만 했다. 줄 `<span>` 들을 `block w-max min-w-full` 인 `<span>` 하나로 감쌌다. `<pre>` 가 `overflow-x-auto` 라서, 감싸지 않으면 가로로 밀었을 때 배경색이 보이는 폭에서 끊긴다.
3. **표시 글자에 `select-none`.** 비교 칸을 긁어 복사할 때 `-`·`+` 가 딸려 오지 않게 했다. 계획서에 없는 클래스다.
4. **줄 사이에 개행 문자를 넣지 않았다.** 줄 `<span>` 이 `block` 이라 개행을 따로 넣으면 빈 줄이 생긴다. 그래서 `<pre>` 의 `textContent` 는 더 이상 원래 JSON 과 같지 않다. 기존 테스트의 `pre.textContent` 단언은 `data-diff` 줄에서 표시 글자를 뺀 텍스트를 `\n` 으로 이어 견주도록 고쳤다(§6.3 의 "표시 글자를 뺀 것이 원래 줄" 규칙을 따른 것이다).
5. **원본 미발견 시 압축 칸.** 압축 문자열을 자기 자신과 `diffLines` 해 전부 same 으로 그린다. 별도 분기를 두지 않았다.
6. **빈 문자열.** `"".split("\n")` 을 따라 빈 줄 하나로 다룬다. 이어 붙이면 입력과 같다는 규칙이 그대로 선다. 테스트로 고정했다.
7. **색 단언.** 테스트가 `style.backgroundColor`·`style.color` 가 `var(--status-failed-*)`·`var(--status-done-*)` 인지까지 본다. §6.4 는 `data-diff` 개수와 텍스트만 요구했다.
8. **view 테스트의 픽스처.** 기존 응답은 `$schema` 키만 빠져 added 줄이 생기지 않는다. 설명이 `"A tool.  "` 에서 `"A"` 로 바뀐 응답(`cleanedResponse`)을 테스트 파일 안에 따로 만들었다.

## 남은 위험

- `on-accent` 변형은 `Button.tsx` 주석상 accent-soft 면 위에 놓는 갈래다. 표의 흰 면 위에서 쓰는 것은 계획서 §6.1 의 결정이지만, 실제 화면에서 테두리 대비가 충분한지는 눈으로 확인하지 않았다.
- 색 칸은 `<pre>` 의 안쪽 여백(`px-3`) 안에서만 칠해진다. 칸 가장자리까지 닿지 않는다.
- 설명 한 글자만 바뀌어도 그 줄 전체가 removed·added 로 칠해진다. 줄 단위로 정한 §6.1 의 결과다.
- 라이트·다크 양쪽에서 상태 색 위 글자 대비는 기존 토큰을 믿었고 따로 재지 않았다.
