## 임의로 판단한 부분

계획서가 정하지 않았거나 모호한 경계다. 전부 "건드리지 않는 쪽" 으로 골랐다.

### 패턴 매칭 (`planSourceEdits`)

1. **찾기는 느슨하게, 고치기는 엄격하게.** 출현 수 m 은 `키: 값` 글자 패턴만으로 센다. 문맥(앞뒤 토큰)이 낯설다고 출현에서 빼지 않는다. 빼면 m 이 줄어 우연히 n 과 맞고, 도구 정의가 아닌 자리를 고칠 수 있기 때문이다.
2. **m = n 인데 안전하게 떼어 낼 수 없는 출현이 있으면 그룹 전체 `unsupported`.** 계획서에 없는 경우다. 예: `required: [].concat(x)`, `title: "a" + b`, 앞 줄이 `//` 주석으로 끝나는 `.describe(...)`. §3.4 의 문장 가운데 사실과 맞는 것이 `unsupported` 문장뿐이라 그것을 썼다. 새 문장은 만들지 않았다.
3. **속성 삭제의 문맥 조건.** 값 뒤 첫 토큰이 `,` 나 `}` 여야 한다. 줄 전체가 그 속성이 아니면 앞 토큰이 `{` 나 `,` 여야 한다. 아니면 2번으로 간다.
4. **속성 삭제는 앞 쉼표를 우선 지운다.** `{ type: "object", properties: {}, required: [] }` 에서 두 속성의 삭제 범위가 겹치지 않게 하기 위해서다. 그래도 `{ properties: {}, required: [] }` 처럼 객체의 첫 속성과 그 다음 속성을 함께 지우면 범위가 겹쳐 두 그룹 모두 "같은 자리" ambiguous 가 된다. 안전하지만 고칠 수 있는 것을 못 고치는 경우다.
5. **끝 쉼표 없는 마지막 줄 속성**을 줄째 지우면 앞 속성의 쉼표가 끝 쉼표로 남는다(`type: "object",\n}`). JS·TS·Python 에서 유효해서 그대로 뒀다.
6. **`LIT(x)` 에서 뺀 표기.** 그 따옴표 안에서 다른 값이 되는 표기는 리터럴로 치지 않는다. 글자 그대로 표기는 `x` 에 `\`, 그 따옴표 문자, (백틱이 아닐 때) 개행, (백틱일 때) `${` 가 있으면 뺀다. JSON 표기는 작은따옴표·백틱에서 `x` 에 그 따옴표가 있으면 뺀다. 예: 내용이 `a" + "b` 일 때 소스의 `"a" + "b"` 는 세지 않는다.
7. **`\'` 표기는 찾지 않는다.** 작은따옴표 안의 `it\'s` 같은 표기는 §3.2 의 두 표기에 없어서 `not-found` 다.
8. **여는 따옴표 앞이 `\` 면 세지 않는다**(`description-cleaned` 만). 다른 문자열 안의 이스케이프된 따옴표다.
9. **`after` 이스케이프에 `\r` → `\r` 를 더했다.** 계획서 목록(`\`, 따옴표, 개행, 백틱의 `${`)에는 없지만 날 CR 은 리터럴을 깬다.
10. **`additionalProperties: true` 만 본다.** Python 의 `True` 는 찾지 않는다.
11. **"아무 문자열 리터럴"** 에서 보간(`${`)이 있는 템플릿 리터럴은 뺐다. 값이 문자열 상수가 아니라 식이다.
12. **맨 키의 경계.** 앞 글자가 `[\w$.]` 이면 키가 아니다(`patternProperties`, `schema.title`).
13. **판정 순서.** m = 0 이면 `not-found`, 그다음 after 불일치, 그다음 m ≠ n. after 가 갈리고 m ≠ n 이기도 하면 after 불일치 문장이 나온다.
14. **겹침 판정**은 처음 `ready` 였던 범위 전부를 한 번에 본다(차례로 내리면 순서에 따라 달라진다). 같은 그룹 안의 겹침도 그 그룹을 ambiguous 로 내린다. 맞닿기만 한 범위는 겹침이 아니다.
15. **런타임 형식.** 라우트는 `change.kind`·`path` 만 검사하므로, `before`·`after`·`key` 가 문자열이 아니거나 kind 가 모르는 값이면 `unsupported` 다.

### 파일 찾기 (`resolveSourceFile`)

16. **실제 경로도 검사한다.** §3.3 의 조건에 더해 `realpath` 가 루트 안이고 `node_modules` 를 지나지 않아야 한다. 심볼릭 링크로 루트 밖 파일을 쓰는 것을 막는다. 계획서보다 좁다.
17. 확장자는 대소문자를 구분한다(`.JS` 는 후보가 아니다). `--url=…` 한 토큰 표기도 원격으로 본다. `--` 로 시작하는 옵션은 전부 값을 하나 받는다고 보고 건너뛴다.

### 라우트

18. `writeFileContent` 가 `saved: false` 를 준 경우(읽은 뒤 쓰기 직전에 바뀜)의 conflict 본문은 읽었던 내용의 미리보기이고 `mtimeMs` 도 읽었던 값이다. 다음 적용이 다시 conflict 로 떨어져 새 미리보기를 받는다. 낡은 diff 에 새 mtime 을 붙이지 않으려는 것이다.
19. 쓰기 실패(`EACCES` 등)는 기존 `writeErrorMessage` 문장으로 400 이다. 계획서에 없는 경로다.
20. 계획서 목록에 없는 라우트 테스트 1건을 더했다(소스 파일을 찾지 못하면 400 과 §3.3 문장).

### 웹

21. **`<div aria-label>` 대신 `<section aria-label>`.** 계획서는 `div` 지만 biome 의 `useAriaPropsSupportedByRole` 이 오류로 막는다. 문장과 `aria-label` 값은 그대로다.
22. **카드 다시 마운트의 키 위치.** `SourceEditCard` 가 아니라 `TokensPanel` 이 `<TokensResult key={resultSerial}>` 로 건다. 결과 객체에는 키로 쓸 값이 없고, 내용이 같은 결과가 다시 와도 비워져야 해서 일련번호를 썼다. 부작용으로 다시 분석 뒤 펼쳐 둔 도구 비교도 접힌다.
23. **다시 분석 중 표시.** 결과 단계 위에 `<p role="status">분석 중…</p>` 를 둔다. 계획서에 문장이 없어 기존 버튼 라벨을 다시 썼다. 요청 중 `다시 분석` 을 또 눌러도 요청은 하나다.
24. **상태 색은 `<li>` 전체에 입혔다**(ready 는 `--status-done-fg`, 나머지는 `text-ink-muted`).
25. **`DIFF_*` 상수를 `tool-diff.ts` 로 옮겼다.** `SourceEditCard` 가 `TokensResult` 에서 가져오면 순환 import 가 된다.

## 남은 위험

- 글자 패턴이라 주석·문자열 안의 같은 글자도 출현으로 센다. 대부분 m ≠ n 으로 걸러지지만 **우연히 m = n 이면 도구 정의가 아닌 자리를 고친다.** 미리보기와 확인이 마지막 방어선이다.
- 실제 서버를 띄우는 E2E 는 없다. 화면에서 실제 예제 서버로 미리보기 → 적용 → 다시 분석을 눌러 보는 확인은 하지 않았다.
- 적용 뒤 서버가 여전히 뜨는지는 검사하지 않는다. `다시 분석` 이 실패할 때 드러난다.
- 4번의 이웃 속성 겹침은 흔한 모양(`properties: {}` 와 `required: []` 가 나란히, 객체의 첫 속성부터)에서 ambiguous 를 낸다. 넓히려면 범위 병합 규칙이 필요하고 ADR-0106 의 범위다.

## 수정 1: 공통 파라미터(promoted) 변경은 자동 수정에서 뺀다

리뷰 뒤 계획서가 고쳐졌다(main `b6ddb4f` 의 §3.2·§3.4·§5.1). `description-removed` 의 reason 이
`promoted` 면 압축기가 그 설명을 서버 `instructions` 사전으로 옮긴 것이라, 소스에서 설명만 지우면
정보가 사라진다. 위 본문의 숫자(예: `source-edits.test.ts` 30건)는 이 수정 전의 것이다.

### 바뀐 것

| 파일 | 내용 |
|---|---|
| `packages/dashboard/src/server/source-edits.ts` | reason=`promoted` 는 소스를 찾지 않고 항상 `unsupported`(§3.4 의 promoted 문장). 같은 before 의 promoted 변경이 `edits` 에 있으면 그 before 의 다른 사유 `description-removed` 그룹은 `ambiguous`(§3.4 의 새 문장) |
| `packages/dashboard/tests/source-edits.test.ts` | 6건 추가(30 → 36). `removed()` 헬퍼가 reason 을 받는다 |

계획서 파일은 건드리지 않았다. worktree 의 계획서는 여전히 옛 판이다.

판정 순서는 요청대로다. `not-found` 다음이고 다른 `ambiguous`(after 불일치, m ≠ n)와 겹침 판정보다 앞이다.

구현 도중 `pnpm typecheck --force` 가 한 번 빨강이었다(`TS2339`, promoted 판정 함수가 타입을 좁히지

### 임의로 판단한 부분

1. **요청한 2건 외에 테스트 4건을 더했다.** promoted 는 소스에 없어도 `not-found` 가 아니라
   `unsupported`, 같은 before 여도 소스에 없으면 `not-found` 가 먼저, m ≠ n 이어도 공통 파라미터 문장이
   먼저, before 가 다른 promoted 는 다른 그룹에 영향 없음.
2. **promoted 는 출현 수 n 에 넣지 않는다.** 그룹에 들어가지 않으므로 같은 before 의 다른 사유 그룹은
   promoted 를 뺀 건수로 센다. 다만 그 그룹은 2번 규칙으로 어차피 `ambiguous` 라 결과에 차이가 없다.
3. **`description-cleaned` 에는 적용하지 않았다.** before 가 promoted 와 같은 `description-cleaned` 그룹은
   계획서에 언급이 없어 그대로 둔다. 압축기가 한 문자열을 정리하면서 동시에 승격할 일은 없다고 봤지만
   확인한 것은 아니다.
4. promoted 인데 `before` 가 문자열이 아닌 요청(형식 검사를 통과한 비정상 값)도 promoted 문장으로
   `unsupported` 다.
