## 임의로 판단한 부분

1. **묶음 키.** 네 값을 구분자로 잇지 않고 `JSON.stringify([status, path, text, detail])` 로 만들었다.
   설명 문장 안에 어떤 글자든 올 수 있어, 구분자로 이으면 서로 다른 묶음이 겹칠 수 있기 때문이다.
2. **기존 미리보기 테스트의 순서.** `MCP 수정하기를 누르면 …` 테스트는 `["not-found", "ready"]` 를 기대했는데
   `ready` 가 먼저 오는 규칙에 따라 `["ready", "not-found"]` 로 고쳤다. 도구가 하나인 묶음에 `<details>` 가
   없다는 단언을 더했다.
3. **기존 `ready 가 0 이면 …` 테스트의 이름.** `ready 가 0 이면 적용 버튼이 없고 닫기로 미리보기를 닫는다` 로
   바꾸고, `닫기` 를 누르면 미리보기가 닫히는 것까지 단언했다. 계획서는 라벨만 정했고 동작은 기존 `취소` 와 같게 뒀다.
4. **계획서에 없는 테스트 둘.** `같은 도구가 한 묶음에 두 번 오면 이름도 두 번 남는다`(§7.1 주석의 단언),
   `결과가 없으면 묶음도 없다`.
5. **`toolsLabel([])`.** 계획서가 정하지 않았다. 빈 문자열을 돌려준다. 묶음에는 도구가 항상 하나 이상이라
   화면에서는 일어나지 않는다.
6. **모양(클래스).** 건수 `<span>` 과 펼친 도구 목록은 기존 도구 이름과 같은 `font-mono text-xs` 로 뒀고,
   `<summary>` 에 `cursor-pointer` 를 줬다. 계획서는 요소와 문장만 정했다.
7. **건수 `<span>` 앞의 공백.** 변경 문장과 건수 사이에 공백 하나를 뒀다. `<li>` 의 `textContent` 는
   `경로 문장 N건 · 도구` 꼴이다.

## 남은 위험

- 실제 브라우저로 눈으로 보지는 않았다. jsdom 과 fetch 스텁으로만 검증했다. `<details>` 의 펼침 모양과
  긴 도구 이름 목록의 줄바꿈은 live-weather-server 로 한 번 열어 보는 것이 좋다.
- 프록시 안내 문장은 `mcpeak-optimize-proxy` 라는 이름을 글자로 적는다. 그 실행 파일 이름이 바뀌면 이 문장도
  따라 고쳐야 한다.
