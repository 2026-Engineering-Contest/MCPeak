## 임의로 판단한 부분

1. **"확인 안 함" 문안** (§6.2 에 행이 없음). message 는 `확인 안 함: <무엇을> 판정하지 못했습니다 (<원인>)`, OAuth 는 `확인 안 함: OAuth 메타데이터 <url> 를 읽지 못했습니다 (<원인>)`. fix 는 공통 `이 항목은 통과가 아니라 미확인입니다. 서버에 닿는지 확인하고 다시 실행하세요.` 원인은 타임아웃이면 `5000ms 안에 응답이 없습니다`, 그 밖에는 `요청 실패: <오류 메시지 첫 줄>`. evidence 는 `[프로브 URL, 원인]` 이라 같은 규칙의 두 OAuth 프로브가 §3.0 중복 제거에 겹치지 않는다.
2. **info 변형 문안** (§6.2 에는 medium/high 문안만 있음).
   - plaintext localhost info: message 는 같고 fix 만 `로컬호스트 안에서만 오가므로 보통은 괜찮습니다. 외부에 노출한다면 https 를 쓰세요.`
   - unauthenticated info: message 는 §3.6 의 인용문 `인증 없이 열려 있습니다. 로컬 전용이면 정상입니다`, fix `네트워크에 노출할 서버라면 인증을 붙이고 --header-env 로 다시 점검하세요.`
   - list-changed info: `감사 중 도구 목록 변경 알림이 왔지만 목록은 그대로입니다` / `지금은 문제가 없습니다. 알림이 반복되면 서버가 정의를 바꾸는 시점을 확인하세요.`
3. **unauthenticated 판정**. 2xx 이고 본문(JSON 또는 `text/event-stream` 의 data 줄)에 `result` 가 있으면 medium. JSON-RPC `error` 이거나 2xx 가 아니면 발견 없음. 2xx 인데 JSON-RPC 로 읽을 수 없으면 "확인 안 함" info. 헤더를 안 줬으면 프로브 없이 info(감사가 이미 연결에 성공한 뒤 호출된다는 전제).
4. **origin-check 와 인증**. `ProtocolContext` 에는 헤더 값이 없어(이름만 있음) Origin 프로브도 인증 없이 보낸다. 그래서 `--header-env` 를 줬고 Origin 프로브가 401 이면 Origin 검사 여부를 알 수 없으므로 "확인 안 함" info 로 낸다. 403 등 그 밖의 비 2xx 는 "Origin 을 거른다" 로 본다.
5. **session-in-url 의 관측 범위**. 감사 연결 자체의 리다이렉트는 `ProtocolContext` 에 없으므로, 이 규칙이 보내는 프로브들(`redirect: "manual"`)의 `Location` 과 응답 본문 URL, 그리고 사용자가 준 `--url` 자체를 본다. `--url` 포함은 계획서 문구("연결 중 관측된")보다 넓다. evidence·message 의 URL 은 세션 파라미터 값을 `<redacted>` 로 가린다(비밀 금지 원칙). 같은 URL 은 한 번만 낸다.
6. **oauth-endpoint evidence**. `evidence[0]` 을 `<well-known 이름>.<필드>`(예: `oauth-authorization-server.authorization_endpoint`)로 해 두 문서의 같은 필드가 중복 제거로 사라지지 않게 했다. 값은 80자로 자른다. 문자열이 아닌 필드는 보지 않는다. 2xx 가 아니거나 JSON 객체가 아니면 OAuth 서버가 아닌 것으로 보고 발견 없음.
7. **프로브 순서와 값**. 헤더 없는 initialize → Origin initialize(로컬만) → protected-resource → authorization-server 를 순서대로 하나씩 보낸다. initialize 본문은 고정값(`protocolVersion` 은 고정된 SDK 의 `LATEST_PROTOCOL_VERSION`, `clientInfo` `mcpeak-audit`/`0.0.0`). 프로브가 만든 서버 세션은 DELETE 로 닫지 않는다.
8. **로컬호스트 판정**에 `URL.hostname` 이 IPv6 를 `[::1]` 로 주는 것을 반영해 `::1`·`[::1]` 둘 다 넣었다. http 대상인데 `url` 이 없거나 URL 로 읽히지 않으면 HTTP 규칙을 건너뛴다(CLI 가 막는다는 전제).
9. **정렬**. `runProtocolRules` 도 반환 전에 §3.0 키(`ruleId`, `path`, `evidence[0]`, 코드 단위 비교)로 정렬한다. 최종 정렬·중복 제거는 T6 몫이지만 이 함수 단독 출력도 결정론적이게 했다.
10. **server-request**는 세 메서드의 `kind: "request"` 만 센다. `ping` 이나 알림은 세지 않는다. 메서드마다 발견 하나, evidence `[method, "<n>회"]`.
11. **server-request 와 injection 의 관계** (오케스트레이터 결정 1, 선택지 가). 어떤 메서드에 server-request-injection(high)이 걸리면 그 메서드의 server-request(info)는 내지 않는다. injection 의 evidence 는 `[조각, method, "<n>회", params 경로]` 라 횟수가 사라지지 않는다. params 문자열은 §3.0.2 규칙(값과 키 이름, 점 경로, `[i]`, 키에 `(key)` 접미, 접두 `params`)으로 `protocol.ts` 안의 `paramStrings` 가 걷는다.
12. "확인 안 함" 의 원인은 오류 메시지 첫 줄만 쓴다. 이 코드는 시각·소요 시간을 넣지 않는다(오케스트레이터 지시 3 확인).

## 픽스처 형식 (T6 에 전달할 것)

§8.1 의 `protocolContext` 는 `{ target, fetch?, serverMessages?, listChanged? }` 이고, `fetch` 는 함수 대신 **응답표**(`Route[]`)다.

```json
{ "method": "POST", "url": "https://…/mcp",
  "headers": { "origin": "http://evil.invalid" },
  "response": { "status": 200, "headers": { "content-type": "application/json" }, "body": "…" } }
```

앞에서부터 처음 맞는 경로가 답한다. `headers` 는 부분 일치(값이 `null` 이면 그 헤더가 없어야 맞음), 맞는 경로가 없으면 404, `response` 대신 `"throws": "TimeoutError"` 를 주면 그 이름의 `DOMException` 을 던진다.

해석기: `packages/audit/tests/helpers/fake-fetch.ts`

```ts
export interface Route { method; url; headers?; response?: { status; headers?; body? }; throws? }
export interface FetchCall { method; url; headers: Headers; body: string | undefined; signal: AbortSignal | undefined }
export function fakeFetch(routes: readonly Route[]): { fetch: typeof globalThis.fetch; calls: FetchCall[] };
```

T6 의 `rules-fixtures.test.ts` 는 `fakeFetch(fixture.protocolContext.fetch ?? []).fetch` 를 `ProtocolContext.fetch` 로, `serverMessages` 는 없으면 `[]`, `listChanged` 는 없으면 `{ notified: false, surfaceHashBefore: "h1", surfaceHashAfter: "h1" }` 로 채우면 된다(`protocol-rules.test.ts` 의 픽스처 절과 같은 방식).

HTTP 픽스처는 "다른 규칙 0건" 을 맞추려고 `headerNames: ["Authorization"]` 과 401 경로를 둔다. 헤더가 없으면 `unauthenticated` info 가 항상 함께 나오기 때문이다. origin-check 픽스처는 plaintext info 를 피하려고 `https://localhost` 를 쓴다.

## server-request-injection (T1 통합 뒤 구현)

- `protocol.ts` 의 `findInstruction` 이 문자열 하나를 본다. 먼저 T1 의 `findInjection(raw)` 로 `desc/injection` 을 모든 형(raw, folded, 디코딩형, rot13)에서 찾는다. 없으면 `COVERT_ACTION_PATTERNS`·`SHADOWING_PATTERNS` 를 `normalizeTextWithSources(raw)` 의 형 순서대로 대조한다. raw 에는 description.ts 와 같은 방식으로 대소문자 무시 사본(`flags + "i"`)을 대고, 나머지 형에는 원본을 댄다. 정규식 글자는 복제하지 않았다.
- 문자열 하나에 발견 하나이고 injection 이 먼저다. 조각은 `evidenceFragment` 로 다듬는다(80자, 보이지 않는 문자 표시).
- evidence: `[조각, method, "<n>회", params 경로, 형]`. 형(`raw`·`folded`·`base64`…)을 마지막에 더한 것은 임의 판단이다.
