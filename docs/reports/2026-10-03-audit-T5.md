## 임의로 판단한 부분

1. **flow 구획의 첫 줄은 발견의 `message` 를 그대로 쓴다.** 둘째 줄(`외부 입력에 숨은 지시가…`)과
   `해결:` 줄은 §6.1 의 고정 문장을 렌더러가 직접 쓴다. §6.2 에 flow 행이 없고 §3.4 는 evidence 에
   "각 집합의 도구 이름 최대 3개" 라고만 적어 집합 구분 형식이 정해지지 않았다. evidence 를 파싱하면
   T2 형식과 어긋날 때 글자가 깨지므로 message 를 쓰는 쪽을 골랐다. 따라서 **T2 의 flow 발견 message 는
   `이 서버는 외부 입력을 읽고(<a, b, c>), 비공개 데이터에 닿고(<d, e>), 밖으로 쓸 수 있습니다(<f>).`
   이어야 §6.1 과 일치한다.** 발견의 `fix` 는 flow 구획에서 쓰지 않는다.
2. **빈 줄 배치.** §6.1 은 블록 사이 간격을 적지 않았다. 머리 세 줄 뒤, 판정 줄 뒤, 발견 블록마다,
   flow·skipped 구획 앞, 마지막 두 줄 앞에 빈 줄 하나를 둔다. 출력 끝에는 개행 하나(§4 의 JSON 규칙과 맞춤).
3. **판정 줄의 개수는 `report.counts` 를 그대로 쓴다.** 렌더러가 다시 세지 않는다. counts 의 정합성은
   T6(`audit`) 책임이다.
4. **렌더러가 발견을 다시 정렬한다.** 심각도별로 나눈 뒤 §3.0 키 `(toolIndex ?? -1, ruleId, path,
   evidence[0])` 로 정렬한다. 문자열 비교는 `localeCompare` 가 아닌 코드 단위 비교다(로캘 독립, 결정론).
   중복 제거는 하지 않는다(T6 책임).
5. **"같은 도구" 접기 키는 `(ruleId, toolIndex)` 이고 같은 심각도 안에서만 센다.** `toolIndex` 가 없는
   위치(instructions·launch·protocol 등)는 접지 않는다. 접은 줄은 셋째 발견의 `해결:` 줄 바로 뒤에 둔다.
6. **`launch` 위치에서 path 가 빈 문자열이면 `실행 명령` 만 쓴다.** §6.1 의 "path 가 비면 생략" 규칙을
   이 위치에도 적용했다.
7. **flow 발견이 여러 개면** 머리 줄 하나 아래 각 발견마다 세 줄을 반복한다. 현재 규칙은 하나뿐이다.
8. **skipped 는 받은 순서대로 적는다.** 순서 결정은 T6 책임이다.
