## 오케스트레이터 결정 (중간 보고에 대한 회신. 그대로 구현했다)

1. **재생에서도 gateway 를 bridge 에 붙인다.** gateway 는 live·record·replay 모두 internal 과 bridge 둘에
   붙는다. target 은 어느 모드에서도 internal 하나에만 붙는다. 재생에서 상류에 접속하지 않는 것은 게이트웨이
   코드(T2)가 env `MCPEAK_GATEWAY_MODE`(`live`|`record`|`replay`)를 보고 지킨다. §8.2 의 it 은
   "gateway 는 live·record·replay 모두 internal 과 bridge 에 붙는다(제어 포트 publish 는 internal 전용에서 되지
   않는다)" 로 바꾸고 "target 은 어느 모드에서도 internal 네트워크 하나에만 붙는다" 를 더했다.
2. **T2 와의 접점.** `MCPEAK_GATEWAY_TOKEN`(64자 소문자 hex), `MCPEAK_GATEWAY_INTERNAL_SUBNET`(CIDR),
   `docker create` → `docker network connect bridge` → `docker start` 순서, 명령
   `node /opt/mcpeak/gateway/server.mjs`, 루트 FS 읽기 전용에 `--tmpfs /tmp`. 제어 포트는 컨테이너 안에서
   `0.0.0.0:7000` 으로 듣는다고 가정한다.
3. **`Observation.unparsedLines`.** `types.ts` 에 선택 필드 하나를 더했다. 백엔드는 언제나 채운다(없으면 0).
   `gaps` 에는 싣지 않는다.
4. **네트워크 이름은 `mcpeak-audit-<runId>-net`.** §8.2 의 "이름이 `mcpeak-audit-<runId>-` 로 시작" 에 맞췄다
   (§3.0 문면의 `mcpeak-audit-<runId>` 와 다르다).

## 재생 모드 실측 (ADR-0106 근거)

환경: Docker Engine 29.2.1 (Docker Desktop, macOS, Darwin 25.5.0), 이미지 `mcpeak-audit-sandbox:9199c91b63ce`.
시험 자원은 `mcpeak-t1probe-*` 이름으로 만들고 전부 지웠다(라벨 `mcpeak.audit=1` 은 붙이지 않았다).

아래에서 `$SRV` 는 7000 번에서 듣는 한 줄짜리 Node HTTP 서버다. 둘째 시험의 서버는 요청을 받으면
`fetch("http://1.1.1.1/")` 를 3초 제한으로 해 보고 결과와 인터페이스 주소를 돌려준다.

**시험 1. `--internal` 네트워크에만 붙은 컨테이너의 `-p`.**

```
docker network create --internal mcpeak-t1probe-net
docker network inspect -f '{{json .IPAM.Config}}' mcpeak-t1probe-net
docker run -d --name mcpeak-t1probe-gw --network mcpeak-t1probe-net -p 127.0.0.1::7000 \
  --read-only --cap-drop ALL --cap-add NET_BIND_SERVICE --tmpfs /tmp $IMG node -e "$SRV"
docker inspect -f '{{json .NetworkSettings.Ports}}' mcpeak-t1probe-gw
docker port mcpeak-t1probe-gw
```

```
[{"Subnet":"172.24.0.0/16","Gateway":"172.24.0.1"}]
{"7000/tcp":[]}
(docker port 는 빈 출력)
```

포트가 publish 되지 않는다. 호스트에서 제어 포트에 닿을 길이 없다.

**시험 2. masquerade 를 끈 실행별 브리지를 제어용으로 붙이기.**

```
docker network create --internal mcpeak-t1probe-net
docker network create -o com.docker.network.bridge.enable_ip_masquerade=false mcpeak-t1probe-ctl
docker create --name mcpeak-t1probe-gw --network mcpeak-t1probe-net -p 127.0.0.1::7000 --read-only \
  --cap-drop ALL --cap-add NET_BIND_SERVICE --security-opt no-new-privileges --tmpfs /tmp $IMG node -e "$SRV"
docker network connect mcpeak-t1probe-ctl mcpeak-t1probe-gw
docker start mcpeak-t1probe-gw
docker inspect -f '{{json .NetworkSettings.Networks}}' mcpeak-t1probe-gw     # 주소만 추림
docker inspect -f '{{json .NetworkSettings.Ports}}' mcpeak-t1probe-gw
curl -s -m 8 http://127.0.0.1:63954/
```

```
{'mcpeak-t1probe-ctl': '172.25.0.2', 'mcpeak-t1probe-net': '172.24.0.2'}
{"7000/tcp":[{"HostIp":"127.0.0.1","HostPort":"63954"}]}
EGRESS-OK 200 [["lo","127.0.0.1"],["eth0","172.25.0.2"],["eth1","172.24.0.2"]]
```

포트는 publish 되지만 컨테이너에서 `1.1.1.1` 로 나가는 요청이 200 으로 돌아온다. Docker Desktop 에서는
masquerade 를 꺼도 외부 접속이 막히지 않는다. 일반 docker 옵션으로 "호스트에서 제어 포트는 닿고 외부로는 못
나가는" 게이트웨이는 만들지 못했다.

**시험 3. internal 로 create 한 뒤 bridge 를 connect 하고 start (채택한 방식).**

```
docker create --name mcpeak-t1probe-gw --network mcpeak-t1probe-net -p 127.0.0.1::7000 ... $IMG node -e "$SRV"
docker network connect bridge mcpeak-t1probe-gw
docker start mcpeak-t1probe-gw
curl -s -m 8 http://127.0.0.1:<HostPort>/
```

```
EGRESS-OK 200 [["lo","127.0.0.1"],["eth0","172.24.0.2"],["eth1","172.17.0.2"]]
```

포트가 publish 된다(첫 실행에서는 `HostPort` 63867). **인터페이스 순서가 시험 2 와 반대다**(여기서는 eth0 이
internal, 시험 2 에서는 eth1 이 internal). 그래서 게이트웨이가 인터페이스 번호로 internal 쪽을 고르면 안 되고,
서브넷을 env 로 준다.

덧붙여 확인한 것: `docker rm -f <없는 컨테이너>` 는 종료 코드 0 이고 stderr 에
`Error response from daemon: No such container: …` 를 낸다. `docker network rm <없는 것>` 은 1 과
`network … not found`, `docker volume rm <없는 것>` 은 1 과 `get …: no such volume` 이다. `destroy` 는 이 세
문장을 "이미 없다 = 치웠다" 로 본다. `--user 1000:1000` 이면 `HOME` 은 지정하지 않아도 `/home/node` 다.

## 제어 포트에 보내는 요청 형식

전부 `http://127.0.0.1:<publish 된 포트><경로>` 이고 헤더 `authorization: Bearer <토큰>` 이 붙는다. 본문이
있으면 `content-type: application/json` 이다. §3.7 의 표 그대로다.

| 시점 | 요청 | 본문 | 기대하는 응답 | 제한 |
|---|---|---|---|---|
| `start` | `GET /health` | 없음 | 200 이면 준비됨. 그 밖과 접속 실패는 100ms 뒤 다시(최대 100번) | 1초 |
| `start` | `GET /ca` | 없음 | `{ "pem": "…" }`. `pem` 이 빈 문자열이 아닌 문자열이어야 한다 | 5초 |
| `start` | `POST /secrets` | `{ "secrets": [{ "label", "value" }] }` | 200 | 5초 |
| `start`(재생) | `POST /session` | 세션 파일 내용을 읽은 그대로 | 200. 아니면 `{ "error": "<한 줄>" }` 을 원인으로 쓴다 | 30초 |
| `mark` | `POST /phase` | `{ "phase": SandboxPhase }` | 200 | 5초 |
| `snapshot` | `GET /observation` | 없음 | `{ requests, tlsRejections, dnsNames }` 셋 다 배열 | 30초 |
| `snapshot`(녹화) | `GET /session` | 없음 | JSON. `JSON.stringify(값, null, 2) + "\n"` 으로 다시 써서 `0600` 으로 저장 | 30초 |

`POST /secrets` 의 목록 순서: env 카나리(이름순, 자리표 `<canary:NAME>`), 파일 카나리(`HomePlan` 순서,
자리표 `<canary:~/경로>`), 전달 env(이름순, 자리표 `<env:NAME>`). env 카나리와 전달 env 는
`target.forwardedEnvNames` 로 가른다. 값이 빈 문자열인 것은 보내지 않는다.

## 임의로 판단한 부분

표에 없어 가정한 것과 문면과 다르게 간 것이다.

1. **HOME 과 CA 변수 다섯은 `--env-file` 로 넘긴다.** §3.0 은 전부 `-e NAME` 이라고 했지만 그대로는 서지 않는다.
   `-e HOME` 이면 docker CLI 자신의 호스트 `HOME` 이 컨테이너에 들어가고, `backend.ts` 의 주석은 `launchEnv` 가
   `SandboxSpec.env` 와 `dockerClientEnv()` 만 담는다고 한다. `SSL_CERT_FILE` 을 CLI 의 env 에 실으면 Go 로 된
   docker CLI 의 신뢰 저장소가 없는 파일로 바뀐다. 값이 비밀이 아닌 고정 경로라 파일로 넘겼다. argv 에는 파일
   경로만 실린다. 테스트 하나를 더해 고정했다.
2. **gateway 에 `--security-opt no-new-privileges` 를 더했다.** §3.0 의 gateway 옵션에는 없다. 강화 쪽이다.
   사용자는 이미지 기본(root)이다. T2 가 `openssl` 을 자식으로 띄우는 데는 영향이 없다.
3. **trace 를 읽는 일회용 컨테이너에 `--read-only --cap-drop ALL --security-opt no-new-privileges
   --user 1000:1000` 과 라벨을 더했다.** 서버가 건드릴 수 있는 파일을 읽으므로 읽는 쪽 권한을 떨궜다.
4. **gateway 의 internal 쪽 주소를 서브넷으로 알려 준다.** `docker network inspect` 한 번이 더 든다.
5. **명령은 `target.command` 를 그대로 넘긴다**(§8.2 의 단언). basename 으로 바꾸지 않았다. 남은 위험 2 를 보라.
6. **`start` 실패 뒤 정리까지 실패하면 `detail` 끝에 붙인다.**
   `<원래 detail> (격리 자원도 다 치우지 못했습니다: 볼륨 1개)` 꼴이다. 조용히 새는 것을 막으려는 것이고, 문안은
   §6 에 없어 내가 정했다.
7. **`start-failed` 의 내가 정한 `detail` 문장.** docker 오류가 아닌 실패에 쓴다.
   `격리 네트워크의 서브넷을 읽지 못했습니다`, `게이트웨이의 주소나 제어 포트를 읽지 못했습니다`,
   `게이트웨이가 10초 안에 준비되지 않았습니다`, `게이트웨이가 CA 인증서를 주지 않았습니다`,
   `게이트웨이가 가릴 값 목록을 받지 않았습니다(POST /secrets 가 HTTP <n>)`.
8. **`gaps` 의 `reason` 문장.** docker 나 fetch 오류의 첫 줄을 자리표로 바꿔 싣고, 그 밖에는
   `시스템 콜 기록을 해석하지 못했습니다: <오류>`, `단계를 알리지 못했습니다(POST /phase 가 HTTP <n>)`,
   `관측을 받지 못했습니다(GET /observation 이 HTTP <n>)`, `게이트웨이의 관측 응답이 형식에 맞지 않습니다`,
   `녹화를 받지 못했습니다(GET /session 이 HTTP <n>)`, `세션 파일을 쓰지 못했습니다: <오류>` 다.
   녹화 저장 실패는 실을 자리가 `gaps` 뿐이라 `source: "gateway"` 로 실었다. T5 가 이것을 "관측이 비었습니다" 문장에
   넣으면 뜻이 조금 어긋난다.
9. **자리표.** §4·§5.1 의 `<container>`, `<network>`, `<tmp>`, `<gateway>` 에 더해 `<volume>`, `<token>`,
   `<control>`(`127.0.0.1:<포트>`), `<run>`(남은 runId)을 썼다. 요청 기록의 `host`·`path`·헤더 값,
   `tlsRejections.host`, `dnsNames.name` 에 실린 게이트웨이 주소도 `<gateway>` 로 바꾼다(본문은 건드리지 않는다).
   서버가 게이트웨이 IP 로 직접 요청하면 `report.sandbox.requests` 에 실행마다 다른 주소가 나오기 때문이다.
10. **`SANDBOX_CLEANUP_FAILED` 의 문장은 자리표로 바꾸지 않는다.** stderr 로만 가고, 사용자가 직접 치울 때 임시
    디렉터리 경로가 필요하다. 실패한 `destroy` 를 다시 부르면 남은 것만 다시 시도한다.
11. **mark 에서 난 실패는 던지지 않고 기억했다가 `snapshot` 의 `gaps` 에 낸다.** `mark` 가 던지면 감사 전체가 죽는다.
12. **개행으로 끝나지 않은 trace 의 마지막 줄은 세지 않는다.** strace 가 쓰는 중인 줄이 반으로 잘려 직전 단계에
    붙는 것을 막는다.
13. **재생 파일은 자원을 만들기 전에 JSON 으로 읽히는지도 본다.** 형식 검증은 게이트웨이의 400 에 맡기고 그 원인
    한 줄을 `SANDBOX_SESSION_UNREADABLE` 에 싣는다(만든 것은 치운 뒤).
14. **`홈 디렉터리는 0755` 는 백엔드에서 단언하지 못한다.** `DockerIo` 에 mkdir 이 없다. `writeFile` 이 상위
    디렉터리를 `0755` 로 만든다고 가정했다. T6 의 `audit-sandbox-io.ts` 가 그렇게 해야 한다. 홈 파일은
    `HomePlan` 의 `mode` 그대로 쓴다(전부 `0644`).
15. **`detect` 는 `docker version` 이 거절되면(ENOENT 가 아닌 것, 예: 시간 초과) `daemon-down` 으로 본다.**
16. **토큰은 `io.random()` 네 번(64자), runId 는 한 번이다.**

## 남은 위험

1. **T2 와의 접점은 아직 실물로 맞춰 보지 않았다.** 게이트웨이가 스텁이라 `health → ca → secrets → session` 과
   `phase`·`observation` 은 가짜 fetch 로만 확인했다. §9.2 의 손 연기 시험이 처음 드러낸다. 특히 `--dns` 가
   Docker 내장 DNS(`127.0.0.11`)의 상류로 들어가는 것을 확인했다(`/etc/resolv.conf` 에 게이트웨이 주소가 직접
   적히지 않는다). 이름 풀이가 게이트웨이까지 가는지는 T2 의 DNS 가 떠야 확인된다.
2. **`command` 가 호스트 절대 경로면 컨테이너에 없다.** `/opt/homebrew/bin/node` 같은 값이면 basename 은 `node` 라
   격리가 켜지지만 strace 가 그 경로를 못 찾아 연결이 실패한다. basename 으로 바꿔 넘길지는 결정이 필요하다
   (§8.2 는 "원래 command" 라고 단언한다).
3. **단계 경계에 걸친 strace 줄.** `-f` 는 `<unfinished …>` 와 `… resumed>` 를 따로 쓴다. 둘 사이에 mark 가 오면
   해석기가 단계별로 따로 받는다. T4 의 해석기가 이것을 `unparsed` 로 셀 수 있다.
4. **trace 크기에 상한이 없다.** `cat` 의 stdout 을 통째로 문자열로 받는다. 서버가 볼륨에 큰 파일을 쓰면 호스트
   메모리를 쓴다. `mark` 마다 처음부터 다시 읽으므로 호출이 많으면 읽는 양이 제곱으로 는다.
5. **`mark` 한 번이 컨테이너 하나다.** 도구 수십 개면 `docker run` 이 수백 번 돈다. 손 확인에서 체감 지연은
   없었지만 재지 않았다.
6. **`DOCKER_TLS_VERIFY`·`DOCKER_CERT_PATH` 는 `dockerClientEnv` 목록에 없다**(§5.3 의 다섯 개만). TLS 로 붙는
   데몬에서는 `launchTarget` 의 docker CLI 가 데몬을 못 찾을 수 있다. T6 의 io 가 정할 일이다.
7. **재생의 격리 주장이 약해졌다**(결정 1). gateway 가 bridge 에 붙어 있으므로 "재생은 네트워크가 없다" 는
   게이트웨이 코드가 지키는 것이지 Docker 가 지키는 것이 아니다. §6.1 의 `재생(네트워크 없음)` 문안과 ADR-0106
   에 반영이 필요하다.
8. **이미지 빌드 실패의 `detail` 은 stderr 의 첫 줄이다**(§8.2). BuildKit 은 첫 줄이 진행 줄이고 원인은 끝에
   있는 경우가 많다. 문면대로 두었다.
9. **손 확인 첫 실행에서 `docker image inspect` 가 0 이 아니어서 빌드 경로를 탔다**(진행 문장이 찍혔고 캐시된
   레이어로 바로 끝났다). 둘째 실행에서는 재현되지 않았다. 원인은 확인하지 못했다. 같은 데몬을 쓰는 다른 세션이
   그 사이에 이미지를 지웠을 수 있다. 그 결과 `mcpeak-audit-sandbox:9199c91b63ce` 를 내 실행이 다시 태그했다
   (내용은 같다).
10. **실측은 Docker Desktop(macOS) 한 곳이다.** Linux 엔진에서 `--internal` 의 포트 publish 와 masquerade 동작이
    같은지는 보지 않았다.
