## 임의로 판단한 부분

계획서가 정하지 않았거나 두 곳이 어긋나 내가 고른 것이다. 통합 전에 봐 주기 바란다.

1. **호출의 차례.** `NetworkContext` 에 호출 목록이 없어서 "계획 순서로 첫 호출" 을 입력에서 알 수 없다. 입력
   순서에 기대면 "입력 순서와 무관" 이 깨진다. 그래서 도구 번호, 그 안에서 `placeholder` 를 맨 앞, 나머지는
   callId 의 코드 단위 순으로 세웠다. 페이로드 호출끼리는 실제 계획 순서(§3.3 표 순서)와 다를 수 있다. 예:
   `url:loopback` 이 `url:metadata` 앞에 온다. 위치와 `호출: …` 칸이 이 순서를 쓴다.
2. **출력에 싣는 호스트·경로에서 카나리를 가린다.** 서버가 값을 쿼리나 하위 도메인에 실으면 그 문자열이
   `undeclared-destination` 의 message 에 그대로 들어간다. "message·evidence 에 카나리 값을 쓰지 않는다" 와 §4 를
   지키려고 모든 규칙의 호스트·경로·헤더 이름을 가린 뒤에 쓴다. 경로는 바늘이 걸린 토큰을, 호스트는 바늘이 걸친
   레이블을 통째로 `<canary:NAME>` 으로 바꾼다. 가린 뒤에도 값이 찾아지면 문자열 전체를 자리표로 바꾼다.
   접는 키의 호스트도 가린 것을 쓴다. 이름 조회 채널의 `<host>` 는 가린 질의 이름이다
   (`<canary:GITHUB_TOKEN>.t.attacker.net`).
3. **canary-exfiltration 의 evidence 첫 칸은 `<host> <canary:NAME>` 이다.** `finalize` 의 중복 키가
   (ruleId, 위치, evidence[0]) 라서, 첫 칸이 호스트만이면 같은 도구·호스트의 카나리 둘이 하나로 지워진다.
   나머지 칸은 `<채널>: <형>` 이다(예: `요청의 본문: base64`). message 에는 채널 차례(URL, 헤더, 본문, 이름 조회)로
   첫째를 쓴다.
4. **`normalizeText` 와 `needlesFor` 를 둘 다 쓴다.** 먼저 `findForm(needlesFor(값))` 으로 찾고, 못 찾으면 요청
   쪽을 `normalizeText` 로 풀어 접은 값과 대조한다. 둘째 단계가 잡는 것은 값 사이에 폭 없는 문자를 끼운 경우와
   긴 base64·hex 토큰 안의 값이다. 그래서 형 이름에 `folded` 가 나올 수 있다(§3.4 는 네 형만 적었다).
5. **퍼센트 인코딩을 풀어서도 찾는다.** base64 의 `+`·`/`·`=` 가 쿼리에서 `%2B` 등으로 바뀌면 바늘이 안 맞는다.
   경로·헤더 값·본문 모두 받은 그대로와 푼 것 둘을 본다. `normalize.ts` 에 없는 디코딩이라 `network.ts` 에 두었다.
6. **`replay-miss` 는 (규칙, 도구, 호스트)로 접는다.** §8.4 의 이름은 "요청마다 한 번" 이고 §3.4 의 접기는
   호스트 단위다. §3.4 를 따랐다. 그 이름의 테스트는 호스트가 다른 두 요청으로 썼고, 같은 호스트 넷이 한 건으로
   접히는 테스트를 따로 두었다.
7. **`direct-ip` 의 접는 키는 포트를 뺀 주소다.** 포트가 여럿이면 `주소:포트` 를 정렬한 첫째가 message 에, 나머지가
   evidence 에 실린다. IPv6 는 `[주소]:포트` 로 적는다.
8. **`mode` 를 읽지 않는다.** `served` 가 이미 재생 누락을 말해 준다. 계약 필드라 그대로 받기만 한다.
9. **위치가 `server` 인 두 규칙(declared·pinned)의 둘째 칸.** 호출이 하나라도 있으면 `호출: …` 만 적고 단계는
   적지 않는다. 여러 도구에 걸치면 callId 를 글자가 같은 것끼리 한 번만 적는다(`placeholder` 가 도구 수만큼
   되풀이되지 않게).
10. **호출이 아닌 단계가 여럿이면 `단계: 시작, 종료` 로 잇는다.** §6.2 는 하나만 적은 모양이다.
11. **같은 (도구, 호스트)에 요청과 인증서 거부가 함께 있으면** `undeclared-destination` 은 요청 문장으로 한 건이다.
    "내용 못 봄" 문장은 요청이 하나도 없을 때만 쓴다.
12. **픽스처의 `expect.also`.** 요청이 하나라도 있으면 `declared-destination`(info) 이나
    `undeclared-destination` 중 하나가 반드시 난다. 그래서 "같은 가족의 다른 규칙은 걸리지 않는다" 를 글자대로
    지킬 수 없는 행이 있다(canary·internal·replay-miss). 함께 나도 되는 규칙을 `also` 에 적게 하고 테스트가 그
    밖의 규칙이 0 인지 본다. 반례 파일 이름은 `network-<규칙>.counter.json` 이다.
13. **선언으로 보는 표면 문자열을 좁혔다.** 키가 아니고, 위치가 `instructions` 이거나 도구·프롬프트·리소스의
    `description`(스키마 속성의 `.description` 포함)인 것만 본다. 이름·제목·기본값·리소스 uri·호출 응답(`result`)의
    URL 은 선언이 아니다. T5 가 `collectStrings` 결과를 통째로 넘겨도 된다.
14. **URL 다듬기.** 찾은 URL 끝의 `.,;:!?` 는 떼고 푼다(문장 끝 마침표). 호스트는 §3.7 의 호스트 이름 문법에
    맞아야 받는다(밑줄, 빈 레이블, 템플릿 꼴은 버린다). `.invalid` 등은 끝 레이블로 판정해서 `http://example/`
    같은 한 레이블 이름도 받지 않는다.
15. **`--allow-host` 값은 검증하지 않는다.** 소문자로 바꾸고 앞뒤 공백만 뗀다. 값이 이미 `*.` 로 시작하면 그 항목
    하나만 넣는다(`*.*.` 항목을 만들지 않는다). IP 를 주면 그대로 들어간다.
16. **호스트 대조.** 요청 쪽을 소문자로 바꾸고 끝의 점 하나를 뗀다. `*.example.com` 은 `example.com` 자체를 덮지
    않는다(`--allow-host` 는 두 항목을 함께 만들므로 문제없다).
17. **내부 주소 표는 `node:net` 의 `BlockList` 로 만들었다.** IPv4 로 사상된 IPv6(`::ffff:10.0.0.5`)도 내부로 본다.
    T4 의 `behavior/internal-address` 가 같은 표를 따로 가져야 한다. 공유할 파일이 내 Files 에 없다.

## 남은 위험

- **이름 조회의 base64·base32 유출은 못 잡는다.** 게이트웨이가 이름을 소문자로 남기는데 base64 바늘은
  대소문자를 가린다. hex 와 raw 만 잡힌다. DNS 유출에 흔한 base32 는 바늘 자체가 없다(`needlesFor` 의 범위).
- **T4 와 내부 주소 표가 어긋나면** 같은 접속이 `direct-ip` 와 `internal-address` 양쪽에 걸리거나 양쪽에서 빠진다.
  통합 때 경계 주소(`172.31.255.254`, `172.32.0.1`, `::ffff:10.0.0.5`)로 두 규칙을 함께 돌려 보기 바란다.
- **T5 의 `finalize`.** 지금 `audit.ts` 의 `orderedLocation` 은 `call` 위치의 필드를 지우고 `toolIndexOf` 는
  `call` 을 -1 로 본다(§9.4 에 T5 몫으로 적혀 있다). 그것이 들어가기 전에는 같은 호스트의 발견이 도구가 달라도
  중복 키로 합쳐진다. `runNetworkRules` 의 정렬은 T5 가 넓힌 뒤의 `finalize` 와 같은 키다.
- **경로의 제어 문자.** 경로와 헤더 이름은 서버가 정하는 문자열이다. 카나리는 가리지만 ANSI 이스케이프 같은
  제어 문자는 거르지 않았다. 게이트웨이의 HTTP 파서가 대부분 거절하겠지만 확인하지 않았다. 리포트 렌더러 쪽에서
  거르는지 볼 필요가 있다.
- **base64 로 실린 값을 가릴 때 경로가 많이 지워진다.** base64 는 `/` 도 알파벳이라 `/c/<base64>` 가 통째로
  `<canary:NAME>` 이 된다. 값이 남는 것보다 낫다고 보았다.
- **본문이 잘렸거나(`bodyTruncated`) 앱이 직접 압축·암호화한 본문**은 대조하지 못한다. 앞쪽은 T5 의 `skipped`
  문장이 알린다.
- **접은 형 대조의 범위.** `MCPEAK_CANARY_…` 의 `_` 를 `-` 나 공백으로 바꿔 보낸 것도 같은 값으로 본다. 오탐이라기
  보다 변형 유출이지만 형 이름은 `folded` 로 나온다.
- **Host 가 IP 인 요청**은 게이트웨이가 `blocked` 로 남기므로 `internal-destination` 과 `undeclared-destination` 이
  함께 난다(§3.4 를 글자대로 따른 결과다). `sandbox-target-server` 의 `fetch_status` 가 `url:metadata` 로
  `http://169.254.169.254/…` 를 부를 때, 접속이 게이트웨이가 아니라 그 주소로 바로 가므로 요청 기록은 생기지
  않을 것으로 보지만, 실제 실행에서 "여섯 규칙이 정확히 한 번" 에 영향이 없는지 T6 의 E2E 에서 확인이 필요하다.
