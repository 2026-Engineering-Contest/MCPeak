## 임의로 판단한 부분

1. **§7.3 의 최소 기준 파일.** 계획서가 적은 모양 그대로 `parseBaseline` 을 통과했다. 필드를 더 맞출 필요가
   없었다.
   ```json
   { "schemaVersion": 1, "server": { "name": "s", "version": "1" }, "tools": [], "surfaceHash": "<0 을 64번>" }
   ```
   `surfaceHash` 는 `"0".repeat(64)` 다. `readHash` 가 요구하는 것은 64자 소문자 hex 뿐이고 실제 해시와
   맞는지는 `parseBaseline` 이 보지 않는다.
2. **테스트를 먼저 썼지만 빨간 상태를 따로 실행해 확인하지는 않았다.** 테스트 파일들을 쓴 뒤 구현을 쓰고
   처음 돌렸을 때 전부 녹색이었다. 구현 없이 돌려 실패를 본 기록은 없다.
3. **계획서에 없는 테스트 다섯 건을 더했다**(`analyze-security.test.ts`).
   - `ANALYZE_USAGE 문장은 계약의 두 줄 그대로다`: §4.4 문장을 글자 단위로 고정한다.
   - `갱신 대상을 읽지 못하면 거절한다`: §4.4 의 "ENOENT 제외" 줄. 디렉터리를 `dir.json` 으로 만들어 EISDIR 로
     확인한다.
   - `audit 모듈을 못 읽으면 ANALYZE_RUNTIME_UNAVAILABLE 문장이다`(`prepareSecurityRun`): §5.2 의 둘째 불릿.
   - `candidateEnv 가 없으면 process.env 를 읽는다`.
   - `runner 를 바꾸지 않으면 실제 runAuditCommand 가 돌고, 대상이 없으면 CLI 의 문장이 error 다`: fake 없이
     `["--json"]` 만 넘긴다. CLI 가 연결 전에 사용법 오류로 끝나므로 서버를 띄우지 않는다. 기본 runner 와
     실제 `nodeAuditDependencies` 조립이 이어져 있는지 보는 유일한 유닛테스트다. 문장 전문이 아니라
     `오류 [` 로 시작하는지와 io 로 흘러간 글자가 같은지만 단언했다(문장은 cli 의 것이다).
4. **`형식이 틀리면 400 이다` 에 사례 다섯을 더했다**(`argv: [1]`, `serverId: 1`, `baselinePath: 1`,
   `allowHosts: [1]`, `sandbox: null`). 계획서의 넷은 그대로 있다.
5. **`startTestServer` 의 늘린 인자는 셋째 자리의 객체 하나다**(`{ prepare?, analyze? }`). 계획서는 "인자를
   늘린다" 고만 했다. 위치 인자 둘을 더하면 호출부가 `undefined` 를 셋씩 적게 된다. 기존 호출부는 고치지
   않았다.
6. **`loadAudit` 실패를 `prepareSecurityRun` 안에서 `parseBaseline` 실패와 갈라 잡았다.** 한 `try` 로 묶으면
   모듈 로드 실패가 "기준 파일이 아닌 파일" 문장으로 나간다.
7. **`GET /api/analyze/security/<runId>` 의 runId 는 `decodeParam` 으로 푼다.** 풀 수 없는 인코딩이면
   run 을 찾지 않고 404 문장을 낸다. 계획서는 이 경우를 적지 않았다.
8. **`routes.ts` 에 상수 둘을 뒀다**(`SECURITY_PATH`, `PROBE_POLICIES`). `probe` 값 집합은 CLI 의
   `PROBE_POLICIES` 가 export 되지 않아 다시 적었다. `ProbePolicy` 유니온이 늘면 이 집합은 타입체크가 잡지
   못한다(아래 "남은 위험").
9. **ADR 의 선택지 항목을 표로 적었다.** 다섯 결정이 한 문서에 있어 번호 목록보다 표가 짧다. 날짜는
   작성일인 2026-10-04 다.
10. **biome 이 `RunView.tsx` 의 `RunCounts` 조건을 여러 줄로 다시 접었다.** 조건에 `&& flow !== "audit"` 를
    더해 100자를 넘었기 때문이다. 뜻이 바뀐 곳은 지시한 두 곳뿐이다. `run-registry.ts` 의 import 와
    `run-target.ts` 의 `describeRun` 시그니처는 짧아져 한 줄이 됐다.

## 남은 위험

- **실제 서버에 붙는 경로는 이 태스크에서 돌리지 않았다.** `reportText` 가 CLI stdout 과 바이트 단위로
  같은지, `sandbox.cwd` 를 루트로 바꾼 것이 격리 마운트 범위에서 맞게 도는지는 T4 의 E2E 가 본다.
- **리포트 없이 끝났는데 stderr 도 비면 `400 { error: "" }` 이 된다.** 계획서 §5.3 그대로다. CLI 가 문장
  없이 0 이 아닌 코드로 끝나는 경로를 찾지는 못했지만, 그런 경로가 생기면 화면에 빈 alert 가 뜬다.
- **`routes.ts` 의 `PROBE_POLICIES` 는 손으로 복제한 집합이다.** `ProbePolicy` 에 값이 더해지면 화면이
  보낸 새 값이 "요청 형식이 올바르지 않습니다." 로 거절된다.
- **`sandboxLine`·`limits` 는 `renderReport` 의 줄 배치에 기댄다**(ADR-0110 "결과"). 배치가 바뀌면 이
  패키지의 테스트 셋이 빨개진다.
- **ADR 번호 0109** 는 작성 시점의 다음 번호다. 머지 직전에 다시 확인해야 한다(계획서 §3).
- 커밋하지 않았다. 커밋·푸시는 사람이 한다.
