## 임의로 판단한 부분

계획서가 글자로 정하지 않아 내가 고른 것이다. 리뷰에서 봐 주면 좋겠다.

1. **`useRunEvents` 를 `SecurityPanel` 본체가 아니라 그 파일 안의 자식 `SecurityProgress` 가 부른다.** 계획서 §5.7 은 패널에서 `const run = useRunEvents(runId)` 라고 적었다. 그대로 하면 "다시 점검" 으로 `runId` 가 바뀐 첫 렌더에 앞 run 의 `done`/`failed` 상태가 남아 있어(훅이 효과 안에서 상태를 비운다) 새 run 의 결과를 곧바로 읽고 409 를 받는다. 자식을 `key={runId}` 로 run 마다 새로 마운트해 이것을 막았고, ref 하나로 완료 보고를 run 당 한 번으로 묶었다. `"다시 점검은 같은 요청을 다시 POST 한다"` 테스트가 "새 run 이 끝나기 전에는 결과 GET 이 한 번뿐" 임을 단언한다. `run-stream.ts` 는 고치지 않았다.
2. **"다시 점검" 은 시작에 성공한 뒤에 앞 결과를 내리고 서버 선택 단계의 진행 패널로 돌아간다.** 계획서는 진행 패널을 `result === null` 일 때만 그린다고 했고, 격리 점검은 수 분이 걸려 진행이 보여야 한다고 봤다. 시작(POST)이 실패하면 앞 결과는 그대로 두고 그 위에 서버 문장을 보인다(토큰 탭의 다시 분석과 같은 규칙).
3. **`target.rememberCommand()` 는 `점검 시작` 경로에서만 부른다.** "다시 점검" 에서는 부르지 않는다.
4. **체크박스 마크업은 기존 `Toggle`(`components/Field.tsx`)을 그대로 썼다.** `<label><input type="checkbox">글자</label>` 와 그 아래 `pl-6 text-xs text-ink-muted` 힌트다. DOM id 는 `security-update-baseline`, `security-sandbox`, `security-compare-host`, 입력칸은 `security-baseline-path` 다.
5. **격리 하위 옵션(`--compare-host` 체크박스, 허용 호스트)은 격리를 켰을 때만 그린다.** 계획서의 "켜면 바로 아래 ... 그 아래" 를 그렇게 읽었다. 원격(http) 대상이면 체크가 남아 있어도 꺼진 것으로 그리고 하위 옵션을 숨긴다. 갱신 체크박스도 경로가 비면 꺼진 것으로 그린다(요청 조립과 같은 규칙).
6. **계획서에 없는 글자 둘을 더했다.** 옵션 묶음의 `<h2>` `점검 옵션`(접속 폼의 `접속` 제목과 같은 클래스), 그리고 `ArgChips` 위의 `<p>` `허용 호스트`. 뒤의 것은 `ArgChips` 의 라벨이 `서버 인자` 로 고정돼 있어서다. 아래 "보고만 하는 것" 1번 참고.
7. **`호출 정책` 은 `<label>` 이 아니라 `<p>` 다.** `SegmentedControl` 은 `<fieldset>` 이라 `htmlFor` 를 걸 입력이 없다. `StepServer` 의 `실행 방법` 과 같은 모양이다.

1. **`ArgChips` 의 라벨이 `서버 인자`, 입력칸 placeholder 가 `인자 하나씩 추가`, 제거 버튼이 `인자 X 제거` 로 고정이다.** 허용 호스트 자리에서 그대로 보인다. 계획서가 이 컴포넌트를 쓰라고 했고 수정 금지 목록에 있어 그대로 뒀다. `ArgChips` 에 라벨 prop 을 더하는 후속이 있으면 내가 더한 `<p>` `허용 호스트` 는 지우면 된다.

## 남은 위험

- **스트림이 붙지 못하면 버튼이 `점검 중…` 으로 남는다.** run 이 없다는 404(대시보드 서버를 다시 시작한 경우)에서 `run.error` 문장은 보이지만 `runId` 가 서 있어 `점검 시작` 이 다시 켜지지 않는다. 탭을 오가면 패널이 새로 마운트돼 풀린다. 계획서는 문장을 보이라고만 했고 이때 `runId` 를 비울지는 정하지 않아 그대로 뒀다.
- **탭을 옮기면 도는 점검의 화면 상태가 사라진다.** `SecurityPanel` 이 언마운트되므로 `runId`·결과가 없어진다(토큰 탭의 결과도 같은 식이다). 서버의 run 은 계속 돈다. 접속 상태만 남는다는 것이 계획서의 범위다.
- **실제 서버로는 돌려 보지 않았다.** 테스트는 jsdom 과 fetch·EventSource 스텁뿐이다. 실제 응답 모양과의 맞춤은 `api-types.ts` 타입과 T4 의 E2E 에 기대고 있고, 화면의 생김새(여백, 440px 진행 패널, 좁은 폭에서의 요청 표)는 브라우저에서 본 적이 없다.
- **`views` 가 `findings` 보다 짧게 오면** `splitFindings` 가 `undefined` 를 `SecurityFindingView` 로 단언하므로(§5.6 그대로) 화면이 그 발견에서 던진다. 서버 계약이 "같은 순서·같은 길이" 라 정상 응답에서는 일어나지 않는다.

### A. 허용 호스트 입력의 문장

오케스트레이터가 허용 Files 에 `packages/dashboard/web/src/components/ArgChips.tsx` 를 더했다.

- `SecurityPanel` 은 `label="허용 호스트"`, `placeholder="호스트 이름 하나씩 추가 (예: api.example.com)"`, 제거 버튼 이름 `허용 호스트 X 제거`, `hint="--allow-host"` 로 부른다. 내가 따로 넣었던 `<p>` `허용 호스트` 는 지웠다.

### B. 없는 run 에서 버튼이 풀리지 않던 것

- `SecurityProgress` 는 `useRunEvents` 의 `missing` 이 true 가 되면 `onMissing(run.error)` 를 한 번 부른다. 부모는 `runId` 를 null 로 되돌리고 그 문장을 `error` 에 세운다(`<pre role="alert">`). 버튼이 `점검 시작` 으로 돌아온다. 완료 보고와 같은 ref 를 쓰므로 부모에 알리는 것은 run 당 한 번이다.
- `missing` 이 아닌 `error`(조회만 실패)는 이전처럼 문장만 보이고 진행 패널과 `점검 중…` 을 유지한다. `run-stream.ts` 는 고치지 않았다.
- 테스트 둘을 더했다. `"없는 run 이면 그 문장을 보이고 다시 시작할 수 있다"` 는 `GET /api/runs/r1` 이 404 인 경우다(`run-view.test.tsx` 가 `missing` 을 만드는 방식). alert 의 글자가 훅이 만든 세 줄과 같고, 진행 패널이 사라지고, 스트림이 닫히는 것을 본다. `"run 조회만 실패하면 문장을 보이고 진행을 유지한다"` 는 500 인 경우다.

임의로 판단한 것 하나. 404 가 온 직후 한 렌더 동안은 진행 패널 안의 alert 가 그 문장을 보이고, 부모가 상태를 바꾼 다음 렌더에 그 자리가 부모의 alert 로 바뀐다. 문장이 같아 화면에서는 구별되지 않는다. 테스트는 버튼이 돌아온 뒤의 alert 를 본다.
