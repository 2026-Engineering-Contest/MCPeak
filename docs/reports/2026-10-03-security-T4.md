## 임의로 판단한 부분

1. **없는 명령 스펙의 접두 단언을 바꿨다.** `"오류 ["` 로 시작한다는 계획서의 단언을
   `error.split("\n")[0] === "→ 서버에 붙지 못했습니다: mcpeak-no-such-binary-xyz"` 로 바꿨다. `"해결:"` 포함 단언은 그대로다.
   `audit` 의 문장이 `오류 [코드]` 꼴이어야 한다는 것이 계획서의 의도였다면 이것은 테스트가 아니라 cli 쪽 문장의 문제이고,
   그 경우 이 단언을 되돌려야 한다. 오케스트레이터의 판단이 필요하다.
2. **"점검 run 은 Runs 목록에 없다" 스펙 안에서 점검을 한 번 돌린다.** 계획서는 `GET /api/runs` 만 적었다. 스펙 하나만 골라
   돌리면 점검 run 이 하나도 없는 상태에서 통과해 버리므로 그 앞에 weather 점검을 하나 넣었다.
3. **PATH 스펙의 비교 기준과 요청 꼴.** "격리 없는 같은 점검" 은 `inRepo` 서버에 `sandbox` 필드 없이 보낸 weather 점검으로 잡았다.
   격리 요청은 `sandbox: { compareHost: false, allowHosts: [] }` 다. PATH 로 줄 빈 디렉터리는 임시 루트와 따로 `mkdtemp` 로
   만들고 `afterAll` 에서 지운다(임시 루트에는 기준 파일이 생기므로 빈 디렉터리가 아니다).
4. **기준 파일 스펙의 단언 형태.** "ruleId 가 있고 그 message 가 같다" 를, `surface/baseline-created` 발견의 message 목록이
   정확히 `["기준 파일을 만들었습니다: weather.baseline.json"]` 한 건이라는 단언으로 적었다(여러 건이면 빨갛다).
5. **잔존 스펙은 계획서대로 "전부 빈 출력" 이다.** 실행 전 스냅샷과의 차이로 보는 방식은 쓰지 않았다. 그렇게 하면
   다른 세션과 겹쳐도 녹색이 되지만 계획서의 단언과 달라지고, 내 실행이 남긴 것과 남의 것을 id 만으로는 가를 수 없다.
   cli 의 `os.tmpdir()` 잔존(`mcpeak-audit-sandbox-*`)은 계획서 §7.5 에 없어 스펙에 넣지 않았고 수동으로만 확인했다.
6. **SSE 도우미는 `done` 이 오기 전에 스트림이 닫히면 그때까지의 이벤트로 돌아온다.** 그 경우 뒤의 결과 조회가 409 로
   빨갛게 되므로 따로 던지지 않았다.
7. **대기에 Monitor 를 썼다.** 다른 세션의 실행이 끝나기를 기다리는 폴링 루프 세 번이다. 태스크 작업 자체는 전부 전경에서 돌렸다.

## 남은 위험

- **같은 러너에서 두 격리 실행이 겹치면 양쪽 다 빨갛다.** CI 는 러너가 따로라 문제가 없지만, 로컬에서 worktree 둘이 동시에
  격리 E2E 를 돌리면 잔존 단언이 상대의 자원을 센다. 이번에 두 번 실제로 밟았다. 통합 게이트에서 이 파일을 돌릴 때는
  `mcpeak-sandbox-npx` 세션이 조용한지 먼저 봐야 한다.
- **Docker 스펙의 소요 시간은 이미지가 이미 있는 상태의 값이다**(약 3초). 이미지를 처음 만드는 CI 실행은 몇 분이 걸릴 수 있다.
  타임아웃은 cli 와 같은 600초다.
- **ci.yml 명령은 `--project` 없이 돈다.** 파일 직렬은 e2e 갈래의 `fileParallelism: false` 에 기대고, 이번 재시도에서
  두 파일이 겹치지 않고 32개 전부 통과하는 것으로 확인했다(한 번).
- `ci.yml` 은 전원 리뷰 대상이다.
