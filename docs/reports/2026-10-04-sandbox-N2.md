## 실패 경로에 넣은 방식

연결 실패 문장은 `packages/audit/src/audit.ts` 의 `connectFailed` 가 세 줄로 만든다(대상 줄, 원인 줄, 해결 줄).
CLI 는 그 블록을 그대로 찍고 뒤에 서버 프로세스 진단을 붙인다. 고친 자리는 `audit-command.ts` 안의
`writeAuditFailure` 하나다. 오류 코드가 `CONNECT_FAILED` 이고 실패한 연결이 "격리 쪽 + 실행기" 였을 때만
`해결: ` 로 시작하는 줄을 빼고 새 해결 줄을 끝에 붙인다. 대상 줄, 원인 줄, 진단 블록은 그대로다.

실제 출력(유닛 스펙이 글자까지 고정한다):

```
격리 컨테이너를 준비합니다.
격리 안에서는 패키지를 매번 새로 받습니다. 서버가 뜨기까지 1분까지 기다립니다.
→ 서버에 붙지 못했습니다: npx -y pkg@9.9.9
→ 제한 시간 안에 MCP 초기화를 마치지 못했습니다.
해결: 격리 안에서 패키지를 받지 못했거나 1분 안에 뜨지 못했습니다. 패키지 이름과 버전을 확인하고, 큰 패키지는 로컬에 설치한 뒤 node 로 띄우세요.
```

## 임의로 판단한 부분

1. **해결 줄을 바꾸는 방식.** `CONNECT_FAILED` 블록에서 `해결: ` 로 시작하는 줄을 빼고 새 줄을 끝에 붙인다.
   블록의 모양(마지막 줄이 해결)은 `packages/audit` 가 정한 것이라, 그쪽이 해결 줄의 머리말을 바꾸면 해결 줄이
   둘 나온다. 유닛 스펙이 진짜 `audit` 로 전체 문자열을 고정하므로 그때 빨강이 된다.
2. **실패 표지는 "격리 쪽 연결이 던졌는가" 로 세운다.** 원인이 제한 시간인지 다른 것인지(이미지 없음, docker
   CLI 실패 등)는 가르지 않는다. 지시의 조건(격리 대상이고 명령이 npx·npm 인 접속 실패)을 그대로 따랐다.
3. **진행 문장은 `connect` 안에서 낸다.** 격리가 실제로 켜졌는지는 CLI 가 미리 알 수 없고(Docker 가 없으면 audit
   가 원래 대상으로 붙는다), audit 가 다른 대상을 넘겼다는 것이 유일한 신호다. 그래서 Docker 가 없는 실행에는
   문장도 60초도 없다. 스펙으로 고정했다.
4. **`progress` 정의를 위로 올렸다.** `connect` 가 쓰기 때문이다. 식은 그대로다.
5. 스펙을 지시보다 더 썼다: `npm` 대상, 역슬래시 경로, 인자에 `npx` 가 있는 `node`, 격리 없는 npx 와 Docker 없는
   `--sandbox` npx 는 기본값 그대로, 실패 뒤 서버 프로세스 진단 블록이 node 대상의 것과 글자까지 같다.
6. 유닛 스펙에서 npx 대상의 종료 코드는 `not.toBe(1)` 로 본다. 절대 경로 npx 등은 launch 규칙 발견으로 2 가
   나온다. 이 스펙이 보는 것은 연결 옵션이지 발견 수가 아니다.
7. E2E 의 registry 단언은 evidence 첫 칸이 `registry.npmjs.org` 이거나 `registry.npmjs.org ` 로 시작하는 network
   발견을 모은다. 카나리 유출 발견의 첫 칸이 `<호스트> <자리표>` 꼴이라, 정확 일치만 보면 그 발견을 놓친다.
8. E2E 의 "서버 전체 위치" 는 `ruleId` 가 `behavior/` 로 시작하고 `location.kind === "server"` 인 발견으로 봤다
   (`types.ts` 의 `Location` 주석: 호출이 아닌 단계의 관측은 `{ kind: "server" }` 에 붙는다).
9. E2E 스펙은 `once()` 로 나눠 쓰지 않고 `cli()` 를 직접 부른다. 이 실행을 보는 스펙이 하나뿐이다.

## 남은 위험

1. **잔존 검사가 라벨 전체를 센다.** `audit-sandbox-e2e.test.ts` 의 `leftovers()` 는 `mcpeak.audit=1` 라벨과
   `os.tmpdir()` 의 `mcpeak-audit-sandbox-*` 전부를 센다. 같은 머신에서 두 실행이 겹치면 서로의 자원을 잔존으로
   세어 양쪽이 빨강이 된다. 실패 문장은 "남았다" 만 말하고 누구 것인지 말하지 않아 정리 결함으로 오진하기 쉽다.
   실행별 식별자로 좁히는 것이 맞아 보이지만 지시대로 고치지 않았다. 로컬 운용 지침의 거짓 신호 표에 들어갈
   항목이다.
2. E2E 가 `registry.npmjs.org` 와 특정 패키지 버전(`2026.8.31`)에 기댄다. 레지스트리가 느리거나 그 버전이 내려가면
   빨강이다. 60초 안에 못 받으면 접속 실패(종료 코드 1)로 드러난다. 지금 실측은 전체 28.6초다.
3. 60초는 core 의 상한이라 더 줄 수 없다. 큰 패키지나 느린 회선에서는 여전히 실패하고, 그때 사용자가 보는 것이
   새 해결 줄이다. 상한을 올리는 것은 `packages/core` 의 일이다.
4. `--sandbox-replay` 로 npx 서버를 돌릴 때도 진행 문장과 60초가 적용된다. 재생에서 "매번 새로 받습니다" 가
   글자 그대로 맞는지는 확인하지 않았다(재생 실행으로 npx 서버를 돌려 보지 않았다).
5. `npm` 을 명령으로 준 경우는 유닛 스펙으로만 봤고 실물은 `npx` 만 돌렸다(N1 의 남은 위험 6번과 같다).
6. Windows 의 `npx.cmd` 는 실행기로 보지 않는다. 백엔드의 판정과 같게 두라는 지시대로다.
