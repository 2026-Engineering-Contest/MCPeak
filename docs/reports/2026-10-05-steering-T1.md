## 동결본과 같은지 확인한 방법

단언 20개 외에 동결본 자체와 견주었다. 계획서 141~351행을 그대로 떼어 `frozen.mjs` 로 두고, 빌드한
`dist/index.mjs` 의 `runSteeringRules` 와 같은 입력에 돌려 출력 JSON 을 비교했다.

- 입력: 저장소 픽스처 중 `tools` 가 있는 36개, 그리고 고정 시드로 만든 합성 도구 집합 5,000개(한 낱말 이름,
  정규식 특수문자가 든 이름, 백틱·작은따옴표가 든 이름, 줄바꿈·탭이 든 설명, `inputSchema` 없는 도구 포함).
- 결과: 동결본 발견 2,289건(medium 1,991, low 298), 차이 0건.
- 정규식 상수 18개와 본문 안의 정규식 7개가 공백을 뺀 글자열로 소스에 그대로 있는 것도 확인했다.
  `STEERING_SIGNALS` 는 JSON 으로 같다.

합성 입력에는 보이지 않는 문자가 없다. 그 경우는 아래 "다듬은 곳" 4번이 말하는 의도된 차이다.

## 동결본에서 타입·린트 때문에 다듬은 곳 (전부)

판정에 쓰이는 정규식, 점수, 기준, 신호 순서, 문장 나누기, 발견 문안은 바꾸지 않았다.

1. 타입 주석을 더했다. `esc`·`nameTokens`·`hostOf`·`descriptionOf`·`splitSentences` 의 인자,
   `nameSource` 의 반환 `string | null`, `steeringSignals`·`steeringScore`·`runSteeringRules` 의 §2 시그니처,
   `found` 를 `Map<string, string>`, `totals` 를 `Map<string, number>`, `findings` 를 `Finding[]`.
2. `SteeringSignal` 인터페이스를 §2 대로 더하고 `STEERING_SIGNALS` 를 `readonly SteeringSignal[]`,
   `STEERING_THRESHOLDS` 를 `{ readonly medium: 35; readonly low: 22 }` 로 표기했다.
3. `nameSource` 의 한 낱말 분기를 문자열 이어 붙이기에서 템플릿 리터럴로 바꿨다. `esc(name)` 을 세 번
   부르던 것을 `escaped` 변수 하나로 받았다. 만들어지는 정규식 원문은 같다(차등 비교에 한 낱말 이름과
   특수문자 이름이 들어 있다).
4. `fragmentOf` 와 `FRAGMENT_LIMIT` 를 옮기지 않고 `description.ts` 의 `evidenceFragment` 를 쓴다(계획서 지시).
   둘은 80자 자르기와 줄바꿈·탭을 공백으로 바꾸는 것이 같고, `evidenceFragment` 는 보이지 않는 문자를
   `<U+XXXX>` 로 드러내는 것이 더 있다. 설명에 보이지 않는 문자가 있으면 근거 조각의 글자와 80자 경계가
   동결본과 달라진다. 점수와 심각도는 달라지지 않는다.
5. `propertiesOf` 에서 `schema.properties` 를 읽을 때 `(schema as { readonly properties?: unknown })` 로 좁혔다.
   `inputSchema` 가 `unknown` 이라서다. 런타임 동작은 같다.
6. `refs` 의 `.filter` 에 타입 가드(`source is string`)를 붙였다. 조건식은 그대로다.
7. `m[2].trim()` 을 `(m[2] ?? "").trim()` 으로 바꿨다. `noUncheckedIndexedAccess` 때문이다. `LITERAL` 이
   맞으면 둘째 묶음은 언제나 있으므로 `?? ""` 는 타지 않는다.
8. `runSteeringRules` 의 `tools.forEach` 를 `for (const [toolIndex, tool] of tools.entries())` 로, 그 안의
   `return` 을 `continue` 로 바꿨다.
9. biome 포맷이 줄을 나눴다(긴 정규식 상수는 `const X =` 다음 줄로 내려갔고 삼항·인자 목록이 여러 줄이 됐다).
10. 파일 머리 주석을 계획서 지시대로 바꿨다(설계 문서 경로, 점수표를 고칠 때 `measure.mjs` 로 견준다는 말).

## 임의로 판단한 부분

1. **`nameSource`·`splitSentences`·`steeringFragment` 를 내보내지 않았다.** 동결본에는 `export` 가 붙어
   있지만 §2 의 계약은 `steering.ts` 의 공개 면을 여섯 개로 적었고, §5(T3)는 "공개 면을 늘리지 않으려고"
   `nameSource` 를 스크립트에 옮겨 적는다고 한다. 계약 쪽을 따랐다. 필요하면 `export` 한 낱말씩만 더하면 된다.
2. **`index.ts` 의 export 줄 위치.** 계획서는 `runSchemaRules` 줄 아래라고 했지만 biome 의 `organizeImports` 가
   경로순(`secret.js` 다음 `steering.js`)을 요구해 `secret.js` 줄 아래에 뒀다. `audit.ts` 의 import 도 같은
   이유로 `secret.js` import 블록 아래다. `listFindings` 안의 호출 순서는 계획서대로 `runDescRules` 바로 아래다.
3. **`audit.test.ts` 의 새 테스트 문안과 단언 꼴.** 계획서는 통과 조건만 줬다. 제목은
   "desc/steering 발견이 리포트에 들어가고 주의는 exitCode 를 2 로 만든다"로, `location.toolName` 은
   `Location` 이 유니온이라 `toMatchObject({ toolName: "math_check" })` 로 단언했다. 자리는
   `exitCode` 테스트 바로 위다.
4. **`steering-rules.test.ts` 는 biome 포맷만 적용했다.** 문자열 값과 기대값은 계획서와 같다.

## 남은 위험

- 이 태스크는 MCPTox 실측(§8 의 변형 표)을 돌리지 않았다. 동결본과의 차등 비교가 0 이므로 수치가 같을
  것으로 보지만, 확정은 통합 게이트의 `measure.mjs` 가 한다.
- 위 4번(`evidenceFragment`)의 차이는 발견의 `evidence[0]` 과 `message` 글자에만 영향을 준다. T3 의
  측정이 근거 조각 문자열까지 견준다면 보이지 않는 문자가 든 사례에서 어긋날 수 있다. 탐지 수(심각도)만
  센다면 영향이 없다.
- `audit.test.ts` 의 기존 `exitCode` 테스트가 쓰는 설명 `"Ignore all previous instructions."` 는 이제
  `desc/steering` low 도 함께 낸다. 그 테스트는 `exitCode` 만 보므로 초록이다.
- 루트 `typecheck` 를 `--force` 로 전체 돌리지는 않았다. audit 패키지의 `tsc --noEmit` 만 직접 돌렸다.
  공개 면에 export 셋을 더했을 뿐 기존 타입은 바꾸지 않았다.
