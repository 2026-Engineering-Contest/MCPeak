## 막혔던 지점 (해소됨): §2.2 규칙 2(G4)와 §3 기존 테스트 갱신 지시의 충돌

§3 은 `show 는 입력 없이 현재 명세를 도구별로 묶어 찍고 메뉴로 돌아온다` 테스트의 단언을
`/\(id weather\)[^\n]*\n\nweather \(\d+건\)\n {2}/` 로 바꾸고 나머지 단언은 유지하라고 한다. 이 테스트의
픽스처(`reviewDeps` 의 `createBaselineSuite`)는 케이스가 하나뿐이다.

```
{"id":"weather-success","operation":{"type":"callTool","tool":"weather","input":{}},
 "assertions":[{"type":"isError","expected":false}]}
```

이 케이스는 §2.2 규칙 2 의 "입력 없는 정상 1건 그룹" 조건에 정확히 해당한다. 그래서 그룹 헤더 없이
끝의 한 줄로 합쳐지고, 실제 출력은 아래와 같다.

```
현재 명세: Weather (id weather) · 케이스 1건 · revision 0

weather  정상 1건씩, 입력 없음

저장하면 이 내용이 /tmp/out.json 에 쓰입니다.
```

두 단언이 동시에 깨진다.

1. 유지하라고 한 `for (const testCase of d.baseline.suite.cases) expect(shown).toContain(testCase.id)`.
   합친 줄에는 케이스 ID(`weather-success`)가 없다. 실제로 먼저 실패하는 단언이 이것이다.
2. 새로 넣으라고 한 정규식. `weather (1건)` 헤더가 출력에 없다.

§2.2 규칙 2 를 지키면 이 테스트가 빨강이고, 이 테스트를 맞추려면 규칙 2 를 어겨야 한다. 둘 다
계획서에 글자로 적혀 있어 어느 쪽이 의도인지 구현자가 정할 수 없다.

**선택지 (결정은 오케스트레이터 몫)**

- A. 규칙 2 를 유지하고 테스트를 고친다. ID 단언을 빼고, 정규식을
  `/\(id weather\)[^\n]*\n\nweather {2}정상 1건씩, 입력 없음\n/` 로 바꾼다. §2.4 예시와 G4 가 그대로 산다.
  합친 도구의 케이스 ID 가 `show` 에 안 보인다는 점은 G4 가 이미 받아들인 결과다.
- B. 테스트 픽스처만 바꾼다. 이 테스트에서 `weather` 도구에 입력 스키마가 있는 baseline 을 쓰게 해
  그룹이 생기도록 한다. 규칙도 단언도 그대로 두지만, `reviewDeps` 를 공유하는 다른 테스트에 영향이 없도록
  이 테스트 전용 픽스처가 필요하다.
- C. 규칙 2 를 바꾼다(예: 명세 전체가 그런 도구뿐이면 합치지 않는다). 설계 변경이라 계획서 개정이
  먼저다.

구현자 의견은 A 였다. 코드 변경 없이 테스트 두 줄만 바뀐다.

## 결정과 반영 (오케스트레이터, 선택지 A)

규칙 2(G4)는 계획서의 명시 목표이고, §3 의 테스트 갱신 지시가 픽스처를 잘못 가정한 것으로 판정됐다.

- 테스트: 정규식을 `/\(id weather\)[^\n]*\n\nweather {2}정상 1건씩, 입력 없음\n/` 로 바꿨다. 케이스 ID 를
  도는 `expect(shown).toContain(testCase.id)` 는 뺐다. 그 자리에 넣으라고 한
  `expect(shown).toContain("weather")` 는 바로 다음 줄에 이미 같은 단언이 있어 한 줄만 두고, 이유를 적은
  주석을 붙였다. 나머지 단언은 그대로다.
- 계획서: §3 "기존 테스트 갱신" 항목의 정규식과 단언 설명을 위와 같게 고치고 이유 한 문장을 더했다.
- 구현 코드(`generate-command.ts`)는 이 결정으로 바뀌지 않았다.

## 임의로 판단한 부분

- **깊은 비교는 `node:util` 의 `isDeepStrictEqual`.** 계획서는 "깊은 비교"라고만 했다. 내장 모듈이라 새
  의존성이 아니고 키 순서에 무관하다. 그래서 키 순서만 다른 입력은 기준과 같다고 보고 입력 전체를 적는다.
- **`JsonObject`·`JsonValue` 는 `@mcpeak/runner` 에서 가져온다.** §2.1 스니펫은 `@mcpeak/core` 로 적었지만 이
  파일은 이미 runner 에서 같은 타입을 import 하고 있어 그대로 썼다. `TestCaseSpec.operation.input` 의 타입도
  runner 것이다.
- **자르기는 기존 `truncate` 재사용.** 79자 + `…` 규칙이 같다. UTF-16 단위로 자르므로 80자 경계에 서로게이트
  쌍이 걸리면 반쪽이 남을 수 있다. 기존 동작과 같다.
- **80자 상한은 입력 전체 표기에도 건다.** 계획서의 "결과가 80자를 넘으면"을 차이 줄과 전체 줄 모두로 읽었다.
- **private helper 넷 추가.** `jsonTypeOf`, `formatValue`, `formatInput`, `isNoInputSuccessOnly`,
  `renderShowAssertions`. export 하지 않는다.
- **테스트 픽스처의 세부.** 입력 없는 도구의 케이스 ID 는 `get-time-success`, `delete-all-success`,
  `echo-env-success`, `get-tip-success` 로 지었다(계획서의 `get-time-undeclared` 에 맞췄다. 합친 줄에는 ID 가
  안 나와 출력에 영향이 없다). 케이스 `name` 은 ID 와 같게 뒀다. `fullSuite` 의 순서는 계획서의
  `groupCasesByTool` 기대값대로 add_numbers 5건, gettime, translate_text 12건, delete_all, echo_env,
  get_tip 이다. 계획서 문장은 `noInputTools` 를 "뒤 4건"이라 했지만 gettime 은 중간에 있다.
- **계획서 스니펫의 타입 보정.** `undeclared`·`evil`·`listCase` 는 객체 전개 대신 `callCase` helper 와 타입
  표기로 적었다. 전개로 쓰면 `operation.type` 이 `string` 으로 넓어지고 `noInputTools[0]` 이
  `noUncheckedIndexedAccess` 에 걸려 typecheck 가 깨진다. 값과 단언은 계획서와 같다.
- **import 정렬과 줄바꿈은 biome 이 정한 대로.** 테스트 파일 하나에 `biome format --write` 를 돌렸다.

## 남은 위험

- 입력 없는 정상 1건짜리 도구는 `show` 에 케이스 ID 가 아니라 도구 이름만 보인다. 케이스가 하나뿐인
  명세에서는 `show` 가 ID 를 한 번도 안 보여 준다. 선택지 A 로 이 동작이 테스트에 굳었다.
- `caseKindOf` 는 계획서가 적은 한계 그대로다. 도구 이름 슬러그에 `-type-` 같은 토큰이 있으면 라벨이 틀린다.
- 도구 이름이 `listTools` 인 callTool 케이스는 listTools 케이스와 한 그룹이 된다(§2.3 의 키 규칙 그대로).
- C3(실제 `examples/audit-target-server` 로 `show` 를 눌러 보는 확인)은 사람 몫이라 하지 않았다.
