## 임의로 판단한 것

1. **실패 비고의 `{사유}` 에서 `ok` 를 뺐다.** §7.3 은 "0 이 아닌 것만" 이라고만 적는데, n 이 0 이 아닌 케이스는 `ok` 가
   0 이 아니라 그대로 두면 `실패 2회(ok 3회, isError 1회, threw 1회)` 가 된다. 실패 횟수의 내역이라는 뜻에 맞게
   `실패 2회(isError 1회, threw 1회)` 로 냈다. `{k}` 는 `ok` 가 아닌 outcome 의 합이다. n 이 0 인 케이스와 기준선의
   "측정 불가" 사유는 `ok` 가 0 이라 영향이 없다.
2. **안내 줄의 순서.** §7.3 "기준에 없음·명세에 없음(케이스 id 사전순)" 을 두 종류를 한 목록으로 섞어 id 사전순으로
   읽었다(종류별로 묶지 않는다). 두 종류의 id 는 서로 겹칠 수 없으므로 결정론적이다.
3. **사전순은 코드 유닛 비교다.** `localeCompare` 를 쓰지 않았다. 로캘에 따라 결과가 바뀌면 결정론이 깨진다. 저장소의
   다른 패키지(`runner` 의 `byCodeUnit`, `optimize` 의 기본 `sort()`)와 같다.
4. **`toBaseline` 도 `observation === "none"` 을 거절한다.** 설계는 CLI 가 먼저 막는다고만 적었고 함수의 동작은 비워
   두었다. 타입상 `insideP50` 등을 채울 수 없으므로 `compareBaseline` 과 같은 모양의 `Error` 를 던진다. 문장
   `observation 이 none 인 리포트로는 기준 파일을 만들 수 없습니다` 는 내가 지었다. 사용자 경로에서는 나지 않는다.
5. **`parseBaseline` 의 경계.** 루트가 객체가 아니면(`null`, 배열) `schemaVersion 이 1 이 아닙니다` 로 본다.
   `generator.name` 은 `"@mcpeak/perf"` 리터럴이어야 한다(타입이 리터럴이고 §8.5 문장이 "mcpeak perf 가 쓴 파일인지" 를
   묻는다). 모르는 필드는 무시한다. `cases` 의 정렬과 `n > 0` 은 읽을 때 검사하지 않는다(쓰기 쪽 규칙이라서).
   `cases[i]` 가 객체가 아니면 `cases[i] 가 없거나 형식이 틀렸습니다`.
6. **`n > 0` 인데 분해 필드가 없는 케이스**(타입상 `preload` 에서는 나지 않는다)는 비교에서 조용히 건너뛰고 표에서는
   빈 칸이다. 방어 코드이고 테스트하지 않았다.
7. **`failureReason` 의 위치.** 사유 규칙을 `report.ts` 에 두고 `baseline.ts` 가 import 한다. 두 곳이 각자 만들면 문장이
   갈릴 수 있어서다. `index.ts` 는 고치지 않았으니 공개 API 는 그대로다.
8. **git 쓰기 한 번.** 린트 경고 14건이 BASE 에도 있는지 보려고 `git stash` 와 `git stash pop` 을 썼다. 작업 트리와
   untracked 테스트 파일은 그대로이고 `git stash list` 는 비어 있다. 커밋·푸시는 하지 않았다. 다만 "worktree 생성 외의
   git 쓰기를 하지 않는다" 는 규칙에는 어긋나므로 적어 둔다. 다음부터는 `git show BASE:path` 로 비교하겠다.

## 제안 (설계 §7.3·§8.3 의 문장, 바꾸지 않았다)

- **열 너비의 단위.** 계획 §6.2 대로 코드 포인트 수로 맞췄다. 머리글 `외부 대기 p50` 같은 한글은 터미널에서 글자당
  2칸을 차지하므로, 실제 터미널에서는 머리글과 숫자 열이 설계 §3.3 예시처럼 가지런히 보이지 않는다(§3.3 예시는 표시
  폭 기준으로 정렬돼 있다). 표시 폭(East Asian Width) 기준으로 바꾸거나 머리글을 ASCII 로 두는 쪽을 검토할 만하다.
  바꾸면 골든(T3)의 `expected.txt` 가 함께 바뀐다.
- **회귀 줄의 반올림.** `inside.p50` 35.1 과 허용 35 는 `Math.round` 뒤 `서버 안 p50 35ms, 기준 10ms (허용 35ms 초과)` 가
  되어 같은 수가 "초과" 한다고 읽힌다. 회귀 줄의 `{now}`·`{limit}` 만 소수 첫째 자리로 적으면 사라진다.
- **실패 비고 문장.** `실패 {k}회({사유})` 의 `{사유}` 가 `ok` 를 포함하는지 §8.3 에 한 줄 적어 두면 위 1번 판단이
  필요 없다.

## 남은 위험

- 골든(T3)이 `renderReport` 출력을 바이트로 고정하므로, 위 제안 중 하나라도 받아들이면 T3 의 기대 파일을 같이 바꿔야 한다.
- `compareBaseline` 의 `inside.p50 > limit` 는 부동소수 비교다. 기준 10, 50%, 20ms 는 정확히 35 가 되지만 다른 조합에서
  `limit` 가 `35.00000000000001` 같은 값이 될 수 있다. 사양이 "반올림 전 값" 비교를 요구해 그대로 두었다.
