## 담은 내용

- 배경: `ToolDef.inputSchema`는 타입이 `unknown`이고 남의 서버가 쓴 임의의 JSON Schema라는 점,
  설계 문서 §4.1의 `anyOf` 오탐 예시를 JSON 그대로 옮김
- 선택지 A(미지원 키워드 무시) / B(완전한 JSON Schema 검증기) / C(부분집합만 검사하고 침묵)
- 결정: C안. 정규화 규칙(루트 포기, 필드 단위 포기, `additionalProperties` 기본값 처리) 요약
- 이유: 승인 차단 근거이므로 오탐 1건이 미탐 1건보다 비싸다는 점, B안을 버린 두 이유
  (목록 밖 런타임 의존성 금지, 통제 못 하는 코드가 차단 권한을 가짐),
  ADR-0010과 대상이 다른 점(우리가 정의한 것 대 남이 쓴 것, 지원 범위 대 못 읽을 때의 행동)
- 결과: 미탐 감수, `SCHEMA_NOT_ANALYZABLE`을 finding으로 내보내는 이유
  (finding 0건의 두 가지 뜻을 소비자가 구분해야 함), severity가 `advisory`인 이유,
  정보 손실 지점을 테스트로 고정해야 한다는 점

## 내가 임의로 판단한 부분

1. 제목을 "서버 입력 스키마는 해석 가능한 부분집합만 검사하고 나머지는 침묵한다"로 잡았다.
   ADR-0010의 "~한다" 서술형 제목 형식을 따랐다.
2. 머리말에 `승인: 미승인`과 `참조:` 줄을 넣었다. 지시에 없었지만 ADR-0010에 있는 항목이고
   "형식은 ADR-0010을 따르라"는 지시에 포함된다고 봤다.
3. 결정 항목에 설계 문서 §4.2의 정규화 규칙 세 가지를 요약해 넣었다. 지시의 필수 항목은
   아니지만, 결정 항목에 "C안 채택"만 적으면 무엇을 검사하고 무엇을 포기하는지가 ADR만
   읽어서는 안 보인다고 판단했다. 루트 차단 키워드 전체 목록은 설계 문서에 있으므로
   중복 기재하지 않고 계열 이름으로만 적었다.
4. 결과 항목에 severity가 `advisory`라는 점과 정보 손실 지점을 테스트로 고정해야 한다는
   점을 추가했다. 각각 설계 문서 §6, §12에서 가져왔다.
