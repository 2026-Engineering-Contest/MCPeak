# 시험 실행 입력값 교정 설계 (2026-08-15)

- 담당 패키지: `cli` (주), `generate` (교정 요청과 명세 반영)
- 작성자: @seodduu
- 선행: `docs/superpowers/specs/2026-08-15-dry-run-approval-gate-design.md`(승인 전 시험 실행 게이트),
  ADR-0024(케이스 분류 저장 위치), ADR-0023(초기화 훅), ADR-0017(승인 지문 계산 범위),
  ADR-0022(위반 케이스 생성 정책), ADR-0008(승인 화면 redaction 범위)
- 신규 ADR 대상 2건: 교정 단계의 권한 경계(§11.1), 지문 표시 시점 이동(§11.2)

## 1. 배경

### 1.1 분류 화면이 감당하지 못하는 질문

시험 실행 게이트는 실패한 케이스를 사람에게 넘기고 **서버 결함 / 명세 오류 / 판단 보류** 중
하나를 받는다. 이 질문은 답하기 어렵다. 서버가 무엇을 약속했는지는 코드 어디에도 없고, 사람
머릿속이나 문서에만 있기 때문이다.

문제는 **지금 그 어려운 질문을 받는 실패의 다수가 사실 쉬운 문제**라는 것이다.
`examples/weather-server` 에 게이트를 처음 돌렸을 때 나온 실패가 그렇다.

```
  [1] get_weather가 오류 없이 응답한다
      isError  정상 응답을 기대했지만 오류 응답을 받았습니다.
```

원인은 `packages/generate/src/synthesize.ts:69` 의 `synthesizeValue` 다. 입력값을 스키마만 보고
합성하는데, 우선순위가 `const` → `default` → `examples[0]` → `enum[0]` → 타입별 고정값이다.
앞의 넷이 없으면 문자열은 `"example"` 이 된다.

```json
{ "city": { "type": "string", "description": "도시 이름" } }
```

`weather-server` 의 선언에는 넷이 다 없다. 그래서 `city: "example"` 로 호출하고, 서버는
`서울/부산/제주` 만 알기 때문에 오류를 준다.

**이 실패에는 정보가 없다.** 서버도 멀쩡하고 명세의 의도도 맞다. 값 하나가 틀렸을 뿐이다.
그런데 사용자는 이것을 "서버가 틀렸나 명세가 틀렸나" 라는 질문으로 받는다. 답하기 쉬운
질문(값이 무엇인가)을 답하기 어려운 질문으로 바꿔서 던지고 있다.

### 1.2 서버는 이미 답을 줬다

같은 실행에서 서버가 반환한 오류 본문이 이렇다.

```
→ '문자열' 의 날씨 데이터가 없습니다. 사용 가능한 도시: 서울, 부산, 제주
→ 이 예제 서버는 고정 데이터만 가지고 있습니다.
```

지금은 이 문장을 화면에 찍고 버린다. 값을 고칠 근거가 손에 있는데 쓰지 않는다.

### 1.3 무엇을 만드는가

분류 화면 **앞에** 입력값 교정 단계를 넣는다. 실패가 입력값 때문으로 보이면 값을 고쳐 그
케이스만 다시 실행한다. 통과하면 분류 질문이 뜨지 않고 교정된 값이 명세에 반영된다.

두 번 고쳐도 실패하면 분류 화면으로 넘긴다. 그때 남는 질문은 "서버가 깨졌나, 아니면 이 단언이
틀렸나" 로 좁혀져 있다. 값 문제는 이미 배제됐기 때문이다.

## 2. 목표 / 비범위 / 완료 조건

### 목표

1. 입력값 합성 실패가 만든 케이스 실패가 분류 화면에 도달하지 않는다.
2. 교정에 쓸 값의 후보를 서버의 오류 응답에서 뽑는다. 근거가 없으면 사람에게 받는다.
3. 교정 결과가 저장되는 명세에 반영된다.
4. 사용자가 승인하는 지문이 실제로 실행되고 저장되는 명세의 지문과 같다.

### 비범위

- **기대값·단언 교정.** 이 단계는 `operation.input` 만 고친다. §4.3 이 근거다.
- **생성 시점 사전 질문.** 실패 전에 값을 묻는 방식은 §12 에서 배제했다.
- **`test` 경로.** 저장된 명세를 실행할 때는 교정하지 않는다. 그 시점의 실패는 회귀다.
- **위반 케이스의 입력 교정.** 입력이 일부러 틀린 케이스다. §4.2 가 근거다.

### 완료 조건

- `examples/weather-server` 대상 `generate` 대화형 경로에서, `city` 합성 실패가 분류 화면에
  도달하지 않고 교정 단계에서 끝난다.
- 교정된 값이 저장된 명세의 `cases[].operation.input` 에 들어 있다.
- 화면에 표시된 최종 지문과 저장된 `approval.fingerprint` 가 같다. 교정이 있어도 같다.
- 교정을 두 번 해도 실패하면 분류 화면이 뜨고, 그 화면에 시도 이력이 함께 나온다.
- 교정 단계 전체를 끄는 길이 있다(`--no-repair`).

## 3. 저장 경로 순서 (기존 설계 §4.2 를 대체한다)

기존 순서와 다른 곳에 **▲** 를 붙였다.

```
 1. dryRun 이 꺼져 있으면 §8.5 확인 후 12 로 간다
 2. §8.1 고지 + 확인. 거절하면 메뉴로
 3. resetCmd 가 있으면 runResetCommand. 실패하면 안내 후 메뉴로
 4. wireCassette
 5. runDryRun
 6. warnings 표시
 7. aborted 면 §8.4 표시 후 메뉴로
 8. 결과 표시(§8.2)
 9. ▲ 입력값 교정 (§4). 교정→재실행을 케이스당 최대 2회
10. ▲ 교정 결과를 후보 명세에 반영 (§5)
11. 남은 실패를 분류(§8.3). 미분류·명세 오류면 안내 후 메뉴로
12. ▲ 최종 지문 표시 (기존 1번 자리에서 여기로 이동. §6)
13. 저장 확인
14. finalize → saveSuite. approval.cases 를 함께 쓴다
15. cassette.flush()
16. 커버리지 보고
```

12번이 이동하는 이유는 9~10 이 명세를 바꾸기 때문이다. 근거는 §6 이다.

## 4. 입력값 교정

### 4.1 단계 구조

케이스 하나에 대해 최대 세 번 실행한다.

| 회차 | 값의 출처 | 실패하면 |
|---|---|---|
| 1 | `synthesizeValue` 합성값 (기존) | 2회차로 |
| 2 | AI 제안. 근거가 없으면 사람 입력 | 3회차로 |
| 3 | 사람 입력 | 분류 화면(§8.3)으로 |

2회차에서 AI 제안을 쓴 경우에만 3회차가 있다. 2회차가 이미 사람 입력이었으면 3회차를 하지
않고 바로 분류로 간다. **같은 사람에게 같은 질문을 두 번 하지 않는다.**

상한이 2회인 이유는 세 번 틀렸으면 값 문제가 아닐 가능성이 크기 때문이다. 통과할 때까지 값을
흔들면 억지로 만든 통과가 되고, 그런 케이스는 회귀 테스트로서 가치가 없다.

### 4.2 교정 대상 판별 (전량)

실패한 케이스가 아래를 **모두** 만족할 때만 교정 대상이다.

1. `operation.type === "callTool"` 이다. `listTools` 케이스에는 입력이 없다.
2. `operation.input` 의 키가 하나 이상이다.
3. 케이스의 `origin` 이 `schemaBaseline` 또는 `ai` 다. `user` 는 사람이 직접 쓴 값이므로
   도구가 고치지 않는다.
4. **위반 케이스가 아니다.** ADR-0022 가 만드는 케이스는 입력을 일부러 어긋나게 만든 것이라
   고치면 케이스의 목적이 사라진다. 판별은 `isError` 단언의 `expected` 로 한다.
   `expected === true` 인 케이스는 교정하지 않는다.
5. 실패 사유가 `isError` 단언이다. 즉 **정상 응답을 기대했는데 오류 응답을 받았다.**
   본문 스키마 불일치(`bodyMatchesSchema`)는 교정 대상이 아니다. 그것은 응답의 모양 문제이고
   입력값을 바꿔도 안 바뀐다.

다섯 중 하나라도 어긋나면 교정하지 않고 곧바로 분류 화면으로 보낸다.

### 4.3 AI 제안의 권한 경계 (전량)

AI 는 **값 후보만 낸다.** 판정은 실제 서버가 한다.

허용되는 변경은 하나다.

- 교정 대상 케이스의 `operation.input` 안의 **값**

금지되는 변경 전량. 하나라도 있으면 **제안 전체를 폐기하고** 사람 입력으로 넘어간다.

- `operation.input` 의 키 추가·삭제
- `operation.tool` 변경
- `assertions` 의 어떤 변경이든
- `name`·`id`·`timeoutMs` 등 케이스 메타데이터
- 케이스 추가·삭제
- 교정 대상이 아닌 케이스의 어떤 변경이든
- 케이스 밖의 스위트 메타데이터(`id`·`name`·`schemaVersion`·`defaultTimeoutMs`·`approval`)

기대값 변경을 막는 것이 이 절의 핵심이다. 뚫리면 AI 가 서버에 맞춰 단언을 무력화하는 경로가
열리고, "서버가 틀렸을 가능성" 이 그 순간 사라진다. 게이트의 존재 이유가 없어진다.

### 4.4 AI 제안 요청

기존 authoring provider 경로를 그대로 쓴다. 새 전송 규격을 만들지 않는다.

- `prepareAuthoringRequest({ mode: "revise", instruction, baseline, candidate, tools, ... })`
- `dispatchAuthoringRequest`
- 돌아온 candidate 를 §4.3 으로 검사한 뒤 통과분만 쓴다

`mode` 에 값을 추가하지 않는 이유는 `AuthoringRequestMode` 가 `generate` 의 공개 타입이고,
교정 요청이 `revise` 와 구조적으로 같기 때문이다. 다른 것은 `instruction` 뿐이다.

`instruction` 에 담는 것 전량.

```
시험 실행에서 아래 케이스가 실패했습니다. 입력값만 고쳐 주세요.
단언과 케이스 구조는 바꾸지 마세요.

케이스: <case.name> (id: <case.id>)
툴: <tool>
보낸 입력: <operation.input 을 canonicalJson 으로>
서버 응답: <오류 본문>
```

**서버 응답 본문이 외부 provider 로 나간다.** 이것이 이 요청의 유일한 새 노출이다. ADR-0008 이
정한 redaction 규칙을 그대로 적용한다. `prepareAuthoringRequest` 의 `redaction` 옵션에 승인
화면과 같은 값을 넘긴다. redaction 후 본문이 비면 요청을 보내지 않고 사람 입력으로 간다.
보낼 근거가 없기 때문이다.

provider 가 없으면(`--provider` 미지정) 이 단계를 건너뛰고 사람 입력으로 간다. AI 제안은
선택이지 전제가 아니다.

### 4.5 사람 입력

교정 대상 케이스의 `operation.input` 키마다 값을 받는다. 현재 값을 기본값으로 보여준다.

- 엔터만 누르면 현재 값을 유지한다.
- 입력한 문자열은 JSON 으로 파싱을 **시도**하고, 실패하면 문자열 그대로 쓴다.
  `서울` 은 문자열, `42` 는 숫자, `{"a":1}` 은 객체가 된다.
- 파싱 결과가 그 필드의 스키마 타입과 안 맞으면 다시 묻는다. 스키마는 `tools` 선언에 있다.
- 모든 필드를 그대로 두면(전부 엔터) 교정을 포기한 것으로 보고 분류 화면으로 간다.
  같은 값으로 다시 실행하면 결과가 같기 때문이다.

### 4.6 같은 값의 재사용

`(tool, 필드경로)` 를 키로 이번 검토 세션 안에서 캐시한다.

`get_weather` 케이스가 다섯 개면 전부 `city` 로 실패한다. 첫 케이스에서 받은 값을 나머지
네 개에 자동 적용하고, 그 케이스들은 묻지 않고 바로 재실행한다. 안 하면 같은 질문을 다섯 번
받는다.

캐시는 저장하지 않는다. 검토 세션이 끝나면 사라진다.

### 4.7 값 되돌리기

3회차까지 실패하면 그 케이스의 `operation.input` 을 **1회차 값(합성값)으로 되돌린다.**

반영 규칙이 "통과한 것만" 이기 때문이다. 실패한 값을 명세에 남기면 다음 실행에서 무엇을
시도했었는지 헷갈리고, 그 값이 합성값보다 낫다는 근거도 없다.

단 **시도 이력은 분류 화면에 보여준다.** 사용자가 `m` 을 고르고 `edit` 으로 들어갈 때 방금
손으로 넣은 값을 또 넣지 않게 하기 위해서다.

## 5. 명세 반영

### 5.1 기존 경로를 쓴다

교정으로 통과한 값은 후보 명세에 즉시 반영한다. 반영은 `cli` 가 직접 객체를 고치지 않고
`generate` 의 기존 3단 경로를 그대로 탄다.

```
reviewLocalAuthoringCandidate({ session, candidate: <교정된 suite 전체>, tools })
  → createAuthoringDiff({ session, candidate })
  → applyAuthoringChanges({ session, preview, selectedChangeIds: <전량>, approval })
```

`edit` 메뉴가 이미 쓰는 경로다. 이렇게 하면 revision 증가, provenance 갱신, 지문 재계산이
`generate` 안에서 한 번에 일어난다. `cli` 가 `TestSuiteSpec` 을 직접 조립해 넣으면 그 세 가지가
갈린다.

### 5.2 provenance

교정된 케이스의 `origin` 은 **`user`** 가 된다. 로컬 편집 경로를 타기 때문이다.

AI 가 값을 제안한 경우도 `user` 다. 사람이 그 값을 눈으로 보고 엔터를 눌렀기 때문이고,
`--provider` 없이도 같은 결과에 도달할 수 있기 때문이다. `ai` 로 표시하면 "AI 가 만든 케이스"
와 "AI 가 값을 제안한 케이스" 가 같은 값이 되어 구분이 사라진다.

### 5.3 반영 시점

케이스마다 즉시 반영하지 않고 **교정 단계 전체가 끝난 뒤 한 번에** 반영한다. 케이스마다
`applyAuthoringChanges` 를 부르면 revision 이 교정 수만큼 늘고 지문도 그만큼 다시 계산된다.
사용자가 볼 값은 마지막 하나뿐이다.

### 5.4 반영 결과 표시

저장 확인 직전에 무엇이 바뀌었는지 보여준다(§8.7). 지문이 바뀐 이유가 화면에 남아야 사용자가
나중에 diff 를 보고 놀라지 않는다.

## 6. 지문 표시 시점

### 6.1 지금의 문제

현재 저장 경로는 최종 지문을 **시험 실행 전에** 찍는다(`generate-command.ts` 의 `save` 분기
첫 줄). 교정이 명세를 바꾸면 그 지문은 더 이상 저장될 명세의 것이 아니다. 사용자는 A 를 보고
승인했는데 저장되는 것은 B 가 된다.

지문은 "내가 승인한 그 명세가 맞다" 를 증명하는 장치다(ADR-0017). 그 증명이 깨진다.

### 6.2 결정

**지문 표시를 시험 실행과 분류 뒤로 옮긴다.** §3 의 12번 자리다.

- 교정이 없었으면 지금과 같은 값이 찍힌다. 화면 순서만 바뀐다.
- 교정이 있었으면 교정이 반영된 지문이 찍힌다.
- 저장되는 `approval.fingerprint` 는 항상 화면에 찍힌 그 값이다.
- `approval.cases` 의 판정은 실제로 실행된 명세에 대한 것이다. 교정 후 재실행분이 반영된다.

### 6.3 교정된 케이스의 판정

교정으로 통과한 케이스는 `approval.cases` 에 `passed` 로 들어간다. 실제로 통과했기 때문이다.
"원래는 실패했었다" 는 파일에 남기지 않는다. 그것은 생성 과정의 사실이고 명세의 성질이 아니다.
승인 블록에 시각·환경을 안 넣기로 한 것과 같은 기준이다(기존 설계 §7.1).

## 7. 옵션

| 옵션 | 값 | 규칙 |
|---|---|---|
| `--no-repair` | 없음 | 한 번만. 교정 단계를 통째로 끈다. `--no-dry-run` 과 함께 쓰면 사용 오류 |

`--no-repair` 를 주면 실패가 곧바로 분류 화면으로 간다. 지금 동작과 같다.

AI 제안은 별도 옵션을 두지 않는다. `--provider` 가 있으면 쓰고 없으면 안 쓴다. 옵션을 하나 더
만들면 "제안은 받고 싶은데 케이스 생성은 안 받고 싶다" 는 조합까지 설명해야 하는데, 그 조합에
실사용 근거가 없다.

## 8. 화면 (전량)

문안을 바꾸지 마라. 기존 게이트 설계의 §8 을 잇는 번호다.

### 8.6 입력값 교정 (AI 제안이 있을 때)

```
  [1] get_weather가 오류 없이 응답한다
      isError  정상 응답을 기대했지만 오류 응답을 받았습니다.

      입력값이 거절된 것으로 보입니다. 서버 응답에서 값을 찾았습니다.
      city: [서울]
```

`[서울]` 이 기본값이다. 엔터면 그 값, 고쳐 쓰면 그 값이다.

### 8.6.1 입력값 교정 (근거가 없을 때)

```
  [1] get_weather가 오류 없이 응답한다
      isError  정상 응답을 기대했지만 오류 응답을 받았습니다.

      입력값이 거절된 것으로 보입니다. 서버 응답에 쓸 만한 값이 없어 직접 받습니다.
      city (string, 현재 "example"): 
```

### 8.6.2 재실행 결과

```
      ▸ 다시 실행 중... 1건
      ✓ 통과
```

실패하면 다음 회차로 간다. 마지막 회차도 실패하면 아래를 찍고 분류로 넘어간다.

```
      ✗ 여전히 실패합니다. 입력값 문제가 아닐 수 있습니다.
```

### 8.6.3 값 재사용 고지

같은 툴·같은 필드를 쓰는 다른 케이스에 값을 적용할 때 한 줄 찍는다.

```
      같은 값을 get_weather.city 를 쓰는 케이스 4건에 함께 적용합니다.
```

### 8.7 분류 화면의 시도 이력

교정을 시도했던 케이스가 분류 화면에 도달하면 이력을 함께 찍는다. 기존 §8.3 화면의 선택지
바로 위다.

```
  [1] get_weather가 오류 없이 응답한다
      입력값을 두 번 고쳐 봤지만 결과가 같습니다.
        city: "example" → 오류
        city: "서울"    → 오류

      [s] 서버 결함  명세가 옳다. 이 케이스를 회귀 테스트로 남긴다
      [m] 명세 오류  추측이 틀렸다. 저장 전에 고친다
      [?] 판단 보류  분류를 미룬다. 저장은 막힌다
      선택: 
```

교정을 아예 시도하지 않은 케이스(§4.2 를 못 만족)는 이력 줄이 없다. 기존 화면 그대로다.

### 8.8 반영 요약

저장 확인 직전에 찍는다. 교정이 0건이면 찍지 않는다.

```
  입력값 교정 2건이 명세에 반영되었습니다.
    get_weather.city: "example" → "서울"
    add_todo.title: "example" → "장보기"
```

## 9. 결정론성

- 교정은 **생성 시점에만** 돈다. 저장된 명세에는 확정된 값만 남고, 그 파일로 `test` 를 돌리는
  것은 지금과 똑같이 결정론적이다.
- AI 개입 흔적을 파일에 남기지 않는다. 남길 필요가 없고, 남기면 지문에 들어간다.
- `generate` 자체는 같은 서버·같은 선언으로 두 번 돌려도 결과가 다를 수 있다. `--provider` 를
  쓰는 순간 이미 그렇다. 새 성질이 아니지만 도움말에 적는다.
- 재실행은 케이스 하나만 대상으로 한다. 스위트 전량을 다시 돌리지 않는다. 앞서 통과한 케이스가
  상태 변화로 뒤집히는 것을 막기 위해서다.

## 10. 카세트·초기화 훅과의 상호작용

- **재시도는 새 카세트 키다.** 입력값이 다르므로 매칭 키가 달라진다(ADR-0003). 재시도 응답이
  새로 녹화되고, 실패했던 1회차 응답도 카세트에 남는다.
- **죽은 항목이 남는다.** 교정으로 명세가 바뀌면 1회차 키는 다시 조회되지 않는다. 동작에는
  지장이 없고 파일이 커진다. 정리는 `record` 패키지 소유라 이 설계의 비범위다(§13).
- **재시도 사이에 초기화하지 않는다.** `--reset-cmd` 는 시험 실행 맨 앞 1회다(ADR-0023).
  재시도마다 초기화하면 앞서 통과한 케이스의 상태까지 날아가 결과가 뒤집힌다.
- **호출 수가 늘어난다.** 케이스당 최대 3회다. §8.1 고지의 케이스 수가 실제 호출 수와 달라질
  수 있으므로, 고지에 한 줄을 더한다.

  ```
    실패한 케이스는 값을 고쳐 최대 2회까지 다시 호출합니다.
  ```

  `--no-repair` 면 이 줄을 찍지 않는다.

## 11. 신규 ADR 대상

### 11.1 교정 단계의 권한 경계

§4.3 과 §4.4 다. 다르게 갈 수 있었던 판단이 셋이다.

- AI 가 기대값까지 고치게 할 것인가. 허용하면 실패가 거의 사라지지만 게이트가 무력해진다.
- 재시도 상한을 2회로 둘 것인가, 통과까지 반복할 것인가.
- 서버 오류 응답을 외부 provider 에 보낼 것인가. 보내면 제안 품질이 오르고 노출이 는다.

### 11.2 지문 표시 시점 이동

§6 이다. ADR-0017 이 정한 "승인 지문" 의 의미에 영향이 있다. 사용자가 승인하는 대상이 시험
실행 **전** 명세에서 **후** 명세로 바뀐다. 되돌릴 수 있었던 선택은 "교정을 반영하지 않고
사용자에게 수동 편집을 요구한다" 였다.

## 12. 배제한 안

**생성 시점 사전 질문.** 스키마에 힌트가 없는 필드를 시험 실행 전에 미리 묻는 안이다. 두
가지로 배제했다.

1. **증거 없이 비용부터 받는다.** 툴 20개짜리 서버면 문자열 필드가 30개쯤 되는데 대부분은
   합성값으로 통과한다. 통과할 값까지 다 물으면 생성 자체가 벽이 된다.
2. **질문의 질이 낮다.** 사전 질문 시점에는 `사용 가능한 도시: 서울, 부산, 제주` 가 없다.
   사람도 `description` 만 보고 추측해야 한다. 질문을 실패 뒤로 미루면 화면에 근거가 이미 있다.

대신 잃는 것이 하나 있다. **잘못된 호출이 이미 나간 뒤에 묻는다는 것이다.** 상태를 바꾸는
툴이면 쓰레기 데이터가 남을 수 있다. 시험 실행 자체가 실제 호출이고 고지에 그렇게 적혀 있으며
`--reset-cmd` 가 뒷정리를 맡으므로 감수한다. 파괴적인 서버를 위한 사전 질문 모드는 후속으로
남긴다(§13).

## 13. 미해결과 후속

- **사전 질문 모드.** 파괴적인 서버용. §12 에서 배제했지만 실사용에서 요구가 오면 옵션으로
  되살린다.
- **카세트의 죽은 항목 정리.** §10. `record` 패키지 소유다.
- **본문 스키마 불일치의 교정.** §4.2 가 제외했다. 응답의 모양 문제는 입력값으로 안 고쳐지지만,
  "관찰된 응답으로 스키마를 갱신" 은 별개의 유용한 기능이다. 다만 그것은 서버가 옳다는 전제를
  깔기 때문에 이 게이트와 다른 판단이 필요하다.
- **`synthesizeValue` 자체 개선.** `description` 을 AI 에게 읽혀 값을 고르는 안. 서버를 안
  부르고 처리되지만 근거가 추측이라 이 설계의 교정과 겹친다. 교정 단계의 실사용 빈도를 본 뒤
  판단한다.
