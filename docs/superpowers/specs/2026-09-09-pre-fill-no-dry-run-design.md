## 1. 배경

`--no-dry-run` 은 "승인 전 시험 실행을 건너뛴다" 는 옵션이다. 파서는 이 옵션을 **툴을 실행하지
않는 경로**로 취급한다. `--reset-cmd` 와 함께 주면 "시험 실행을 끄면 서버를 접촉하지 않는다.
초기화는 접촉을 전제한 옵션" 이라며 사용 오류로 돌려주고(`packages/cli/src/generate-command.ts:496-500`),
저장 직전 화면도 "케이스 N건이 실제 서버에서 확인되지 않은 채 저장됩니다" 라고 말한다
(`generate-command.ts:1399-1407`).

정확히는 **`callTool` 이 0회**다. `listTools` 는 이 경로에서도 부른다. 툴 선언을 읽지 않으면
baseline 자체를 만들 수 없기 때문이다. 위 주석의 "접촉하지 않는다" 는 그 구분을 생략한 표현이고,
사용자가 이 옵션에서 기대하는 것도 선언 조회가 아니라 **툴 실행 0회**다.

그런데 AI 사전보완은 이 옵션을 보지 않는다. `runPreFill`(`generate-command.ts:2034-2100`)은
검토 세션을 만들기 전에 한 번 돌고(`generate-command.ts:2187`), 전송 확인을 받은 뒤
`applyPreFill` 에 실제 `client` 를 넘긴다(`generate-command.ts:2080-2084`). `applyPreFill`
(`packages/cli/src/pre-fill-wiring.ts:132-133`)은 제안이 있는 케이스를 baseline 값 한 벌과 AI 값
한 벌로 **실제 서버에 각각 한 번씩** 실행해 채택을 정한다. 이것이 사전보완 설계서 §4.4 의 규칙
"채택은 실행이 정한다" 의 구현이고, 그 규칙 자체는 옳다. 문제는 `input.dryRun` 을 확인하는 곳이
저장 메뉴(`generate-command.ts:1399`) 하나뿐이라, 사전보완 회차의 실행이 그 앞에서 이미 끝난다는
점이다.

이슈의 기록이 이것을 보여준다. `--no-dry-run` 에 검토 메뉴 취소까지 했는데 `mutate` 가
`{"x":"example"}` 과 `{"x":"real"}` 로 두 번 호출됐다. 상태를 바꾸는 서버(notion · git · filesystem)
에서는 사용자가 생략했다고 믿은 실행의 부작용이 남는다. 데모 순서 문서가 이것을 A-1 로 올린
이유다.

같은 자리에 둘째 결함이 있다. 사전보완의 전송 확인 화면(`showPreFillRequest`,
`generate-command.ts:1889-1910`)은 provider 에 **무엇을 보내는지**만 적고, 제안을 받으면 그 뒤에
**서버를 실제로 부른다**는 사실을 적지 않는다. 사용자가 실제 호출을 허락하는 지점은 저장 메뉴의
"계속할까요?" 라고 알고 있는데, 실제 첫 호출은 그보다 앞의 전송 확인에서 일어난다. 그래서 검토
메뉴에서 취소해도 늦다. 이 화면이 사실을 말해야 취소가 의미를 가진다.

이슈 본문과 현재 코드는 일치한다. 검토 기준 커밋 `c0a1934` 와 현재 HEAD 사이에 두 함수의 구조
변경은 없고 줄 번호만 조금 밀렸다.

## 2. 목표 / 비범위 / 완료 조건

### 목표

1. `--no-dry-run` 에서는 사전보완을 포함해 `callTool` 이 0회다. `listTools` 만 부른다.
2. 사전보완이 실제 서버를 부르기 전에, 그 사실과 건수를 사용자가 승인하는 화면에 적는다.
3. 기본 경로(시험 실행 켜짐)의 채택 규칙과 화면은 바꾸지 않는다. 기존 테스트가 그대로 통과한다.

### 비범위

- **사전보완 실행을 저장 시점의 시험 실행으로 옮기는 재구성.** 검토 메뉴에서 취소하면 호출도 없게
  만드는 가장 깨끗한 해법이지만, 세션의 승인 초안을 시험 실행 뒤에 다시 쓰는 구조 변경이라 한 주
  범위를 넘는다. `--reset-cmd` 가 사전보완 앞에서는 돌지 않는 문제(#399)와 같은 뿌리이므로 #399
  에서 함께 다룬다.
- **실행 없이 AI 제안을 채택하는 모드.** §3.2 에서 기각한다.
- **`--no-dry-run` 과 `--provider` 의 조합을 사용 오류로 만드는 것.** provider 는 검토 메뉴의
  `revise` 에도 쓰이므로 조합 자체는 유효하다.
- `--reset-cmd` · `--no-repair` 와의 조합 규칙. 이미 파서가 정하고 테스트가 있다.

### 완료 조건

구현 PR 의 통과 기준이다. 각 항목은 구현 계획의 태스크 하나 또는 통합 게이트에 대응한다.

1. `generate --no-dry-run --provider codex --model m` 을 채울 빈틈이 있는 툴에 주입 client 로
   실행하면 `client.callTool` 호출이 0회, provider `preFill` 호출이 0회, 종료 코드 0, baseline 의
   케이스가 하나도 빠지지 않고 검토 세션에 들어간다. 검토 메뉴에서 취소해도 같다.
2. 1 의 화면에 건너뜀 고지 한 줄과 해결 수단(`--no-dry-run` 없이 실행)이 있고, 전송 확인 화면
   (`AI 사전보완 요청`)은 나오지 않는다.
3. `--no-dry-run` 인데 채울 빈틈이 없는 툴이면 건너뜀 고지를 찍지 않는다.
4. `--no-dry-run --baseline-only` 에서도 `callTool` 이 0회다.
5. 시험 실행이 켜진 기본 경로에서 전송 확인 화면이 "제안이 돌아온 케이스마다 baseline 값과 제안
   값으로 실제 서버를 각각 한 번씩 부릅니다. 위 케이스 N개가 그 상한입니다" 를 **`confirm` 이
   호출되기 전에** 출력한다. N 을 실제 실행 수로 적지 않는다.
6. 전송 확인을 거절하면 `callTool` 이 0회다. provider 가 던져도 `callTool` 이 0회다.
7. `mcpeak help generate` 의 `--no-dry-run` 설명이 AI 사전보완도 건너뛴다고 말한다. 루트 README 의
   `generate` 절도 같은 사실을 한 문장으로 적는다.
8. ADR 초안(§5)이 `docs/adr/` 에 있고 색인에 올라 있다. `.changeset/` 에 `@mcpeak/cli` patch 가
   있다.
9. 기존 테스트 `baseline 이 실패하고 제안이 통과하면 AI 값을 쓰고 출처를 남긴다` 가 그대로
   통과한다. 즉 기본 경로의 실행과 채택은 바뀌지 않는다.
10. `pnpm typecheck --force` 가 `Cached: 0 cached` 로, `pnpm test` · `pnpm biome ci .` · `pnpm build
    --force` 뒤 `pnpm --filter @mcpeak/cli test:e2e` 가 통과한다.

## 3. 결정

### 3.1 `--no-dry-run` 이면 사전보완 회차를 통째로 건너뛴다

`runPreFill` 에서 provider 유무와 `preparePreFillRequest` 의 대상 판정을 거친 **뒤**, 전송 확인
화면을 보이기 **전**에 `input.dryRun` 을 본다. 꺼져 있으면 고지 한 줄을 쓰고 `skip`(baseline 그대로,
채택 없음)을 돌려준다. provider 도 부르지 않는다.

검사 위치를 대상 판정 뒤에 두는 이유는 고지의 소음이다. 채울 빈틈이 없는 서버에서는 사전보완이
원래 안 도는데 "건너뜁니다" 라고 하면 거짓이 된다(§2 완료 조건 3). 대상 판정
`preparePreFillRequest` 는 결정론적이고 서버를 부르지 않으므로 그 앞에 두어도 잃는 것이 없다.

고지 문안. 사용자가 할 수 있는 일을 같은 줄에 적는다.

```
▸ 시험 실행이 꺼져 있어(--no-dry-run) AI 사전보완을 건너뜁니다. 제안 값의 채택은 실제 서버
  실행이 정하는데 그 실행이 없습니다. baseline 값으로 진행합니다.
  AI 사전보완이 필요하면 --no-dry-run 없이 실행하세요.
```

### 3.2 실행 없이 채택하는 모드는 만들지 않는다

다르게 갈 수 있었다. `--no-dry-run` 에서도 provider 를 부르고, 실행 판정 없이 제안 값을 그대로
후보로 넣는 안이다. 파일이 어차피 미검증(`approval.cases` 없음)이니 AI 추측이 `"example"` 자리값
보다 낫다는 논리다.

기각한다. 사전보완 설계서 §4.4 의 실측(`server-filesystem` 에서 baseline 6/14 통과, AI 1/14 통과)이
보여주듯 AI 값이 baseline 값보다 나쁜 툴이 실제로 있고, 실행 없이는 어느 쪽인지 알 수 없다. 규칙
"둘 다 모르면 baseline" 은 결정론적이고 재현 가능한 쪽을 기본값으로 둔 의도적 선택이고, 실행이
없는 경우는 "둘 다 모른다" 의 극단이다. 또 `--no-dry-run` 은 사용자가 "확인되지 않은 채 저장"
을 명시적으로 받아들인 경로라, 거기서 AI 가 값을 바꾸면 무엇이 바뀌었는지 사용자가 볼 기회가
검토 메뉴의 diff 뿐이다. 이 결정은 ADR 대상이다(§5).

### 3.3 전송 확인 화면이 실제 실행을 고지한다

`showPreFillRequest` 의 "받는 것:" 줄 다음에 한 줄을 더한다.

```
채택 판정: 제안이 돌아온 케이스마다 baseline 값과 제안 값으로 실제 서버를 각각 한 번씩
  부릅니다. 위 케이스 N개가 그 상한입니다. 상태를 바꾸는 툴이면 그 부작용이 남습니다.
```

**N 을 실제 실행 수로 적지 않는다.** 화면이 뜨는 시점에는 아직 제안을 받지 않았고, `applyPreFill`
(`pre-fill-wiring.ts:117-128`)이 실제로 실행하는 것은 제안이 돌아온 케이스 중 `callTool` 이고
입력이 객체인 것뿐이다. 요청 케이스 수는 그 상한이다. 확정 수처럼 적으면 상태를 바꾸는 서버에서
사용자가 부작용 범위를 과대평가하고, 그 화면을 한 번 불신하면 다음부터 읽지 않는다. `request.cases.length`
는 같은 화면 `대상:` 줄의 값이므로 "위 케이스" 로 가리킨다.

전송 확인 질문 `이 요청을 전송할까요?` 는 바꾸지 않는다. 기존 테스트가 이 문구에 걸려 있고,
바꿔서 얻는 것이 없다. 사용자가 여기서 `n` 을 고르면 provider 도 서버도 부르지 않는다는 기존
동작이 그대로 "실제 호출을 막는 지점" 이 된다.

### 3.4 검토 메뉴 취소 뒤의 호출은 이번에 막지 않는다

시험 실행이 켜진 기본 경로에서, 전송을 승인하고 제안을 받았다면 검토 메뉴에 닿기 전에 대상
케이스가 이미 실행된다. 이 순서는 유지한다. §3.3 이 그 사실을 승인 화면에 적으므로 사용자는
전송 확인에서 거절할 수 있다. 순서를 바꾸는 재구성은 비범위(#399)다.

## 5. ADR 초안

`docs/adr/0089-시험-실행이-꺼지면-사전보완도-건너뛴다.md`. 배경은 §1, 선택지는 (a) 통째로
건너뜀 · (b) 실행 없이 제안 채택 · (c) `--no-dry-run` + `--provider` 조합을 사용 오류로, 결정은
(a), 이유는 §3.2, 결과는 "`--no-dry-run` 에서 provider 는 검토 메뉴의 `revise` 에만 쓰인다" 와
"사전보완 실행 시점을 옮기는 논의는 #399" 두 줄. 번호는 작성 시점에 색인의 최대값 + 1 로 다시
확인한다(ADR README 가 번호 충돌 위험을 적어 두었다).
